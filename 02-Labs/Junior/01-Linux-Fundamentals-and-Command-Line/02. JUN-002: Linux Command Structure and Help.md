- **Level:** Junior
- **Difficulty:** 1/5
- **Estimated time:** 40–60 minutes
- **Environment:** One Ubuntu Server 24.04 LTS system or VM
- **Privileges:** Standard user account

---

## Lab Mission

In the previous lab, you learned how to move around a Linux system with `pwd`, `ls`, and `cd`.

Now you need to understand what you are actually typing when you enter a command.

Linux has thousands of commands, and trying to memorize all of them is not a sensible way to learn the operating system. A much more useful skill is knowing how commands are structured and how to find reliable information when you do not remember exactly how something works.

In this lab, you will learn how to recognize the command, options, and arguments in a command line. You will also use built-in help, manual pages, `whatis`, `apropos`, and a few other tools to investigate commands for yourself.

The goal is simple: when you encounter an unfamiliar command later in Linux World, you should know how to begin understanding it.

---

## What you will learn

By the end of this lab, you should be able to:

* Recognize the basic structure of a Linux command.
* Distinguish between a command, an option, and an argument.
* Recognize short and long options.
* Understand that command syntax is not identical for every Linux command.
* Use `--help` when a command supports it.
* Open and navigate manual pages with `man`.
* Search inside a manual page.
* Use `whatis` for short command descriptions.
* Use `apropos` to search for commands by topic.
* Use `type` to investigate how the shell interprets a command name.
* Use `command -V` as another way to inspect a command.
* Recognize when a command is not installed or cannot be found.
* Use documentation instead of guessing command syntax.

# 1. The basic shape of a Linux command

A simple command can contain several parts.

Consider:

```bash
ls -l /etc
```

You can read it as:

```text
ls        -l        /etc
│         │          │
command   option     argument
```

The **command** tells the system what program or operation you want to invoke.

Here:

```text
ls
```

is the command.

The **option** changes how the command behaves.

Here:

```text
-l
```

asks `ls` to use its long listing format.

The **argument** tells the command what to operate on.

Here:

```text
/etc
```

is the directory being listed.

So:

```bash
ls -l /etc
```

can be read naturally as:

> Run `ls`, use the long listing format, and operate on `/etc`.

Understanding commands this way is much more useful than memorizing entire command lines.

---

# 2. Commands do not always need options or arguments

A command can be perfectly valid without either.

You already used:

```bash
pwd
```

in JUN-001.

There is only a command here.

You also used:

```bash
ls
```

which lists the current directory when no other location is supplied.

Now compare:

```bash
ls /etc
```

Here:

```text
ls       /etc
│         │
command   argument
```

There is no option.

Now compare that with:

```bash
ls -l
```

Here:

```text
ls       -l
│         │
command   option
```

Finally:

```bash
ls -l /etc
```

contains all three:

```text
command + option + argument
```

This pattern appears constantly in Linux.

# 4. Short options

Many Linux commands support short options beginning with a single hyphen:

```text
-
```

Examples include:

```bash
ls -l
ls -a
```

You have already used both.

Some commands allow compatible short options to be combined.

For example:

```bash
ls -la
```

is commonly equivalent to:

```bash
ls -l -a
```

Try both:

```bash
ls -l -a
```

and:

```bash
ls -la
```

Compare the results.

You should see the same style of listing: long-format information including hidden entries.

You may also encounter:

```bash
ls -al
```

For these particular `ls` options, that works as well.

Do not turn this into a universal rule that every short option for every command can always be combined in any order. Command-line interfaces differ.

When you are unsure, check the command's documentation.

That is one of the main skills this lab is designed to teach.

---

# 5. Long options

Many modern Linux commands also provide long options.

Long options commonly begin with:

```text
--
```

For example:

```bash
ls --all
```

For GNU `ls`, `--all` corresponds to the short option:

```bash
ls -a
```

Try both:

```bash
ls -a
```

and:

```bash
ls --all
```

You should see equivalent behavior.

Another example is:

```bash
ls --help
```

Do not run it yet. We will use it properly in a moment.

A useful visual distinction is:

```text
-a       short option
--all    long option
```

Long options can be easier to understand when you are still learning because their names are often more descriptive.

---

# 6. Some options need their own arguments

Not every option is simply an on/off switch.

Some options require additional information.

A safe example is `head`, a command that displays the beginning of input or a file.

Ubuntu normally includes a file called:

```text
/etc/services
```

First, make sure it exists:

```bash
ls /etc/services
```

Now run:

```bash
head -n 5 /etc/services
```

You should see the first five lines of the file.

Break the command down:

```text
head      -n      5      /etc/services
│          │      │           │
command   option  value      file argument
```

Here, `-n` needs a value telling `head` how many lines to display.

The value is:

```text
5
```

The file being read is:

```text
/etc/services
```

You may also see the long form:

```bash
head --lines=5 /etc/services
```

The exact syntax an option accepts is something you should confirm from that command's documentation rather than assume.

---

# 7. Commands can accept more than one argument

Some commands can operate on multiple arguments.

For example:

```bash
ls /etc /var
```

Here the command is:

```text
ls
```

and the arguments are:

```text
/etc
/var
```

Run:

```bash
ls /etc /var
```

`ls` will list both locations.

The general idea is that a command line may contain:

```text
command
command argument
command option
command option argument
command option option argument
command argument argument
```

and other variations.

There is no single arrangement that describes every Linux command.

That is why documentation matters.

---

# 8. Spaces matter

The shell uses spaces to help separate parts of a command line.

Compare:

```bash
ls -l /etc
```

with:

```text
ls-l /etc
```

These are not the same.

Do not run the second one yet.

In:

```bash
ls -l /etc
```

the shell can distinguish:

```text
ls
-l
/etc
```

If you type:

```bash
ls-l /etc
```

the shell interprets `ls-l` as the command name.

Try it:

```bash
ls-l /etc
```

On a typical Ubuntu installation, you should receive an error indicating that `ls-l` could not be found.

The exact wording may vary.

The important point is that Linux did not automatically interpret `ls-l` as `ls -l`.

Command syntax matters.

---

# 9. Case matters too

Linux command names are case-sensitive.

You have been using:

```bash
ls
```

Now try:

```bash
LS
```

On a normal Ubuntu installation, this should fail unless something unusual in your environment defines a command named `LS`.

The shell does not normally treat:

```text
ls
```

and:

```text
LS
```

as the same command.

This applies to many other parts of Linux as well, including filenames.

# 10. Stop guessing and ask the command

You will regularly forget an option.

That is normal.

You may remember the command but forget exactly how an option works. Or you may find a command in somebody else's script and have no idea what it does.

Your first instinct should not be to guess.

Many commands provide help directly.

Try:

```bash
ls --help
```

This produces a fairly large amount of information.

Near the beginning, you should see usage information describing how `ls` can be invoked.

Farther down, you will see available options and descriptions.

You do not need to memorize the page.

Instead, look for options you already know:

```text
-a
-l
```

Then find:

```text
--all
```

The point is to connect commands you have already used with the command's own help information.

---

# 11. `--help` is common, not universal

This distinction matters.

Many GNU command-line programs support:

```text
--help
```

but you should not assume every command, shell builtin, script, or application in Linux behaves identically.

If:

```bash
some-command --help
```

does not give useful help, that does not automatically mean the command has no documentation.

There may be a manual page, a different help mechanism, project documentation, or shell-specific help.

Linux administration gets much easier when you stop expecting every command to have exactly the same interface.

---

# 12. Manual pages

One of the most important Linux documentation tools is:

```bash
man
```

`man` is short for **manual**.

Try:

```bash
man ls
```

If the manual system is installed, a documentation page for `ls` should open.

You are no longer looking at ordinary terminal output. You are viewing documentation through a pager.

A manual page commonly contains sections such as:

```text
NAME
SYNOPSIS
DESCRIPTION
OPTIONS
AUTHOR
COPYRIGHT
SEE ALSO
```

The exact sections depend on the page.

For now, concentrate on three of them.

### NAME

This gives you the command name and a short description.

### SYNOPSIS

This shows the general way the command can be used.

### DESCRIPTION

This explains what the command does in more detail.

---

# 13. Read a synopsis without being intimidated by it

The synopsis of a manual page may contain notation that looks unfamiliar.

For example, you may encounter something conceptually similar to:

```text
command [OPTION]... [FILE]...
```

Square brackets commonly indicate something optional in command documentation.

The dots indicate that more than one may be accepted.

You are not expected to understand every documentation convention immediately.

The important thing at this stage is recognizing that the synopsis gives you a compact description of valid command usage.

Do not type brackets from documentation literally unless the documentation specifically tells you to.

If documentation shows:

```text
[OPTION]
```

that usually means "an optional value belongs here," not "type the characters `[OPTION]`."

---

# 14. Move around a manual page

While viewing:

```bash
man ls
```

try these keys:

```text
Space      move forward
b          move backward
/          search
n          next search result
q          quit
```

For example, while inside the manual page, type:

```text
/--all
```

and press Enter.

The pager should search for `--all`.

Press:

```text
n
```

to move to the next matching occurrence if there is one.

When you are finished, press:

```text
q
```

to return to your shell.

This is much more useful than scrolling through a large manual page from beginning to end every time you need one option.

# 16. Get a short description with `whatis`

Sometimes you do not need an entire manual page.

You just want a quick answer to:

**What is this command?**

Try:

```bash
whatis ls
```

You may receive output similar to:

```text
ls (1) - list directory contents
```

Now try:

```bash
whatis pwd
```

and:

```bash
whatis head
```

The wording comes from the manual-page database available on your system.

If `whatis` cannot find an entry, your local manual database or documentation installation may differ.

The important difference is:

```text
man      detailed manual page
whatis   short description
```

---

# 17. Search by topic with `apropos`

Sometimes you have the opposite problem.

You know what you want to accomplish, but you do not know the command name.

That is where:

```bash
apropos
```

can help.

Try:

```bash
apropos directory
```

The result may be long because many manual-page descriptions contain the word `directory`.

Try something more specific:

```bash
apropos "list directory"
```

Results depend on the manual database installed on your system.

The idea is more important than getting identical output:

```text
whatis   → I know the command name. Tell me what it is.

apropos  → I know the topic. Help me find relevant commands.
```

That distinction is useful when you are exploring Linux without already knowing the answer.

# 18. What exactly is the shell running?

You type:

```bash
ls
```

but how does the shell interpret that name?

A useful command for investigating this is:

```bash
type
```

Run:

```bash
type ls
```

Your output may show that `ls` resolves to an executable path, or your environment may have an alias or other definition for it.

Now try:

```bash
type pwd
```

You may discover something interesting.

`pwd` can be provided as a shell builtin in Bash.

Try:

```bash
type cd
```

You should see that `cd` is handled by the shell itself.

This introduces an important idea:

> Not every command you type is necessarily the same kind of thing.

Some names resolve to executable programs.

Some are shell builtins.

Some environments define aliases or functions.

You do not need to explore all of those categories yet. The important skill is knowing that you can ask the shell.

Bash also provides:

```bash
command -V
```

Try:

```bash
command -V ls
```

Then:

```bash
command -V cd
```

And:

```bash
command -V pwd
```

Compare the information with what you saw from `type`.

This is another useful way to investigate how a command name will be interpreted.

You do not need to choose a favorite yet. Learn what the tools are telling you.

# 20. Finding executable paths

You may also encounter:

```bash
which
```

For example:

```bash
which ls
```

On a typical Ubuntu system, you may receive a path such as:

```text
/usr/bin/ls
```

However, `which` is primarily useful for locating an executable found through your command search path. It does not give you the same complete picture as shell-aware tools such as:

```bash
type
```

or:

```bash
command -V
```

For example, compare:

```bash
which cd
```

with:

```bash
type cd
```

Because `cd` is normally a shell builtin, `which` may not provide the information you actually need.

A useful habit is:

> If you want to know how your shell will interpret a command name, start with `type` or `command -V`.

You will learn more about command resolution and `PATH` in JUN-024.

You just discovered that commands such as `cd` can be shell builtins.

Bash provides a built-in help system for these.

Try:

```bash
help cd
```

You should receive information about Bash's `cd` command.

Now try:

```bash
help pwd
```

This gives you another documentation route:

```text
program documentation     --help
manual documentation      man
Bash builtin help         help
```

You do not need to use all three every time.

The point is knowing that Linux and the shell already contain documentation you can consult.

# 23. When the shell cannot find a command

Deliberately enter a command that should not exist:

```bash
veriqta-example-command
```

On a typical Bash environment, you should receive an error indicating that the command could not be found.

The exact message can vary.

What does that tell you?

It does **not** tell you:

* that Linux is broken,
* that you need `sudo`,
* or that you should start changing system configuration.

It tells you that the shell could not resolve the command name in its current environment.

A misspelling can produce the same kind of problem.

For example:

```bash
pwdd
```

should fail on a normal system because the command is:

```bash
pwd
```

not:

```text
pwdd
```

Always check the simplest explanation first.

# 24. Investigate instead of guessing

Suppose you see this command in documentation:

```bash
ls -h
```

You do not remember what `-h` means.

There are several better responses than guessing.

You could use:

```bash
ls --help
```

Or:

```bash
man ls
```

and search for:

```text
-h
```

You could also search for the long option:

```text
--human-readable
```

Now you can determine what the option actually does from the command's documentation.

This is a small example of a much larger engineering habit:

**Use evidence before assumptions.**

Later, the evidence may come from logs, metrics, process state, network connections, configuration, or system events.

At this stage, the evidence is simply documentation.

The habit is the same.

# 25. Read commands before running them

Consider:

```bash
head -n 3 /etc/services
```

Before running it, break it apart.

What is the command?

```text
head
```

What is the option?

```text
-n
```

What value belongs to that option?

```text
3
```

What file is being supplied?

```text
/etc/services
```

Now run it:

```bash
head -n 3 /etc/services
```

You should see the first three lines of the file.

Do the same mental exercise with:

```bash
ls -la /etc
```

You should be able to identify the command, the options, and the argument before pressing Enter.

This habit becomes increasingly valuable when command lines become longer.

# 26. A controlled failure

Now deliberately make a syntax mistake.

Run:

```bash
ls --this-option-does-not-exist
```

`ls` should report that the option is unrecognized or invalid.

The exact wording depends on the implementation and environment.

Read the error.

Do not ignore it.

Now check the actual options:

```bash
ls --help
```

Or:

```bash
man ls
```

The failure happened because you supplied an option that `ls` does not recognize.

The correct response is not to add `sudo`.

The correct response is to verify the syntax.

---

## Engineer Note

Many beginner command-line problems are treated as permission problems when they are actually syntax problems.

If a command fails, read the error before deciding what kind of problem you have.

Compare:

```text
command not found
```

with:

```text
unrecognized option
```

and:

```text
No such file or directory
```

Those messages describe different failures.

Treating every failure the same way makes troubleshooting harder.

Earlier you used:

```bash

```

Now try:

```bash

```

The command should complain because `-n` expects additional information.

Again, exact output can vary.

The useful question is:

**What information is missing?**

Consult:

```bash
head --help
```

Find the description of:

```text
-n
```

The documentation shows that the option expects a number.

Now run a complete command:

```bash

```

The problem was not the `head` command itself.

The command line was incomplete.

# 28. Build a help workflow

When you encounter a command you do not understand, you now have several ways to investigate it.

A practical workflow is:

### First: identify what the command name represents

```bash
type COMMAND
```

or:

```bash
command -V COMMAND
```

### Then try quick help when appropriate

```bash
COMMAND --help
```

### For a Bash builtin

```bash
help COMMAND
```

### For detailed system documentation

```bash
man COMMAND
```

### If you know the command but want a short description

```bash
whatis COMMAND
```

### If you know the task but not the command

```bash
apropos KEYWORD
```

You will not always need every step.

Choose the tool that matches the question you are trying to answer.

### 6. What does `man` provide?

It opens the manual page for a command or other documented topic when the relevant manual entry is installed.

### 7. How can you search while viewing a manual page?

Press `/`, enter the search text, and press Enter. `n` can be used to move to the next match.

### 8. What does `whatis` help you discover?

It provides short descriptions from the manual-page database.

### 9. When would `apropos` be useful?

When you know the subject or task you are interested in but do not know the relevant command or manual-page name.

### 10. What does `type` help you determine?

It shows how the shell interprets a command name.

### 11. Why might `type cd` be more useful than `which cd`?

Because `cd` is normally a shell builtin, and `type` understands shell command types rather than only looking for an executable path.

### 12. What does an `unrecognized option` error suggest?

The command was found, but the option supplied is not accepted by that command.

### 13. Is `command not found` the same problem as an invalid option?

No. `command not found` means the shell could not resolve the command name. An invalid-option error means the command was found and started, but it did not accept the supplied option.

### 14. Why should you avoid guessing unfamiliar options?

Because command interfaces differ. Documentation allows you to verify the actual syntax and behavior before using the command.

# 36. Interview Practice

### What are the basic parts of a Linux command line?

A command line can contain a command, options that modify its behavior, option arguments or values where required, and other arguments representing the objects the command should operate on.

For example:

```bash
head -n 5 /etc/services
```

contains the `head` command, the `-n` option, the value `5`, and the `/etc/services` file argument.

### What is the difference between a short option and a long option?

Short options commonly use one hyphen and a short name:

```text
-a
```

Long options commonly use two hyphens and a descriptive name:

```text
--all
```

The exact option syntax depends on the command.

### How can you get help for a Linux command?

Depending on the command, useful sources include:

```bash
COMMAND --help
man COMMAND
help COMMAND
whatis COMMAND
```

Bash's `help` is particularly useful for shell builtins.

### What is the purpose of `apropos`?

It searches manual-page names and descriptions for a keyword or phrase, which can help when you know what you want to do but do not know the relevant command name.

### What is the difference between `type` and `which`?

`type` tells you how the shell interprets a command name and can identify things such as builtins and aliases as well as executable commands. `which` is generally concerned with locating an executable through the command search path and may not accurately describe every kind of shell command.

### Why is reading error output important?

Different errors point to different classes of problems. A missing command, invalid option, nonexistent path, and permission problem should not all be investigated in the same way.
