- **Level:** Junior  
- **Difficulty:** 2/5  
- **Estimated time:** 75–90 minutes  
- **Environment:** Ubuntu Server 24.04 LTS or a similar Linux system  
- **Privileges:** Standard user account  
- **Primary skills:** Reading, interpreting, testing and troubleshooting Linux file and directory permissions  
- **Prerequisites:** JUN-001 through JUN-006

---

## Lab Mission

Linux is a multi-user operating system.

That means the system needs rules for answering questions such as:

- Who can read this file?
- Who can modify it?
- Who can execute it?
- Who can enter this directory?
- Why can one user access something while another cannot?
- Why does a file exist but still return `Permission denied`?

Those rules begin with Linux permissions.

You have already seen output such as:

```text
-rw-r--r--
```

or:

```text
drwxr-xr-x
```

in earlier labs.

Until now, you were not expected to understand every character.

That changes here.

In this lab, you will learn how to read the permission information Linux exposes, understand the three permission classes:

```text
user
group
other
```

and interpret the three basic permission types:

```text
read
write
execute
```

You will also discover something that causes many beginner mistakes:

**Permissions do not mean exactly the same thing for files and directories.**

For a regular file, `r`, `w`, and `x` describe operations on the file itself.

For a directory, those same letters control your ability to list names, modify directory entries, and traverse through the directory.

By the end of this lab, a permission string should no longer look like random characters.

You should be able to read it as evidence.

---

## What You Will Learn

By the end of this lab, you should be able to:

- Read the permission field from `ls -l`.
- Separate file type from permission bits.
- Identify the `user`, `group`, and `other` permission classes.
- Understand `r`, `w`, `x`, and `-`.
- Explain read permission on a regular file.
- Explain write permission on a regular file.
- Explain execute permission on a regular file.
- Explain read permission on a directory.
- Explain write permission on a directory.
- Explain execute permission on a directory.
- Understand why directory permissions must be interpreted differently from file permissions.
- Inspect permissions with `ls -l`, `ls -ld`, and `stat`.
- Identify your current user and group information.
- Understand that ownership and permissions work together.
- Recognize that permissions on parent directories can affect access to a file.
- Distinguish `Permission denied` from a missing-path error.
- Investigate permission failures using evidence instead of immediately using `sudo`.
- Understand why a readable script is not automatically executable.
- Understand why file deletion depends heavily on the containing directory.
- Build a reliable permission-troubleshooting process.

# 2. Start With `ls -l`

Run:

```bash
ls -l documents/report.txt
```

A typical result may look similar to:

```text
-rw-r--r-- 1 student student 35 Sep 27 09:30 documents/report.txt
```

Your username, group, size, timestamp and exact permissions may differ.

Focus on the first field:

```text
-rw-r--r--
```

This field contains information about:

1. the type of filesystem object,
2. permissions for the owning user,
3. permissions for the owning group,
4. permissions for everyone else.

It can be separated like this:

```text
- | rw- | r-- | r--
    user  group other
```

The first character is not part of the basic `rwx` permission triplets.

It identifies the type of filesystem object.

---

# 3. The First Character Describes the Object Type

Consider:

```text
-rw-r--r--
```

The first character is:

```text
-
```

For ordinary `ls -l` output, that indicates a regular file.

Now inspect a directory:

```bash
ls -ld documents
```

You may see something similar to:

```text
drwxr-xr-x
```

The first character is:

```text
d
```

which indicates a directory.

So compare:

```text
-rw-r--r--
^
regular file
```

with:

```text
drwxr-xr-x
^
directory
```

You learned filesystem object types earlier.

Now you are connecting that knowledge to permission output.

---

# 4. The Remaining Nine Characters

After the object-type character come nine permission positions.

For example:

```text
rw-r--r--
```

Split them into three groups:

```text
rw-  r--  r--
```

These groups represent:

```text
user   group   other
```

Often abbreviated:

```text
u   g   o
```

So:

```text
-rw-r--r--
```

can be read as:

```text
-    rw-    r--    r--
|     |      |      |
|     |      |      └── other
|     |      └───────── group
|     └──────────────── user
└────────────────────── object type
```

This structure is fundamental.

---

# 5. Who Are `user`, `group`, and `other`?

The three permission classes are:

## User

The permissions assigned to the file's owning user.

You may also hear this described as the **owner** permissions.

## Group

The permissions associated with the file's owning group.

## Other

The permissions used for users who are neither the file's owner nor being granted access through the file's owning group.

So when you see:

```text
-rw-r--r--
```

you should begin reading it as:

```text
owner: rw-
group: r--
other: r--
```

Ownership itself receives dedicated treatment in:

**JUN-008 — File Ownership**

For now, you need enough ownership awareness to understand whose permission fields you are reading.

# 7. The Three Basic Permission Letters

Linux's traditional permission model uses three fundamental letters:

```text
r
w
x
```

They stand for:

```text
r = read
w = write
x = execute
```

When a permission is absent, `ls -l` normally shows:

```text
-
```

For example:

```text
r--
```

means:

```text
read allowed
write not allowed
execute not allowed
```

And:

```text
rwx
```

means all three positions are present.

---

# 8. Permission Positions Have a Fixed Order

Within each permission class, the positions are always:

```text
r w x
```

So:

```text
rw-
```

means:

```text
read     yes
write    yes
execute  no
```

And:

```text
r-x
```

means:

```text
read     yes
write    no
execute  yes
```

And:

```text
---
```

means none of the three basic permissions are granted for that class.

You do not rearrange them as:

```text
wrx
```

or:

```text
xrw
```

The positions have meaning.

---

# 9. Read a Permission String Manually

Suppose you see:

```text
-rwxr-x---
```

Break it down:

```text
-    rwx    r-x    ---
```

Interpretation:

```text
Object type: regular file

User:
read      yes
write     yes
execute   yes

Group:
read      yes
write     no
execute   yes

Other:
read      no
write     no
execute   no
```

You should eventually be able to read this without translating every character individually.

That fluency comes through practice.

# 14. Read and Write Are Independent Permissions

A common beginner assumption is:

> If I can read a file, I should be able to edit it.

That is not necessarily true.

Another incorrect assumption is:

> If I can write to a file, I must be able to read it.

The permissions are distinct.

A permission set can grant one capability without granting another.

For example, conceptually:

```text
r--
```

means readable but not writable or executable.

And:

```text
-w-
```

means the write position is present while read and execute are absent.

Whether a particular operation succeeds can also depend on directory access, process identity, filesystem behavior, access-control mechanisms, and other factors.

The permission string is important evidence, but it exists within a larger access-control context.

# 19. Directory Permissions Mean Something Different

Now we reach one of the most important concepts in this lab.

For a regular file:

```text
r = read file contents
w = modify file contents
x = execute the file
```

For a directory, the meanings change.

A useful beginner model is:

```text
r = read the directory's entries/names
w = modify directory entries
x = traverse/search the directory
```

That means directory `x` does **not** mean:

> execute the directory.

Directories are not programs.

For directories, `x` is about traversal and pathname resolution through that directory.

# 23. Parent Directory Permissions Matter

This is a critical troubleshooting principle.

Suppose:

```text
/home/student/application/config/app.conf
```

itself appears readable.

Access can still fail if your process cannot traverse one of the directories in the path.

Conceptually:

```text
/
↓
home
↓
student
↓
application
↓
config
↓
app.conf
```

Linux must resolve the path component by component.

That means when a file appears to have reasonable permissions but still cannot be accessed, do not inspect only the final file.

Inspect the path leading to it.

# 25. Directory Write Permission Is About Directory Entries

Create:

```bash
mkdir directory-tests/write-test
```

Create:

```bash
touch directory-tests/write-test/existing.txt
```

Inspect:

```bash
ls -ld directory-tests/write-test
```

Directory write permission participates in operations that modify entries in the directory, such as creating, removing, or renaming entries.

This leads to a surprising but important Linux concept:

**Deleting a file is not controlled solely by the file's own write permission.**

Deletion changes the directory entry that refers to the file.

Therefore, the containing directory's permissions are central to whether deletion is allowed.

# 27. Do Not Misinterpret File Write Permission

A common assumption is:

> If a file is not writable, nobody can delete it.

That is not how traditional Linux permissions work.

File write permission governs modification of the file's contents.

Deletion is primarily controlled by permissions and rules affecting the containing directory.

Later, JUN-010 introduces the sticky bit, which adds another important rule commonly seen on shared directories such as `/tmp`.

For now, remember:

```text
file write permission
```

and:

```text
permission to remove the directory entry
```

are different questions.

# 29. File Permissions and Directory Permissions Work Together

Suppose you want to read:

```text
project/config/app.conf
```

Several conditions may matter.

At a basic level:

- You need sufficient traversal/search access through the directories in the path.
- You need appropriate access to the final file.
- Your process identity matters.
- Ownership and group membership matter.
- Additional access-control mechanisms may also matter.

So this troubleshooting approach is incomplete:

```text
cat failed
↓
look only at app.conf
```

A better approach is:

```text
cat failed
↓
read the error
↓
confirm identity
↓
confirm the path
↓
inspect the final file
↓
inspect relevant parent directories
↓
identify where access breaks
↓
correct the actual cause
↓
verify
```


You may see something similar to:

```text
-rw------- 1 student student ...
```

Two fields after the link count identify the owning user and owning group.

The permission triplets do not exist independently of those identities.

For example:

```text
rw- --- ---
```

means very little until you know which user owns the file.

Likewise:

```text
--- r-- ---
```

requires knowing which group owns the file and whether the process's user has relevant group membership.

JUN-008 goes deeper into:

- file owners,
- file groups,
- `chown`,
- `chgrp`,
- ownership behavior,
- and ownership troubleshooting.

For this lab, understand the relationship:

**Permissions define capabilities for permission classes; ownership helps determine which class applies.**

---

# 34. Do Not Assume the Owner Always Has Every Permission

Ownership does not automatically mean:

```text
rwx
```

An owner can have:

```text
r--
```

or:

```text
rw-
```

or even:

```text
---
```

in the traditional mode bits.

You demonstrated this when you created controlled permission states.

Being the owner and having a particular permission are separate concepts.

Ownership identifies a permission class.

The permission bits describe the capabilities assigned to that class.

---

# 35. Do Not Assume Group Members Can Write

If you see:

```text
-rw-r--r--
```

the group field is:

```text
r--
```

That means the basic group permissions include read but not write or execute.

Being a member of the file's group does not automatically grant every capability.

Again:

```text
identity
+
ownership
+
permissions
```

must be considered together.

---

# 36. `other` Does Not Mean Anonymous Users Only

The permission class:

```text
other
```

means users who are not receiving access as the file owner or through the applicable owning-group class in the traditional permission evaluation model.

It does not simply mean:

> internet users

or:

> unauthenticated users.

It is a local Unix permission category.

For example:

```text
r--
```

for `other` means the traditional mode grants read permission to users falling into that class.

---

# 37. Permissions Are Not the Entire Linux Security Model

Traditional permission bits are foundational, but they are not the only access-control mechanism Linux systems may use.

Real systems can also involve mechanisms such as:

- Access Control Lists
- AppArmor
- SELinux on distributions that use it
- filesystem mount options
- capabilities
- immutable attributes
- container isolation
- application-level authorization
- network controls

You are not expected to understand those mechanisms yet.

The important lesson is:

**A permission string is critical evidence, but it is not proof that no other security control exists.**

Later Linux World labs introduce additional layers at the appropriate stage.

# 39. Do Not Respond to Every Permission Error With `sudo`

Suppose:

```bash

```

returns:

```text

```

```text

```

- Which groups am I in?
- Who owns the file?
- Which permissions are set?
- Can I traverse the parent directories?
- Is this the correct path?
- Should my account have access?

Use this model when access fails:

```text

        ↓

        ↓

        ↓
```

# 43. File Permission Quick Reference

For a **regular file**:

| Permission | Basic Meaning |
|---|---|
| `r` | Read file contents |
| `w` | Modify file contents |
| `x` | Execute the file as a program/script when other execution requirements are satisfied |
| `-` | That permission position is absent |

Do not interpret this table as the entire Linux security model.

It describes the traditional permission bits you are learning in this lab.

---

# 44. Directory Permission Quick Reference

For a **directory**:

| Permission | Basic Meaning |
|---|---|
| `r` | Read/list directory entry names |
| `w` | Modify directory entries, subject to other required permissions/rules |
| `x` | Traverse/search the directory and resolve names through it |
| `-` | That permission position is absent |

The directory meaning of `x` is especially important.

You do not "execute" a directory.

You traverse/search it.

---

# 45. Why Directory Permissions Are Often More Subtle

For files, beginners can often understand:

```text
r = read
w = write
x = execute
```

fairly quickly.

Directories require more reasoning because operations interact.

For example:

- listing names,
- accessing known names,
- creating entries,
- deleting entries,
- renaming entries,
- traversing into subdirectories

depend on combinations of directory permissions and sometimes permissions on other objects.

That is why you should test actual operations rather than assuming what a single letter means in isolation.

# 50. A Practical Permission Investigation Workflow

When an access operation fails, start with the actual operation.

For example:

```bash
cat path/to/file
```

Then investigate systematically:

```text
1. Read the exact error.

2. Confirm your identity.

3. Confirm the path.

4. Identify the object type.

5. Inspect the final object's permissions and ownership.

6. Inspect relevant directories in the path.

7. Determine which operation is being denied:
   read?
   write?
   execute?
   directory traversal?
   directory modification?

8. Form a hypothesis.

9. Test the hypothesis safely.

10. Correct the actual cause.

11. Repeat the original failing operation.

12. Verify that access is correct without granting unnecessary permissions.
```

That final point matters.

The objective is not:

> make the error disappear at any cost.

The objective is:

> provide the intended access and no more than necessary.

# 51. Least Privilege

A foundational security principle is **least privilege**.

A user, process, service, or application should receive the permissions it actually requires—not every permission available.

For example, if an application only needs to read a configuration file, granting broad write access may be unnecessary.

If a script only needs to be executable by its owner, making it broadly writable would introduce additional risk without solving a requirement.

You will learn how to express permission changes precisely in JUN-009.

For now, develop the reasoning habit:

**What access is actually required?**

Do not begin with:

**How can I grant everything?**

# 52. Common Mistakes to Avoid

### Reading all ten characters as permissions

In:

```text
-rw-r--r--
```

the first character identifies the object type.

The following nine positions contain the traditional user/group/other permission triplets.

### Forgetting the three permission classes

Read permissions as:

```text
user | group | other
```

### Thinking `x` means the same thing everywhere

For a regular file, it relates to execution.

For a directory, it relates to traversal/search.

### Assuming readable means writable

Read and write are separate permissions.

### Assuming readable means executable

A script can be readable without being directly executable.

### Assuming a file's permissions alone determine access

Parent-directory traversal matters.

### Assuming a read-only file cannot be deleted

Deletion primarily modifies the containing directory entry.

### Looking only at the final file

The blocking permission may be on a directory earlier in the path.

### Automatically using `sudo`

Privilege escalation can hide the real cause and may grant unnecessary access.

### Changing permissions before understanding the failure

Inspect first.

### Granting broad permissions because they make the error disappear

A working system is not necessarily a securely configured system.

### Treating every incident component as broken

Inspect healthy components and leave them unchanged.

# 58. Interview Practice

### How do you read `-rw-r--r--`?

The first character indicates a regular file. The owner has read and write permission, the group has read permission, and other users have read permission. None of the three classes has execute permission.

### What are the three Linux permission classes?

The owning user, the owning group, and other.

### What are the three basic permissions?

Read, write, and execute.

### What does execute permission mean on a directory?

It means traversal or search permission. It allows pathname resolution through the directory rather than "executing" the directory.

### What is the difference between read permission on a file and read permission on a directory?

On a regular file, read permission controls reading the file's contents. On a directory, read permission relates to reading its directory entries or names.

### Why can a readable file still return `Permission denied`?

The process may be unable to traverse one of the parent directories, the relevant permission class may not actually apply as assumed, or another access-control mechanism may be involved.

### Why can a read-only file sometimes still be deleted?

Because deleting a pathname primarily modifies the containing directory entry. File write permission controls modification of file contents; deletion is governed mainly by the containing directory's access rules and other applicable controls.

### How would you inspect a directory's own permissions?

```bash
ls -ld DIRECTORY
```

### How would you inspect detailed permission metadata?

```bash
stat PATH
```

### How would you identify the current user's group memberships?

```bash
id
```

### A service reports `Permission denied` while reading a configuration file. What would you investigate?

I would first confirm the exact error and path, identify the process or user context, inspect the file's permissions and ownership, inspect traversal permissions on relevant parent directories, determine which access requirement is failing, and only then make the smallest appropriate correction.

### Why is immediately using `sudo` poor troubleshooting?

Because it can bypass the restriction without identifying why access failed, may grant unnecessary privileges, and may hide an incorrect ownership or permission configuration.

### What is least privilege?

It is the principle of granting only the access required for the intended task rather than granting unnecessarily broad permissions.

```text
Can I read its entries?
Can I modify its entries?
Can I traverse through it?
```

You also learned that access failures must be investigated in context.

A file's permissions are not the only evidence.

The user matters.

The group matters.

The containing directories matter.

The requested operation matters.

And the intended security boundary matters.

When Linux says:

```text
Permission denied
```

your first objective should not be to overpower the restriction.

Your first objective should be to understand it.

That distinction becomes increasingly important as Linux World moves into ownership, permission modification, privilege management, services, automation, security, and production troubleshooting.
