# JUN-006: File Paths and Wildcards

- **Level:** Junior  
- **Difficulty:** 1/5  
- **Estimated time:** 60–75 minutes  
- **Environment:** Ubuntu Server 24.04 LTS or a similar Linux system  
- **Privileges:** Standard user account  
- **Primary skills:** Linux paths, path interpretation, shell wildcards and safe filename matching  
- **Prerequisites:** JUN-001 through JUN-005

---

## Lab Mission

You already know how to move through the Linux filesystem and work with individual files.

Now imagine a directory containing:

```text
application.log
application-old.log
database.log
security.log
README.md
app.conf
database.conf
```

You could work with every filename individually.

But Linux gives you another option.

You can describe groups of filenames using patterns such as:

```text
*.log
```

or:

```text
app*
```

or:

```text
?.conf
```

These patterns are commonly called **wildcards**, and the shell's process of matching them against pathnames is known as **pathname expansion** or **globbing**.

This is extremely useful, but it also introduces risk.

A pattern that matches more files than you expected can turn a harmless listing command into an unpleasant surprise when the same pattern is used with `cp`, `mv`, or `rm`.

In this lab, you will strengthen your understanding of absolute and relative paths, work with path components and special path references, and learn the core wildcard patterns:

```text
*
?
[...]
```

Most importantly, you will learn to **preview a match before using it in a command that changes the filesystem**.

---

## What you will learn

By the end of this lab, you should be able to:

- Distinguish absolute and relative paths.
- Understand how Linux interprets a pathname.
- Recognize path components separated by `/`.
- Use `~`, `.`, and `..` confidently.
- Build paths across multiple directory levels.
- Understand that Linux paths and filenames are case-sensitive.
- Work with filenames containing spaces safely.
- Understand what shell wildcard expansion does.
- Use `*` to match zero or more characters within a pathname component.
- Use `?` to match exactly one character within a pathname component.
- Use bracket expressions such as `[123]` and `[ab]`.
- Use ranges such as `[0-9]` where appropriate.
- Combine directory paths with wildcard patterns.
- Understand why `*` does not normally match leading-dot filenames.
- Understand that shell wildcards normally do not cross `/`.
- Recognize what happens when a wildcard pattern matches nothing in Bash's default configuration.
- Preview wildcard matches before using destructive commands.
- Troubleshoot unexpected wildcard results.

# 2. Revisit what a path actually represents

Consider:

```text
/home/student/linux-world-labs/JUN-006/application/config/app.conf
```

This is a pathname.

The `/` characters separate its components.

Conceptually:

```text
/
└── home
    └── student
        └── linux-world-labs
            └── JUN-006
                └── application
                    └── config
                        └── app.conf
```

Your actual username may not be `student`, so your real path may differ.

The important idea is that Linux resolves the components of the path to reach the final object.

---

# 3. Absolute paths begin at `/`

An **absolute path** starts from the filesystem root:

```text
/
```

For example:

```text
/etc/hostname
```

is absolute because it begins with `/`.

So is a path such as:

```text
/home/student/linux-world-labs/JUN-006/application/config/app.conf
```

An absolute path does not depend on your current working directory.

You can demonstrate this with a real system file.

From your lab directory:

```bash
cat /etc/hostname
```

Now move somewhere else:

```bash
cd /tmp
```

Run the same command:

```bash
cat /etc/hostname
```

The path still refers to the same location because it starts from `/`.

Return to the lab:

```bash
cd ~/linux-world-labs/JUN-006
```

# 4. Relative paths depend on your current location

From:

```text
~/linux-world-labs/JUN-006
```

this is a relative path:

```text
application/config/app.conf
```

It does not begin with `/`.

Run:

```bash
ls -l application/config/app.conf
```

It works because your current directory provides the starting point.

Now move:

```bash
cd application/logs
```

Try:

```bash
ls -l application/config/app.conf
```

The command should fail.

Why?

Because from your new location, Linux is effectively trying to resolve a path beginning beneath your current directory:

```text
.../application/logs/application/config/app.conf
```

That path does not exist.

The relative path did not change.

Your starting location did.

# 11. Linux paths are case-sensitive

Create:

```bash
mkdir practice/Production
```

Now:

```bash
ls -ld practice/Production
```

Try:

```bash
ls -ld practice/production
```

The second command should fail.

These are different names:

```text
Production
production
PRODUCTION
```

Linux filesystems commonly used on Linux systems treat filename case as significant.

That means a capitalization error can produce a genuine path error.

When you receive:

```text
No such file or directory
```

check capitalization as well as spelling.

# 12. Filenames can contain spaces

Create:

```bash
touch "practice/system report.txt"
```

Verify:

```bash
ls -l practice
```

The file's name is:

```text
system report.txt
```

The space is part of the filename.

Now try:

```bash
ls -l practice/system report.txt
```

The shell interprets the spaces as separators between command arguments.

The command therefore does not refer to the intended pathname as one unit.

Use quotes:

```bash
ls -l "practice/system report.txt"
```

This works because the quoted text is kept together as one shell word.

You can also escape the space:

```bash
ls -l practice/system\ report.txt
```

Both approaches identify the intended file.

Quoting and shell parsing become much more important later in Bash.

For now, remember:

**A path containing spaces must be passed to the command in a way that preserves those spaces as part of the same argument.**

# 13. Before wildcards: understand who performs the matching

Consider:

```bash
ls application/logs/*.log
```

It is tempting to think that `ls` receives `*.log` and searches for matching files.

In the normal Bash behavior used in this lab, that is not what happens.

The **shell** examines the wildcard pattern first.

It finds matching pathnames and expands the pattern.

Conceptually, you type:

```text
ls application/logs/*.log
```

and the shell may transform that into something similar to:

```text
ls application/logs/application-old.log application/logs/application.log application/logs/database.log application/logs/security.log
```

Then `ls` receives the expanded pathname arguments.

This distinction becomes important when troubleshooting wildcard behavior.

---

# 14. The `*` wildcard

The wildcard:

```text
*
```

matches zero or more characters within a pathname component, subject to shell matching rules.

From the lab root, run:

```bash
ls application/logs/*.log
```

You should see the `.log` files directly inside:

```text
application/logs/
```

The pattern:

```text
*.log
```

means:

> Match names ending in `.log`, with zero or more characters before `.log`.

Examples that match include:

```text
application.log
database.log
security.log
```

---

# 15. `*` can match zero characters

This detail matters.

Create:

```bash
touch practice/.log
```

Inside ordinary non-hidden filename matching, a pattern such as:

```text
*.log
```

can conceptually match `.log` because `*` is capable of matching zero characters.

However, Bash has a separate rule concerning filenames beginning with `.`.

By default, wildcard matching does not match that leading `.` unless the pattern itself begins appropriately with `.`.

So from:

```bash
ls practice/*.log
```

you should not expect the hidden `.log` file to appear.

We will examine hidden files shortly.

The important distinction is:

`*` can match zero characters, but leading-dot behavior is controlled separately.

---

# 16. Match names by prefix

Run:

```bash
ls application/logs/application*
```

The pattern means:

> Match names in `application/logs` that begin with `application` and then contain zero or more additional characters.

You should match files such as:

```text
application.log
application-old.log
```

Now:

```bash
ls application/config/app*
```

This should match names beginning with `app`, including:

```text
app.conf
app.conf.backup
```

The wildcard does not know what a "configuration file" is.

It simply matches pathname characters.

---

# 17. Match names by suffix

Run:

```bash
ls application/config/*.conf
```

This matches names ending exactly in:

```text
.conf
```

Notice the difference between:

```text
app.conf
```

and:

```text
app.conf.backup
```

The second name does not end in `.conf`.

So a pattern such as:

```text
*.conf
```

should not match:

```text
app.conf.backup
```

This is a good reminder that wildcard matching is based on the filename pattern, not your interpretation of what the file represents.

# 19. `?` matches exactly one character

The wildcard:

```text
?
```

matches exactly one character within a pathname component.

Look at your report files:

```bash
ls application/reports
```

You have:

```text
report1.txt
report2.txt
report3.txt
report-final.txt
summary.md
```

Run:

```bash
ls application/reports/report?.txt
```

This should match:

```text
report1.txt
report2.txt
report3.txt
```

because each filename has exactly one character between:

```text
report
```

and:

```text
.txt
```

It should not match:

```text
report-final.txt
```

because `-final` contains more than one character.

---

# 20. Compare `*` and `?`

Compare:

```bash
ls application/reports/report*.txt
```

with:

```bash
ls application/reports/report?.txt
```

The first is broader.

`*` can match zero or more characters.

The second is more specific.

`?` requires exactly one character.

This is one of the most useful ideas in wildcard work:

**Choose the narrowest pattern that correctly describes what you intend to match.**

---

# 21. Bracket expressions match one character from a set

Run:

```bash
ls application/reports/report[12].txt
```

The bracket expression:

```text
[12]
```

matches one character that is either:

```text
1
```

or:

```text
2
```

So the expected matches are:

```text
report1.txt
report2.txt
```

but not:

```text
report3.txt
```

You can use letters too.

Create:

```bash
touch practice/server-a.log
touch practice/server-b.log
touch practice/server-c.log
```

Now:

```bash
ls practice/server-[ab].log
```

This should match:

```text
server-a.log
server-b.log
```

---

# 22. Character ranges

Bracket expressions can also describe ranges.

Run:

```bash
ls application/reports/report[1-3].txt
```

This should match:

```text
report1.txt
report2.txt
report3.txt
```

Another common example is:

```text
[0-9]
```

for a single digit.

For example:

```bash
ls application/logs/archive/application-0[1-3].log
```

should match:

```text
application-01.log
application-02.log
application-03.log
```

Be aware that range interpretation can be affected by locale and character collation rules, especially with alphabetic ranges.

For simple numeric practice such as `[0-9]`, the intention is straightforward.

# 23. Combine wildcard types

You can combine wildcard constructs in the same pathname component.

For example:

```bash
ls application/logs/archive/application-0?.log
```

Here:

```text
application-0
```

must appear literally.

Then:

```text
?
```

matches exactly one character.

Then:

```text
.log
```

must appear literally.

Your current files:

```text
application-01.log
application-02.log
application-03.log
```

all satisfy that pattern.

# 24. Wildcards work with paths, not just bare filenames

You do not need to enter a directory before using a pattern.

From the lab root:

```bash
ls application/scripts/*.sh
```

The shell matches `.sh` files inside:

```text
application/scripts/
```

Likewise:

```bash
ls application/config/*.conf
```

matches appropriate entries inside `config`.

And:

```bash
ls application/logs/archive/*.log
```

matches `.log` entries inside the archive directory.

A wildcard can therefore be part of a larger pathname.

---

# 25. Wildcards normally operate one pathname component at a time

Suppose you run:

```bash
ls application/*.log
```

You might expect it to find every `.log` file somewhere beneath `application`.

It does not.

Your `.log` files are mostly inside:

```text
application/logs/
```

The `*` in ordinary Bash globbing does not cross the `/` directory separator.

Similarly:

```text
application/*.log
```

describes entries directly under:

```text
application/
```

that end in `.log`.

It does not recursively search all descendant directories.

Recursive searching is a different problem and will be taught later with tools such as `find`.

Do not confuse wildcard expansion with recursive filesystem searching.

---

# 26. A wildcard can match directory names too

Wildcards do not mean "files only."

Run:

```bash
ls -d application/*
```

The pattern can match entries directly beneath `application`, including directories.

Depending on your current structure, you should see names such as:

```text
application/config
application/logs
application/reports
application/scripts
```

Why use:

```text
-d
```

here?

Because without it, `ls` may list the contents of matched directories rather than simply showing the directory entries themselves.

If you are unsure about the option:

```bash
ls --help
```

This reinforces the JUN-002 habit of checking documentation rather than guessing.

# 27. Hidden files behave differently

You created:

```text
application/.environment
application/.release
```

Run:

```bash
ls application
```

They are not shown.

Now:

```bash
ls -a application
```

They appear.

What about:

```bash
ls -d application/*
```

The leading-dot files are not normally included by Bash's default wildcard behavior.

A leading `.` must normally be matched explicitly.

Try:

```bash
ls -d application/.*
```

This pattern begins with a literal dot before the wildcard.

Depending on the exact pattern and shell behavior, dot-related directory entries can require care, so do not use broad dotfile patterns with destructive commands.

For a safe listing, compare the results with:

```bash
ls -la application
```

The key lesson is:

**A bare `*` does not normally include names beginning with `.` in Bash's default configuration.**

# 28. Why hidden-file behavior matters

Suppose you think:

```text
*
```

means:

> absolutely everything in this directory.

That assumption can be wrong.

Hidden files may be excluded from the match.

This matters during tasks such as:

- copying directory contents,
- moving application data,
- cleaning a workspace,
- packaging files,
- reviewing configuration,
- or verifying that a directory is truly empty.

You should understand what your pattern matches rather than relying on what the wildcard looks like.

# 29. Preview before you act

This is the most important operational habit in this lab.

Suppose you intend to work with:

```text
application/logs/*.log
```

Before using that pattern with a command that changes files, preview it with a non-destructive command.

For example:

```bash
ls -l application/logs/*.log
```

Inspect the result.

Ask:

- Did it match the files I expected?
- Did it match anything unexpected?
- Did I use the correct directory?
- Is the pattern too broad?
- Are hidden files relevant?
- Am I about to affect directories as well as files?

Only after understanding the match should you consider using the pattern with a modifying command.

Bash provides a useful builtin:

```text
printf
```

You can use it to display each expanded pathname on its own line.

Try:

```bash
printf '%s\n' application/logs/*.log
```

The shell expands the wildcard before `printf` receives the arguments.

You should see the matched pathnames individually.

Now:

```bash
printf '%s\n' application/reports/report?.txt
```

And:

```bash
printf '%s\n' application/logs/archive/application-0[1-3].log
```

This is a useful way to inspect pathname expansion without changing the matched files.

You do not need to learn `printf` fully yet.

Here it is simply a safe inspection tool.

---

# 31. What happens when nothing matches?

Try a pattern that should match nothing:

```bash
printf '%s\n' application/logs/*.csv
```

In Bash's default configuration, when a pathname expansion pattern matches nothing, the pattern is normally left unchanged.

So you may see:

```text
application/logs/*.csv
```

printed literally.

That does **not** mean a file named:

```text
*.csv
```

exists.

Check:

```bash
ls application/logs
```

There are no `.csv` files.

Now try:

```bash
ls application/logs/*.csv
```

Because the shell passes the unmatched pattern through literally, `ls` will normally report that no such path exists.

This behavior is shell-dependent and can also be changed through Bash options.

For this lab, we are using Bash's normal default behavior.

---

# 32. An unmatched wildcard is not an empty result

This distinction matters.

You type:

```text
*.csv
```

There are no matches.

Under the Bash behavior used here, the shell does not normally remove the argument.

Instead, the literal pattern remains.

A command may therefore receive:

```text
*.csv
```

as an argument.

This can produce confusing errors if you assume "no matches" means "the command receives nothing."

When wildcard behavior surprises you, inspect the expansion rather than guessing.

---

# 33. Quoting changes wildcard behavior

Compare:

```bash
printf '%s\n' application/logs/*.log
```

with:

```bash
printf '%s\n' 'application/logs/*.log'
```

The first allows the shell to perform pathname expansion.

The second quotes the wildcard, so the `*` is passed literally rather than expanded.

You should see the difference immediately.

Double quotes also prevent ordinary pathname expansion:

```bash
printf '%s\n' "application/logs/*.log"
```

The deeper rules of shell quoting come later.

For now, remember:

**If you quote a wildcard pattern, you usually prevent the shell from expanding that wildcard.**

---

# 34. A wildcard does not mean regular expression

You may encounter another kind of pattern language later called **regular expressions**.

Do not assume shell wildcards and regular expressions mean the same thing.

For example, in shell globbing:

```text
*
```

means zero or more characters within the relevant pathname component.

In regular-expression syntax, `*` has a different relationship to the preceding expression.

This lab is about **shell pathname expansion**, not regular expressions.

Keeping those concepts separate now will save confusion later.

Compare it with:

```bash
ls application/logs/*.log
```

The second pattern includes unrelated log names such as:

```text
database.log
security.log
```

The first is more specific.

When changing multiple files, precision is valuable.

# 38. Controlled failure: a pattern is too narrow

Try:

```bash
ls application/reports/report?.md
```

You should get no pathname match because your numbered reports use `.txt`, not `.md`.

Investigate:

```bash
ls application/reports
```

Then compare the actual names with your pattern.

The problem is not `ls`.

Your pattern does not describe the existing filenames.

Correct it:

```bash
ls application/reports/report?.txt
```

This should match the numbered reports.

# 39. Controlled failure: a pattern is too broad

Suppose you want only:

```text
report1.txt
report2.txt
report3.txt
```

You use:

```bash
ls application/reports/*
```

That also includes:

```text
report-final.txt
summary.md
```

The command succeeded.

But your pattern was wrong for your intention.

This is an important class of engineering failure:

**The system did exactly what you asked, but what you asked was not what you intended.**

A better pattern is:

```bash
ls application/reports/report[1-3].txt
```

Previewing allows you to catch that mistake before using the pattern with a modifying command.


not:

```text

```

Investigate:


Correct:


Again, the wildcard is not the root cause.

# 41. Controlled failure: wrong directory depth

Try:

```bash

```

You know configuration files exist.

Yet this pattern should not match them.

Why?

Because the `.conf` files are inside:

```text
application/config/
```

not directly beneath:

```text
application/
```

Inspect:

```bash

```

```bash

```


# 42. Controlled failure: quoted wildcard

Run:

```bash
ls 'application/logs/*.log'
```

The command should fail because the shell does not expand the quoted `*`.

`ls` receives a literal pathname containing an asterisk.

Now:

```bash
ls application/logs/*.log
```

The shell performs pathname expansion and supplies the matching paths.

This is an important diagnostic clue.

When a wildcard unexpectedly appears literally in an error message, consider whether quoting or lack of matches affected shell expansion.

# 43. Wildcards and deletion require discipline

You know from JUN-004 that:

```text
rm
```

removes files.

You now know that:

```text
*
```

can represent multiple pathnames.

Combining those ideas means a pattern can cause one command to remove several files.

For that reason, do not begin with a destructive command.

Suppose you want to remove disposable `.tmp` files from:

```text
practice/
```

First create some:

```bash

touch practice/cache2.tmp
touch practice/cache3.tmp
touch practice/keep.txt
```

```bash

```

You should see only:

```text

cache2.tmp
cache3.tmp
```

Check the file that must remain:

```bash

```

Now, because these files were created specifically for this exercise:

```bash
rm practice/*.tmp
```

Verify the removal:

```bash
ls -l practice/*.tmp
```

Now verify preservation:

```bash
ls -l practice/keep.txt
```

The job is not complete until you have confirmed both:

- the intended files were removed,
- the file you intended to preserve remains.

# 44. Never assume `*` means what you intended

Imagine a directory containing:

```text
application.log
database.log
security.log
customer-data.csv
backup.tar
```

If your goal is to remove old logs, this:

```text
*
```

is far too broad.

Even:

```text
*.log
```

may still be too broad if you intended to remove only one category of logs.

A safer approach begins by describing your intention precisely.

For example:

```text

```

may be more appropriate if that naming scheme accurately describes the disposable files.

Then preview.

Then verify.

Then act.

The wildcard itself is not dangerous.

**An insufficiently understood match used with a destructive command is dangerous.**

# 45. Avoid building dangerous habits with `rm -rf *`

You may encounter:

```text
rm -rf *
```

in tutorials, scripts or online discussions.

Do not turn it into a reflex.

You already learned in JUN-004 that recursive forced deletion can remove directory trees with little interaction.

You have now learned another important fact:

```text
*
```

is expanded by the shell according to the current directory and matching rules.

That means the effect depends heavily on:

- where you are,
- what names exist,
- what the pattern matches,
- and which files are not matched.

This lab does not require:

```text
rm -rf *
```

at any point.

Use deliberately scoped cleanup commands instead.

# 50. A practical wildcard workflow

When a command will affect multiple paths, use this reasoning process:

```text
What exactly am I trying to match?
        ↓
Which directory contains those objects?
        ↓
What filename structure do they share?
        ↓
What is the narrowest useful pattern?
        ↓
Preview the expansion
        ↓
Check for unexpected matches
        ↓
Check for missing expected matches
        ↓
Only then use the pattern with the intended operation
        ↓
Verify the resulting state
```

For example:

```bash
ls -l application/logs/application*.log
```

or:

```bash
printf '%s\n' application/logs/application*.log
```

can be used to inspect a match before a modifying operation.

The preview is not wasted time.

It is part of the operation.

# 51. Common mistakes to avoid

### Confusing `/` and `~`

`/` is the filesystem root.

`~` is expanded by the shell to your home directory in the context used here.

They are not interchangeable.

### Forgetting that relative paths depend on location

If the same relative path works in one directory and fails in another, inspect:

```bash
pwd
```

before blaming the command.

### Ignoring case

```text
Reports
```

and:

```text
reports
```

are different names on typical Linux filesystems.

### Forgetting to protect spaces

A pathname containing spaces must be passed as the intended argument, commonly using quoting or escaping.

### Assuming `*` means recursive search

It does not normally cross `/`.

### Assuming `*` includes hidden files

A bare `*` normally excludes leading-dot names under Bash's default behavior.

### Confusing wildcards with regular expressions

They are different pattern systems.

### Assuming an unmatched wildcard disappears

Under Bash's default configuration, an unmatched glob pattern normally remains literal.

### Quoting a wildcard when you intended expansion

Quotes prevent normal pathname expansion.

### Using a pattern that is broader than the requirement

A command can succeed and still affect the wrong set of files.

### Testing a pattern first with `rm`

Do not use deletion as your preview mechanism.

Use a non-destructive command first.

# 57. Interview Practice

### What is the difference between an absolute path and a relative path?

An absolute path starts from `/` and identifies a location from the filesystem root. A relative path is interpreted from a starting location, usually the current working directory.

### What do `.` and `..` mean in Linux paths?

`.` represents the current directory, while `..` represents its parent directory.

### What does `~` mean?

In common shell usage, `~` is expanded to the user's home directory.

### What is globbing?

Globbing, or pathname expansion, is the shell's process of matching wildcard patterns against pathnames and replacing matching patterns with the resulting pathnames before executing the command.

### What does `*` match?

In ordinary shell pathname expansion, `*` matches zero or more characters within a pathname component, subject to rules such as leading-dot handling.

### What does `?` match?

Exactly one character within a pathname component.

### What does `[abc]` match?

One character from the specified set: `a`, `b`, or `c`.

### Does `*.log` normally include hidden `.log` files?

Not if the filename begins with `.` and the pattern itself does not begin appropriately with `.` under Bash's default behavior.

### Does `*` recursively descend through directories?

No. Ordinary `*` does not cross `/`.

### What happens if a Bash wildcard matches nothing?

Under Bash's default behavior, the pattern normally remains unchanged and is passed literally to the command.

### Why might `'*.log'` behave differently from `*.log`?

Quoting prevents the shell from performing normal pathname expansion on the wildcard.

### Why should wildcard matches be previewed before a destructive operation?

Because a syntactically valid pattern may match more files than intended. Previewing allows you to verify the target set before changing or deleting anything.

### A wildcard command matched unexpected files. How would you investigate?

I would inspect my current directory, verify the directory portion of the path, list the available filenames, examine the pattern character by character, preview the expansion with a non-destructive command, and narrow the pattern until it represents the intended files.

### What is the difference between wildcard matching and `find`?

Wildcard expansion matches pathnames according to shell patterns in the path components provided. `find` is a filesystem traversal and search tool that can recursively inspect directory trees according to search criteria. `find` is covered later in Linux World.
