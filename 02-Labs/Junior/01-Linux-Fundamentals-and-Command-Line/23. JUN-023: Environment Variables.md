## Lab Mission

Every Linux process runs with context.

A program may need to know:

- which user's home directory applies,
- which language or locale is configured,
- what terminal type is in use,
- where commands may be searched for,
- what application mode has been selected,
- which configuration values were supplied when the process started.

One important mechanism for supplying this context is the **environment**.

You have already encountered names such as:

```text
HOME
USER
PATH
SHELL
TERM
```

Until now, you have mostly used their effects without investigating how they work.

In this lab, you will build the mental model.

You will learn that these are different concepts:

```text
shell variable
        ↓
exists in the current shell

environment variable
        ↓
part of the environment supplied to child processes
```

You will prove this behavior instead of simply memorizing it.

Your investigation model is:

```text
CREATE VALUE
     ↓
INSPECT VALUE
     ↓
START CHILD PROCESS
     ↓
TEST VISIBILITY
     ↓
EXPORT VALUE
     ↓
START NEW CHILD PROCESS
     ↓
PROVE INHERITANCE
     ↓
CHANGE / REMOVE VALUE
     ↓
VERIFY SCOPE
```

By the end, you should understand not only how to set an environment variable, but **which process can see it, why it can see it, and when the value disappears**.

# 2. What Is a Variable?

At its simplest, a variable associates a name with a value.

Conceptually:

```text
NAME
  ↓
VALUE
```

For example:

```text
COURSE
  ↓
Linux World
```

In Bash, you can create a shell variable like this:

```bash
COURSE="Linux World"
```

There must be no spaces around the assignment operator.

Correct:

```bash
COURSE="Linux World"
```

Incorrect:

```bash
COURSE = "Linux World"
```

The second form is not Bash variable-assignment syntax.

Now display the value:

```bash
echo "$COURSE"
```

You should see:

```text
Linux World
```

You have created a variable in your current shell.

But you have **not yet proved that it is an environment variable**.

That distinction is the core of this lab.

---

# 3. Variable Expansion

When you write:

```bash
echo "$COURSE"
```

the shell recognizes:

```text
$COURSE
```

as a request to expand the variable.

Conceptually:

```text
command text

echo "$COURSE"

        ↓

shell performs variable expansion

        ↓

echo "Linux World"
```

The program receives the resulting argument after the shell has processed the variable reference.

You can also use braces:

```bash
echo "${COURSE}"
```

The output should still be:

```text
Linux World
```

Braces become especially useful when text appears immediately after the variable name.

Try:

```bash
echo "${COURSE}-Lab"
```

Expected:

```text
Linux World-Lab
```

The braces make the variable boundary explicit.

---

# 4. Quoting Changes Expansion Behavior

You do not need the full shell-parsing curriculum yet, but one distinction matters immediately.

Run:

```bash
echo "$COURSE"
```

You should see the variable's value.

Now run:

```bash
echo '$COURSE'
```

You should see:

```text
$COURSE
```

Why?

At this level, remember:

```text
double quotes
    ↓
allow variable expansion

single quotes
    ↓
preserve the variable reference literally
```

Compare:

```bash
echo "Course: $COURSE"
```

with:

```bash
echo 'Course: $COURSE'
```

The first expands the variable.

The second does not.

This distinction becomes increasingly important as you move into shell configuration and Bash scripting.

# 5. Shell Variable vs Environment Variable

You created:

```bash
COURSE="Linux World"
```

Your current shell knows the value.

Confirm:

```bash
echo "$COURSE"
```

Now ask `printenv` for it:

```bash
printenv COURSE
```

You should normally receive no value.

Why?

Because:

```text
COURSE="Linux World"
```

created a shell variable.

It has not yet been exported into the environment supplied to child processes.

This gives you the first major distinction:

```text
SHELL VARIABLE
     ↓
known to the current shell

EXPORTED ENVIRONMENT VARIABLE
     ↓
included in the environment supplied to subsequently started child processes
```

Do not treat those as identical concepts.

# 6. Prove the Process Boundary

Your current shell can expand:

```bash
echo "$COURSE"
```

Now start a child Bash shell:

```bash
bash
```

You are now inside a new shell process.

Try:

```bash
echo "$COURSE"
```

Because `COURSE` was not exported before this child was created, it should normally be empty here.

Also try:

```bash
printenv COURSE
```

Again, you should not see the value.

Leave the child shell:

```bash
exit
```

Back in the original shell, run:

```bash
echo "$COURSE"
```

You should see:

```text
Linux World
```

This proves something important:

```text
PARENT SHELL
COURSE="Linux World"
        │
        │ not exported
        ▼
CHILD SHELL
COURSE unavailable
```

The variable existed in the parent shell.

It was not part of the environment inherited by the child.

Now run:

```bash

```

You have not changed the text stored in `COURSE`.

Verify:

```bash

```

You should now see:

```text
Linux World
```

Start another child shell:

```bash
bash
```

Inside it:

```bash

```

You should now see:

```text
Linux World
```

Also:

```bash
printenv COURSE
```

The value should be visible.

Exit:

```bash

```

You have now proved:

```text
PARENT SHELL

COURSE="Linux World"
export COURSE

        │
        │ child created
        ▼

CHILD SHELL

COURSE="Linux World"
```

That is environment inheritance.

# 9. Environment Inheritance Is Directional

Create another exported variable:

```bash
export PARENT_VALUE="created-in-parent"
```

Start a child shell:

```bash
bash
```

Inside the child:

```bash
printenv PARENT_VALUE
```

You should see:

```text
created-in-parent
```

Now change it inside the child:

```bash
PARENT_VALUE="changed-in-child"
```

Verify:

```bash
echo "$PARENT_VALUE"
```

You should see:

```text
changed-in-child
```

Exit the child:

```bash
exit
```

Back in the parent:

```bash
echo "$PARENT_VALUE"
```

You should still see:

```text
created-in-parent
```

Why?

Because the child received its own environment state when it was created.

Changing the child's copy does not rewrite the parent's variable.

Conceptually:

```text
PARENT
PARENT_VALUE=created-in-parent
          │
          │ inherited
          ▼
CHILD
PARENT_VALUE=created-in-parent
          │
          │ changed locally
          ▼
CHILD
PARENT_VALUE=changed-in-child
```

The parent remains:

```text
PARENT_VALUE=created-in-parent
```

A child process does not normally reach backward and rewrite its parent's environment.

---

# 10. Export Affects Future Child Processes

This timing matters.

Suppose:

```text
Parent shell
    ↓
creates child A
    ↓
parent exports NEW_VALUE
    ↓
creates child B
```

Child A does not magically receive the parent's later environment change.

Child B can inherit the new exported value when it starts.

The useful mental model is:

```text
PROCESS STARTS
      ↓
receives environment
      ↓
continues with its own process environment
```

Environment inheritance happens as processes are created.

Do not think of exported variables as a live global database automatically synchronized across all existing processes.

# 20. Variables Are Case-Sensitive

Create:

```bash
TEAM="platform"
```

Then:

```bash
team="linux"
```

Inspect:

```bash
echo "$TEAM"
```

Then:

```bash
echo "$team"
```

They are different variables.

Linux shell variable names are case-sensitive.

Therefore:

```text
TEAM
```

and:

```text
team
```

are not interchangeable.

By convention, environment-variable names are often written in uppercase:

```text
HOME
PATH
LANG
APP_ENV
```

but uppercase is a convention, not what technically makes a variable an environment variable.

`export` is what matters for the shell-to-child environment behavior demonstrated in this lab.

---

# 21. Variable Names Have Syntax Rules

Use simple names such as:

```text
COURSE
LAB_LEVEL
APP_MODE
VERIQTA_ENV
```

A Bash variable name normally uses:

- letters,
- digits,
- underscores,

and cannot begin with a digit.

Examples:

```text
APP_MODE
APP2
VERIQTA_LAB_23
```

Avoid names containing spaces or hyphens when creating shell variables.

For example:

```text
APP-MODE
```

is not a normal Bash variable name.

Do not confuse:

```text
variable name
```

with:

```text
variable value
```

The value may contain spaces when quoted correctly:

```bash
COURSE_NAME="VERIQTA Linux World"
```


# 23. Environment Variables Are Often Application Configuration

Imagine an application that needs:

```text
application mode
region
log level
API endpoint
feature setting
```

An application may be designed to read environment variables such as:

```text
APP_ENV
REGION
LOG_LEVEL
API_URL
FEATURE_MODE
```

For example:

```bash
env APP_ENV=testing printenv APP_ENV
```

Output:

```text

```

The important concept is:

```text
APPLICATION PROCESS
        ↓
receives environment
        ↓
application code may read values
        ↓
behavior may change
```

Environment variables do not magically control applications.

The application must be designed to read and use the variable.

Setting:

```bash

```

# 24. Environment Variable Names Are Application-Specific

Variables such as:

```text
HOME
PATH
TERM
LANG
```

are widely recognized in Unix/Linux environments.

But:

```text
DATABASE_HOST
APP_ENV
LOG_LEVEL
CLOUD_REGION
```

may be meaningful only to particular software.

Never assume:

```text

    ↓
Linux automatically understands its meaning
```

Instead:

```text

        ↓
process receives environment
        ↓
application reads variable
        ↓
application decides what the value means
```

This becomes important in:

- containers,
- CI/CD,
- cloud workloads,
- application deployments,
- system services,
- automation.

# 27. Environment Variables and Process Inheritance

You can now connect this lab with JUN-017.

In JUN-017, you learned:

```text
parent process
        ↓
child process
```

Now add environment inheritance:

```text
PARENT PROCESS
environment:
APP_MODE=training
        │
        │ creates child
        ▼
CHILD PROCESS

```

The child can then:

- use those values,
- change its own copy,
- add values,
- remove values,

A variable may exist in:

```text
your interactive shell
```

but not in:

```text
a process that was started elsewhere
```

# 28. Controlled Failure — Variable Exists but Child Cannot See It

Return to your normal lab shell.

Create:

```bash
LAB_REGION="east"
```

Verify:

```bash
echo "$LAB_REGION"
```

You should see:

```text
east
```

Now:

```bash
printenv LAB_REGION
```

It should normally show nothing.

Start:

```bash
bash
```

Inside:

```bash
echo "$LAB_REGION"
```

The value should not be present.

Exit:

```bash
exit
```

### Symptom

The current shell can display `LAB_REGION`, but the child cannot.

### Evidence

Parent shell expansion:

```bash
echo "$LAB_REGION"
```

returns:

```text
east
```

while:

```bash
printenv LAB_REGION
```

does not show an exported environment value.

The child also cannot see it.

### Hypothesis

`LAB_REGION` exists only as a shell variable and was not exported before the child started.

### Fix

Run:

```bash
export LAB_REGION
```

Then create a **new** child:

```bash
bash
```

Inside:

```bash
printenv LAB_REGION
```

You should now see:

```text
east
```

Exit:

```bash
exit
```

### Root Cause

The variable was not exported into the environment inherited by the child.

### Prevention

When an application requires an environment variable, verify that the process is actually started with that variable in its environment.

# 31. Sensitive Values Require Care

Environment variables are frequently used to pass configuration.

Some systems also use them for sensitive values such as:

```text
tokens
credentials
API keys
password-like secrets
```

This requires caution.

Do not use real credentials in this lab.

Do not paste secrets into:

```text
screenshots
GitHub issues
README files
support tickets
chat messages
terminal recordings
public documentation
```

Do not assume:

```text
environment variable
=
secret vault
```

An environment variable is a configuration-delivery mechanism, not automatically a secure secret-management system.

The visibility and exposure risks depend on:

# 39. Knowledge Check

### 1. What is a shell variable?

A named value maintained by the current shell.

### 2. Is every shell variable automatically part of the environment supplied to child processes?

No.

### 3. What does `export` do?

It marks a shell variable so its value is included in the environment supplied to subsequently created child processes.

No.

No.

They make the variable-name boundary explicit when needed.

```bash

```

Normally, no.

Yes.

No.

The child has its own process environment.

No.

The shell expands the variable inside double quotes.

The variable reference is preserved literally because single quotes prevent that expansion.

The path to the user's home directory.

It participates in locating commands when an explicit command path is not supplied.

No.

No.

No.

No.

From parent process to newly created child process.

# 40. Interview Practice

### What is an environment variable?

An environment variable is a named value included in a process's environment and available to software that reads it.

### What is the difference between a shell variable and an environment variable in Bash?

A shell variable exists in the current shell. When it is exported, its value is included in the environment supplied to subsequently created child processes.

### What does `export` do?

It marks a shell variable for inclusion in child-process environments.

### Does export make a variable global across the whole operating system?

No. Its effect follows the process environment and inheritance model.

### Does export make a variable permanent?

No. Persistence requires separate configuration.

### How can you inspect an environment variable?

For example:

```bash
printenv HOME
```

### How can you display the current environment?

```bash
env
```

### Why can `echo "$VAR"` display a value when `printenv VAR` does not?

Because `VAR` may exist only as a shell variable and may not have been exported.

### How do child processes receive environment variables?

A child receives an environment when it is created. Exported values from the parent can be included in that environment.

### Can a child process change its parent's environment?

Not through normal environment inheritance. It can change its own environment and pass values to its own descendants.

### If I export a new value, will already-running processes automatically receive it?

No. Existing processes do not automatically synchronize their environments with later changes in the parent.

### What does `unset` do?

It removes the named variable from the current shell.

### What does `env NAME=value command` do?

It runs the command with the supplied environment value without permanently changing that value in the current shell.

### Why are environment variables useful?

They provide a common way to pass configuration and execution context to processes.

### Are environment variables safe for secrets?

They are not automatically secure secret storage. Sensitive values require appropriate secret-management and exposure controls.

### What is PATH?

PATH is an environment variable containing a sequence of directories used during command lookup. Its detailed behavior is covered in the next lab.

### Why can an application launched by systemd have different environment variables from your interactive shell?

Because it is started by a different parent and receives an environment according to that service's startup context rather than automatically inheriting your interactive shell's current environment.

### How would you troubleshoot an application that says an environment variable is missing?

I would verify the exact variable name and case, determine whether it is defined and exported in the relevant process context, identify which process launches the application, check whether the application was started after the value became available, and confirm that the application actually expects that variable.
