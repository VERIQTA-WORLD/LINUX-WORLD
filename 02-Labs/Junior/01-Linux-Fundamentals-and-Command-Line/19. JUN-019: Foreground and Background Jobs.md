# JUN-019: Foreground and Background Jobs

- **Level:** Junior  
- **Difficulty:** 2/5  
- **Estimated time:** 75–100 minutes  
- **Environment:** Ubuntu Server 24.04 LTS or a similar Linux system  
- **Privileges:** Standard user; no `sudo` required  
- **Primary skills:** Foreground jobs, background jobs, shell job control, `&`, `jobs`, job IDs, `%` job specifications, `Ctrl+Z`, `bg`, `fg`, `jobs -l`, process/job relationships, safe job cleanup  
- **Prerequisites:** JUN-001 through JUN-018

---

## Lab Mission

You already know that Linux can run many processes at the same time.

You also know how to inspect processes and send signals to them.

But there is another layer between you and some of those processes:

```text
your interactive shell
```

When you type:

```bash
sleep 60
```

your shell normally waits while that command runs in the **foreground**.

When you type:

```bash
sleep 60 &
```

your shell starts the command as a **background job** and gives you the prompt back.

You can also temporarily stop a foreground job:

```text
Ctrl+Z
```

continue it in the background:

```bash
bg
```

or return it to the foreground:

```bash
fg
```

This is called **job control**.

Job control is not the same thing as general Linux process management.

That distinction matters.

A process has a:

```text
PID
```

A shell-managed job has a:

```text
job ID
```

These identifiers belong to different layers.

By the end of this lab, you should be able to manage several commands from one interactive shell without confusing:

```text
PROCESS
JOB
PID
JOB ID
FOREGROUND
BACKGROUND
STOPPED
RUNNING
```

Your operating model will become:

```text
COMMAND
   ↓
SHELL STARTS JOB
   ↓
FOREGROUND OR BACKGROUND?
   ↓
OBSERVE
   ↓
STOP / CONTINUE / FOREGROUND / BACKGROUND
   ↓
VERIFY
   ↓
CLEAN UP
```

# 1. The Shell Is Managing More Than Commands

When you enter a command at an interactive shell, the shell does more than read text.

It may:

```text
parse the command
        ↓
start a process
        ↓
place it in a job
        ↓
decide whether that job is foreground or background
        ↓
track its state
        ↓
report state changes to you
```

Consider:

```bash
sleep 30
```

The shell starts the command and normally waits.

During that time, you do not receive your normal interactive prompt back until the command finishes or something changes its state.

Now compare:

```bash
sleep 30 &
```

The shell starts the command but does not wait for it to finish before returning the prompt.

This is the foundation of shell job control.

---

# 2. Foreground Jobs

A **foreground job** is the job currently attached to the terminal's foreground process group under the shell's job-control model.

At this stage, you do not need to master process-group internals.

Operationally, think of it as:

```text
FOREGROUND JOB
        ↓
currently interacting with terminal
        ↓
shell waits for it
```

Run:

```bash
sleep 10
```

While it runs, your shell does not immediately present another prompt.

After approximately ten seconds, the command completes and your prompt returns.

That command was running in the foreground.

---

# 3. Why Foreground Execution Is Useful

Foreground execution is appropriate when you want to:

- interact directly with a program,
- see its output immediately,
- provide keyboard input,
- wait for completion,
- interrupt it from the terminal,
- keep your attention on one active command.

Many commands you have used throughout Linux World have run in the foreground.

For example:

```bash
ls
```

usually finishes so quickly that the foreground relationship is barely noticeable.

But:

```bash
sleep 30
```

makes the behavior obvious.

# 5. Job ID vs PID

This distinction is central to the lab.

A:

```text
PID
```

belongs to Linux process management.

A:

```text
job ID
```

belongs to the current shell's job-control system.

Conceptually:

```text
SHELL
  │
  └── JOB [1]
         │
         └── PROCESS PID 18452
```

The shell may refer to the job as:

```text
%1
```

Linux process tools may refer to the process as:

```text
18452
```

These are different namespaces for different purposes.

Do not run:

```bash
kill 1
```

when you mean:

```bash
kill %1
```

Those are dramatically different targets.

`1` means PID 1.

`%1` means job 1 in the current shell.

The `%` matters.


You may see something structurally similar to:

```text

```

The exact spacing may differ.

This tells you:

```text
[1]

command
```

The:

```text
+
```

has meaning too.

For now, understand that it marks the shell's **current job**, which is commonly the default target for commands such as `fg` or `bg` when you do not specify another job.

We will make that clearer when multiple jobs exist.

Run:

```bash

```

The `-l` option includes process ID information.

You may see:


```text
JOB ID
[1]

PID
18452
```

```bash

```

```text

```

# 8. `jobs` Only Knows About the Current Shell's Jobs

This is another critical distinction.

Open a second terminal or SSH session.

In Terminal 1, run:

```bash
sleep 180 &
```

Then:

```bash
jobs
```

You should see the job.

Now go to Terminal 2 and run:

```bash
jobs
```

You should not expect Terminal 2's shell to show Terminal 1's job.

Why?

Because:

```text
jobs
```

reports jobs known to the **current shell**.

But from Terminal 2, process tools may still see the process:

```bash
pgrep -a sleep
```

This demonstrates:

```text
PROCESS VISIBILITY
and
SHELL JOB TABLE
```

are not the same thing.

---

# 9. The Shell Job Table

An interactive shell maintains information about jobs it created and is managing.

Conceptually:

```text
SHELL A
├── Job 1
├── Job 2
└── Job 3

SHELL B
├── Job 1
└── Job 2
```

Notice something important:

Both shells can have:

```text
Job 1
```

at the same time.

That is not a conflict.

Job IDs are meaningful within the context of the shell managing them.

Therefore:

> A job ID is not a machine-wide process identifier.

# 10. Bring a Background Job to the Foreground

Start a fresh background job if necessary:

```bash
sleep 120 &
```

Inspect:

```bash
jobs
```

Suppose it appears as:

```text
[1]+  Running                 sleep 120 &
```

Bring it to the foreground:

```bash
fg %1
```

Your prompt should no longer be available while `sleep` remains in the foreground.

You have changed:

```text
BACKGROUND
        ↓
fg %1
        ↓
FOREGROUND
```

You did not create a new `sleep` process merely by using `fg`.

You changed how the shell manages the existing job.

# 11. `Ctrl+Z` Stops a Foreground Job

While the `sleep` command is in the foreground, press:

```text
Ctrl+Z
```

You should receive your shell prompt again.

The shell may display something similar to:

```text
[1]+  Stopped                 sleep 120
```

Now run:

```bash
jobs
```

The job should appear as:

```text
Stopped
```

This is not termination.

The process still exists.

Verify:

```bash
jobs -l
```

Record its PID.

Then:

```bash
ps -p PID -o pid,ppid,user,stat,etime,cmd
```

You should normally see a stopped process state beginning with:

```text
T
```

This connects directly to JUN-017 and JUN-018.

---

# 12. What `Ctrl+Z` Actually Represents

`Ctrl+Z` is not a magical shell pause button.

In an interactive terminal with job control, it normally causes a terminal-generated stop signal to be sent to the foreground process group.

You learned `SIGSTOP` in JUN-018.

`Ctrl+Z` normally involves:

```text
SIGTSTP
```

which means a terminal stop request.

At a junior level, the important distinction is:

```text
SIGSTOP
cannot be caught or ignored

SIGTSTP
terminal stop signal that applications can handle differently
```

Both can result in a stopped process state, but they are not identical signals.

Your operational model is:

```text
Ctrl+Z
        ↓
terminal stop request
        ↓
foreground job stops
        ↓
shell regains terminal control
```

# 14. Return the Background Job to the Foreground

Now run:

```bash

```

The job returns to the foreground.

Your shell waits again.

Press:

```text
Ctrl+C
```

to interrupt this disposable `sleep` process.

The process should terminate.

Your prompt returns.

Check:

```bash

```

The job should no longer be running.

This gives you a complete lifecycle:

```text
START FOREGROUND
        ↓
Ctrl+Z
        ↓
STOPPED
        ↓
bg
        ↓
RUNNING IN BACKGROUND
        ↓
fg
        ↓
RUNNING IN FOREGROUND
        ↓
Ctrl+C
        ↓
TERMINATED
```

# 15. `Ctrl+C` and `Ctrl+Z` Are Not the Same

You have now used both.

### `Ctrl+C`

Normally causes:

```text
SIGINT
```

to be delivered to the foreground process group.

A simple command such as `sleep` normally terminates.

### `Ctrl+Z`

Normally causes:

```text
SIGTSTP
```

to be delivered to the foreground process group.

A simple command such as `sleep` normally stops but remains present.

Conceptually:

```text
Ctrl+C
        ↓
INTERRUPT
        ↓
often termination

Ctrl+Z
        ↓
STOP REQUEST
        ↓
process remains
```

Do not confuse:

```text
stopped
```

with:

```text
terminated
```

# 17. Current and Previous Jobs

When several jobs exist, Bash commonly marks jobs with:

```text
+
```

and:

```text
-
```

The:

```text
+
```

marks the **current job**.

The:

```text
-
```

marks the **previous job**.

For example:

```text
[1]   Running   sleep 200 &
[2]-  Running   sleep 220 &
[3]+  Running   sleep 240 &
```

means:

```text
Job 3 = current job
Job 2 = previous job
```

Other jobs may have no marker.

These markers help the shell choose default targets.

---

# 18. `fg` Without a Job ID

If you run:

```bash
fg
```

without specifying:

```text
%JOB_ID
```

the shell normally selects the current job.

This can be convenient.

It can also be ambiguous to a human reading your work.

When multiple jobs exist, explicit targeting is often clearer:

```bash
fg %3
```

rather than:

```bash
fg
```

The engineering habit is:

> When target ambiguity matters, specify the target.

---

# 19. `bg` Without a Job ID

The same principle applies to:

```bash
bg
```

If a suitable current stopped job exists, Bash can operate on that job without an explicit job specification.

But when several jobs exist, prefer clarity:

```bash
bg %2
```

This makes your intent visible.

---

# 20. Understanding `%1`

When you write:

```bash
fg %1
```

the:

```text
%1
```

means:

```text
job 1 in this shell
```

Likewise:

```text
%2
%3
%4
```

refer to other shell jobs.

The `%` tells the shell:

```text
interpret this as a job specification
```

rather than as an ordinary numeric PID.

This is why:

```bash
kill %1
```

and:

```bash
kill 1
```

are not equivalent.

You learned `kill` in JUN-018.

Because the shell understands job specifications, you can use:

```bash
kill -TERM %1
```

to send `SIGTERM` to the selected job.

Before doing so:

```bash
jobs -l
```

Confirm:

```text
job ID
PID
state
command
```

Then, for a disposable lab job:

```bash
kill -TERM %1
```

Verify:

```bash
jobs
```

and:

```bash
jobs -l
```

If necessary, verify the recorded PID:

```bash
ps -p PID -o pid,ppid,user,stat,cmd
```

This connects shell job control with Linux signals.

# 22. Do Not Confuse Job IDs with PIDs

Suppose:

```text
[2]  18452 Running sleep 220 &
```

Then:

```text
2
```

is the job ID.

```text
18452
```

is the PID shown for that job.

These commands target different identifier types:

```bash
fg %2
```

targets shell job 2.

```bash
kill -TERM 18452
```

targets process PID 18452.

```bash
kill -TERM %2
```

uses the shell's job specification to target job 2.

But:

```bash
kill -TERM 2
```

targets PID 2—not job 2.

That can be a completely unrelated system process.

Never remove `%` casually when working with job IDs.

---

# 23. Background Does Not Mean Stopped

This is another common beginner mistake.

A background job can be:

```text
running
```

A stopped job can be:

```text
not executing
```

These are separate dimensions.

Conceptually:

```text
FOREGROUND + RUNNING

BACKGROUND + RUNNING

STOPPED
```

For example:

```bash
sleep 200 &
```

creates a running background job.

But:

```text
Ctrl+Z
```

on a foreground `sleep` normally creates a stopped job.

Then:

```bash
bg
```

continues it as a running background job.

So:

```text
background
```

does not mean:

```text
paused
```

---

# 24. Background Does Not Mean Detached

Another important boundary:

```text
BACKGROUND
```

does not automatically mean:

```text
independent of the shell
```

A background job is still associated with the shell's job-control environment.

This lab does not yet teach techniques for deliberately keeping commands alive independently of an interactive terminal or shell session.

For now, remember:

> `&` means "run this as a background job." It does not mean "turn this into a permanent service."

Do not use:

```bash
command &
```

as a substitute for proper service management.

You will learn systemd next.

# 26. Job Completion Is Not a Failure

If:

```bash
jobs
```

no longer lists your `sleep 10` job after it completed, that is normal.

Do not conclude:

```text
job disappeared unexpectedly
```

without considering its expected runtime.

This connects directly to process lifetime from JUN-017.

Ask:

```text
Was the command expected to finish?
How long was it supposed to run?
Did it complete normally?
```

A finished job should not remain active forever.

# 27. Job State Can Change Between Commands

Job information is time-sensitive.

Imagine:

```text
10:00:00
jobs
[1] Running sleep 5 &

10:00:06
sleep has completed

10:00:07
jobs
job no longer active
```

That does not mean:

```text
jobs lost the process
```

The underlying command finished.

Like process investigation, job control requires awareness of time.

# 33. Job Control and Signals Work Together

JUN-018 and JUN-019 are closely connected.

You learned:

```text
SIGINT
SIGTERM
SIGSTOP
SIGCONT
```

Now job control adds terminal/shell behavior.

Conceptually:

```text
Ctrl+C
        ↓
SIGINT toward foreground process group

Ctrl+Z
        ↓
SIGTSTP toward foreground process group

bg
        ↓
shell continues stopped job in background

fg
        ↓
shell places job in foreground
        +
continues it when necessary
```

You do not need to manually send every signal.

The shell provides a job-control interface over the process model.

# 34. `fg` and `bg` Are Shell Builtins

Check:

```bash
type fg
```

Then:

```bash
type bg
```

Then:

```bash
type jobs
```

Bash should identify these as shell builtins.

That makes sense.

The shell itself maintains its job table and controls which jobs are foreground or background.

An external program would not have the same direct relationship with the shell's internal job table.

This is why:

```text
jobs
fg
bg
```

belong naturally to shell job control.

# 35. Why a Second Shell Has Its Own Job IDs

Imagine two SSH sessions.

### Shell A

```text
[1] sleep 300
```

### Shell B

```text
[1] another-command
```

Both can legitimately have:

```text
job 1
```

because the identifiers are local to their respective shell job tables.

Therefore, a note such as:

```text
Job 1 failed
```

is incomplete without context.

A better operational record might include:

```text
shell/session context
command
PID
job state
timestamp
```

when those details matter.

# 36. Background Jobs Can Still Produce Terminal Output

Running something in the background does not inherently mean:

```text
silent
```

A background process may still have output connected to the same terminal.

That can cause text to appear while you are typing other commands.

This lab does not yet teach output redirection—that begins in JUN-026.

For now, understand the operational consequence:

> Background execution changes job-control placement. It does not automatically redirect output.

Later you will learn how standard input, standard output and standard error interact with background work.

---

# 37. Background Jobs and Terminal Input

Foreground/background placement also matters for terminal input.

The foreground job is the job intended to interact with the terminal directly.

A background job that attempts to read from the controlling terminal may be stopped by terminal job-control behavior.

You do not need to manufacture that condition in this junior lab.

The important mental model is:

```text
TERMINAL
        ↓
FOREGROUND JOB
        ↓
interactive terminal relationship
```

This is one reason job control is more than:

```text
add &
```

---

# 38. Job Control Is Not Service Management

Suppose you want an application to:

- start at boot,
- restart after failure,
- run under a dedicated identity,
- have controlled dependencies,
- have predictable lifecycle management.

The solution is not simply:

```bash
application &
```

A background shell job is not a production service-management strategy.

You are about to learn the correct system layer:

```text
systemd
```

in JUN-020.

For now:

```text
SHELL JOB CONTROL
```

is for controlling work associated with your interactive shell.

```text
SERVICE MANAGEMENT
```

is a different operational responsibility.

# 39. Troubleshooting Job Control

When job control behaves differently from what you expected, investigate systematically.


# 40. Common Mistakes

### Thinking `&` means "detach permanently"

It means start the command as a background job.

### Thinking background means stopped

A background job can be actively running.

### Thinking `Ctrl+Z` terminates a command

It normally stops the foreground job.

### Thinking `Ctrl+C` and `Ctrl+Z` do the same thing

They normally result in different signals and different outcomes.

### Confusing job IDs with PIDs

`%1` and PID `1` are completely different targets.

### Forgetting `%`

```bash
kill %1
```

and:

```bash
kill 1
```

do not mean the same thing.

### Assuming `jobs` lists every process

It reports jobs known to the current shell.

### Looking for another shell's job with `jobs`

Use process inspection when investigating system-visible processes outside your current shell's job table.

### Guessing a job ID

Run:

```bash
jobs
```

first.

### Using bare `fg` when multiple jobs make intent unclear

Specify:

```bash
fg %JOB_ID
```

### Assuming a completed background job failed because it disappeared

Check whether it was expected to finish.

### Leaving stopped jobs behind

Inspect your job table before leaving the lab.

### Treating background jobs as production services

Use the appropriate service-management layer.

### Killing a job when `bg` or `fg` would solve the actual problem

Understand state before acting.

# 46. Knowledge Check

### 1. What is shell job control?

It is the shell's mechanism for tracking and controlling commands or pipelines associated with an interactive shell session, including foreground, background and stopped jobs.

### 2. What is a foreground job?

A job currently placed in the terminal's foreground under the shell's job-control model.

### 3. What is a background job?

A job allowed to run without occupying the shell's foreground position.

### 4. How do you start a command as a background job?

Append:

```bash
&
```

For example:

```bash
sleep 60 &
```

### 5. What might Bash print when a background job starts?

A job ID and process ID, such as:

```text
[1] 18452
```

### 6. What does `[1]` represent?

The shell job ID.

### 7. What does `18452` represent in that example?

A process ID associated with the started job.

### 8. Are job IDs and PIDs the same thing?

No.

### 9. Are job IDs system-wide?

No. They belong to a shell's job-control context.

### 10. What does `jobs` show?

Jobs tracked by the current shell.

### 11. Does `jobs` list every process on Linux?

No.

### 12. What does `jobs -l` add?

Process ID information.

### 13. What does `%1` mean?

Job 1 in the current shell.

### 14. Is `%1` the same as PID 1?

No.

### 15. Why is the `%` important?

It identifies a shell job specification rather than an ordinary numeric PID.

### 16. What does `fg` do?

It places a selected job in the foreground and continues it if necessary.

### 17. What does `bg` do?

It continues a stopped job in the background.

### 18. What does `Ctrl+Z` normally do in an interactive job-control terminal?

It normally causes a terminal stop signal, `SIGTSTP`, to be delivered to the foreground process group.

### 19. Does `Ctrl+Z` normally terminate the process?

No.

### 20. What process state may appear afterward?

A stopped state commonly beginning with `T`.

### 21. What does `Ctrl+C` normally generate for the foreground process group?

`SIGINT`.

### 22. Are `Ctrl+C` and `Ctrl+Z` equivalent?

No.

### 23. What does `Ctrl+C` commonly do to a simple `sleep` process?

Interrupts it, causing it to terminate.

### 24. What does `Ctrl+Z` commonly do to `sleep`?

Stops it while leaving the process present.

### 25. What does `bg %1` mean?

Continue job 1 in the background.

### 26. What does `fg %1` mean?

Place job 1 in the foreground.

### 27. What does `+` commonly indicate in `jobs` output?

The current job.

### 28. What does `-` commonly indicate?

The previous job.

### 29. What can plain `fg` use as its target?

Normally the current job.

### 30. Why might explicit `fg %2` be better when multiple jobs exist?

It makes the intended target clear.

### 31. Can a background job still be running?

Yes.

### 32. Does background mean stopped?

No.

### 33. Does background automatically mean detached from the shell?

No.

### 34. Does `&` turn a command into a production service?

No.

### 35. Can a background job still write to the terminal?

Yes, depending on how its output is connected.

### 36. Why doesn't another shell's `jobs` command necessarily show your job?

Each shell maintains its own job table.

### 37. Can process tools still see a process created by another shell?

Potentially yes, subject to normal visibility and permission conditions.

### 38. What happens when a background command completes naturally?

The shell records the completion and may report the job as done before removing it from the active job list.

### 39. Is disappearance from `jobs` always an error?

No. The job may have completed normally.

### 40. What does `fg %99` do if job 99 does not exist?

The shell reports that the job cannot be found.

### 41. What should you do instead of guessing job IDs?

Run `jobs` or `jobs -l`.

### 42. Can `kill` use a shell job specification?

Yes, in a shell that supports job specifications.

### 43. What does this mean?

```bash
kill -TERM %2
```

Send `SIGTERM` to job 2 as resolved by the current shell.

### 44. Why is this different?

```bash
kill -TERM 2
```

It targets PID 2 rather than shell job 2.

### 45. Is `bg` the same as `SIGCONT`?

Not exactly. `bg` is a shell job-control operation that continues a stopped job in the background; continuation involves the process-control mechanisms underneath.

### 46. Is `fg` just another name for `SIGCONT`?

No. It changes the job's foreground placement and continues it when necessary.

### 47. Why are `jobs`, `fg` and `bg` shell builtins?

Because the shell itself maintains the job table and foreground/background job-control state.

### 48. Should shell backgrounding replace system service management?

No.

### 49. What should you inspect before leaving an interactive lab session?

The current shell's job table and any remaining lab processes.

### 50. What is the central job-control model?

```text
start
→ foreground/background
→ inspect
→ stop if needed
→ fg/bg deliberately
→ verify
→ complete or terminate safely
→ clean up
```

# 47. Interview Practice

### What is the difference between a foreground and background job?

A foreground job is currently attached to the terminal's foreground under the shell's job-control model, while a background job can continue without occupying the shell's foreground position.

### How do you start a command in the background?

Append `&`:

```bash
sleep 60 &
```

### How do you list jobs in Bash?

```bash
jobs
```

### How do you include process IDs?

```bash
jobs -l
```

### What is the difference between a job ID and a PID?

A job ID is assigned and tracked by the shell for job control. A PID identifies a process in Linux. They are different identifiers.

### What does `%1` mean?

It refers to job 1 in the current shell.

### Why is `%1` different from `1`?

`%1` is a shell job specification. A plain numeric `1` used as a process target means PID 1.

### How do you bring job 2 to the foreground?

```bash
fg %2
```

### How do you continue a stopped job in the background?

```bash
bg %JOB_ID
```

### What does `Ctrl+Z` normally do?

It normally causes `SIGTSTP` to be sent to the foreground process group, which commonly stops the job and returns control to the shell.

### What is the difference between `Ctrl+C` and `Ctrl+Z`?

`Ctrl+C` normally generates `SIGINT`, commonly interrupting a simple foreground process. `Ctrl+Z` normally generates `SIGTSTP`, commonly stopping the foreground job without terminating it.

### How can you verify that a stopped job still has a process?

Use `jobs -l` to obtain the PID and inspect it with `ps`.

### Why might `jobs` not show a process that you know exists?

The process may not be a job tracked by the current shell. For example, it may have been started by another shell or another system component.

### Can two shells both have a job numbered 1?

Yes. Job IDs are local to each shell's job-control context.

### Does running a command with `&` detach it permanently?

No. It makes it a background job; that is not the same as making it independent of the shell session.

### Is a background job a Linux service?

No. Shell job control and system service management are different layers.

### What does the `+` marker in `jobs` mean?

It commonly identifies the current job, which is the default target for certain job-control operations when no explicit job is supplied.

### What does the `-` marker mean?

It commonly identifies the previous job.

### How would you safely manage several long-running commands in one shell?

I would start appropriate commands as background jobs, inspect them with `jobs -l`, record their job IDs and PIDs, explicitly target jobs with `%JOB_ID`, use `fg` and `bg` deliberately, verify state changes, and clean up only the jobs I created.

### Why should you avoid confusing job IDs and PIDs?

Because they belong to different namespaces, and using a numeric PID when I intended a shell job could target a completely different process.
