# JUN-025: Shell Configuration

- **Level:** Junior  
- **Difficulty:** 2/5  
- **Estimated time:** 75–100 minutes  
- **Environment:** Ubuntu Server 24.04 LTS with Bash  
- **Privileges:** No `sudo` required  
- **Primary skills:** Bash startup files, `.bashrc`, `.profile`, interactive shells, login shells, persistent user environment configuration, aliases, persistent PATH configuration, safe configuration testing and recovery  
- **Prerequisites:** JUN-001 through JUN-024

---

## Lab Mission

In JUN-023, you learned that:

```bash
export APP_ENV="training"
```

changes the environment of your current shell and future child processes.

In JUN-024, you temporarily changed:

```bash
export PATH="$HOME/some-directory:$PATH"
```

and proved that PATH ordering affects command resolution.

But there was an important limitation:

```text
you close the shell
        ↓
start a new session
        ↓
your temporary changes may be gone
```

Linux users therefore need a controlled way to configure future shell sessions.

With Bash, that involves **shell startup files**.

Files such as:

```text
~/.bashrc
~/.profile
```

can influence shell environments when Bash or the login environment starts under the appropriate conditions.

But these files are not interchangeable, and editing them carelessly can break:

- command lookup,
- aliases,
- environment variables,
- interactive shell behavior,
- future terminal sessions.

Your mission is to learn the startup model before making persistent changes.

The engineering model for this lab is:

```text
IDENTIFY SHELL
      ↓
IDENTIFY SHELL CONTEXT
      ↓
IDENTIFY RELEVANT STARTUP FILE
      ↓
BACK UP CONFIGURATION
      ↓
MAKE ONE CONTROLLED CHANGE
      ↓
LOAD / START APPROPRIATE SHELL
      ↓
VERIFY BEHAVIOR
      ↓
TEST A NEW SHELL
      ↓
REMOVE TEST CONFIGURATION
      ↓
VERIFY RECOVERY
```

The goal is not to fill `.bashrc` with customizations.

The goal is to understand **where shell configuration belongs, when it is read, and how to change it safely**.

# 2. Shell Configuration Is About Future Shell Behavior

Suppose you run:

```bash
export VERIQTA_MODE="training"
```

Verify:

```bash
printenv VERIQTA_MODE
```

The variable exists in the current environment.

But that command alone does not mean:

```text
every future login
every future terminal
every shell on the machine
every user
every systemd service
```

will automatically receive that value.

Interactive commands change the current shell state.

Persistent shell configuration uses startup files that are read when particular shell contexts begin.

Think:

```text
CURRENT SHELL COMMAND

export VERIQTA_MODE="training"
        ↓
current shell changes
        ↓
future children may inherit it
```

versus:

```text
STARTUP FILE
        ↓
appropriate future shell starts
        ↓
shell reads configuration
        ↓
configuration establishes shell state
```

Persistence therefore depends on **where the configuration is stored and which startup process reads it**.

# 3. Interactive Shells and Login Shells

Two terms matter in this lab:

```text
interactive shell
login shell
```

They describe different properties.

An **interactive shell** is a shell intended to interact with a user.

You type commands.

The shell displays prompts and accepts more commands.

A **login shell** is a shell started as part of a login-style session.

These concepts are not opposites.

A shell can be:

```text
interactive + login
interactive + non-login
```

and shells can also run non-interactively.

That matters because Bash does not read every startup file in every situation.

A useful junior-level model is:

```text
BASH STARTS
    ↓
what kind of shell is this?
    ↓
startup behavior depends on context
```

Do not assume:

```text
Bash always reads .bashrc
```

or:

```text
Bash always reads .profile
```

Neither statement is universally correct.

# 6. Bash Login Startup Selection

For an interactive login Bash shell, the simplified startup sequence includes:

```text
/etc/profile
     ↓
then Bash looks for the first available user file from:

~/.bash_profile
~/.bash_login
~/.profile
```

That last part matters.

Bash does **not** simply read all three user files in sequence.

It uses the first readable one it finds in that order.

Conceptually:

```text
LOGIN BASH

~/.bash_profile exists?
       │
   yes ┴ no
    │     ↓
    │   ~/.bash_login exists?
    │        │
    │    yes ┴ no
    │     │     ↓
    │     │   ~/.profile
    ▼     ▼
first applicable file is used
```

Therefore, creating a `.bash_profile` without understanding the existing configuration can unexpectedly prevent `.profile` from being selected directly by Bash during login startup.

That is why configuration changes require context.




# 19. Be Careful with Repeated PATH Modification

There is a subtle issue with configuration such as:

```bash
export PATH="$HOME/linux-world-labs/JUN-025/bin:$PATH"
```

Every time that line runs, it prepends the directory to the current PATH value.

If you repeatedly source `.bashrc`, you may therefore create repeated PATH entries.

For example:

```text
lab-bin:lab-bin:lab-bin:/usr/bin:...
```

The system may still function, but the configuration is untidy and can complicate troubleshooting.

For this junior lab, the important lesson is:

```text
source is useful for testing
but repeatedly sourcing configuration can repeat its effects
```

Do not keep sourcing `.bashrc` unnecessarily.

More advanced conditional configuration and shell scripting patterns come later.


# 24. Controlled Failure — Edited File, Current Shell Unchanged

Ensure `.bashrc` contains:

```bash
export VERIQTA_LAB="JUN-025"
```


The configuration file says:

```text

```

but the current shell still has:

```text

```


Then:


```bash

```

# 26. Controlled Failure — Broken PATH Configuration

You will not intentionally destroy PATH in this lab.

Instead, understand the failure safely.

Suppose someone writes:

```text
export PATH="$HOME/my-tools"
```

instead of:

```text
export PATH="$HOME/my-tools:$PATH"
```

The first version replaces the previous PATH value.

That can remove directories containing normal commands.

The shell may then stop resolving familiar external programs.

The safer pattern when adding a directory at the front is:

```bash
export PATH="$HOME/my-tools:$PATH"
```

The existing PATH is preserved after the new directory.

If PATH becomes damaged in an interactive shell, remember that explicit paths may still work.

For example, if available at that location:

```bash
/usr/bin/ls
```

does not need PATH to discover `ls`.

This connects directly to JUN-024.

The important recovery principle is:

```text
PATH BROKEN
    ↓
do not panic
    ↓
use known explicit paths where appropriate
    ↓
repair the configuration
    ↓
start or reload a clean shell
    ↓
verify command resolution
```

# 30. Keep Secrets Out of Casual Shell Configuration

- accidental repository commits,

- debugging,

Use harmless values only.

# 39. Knowledge Check

### 1. What is a shell startup file?

A configuration file that a shell or login environment may read under specific startup conditions.

### 2. What is `.bashrc` commonly used for?

User-level interactive Bash configuration such as aliases, prompt settings, shell options, and other interactive customizations.

### 3. What is `.profile` commonly used for on Ubuntu?

User-level login-session environment configuration.

### 4. Does Bash read every startup file every time it starts?

No. Startup behavior depends on how Bash was invoked and the shell context.

### 5. What is an interactive shell?

A shell that interacts with a user by accepting commands and presenting an interactive session.

### 6. What is a login shell?

A shell operating in login-shell mode as part of a login-style session.

### 7. Can a shell be both interactive and a login shell?

Yes.

### 8. For an interactive non-login Bash, which user file is normally important?

`~/.bashrc`.

### 9. What is the simplified user-file order for a Bash login shell?

Bash looks for the first readable file among:

```text
~/.bash_profile
~/.bash_login
~/.profile
```

in that order.

### 10. Why can creating `.bash_profile` unexpectedly change behavior?

Because Bash may select it instead of `.profile` during login startup.

### 11. Why might `.bashrc` still be loaded during an Ubuntu login?

Ubuntu's default `.profile` commonly contains logic that sources `.bashrc` when appropriate for Bash.

### 12. Does editing `.bashrc` automatically change the current shell?

No.

### 13. What does `source ~/.bashrc` do?

It reads and executes commands from `.bashrc` in the current shell.

### 14. Is sourcing a file the same as starting a new Bash process?

No.

### 15. Why should you back up `.bashrc` before major changes?

So you have a known-good configuration to restore if the new configuration breaks shell behavior.

### 16. Where would you commonly configure an interactive Bash alias?

`~/.bashrc`.

### 17. Can aliases affect command resolution?

Yes.

### 18. Why should aliases for important commands be used carefully?

They can change what a familiar command name does and create operational or safety problems.

### 19. How can you make a PATH addition reproducible for future interactive Bash shells?

Place an appropriate PATH export in the startup configuration that those shells read, such as `.bashrc` when that scope is intended.

### 20. Why should the existing PATH normally be preserved when adding a directory?

Replacing PATH can remove normal command directories and cause command-resolution failures.

### 21. Does `.bashrc` automatically configure a systemd service?

No.

### 22. Why not?

A systemd service is started through systemd's own process and service configuration rather than automatically through your interactive Bash startup.

### 23. Why can repeatedly sourcing `.bashrc` create repeated PATH entries?

A PATH-prepending line can prepend the same directory again each time it executes.

### 24. Should real secrets be placed casually into `.bashrc`?

No.

### 25. What is the safest general workflow for shell configuration?

Inspect, back up, make a small controlled change, test it, verify a fresh shell, and preserve a recovery path.

# 40. Interview Practice

### What is `.bashrc`?

`.bashrc` is a user-level Bash startup file commonly used for interactive shell configuration.

### What is `.profile`?

`.profile` is commonly used for user login-session environment configuration and may be read by compatible login environments.

### What is the difference between an interactive shell and a login shell?

Interactive describes whether the shell is interacting with a user. Login describes how the shell was invoked and which login startup behavior applies. A shell can be both.

### Does Bash always read `.bashrc`?

No. Bash startup-file behavior depends on how the shell is invoked. Interactive non-login Bash normally reads `.bashrc`, while other contexts have different rules.

### What happens when you run `source ~/.bashrc`?

The current shell reads and executes commands from `.bashrc`, allowing configuration changes to affect that shell without starting another Bash process.

### Why might a change in `.bashrc` not affect an already-running shell immediately?

Editing the file changes data on disk. The existing shell does not automatically re-execute the modified file.

### How would you test a `.bashrc` change safely?

I would back up the original file, make one small change, inspect it, source it if appropriate, verify the expected behavior, then start a fresh interactive Bash and verify again.

### What happens if `.bash_profile` exists?

For a Bash login shell, it can be selected before `.bash_login` or `.profile`, so its presence can change which user login startup file Bash reads.

### How would you persist an interactive Bash alias?

I would place the alias in the appropriate interactive Bash startup configuration, commonly `~/.bashrc`, then test it in a fresh interactive Bash.

### Why can a PATH line in `.bashrc` be dangerous?

A malformed line can remove trusted command directories, introduce untrusted directories, alter command selection, or repeatedly duplicate entries.

### Why doesn't changing PATH in `.bashrc` necessarily change a systemd service's PATH?

The service is not automatically launched through the user's interactive Bash startup process. It receives environment configuration through its own launch context.

### How would you recover from a broken `.bashrc`?

I would use a known-good backup, restore the file, then test the restored configuration in an appropriate shell and verify normal command resolution.

### Why should shell startup files be treated like code?

Their commands execute automatically in relevant shell contexts and can affect environment variables, PATH, aliases, command behavior, and the usability of future sessions.
