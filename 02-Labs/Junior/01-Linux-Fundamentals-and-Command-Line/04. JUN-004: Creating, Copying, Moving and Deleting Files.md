# JUN-004: Creating, Copying, Moving and Deleting Files

- **Level:** Junior  
- **Difficulty:** 1/5  
- **Estimated time:** 60–75 minutes  
- **Environment:** Ubuntu Server 24.04 LTS or a similar Linux system  
- **Privileges:** Standard user account  
- **Primary skills:** Creating, copying, moving, renaming and deleting files and directories  
- **Prerequisites:** JUN-001, JUN-002 and JUN-003

---

## Lab Mission

You now know how to move around a Linux filesystem, inspect paths, distinguish files from directories, and check what kind of object you are dealing with.

The next step is learning how to change that filesystem deliberately.

In this lab, you will create files and directories, copy them, move them to new locations, rename them and remove them when they are no longer needed.

These are basic operations, but they deserve careful practice. A mistyped navigation command is usually easy to recover from. A mistyped deletion command can remove something you intended to keep.

The habit you should develop is simple:

**Inspect first. Change second. Verify afterward.**

By the end of the lab, you should be able to manage files and directories confidently without treating commands such as `cp`, `mv` and `rm` as commands to run blindly.

---

## What you will learn

By the end of this lab, you should be able to:

- Create empty files with `touch`.
- Create directories with `mkdir`.
- Create nested directories with `mkdir -p`.
- Copy files with `cp`.
- Copy directories recursively with `cp -r`.
- Move files and directories with `mv`.
- Rename files and directories with `mv`.
- Delete files with `rm`.
- Delete empty directories with `rmdir`.
- Delete directories recursively with `rm -r`.
- Use interactive confirmation where appropriate.
- Recognize when a destination changes the meaning of `cp` or `mv`.
- Understand the difference between copying, moving and renaming.
- Verify filesystem changes after performing them.
- Investigate common file-management errors.
- Use safer habits around destructive commands.

# 3. `touch` has another important behavior

`touch` is often introduced as a command for creating empty files, but that description is incomplete.

If the file does not exist:

```bash
touch example.txt
```

it can create it.

If the file already exists, `touch` normally updates certain timestamps rather than replacing the file with a new empty file.

You can observe this without putting important data at risk.

Run:

```bash
stat notes.txt
```

Look at the timestamps.

Now run:

```bash
touch notes.txt
```

Then:

```bash
stat notes.txt
```

Compare the results.

Depending on how quickly you run the commands and your system's timestamp precision, you should see relevant timestamp changes.

The important lesson is:

**Do not assume that every command has only one behavior just because you first learned it for one purpose.**

# 7. What happens if the directory already exists?

Try:

```bash
mkdir configs
```

You should receive an error similar to:

```text
mkdir: cannot create directory 'configs': File exists
```

Read the error carefully.

The command did not fail because `mkdir` is broken.

It failed because you asked it to create a directory at a path that already exists.

Verify:

```bash
ls -ld configs
```

This is a simple example of a useful Linux habit:

```text
Command fails
    ↓
Read the error
    ↓
Inspect the target
    ↓
Understand the current state
    ↓
Decide what action is actually required
```

Do not respond to every error by adding `sudo`.

Privileges are not the problem here.

# 8. Creating nested directories

Suppose you want this structure:

```text
archive/
└── 2026/
    └── september/
```

Try:

```bash
mkdir archive/2026/september
```

Because `archive` and `archive/2026` do not yet exist, the command should fail.

You may see an error similar to:

```text
No such file or directory
```

`mkdir` cannot create `september` inside parent directories that do not exist unless you tell it to create those parents as well.

Now run:

```bash
mkdir -p archive/2026/september
```

The `-p` option tells `mkdir` to create missing parent directories as needed.

Verify each level:

```bash
ls -ld archive
ls -ld archive/2026
ls -ld archive/2026/september
```

You can also inspect:

```bash
ls archive
```

and:

```bash
ls archive/2026
```

The resulting structure is:

```text
archive/
└── 2026/
    └── september/
```

# 11. Copying while changing the name

`cp` does not require the destination to be an existing directory.

You can also provide a new destination filename.

Run:

```bash
cp notes.txt notes-backup.txt
```

Verify:

```bash
ls -l
```

You should now have both:

```text
notes.txt
notes-backup.txt
```

Conceptually:

```text
source
notes.txt
   │
   └──── copy ────> notes-backup.txt
```

The source remains.

The destination is a separate file.

# 12. Source and destination matter

The basic pattern is:

```text
cp SOURCE DESTINATION
```

For example:

```bash
cp notes.txt backups/
```

means:

> Copy `notes.txt` into the existing `backups` directory.

But:

```bash
cp notes.txt backup-notes.txt
```

means:

> Create a copy of `notes.txt` at the path `backup-notes.txt`.

The meaning of the destination therefore matters.

Before running a copy command, ask:

- What is my source?
- What is my destination?
- Does the destination already exist?
- Is it a file or directory?
- Could an existing file be replaced?

Those questions become increasingly important as you work with real data.

# 14. Copying a directory is different

Try:

```bash
cp configs backups/
```

You should receive an error indicating that `configs` is a directory and was not copied.

A directory can contain other objects, so copying it requires recursive behavior.

Use:

```bash
cp -r configs backups/
```

Here:

```text
-r
```

means recursive.

The command copies the directory and its contents.

Verify:

```bash
ls -l backups/
```

You should now find:

```text
configs
```

inside `backups`.

Inspect further:

```bash
ls -l backups/configs/
```

You should find the copied:

```text
server.conf
```

Your structure now includes:

```text
backups/
└── configs/
    └── server.conf
```

---

# 15. Why recursive copying matters

A directory can contain:

```text
directory/
├── file1
├── file2
└── another-directory/
    └── file3
```

Copying the directory therefore means traversing the directory structure and copying what is beneath it.

That is why recursive operations deserve more attention than copying one file.

The deeper the source tree, the more data an operation can affect.

Before using recursive options on important data, inspect the source and destination carefully.

# 16. Moving a file

Now move the original:

```text
application.log
```

into:

```text
logs/
```

Run:

```bash
mv application.log logs/
```

Verify the current directory:

```bash
ls -l
```

The original `application.log` should no longer appear there.

Now:

```bash
ls -l logs/
```

The file should exist inside `logs`.

This is different from `cp`.

With:

```bash
cp SOURCE DESTINATION
```

the source normally remains.

With:

```bash
mv SOURCE DESTINATION
```

the source path no longer remains at its original location after a successful move.

---

# 17. Copy versus move

Compare these two ideas:

```text
COPY

source
  ├──────────────> destination
  │
  └── still exists
```

and:

```text
MOVE

source ──────────> destination

old source path no longer contains the object
```

This difference seems simple, but confusing the two can matter greatly when working with configuration files, application data or backups.

# 22. Interactive confirmation

For operations where you want confirmation before overwriting an existing destination, GNU `cp` supports:

```bash
cp -i SOURCE DESTINATION
```

The `-i` option requests confirmation before overwriting an existing file.

Try:

```bash
cp -i source-test.txt destination-test.txt
```

You should receive an interactive prompt if the destination would be overwritten.

Answer:

```text

```

for no.

Do not depend on interactive mode as your only safety mechanism.

The stronger habit is still:

```text
inspect → understand → execute → verify
```

Interactive confirmation is an additional safeguard.

# 25. `rm` is not an undo command

When you run:

```bash
rm file
```

you should not assume there is a simple command-line undo operation that will restore it.

On real systems, recovery may be difficult, unreliable or impossible depending on the filesystem and what happened afterward.

That is why the right question before deletion is not:

> Can I recover this later?

The better question is:

> Have I verified that this is the correct object to remove?

# 30. Why recursive deletion requires extra care

Consider:

```text
project/
├── configs/
├── logs/
├── scripts/
├── backups/
└── data/
```

A recursive deletion aimed at `project/` can affect everything beneath that directory.

The consequences therefore depend heavily on the path you provide.

This is why:

```bash
rm -r DIRECTORY
```

should never become a command you type mechanically.

Before recursive deletion, verify:

```bash
pwd
```

Inspect the target:

```bash
ls -ld TARGET
```

Inspect its contents:

```bash
ls -la TARGET
```

Only then decide whether removal is appropriate.

---

# 31. Be especially careful with `rm -rf`

You will see commands on the internet that use:

```text
rm -rf
```

Understand what the options mean before using them.

With GNU `rm`:

```text
-r
```

means recursive.

```text
-f
```

means force. Among other behavior, it suppresses prompts for nonexistent files and ignores nonexistent operands.

Together, they can remove directory trees with very little interaction.

That makes `rm -rf` useful in legitimate automation and cleanup tasks, but it also makes mistakes more dangerous.

You do **not** need `rm -rf` for the normal exercises in this lab.

Do not add `-f` merely because you saw it in somebody else's command.

Use only the options you actually need.

---

# 32. Never copy destructive commands blindly

A command copied from documentation, a forum, a message, a script, an AI assistant or another engineer can still be wrong for your machine.

Before running a destructive command, identify:

- The command
- The options
- The target
- Whether the target is absolute or relative
- Your current directory
- What exists beneath the target
- Whether the operation is reversible
- Whether the command requires elevated privileges

You learned how to inspect command documentation in JUN-002.

Use it:

```bash
rm --help
```

If manual pages are available:

```bash
man rm
```

Do the same for:

```bash
cp --help
mv --help
mkdir --help
```

The objective is not to memorize the documentation.

The objective is to become comfortable checking it before using unfamiliar options.

```bash

```

# 40. Copying is not a backup strategy by itself

You have created files inside:

```text
backups/
```

during this lab.

That does not automatically make this a proper backup system.

A reliable backup strategy involves questions such as:

- What is being backed up?
- How often?
- Where is the backup stored?
- Is it isolated from the original failure?
- How long is it retained?
- Has restoration been tested?
- What happens if the original server is lost?

Those subjects appear later in Linux World.

For this lab, `backups/` is simply a directory name used for practice.

# 46. A safer way to think about file operations

Before performing a filesystem operation, think in terms of:

```text
SOURCE
DESTINATION
ACTION
EXPECTED RESULT
VERIFICATION
```

For example:

```text
Source:
config/app.conf

Destination:
backup/app.conf.backup

Action:
Copy

Expected result:
Both paths should exist.

Verification:
Inspect both source and destination.
```

For a move:

```text
Source:
logs/error.log

Destination:
archive/error-old.log

Action:
Move and rename

Expected result:
Old source path disappears.
New destination path exists.

Verification:
Check both paths.
```

For deletion:

```text
Target:
logs/old/obsolete.log

Action:
Delete

Expected result:
Target disappears.

Preservation requirement:
logs/application.log must remain.

Verification:
Check both the removed target and the file that must remain.
```

This way of thinking becomes much more valuable when the filesystem contains important data.

# 47. Common mistakes to watch for

### Running commands from the wrong directory

A relative path depends on your current location.

Use:

```bash
pwd
```

when location matters.

---

### Confusing source and destination

With:

```bash
cp SOURCE DESTINATION
```

and:

```bash
mv SOURCE DESTINATION
```

the order matters.

Pause long enough to identify both before pressing Enter.

---

### Assuming a path exists

Inspect it.

```bash
ls -ld PATH
```

---

### Assuming a path is a directory

Check:

```bash
file PATH
```

or:

```bash
ls -ld PATH
```

---

### Forgetting that `mv` can rename

Moving and renaming are closely related path operations.

---

### Forgetting recursive behavior for directories

Copying a directory requires recursive handling with the tools used in this lab.

---

### Deleting before inspecting

This is one of the habits you should remove early in your Linux journey.

Inspect first.

---

### Adding `sudo` when a command fails

An error does not automatically mean you need more privileges.

Read the error and determine the cause.

---

### Using `-f` unnecessarily

Force options are not badges of experience.

Use them only when their behavior is actually required and understood.

# 52. Knowledge Check

Try answering these without looking back first.

### 1. Which command can create an empty file?

```bash
touch FILE
```

`touch` can create a file when the specified path does not already exist.

---

### 2. What happens when `touch` is used on an existing file?

It normally updates relevant timestamps rather than replacing the file with a newly empty file.

---

### 3. Which command creates a directory?

```bash
mkdir DIRECTORY
```

---

### 4. What does `mkdir -p` do?

It creates the requested directory and any missing parent directories required for the path.

---

### 5. What is the basic structure of a copy command?

```bash
cp SOURCE DESTINATION
```

---

### 6. Does copying a file normally remove the source?

No. A successful copy leaves the source in place and creates the destination copy.

---

### 7. Why might `cp` need `-r`?

When copying a directory and its contents recursively.

---

### 8. Which command moves a file?

```bash
mv SOURCE DESTINATION
```

---

### 9. Which command is commonly used to rename files in Linux?

```bash
mv
```

Renaming can be performed by moving an object from one path or name to another.

---

### 10. What is the important difference between `cp` and `mv`?

`cp` normally leaves the source in place and creates a copy. `mv` changes the object's path so the old source path no longer contains it after a successful move.

---

### 11. Which command removes a file?

```bash
rm FILE
```

---

### 12. Which command removes an empty directory?

```bash
rmdir DIRECTORY
```

---

### 13. Why does `rmdir` refuse to remove a non-empty directory?

It is designed to remove empty directories, providing a useful safety boundary when contents are still present.

---

### 14. What does recursive deletion mean?

It means the operation descends through a directory tree and removes the directory and objects beneath it.

---

### 15. Why should recursive deletion receive extra attention?

Because one command can affect an entire directory tree rather than a single object.

---

### 16. What does `rm -i` do?

It requests interactive confirmation before removing each specified file.

---

### 17. Why shouldn't you automatically add `sudo` when `cp`, `mv`, `mkdir` or `rm` fails?

Because the failure may be caused by an incorrect path, missing object, wrong object type or another issue unrelated to privileges.

---

### 18. Why is `pwd` useful before a destructive operation involving relative paths?

Because relative paths are interpreted from the current working directory. Confirming your location helps you understand exactly what the target path refers to.

---

### 19. Why should you verify both the target you deleted and nearby data you intended to preserve?

Because safe deletion means not only removing the intended object but also confirming that unrelated required data remains intact.

---

### 20. What is the main safety principle from this lab?

**Inspect first. Change second. Verify afterward.**

# 53. Interview Practice

### How do you create an empty file in Linux?

A common method is:

```bash
touch filename
```

If the file does not exist, `touch` can create it.

---

### How do you create a directory?

```bash
mkdir directory-name
```

---

### How do you create nested directories when the parent directories do not yet exist?

Use:

```bash
mkdir -p parent/child/directory
```

---

### How do you copy a file?

```bash
cp SOURCE DESTINATION
```

---

### How do you copy a directory recursively?

With GNU `cp`, one common form is:

```bash
cp -r SOURCE_DIRECTORY DESTINATION
```

---

### How do you move a file?

```bash
mv SOURCE DESTINATION
```

---

### How do you rename a file?

You can use `mv`:

```bash
mv old-name new-name
```

---

### How do you remove a file?

```bash
rm FILE
```

---

### How do you remove an empty directory?

```bash
rmdir DIRECTORY
```

---

### Why might you prefer `rmdir` when you expect a directory to be empty?

Because it refuses to remove the directory if contents remain, which can help catch an incorrect assumption.

---

### What is the danger of recursive deletion?

A recursive operation can remove an entire directory tree, so an incorrect target path can affect much more data than intended.

---

### What should you check before deleting a directory recursively?

At minimum, verify your current location when relative paths are involved, inspect the target path, inspect its contents, understand the options being used and confirm that the target is actually intended for deletion.

---

### A `cp` command says the source does not exist. What should you do?

Read the error, verify the current directory, inspect the expected source location, check the spelling and capitalization of the path, and determine the actual source path before retrying.

---

### Why is successful command execution not enough to prove that a filesystem task was completed correctly?

Because a command can succeed while producing a result different from what you intended. You should inspect the resulting filesystem state and confirm both the expected changes and anything that should have remained unchanged.
