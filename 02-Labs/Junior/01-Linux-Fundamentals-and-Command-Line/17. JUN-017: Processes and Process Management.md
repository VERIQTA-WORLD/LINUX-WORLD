## Lab Mission

A Linux system is not just files stored on disk.

It is also a constantly changing collection of running processes.

Your SSH session is associated with processes.

Your shell is a process.

System services run as processes.

Web servers run as processes.

Package managers run as processes.

Monitoring agents run as processes.

Applications may create multiple processes.

Even the commands you execute during troubleshooting become processes.

When a production system behaves unexpectedly, one of the first questions is often:

> What is actually running right now?

That question quickly becomes more specific:

```text
Which process is running?
Who owns it?
What is its PID?
Who started it?
What is its parent?
What command launched it?
What state is it in?
How long has it existed?
How much CPU or memory is it using?
Does the process still exist?
What does the kernel know about it?
```

A weak troubleshooting pattern is:

```text
Application looks strange
        ↓
guess process name
        ↓
restart or kill something
        ↓
hope
```

A stronger engineering pattern is:

```text
SYMPTOM
        ↓
IDENTIFY PROCESS
        ↓
CONFIRM PID
        ↓
CONFIRM OWNER
        ↓
INSPECT PARENT
        ↓
INSPECT STATE
        ↓
INSPECT COMMAND
        ↓
INSPECT RESOURCE EVIDENCE
        ↓
CORRELATE
        ↓
DECIDE WHAT ACTION IS JUSTIFIED
```

This lab focuses on the **inspection and reasoning** portion of that workflow.

You will not terminate processes here.

You will first learn how to understand them.

# 1. Start with the Process Mental Model

A **program** is executable code stored somewhere.

A **process** is an executing instance of a program.

For example, a shell executable may exist on disk:

```text
/bin/bash
```

When Bash is running, Linux represents that running instance as a process.

The distinction is:

```text
PROGRAM
code stored on disk
        ↓
executed
        ↓
PROCESS
running instance managed by the kernel
```

One program can have multiple processes.

For example:

```text
PROGRAM
/usr/bin/bash

        ↓

PROCESS
PID 2101

PROCESS
PID 2457

PROCESS
PID 3102
```

These can all be separate running instances of Bash.

Do not identify a process only by program name.

A process has runtime identity.

---

# 2. Every Process Has a PID

Linux assigns each process a numeric:

```text
PID
```

or:

```text
Process ID
```

The PID identifies that process while it exists.

Conceptually:

```text
PID 4217
        ↓
one currently existing process
```

PIDs are not permanent identities.

A process can terminate.

Later, the kernel may reuse that numeric PID for another process.

Therefore:

> A PID identifies a process at a particular point in time. It is not a permanent application identifier.

This becomes important during incident investigation.

# 4. Understand the Basic `ps` Output

The default:

```bash
ps
```

commonly displays fields such as:

```text
PID
TTY
TIME
CMD
```

### PID

The process ID.

### TTY

The terminal associated with the process, if applicable.

An interactive shell connected through a terminal may show something like:

```text
pts/0
```

Not every process has a terminal.

### TIME

CPU time consumed by the process.

Do not confuse this with:

```text
how long the process has existed
```

Those are different measurements.

### CMD

A representation of the command or process name.

Run:

```bash
ps
```

again.

The PID of the new `ps` invocation may differ from the previous one because you created a new process.

# 6. PID and PPID

Processes can create other processes.

The process that creates another process is commonly described as the:

```text
parent process
```

The created process is its:

```text
child process
```

The child's record contains a:

```text
PPID
```

or:

```text
Parent Process ID
```

Conceptually:

```text
PARENT
PID 4000
    │
    └── CHILD
        PID 4012
        PPID 4000
```

Run:

```bash
ps -p $$ -o pid,ppid,user,stat,cmd
```

Record:

```text
Shell PID:
Shell PPID:
```

Now inspect the parent using the numeric PPID you observed:

```bash
ps -p PARENT_PID -o pid,ppid,user,stat,cmd
```

Replace `PARENT_PID` with the actual value.

Depending on how you accessed the machine, the parent might be related to:

- SSH,
- a terminal,
- a login process,
- a container runtime,
- another shell,
- or another environment-specific process.

Do not assume.

Inspect.

---

# 7. Parent-Child Relationships Are Runtime Evidence

Imagine:

```text
sshd
└── bash
    └── application
```

The process tree tells you more than three process names.

It provides evidence about execution ancestry.

During troubleshooting, this can help answer:

```text
Who launched this process?
Did it come from my shell?
Was it created by a service?
Is this process part of a larger application tree?
```

Parent-child relationships are therefore useful investigative evidence.

They do not, by themselves, prove intent or root cause.

# 10. `ps` Is a Snapshot

This is one of the most important lessons in the lab.

Run:

```bash
ps aux
```

You are seeing a snapshot.

Conceptually:

```text
SYSTEM
10:00:00
        ↓
ps snapshot

SYSTEM
10:00:05
        ↓
could already be different
```

Processes can:

- start,
- exit,
- change state,
- consume more CPU,
- consume less CPU,
- create children,
- finish work,

between observations.

Therefore:

```text
ps shows 20% CPU once
```

does not automatically prove:

```text
process continuously uses 20% CPU
```

Resource monitoring over time comes later in the curriculum.

For now:

> Treat `ps` as evidence from a moment, not a complete performance history.

# 11. Build a Useful Process View

Instead of accepting every default field, ask `ps` for the evidence you need.

Run:

```bash
ps -e -o user,pid,ppid,stat,etime,comm
```

You now have:

```text
USER
PID
PPID
STAT
ELAPSED
COMMAND NAME
```

Another useful view is:

```bash
ps -e -o pid,ppid,user,%cpu,%mem,stat,etime,cmd
```

This gives you:

```text
identity
ancestry
ownership
resource snapshot
state
age
command
```

This is much more useful during investigation than blindly reading hundreds of default columns.

# 12. Process Ownership

Every userspace process runs under a user identity.

Inspect:

```bash
ps -e -o user,pid,ppid,comm
```

You will likely see processes belonging to:

```text
root
your user
service accounts
system accounts
```

This connects directly to JUN-011 through JUN-014.

The process owner matters because Linux uses identity when making authorization decisions.

A process running as:

```text
root
```

operates with a very different privilege context from one running as an unprivileged service account.

But remember:

> Seeing `root` does not prove a process is malicious.

Many legitimate system processes require privileged operation.

The correct question is:

```text
Why is this process running under this identity?
```

# 13. Process State

A process is not simply:

```text
running
```

or:

```text
not running
```

Linux tracks process state.

Inspect:

```bash
ps -e -o pid,ppid,stat,comm
```

The first character in the `STAT` field represents the main process state.

Common states include:

```text
R
S
D
T
Z
I
```

You may not see every state on your system.

---

## `R` — Running or Runnable

A process marked:

```text
R
```

is running on a CPU or ready to run.

This does not necessarily mean it is consuming an entire CPU continuously.

---

## `S` — Interruptible Sleep

A process marked:

```text
S
```

is waiting for something and can be awakened by events.

Many healthy processes spend substantial time sleeping.

For example, a server may wait for:

```text
network request
timer
input
work
```

Sleeping does not mean broken.

---

## `D` — Uninterruptible Sleep

A process marked:

```text
D
```

is commonly waiting in an uninterruptible kernel sleep, often associated with I/O.

A brief `D` state can be normal.

A process remaining in `D` unexpectedly may justify deeper investigation into:

```text
storage
filesystem
device
network-backed storage
kernel I/O
```

Do not conclude root cause from the letter alone.

---

## `T` — Stopped

A process marked:

```text
T
```

has been stopped.

You will learn process control and signals in JUN-018 and job control in JUN-019.

For this lab, recognize the state.

Do not manufacture it yet.

---

## `Z` — Zombie

A process marked:

```text
Z
```

is a zombie.

At a junior level, understand this carefully:

The child process has finished execution, but its parent has not yet collected its termination status.

Conceptually:

```text
CHILD FINISHES
        ↓
termination information remains
        ↓
PARENT has not yet collected it
        ↓
ZOMBIE ENTRY
```

A zombie is not a normal running workload consuming CPU.

You will investigate zombie-process incidents much later in Linux World.

---

## `I` — Idle Kernel Thread

On some Linux systems, you may see:

```text
I
```

for idle kernel threads.

Do not assume every state code appears identically across every environment.

Consult:

```bash
man ps
```

when you need exact semantics for your system.

---

# 14. Process State Is Not Process Health

This distinction is critical.

You cannot conclude:

```text
S = healthy
R = unhealthy
D = broken
```

Process state describes what the process is doing from the scheduler/kernel perspective at that moment.

It does not provide a complete application-health verdict.

For example:

```text
Web server
STAT = S
```

could be completely healthy while waiting for requests.

A process in:

```text
R
```

could simply be performing legitimate computation.

Use state as evidence, not as a diagnosis.

---

# 15. Additional `STAT` Characters

You may see states such as:

```text
Ss
S+
Ssl
R+
```

The first character gives the main state.

Additional characters provide other attributes.

For example, depending on `ps` semantics:

```text
s
```

can indicate a session leader.

```text
+
```

can indicate membership in the foreground process group associated with a terminal.

```text
l
```

can indicate a multithreaded process.

You are not expected to memorize every modifier in JUN-017.

When necessary:

```bash
man ps
```

Search the manual for:

```text
PROCESS STATE CODES
```

The professional skill is knowing how to verify meaning rather than inventing it.

# 16. Search for Processes with `pgrep`

Scanning:

```bash
ps aux
```

manually becomes inefficient on busy systems.

`pgrep` can locate processes by matching process attributes.

Try:

```bash
pgrep bash
```

Depending on your system, you may see one or more PIDs.

Now include the process name:

```bash
pgrep -l bash
```

You may see output structurally similar to:

```text
12457 bash
```

Your values will differ.

---

# 17. Process Name vs Full Command Line

This distinction causes real troubleshooting mistakes.

By default, `pgrep` commonly matches the process name used for matching, not every argument in the full command line.

Suppose a process command line contains:

```text
python3 /opt/application/worker.py
```

Its process name may be:

```text
python3
```

Searching only:

```bash
pgrep worker.py
```

may not behave as you expect.

`pgrep` can search the full command line with:

```bash
pgrep -f PATTERN
```

For example:

```bash
pgrep -af bash
```

`-a` displays the full command line for matching processes.

`-f` matches against the full command line.

Use broad patterns carefully.

A pattern can match more processes than you intended.

---

# 18. Do Not Confuse Search Results with Proof

Suppose:

```bash
pgrep -af application
```

returns several processes.

That does not automatically tell you:

```text
which one is broken
which one serves production
which one owns the network port
which one should be terminated
```

Search narrows the investigation.

It does not replace it.

The next step is to inspect:

```text
PID
PPID
USER
STATE
ELAPSED TIME
COMMAND LINE
```

for the relevant process.

# 22. Process Lifetime

A PID exists only while the process exists.

You can observe this safely using:

```bash
sleep 60
```

But running that directly would occupy your current shell for 60 seconds.

Background job control belongs to JUN-019, so we will not use `&` here as a learner requirement.

Instead, open a **second terminal or SSH session**.

### Terminal 1

Run:

```bash
sleep 60
```

Leave it running.

### Terminal 2

Search:

```bash
pgrep -a sleep
```

You should see the running `sleep` process.

Record its PID.

Inspect it:

```bash
ps -p PID -o pid,ppid,user,stat,etime,cmd
```

Replace `PID` with the actual value.

After 60 seconds, run:

```bash
ps -p PID -o pid,ppid,user,stat,etime,cmd
```

again.

The process should no longer exist.

This demonstrates:

```text
PROCESS CREATED
        ↓
PID ASSIGNED
        ↓
PROCESS EXISTS
        ↓
PROCESS COMPLETES
        ↓
PROCESS ENTRY DISAPPEARS
```

# 23. Processes Can Disappear During Investigation

This is normal.

Imagine:

```text
10:00:01
pgrep finds PID 5200

10:00:02
process finishes

10:00:03
ps -p 5200
returns nothing
```

Do not immediately conclude:

```text
ps is broken
```

The process may simply have exited.

Short-lived processes are common.

This creates an important troubleshooting challenge:

> Process evidence can become stale quickly.

Record timestamps and observations when timing matters.

---

# 24. Inspect Elapsed Time

Run:

```bash
ps -e -o pid,etime,comm
```

`ETIME` shows elapsed time since the process started.

This is different from:

```text
TIME
```

which normally represents accumulated CPU time.

Conceptually:

```text
ELAPSED TIME
How long has this process existed?

CPU TIME
How much CPU execution time has it accumulated?
```

A process can exist for:

```text
3 hours
```

while consuming only:

```text
a few seconds of CPU time
```

because it spends most of its time waiting.

---

# 25. Inspect Process Start Time

Run:

```bash
ps -e -o pid,lstart,comm
```

This can display a full process start timestamp.

For a specific process:

```bash
ps -p 1 -o pid,lstart,etime,comm
```

This can help answer questions such as:

```text
Did this process start when the machine started?
Did it restart recently?
Did it begin around the time of an incident?
```

Do not infer causation merely because timestamps are close.

Timestamp correlation generates investigative hypotheses.

It does not automatically prove root cause.

---

# 26. Observe CPU and Memory Evidence

Run:

```bash
ps -e -o pid,user,%cpu,%mem,comm
```

You can also sort the snapshot by CPU:

```bash
ps -e -o pid,user,%cpu,%mem,comm --sort=-%cpu
```

Or memory:

```bash
ps -e -o pid,user,%cpu,%mem,comm --sort=-%mem
```

This is useful for quick triage.

But remember:

```text
ONE PS SNAPSHOT
        ≠
SUSTAINED PERFORMANCE HISTORY
```

You will learn deeper CPU, memory and process monitoring later.

For now, use these values as initial evidence.

---

# 27. Do Not Diagnose from the Highest Number Alone

Suppose your snapshot shows:

```text
process-a  35% CPU
process-b   8% CPU
process-c   1% CPU
```

You cannot automatically conclude:

```text
process-a is the problem
```

Questions remain:

```text
Is 35% expected for this workload?
How many CPUs exist?
Is the process doing legitimate work?
Is the measurement sustained?
Did the incident even involve CPU?
```

Process investigation requires context.

Numbers without context can mislead.

```text

```

Some directory names are numeric:

```text

2
...

```

A numeric directory:


Conceptually:

```text

        ↓
/proc/2450/
```

This gives you another way to investigate process state.

# 31. Inspect the Process Command Line

Run:

```bash
cat /proc/$$/cmdline
```

You may notice the output is not formatted like a normal sentence.

The process command line is stored with null-byte separators rather than ordinary spaces.

Do not modify it.

The important concept is:

```text
/proc/PID/cmdline
```

contains the arguments associated with the process.

`ps` and other tools can present process information in more human-readable forms.

# 32. Inspect the Executable Link

Run:

```bash
ls -l /proc/$$/exe
```

`exe` is a symbolic link representing the executable associated with the process.

For your shell, it may point to something such as:

```text
/usr/bin/bash
```

or another valid shell executable path.

Your environment may differ.

This connects:

```text
PROCESS
        ↓
running executable
        ↓
filesystem object
```


# 38. Process vs Service

Do not use these words as synonyms.

A:

```text
process
```

is a running execution context represented by the kernel.

A:

```text
service
```

is an operational abstraction for providing functionality and may be managed by a service manager such as systemd.

One service might have:

```text
one process
```

or:

```text
multiple processes
```

and not every process is a service.

Conceptually:

```text
SERVICE

        ↓
may involve
        ↓
master process
worker process
worker process
...
```

You will study:

```text

services
units
service lifecycle
```

in JUN-020 through JUN-022.

For now:

> Do not assume one service equals one PID.

# 43. Common Mistakes

### Assuming every process with high CPU is broken

Resource use needs workload context and observation over time.

### Assuming `S` means a process is stuck

Sleeping is normal for many healthy processes.

### Assuming `R` means a process is overloaded

It only indicates running or runnable state at that moment.

### Treating `TIME` as process age

`TIME` and elapsed lifetime are different.

### Searching only by process name

Interpreters such as `python3` or `java` can represent many applications.

### Using a broad `pgrep -f` pattern without inspecting matches

Full command-line matching can return more processes than intended.

### Assuming one application equals one PID

Applications and services may use multiple processes.

### Assuming one service equals one process

Service architecture varies.

### Treating a PID as permanent

PIDs can be reused.

### Assuming a missing PID means a crash

The process may have completed normally.

### Treating process state as an application-health verdict

State is only one piece of evidence.

### Trying to manage unfamiliar kernel threads

Understand what you are looking at first.

### Reaching for `sudo` just to inspect your own processes

Use the least privilege necessary.

### Terminating a process before understanding it

Investigation should precede intervention.

# 49. Knowledge Check

### 1. What is a Linux process?

A process is a running execution instance managed by the kernel.

### 2. What is the difference between a program and a process?

A program is executable code stored on the system. A process is a running instance of that program.

### 3. Can one program have multiple processes?

Yes.

### 4. What is a PID?

A Process ID, which identifies a currently existing process within its PID namespace.

### 5. Is a PID permanent?

No. After a process exits, its PID can eventually be reused.

### 6. What is a PPID?

The Process ID of a process's parent.

### 7. What does `ps` do?

It displays process information.

### 8. Is `ps` generally a historical performance record?

No. It provides process information representing a snapshot when the command gathers it.

### 9. What does `ps -e` request?

All processes visible to the command.

### 10. What does `ps -ef` provide?

A full-format listing of processes.

### 11. What does `ps aux` commonly display?

A broad process listing including ownership, PID, CPU and memory metrics, state and command information.

### 12. What does `USER` indicate?

The user identity associated with the process.

### 13. What does `STAT` show?

The process state plus possible additional status flags.

### 14. What does `R` generally mean?

Running or runnable.

### 15. What does `S` generally mean?

Interruptible sleep.

### 16. Is an `S` process automatically unhealthy?

No.

### 17. What does `D` generally represent?

Uninterruptible sleep, often while waiting in the kernel for I/O-related work.

### 18. Does `D` automatically prove a storage failure?

No.

### 19. What does `T` represent?

A stopped process.

### 20. What does `Z` represent?

A zombie process: a terminated child whose parent has not yet collected its termination status.

### 21. Is a zombie a normally executing CPU workload?

No.

### 22. What is `pgrep` used for?

Finding process IDs by matching process attributes such as process names.

### 23. What does `pgrep -a` add?

It displays matching PIDs with command-line information.

### 24. What does `pgrep -f` change?

It matches against the full command line.

### 25. Why should `pgrep -f` patterns be chosen carefully?

Broad patterns may match more processes than intended.

### 26. What does `pstree` show?

Processes in a parent-child hierarchy.

### 27. Why are parent-child relationships useful?

They provide evidence about how processes were created and how they relate to other running processes.

### 28. What is commonly PID 1 on Ubuntu Server?

On a standard systemd-based Ubuntu Server, it is normally `systemd`.

### 29. Is PID 1 guaranteed to be systemd in every Linux environment?

No.

### 30. What is elapsed time?

How long the process has existed.

### 31. Is `TIME` in common `ps` output the same as elapsed time?

No. It normally represents accumulated CPU time.

### 32. What does `%CPU` provide?

A CPU-use metric for the process according to the semantics of the selected `ps` view.

### 33. Does one high `%CPU` observation prove a process is faulty?

No.

### 34. What does `%MEM` represent?

The process's reported percentage of physical memory.

### 35. What is `/proc`?

A virtual filesystem interface exposing process and kernel information.

### 36. What does `/proc/PID` represent?

Process information for the process with that PID, while it exists and is visible in that PID namespace.

### 37. What can `/proc/PID/status` show?

Information including process name, state, PID, PPID and identity information.

### 38. What is `/proc/PID/exe`?

A symbolic link associated with the process's executable.

### 39. What is `/proc/PID/cwd`?

A symbolic link representing the process's current working directory.

### 40. What happens to `/proc/PID` when the process exits?

That process-specific directory disappears.

### 41. If `ps -p PID` suddenly returns nothing, does that prove the process crashed?

No. It may have completed normally.

### 42. Why can process names such as `python3` be insufficient?

The same runtime can execute many different applications.

### 43. What additional evidence can help identify such a process?

PID, PPID, owner, full command line, executable and process ancestry.

### 44. Is a process the same as a service?

No.

### 45. Can one service have multiple processes?

Yes.

### 46. Is every process a service?

No.

### 47. What are bracketed names such as `[kworker/...]` often associated with?

Kernel threads.

### 48. Should an unfamiliar kernel thread be treated as malicious merely because its name is unfamiliar?

No.

### 49. What should happen before process intervention?

Process identification and evidence-based investigation.

### 50. What is the central workflow from this lab?

```text

→ inspect owner
→ inspect parent
→ inspect state
→ inspect command
→ inspect timing/resources
→ verify through /proc
→ correlate
→ decide
```

# 50. Interview Practice

### What is the difference between a program and a process?

A program is executable code stored on the system. A process is a running instance of that code managed by the kernel.

### What is a PID?

A PID is a Process ID used to identify a currently existing process within its PID namespace.

### What is a PPID?

A PPID is the Process ID of the process's parent.

### How do you list Linux processes?

I can use commands such as `ps`, `ps -e`, `ps -ef`, or `ps aux`, depending on the information I need.

### How would you inspect one specific PID?

For example:

```bash
ps -p PID -o pid,ppid,user,stat,lstart,etime,%cpu,%mem,cmd
```

I can then correlate that information with `/proc/PID`.

### How do you search for a process by name?

I can use:

```bash
pgrep -l NAME
```

or:

```bash
pgrep -a NAME
```

depending on the output I need.

### What if the identifying text is only in the process's full command line?

I can use `pgrep -f`, usually with `-a` for visible command-line evidence, while choosing the search pattern carefully.

### What does the `S` process state mean?

It generally means interruptible sleep. That is normal for many processes waiting for events or work and does not by itself indicate a problem.

### What does `D` mean?

It generally indicates uninterruptible sleep in the kernel, often associated with I/O. I would use it as evidence for further investigation rather than declaring a root cause from the state alone.

### What is a zombie process?

It is a process that has finished execution but still has an entry because its parent has not yet collected its termination status.

### What is `/proc/PID`?

It is a virtual filesystem interface exposing information about a currently existing process.

### How would you determine what executable a process is associated with?

I can inspect:

```bash
ls -l /proc/PID/exe
```

subject to permissions and process lifetime.

### Why might `/proc/PID` disappear while you are investigating?

The process may have exited.

### How would you determine what started a process?

I would inspect its PPID and process ancestry, using tools such as `ps` and `pstree`, and correlate that with other system evidence.

### Why shouldn't you terminate a process simply because it uses the most CPU in one `ps` snapshot?

Because the measurement is only one observation and may represent legitimate temporary workload. I need context and, for performance diagnosis, observations appropriate to the time period involved.

### Is a process the same as a service?

No. A process is a kernel-managed execution instance. A service is an operational abstraction that may consist of one or multiple processes and may be managed by a service manager.

### What information would you collect before controlling an unfamiliar process?

At minimum I would identify its PID, PPID, owner, state, command line, executable, age, relevant resource evidence and process ancestry, then correlate those observations with the reported problem.
