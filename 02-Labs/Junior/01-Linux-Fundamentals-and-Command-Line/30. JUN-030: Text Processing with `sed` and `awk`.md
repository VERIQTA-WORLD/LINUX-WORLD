## 3. Transform Text with `sed`

Start with:

```bash id="88o5h7"
sed 's/production/prod/' services.txt
```

You should see transformed output in the terminal.

Inspect the original file:

```bash id="09wqhz"
cat services.txt
```

It is unchanged.

That is the first important `sed` principle:

```text id="k7nb6u"
sed reads input
     ↓
applies editing instructions
     ↓
writes transformed text to stdout
```

By default, it does **not** rewrite the input file.

### Understand the substitution command

The expression:

```text id="5ws46r"
s/production/prod/
```

can be read as:

```text id="wksm82"
s
│
└─ substitute

production
│
└─ search pattern

prod
│
└─ replacement
```

The `/` characters act as separators in this form.

So:

```bash id="sspmwy"
sed 's/production/prod/' services.txt
```

means:

> For each input line, replace the first matching `production` with `prod`.

### Preview before writing

This is an excellent operational habit.

First:

```bash id="sw5u10"
sed 's/production/prod/' services.txt
```

Inspect the result.

Only when the transformation is correct should you consider redirecting it:

```bash id="0b62y2"
sed 's/production/prod/' services.txt > services-preview.txt
```

Verify:

```bash id="tdktsm"
cat services-preview.txt
```

The workflow is:

```text id="lq70cd"
TRANSFORMATION IDEA
        ↓
PREVIEW TO TERMINAL
        ↓
VERIFY
        ↓
REDIRECT TO NEW FILE
        ↓
VERIFY NEW FILE
```

That is safer than modifying important source data immediately.

## 4. First Match vs Every Match on a Line

Create:

```bash id="4i33qp"
nano replacement-test.txt
```

Enter:

```text id="hnbp59"
error error error
healthy error healthy
```

Save and exit.

Run:

```bash id="7bbpmb"
sed 's/error/ERROR/' replacement-test.txt
```

Notice the first line.

Only the first matching occurrence on each line is replaced.

Now run:

```bash id="edv0fz"
sed 's/error/ERROR/g' replacement-test.txt
```

The trailing:

```text id="sg8r6k"
g
```

means apply the substitution globally across matching occurrences on each line.

The distinction is:

```text id="8t3evf"
s/old/new/
→ first matching occurrence on each line
```

```text id="0dn2qq"
s/old/new/g
→ all matching occurrences on each line
```

Do not interpret `g` as:

> search every line.

`sed` is already processing the input line by line.

Here, `g` changes how many matching occurrences are replaced **within each line**.

## 5. Select and Remove Lines with `sed`

`sed` can address specific lines.

Run:

```bash id="b1lqcw"
sed -n '1p' incidents.log
```

Here:

```text id="cl1s9a"
-n
```

suppresses the normal automatic printing of every input line.

Then:

```text id="6kz59a"
1p
```

means:

> print line 1.

Try:

```bash id="o5pwsp"
sed -n '2p' incidents.log
```

Now print a range:

```bash id="4f6l8k"
sed -n '2,4p' incidents.log
```

This prints lines 2 through 4.

### Why `-n` matters

Compare:

```bash id="6ubfsv"
sed '2p' incidents.log
```

with:

```bash id="t1px3m"
sed -n '2p' incidents.log
```

Without `-n`, `sed` still performs its normal output behavior, and the explicitly printed line can appear in addition to that normal output.

With:

```text id="74iw1v"
-n
```

you suppress automatic output and print only what you explicitly request.

### Delete from the output stream

Run:

```bash id="vpxeqc"
sed '1d' incidents.log
```

The first line is omitted from the output.

The source file remains unchanged.

Try:

```bash id="ah3sp6"
sed '2,4d' incidents.log
```

This removes lines 2 through 4 from the output stream.

The `d` command means:

```text id="k92s9s"
delete this addressed line from sed's current output processing
```

It does not mean:

```text id="i7xw35"
permanently delete those lines from the source file
```

That distinction is essential.

## 6. Understand `awk` Records and Fields

Now move to:

```bash id="us3tb6"
awk
```

`awk` commonly views text as:

```text id="8i69km"
records
   ↓
split into fields
```

By default:

```text id="0fb63k"
one input line
=
one record
```

and whitespace commonly separates fields.

Start with the incident log:

```bash id="q50r9g"
awk '{print $0}' incidents.log
```

`$0` means:

```text id="mqxw63"
the entire current record
```

Now:

```bash id="8id3fk"
awk '{print $1}' incidents.log
```

You should see the first whitespace-separated field:

```text id="jvk9g4"
09:00
09:01
09:02
...
```

Run:

```bash id="vvz8g7"
awk '{print $2}' incidents.log
```

You should see:

```text id="a2pwhz"
INFO
WARN
ERROR
...
```

The model is:

```text id="c1jztr"
INPUT LINE
09:02 ERROR api database timeout
   │
   ▼
awk fields
   │
   ├─ $1 → 09:02
   ├─ $2 → ERROR
   ├─ $3 → api
   ├─ $4 → database
   ├─ $5 → timeout
   └─ $0 → entire line
```

### Print multiple fields

Run:

```bash id="6xwym3"
awk '{print $2, $3}' incidents.log
```

This prints fields 2 and 3 separated by awk's default output field separator, typically a space.

The important distinction from `cut` is that `awk` is not limited to simply selecting a fixed delimiter field.

It can also apply conditions and perform calculations.

## 7. Use a Custom Field Separator

Your `services.txt` file uses:

```text id="kplozq"
|
```

rather than whitespace.

Tell `awk`:

```bash id="n1aef4"
awk -F '|' '{print $1}' services.txt
```

Here:

```text id="o6a94v"
-F '|'
```

sets the input field separator.

Now:

```bash id="pkmdq5"
awk -F '|' '{print $1, $3}' services.txt
```

This prints:

```text id="n3tuxn"
service status
```

for each record.

Compare this with:

```bash id="m38bqu"
cut -d '|' -f 1,3 services.txt
```

Both can extract fields.

So which should you use?

A useful junior rule is:

```text id="1f1ez3"
simple fixed field extraction
→ cut is often enough
```

```text id="bdgdyk"
field extraction + conditions/calculation/formatting
→ awk becomes more useful
```

Do not use a more powerful tool merely because it exists.

Choose the clearest tool for the problem.

## 8. Filter Records by Field Values

Suppose you need:

> Show only production services.

Run:

```bash id="a7j80u"
awk -F '|' '$2 == "production" {print $0}' services.txt
```

Break it down:

```text id="ehh6sl"
-F '|'
→ split fields using |
```

```text id="ahqzj6"
$2 == "production"
→ condition
```

```text id="3cs8jg"
{print $0}
→ action when condition is true
```

Conceptually:

```text id="u8pcqs"
READ RECORD
    ↓
split into fields
    ↓
is $2 equal to production?
    │
 ┌──┴──┐
yes    no
 │      │
 ▼      ▼
print   skip
```

### Show degraded services

```bash id="xb75fn"
awk -F '|' '$3 == "degraded" {print $1, $4}' services.txt
```

This reports the service and latency for degraded records.

### Compare numeric values

Ask:

> Which services have latency greater than 30?

Run:

```bash id="88b4xm"
awk -F '|' '$4 > 30 {print $1, $4}' services.txt
```

You should see services whose fourth field is numerically greater than 30.

This is something `cut` alone cannot express.

`cut` can extract field 4.

It does not decide:

```text id="o2j7od"
only records where field 4 > 30
```

That is where `awk` becomes valuable.

## 9. Format Output and Calculate a Simple Total

Raw input formatting is not always the format you want to report.

Run:

```bash id="csce2i"
awk -F '|' '{print "service=" $1, "status=" $3}' services.txt
```

This creates output such as:

```text id="ktib67"
service=api status=healthy
```

You are not modifying the source.

You are generating a new representation.

### `BEGIN`

`awk` can perform an action before processing input records.

Run:

```bash id="d0qk5n"
awk -F '|' 'BEGIN {print "SERVICE STATUS"} {print $1, $3}' services.txt
```

The `BEGIN` block executes before normal records are processed.

At this level, use it for simple setup or headings.

### Calculate a total

You can also accumulate numeric values.

Run:

```bash id="sk4i7z"
awk -F '|' '{total = total + $4} END {print total}' services.txt
```

The model is:

```text id="w7zvkl"
record 1 → add field 4
record 2 → add field 4
record 3 → add field 4
...
END
 ↓
print total
```

`END` runs after the input has been processed.

This is your first small taste of why `awk` is more than a field extractor.

Do not expand this into complex programming yet.

The goal is to understand:

```text id="mtdazv"
BEGIN
→ before records
```

```text id="yl6qxh"
normal action
→ for matching/current records
```

```text id="3ezgzo"
END
→ after input
```

## 10. Combine the Tools Without Losing the Evidence

Suppose you want to investigate only `ERROR` events.

You already know:

```bash id="2a9chc"
grep "ERROR" incidents.log
```

Now extract the service field:

```bash id="9yv3cn"
grep "ERROR" incidents.log | awk '{print $3}'
```

Then group and count:

```bash id="t8ndkv"
grep "ERROR" incidents.log | awk '{print $3}' | sort | uniq -c
```

The pipeline is:

```text id="j8cx91"
incidents.log
     │
     ▼
grep ERROR
     │
     ▼
error records
     │
     ▼
awk field 3
     │
     ▼
service names
     │
     ▼
sort
     │
     ▼
group identical values
     │
     ▼
uniq -c
     │
     ▼
frequency summary
```

But `awk` can also perform the filtering itself:

```bash id="fhj2t0"
awk '$2 == "ERROR" {print $3}' incidents.log
```

This demonstrates an important engineering principle.

There may be multiple technically valid solutions.

For example:

```bash id="8o2huf"
grep "ERROR" incidents.log | awk '{print $3}'
```

and:

```bash id="cnhyd2"
awk '$2 == "ERROR" {print $3}' incidents.log
```

can produce equivalent results for this dataset.

Your goal is not to maximize the number of commands.

Your goal is to make the transformation:

- correct,
- understandable,
- easy to verify,
- appropriate for the input.

### Save a transformed report

Preview first:

```bash id="qlv9j7"
awk -F '|' '$2 == "production" {print $1, $3, $4}' services.txt
```

If correct, redirect it:

```bash id="lpfocg"
awk -F '|' '$2 == "production" {print $1, $3, $4}' services.txt > production-services.txt
```

Verify:

```bash id="smhbtp"
cat production-services.txt
```

Again:

```text id="c3kfq6"
PREVIEW
   ↓
VERIFY
   ↓
WRITE
   ↓
VERIFY FILE
```

## 11. Controlled Failures and Troubleshooting

### Failure 1 — `sed` changed only one occurrence

Run:

```bash id="4m15z8"
sed 's/error/ERROR/' replacement-test.txt
```

If you expected every `error` on a line to change, the command is incomplete for that goal.

Use:

```bash id="y2ag2d"
sed 's/error/ERROR/g' replacement-test.txt
```

**Root cause:** without `g`, substitution normally affects the first matching occurrence on each line.

---

### Failure 2 — `sed` prints more than expected

Run:

```bash id="sksb9q"
sed '2p' incidents.log
```

If you expected only line 2, you may be surprised.

Use:

```bash id="qlfb7c"
sed -n '2p' incidents.log
```

**Root cause:** normal `sed` behavior prints processed lines unless suppressed with `-n`.

---

### Failure 3 — `awk` prints the wrong field

Run:

```bash id="c0y6y1"
awk -F '|' '{print $3}' services.txt
```

If you expected service names, the tool is not wrong.

Your field assumption is wrong.

Inspect the structure:

```text id="f8i8ls"
$1 → service
$2 → environment
$3 → status
$4 → latency
```

Use:

```bash id="pr9zqp"
awk -F '|' '{print $1}' services.txt
```

---

### Failure 4 — Wrong field separator

Run:

```bash id="l4wj8b"
awk '{print $2}' services.txt
```

Because the file is pipe-delimited and contains no normal whitespace between those fields, the result will not represent the environment field you intended.

Correct it:

```bash id="syjz63"
awk -F '|' '{print $2}' services.txt
```

**Root cause:** your parsing model did not match the input format.

---

### Failure 5 — Text replacement is broader than intended

Remember from JUN-028 that patterns can have regular-expression meaning.

A `sed` substitution pattern is also pattern-based.

Do not blindly assume every character is interpreted literally.

At this level, keep patterns simple and preview the output before writing anything.

---

### Failure 6 — Overwriting the source through careless redirection

Never do this casually:

```text id="3n81xg"
sed '...' important-file > important-file
```

The shell establishes output redirection before the command produces its useful output.

That can truncate the destination.

Use a separate output file:

```bash id="2gr3b4"
sed 's/production/prod/' services.txt > services-new.txt
```

Then verify:

```bash id="nhkw6f"
cat services-new.txt
```

This is a direct application of JUN-026.

---

### Failure 7 — Long pipeline produces the wrong answer

Suppose:

```bash id="r03q0l"
grep "ERROR" incidents.log | awk '{print $3}' | sort | uniq -c
```

looks wrong.

Do not rewrite the entire pipeline.

Run:

```bash id="n4m90c"
grep "ERROR" incidents.log
```

Then:

```bash id="mbztuf"
grep "ERROR" incidents.log | awk '{print $3}'
```

Then:

```bash id="4ks3g6"
grep "ERROR" incidents.log | awk '{print $3}' | sort
```

Finally:

```bash id="4bh2ga"
grep "ERROR" incidents.log | awk '{print $3}' | sort | uniq -c
```

Find the first stage where the output stops matching your expectation.

That stage usually contains the wrong assumption.

## 13. Final Practical — Investigate Before Declaring a Service Problem

A teammate reports:

> `worker` is the main production problem because its latency is high and it appears in warnings.

Use the available data to investigate rather than accepting the claim.

First inspect the worker record:

```bash id="n6n7gx"
awk -F '|' '$1 == "worker" {print $0}' services.txt
```

Now identify all production services that are not healthy:

```bash id="u5szy7"
awk -F '|' '$2 == "production" && $3 != "healthy" {print $1, $3, $4}' services.txt
```

At this point, `&&` is being used inside an `awk` condition to mean both conditions must be true. You have seen `&&` previously in the shell; here it is part of the `awk` expression.

Now identify high-latency services:

```bash id="0v9u2s"
awk -F '|' '$4 > 30 {print $1, $4}' services.txt
```

Inspect worker-related incidents:

```bash id="46sl00"
grep "worker" incidents.log
```

Inspect ERROR incidents:

```bash id="8obmvs"
grep "ERROR" incidents.log
```

Now answer:

```text id="gghu8o"
What is worker's recorded status?

What is worker's recorded latency?

Are there other production services marked degraded?

Are there other services with latency greater than 30?

Does worker appear in an ERROR record?

What does the available evidence actually prove?

Does warning frequency alone prove root cause?

What additional evidence would be needed before declaring worker the primary cause?
```

The engineering lesson is:

```text id="h0cn0h"
TRANSFORM DATA
      ↓
LOCATE RELEVANT RECORDS
      ↓
COMPARE EVIDENCE
      ↓
FORM HYPOTHESIS
      ↓
DO NOT OVERSTATE CONCLUSION
```

`sed` and `awk` help you manipulate and interrogate text.

They do not replace engineering judgment.

## 14. Knowledge Check, Interview Practice, and Cleanup

### Knowledge Check

1. **What is `sed` primarily used for?**  
   Stream-oriented text editing and transformation.

2. **Does `sed 's/old/new/' file` normally modify `file`?**  
   No. It normally writes transformed text to stdout.

3. **What does the `s` command mean in `sed`?**  
   Substitute.

4. **What does the `g` flag do in `s/old/new/g`?**  
   It replaces all matching occurrences on each processed line rather than only the first matching occurrence.

5. **What does `sed -n '3p' file` do?**  
   It suppresses normal automatic output and prints line 3.

6. **What does `sed '3d' file` do?**  
   It omits line 3 from the output stream without normally modifying the source file.

7. **What does `$0` represent in `awk`?**  
   The entire current input record.

8. **What does `$1` represent?**  
   The first field.

9. **What does `-F '|'` do in `awk`?**  
   It sets `|` as the input field separator.

10. **What does `$4 > 30` mean in an `awk` condition?**  
    Process records where field 4 compares numerically greater than 30.

11. **When might `cut` be clearer than `awk`?**  
    When the task is simply extracting fixed fields from predictably delimited text.

12. **When does `awk` become especially useful?**  
    When field extraction needs conditions, calculations, or custom output formatting.

13. **What does an `awk` `BEGIN` block do?**  
    It runs before normal input records are processed.

14. **What does an `awk` `END` block do?**  
    It runs after input processing is complete.

15. **Why should transformations be previewed before redirecting them into files?**  
    To verify that the transformation matches the intended result and reduce the risk of preserving incorrect or destructive output.

### Interview Practice

**What is the difference between `sed` and `awk`?**

`sed` is commonly used for stream-oriented line transformation, substitution, selection, and deletion. `awk` is field-oriented and is especially useful for record conditions, field selection, formatting, and calculations.

**How do you replace every occurrence of one value on each line using `sed`?**

For example:

```bash id="v7qssv"
sed 's/old/new/g' file
```

**How do you print only a specific range of lines with `sed`?**

For example:

```bash id="39o6he"
sed -n '2,5p' file
```

**How do you process pipe-delimited fields with `awk`?**

For example:

```bash id="0tv9s1"
awk -F '|' '{print $1, $3}' file
```

**How do you filter records based on a field value?**

For example:

```bash id="3w3lg4"
awk -F '|' '$3 == "degraded" {print $1}' file
```

**How do you calculate a total from a numeric field with `awk`?**

For example:

```bash id="plfmpp"
awk -F '|' '{total = total + $4} END {print total}' file
```

**Why is redirecting transformed output back to the same source filename dangerous?**

The shell may truncate the destination while establishing redirection before the processing command has read and produced the intended transformed output.

**How would you troubleshoot an incorrect `awk` result?**

I would inspect the raw input, verify the actual delimiter, confirm the field numbers, test the condition separately, simplify the command, and rebuild the transformation progressively.
