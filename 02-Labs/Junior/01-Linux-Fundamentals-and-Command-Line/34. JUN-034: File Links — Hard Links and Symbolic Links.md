## 1. Mission: Understand What a Linux Filename Really Represents

You already know how to create, copy, move, inspect, search, archive, and restore files.

Now you need to understand something deeper:

> A filename is not the file's data itself.

That distinction explains one of the most important filesystem features in Linux:

```text
links
```

Linux supports two major kinds of links:

```text
HARD LINK
```

and:

```text
SYMBOLIC LINK
```

They can appear similar when you use them, but internally they work very differently.

A simplified filesystem model looks like this:

```text
directory entry
     │
     │ contains a name and refers to
     ▼
   inode
     │
     │ describes the filesystem object
     ▼
 file data
```

For a normal regular file, you might think of:

```text
report.txt
    │
    ▼
 inode 48121
    │
    ▼
 file data
```

A hard link creates another directory entry referring to the same inode:

```text
report.txt ─────┐
                │
                ▼
             inode 48121
                │
                ▼
             file data
                ▲
                │
report-link ────┘
```

A symbolic link works differently:

```text
report-symlink
      │
      ▼
symlink object
      │
      │ stores pathname
      ▼
report.txt
      │
      ▼
inode 48121
      │
      ▼
file data
```

This difference explains why:

- hard links share inode numbers;
- symbolic links normally have their own inode;
- deleting one hard-link name does not necessarily remove the data;
- symbolic links can become broken;
- symbolic links can point to directories;
- hard links normally cannot cross filesystem boundaries;
- symbolic links can reference paths on other mounted filesystems;
- renaming a symlink's target can break the link;
- renaming one hard-link name does not break the other names.

### Your mission

You will create a controlled filesystem, inspect inode numbers, create hard and symbolic links, modify data through different names, rename and remove names, intentionally break symbolic links, repair them, and explain exactly what happened.

By the end of this lab, you should be able to answer:

> Is this another name for the same inode, or is this a pathname reference to another object?

That is the core distinction.

### Learning objectives

By the end of this lab, you should be able to:

- explain the difference between a filename, inode, and file data;
- inspect inode numbers;
- inspect hard-link counts;
- create hard links with `ln`;
- prove that two hard-linked names refer to the same inode;
- explain why changing data through one hard link affects the others;
- explain what happens when one hard-link name is removed;
- create symbolic links with `ln -s`;
- inspect symbolic-link targets;
- distinguish a symlink's inode from its target's inode;
- explain absolute and relative symbolic-link targets;
- create symbolic links to directories;
- identify broken symbolic links;
- explain why a symlink can break;
- repair a broken symlink;
- understand the major filesystem limitations of hard links;
- distinguish links from copies;
- troubleshoot link-related problems using evidence.

### Lab boundary

This lab does not cover:

- advanced filesystem internals;
- inode allocation algorithms;
- filesystem forensics;
- bind mounts;
- overlay filesystems;
- mount namespaces;
- advanced `find` link predicates;
- low-level filesystem repair.

The goal is a strong operational understanding of Linux links.

## 3. Create Your First Hard Link

Create a hard link:

```bash
ln documents/service-notes.txt links/service-notes-hard
```

The basic form is:

```text
ln EXISTING_FILE NEW_LINK_NAME
```

Inspect both names:

```bash
ls -li documents/service-notes.txt links/service-notes-hard
```

Look at the inode numbers.

They should be identical.

Conceptually:

```text
documents/service-notes.txt ───┐
                               │
                               ▼
                            inode X
                               │
                               ▼
                            file data
                               ▲
                               │
links/service-notes-hard ──────┘
```

There are now two directory entries referring to the same inode.

### Check the link count

Run:

```bash
stat documents/service-notes.txt
```

Then:

```bash
stat links/service-notes-hard
```

The inode should be the same.

The hard-link count should now reflect the additional hard link.

You can also inspect:

```bash
ls -l documents/service-notes.txt links/service-notes-hard
```

The link-count field should show the relationship.

### Important terminology

It is common to say:

> I created a hard link to the original file.

That is useful conversationally, but internally something more interesting happened.

After the hard link exists, both names refer to the same inode.

Neither pathname is inherently the "real" file while the other is merely a pointer in the same sense as a symlink.

You have:

```text
NAME A ──┐
         ├──> SAME INODE
NAME B ──┘
```

This is one of the most important ideas in the lab.

## 4. Prove That Hard Links Share the Same Data

Read through the original name:

```bash
cat documents/service-notes.txt
```

Now read through the hard-link name:

```bash
cat links/service-notes-hard
```

The content should be identical because both pathnames lead to the same underlying file object.

Now append through the hard-link name:

```bash
printf 'Observation: hard-link write test\n' >> links/service-notes-hard
```

Read through the original name:

```bash
cat documents/service-notes.txt
```

The new line should appear.

Why?

Not because Linux automatically synchronized two independent copies.

There are not two independent copies.

The model is:

```text
documents/service-notes.txt ─┐
                             │
                             ▼
                           inode
                             │
                             ▼
                       SAME FILE DATA
                             ▲
                             │
links/service-notes-hard ────┘
```

You changed the shared data through one pathname.

The other pathname reaches that same data.

### Compare the files

Run:

```bash
cmp documents/service-notes.txt links/service-notes-hard
```

No output normally means the byte content is identical.

But `cmp` alone does not prove a hard-link relationship.

Two separate copies can also contain identical bytes.

The stronger evidence is:

```bash
ls -li documents/service-notes.txt links/service-notes-hard
```

Same inode:

```text
→ same underlying filesystem object
```

for these hard-linked names on the same filesystem.

### Engineer Note

This distinction matters:

```text
same content
≠
same inode
```

Two copied files can contain exactly the same content but have different inodes.

Hard-linked names refer to the same inode.

---

## 5. Prove That a Hard Link Is Not a Copy

Create an actual copy:

```bash
cp documents/service-notes.txt documents/service-notes-copy.txt
```

Now inspect all three:

```bash
ls -li documents/service-notes.txt links/service-notes-hard documents/service-notes-copy.txt
```

You should observe:

```text
service-notes.txt
and
service-notes-hard
→ same inode
```

while:

```text
service-notes-copy.txt
→ different inode
```

Conceptually:

```text
service-notes.txt ─────────┐
                           │
                           ▼
                        inode A
                           │
                           ▼
                        data A
                           ▲
                           │
service-notes-hard ────────┘


service-notes-copy.txt
          │
          ▼
       inode B
          │
          ▼
       data B
```

At the moment of copying:

```text
data A
```

and:

```text
data B
```

may contain the same bytes.

But they are independent filesystem objects.

### Prove independence

Append to the copy:

```bash
printf 'This line exists only in the copy.\n' >> documents/service-notes-copy.txt
```

Inspect the copy:

```bash
tail documents/service-notes-copy.txt
```

Now inspect the hard-linked file:

```bash
tail documents/service-notes.txt
```

The extra copy-only line should not appear there.

This gives you a critical comparison:

| Property | Hard Link | Copy |
|---|---|---|
| Same inode as source | Yes | No |
| Same underlying data object | Yes | No |
| Initially can contain same bytes | Yes | Yes |
| Changes through one pathname affect source data | Yes | No |
| Independent file data after creation | No | Yes |

A hard link is **not** a backup copy.

If the shared underlying data is modified through any hard-linked pathname, every hard-linked name exposes that changed data.

## 6. Remove One Hard-Link Name

Inspect before removal:

```bash
ls -li documents/service-notes.txt links/service-notes-hard
```

Record:

```text
INODE:

LINK COUNT:
```

Now remove the original pathname:

```bash
rm documents/service-notes.txt
```

Verify that pathname:

```bash
ls -l documents/service-notes.txt
```

You should receive a missing-file diagnostic.

Now inspect the hard link:

```bash
ls -li links/service-notes-hard
```

Read it:

```bash
cat links/service-notes-hard
```

The content still exists.

Why?

Because:

```text
rm documents/service-notes.txt
```

removed a directory entry.

It did not necessarily mean:

> destroy the file data immediately.

Before:

```text
documents/service-notes.txt ─┐
                             ├──> inode X → data
links/service-notes-hard ────┘
```

After removing the first name:

```text
links/service-notes-hard
          │
          ▼
       inode X
          │
          ▼
         data
```

The inode still has a hard-linked pathname referring to it.

Inspect:

```bash
stat links/service-notes-hard
```

The hard-link count should now reflect the remaining link.

### Important operational lesson

For ordinary regular files, removing a pathname reduces the hard-link count.

The filesystem can reclaim the file's storage when no directory entries reference the inode **and** no running process still has the file open.

That final qualification matters.

A running process can keep an unlinked file open temporarily even after its last pathname has been removed.

You do not need to reproduce that behavior in this junior lab, but you should know that:

```text
last pathname removed
```

does not always mean:

```text
storage reclaimed at that exact instant
```

## 7. Create and Inspect a Symbolic Link

Recreate a clean target:

```bash
printf 'environment=production\n' > config/application.conf
printf 'port=8080\n' >> config/application.conf
```

Inspect:

```bash
cat config/application.conf
```

Create a symbolic link:

```bash
ln -s ../config/application.conf links/application.conf
```

The basic form is:

```text
ln -s TARGET LINK_NAME
```

Inspect:

```bash
ls -l links/application.conf
```

You should see an arrow similar to:

```text
links/application.conf -> ../config/application.conf
```

The symbolic link stores a pathname.

Conceptually:

```text
links/application.conf
         │
         ▼
     symlink inode
         │
         ▼
"../config/application.conf"
         │
         ▼
config/application.conf
         │
         ▼
     target inode
         │
         ▼
        data
```

### Read through the symlink

Run:

```bash
cat links/application.conf
```

The shell command opens the symlink path, and the kernel resolves the stored target pathname to reach the target object.

You should see:

```text
environment=production
port=8080
```

## 8. Compare Symlink and Target Inodes

Inspect:

```bash
ls -li config/application.conf links/application.conf
```

Unlike hard-linked names, the symbolic link and target should not have the same inode.

Why?

Because the symbolic link is itself a separate filesystem object.

The target is another filesystem object.

Conceptually:

```text
SYMLINK OBJECT
inode A
   │
   ▼
stores target pathname
   │
   ▼
TARGET OBJECT
inode B
   │
   ▼
data
```

### Inspect the symlink itself

Run:

```bash
stat links/application.conf
```

Now:

```bash
stat config/application.conf
```

Compare:

```text
File
Inode
Size
Links
```

Do not expect the symlink's size to equal the target file's data size.

The symlink stores target-path information, not another copy of the target's file content.

### Follow the target deliberately

Run:

```bash
stat -L links/application.conf
```

`-L` tells `stat` to follow the symbolic link.

This is an important troubleshooting distinction:

```text
stat symlink
→ inspect the link object
```

```text
stat -L symlink
→ follow the link and inspect the target
```

When troubleshooting links, always ask:

> Am I inspecting the link itself, or the object it resolves to?

## 9. Relative and Absolute Symbolic Links

Your current symlink contains:

```text
../config/application.conf
```

That is a relative target.

Inspect it:

```bash
ls -l links/application.conf
```

The target is interpreted relative to the directory containing the symbolic link.

Your structure is:

```text
JUN-034/
├── config/
│   └── application.conf
└── links/
    └── application.conf
```

From:

```text
links/
```

the path:

```text
../config/application.conf
```

means:

```text
go up to JUN-034/
then enter config/
then use application.conf
```

### Create an absolute symlink

Determine the full target path:

```bash
pwd
```

Assuming you are still in:

```text
~/linux-world-labs/JUN-034
```

you can create an absolute symlink using the actual absolute path shown by `pwd`.

For example, if `pwd` showed:

```text
/home/student/linux-world-labs/JUN-034
```

the absolute target would be:

```text
/home/student/linux-world-labs/JUN-034/config/application.conf
```

Create:

```text
ln -s /ACTUAL/ABSOLUTE/PATH/config/application.conf links/application-absolute.conf
```

Replace the placeholder with the real path from your environment.

Inspect:

```bash
ls -l links/application-absolute.conf
```

### Relative vs absolute

Relative symlink:

```text
links/application.conf
       │
       ▼
../config/application.conf
```

Absolute symlink:

```text
links/application-absolute.conf
       │
       ▼
/home/.../JUN-034/config/application.conf
```

Neither form is universally superior.

Relative links can remain valid when an entire directory hierarchy is moved together while preserving its internal layout.

Absolute links provide an explicit full target location but depend on that exact path remaining valid.

Choose based on the filesystem layout and operational requirement.


Conceptually:

```text
links/config-current
        │
        ▼
    ../config
        │
        ▼
```

## 11. Break a Symbolic Link on Purpose

Inspect:

```bash
ls -l links/application.conf
```

Verify it works:

```bash
cat links/application.conf
```

Now rename the target:

```bash
mv config/application.conf config/application-v2.conf
```

Inspect the symlink again:

```bash
ls -l links/application.conf
```

The symlink object still exists.

But try:

```bash
cat links/application.conf
```

It should fail because the stored target pathname no longer resolves.

This is a **broken** or **dangling** symbolic link.

Conceptually:

```text
links/application.conf
         │
         ▼
../config/application.conf
         │
         ▼
       X
target pathname no longer exists
```

Notice what did **not** happen:

```text
the symlink was automatically updated
```

A normal symlink stores a pathname.

It does not continuously search for:

> whatever file used to be there.

### Verify the new target exists

Run:

```bash
ls -l config/application-v2.conf
```

The data still exists.

The problem is the pathname stored in the symlink.

This gives you a clean troubleshooting distinction:

```text
target data may still exist elsewhere
```

while:

```text
stored symlink target path is invalid
```

## 12. Repair the Broken Symbolic Link

First inspect the broken link:

```bash
ls -l links/application.conf
```

It still points to:

```text
../config/application.conf
```

But the correct target is now:

```text
../config/application-v2.conf
```

Remove the broken link object:

```bash
rm links/application.conf
```

This removes the symlink.

It does **not** remove:

```text
config/application-v2.conf
```

Verify:

```bash
ls -l config/application-v2.conf
```

Now recreate the symlink:

```bash
ln -s ../config/application-v2.conf links/application.conf
```

Verify the relationship:

```bash
ls -l links/application.conf
```

Test resolution:

```bash
cat links/application.conf
```

You have completed:

```text
SYMPTOM
cat symlink fails
      ↓
INSPECT LINK
ls -l
      ↓
IDENTIFY STORED TARGET
      ↓
VERIFY TARGET PATH
      ↓
DISCOVER PATH NO LONGER EXISTS
      ↓

      ↓

      ↓

```

## 13. Hard Links and Rename Behavior

You have already seen that a symbolic link can break when its stored target pathname changes.

Now compare that with hard links.

Create:

```bash
printf 'hard-link rename test\n' > documents/rename-test.txt
```

Create a hard link:

```bash
ln documents/rename-test.txt links/rename-hard
```

Inspect:

```bash
ls -li documents/rename-test.txt links/rename-hard
```

The inode numbers should match.

Now rename the first pathname:

```bash
mv documents/rename-test.txt documents/rename-test-v2.txt
```

Inspect:

```bash
ls -li documents/rename-test-v2.txt links/rename-hard
```

Read through the hard link:

```bash
cat links/rename-hard
```

It still works.

Why?

Because:

```text
links/rename-hard
```

does not store the pathname:

```text
documents/rename-test.txt
```

Both directory entries independently referred to the same inode.

Before:

```text
documents/rename-test.txt ─┐
                           ├──> inode X
links/rename-hard ─────────┘
```

After rename:

```text
documents/rename-test-v2.txt ─┐
                              ├──> inode X
links/rename-hard ────────────┘
```

The hard link did not need to be updated.

This is one of the clearest differences between hard and symbolic links.

## 14. Understand the Main Hard-Link Restrictions

Hard links are powerful, but they have important restrictions.

### Restriction 1 — Filesystem boundaries

A normal hard link must refer to an inode on the same filesystem.

Why?

Because the hard-link relationship is based on filesystem inode identity.

A pathname on another filesystem cannot simply become another directory entry for the same inode.

So:

```text
filesystem A
    inode 123
```

cannot normally be hard-linked from:

```text
filesystem B
```

as though filesystem B owned that same inode.

Symbolic links do not have that requirement because they store pathnames.

A symlink can reference a pathname that resolves onto another mounted filesystem.

---

### Restriction 2 — Directories

Ordinary users normally cannot create hard links to directories.

This restriction helps protect filesystem hierarchy integrity and prevents problematic directory cycles.

For directory references, symbolic links are normally the appropriate link type.

You have already created:

```text
links/config-current -> ../config
```

That is a normal symlink use case.

---

### Do not memorize only the restrictions

Understand the reason.

Hard link:

```text
another directory entry
        ↓
same inode
```

Symbolic link:

```text
separate filesystem object
        ↓
stores pathname
        ↓
path resolution reaches target
```

The design explains the behavior.

## 15. Hard Link vs Symbolic Link vs Copy

At this point, compare all three models.

### Hard link

```text
name A ─────┐
            ▼
          inode
            │
            ▼
           data
            ▲
            │
name B ─────┘
```

Characteristics:

- same inode;
- same underlying file data;
- changes visible through all hard-linked names;
- removing one name does not break the others;
- normally cannot cross filesystems;
- ordinary users normally cannot hard-link directories.

---

### Symbolic link

```text
symlink
   │
   ▼
stores target pathname
   │
   ▼
target name
   │
   ▼
target inode
   │
   ▼
target data
```

Characteristics:

- symlink has its own inode;
- stores a target pathname;
- can point to directories;
- can reference paths on another filesystem;
- can become broken;
- target rename/removal may invalidate it;
- target and link are distinct filesystem objects.

---

### Copy

```text
original name
     │
     ▼
  inode A
     │
     ▼
   data A


copy name
     │
     ▼
  inode B
     │
     ▼
   data B
```

Characteristics:

- separate inode;
- separate file data;
- changing one does not automatically change the other;
- removing one does not affect the other;
- requires separate storage for the copied file data.

### Comparison table

| Property | Hard Link | Symbolic Link | Copy |
|---|---|---|---|
| Same inode as original regular file | Yes | No | No |
| Separate file data | No | No; link stores target path | Yes |
| Changes to target data visible through both names | Yes | Yes, while symlink resolves to that target | No |
| Can become dangling | Not in the symlink sense while another hard link still names the inode | Yes | No |
| Normally crosses filesystems | No | Yes | Yes |
| Can normally reference directories | Not for ordinary users | Yes | Copying a directory is a different operation |
| Uses target pathname for resolution | No | Yes | No |
| Independent data backup | No | No | Potentially, but backup design requires more than a simple copy |

## 16. Challenge Mode — Investigate Links Without Guessing

You are given a directory containing three paths:

```text
service-a
service-b
service-c
```

You are told:

> Two might refer to the same underlying file. One might be a symbolic link. Determine the relationship using filesystem evidence.

Build your own controlled version.

Create:

```bash
printf 'VERIQTA link investigation\n' > documents/service-a
```

Create:

```bash
ln documents/service-a documents/service-b
```

Create:

```bash
ln -s service-a documents/service-c
```

Do not rely on memory about which command created which relationship.

Investigate them as though someone else created the files.

Use:

```bash
ls -li documents/service-a documents/service-b documents/service-c
```

Then:

```bash
ls -l documents/service-a documents/service-b documents/service-c
```

Then:

```bash
stat documents/service-a
```

```bash
stat documents/service-b
```

```bash
stat documents/service-c
```

Use:

```bash
stat -L documents/service-c
```

Imagine an application uses:

## 18. Knowledge Check and Interview Practice

### Knowledge Check

1. **What is an inode?**  
   A filesystem metadata structure representing a filesystem object and containing information used to manage that object, while directory entries associate names with inode numbers.

2. **Is a filename the same thing as an inode?**  
   No. A directory entry provides a name associated with an inode.

3. **What does `ls -i` show?**  
   Inode numbers.

4. **What does the link-count field represent for a regular file?**  
   The number of hard links—directory entries—currently referring to that inode.

5. **How do you create a hard link?**

   ```bash
   ln EXISTING_FILE NEW_NAME
   ```

6. **How do you create a symbolic link?**

   ```bash
   ln -s TARGET LINK_NAME
   ```

7. **Do two hard-linked names have the same inode?**  
   Yes, when they refer to the same underlying file object.

8. **Does a symbolic link normally have the same inode as its target?**  
   No. The symlink is a separate filesystem object.

9. **Why does editing through one hard link affect the other hard-linked names?**  
   Because the names refer to the same inode and underlying file data.

10. **Why can a symbolic link become broken?**  
    Because its stored target pathname may no longer resolve to an existing object.

11. **Why does renaming one hard-link name not break the other hard links?**  
    The other names independently refer to the same inode rather than storing the renamed pathname.

12. **Can symbolic links point to directories?**  
    Yes.

13. **Can hard links normally cross filesystem boundaries?**  
    No, because the hard-link relationship depends on an inode within the same filesystem.

14. **Is a hard link a backup copy?**  
    No. It is another name for the same underlying filesystem object.

15. **What is the difference between `stat link` and `stat -L link` for a symlink?**  
    `stat link` inspects the symlink object; `stat -L link` follows the link and reports target metadata.

### Interview Practice

**What is the difference between a hard link and a symbolic link?**

A hard link is another directory entry referring to the same inode as an existing regular file. A symbolic link is a separate filesystem object that stores a pathname used to resolve another object.

**How can you prove two filenames are hard links to the same file?**

I can inspect them with:

```bash
ls -li FILE1 FILE2
```

or:

```bash
stat FILE1
stat FILE2
```

and verify that they share the same inode and that the hard-link count reflects the relationship.

**What happens if you delete one of two hard links?**

The removed directory entry disappears and the inode's hard-link count decreases. The remaining hard-linked pathname can still access the underlying data.

**What happens if you delete the target of a symbolic link?**

The symbolic link object can remain, but its stored pathname no longer resolves, leaving a dangling or broken symlink.

**Why can a symbolic link cross filesystem boundaries while a hard link normally cannot?**

A symbolic link stores a pathname, which can resolve through the mounted filesystem hierarchy. A hard link must refer directly to an inode belonging to the same filesystem.

**Can a hard link point to a directory?**

Ordinary users are normally prevented from creating hard links to directories. Symbolic links are normally used when directory linking is required.

**How would you troubleshoot a broken symbolic link?**

I would inspect the link with `ls -l` or `stat`, identify the stored target pathname, verify whether that target exists, locate the intended target if necessary, then repair the symlink and verify resolution.

**What is the difference between a hard link and a copy?**

Hard-linked names share the same inode and underlying data. A copy creates another filesystem object with its own inode and independent data.
