# JUN-012: User Account Management

- **Level:** Junior  
- **Difficulty:** 2/5  
- **Estimated time:** 90–120 minutes  
- **Environment:** Ubuntu Server 24.04 LTS or a similar Debian/Ubuntu system  
- **Privileges:** Administrative privileges are required for account-management operations  
- **Primary skills:** Creating, inspecting, modifying, locking, expiring, validating, and removing Linux user accounts  
- **Prerequisites:** JUN-001 through JUN-011

---

## Lab Mission

In JUN-011, you learned how Linux represents identity:

```text
username ↔ UID
group name ↔ GID
```

You inspected accounts with:

```bash
whoami
id
getent
```

and learned how account information connects to:

```text
/etc/passwd
/etc/shadow
/etc/group
```

Now you will administer those identities.

A Linux user account has a lifecycle:

```text
REQUEST
   ↓
CREATE
   ↓
VERIFY
   ↓
CONFIGURE
   ↓
USE
   ↓
MODIFY
   ↓
RESTRICT / LOCK / EXPIRE
   ↓
REMOVE
   ↓
VERIFY CLEANUP
```

Production user management is not simply:

```bash
sudo useradd username
```

An administrator needs to answer:

- Why does this account exist?
- Is it for a human or a service?
- What UID was assigned?
- What is its primary group?
- Does it need a home directory?
- Which shell should it use?
- Can it authenticate?
- Should the account expire?
- Is it currently locked?
- Does it own files elsewhere?
- What should happen to its home directory when the account is removed?
- What evidence proves the requested change actually happened?

In this lab, you will manage only deliberately created practice accounts.

Do **not** experiment on:

- your own login account,
- `root`,
- service accounts,
- system accounts,
- production users,
- accounts you did not create for this lab.

The operating principle is:

> Identify the account, understand the requested state, make the smallest correct change, and verify the result.

---

## Learning Objectives

By the end of this lab, you should be able to:

- Explain the Linux user-account lifecycle.
- Distinguish account identity from a home directory.
- Distinguish account existence from authentication state.
- Understand the roles of `useradd`, `adduser`, `usermod`, `passwd`, `chage`, and `userdel`.
- Create a user safely.
- Create an account with a home directory.
- Inspect a newly created account.
- Verify UID, GID, home, and shell configuration.
- Set an initial password safely.
- Avoid exposing passwords in shell command lines.
- Change account metadata.
- Change an account's login shell.
- Understand UID changes and their ownership implications.
- Lock and unlock password authentication.
- Inspect password/account status.
- Configure account expiration.
- Inspect password-aging information.
- Distinguish locking from deleting.
- Distinguish password locking from complete account disablement.
- Remove an account while preserving its files.
- Remove an account and its home directory when appropriate.
- Search for remaining files owned by a removed account's UID.
- Troubleshoot account-management failures systematically.
- Document account lifecycle changes professionally.

# 2. The Linux User Account Record

From JUN-011, you already know the structure of a passwd entry:

```text
username:password-field:UID:GID:GECOS:home:shell
```

For example:

```text
veriqta-labuser:x:1001:1001:VERIQTA Lab User:/home/veriqta-labuser:/bin/bash
```

The account record tells you important things about the configured identity:

```text
username
UID
primary GID
descriptive information
home-directory path
login shell
```

But remember:

```text
account record exists
```

does not automatically mean:

```text
home directory exists
```

and:

```text
account exists
```

does not automatically mean:

```text
password authentication is usable
```

and:

```text
shell is configured
```

does not automatically prove:

```text
user is currently logged in
```

Treat each as a separate fact to verify.

# 3. `useradd` and `adduser`

Ubuntu provides both:

```bash
useradd
```

and:

```bash
adduser
```

They are related but not identical interfaces.

`useradd` is the lower-level account creation utility commonly available across Linux distributions.

`adduser` on Debian/Ubuntu systems is a higher-level account-management frontend designed to make common account creation more convenient and interactive.

This lab primarily uses:

```bash
useradd
```

because it exposes the account properties you need to understand explicitly.

That means you will deliberately specify important behavior rather than depending on an interactive frontend to choose it for you.

When working on another distribution, always check the tools and defaults provided by that system.

# 4. Never Assume `useradd` Defaults

Before creating an account, inspect the command documentation:

```bash
man useradd
```

Search for:

```text
-m
```

and:

```text
-s
```

Exit with:

```text
q
```

You can also inspect:

```bash
useradd --help
```

The important lesson is not to memorize:

> `useradd` always creates a home directory.

That behavior can depend on command options and system defaults.

When the desired state matters, specify it.

For this lab:

```text
-m
```

will explicitly request creation of a home directory.

```text
-s
```

will explicitly set the login shell.

Inspect:

```bash

```

Inspect:

# 18. Password Status Is Not the Same as Account Existence

Inspect:

```bash
getent passwd veriqta-labuser
```

The account exists.

Now:

```bash
sudo passwd -S veriqta-labuser
```

The second command tells you about password state.

These answer different questions:

```text
getent passwd
→ does the identity resolve and what is its account configuration?

passwd -S
→ what is the password status?
```

A user can exist while its password is:

- unset,
- locked,
- usable,
- expired,

depending on configuration.

This distinction becomes critical when troubleshooting login problems.

# 19. Lock the Password

Before changing anything:

```bash
sudo passwd -S veriqta-labuser
```

Now lock the password:

```bash
sudo passwd -l veriqta-labuser
```

Verify:

```bash
sudo passwd -S veriqta-labuser
```

Also verify that the identity still exists:

```bash
getent passwd veriqta-labuser
```

and:

```bash
id veriqta-labuser
```

The account has not been deleted.

Its UID still exists.

Its home still exists.

Its files still exist.

This is a major conceptual distinction:

```text
LOCK
≠
DELETE
```

---

# 20. What Password Locking Actually Means

Be precise here.

Running:

```bash
sudo passwd -l USER
```

locks the account's **password** by modifying its password-hash state.

Do not describe this as:

> The user can no longer access the system in any possible way.

That conclusion can be false.

Depending on system configuration, other access mechanisms may still matter, such as:

- SSH public keys,
- already-running sessions,
- privileged account switching,
- service execution,
- other authentication mechanisms.

Therefore:

```text
password locked
```

does not automatically mean:

```text
all possible account access disabled
```

Complete account disablement is a broader administrative/security problem.

This lab teaches you not to confuse the two.

# 23. Account Expiration vs Password Expiration

These concepts are different.

**Password expiration** concerns whether the current password has reached its configured lifetime.

**Account expiration** concerns whether the account itself has passed a configured expiration date.

Conceptually:

```text
ACCOUNT
│
├── account expiration
│
└── password
    └── password aging/expiration
```

A troubleshooting question such as:

> Why can't this user log in?

may therefore require checking more than:

```text
Is the password correct?
```

You may need to inspect:

```text
account exists?
password locked?
password expired?
account expired?
shell appropriate?
authentication mechanism?
```

Later security labs will add further layers.

# 28. Move the Home Directory Deliberately

For this controlled account, change the configured home path and move its existing home contents:

```bash
sudo usermod -d /home/veriqta-renamed -m veriqta-renamed
```

Here:

```text
-d
```

sets the new home-directory path.

```text
-m
```

moves the contents of the old home to the new location when used with the home-directory change.

Verify the account:

```bash
getent passwd veriqta-renamed
```

Verify the new directory:

```bash
ls -ld /home/veriqta-renamed
```

Verify the old path:

```bash
ls -ld /home/veriqta-rename
```

The old path should no longer exist after a successful move in this controlled scenario.

Inspect ownership:

```bash
stat -c '%U %G %u %g %A %n' /home/veriqta-renamed
```

Again:

```text
requested state
↓
change
↓
verify account database
↓
verify filesystem
```

# 29. Changing a UID Is a High-Impact Operation

Inspect:

```bash
id veriqta-renamed
```

The UID is a fundamental ownership identity.

Changing it is not equivalent to changing a display label.

Files on the filesystem may be owned by the old numeric UID.

If an administrator changes a UID without considering existing ownership, files outside automatically handled locations can become associated with the old numeric ID.

This lab will **not** change the UID of your main practice account.

Instead, understand the operational requirement:

Before a UID change, investigate:

```text
current UID
files owned by current UID
running processes
shared storage
mounted filesystems
scheduled jobs
application configuration
external systems
```

Then plan the migration.

Do not casually run:

```text
usermod -u NEW_UID USER
```

on production accounts.

The command is simple.

The consequences are not.


# 32. Removing a User: Decide What Should Happen to Data

Linux provides:

```bash
userdel
```

for removing local user accounts.

# 35. Why UID Reuse Matters

Suppose:

```text
old account:
UID 1003
```

is removed.

Files remain owned by:

```text
UID 1003
```

Later, another account is assigned that same UID.

Those old files may now resolve as being owned by the new account.

That can create unintended access or confusing ownership.

Therefore:

```text
remove account
↓
identify remaining files
↓
archive, delete, or reassign appropriately
↓
verify
```

is safer than ignoring orphaned numeric ownership.

Do not deliberately manipulate system UID allocation in this junior lab.

Understand the risk.

# 46. Common Mistakes to Avoid

### Creating a user before checking whether the name already exists

Always verify first.

### Experimenting on your own account

Use dedicated lab accounts.

### Assuming `useradd` behaves identically on every Linux distribution

Defaults and helper tools differ.

### Assuming account creation automatically means a usable password exists

Verify password state separately.

### Writing passwords directly into shell commands

Use secure interactive mechanisms where appropriate.

### Assuming a configured home path means the directory exists

Verify the filesystem.

### Assuming a home directory means the account still exists

The directory can outlive the account.

### Treating password locking as complete account disablement

Other access mechanisms or existing sessions may still matter.

### Confusing password expiration with account expiration

They are different controls.

### Changing a UID casually

UID changes can affect filesystem ownership and external dependencies.

### Renaming a user and assuming the home path automatically changes

Verify and modify each intended property explicitly.

### Running `userdel -r` without understanding the data requirement

Decide whether the home should be archived, preserved, reassigned, or deleted first.

### Assuming `userdel -r` removes every file the user owns

It does not guarantee removal of arbitrary files elsewhere.

### Forgetting to record the UID before deleting an account

After removal, the username may no longer resolve, while numeric ownership remains.

### Deleting an account without checking running processes

Investigate dependencies first.

### Fixing every login problem with `passwd`

Establish the actual account state before changing it.

# 51. Knowledge Check

### 1. What command creates a user account at a low level on Ubuntu?

```bash
useradd
```

### 2. What does `useradd -m` request?

Creation of the user's home directory.

### 3. What does `useradd -M` request?

That a home directory not be created.

### 4. What does `useradd -s` configure?

The account's login shell.

### 5. What does `useradd -c` configure?

The comment/GECOS field.

### 6. Why should you run `getent passwd USER` before creating a user?

To determine whether the requested identity already resolves.

### 7. What command is commonly used to modify an existing local account?

```bash
usermod
```

### 8. What does `usermod -c` modify?

The account's comment/GECOS field.

### 9. What does `usermod -s` modify?

The configured login shell.

### 10. What does `usermod -l` modify?

The login name.

### 11. Does renaming the login automatically guarantee the home-directory path changes?

No.

### 12. What combination can change the configured home path and move existing home contents?

```bash
usermod -d NEW_HOME -m USER
```

when appropriate.

### 13. Why should a UID change be planned carefully?

Because files and other resources can be owned by the old numeric UID, and dependencies may exist outside the user's home directory.

### 14. What command sets or changes a password interactively?

```bash
passwd USER
```

with appropriate administrative privileges when changing another user's password.

### 15. What does `passwd -S USER` inspect?

Password-status information.

### 16. What does `passwd -l USER` do?

Locks the account's password.

### 17. Does password locking delete the account?

No.

### 18. Does password locking guarantee every possible access mechanism is disabled?

No.

### 19. What does `passwd -u USER` do?

Unlocks the password when the account has an unlockable password state.

### 20. What does `passwd -e USER` do?

Expires the current password immediately so a password change is required at the next applicable password-based login.

### 21. What command displays password-aging and account-expiration information?

```bash
chage -l USER
```

### 22. What does `chage -E DATE USER` configure?

The account expiration date.

### 23. Is account expiration the same as password expiration?

No.

### 24. What does `userdel USER` normally remove?

The local user account entry, subject to the system's behavior and state; it does not automatically mean every user-owned file everywhere is removed.

### 25. What does `userdel -r USER` additionally request?

Removal of the user's home directory and mail spool where applicable.

### 26. Does `userdel -r` guarantee removal of all files owned by the UID across the system?

No.

### 27. Why should you record the UID before account deletion?

Because after the username is removed, remaining files can still carry the old numeric UID.

### 28. Can files remain owned by a deleted account's former UID?

Yes.

### 29. Why can UID reuse create risk?

A later account assigned the same numeric UID may appear to own files left behind by the previous identity.

### 30. What should you check before removing a user?

At minimum: verify the target identity, record the UID, determine required data handling, check relevant files and processes, and understand dependencies.

### 31. What does `/etc/skel` commonly provide?

Initial files that may be copied into newly created user home directories.

### 32. Does an `/etc/passwd` home field prove that the home directory exists?

No.

### 33. Does a home directory prove the user account still exists?

No.

### 34. Why should passwords generally not be embedded directly in ordinary shell commands?

They may be exposed through mechanisms such as process inspection, shell history, or logs.

# 52. Interview Practice

### How would you create a normal Linux user with a home directory and Bash shell?

On an Ubuntu system using `useradd`, one explicit approach is:

```bash
sudo useradd -m -s /bin/bash USER
```

I would first verify that the requested username does not already resolve and would verify the account, UID/GID, home directory, and shell afterward.

### What is the difference between `useradd` and `adduser`?

`useradd` is a lower-level account-management utility commonly available across Linux distributions. On Debian/Ubuntu, `adduser` is a higher-level frontend that provides a more guided workflow and distribution-specific defaults.

### How do you verify that a user exists?

I would query the configured identity database with:

```bash
getent passwd USER
```

and inspect identity information with:

```bash
id USER
```

### Does creating a user automatically mean the user can authenticate with a password?

No. Account existence and password-authentication state are separate properties. I would inspect the password state and configure authentication according to policy.

### What is the difference between locking an account password and deleting an account?

Password locking changes the password-authentication state while leaving the identity, UID, files, and account record in place. Deleting removes the account identity from the local account database. Neither should be confused with complete data cleanup.

### Does `passwd -l` guarantee a user has no access?

No. It locks the password hash, but other access paths or existing sessions may still be relevant depending on the system configuration.

### What is the difference between password expiration and account expiration?

Password expiration requires the password to be changed according to aging policy. Account expiration makes the account itself expired after the configured date.

### What does `chage` do?

It manages and displays password-aging and account-expiration information.

### Why is changing a UID potentially risky?

Filesystem objects are owned by numeric UIDs. Changing the account's UID can leave files elsewhere associated with the old numeric UID, and applications or shared systems may depend on that identity.

### What happens to files when a user is deleted?

Files do not inherently disappear just because the account is removed. Files outside the locations explicitly removed can remain owned by the old numeric UID.

### Why should you record a user's UID before deleting the account?

It lets you search for remaining ownership after the username no longer resolves.

### What does `userdel -r` do?

It removes the account and requests removal of the user's home directory and mail spool where applicable. It does not mean all files owned by that user everywhere are automatically removed.

### How would you safely offboard a Linux user?

I would verify the exact identity and UID, determine the access and data-retention requirements, inspect running processes and dependencies, inventory relevant owned data, restrict access as required, preserve or reassign necessary data, remove the account according to policy, verify the identity and home state, search for remaining ownership using the former UID, remediate it, and document the result.

### A user's login fails. Would you immediately reset the password?

No. I would first inspect whether the account resolves, password status, account and password expiration, configured shell, authentication method, and other relevant access controls. Resetting the password only addresses one possible cause.

### Why should account administration use before-and-after verification?

Because account-management commands can change identity, authentication, and filesystem state. Verification proves that the requested property changed without silently leaving an unintended state elsewhere.
