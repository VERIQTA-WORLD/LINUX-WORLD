# JUN-031: Finding Files with `find`

- **Level:** Junior  
- **Difficulty:** 3/5  
- **Estimated time:** 80–100 minutes  
- **Environment:** Ubuntu Server 24.04 LTS with GNU `find`  
- **Privileges:** No `sudo` required  
- **Primary skills:** filesystem search, search scope, predicates, file types, names, sizes, timestamps, ownership, permissions, safe result handling  
- **Prerequisites:** JUN-001 through JUN-030

## 1. Lab Mission

You already know how to inspect a directory when you know where to look.

For example:

```bash
ls -la /some/path
```

But real Linux systems quickly become too large for manual directory-by-directory inspection.

You may need to answer:

- Where is a configuration file?
- Which `.log` files exist under this application directory?
- Which directories are empty?
- Which files are larger than a certain size?
- Which files were modified recently?
- Which files belong to a particular user?
- Which files have a particular permission mode?
- Where are all files matching a naming pattern?
- Which results belong only to a specific part of the filesystem?

The foundational tool for this is:

```bash
find
```

A useful mental model is:

```text
STARTING PATH
      │
      ▼
walk directory tree
      │
      ▼
evaluate each object
      │
      ├── name?
      ├── type?
      ├── size?
      ├── time?
      ├── owner?
      ├── permissions?
      └── other conditions?
      │
      ▼
matching paths
```

The most important idea is not a particular option.

It is this:

> A `find` command begins with a search scope and then applies tests to filesystem objects inside that scope.

By the end of this lab, you should be able to build a search deliberately rather than running broad filesystem searches and hoping the result contains what you need.

### Learning objectives

You will learn to:

- explain how `find` searches a directory tree;
- choose an appropriate starting path;
- search by exact filename;
- use wildcard name patterns safely;
- perform case-insensitive name searches;
- distinguish files from directories with `-type`;
- combine multiple search conditions;
- search by file size;
- search by modification time;
- search by ownership;
- search by permission mode;
- locate empty files and directories;
- control search depth;
- explicitly print results;
- use `find` results with previously learned tools;
- understand why quoting wildcard patterns matters;
- recognize permission-denied messages as evidence rather than automatically using `sudo`;
- avoid dangerous filesystem-wide searches;
- verify search results before acting on them.

### Lab boundary

This lab does not attempt to teach:

```text
xargs
advanced find expressions
complex -exec workflows
filesystem indexing
locate databases
shell scripting
destructive bulk deletion
```

Those are separate concerns.

The focus here is **finding the correct filesystem objects safely and precisely**.

## 3. Start with Search Scope and Name

The simplest useful form is:

```text
find STARTING_PATH
```

Run:

```bash
find .
```

Here:

```text
.
```

means the current directory.

`find` walks the current directory and its descendants.

This is recursive behavior by default.

### Search for an exact name

Run:

```bash
find . -name 'app.conf'
```

You should find:

```text
./config/app.conf
```

Notice that:

```text
./backups/app.conf.bak
```

does not match the exact name `app.conf`.

### Search using a wildcard

Run:

```bash
find . -name '*.conf'
```

This should find lowercase `.conf` names.

### Why the pattern is quoted

Use:

```bash
find . -name '*.conf'
```

rather than casually writing:

```text
find . -name *.conf
```

Why?

Because the shell understands `*`.

If an unquoted wildcard matches names in your current directory, Bash can expand it **before `find` receives the pattern**.

Quoting:

```text
'*.conf'
```

allows `find` to receive the wildcard expression itself.

The mental model is:

```text
find . -name '*.conf'
             │
             ▼
find receives *.conf
             │
             ▼
find compares filesystem names
```

not:

```text
shell expands *
      ↓
find receives unexpected arguments
```

### Case-insensitive names

Run:

```bash
find . -name '*.conf'
```

Then:

```bash
find . -iname '*.conf'
```

`-iname` performs case-insensitive name matching.

This allows:

```text
cache.CONF
```

to match the pattern as well.

The distinction is:

```text
-name
→ case-sensitive
```

```text
-iname
→ case-insensitive
```

Use the one that matches the question you are asking.

## 4. Distinguish Files, Directories, and Other Objects

Searching only by name can be too broad.

`find` can test filesystem object type.

The most important types for this lab are:

```text
-type f
→ regular file
```

```text
-type d
→ directory
```

Search for regular files:

```bash
find . -type f
```

Search for directories:

```bash
find . -type d
```

Now combine conditions.

Find only regular `.log` files:

```bash
find . -type f -name '*.log'
```

Read it as:

```text
start at .
AND
object must be a regular file
AND
name must match *.log
```

By default, adjacent tests in a typical `find` expression behave as an AND relationship.

So:

```bash
find . -type f -name '*.log'
```

does **not** mean:

```text
files OR names ending in .log
```

It means both conditions must match.

### Search only one subtree

If the question is:

> Which `.log` files exist under the log hierarchy?

prefer:

```bash
find logs -type f -name '*.log'
```

rather than:

```bash
find . -type f -name '*.log'
```

when the narrower starting path is sufficient.

This is an important engineering habit:

> Start as close as practical to the area you actually need to investigate.

Narrower scope usually means:

- fewer irrelevant results;
- less filesystem traversal;
- fewer permission problems;
- easier verification;
- lower risk when later actions are involved.

## 5. Control Search Depth

Sometimes you want to search a directory but not every level beneath it.

Run:

```bash
find logs -type f
```

This includes files inside:

```text
logs/archive/
```

Now run:

```bash
find logs -maxdepth 1 -type f
```

This limits the traversal depth.

You should get files directly under:

```text
logs/
```

without descending to the archived file at the next level.

Compare:

```bash
find logs -maxdepth 1 -type f
```

with:

```bash
find logs -maxdepth 2 -type f
```

The second search can reach one level deeper.

### Why depth control matters

Suppose:

```text
logs/
```

contains thousands of nested archive directories.

If you only need current top-level logs, there is no reason to search the entire hierarchy.

Depth is another way to make search scope precise.

## 6. Search by Size and Modification Time

Names are not always enough.

You may need to locate:

> unusually large files

or:

> recently modified files.

### Search by size

You created:

```text
data/sample.bin
```

at approximately 64 KiB.

Run:

```bash
find . -type f -size +32k
```

This searches for regular files larger than the specified threshold.

Now:

```bash
find . -type f -size -100k
```

This searches for regular files below the specified threshold according to `find`'s size-test semantics.

Common size suffixes include:

```text
c → bytes
k → KiB-sized units
M → MiB-sized units
G → GiB-sized units
```

A practical example is:

```bash
find /some/application/path -type f -size +100M
```

which can help investigate unexpectedly large files within a known application scope.

Do not practice this against arbitrary production paths in this lab.

### Understand `+` and `-`

For many numeric `find` tests:

```text
+n
→ greater than n
```

```text
-n
→ less than n
```

```text
n
→ exact test according to that predicate's units
```

Do not assume every numeric test uses exactly the same human interpretation without checking its documentation.

Use:

```bash
man find
```

when exact boundary behavior matters.

---

### Search by modification time

`find` can inspect file timestamps.

One useful test is:

```text
-mmin
```

for modification age in minutes.

Since you created the lab files recently, run:

```bash
find . -type f -mmin -30
```

If you complete the lab within that window, your recently created files should be candidates.

The expression means:

```text
regular files
AND
modified less than 30 minutes ago
```

You can also encounter:

```text
-mtime
```

which works in 24-hour-based units with specific rounding semantics.

For junior work, remember:

```text
-mmin
→ minute-based modification-age search
```

```text
-mtime
→ day-based modification-age search
```

When precise time boundaries matter, check:

```bash
man find
```

rather than guessing.

### Timestamp caution

"Modified" has a specific filesystem meaning.

Do not automatically interpret:

```text
recently modified
```

as:

```text
recently created
```

or:

```text
recently accessed
```

Different timestamps describe different filesystem events.

## 7. Search by Ownership, Permissions, and Empty Objects

You learned ownership and permissions earlier in Linux World.

`find` can use that metadata as search criteria.

### Search by current owner

First confirm your identity:

```bash
whoami
```

Now use your actual username:

```bash
find . -type f -user YOUR_USERNAME
```

Replace:

```text
YOUR_USERNAME
```

with the username returned by `whoami`.

Do not type the placeholder literally.

This answers:

> Which regular files under this scope are owned by this user?

You can verify selected results with:

```bash
ls -l PATH
```

or:

```bash
stat PATH
```

### Search by group

Determine your group information:

```bash
id
```

Then, when needed:

```text
find STARTING_PATH -group GROUP_NAME
```

Ownership searches are useful during investigations involving:

- deployments;
- shared directories;
- permission problems;
- service files;
- unexpected ownership changes.

Finding an owner is evidence.

It is not by itself proof that the owner caused a problem.

---

### Search by exact permission mode

You set:

```text
config/database.conf
```

to mode:

```text
600
```

Search:

```bash
find . -type f -perm 600
```

Verify the result:

```bash
stat config/database.conf
```

At this level, treat:

```text
-perm 600
```

as an exact permission-mode search.

`find` supports more advanced permission matching forms, but those belong beyond this lab's required boundary.

---

### Find empty files and directories

Run:

```bash
find . -type f -empty
```

You should locate:

```text
data/empty-file.txt
```

Now:

```bash
find . -type d -empty
```

You should locate the empty directory.

The combination matters:

```text
-type f -empty
→ empty regular files
```

```text
-type d -empty
→ empty directories
```

Do not automatically delete an object merely because it is empty.

An empty file or directory may be:

- intentionally created;
- required by an application;
- a mount point;
- a placeholder;
- part of a deployment structure.

First determine why it exists.

## 8. Build Searches from Multiple Conditions

Suppose the requirement is:

> Find regular lowercase `.conf` files under `config`.

Build the search from the question:

```text
scope
→ config

object type
→ regular file

name
→ *.conf
```

Command:

```bash
find config -type f -name '*.conf'
```

Now:

> Find regular `.log` files under `logs` that were modified recently.

Build:

```text
scope
→ logs

type
→ file

name
→ *.log

time
→ less than 30 minutes old
```

Command:

```bash
find logs -type f -name '*.log' -mmin -30
```

Now:

> Find regular files larger than 32 KiB under `data`.

Build:

```bash
find data -type f -size +32k
```

This is the correct way to think about `find`.

Do not start with a giant command.

Translate the requirement into predicates:

```text
WHERE?
   ↓
WHAT TYPE?
   ↓
WHAT NAME?
   ↓
WHAT METADATA?
   ↓
WHAT OTHER CONDITIONS?
```

Then construct the search.

## 9. Use `find` Results Without Acting Blindly

By default, matching paths are printed.

You can make that explicit:

```bash
find . -type f -name '*.log' -print
```

For normal simple searches, `-print` is often optional because printing matching paths is the default action when no other action is specified.

Still, understanding it matters:

```text
tests determine what matches
```

and:

```text
actions determine what happens to matches
```

At this stage, your preferred action is:

```text
-print
```

because it lets you inspect results before doing anything else.

### Use results as investigation input

Suppose you need to know which known log files contain `ERROR`.

You already know how to search their contents directly:

```bash
grep -n "ERROR" logs/api.log logs/worker.log logs/archive/api-old.log
```

`find` answers a different question:

> Which filesystem objects match my search criteria?

`grep` answers:

> Which lines inside text input match my pattern?

Keep the boundary clear:

```text
find
→ filesystem objects
```

```text
grep
→ text content
```

You will encounter more advanced ways of connecting `find` results to other commands later.

For now, locate first, inspect second, act only after verification.

## 10. Controlled Failures and Troubleshooting

### Failure 1 — The wildcard behaves strangely

Suppose you run:

```text
find . -name *.conf
```

and receive unexpected behavior.

The first question should be:

> Did the shell expand the wildcard before `find` received it?

Correct form:

```bash
find . -name '*.conf'
```

**Root cause:** shell expansion and `find` name matching are different stages.

---

### Failure 2 — A result is missing because of case

Run:

```bash
find config -type f -name '*.conf'
```

Then:

```bash
find config -type f -iname '*.conf'
```

If:

```text
cache.CONF
```

appears only in the second search, the issue is case sensitivity.

Do not assume a missing result means the file does not exist.

Your predicate may not match it.

---

### Failure 3 — Too many results

You run:

```bash
find .
```

but only need current log files.

Your search is technically valid but poorly scoped.

Refine it:

```bash
find logs -maxdepth 1 -type f -name '*.log'
```

Better searches often come from adding meaningful constraints rather than filtering huge result sets afterward.

---

### Failure 4 — Wrong object type

Suppose a directory and file share similar naming patterns.

If the requirement is regular files, say so:

```bash
find . -type f -name 'PATTERN'
```

If it is directories:

```bash
find . -type d -name 'PATTERN'
```

Do not infer object type from the name alone.

---

### Failure 5 — Permission denied

On real systems, a search may encounter paths your user cannot read or traverse.

Do not immediately respond with:

```text
sudo find ...
```

First ask:

- Do I actually need to search that protected path?
- Is my starting path too broad?
- Am I authorized to inspect it?
- Can I narrow the search?

A permission-denied message is useful evidence:

```text
my current identity cannot inspect this part of the requested tree
```

Privilege elevation should be deliberate, not reflexive.

---

### Failure 6 — Search returns nothing

A zero-result search can mean:

```text
nothing matched
```

But before concluding the object does not exist, verify your assumptions:

- correct starting path?
- correct capitalization?
- correct `-type`?
- correct wildcard?
- correct size threshold?
- correct time threshold?
- correct owner?
- correct permissions predicate?

"No result" only answers the exact search you asked `find` to perform.

---

### Failure 7 — A broad search becomes noisy

Avoid using:

```text
/
```

as your starting path when:

```text
~/linux-world-labs/JUN-031
```

or an application-specific directory is sufficient.

A search such as:

```text
find /
```

can traverse a huge amount of the system and encounter paths that are irrelevant, protected, virtual, or expensive to inspect.

Use the narrowest reasonable scope.

---

### Troubleshooting model

When a `find` search behaves unexpectedly:

```text
WHAT AM I TRYING TO LOCATE?
          ↓
WHAT IS THE NARROWEST STARTING PATH?
          ↓
FILE, DIRECTORY, OR SOMETHING ELSE?
          ↓
WHAT NAME RULE APPLIES?
          ↓
CASE-SENSITIVE?
          ↓
WHAT METADATA CONDITIONS APPLY?
          ↓
SIZE / TIME / OWNER / PERMISSIONS / EMPTY?
          ↓
ARE WILDCARDS QUOTED?
          ↓
RUN SEARCH
          ↓
VERIFY RESULT WITH ls/stat
          ↓
ONLY THEN CONSIDER AN ACTION
```

## 13. Knowledge Check, Interview Practice, and Cleanup

### Knowledge Check

1. **What does `find` do?**  
   It walks a filesystem hierarchy from a specified starting path and evaluates objects against search conditions.

2. **What does `find .` mean?**  
   Search from the current directory downward.

3. **What does `-name '*.log'` do?**  
   It matches names against the case-sensitive pattern `*.log`.

4. **Why should wildcard patterns usually be quoted in `find` expressions?**  
   To prevent the shell from expanding them before `find` receives the pattern.

5. **What is the difference between `-name` and `-iname`?**  
   `-name` is case-sensitive; `-iname` is case-insensitive.

6. **What does `-type f` mean?**  
   Match regular files.

7. **What does `-type d` mean?**  
   Match directories.

8. **What does `-maxdepth 1` help control?**  
   How deeply `find` descends below the starting path.

9. **What does `-size +32k` search for?**  
   Files whose size satisfies the predicate as greater than the specified 32 KiB-unit threshold.

10. **What does `-mmin -30` mean?**  
    Match objects whose modification age is less than 30 minutes according to `find`'s `-mmin` semantics.

11. **What does `-user NAME` test?**  
    File ownership by the specified user.

12. **What does `-perm 600` mean in this lab?**  
    Match objects with the exact permission mode `600`.

13. **What does `-empty` test?**  
    Empty regular files or directories, commonly combined with `-type` to state which one you want.

14. **What is the difference between `find` and `grep`?**  
    `find` primarily locates filesystem objects based on filesystem properties. `grep` searches text for matching lines.

15. **Why should you verify `find` results before acting on them?**  
    A matching pathname only proves that it satisfied the search expression. It does not prove that modifying or deleting it is safe.

### Interview Practice

**How would you find every `.log` file under `/var/log/myapp`?**

```bash
find /var/log/myapp -type f -name '*.log'
```

assuming that path is the authorized and appropriate search scope.

**How would you make the filename search case-insensitive?**

Use `-iname`, for example:

```bash
find . -type f -iname '*.conf'
```

**How would you find directories instead of files?**

Use:

```bash
find . -type d
```

**Why should `*.log` usually be quoted in a `find` command?**

Because the shell can expand an unquoted wildcard before `find` receives it, changing the command's arguments and potentially the search behavior.

**How would you search for large files under a known application directory?**

For example:

```bash
find /application/path -type f -size +100M
```

I would use the narrowest relevant starting path and verify the results before taking action.

**How would you locate empty directories?**

```bash
find STARTING_PATH -type d -empty
```

**What would you do if `find` reports permission denied?**

I would first verify whether the protected path is actually required, whether my scope is too broad, and whether my account is authorized to inspect it. I would not automatically rerun the search with `sudo`.

**How do you troubleshoot a `find` command that returns no results?**

I verify the starting path, object type, capitalization, wildcard quoting, name pattern, size/time boundaries, ownership, permissions, and other predicates. Then I simplify the search until I identify which condition excludes the expected object.
