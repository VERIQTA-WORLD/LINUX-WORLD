## Lab Mission

Linux does not make access-control decisions based only on names such as:

```text
ann
deploy
developers
```

Behind those human-readable names are numeric identities:

```text
UID
GID
```

Every process runs with user and group identities.

Every normal filesystem object has an owning user and owning group.

Permissions such as:

```text
rwxr-----
```

only become meaningful when Linux determines **which permission class applies to the process requesting access**.

You have already worked with:

```text
owner
group
other
```

You have inspected ownership with:

```bash
ls -l
```

and:

```bash
stat
```

Now you will go beneath those labels and understand the identity system supporting them.

You will investigate:

- usernames,
- user IDs,
- group names,
- group IDs,
- primary groups,
- supplementary groups,
- `/etc/passwd`,
- `/etc/group`,
- `id`,
- `whoami`,
- `groups`,
- `getent`,
- ownership identity,
- account shells,
- home-directory fields,
- system/service identities,
- identity resolution.

You will also connect identity back to the permission model you already know.

The goal is not simply to memorize where Linux stores account information.

The goal is to be able to answer:

> Who is this process running as?

> Which groups does this identity belong to?

> What UID and GID does Linux associate with those names?

> Which ownership information belongs to this file?

> Which permission class is relevant?

> Where did Linux obtain this identity information?

That is the foundation for Linux account administration, access control, service troubleshooting, security investigation, and automation.

# 1. The Identity Layer Behind Linux Permissions

Consider:

```text
-rw-r----- 1 alice developers 1024 Sep 20 10:00 app.conf
```

You already know the permission portion:

```text
rw- r-- ---
```

The owner is:

```text
alice
```

The group is:

```text
developers
```

But Linux ultimately associates those names with numeric identifiers.

Conceptually:

```text
alice
   ↓
UID 1001

developers
   ↓
GID 1005
```

The filesystem stores numeric ownership identifiers.

Tools such as:

```bash
ls -l
```

normally resolve those numbers into human-readable names.

This distinction becomes important when:

- accounts are removed,
- files are copied between systems,
- identity databases differ,
- network identity services are involved,
- containers use different identity mappings,
- backups are restored,
- numeric ownership does not map to a local name.

The fundamental model is:

```text
human-readable identity
        ↕
numeric identity
        ↕
kernel/filesystem access decisions
```

---

# 2. Users

A Linux user is an identity represented by a numeric:

```text
UID
```

or:

```text
User ID
```

A username gives that identity a human-readable name.

For example:

```text
username:
alice

UID:
1001
```

The username is convenient for humans.

The UID is the numeric identity Linux uses internally in many places.

Do not think of a user only as:

> a person who logs into Linux.

Linux also uses user identities for:

- system services,
- daemons,
- applications,
- background processes,
- privilege separation,
- ownership,
- automation.

A Linux system can therefore contain many users that no human directly logs into.

---

# 3. Groups

A Linux group is a collection or identity category represented by a numeric:

```text
GID
```

or:

```text
Group ID
```

A group name provides a human-readable representation.

For example:

```text
group:
developers

GID:
1005
```

Groups allow permissions to be assigned to sets of identities rather than configuring access separately for every user.

Conceptually:

```text
developers
│
├── alice
├── bob
└── carol
```

A file owned by group:

```text
developers
```

can use its group permission bits to provide access to qualifying members of that group.

Groups are therefore central to collaborative access control.

# 4. Inspect Your Current Identity

Begin with:

```bash
whoami
```

This prints the username associated with your current effective user identity.

A typical result might be:

```text
student
```

Your actual username will depend on your environment.

Do not copy an example value into your notes.

Record what your system reports.

Now run:

```bash
id
```

A typical result might resemble:

```text
uid=1000(student) gid=1000(student) groups=1000(student),27(sudo)
```

Your values may differ.

Break the output into pieces.

```text
uid=1000(student)
```

means:

```text
UID:
1000

username:
student
```

Then:

```text
gid=1000(student)
```

identifies the primary group ID and its resolved name.

Finally:

```text
groups=...
```

shows the groups associated with the current identity.

`id` is one of the most useful Linux identity-inspection commands.

---

# 5. Inspect Individual Identity Components

Instead of reading the full `id` output every time, you can request specific fields.

Run:

```bash
id -u
```

This prints your numeric UID.

Now:

```bash
id -un
```

This prints the corresponding username.

Compare:

```bash
id -g
```

with:

```bash
id -gn
```

The first prints your primary numeric GID.

The second prints the primary group's name.

Now inspect all group IDs:

```bash
id -G
```

Then group names:

```bash
id -Gn
```

Record the relationship:

```text
id -u
→ UID

id -un
→ username

id -g
→ primary GID

id -gn
→ primary group name

id -G
→ group IDs

id -Gn
→ group names
```

# 6. `groups`

Run:

```bash
groups
```

This provides a convenient view of the groups associated with your current user.

Compare it with:

```bash
id
```

and:

```bash
id -Gn
```

They overlap in purpose, but `id` provides more detailed identity information.

A good engineer does not memorize commands in isolation.

Understand what question each command answers.

If the question is:

> What is my complete UID/GID identity context?

use:

```bash
id
```

If the question is simply:

> Which group names am I associated with?

then:

```bash
groups
```

may be sufficient.

# 7. Primary and Supplementary Groups

A Linux user has a **primary group**.

The user's account record contains a primary GID.

Inspect yours:

```bash
id -g
```

Then:

```bash
id -gn
```

That is your primary group.

A user may also belong to additional groups.

These are commonly called:

```text
supplementary groups
```

For example:

```text
user:
alice

primary group:
alice

supplementary groups:
developers
docker
project-x
```

Conceptually:

```text
alice
│
├── Primary group: alice
│
└── Supplementary groups:
    ├── developers
    ├── docker
    └── project-x
```

Both primary and supplementary group membership can matter for access decisions.

Do not assume that only the primary group counts when checking whether a process belongs to a file's owning group.

---

# 8. Why the Primary Group Exists

When a process creates a file, Linux needs a group identity to associate with the new object.

The process's group context contributes to that decision.

In ordinary directories without special group-inheritance behavior, the process's filesystem group identity is typically relevant to the new object's group ownership.

You have already seen an important exception.

In JUN-010, you learned that an SGID directory can cause newly created objects to inherit the directory's group.

So these concepts now connect:

```text
user identity
        ↓
primary/effective group context
        ↓
file creation
```

and, where SGID directory behavior applies:

```text
SGID directory
        ↓
directory group inheritance
        ↓
new object receives directory's group
```

Linux identity and filesystem permissions are not separate topics.

They are layers of the same access-control model.

# 9. Inspect `/etc/passwd`

Linux traditionally stores local user account information in:

```text
/etc/passwd
```

This file is normally readable because many programs need access to basic account information.

Inspect the first few entries:

```bash
head /etc/passwd
```

Do not assume your output will match another system exactly.

Each line represents an account.

A line has seven colon-separated fields:

```text
username:password:UID:GID:GECOS:home:shell
```

For example:

```text
alice:x:1001:1001:Alice Example:/home/alice:/bin/bash
```

Break it down:

```text
alice
```

Username.

```text
x
```

Password field placeholder on systems using shadow passwords.

```text
1001
```

UID.

```text
1001
```

Primary GID.

```text
Alice Example
```

GECOS/comment field.

```text
/home/alice
```

Home-directory field.

```text
/bin/bash
```

Login-shell field.

The exact contents of the GECOS field vary and may be empty.

# 10. Find Your Own Account Record

Instead of manually scrolling through the file, query your current username.

First:

```bash
whoami
```

Then use:

```bash
getent passwd "$(whoami)"
```

A result may resemble:

```text
student:x:1000:1000:Student:/home/student:/bin/bash
```

Compare its UID with:

```bash
id -u
```

Compare its primary GID with:

```bash
id -g
```

Compare its username with:

```bash
id -un
```

These tools are presenting different views of the same identity system.

# 11. Why `/etc/passwd` Is Called `passwd`

Historically, password-related information was stored in `/etc/passwd`.

Modern Linux systems normally use shadow-password mechanisms so password hashes are not exposed in a world-readable account database.

You will often see:

```text
x
```

in the second `/etc/passwd` field.

That does **not** mean the user's password is literally:

```text
x
```

It indicates that password authentication information is handled elsewhere, commonly through:

```text
/etc/shadow
```

Do not attempt to alter or expose `/etc/shadow` in this lab.

The important architectural distinction is:

```text
/etc/passwd
→ general account information

/etc/shadow
→ protected authentication-related account data
```

This separation reduces exposure of password hashes and related aging information.

---

# 12. `/etc/passwd` Is Not a List of Human Employees

Inspect several account names:

```bash
cut -d: -f1 /etc/passwd
```

`cut` is being used here only to make the account names easier to inspect. You will study text-processing tools formally later.

You may see accounts associated with services or system components.

Examples vary by installation.

This reinforces:

> Linux user does not necessarily mean human login user.

An account may exist to provide a dedicated security identity for a service.

Instead of running unrelated applications under one powerful identity, Linux services can use separate accounts to reduce privilege and isolate ownership.

# 13. Login Shells

Look again at an account record:

```text
username:x:UID:GID:comment:home:shell
```

The final field is the configured login shell.

For an interactive account, you may see:

```text
/bin/bash
```

or another shell.

Some service or restricted accounts may use values such as:

```text
/usr/sbin/nologin
```

or:

```text
/bin/false
```

depending on the distribution and account configuration.

These values can be part of preventing ordinary interactive shell login for an account.

However, do not infer too much from one field alone.

The shell field does not tell you:

- whether the account is currently logged in,
- whether another authentication path exists,
- whether a service uses the identity,
- whether the account is locked,
- whether remote access is permitted.

Identity investigation should use multiple pieces of evidence.

---

# 14. Home Directory Fields

The sixth `/etc/passwd` field is the configured home directory.

For example:

```text
/home/alice
```

Do not assume that the presence of a home-directory field proves the directory currently exists.

Account configuration and filesystem state can diverge.

You can compare the configured path with the actual filesystem.

For your current user:

```bash
getent passwd "$(whoami)"
```

Then:

```bash
printf '%s\n' "$HOME"
```

And:

```bash
ls -ld "$HOME"
```

The shell variable `$HOME` is used here only to inspect your current environment. Environment variables are covered formally in JUN-023.

Observe how:

```text
account configuration
```

and:

```text
actual filesystem state
```

relate.

A configured path and an existing directory are two separate facts.

# 15. Inspect `/etc/group`

Local group information is traditionally stored in:

```text
/etc/group
```

Inspect:

```bash
head /etc/group
```

Each line generally contains four colon-separated fields:

```text
group_name:password:GID:members
```

For example:

```text
developers:x:1005:alice,bob
```

Break it down:

```text
developers
```

Group name.

```text
x
```

Group-password placeholder or related legacy field.

```text
1005
```

GID.

```text
alice,bob
```

Explicitly listed group members.

Do not assume the member list alone tells you every way a user may be associated with that group.

Primary group membership is represented through the user's primary GID in the account database and may not appear as an explicit username in `/etc/group`'s member field.

This distinction is important.

---

# 16. Primary Group Membership Can Be Easy to Misread

Suppose:

```text
/etc/passwd
```

contains:

```text
alice:x:1001:1005:Alice:/home/alice:/bin/bash
```

and:

```text
/etc/group
```

contains:

```text
developers:x:1005:
```

The group member list appears empty.

Does that prove Alice is not associated with `developers`?

No.

Alice's primary GID is:

```text
1005
```

and the group with GID `1005` is:

```text
developers
```

Therefore `developers` is Alice's primary group even though Alice is not listed after the final colon in that `/etc/group` line.

This is why identity investigation should use tools designed to resolve the complete identity rather than relying on one field in one file.

Use:

```bash
id alice
```

when the account exists.

# 17. `getent`: Query the Identity Database

`getent` means:

```text
get entries
```

It queries databases configured through the system's name-service mechanisms.

Try:

```bash
getent passwd
```

This can display passwd database entries.

Query your account specifically:

```bash
getent passwd "$(whoami)"
```

Query your primary group:

```bash
getent group "$(id -gn)"
```

You can also query using numeric identity values.

Try:

```bash
getent passwd "$(id -u)"
```

and:

```bash
getent group "$(id -g)"
```

This demonstrates identity resolution in both directions:

```text
name → number
number → name
```

---

# 18. Why `getent` Matters

Reading:

```text
/etc/passwd
```

and:

```text
/etc/group
```

is useful for learning local account-file structure.

But Linux systems can obtain identity information from sources beyond local files.

Depending on system configuration, identity services can include technologies such as:

- LDAP,
- directory services,
- other Name Service Switch sources.

The system's Name Service Switch configuration determines how various databases are resolved.

Therefore:

```bash
grep username /etc/passwd
```

answers:

> Is this text present in this local file?

while:

```bash
getent passwd username
```

asks the configured system identity database:

> Can this account identity be resolved?

Those questions are not always identical.

For identity investigation, `getent` is often the more complete conceptual tool.

# 19. The Name Service Switch

Linux commonly uses:

```text
/etc/nsswitch.conf
```

to define how several name databases are resolved.

You do not need to administer NSS in this junior lab.

Inspect only the relevant lines:

```bash
grep '^passwd:' /etc/nsswitch.conf
```

Then:

```bash
grep '^group:' /etc/nsswitch.conf
```

Your system might show something similar to:

```text
passwd: files systemd
group:  files systemd
```

or another configuration.

Do not assume the example matches your system.

The important concept is:

```text
application requests identity
        ↓
system name-service configuration
        ↓
configured identity source(s)
        ↓
identity result
```

This is one reason `getent` is valuable.

It works through the configured database-resolution mechanism rather than treating `/etc/passwd` as the only possible source of identity.



```text

```

with:

```text
owner UID
```

and:

```text
group name
```

with:

```text
group GID
```

You are looking at two representations of the same ownership identities.

# 22. Connect Identity to the Permission Classes

Create:

```bash
touch access-model.txt
chmod 640 access-model.txt
```

Inspect:

```bash
ls -l access-model.txt
```

The standard mode is:

```text
rw-r-----
```

You already know:

```text
owner:
rw-

group:
r--

other:
---
```

But which class applies to a process?

Conceptually, Linux evaluates identity against ownership.

For the traditional owner/group/other model:

```text
Does the process's relevant user identity match the file owner?
        │
       YES
        ↓
owner class

If not:
Does an applicable process group identity match the file's group?
        │
       YES
        ↓
group class

If not:
        ↓
other class
```

This is why:

```text
permissions
```

cannot be fully understood without:

```text
identity
```

and:

```text
ownership
```

---

# 23. A Critical Rule: Permission Classes Are Not Added Together

Suppose a file has:

```text
-r--rw----
```

and the file owner is also a member of the file's group.

A common beginner assumption is:

> The owner gets owner read plus group write.

That is not how the traditional permission classes work.

If the process matches the owner identity, the owner class applies.

Linux does not normally combine:

```text
owner permissions
+
group permissions
```

to create a larger permission set for the owner.

Think:

```text
matching class
```

not:

```text
sum every class I belong to
```

This matters when troubleshooting apparently strange access behavior.

# 24. Your Current Shell Has an Identity Context

Run:

```bash
id
```

Your shell process operates within a user/group identity context.

Commands launched from that shell normally inherit identity credentials from the shell, subject to mechanisms that intentionally change credentials.

Conceptually:

```text
login/session
      ↓
shell
      ↓
command
      ↓
process
```

with identity credentials flowing through the process relationship unless something explicitly changes them.

This connects directly to JUN-010.

Special executable mechanisms such as SUID and SGID can influence effective execution identity.

Without such a mechanism or another privilege/identity transition, a normal command does not simply become another user because a file is owned by that user.


```text

```

```text
UID:
0
```

```text
0
```

> root is just a username.

The human-readable name is conventionally:

```text
root
```

# 26. UID and GID Number Ranges

You may notice that your interactive user has a UID such as:

```text
1000
```

while many system accounts have smaller values.

Linux distributions commonly divide UID/GID ranges into categories such as:

- system identities,
- regular user identities.

However, exact ranges are distribution and configuration dependent.

Do not memorize:

```text
UID below X always means service account
```

as a universal Linux rule.

On Ubuntu, account-allocation defaults and ranges are defined through configuration such as:

```text
/etc/login.defs
```

You can inspect relevant values:

```bash
grep -E '^(UID_MIN|UID_MAX|SYS_UID_MIN|SYS_UID_MAX|GID_MIN|GID_MAX|SYS_GID_MIN|SYS_GID_MAX)' /etc/login.defs
```

Some values may be absent or distribution-specific.

Use the system's actual configuration as evidence.

# 28. Controlled Failure — Unknown User

Query an intentionally unlikely account:

```bash
getent passwd veriqta-user-that-does-not-exist
```

You should receive no matching passwd entry.

Now:

```bash
id veriqta-user-that-does-not-exist
```

You should receive an error indicating that the identity cannot be found.

The exact wording may vary.

The important distinction is:

```text
identity does not resolve
```

This can become operationally important when:

- a service references a nonexistent account,
- ownership points to an unmapped numeric ID,
- an account was removed,
- an external identity service is unavailable,
- configuration contains the wrong username.

Do not solve an unknown-user error by changing file permissions.

Identity resolution and permission mode are different layers.

---

# 29. Controlled Failure — Unknown Group

Query:

```bash
getent group veriqta-group-that-does-not-exist
```

There should be no matching group result.

Compare with a known group:

```bash
getent group "$(id -gn)"
```

This establishes two states:

```text
resolvable group
```

versus:

```text
unresolvable group
```

When a configuration refers to a group name, the first question should be:

> Does this group identity actually resolve?

Not:

> Which chmod command should I run?

# 30. Controlled Investigation — Name vs Number

Create:

```bash
touch identity-mapping.txt
```

Inspect symbolically:

```bash
ls -l identity-mapping.txt
```

Now numerically:

```bash
ls -ln identity-mapping.txt
```

Record:


```bash

```


You have now traced:

```text
filesystem numeric owner
        ↓
identity database
        ↓
human-readable username
```

and:

```text
filesystem numeric group
        ↓
identity database
        ↓
human-readable group name
```

This is the identity-resolution path you need to understand.

# 31. What Happens When a Numeric Identity Has No Name?

Imagine a filesystem object records:

```text
UID 45000
GID 46000
```

but the current system cannot resolve those IDs to names.

The ownership numbers still exist.

A tool may display numeric ownership instead of a username or group name.

This can happen after:

- restoring files from another machine,
- deleting accounts without reassigning files,
- moving storage between environments,
- identity-service failures,
- container or namespace differences,
- UID/GID mismatches between systems.

The lesson is:

> A username is a resolved label for a numeric identity. The numeric ownership itself can exist even when no local name currently resolves to it.

You will encounter this concept again in administration, containers, NFS, backups, migrations, and incident response.

# 32. Identity Is Not the Same as Authentication

These terms are related but different.

**Identity** answers:

> Who is the user or process?

For example:

```text
UID 1000
username alice
```

**Authentication** answers:

> How was the claimed identity verified?

Examples can include:

- password authentication,
- SSH keys,
- other authentication mechanisms.

**Authorization** answers:

> What is this authenticated identity allowed to do?

Linux filesystem permissions participate in authorization.

Conceptually:

```text
IDENTITY
Who are you?

        ↓

AUTHENTICATION
How is that identity verified?

        ↓

AUTHORIZATION
What is that identity allowed to do?
```

Real systems may implement these layers through multiple components, but keeping the concepts separate will make later security material much easier to understand.

# 42. Common Mistakes to Avoid

### Thinking a username is the underlying filesystem ownership value

Linux ownership is represented numerically by UID/GID.

### Thinking every Linux user is a human login account

Services and system components also use user identities.

### Thinking every group membership must appear in `/etc/group`'s member list

A user's primary group is represented through the primary GID in the account record.

### Looking only at `/etc/passwd` when checking whether an identity resolves

Use `getent` when you need system identity resolution.

### Assuming `/etc/passwd` contains modern password hashes

Protected password-related data is normally handled through the shadow-password system.

### Trying to read `/etc/shadow` unnecessarily

This lab does not require its protected contents.

### Assuming the configured home directory must exist

Configuration and filesystem state can differ.

### Assuming `/bin/bash` proves a user is currently logged in

The shell field is account configuration, not session evidence.

### Assuming `/usr/sbin/nologin` alone explains every access path

Use multiple pieces of evidence.

### Looking only at a file's permissions

Identity and ownership determine which permission class applies.

### Adding owner and group permissions together

Traditional owner/group/other classes are not accumulated that way.

### Changing `chmod` when the actual problem is group membership

Repair the layer that is wrong.

### Changing ownership before identifying the process identity

Establish both sides of the access decision first.

### Assuming a numeric UID has the same username on every system

Name-to-number mappings can differ.

# 48. Interview Practice

### What is the difference between a username and a UID?

A username is a human-readable account name. A UID is the numeric user identifier Linux uses internally for identity and ownership. Tools resolve between the numeric ID and the readable name.

### What is the difference between a group name and a GID?

A group name is the human-readable representation of a group, while the GID is its numeric identifier.

### What is a primary group?

It is the group identified by the primary GID in a user's account record. It forms part of the user's group identity and commonly influences group ownership for newly created files unless another mechanism, such as SGID directory inheritance, changes the result.

### What are supplementary groups?

They are additional group memberships associated with a user beyond the primary group. They can allow a process belonging to those groups to qualify for group-based access.

### What does the `id` command show?

It displays user and group identity information, including UID, primary GID, and associated group memberships.

### What is stored in `/etc/passwd`?

It contains local account information such as username, UID, primary GID, descriptive information, configured home directory, and login shell. On modern shadow-password systems, it does not normally contain the actual password hash.

### Why is `/etc/passwd` usually readable?

Programs need access to basic account identity information. Sensitive password-related data is normally separated into a more protected database such as `/etc/shadow`.

### What is stored in `/etc/group`?

Local group definitions, including group names, GIDs, and explicit member lists.

### Why might a user belong to a group without appearing in that group's `/etc/group` member list?

Because the group may be the user's primary group, represented by the primary GID in the user's account record.

### What does `getent` do?

It queries databases through the system's configured name-service mechanisms. For users and groups, it can resolve identities from the sources configured for passwd and group lookups.

### Why use `getent` instead of only reading `/etc/passwd`?

Because `/etc/passwd` is only the local passwd file. A system may use additional configured identity sources, while `getent` queries through the system's resolution mechanism.

### What is the relationship between UID/GID and file ownership?

Filesystem ownership is represented numerically using a user ID and group ID. Commands can resolve those IDs to usernames and group names for display.

### What does `ls -ln` help you investigate?

It shows numeric UID and GID ownership directly, which is useful when troubleshooting name-resolution or cross-system ownership issues.

### How does Linux decide whether owner, group, or other permissions apply?

In the traditional model, if the process's relevant user identity matches the object's owner, the owner class applies. Otherwise, if an applicable process group matches the object's group, the group class applies. Otherwise, the other class applies.

### Are owner and group permissions combined when the owner also belongs to the object's group?

No. Matching the owner selects the owner permission class; the traditional classes are not simply added together.

### What is the difference between identity, authentication, and authorization?

Identity represents who an entity is. Authentication verifies the asserted identity. Authorization determines what that identity is permitted to do.

### Why can UID consistency matter between servers?

Because filesystem ownership is numeric. If the same UID maps to different names on different systems, shared or transferred files can appear to belong to different human-readable identities even though their numeric ownership has not changed.

### How would you investigate an identity-related permission problem?

I would identify the process's UID and groups, verify that required user and group identities resolve, inspect the target's numeric and symbolic ownership, inspect its permission mode and path permissions, determine which permission class applies, and only then decide whether identity, ownership, group membership, or permissions need to change.
