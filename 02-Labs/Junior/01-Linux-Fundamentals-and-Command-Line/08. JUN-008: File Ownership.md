# JUN-008: File Ownership

- **Level:** Junior  
- **Difficulty:** 2/5  
- **Estimated time:** 75–90 minutes  
- **Environment:** Ubuntu Server 24.04 LTS or a similar Linux system  
- **Privileges:** Standard user account with `sudo` access for specific controlled exercises  
- **Primary skills:** Linux file ownership, group ownership, `chown`, `chgrp`, identity-aware access troubleshooting  
- **Prerequisites:** JUN-001 through JUN-007

---

## Lab Mission

In JUN-007, you learned to read permissions such as:

```text
-rw-r-----
```

and divide them into:

```text
user | group | other
```

But that raises an important question:

**Which user? Which group?**

Consider this:

```text
-rw-r----- 1 deploy webteam 1840 Sep 27 10:15 app.conf
```

The permissions tell you what the three permission classes can do.

The ownership fields tell you which identities are connected to two of those classes.

Here:

```text
deploy
```

is the owning user.

And:

```text
webteam
```

is the owning group.

This relationship between **identity, ownership, and permissions** is fundamental to Linux access control.

It is also a common source of production problems.

An application may fail because a deployment created files under the wrong owner.

A web server may be unable to read content because files belong to an unexpected account.

A service may stop writing logs after someone copies files as `root`.

A shared directory may have correct-looking permissions but the wrong group ownership.

In this lab, you will learn how Linux represents file ownership, how to inspect it, how ownership interacts with the permission model you learned in JUN-007, how ownership changes are performed, and how to investigate ownership-related failures without randomly changing permissions.

The goal is not to make every file accessible.

The goal is to understand **who should own what, why, and what evidence proves the ownership is correct.**

---

# What You Will Learn

By the end of this lab, you should be able to:

- Identify the owning user of a file or directory.
- Identify the owning group.
- Read ownership information from `ls -l`.
- Inspect ownership with `stat`.
- Understand the relationship between usernames and numeric UIDs.
- Understand the relationship between group names and numeric GIDs.
- Inspect your own UID, primary GID, and supplementary groups.
- Understand that files have both user ownership and group ownership.
- Understand how newly created files normally receive an owner.
- Understand how group ownership is assigned in ordinary cases.
- Explain how ownership interacts with `user`, `group`, and `other` permissions.
- Understand that being a file owner does not automatically mean having every permission.
- Understand that changing ownership does not automatically change permission bits.
- Use `chown` in controlled exercises.
- Use `chgrp` in controlled exercises.
- Change user and group ownership together.
- Verify ownership changes.
- Understand why ordinary users are restricted from arbitrarily changing file ownership.
- Recognize files accidentally owned by `root`.
- Diagnose ownership-related access failures.
- Avoid solving ownership problems by unnecessarily broadening permissions.
- Apply least-privilege reasoning to ownership decisions.

# 2. Read Ownership From `ls -l`

Run:

```bash
ls -l application/config/app.conf
```

A typical result may resemble:

```text
-rw-r--r-- 1 student student 33 Sep 27 10:20 application/config/app.conf
```

Your username, group, size, timestamp, and permissions may differ.

Break the output down conceptually:

```text
-rw-r--r--  1  student  student  33  Sep 27 10:20  app.conf
     │             │        │
 permissions       │        │
                   │        └── owning group
                   └─────────── owning user
```

The important fields for this lab are:

```text
student student
```

The first is the owning user.

The second is the owning group.

So a long listing gives you both:

```text
permissions + ownership
```

Those pieces should be interpreted together.

---

# 3. Ownership Has Two Main Parts

Every normal Linux filesystem object has ownership information associated with:

```text
user owner
```

and:

```text
group owner
```

For example:

```text
deploy webteam
```

could mean:

```text
owning user:  deploy
owning group: webteam
```

These are separate properties.

A file can belong to:

```text
user: alice
group: developers
```

or:

```text
user: root
group: root
```

or:

```text
user: nginx
group: www-data
```

depending on the system and how the object was created or managed.

Do not assume that the owning user's name and owning group's name must be identical.

They often are on personal files because many Linux systems create a primary group with the same name as the user.

But that is not a requirement.

# 4. Identify Your Current User

Run:

```bash
whoami
```

Record the result.

Now run:

```bash
id
```

A typical result may look similar to:

```text
uid=1000(student) gid=1000(student) groups=1000(student),27(sudo)
```

Your result will differ.

Break this down.

```text
uid=1000(student)
```

identifies your user ID and username.

```text
gid=1000(student)
```

identifies your primary group ID and primary group name.

The `groups=` section shows group memberships known for the current process.

This gives you identity evidence you can compare with filesystem ownership.

# 5. Usernames Are Human-Friendly Names for Numeric IDs

Linux does not fundamentally depend on the text:

```text
student
```

to represent ownership internally.

Users have numeric identifiers called **UIDs**.

Run:

```bash
id -u
```

You should receive your numeric user ID.

For example:

```text
1000
```

Now:

```bash
id -un
```

This displays the corresponding username for your effective user.

You might see:

```text
student
```

Conceptually:

```text
1000
↓
student
```

The numeric UID is fundamental to ownership.

The username is the human-readable identity associated with that UID through the system's account databases.

---

# 6. Groups Also Have Numeric IDs

Run:

```bash
id -g
```

This shows your effective primary group ID in the usual interactive environment.

For example:

```text
1000
```

Now:

```bash
id -gn
```

This displays the corresponding group name.

For example:

```text
student
```

So conceptually:

```text
GID 1000
↓
group name student
```

Filesystems store numeric ownership identifiers.

Tools such as `ls` normally translate those identifiers into names for human readability.

# 10. Who Owns a Newly Created File?

```bash

```

Then create:

```bash

```

In the normal case, the file's owning user should be your effective user.

Why?

This gives you an important general rule:

**A newly created file is normally owned by the effective user ID of the process that created it.**

There are additional rules and exceptions in more advanced Linux environments, but this is the correct foundation.

# 12. Ownership and Permissions Work Together

Suppose:

```text
-rw-r----- 1 deploy webteam app.conf
```

You already know the permission field means:

```text
user:  rw-
group: r--
other: ---
```

Ownership tells you who those first two classes refer to:

```text
user owner:
deploy

group owner:
webteam
```

So the complete interpretation is:

```text
deploy:
read + write

members receiving access through webteam:
read

other:
no basic permissions
```

This is why permissions cannot be fully interpreted without ownership.

But your owner permissions should now resemble:

```text

```

You own the file.

Yet the permission mode does not grant your owner class write or execute permission.

```text
ownership ≠ unlimited permission
```

Restore the file:

```bash

```

# 14. Ownership Does Not Replace Permissions

Imagine:

```text
-r-------- 1 student student report.txt
```

The user `student` owns the file.

But the owner permission triplet is:

```text
r--
```

That ownership does not magically become:

```text
rwx
```

Likewise, changing a file's owner does not automatically mean the file becomes broadly accessible.

Ownership answers:

> Which user is associated with the owner permission class?

Permissions answer:

> What does that class allow?

They are related but separate properties.

---

# 15. Group Ownership Does Not Mean Every Group Member Can Do Everything

Suppose:

```text
-rw-r----- 1 deploy webteam app.conf
```

The group owner is:

```text
webteam
```

The group permission field is:

```text
r--
```

A user whose access is evaluated through that group class does not automatically get:

```text
rw-
```

They receive the capabilities represented by the group permission field—in this example, read only.

Again:

```text
group ownership
```

identifies the group.

```text
group permissions
```

describe the basic access assigned to that class.

# 16. What `chown` Does

The command commonly used to change file ownership is:

```text
chown
```

The name comes from:

```text
change owner
```

A basic form is:

```text
chown USER FILE
```

For example:

```text
chown alice report.txt
```

means:

> Change the user owner of `report.txt` to `alice`.

Changing ownership to arbitrary users is normally privileged.

That restriction is intentional.

If any user could freely make another user own arbitrary files, Linux ownership and storage-accounting assumptions would be undermined.

# 21. Changing the Owner Did Not Automatically Change the Group

Before the ownership change, your file may have looked like:

```text
student student
```

After:

```bash

```

you may see something conceptually like:

```text
root student
```

The user owner changed.

The group owner did not necessarily change.

```text

```

```text

```

# 22. Changing Ownership Does Not Automatically Rewrite Permission Bits

Compare:

```bash
ls -l ownership-tests/chown-test.txt
```

with the permission state you recorded before changing ownership.

In the ordinary case, changing the owner does not mean Linux automatically replaces the file's permission mode with a new arbitrary mode.

For example, if the file was:

```text
-rw-r--r--
```

before the ownership change, you may still see:

```text
-rw-r--r--
```

afterward.

What changed was the identity associated with the owner field.

That can still change effective access because the permission classes now apply to different identities.

This distinction is extremely important.

---

# 23. Why Ownership Changes Can Change Effective Access

Suppose a file begins as:

```text
-rw------- 1 student student report.txt
```

The owner `student` receives:

```text
rw-
```

Group and other receive:

```text
---
```

Now imagine its owner becomes:

```text
root
```

while the mode remains:

```text
-rw-------
```

The permission bits did not change.

But `student` is no longer the owner.

Therefore, the permission class that applies to `student` may change.

This is why:

**unchanged permission bits do not necessarily mean unchanged access.**

Ownership determines who is associated with those permission classes.

# 27. Do Not "Fix" Wrong Ownership With Broad Permissions

Imagine this:

```text
-rw------- 1 root root application.log
```

An application running as another account cannot write to it.

A poor response would be to make the file accessible to everyone just to eliminate the error.

That changes the security boundary without addressing the ownership question.

The better questions are:

- Which account is supposed to write this file?
- Who created it?
- Why is it owned by root?
- Should the application own it?
- Should a service group own it?
- What is the intended permission model?
- Will the same ownership mistake happen again?

Sometimes the correct fix is ownership.

Sometimes it is permissions.

Sometimes it is both.

Troubleshooting should determine which.

# 31. Changing Group Ownership Can Be Restricted

An ordinary user cannot simply assign files to arbitrary groups without restriction.

This prevents users from casually placing files into groups whose access boundaries they should not control.

Your ability to change group ownership depends on factors including:

- whether you own the file,
- which group you are assigning,
- your group memberships,
- your privileges,
- and the system's access rules.

Do not interpret:

```text
I own the file
```

as:

```text
I can assign any group I want.
```

Linux deliberately restricts ownership manipulation.

# 32. `chown` Can Change Owner and Group Together

A common `chown` form is:

```text
chown USER:GROUP FILE
```

For example:

```text
chown alice:developers report.txt
```

means:

```text
user owner  → alice
group owner → developers
```

For a controlled test, create:

```bash

```

Inspect:

```bash

```


```bash

```

This form explicitly sets both ownership fields.

# 33. `chown USER FILE` and `chown USER:GROUP FILE` Are Different

Compare conceptually:

```bash
chown alice file.txt
```

with:

```bash
chown alice:developers file.txt
```

The first requests a change to the user owner.

The second explicitly requests:

```text
user owner:
alice

group owner:
developers
```

Do not assume these commands communicate the same intention.

When ownership matters, be precise about what you intend to change.

# 36. Recursive Ownership Exists — and Requires Caution

`chown` supports recursive operation.

You can confirm this with:

```bash
chown --help
```

Look for:

```text
-R
```

or:

```text
--recursive
```

A recursive ownership operation can affect an entire directory tree.

That makes it powerful.

It also makes it dangerous when:

- the path is wrong,
- the target contains more files than expected,
- symbolic links or traversal behavior are misunderstood,
- or the intended ownership model has not been established.

This lab will not ask you to recursively change ownership on system directories.

Never experiment with commands such as:

```text
sudo chown -R ...
```

against `/`, `/etc`, `/usr`, `/var`, your entire home directory, or another important tree simply to practice.

Use isolated lab data.

# 38. Root-Owned Files in a User Workspace

Create:

```bash

```

Inspect:

```bash
ls -l ownership-tests/root-created.txt
```

Because `touch` was executed through `sudo`, the resulting file will normally be owned by root.

This is a realistic way root-owned files accidentally appear in user-controlled workspaces.

For example, someone may run:

```text
sudo some-command
```

inside a project directory.

That command may create files owned by root.

Later, ordinary tools running as the user's account may be unable to modify those files.

# 39. Why Unnecessary `sudo` Can Create Future Problems

Suppose a developer repeatedly runs build or administration commands with `sudo` inside a project workspace.

Some generated files may become:

```text
root root
```

or otherwise owned by privileged identities.

Later:

- an editor cannot save them,
- a build cannot overwrite them,
- a cleanup command fails,
- a CI process cannot modify them,
- application tooling reports permission errors.

The visible failure occurs later.

But the root cause may be an earlier command that created files under the wrong identity.

This is another reason not to use `sudo` automatically.

# 42. Ownership Problems Can Look Like Permission Problems

A user sees:

```text
Permission denied
```

and concludes:

> The permissions are wrong.

Maybe.

But consider:

```text

```

The permission bits may be exactly what someone intended:

```text
owner:
read + write

everyone else:
none
```

The problem could be that the wrong identity owns the file.

Changing:

```text

```

to a broader mode might hide the ownership error.

A better investigation asks both:

```text
Are the permissions correct?
```

and:


# 43. Ownership Troubleshooting Model

Use this sequence when ownership may be involved:

```text
SYMPTOM
What operation failed?

        ↓

ERROR
What exactly did Linux report?

        ↓

IDENTITY
Which user is performing the operation?
Which groups apply?

        ↓

PATH
Does the target exist?
Is the path correct?

        ↓

OBJECT TYPE
File?
Directory?
Something else?

        ↓

OWNERSHIP
Who owns the object?
Which group owns it?

        ↓

PERMISSIONS
What can user/group/other do?

        ↓

PATH ACCESS
Can the required directories be traversed?

        ↓

EXPECTED STATE
Who should own this object?

        ↓

HYPOTHESIS
Is ownership actually the mismatch?

        ↓

FIX
Change only what is incorrect.

        ↓

RECOVERY VERIFICATION
Repeat the original operation.

        ↓

PREVENTION
Determine how the wrong ownership was created.
```

The **expected state** step is critical.

You cannot call ownership "wrong" until you know what it should be.

# 50. Ownership Is Metadata, Not File Content

Run:

```bash
cat ownership-tests/chown-test.txt
```

Ownership information is not part of the text stored inside that file.

It is filesystem metadata associated with the object.

Likewise:

```text
owner
group
permissions
timestamps
size
```

are metadata.

Changing ownership does not mean editing the text inside the file.

This distinction matters when reasoning about filesystem operations.

---

# 51. Names Can Change While Numeric Ownership Remains Fundamental

Imagine a file whose stored owner UID is:

```text
1050
```

Linux tools may translate that UID into a username if the system can resolve it.

If no corresponding account name can be resolved, tools may display a numeric identifier instead.

This is one reason numeric ownership matters during:

- migrations,
- restored backups,
- containers,
- mounted volumes,
- shared storage,
- deleted user accounts,
- systems with different identity databases.

You do not need to solve those advanced cases yet.

But understand the foundation:

**Filesystem ownership is fundamentally tied to numeric IDs, not merely the text of usernames and group names.**

---

# 52. Engineer Note — Do Not `chown` Things Randomly

A common troubleshooting mistake is seeing:

```text
Permission denied
```

and trying ownership changes until something works.

That is dangerous.

Changing ownership can:

- break services,
- expose data to the wrong account,
- prevent legitimate processes from accessing files,
- interfere with package-managed files,
- break application assumptions,
- alter shared-directory behavior.

Before changing ownership, establish:

```text
current owner
↓
expected owner
↓
reason for the difference
↓
scope of the required correction
```

Then change only what is necessary.

---

# 53. Engineer Note — Be Extremely Careful With Recursive `chown`

A command conceptually shaped like:

```text
sudo chown -R USER:GROUP DIRECTORY
```

can change ownership throughout a tree.

That may be appropriate in a carefully controlled situation.

It may also cause widespread damage if the directory is wrong.

Before any recursive ownership operation, verify:

```bash
pwd
```

Inspect the target:

```bash
ls -ld TARGET
```

Inspect its contents.

Understand its boundaries.

Then verify the result at more than one level.

Do not use recursive ownership changes as a generic cure for permission problems.

# 67. Production Thinking — Ask Who Should Own It

When investigating an ownership problem, do not ask only:

> Who owns this file now?

Ask:

> Who should own this file?

Those are different questions.

The first is evidence.

The second requires understanding the system design.

For example:

- Should a deployment account own application releases?
- Should a service account own generated data?
- Should root own a security-sensitive system configuration?
- Should a shared group own team-managed content?
- Should a log file belong to the service that writes it?

Ownership should reflect operational responsibility and access requirements.

---

# 68. Production Thinking — Root Ownership Is Not Automatically Wrong

You have deliberately repaired root-owned files in this lab.

Do not conclude:

> Root-owned files are bad.

That would be incorrect.

Many system files **should** be owned by root.

For example, system configuration and security-sensitive files often intentionally use privileged ownership.

The correct question is:

> Is root ownership appropriate for this particular object?

In your lab's user-managed deployment workspace, it was not.

In many system locations, it is expected.

Context determines correctness.

---

# 69. Production Thinking — User Ownership Is Not Automatically Correct Either

Likewise, changing everything to your own username is not a valid system-administration strategy.

A production server may have files intentionally owned by:

- root,
- application service accounts,
- database accounts,
- web-server accounts,
- monitoring accounts,
- backup accounts,
- shared operational groups.

The desired owner should come from the system's intended access model.

Do not replace one ownership mistake with another.

---

# 70. Production Thinking — Preserve Least Privilege

Suppose an application requires:

```text
read access to configuration
write access to its log directory
write access to application data
```

That does not imply it needs ownership of:

```text
every file on the server
```

Ownership decisions should have clear boundaries.

A well-designed access model tries to provide:

```text
required access
```

without unnecessarily granting:

```text
unrelated access
```

This principle becomes increasingly important in later Linux security and service-management labs.

# 71. Common Mistakes to Avoid

### Looking only at permission bits

Always inspect owner and group too.

### Assuming the username is the real stored ownership value

Filesystem ownership fundamentally uses numeric IDs.

### Assuming owner and group must have the same name

They are separate properties.

### Assuming ownership grants every permission

It does not.

The permission mode still matters.

### Assuming changing ownership automatically changes permissions

It normally does not simply rewrite the mode because the owner changed.

### Assuming unchanged permissions mean unchanged effective access

Changing ownership can change which permission class applies to a user.

### Using `chmod` to hide an ownership problem

Broadening permissions may make the symptom disappear while leaving the wrong owner in place.

### Running commands with unnecessary `sudo`

Privileged processes can create root-owned files in user workspaces.

### Running recursive `chown` without inspecting the target

A recursive ownership mistake can affect an entire tree.

### Assuming root ownership is always wrong

Many system files intentionally belong to root.

### Assuming your own username is always the correct owner

Production services frequently use dedicated service accounts.

### Changing healthy files during an incident

Only modify objects for which evidence demonstrates a problem.

### Stopping after `chown` succeeds

Repeat the original failed operation and verify recovery.

# 77. Interview Practice

### What is file ownership in Linux?

Linux filesystem objects have an owning user and owning group represented fundamentally by numeric UID and GID values. Those ownership fields interact with the traditional user, group, and other permission classes.

### What is the difference between a UID and a username?

A UID is the numeric identifier associated with a user identity. A username is the human-readable name that the system can resolve to that UID.

### What is the difference between a GID and a group name?

A GID is the numeric group identifier. The group name is its human-readable representation.

### How do you inspect a file's owner and group?

A common command is:

```bash
ls -l FILE
```

For detailed metadata:

```bash
stat FILE
```

### How do you display numeric ownership?

With GNU `ls`:

```bash
ls -ln FILE
```

### What does `chown` do?

It changes file ownership. Depending on its arguments, it can set the user owner and can also set group ownership.

### What does `chgrp` do?

It changes the group ownership of a filesystem object.

### What is the difference between `chown alice file` and `chown alice:developers file`?

The first requests a user-owner change to `alice`. The second explicitly sets the user owner to `alice` and group owner to `developers`.

### Why are ordinary users restricted from arbitrarily changing file ownership?

Unrestricted ownership reassignment would undermine access-control and system-accounting assumptions and could allow users to manipulate ownership boundaries improperly.

### Can ownership change access without changing `rwx` bits?

Yes. Changing ownership can change which permission class applies to a user.

### Why might a file unexpectedly become root-owned?

A privileged command or process may have created or replaced the file while running as root.

### Why is `chmod` not always the correct fix for `Permission denied`?

The permission bits may already represent the intended access model while the wrong user or group owns the object. Broadening permissions could hide the ownership error and grant unnecessary access.

### What would you inspect when an application cannot write a file?

I would inspect the application's process identity, target path, file and parent-directory ownership, permissions, expected ownership model, and any other relevant access controls before changing anything.

### Why should recursive `chown` be used carefully?

It can alter ownership across an entire directory tree. A wrong path or incorrect ownership assumption can affect many files and potentially break services or security boundaries.

### Is `root:root` ownership inherently wrong?

No. Many system files intentionally use root ownership. Correct ownership depends on the purpose of the object and the system's intended access model.

### What does least privilege mean in the context of ownership?

Ownership and permissions should be designed so users and services receive the access required for their responsibilities without unnecessary control over unrelated data or system resources.
