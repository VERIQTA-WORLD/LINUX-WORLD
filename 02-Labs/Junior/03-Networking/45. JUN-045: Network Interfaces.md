## 1. Mission: Investigate the Network Interface Before Blaming the Network

In JUN-044, you learned how Linux participates in network communication.

You explored the relationship between network interfaces, IP addresses, MAC addresses, routing, DNS, transport protocols, and the path information takes through a Linux system.

Consider a production incident.

A monitoring platform reports that an Ubuntu application server is unavailable.

The application team reports:

An engineer logs into the server through an alternative management connection and runs:


## 2. Understand What a Network Interface Represents

A network interface is an operating-system networking endpoint.

Linux uses interfaces to send, receive, and process network traffic according to the capabilities and configuration of the interface.

An interface may represent actual hardware or a software-defined networking component.

A simplified model is:

```text
                APPLICATION
                     |
                     v
              LINUX NETWORK STACK
                     |
                     v
               ROUTING DECISION
                     |
                     v
              NETWORK INTERFACE
                     |
             +-------+-------+
             |               |
             v               v
          PHYSICAL         VIRTUAL
          NETWORK          NETWORK
```

The existence of an interface does not necessarily mean that it has an IP address or a working external connection.

These are separate properties.

### Physical interfaces

Physical interfaces are associated with networking hardware.

Examples include:

- Ethernet network adapters.
- Wireless adapters.
- Additional server network cards.
- Physical ports on a multiport network adapter.

A physical Ethernet interface may connect to a network switch through a cable.

However, the operating system still needs an appropriate driver and configuration to use the hardware.

### Virtual interfaces

A virtual interface is implemented through software or a virtualized networking environment.

Virtual interfaces are common in:

- Virtual machines.
- Cloud instances.
- Linux bridges.
- Containers.
- VPN environments.
- VLAN configurations.
- Virtual Ethernet connections.

For example, a virtual machine may expose an interface named `ens3` even though the guest operating system does not directly own the underlying physical network card.

### Loopback interface

Linux normally provides a loopback interface named:

```text
lo
```

Loopback supports communication within the local networking environment.

A common IPv4 loopback address is:

```text
127.0.0.1
```

The IPv6 loopback address is:

```text
::1
```

Conceptually:

```text
             LINUX HOST
       +----------------------+
       |                      |
       |    APPLICATION A     |
       |          |           |
       |          v           |
       |     LOOPBACK (lo)    |
       |          |           |
       |          v           |
       |    APPLICATION B     |
       |                      |
       +----------------------+
```

Loopback traffic does not need to leave through an external Ethernet adapter.

### Important distinction

Keep these concepts separate:

```text
INTERFACE EXISTS
       ≠
INTERFACE IS ENABLED
```

```text
INTERFACE IS ENABLED
       ≠
PHYSICAL LINK IS OPERATIONAL
```

```text
INTERFACE HAS A LINK
       ≠
INTERFACE HAS A USABLE IP ADDRESS
```

```text
INTERFACE HAS AN IP ADDRESS
       ≠
REMOTE APPLICATION IS REACHABLE
```

These distinctions will guide the practical investigation.

## 3. Understand Linux Network Interface Naming

Linux interfaces have names that allow administrators and networking tools to identify them.

You may encounter names such as:

```text
lo
eth0
ens3
enp1s0
eno1
wlp2s0
br0
veth...
docker0
```

These are examples.

Your system may use entirely different names.

### Traditional interface names

Historically, Ethernet interfaces were commonly named:

```text
eth0
eth1
eth2
```

These names are still used in some environments, including virtualized and container-based systems.

However, you should not assume that the primary Ethernet interface on Ubuntu is always named `eth0`.

### Predictable interface names

Many modern Linux distributions use predictable network-interface naming schemes.

Common examples include:

| Example | General meaning |
|---|---|
| `eno1` | Ethernet interface using an onboard-related naming scheme |
| `ens3` | Ethernet interface using a slot-related naming scheme |
| `enp1s0` | Ethernet interface using a bus/path-related naming scheme |
| `wlp2s0` | Wireless interface using a path-related naming scheme |

Actual names depend on the environment, device information, naming policies, and system configuration.

### Virtual interface names

You may encounter:

| Example | Possible interface type |
|---|---|
| `br0` | Linux bridge |
| `docker0` | Common default Docker bridge name |
| `veth...` | Virtual Ethernet interface |
| `tun0` | Common tunnel-interface name |
| `tap0` | Common TAP-interface name |
| `lo` | Loopback |

Names can be customized, so a name alone should not be treated as conclusive proof of interface type.

### Why interface names matter

Suppose a deployment script assumes:

```bash
ip addr show eth0
```

But the actual interface is named:

```text
ens3
```

The script may fail because the expected interface name does not exist.

This is why infrastructure automation should use the environment's supported interface-discovery and configuration mechanisms rather than relying on arbitrary assumptions.

### Practical Task 1 — Discover interface names

Run:

```bash
ip link show
```

**Purpose:** Display the network interfaces visible in the current network namespace.

Representative output:

```text
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 state UNKNOWN
    link/loopback 00:00:00:00:00:00

2: ens3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP
    link/ether 52:54:00:12:34:56 brd ff:ff:ff:ff:ff:ff
```

Your actual output may differ.

Now run:

```bash
ls /sys/class/net/
```

**Purpose:** List interface entries exposed through Linux sysfs.

You should generally find names corresponding to interfaces shown by `ip link show` in the same network namespace.

### Verification

Record:

```text
Number of interfaces:

Loopback interface:

Non-loopback interface(s):

Main interface name:

Unexpected or unfamiliar interface names:
```

If additional virtual interfaces exist, do not delete them.

They may belong to running services, containers, or other networking components.

## 4. Read and Interpret `ip link show`

The `ip` utility is part of the `iproute2` networking tools.

It provides several interfaces for inspecting and administering Linux networking.

In this lab, you will primarily use its link-inspection functionality.

Run:

```bash
ip link show
```

A representative interface entry may look like:

```text
2: ens3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP mode DEFAULT group default qlen 1000
    link/ether 52:54:00:12:34:56 brd ff:ff:ff:ff:ff:ff
```

Break this output into meaningful components.

### Interface index

```text
2:
```

Linux assigns interfaces numeric indexes.

The index identifies the interface within the relevant networking context.

Do not assume an interface will retain the same index across every reboot or reconstruction of the environment.

### Interface name

```text
ens3
```

This is the interface name used by Linux networking tools.

### Interface flags

```text
<BROADCAST,MULTICAST,UP,LOWER_UP>
```

These flags describe interface capabilities and state.

| Flag | General meaning |
|---|---|
| `BROADCAST` | The interface supports broadcast addressing |
| `MULTICAST` | The interface supports multicast |
| `UP` | The interface is administratively enabled |
| `LOWER_UP` | The lower-layer link is reported operational |
| `LOOPBACK` | The interface is a loopback device |
| `NOARP` | The interface does not use normal ARP behavior |

Not every interface displays the same flags.

### MTU

```text
mtu 1500
```

This represents the configured Maximum Transmission Unit.

You will investigate MTU in Section 7.

### Queueing discipline

```text
qdisc fq_codel
```

The queueing discipline influences how outgoing packets are queued and scheduled.

Different interfaces and environments may display different queueing disciplines.

Detailed Linux traffic control is outside the scope of this junior lab.

### Operational state

```text
state UP
```

This reports the interface's operational state as represented by Linux.

It must be interpreted alongside the interface flags and type.

### Transmit queue length

```text
qlen 1000
```

Where displayed, this represents the interface's configured transmit queue length.

It is not a direct measurement of current application throughput.

### Link-layer address

```text
link/ether 52:54:00:12:34:56
```

This identifies an Ethernet-style link-layer address.

### Broadcast address

```text
brd ff:ff:ff:ff:ff:ff
```

This is the Ethernet broadcast address.

### Practical Task 2 — Inspect one interface

First, identify your main non-loopback interface.

For the remaining examples, replace `ens3` with your actual interface name.

Run:

```bash
ip link show dev ens3
```

**Purpose:** Display link information for one selected interface.

Do not enter the example interface name blindly.

If the command reports:

```text
Device "ens3" does not exist.
```

inspect the available names again:

```bash
ip link show
```

Then use the correct name.

### Checkpoint 1

For your selected interface, identify:

1. Interface index.
2. Interface name.
3. Administrative state.
4. Lower-layer state.
5. MTU.
6. MAC address, if applicable.
7. Queueing discipline.
8. Operational state.

You should be able to explain what each observation means without claiming that it proves complete network connectivity.

## 5. Understand Administrative State and Operational State

This is one of the most important parts of the lab.

A network interface has more than one kind of state.

Two concepts must remain separate:

- Administrative state.
- Operational state.

### Administrative state

Administrative state indicates whether the interface has been enabled through the operating system's networking controls.

In `ip link show`, the flag:

```text
UP
```

indicates that the interface is administratively enabled.

However, this alone does not guarantee that the interface has an operational lower-layer connection.

### Operational state

Operational state reflects the interface's reported ability to operate at the relevant lower layer.

For Ethernet-style interfaces, carrier information is particularly useful.

Consider:

```text
<BROADCAST,MULTICAST,UP,LOWER_UP>
```

This shows that the interface is administratively enabled and its lower-layer link is reported operational.

Now consider:

```text
<BROADCAST,MULTICAST,UP,NO-CARRIER>
```

This indicates that the interface is administratively enabled but carrier is not being reported.

### Compare common observations

| Observation | Interpretation |
|---|---|
| `UP,LOWER_UP` | Administratively enabled; lower-layer link reported operational |
| `UP,NO-CARRIER` | Administratively enabled; no carrier reported |
| No `UP` flag | Interface is not administratively enabled |
| `state DOWN` | Operational state is down |
| `state UNKNOWN` | Operational state is not represented as a conventional known up/down condition |

These observations must be interpreted in the context of the interface type.

### Why loopback may show `UNKNOWN`

You may see:

```text
lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 state UNKNOWN
```

Do not immediately report:

> The loopback interface is broken.

The loopback interface is not a conventional physical Ethernet link.

An operational state of `UNKNOWN` can be normal for certain interface types.

### Understand carrier

For physical Ethernet, carrier commonly indicates whether the relevant lower-layer link is detected.

A simplified example:

```text
          LINUX SERVER
                |
                |
          ETHERNET PORT
                |
                X
          DISCONNECTED LINK
                |
                |
              SWITCH
```

The interface may remain administratively enabled while no carrier is detected.

However, a virtual interface's carrier behavior may depend on its implementation and virtual networking environment.

### Practical Task 3 — Inspect interface state

Run:

```bash
ip -br link show
```

The `-br` option requests a brief display.

Representative output:

```text
lo               UNKNOWN        00:00:00:00:00:00
ens3             UP             52:54:00:12:34:56
```

This view is useful for quickly surveying interfaces.

Next, inspect the full entry:

```bash
ip link show dev ens3
```

Compare the brief state with the detailed flags.

### Verification

Answer:

```text
Is the interface administratively enabled?

Does it report LOWER_UP?

Does it report NO-CARRIER?

What operational state is displayed?

Does the interface type affect how the state should be interpreted?
```

### Engineer note

A single `UP` observation is not proof of:

```text
Correct IP configuration
Correct default gateway
Working DNS
Working firewall configuration
Remote application availability
```

Interface state is one part of a wider networking investigation.

## 6. Understand MAC Addresses and Interface Identity

In JUN-044, you learned that MAC addresses participate in link-layer communication.

Now inspect how Linux exposes them.

A typical Ethernet MAC address contains 48 bits and is displayed as six hexadecimal octets.

Example:

```text
52:54:00:12:34:56
```

In `ip link show`, you may encounter:

```text
link/ether 52:54:00:12:34:56
```

This identifies the interface's current Ethernet-style link-layer address.

### Is a MAC address always permanent?

No.

A MAC address may be:

- Assigned by hardware.
- Assigned by virtualization software.
- Configured administratively.
- Generated for a virtual interface.
- Changed through supported networking configuration.

Do not assume the current MAC address always equals a permanent hardware address.

### Can two interfaces have the same IP address?

Address assignment rules depend on the networking design, address family, and interface configuration.

However, do not confuse interface identity with IP configuration.

A network interface is not defined solely by the IP address assigned to it.

An interface can exist without an IP address.

An interface can also have multiple IP addresses.

### Practical Task 4 — Inspect the MAC address

Run:

```bash
ip link show dev ens3
```

Look for:

```text
link/ether
```

Now inspect the corresponding sysfs entry:

```bash
cat /sys/class/net/ens3/address
```

Replace `ens3` with your actual interface name.

**Purpose:** Display the interface's current link-layer address through sysfs.

For an Ethernet-style interface, compare this with the address displayed by `ip link show`.

### Expected result

The two views should ordinarily identify the same current link-layer address for the selected interface.

If the interface is not Ethernet-style, its address representation may differ.

### Checkpoint 2

Explain:

1. What is a MAC address?
2. Where does `ip link show` display it?
3. Does every interface have an ordinary Ethernet MAC address?
4. Can a virtual interface have a MAC address?
5. Why should an engineer avoid treating the current MAC address as guaranteed permanent hardware identity?

## 7. Understand the Maximum Transmission Unit (MTU)

MTU stands for Maximum Transmission Unit.

It describes the maximum size of a network-layer packet that can be transmitted over a particular link without requiring fragmentation at that link.

For a conventional Ethernet interface, you may see:

```text
mtu 1500
```

For loopback, you may see:

```text
mtu 65536
```

These values serve different environments and should not be interpreted as universal requirements.

### Why MTU matters

Network communication involves carrying IP packets through links.

Different links may support different MTU values.

Consider:

```text
        LINUX SERVER
        MTU 1500
            |
            v
        NETWORK LINK
            |
            v
        INTERMEDIATE PATH
            |
            v
        DESTINATION
```

A communication path may contain links with different MTU constraints.

When packet sizes exceed what a relevant link can carry, protocol-specific fragmentation or packet-size discovery behavior becomes important.

For IPv4, fragmentation may occur under appropriate conditions.

IPv6 routers do not fragment forwarded IPv6 packets.

Detailed Path MTU Discovery and fragmentation troubleshooting belong to later networking work.

### Why not simply increase MTU?

A larger MTU is not automatically better.

For example:

```text
mtu 9000
```

is commonly associated with jumbo-frame configurations in some Ethernet environments.

However, changing one interface to MTU 9000 does not guarantee that every device along the communication path supports the required frame size.

An inconsistent MTU design can create communication problems.

### Practical Task 5 — Inspect MTU

Run:

```bash
ip link show dev ens3
```

Record the MTU.

Now run:

```bash
cat /sys/class/net/ens3/mtu
```

Compare the results.

### Expected result

Both commands should report the selected interface's configured MTU.

### Verification

Record:

```text
Main interface MTU:

Loopback MTU:

Are the values identical?

Was any MTU configuration changed?
No.
```

### Important distinction

```text
LARGER MTU
≠
AUTOMATICALLY FASTER NETWORK
```

MTU selection depends on the networking environment and supported path characteristics.

## 8. Inspect Interface Statistics and Traffic Counters

Interface state tells you whether Linux considers an interface enabled or operational.

Statistics provide another kind of evidence.

Linux maintains counters associated with network interfaces.

These can include:

- Received bytes.
- Transmitted bytes.
- Received packets.
- Transmitted packets.
- Receive errors.
- Transmit errors.
- Dropped packets.

### RX and TX

Two abbreviations appear frequently:

```text
RX = Receive
TX = Transmit
```

From the perspective of the selected interface:

```text
              NETWORK
                 |
                 v
              RX TRAFFIC
                 |
                 v
           LINUX INTERFACE
                 |
                 v
              TX TRAFFIC
                 |
                 v
              NETWORK
```

Receive counters describe incoming traffic.

Transmit counters describe outgoing traffic.

### Practical Task 6 — Inspect interface statistics

Run:

```bash
ip -s link show dev ens3
```

Representative output:

```text
2: ens3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP
    link/ether 52:54:00:12:34:56 brd ff:ff:ff:ff:ff:ff

    RX:  bytes  packets  errors  dropped  missed  mcast
         84210      620       0        0       0     12

    TX:  bytes  packets  errors  dropped  carrier  collsns
         56320      410       0        0       0      0
```

Your values and displayed fields may differ.

### Understand the counters

| Counter | General meaning |
|---|---|
| RX bytes | Amount of received traffic |
| RX packets | Number of received packets |
| RX errors | Receive operations classified as errors |
| RX dropped | Received packets dropped according to interface/driver accounting |
| TX bytes | Amount of transmitted traffic |
| TX packets | Number of transmitted packets |
| TX errors | Transmit operations classified as errors |
| TX dropped | Transmit packets dropped according to interface/driver accounting |

Additional fields depend on the interface and driver.

### Important interpretation rule

A nonzero error or drop counter is an observation, not a complete root-cause diagnosis.

Counters are often cumulative over an interface's lifetime or since a relevant reset.

For example:

```text
RX dropped: 15
```

does not automatically mean:

> The network is currently dropping packets continuously.

You need additional context.

Useful questions include:

- Is the counter increasing?
- Over what observation interval?
- Is there an associated service impact?
- Is the interface receiving substantial traffic?
- Does the interface or driver provide additional diagnostic information?
- Are the statistics consistent with other evidence?


```bash

```

Then:

```bash

```

Inspect errors:

```bash

```

```bash

```

Inspect drops:

```bash

```

```bash

```

Replace `ens3` with the correct interface name.

### Compare the two views

Run:

```bash

```

Compare the statistics with the sysfs values.

Small differences are possible because counters may change while the system continues operating.

## 9. Understand `/sys/class/net` and the Kernel's Interface View

Linux exposes information about devices and kernel objects through sysfs.

The relevant location for network interfaces is:

```text
/sys/class/net/
```

This provides a useful alternative view of interface properties.

### Practical Task 8 — Inspect sysfs

Run:

```bash
ls /sys/class/net/
```

Then inspect your selected interface:

```bash
ls /sys/class/net/ens3/
```

You may encounter entries including:

```text
address
carrier
duplex
flags
ifindex
mtu
operstate
speed
statistics
type
```

The available entries depend on the interface and environment.

### Inspect operational state

Run:

```bash
cat /sys/class/net/ens3/operstate
```

Possible results include:

```text
up
down
unknown
dormant
```

Other operational states may also be reported.

Compare the result with:

```bash
ip link show dev ens3
```

### Inspect carrier

If the interface exposes a readable carrier entry, run:

```bash
cat /sys/class/net/ens3/carrier
```

Common values are:

```text
1
```

for carrier reported, and:

```text
0
```

for no carrier reported.

Some interface types or states may not support a meaningful carrier reading. The command can fail or return information that requires interface-specific interpretation.

Do not force the interface into a different state to obtain a particular value.

### Inspect interface index

Run:

```bash
cat /sys/class/net/ens3/ifindex
```

Compare this with the numeric index shown by:

```bash
ip link show dev ens3
```

### Inspect interface type

Run:

```bash
cat /sys/class/net/ens3/type
```

This reports a numeric link-layer hardware type.

For example, Ethernet-style interfaces commonly use the ARPHRD_ETHER type value:

```text
1
```

This value alone does not prove that the interface corresponds to a dedicated physical Ethernet card. Virtual Ethernet-style interfaces can use the same type.

### Engineer note

Sysfs is useful because it exposes kernel-maintained interface properties.

However, it should not be treated as a replacement for understanding the interface's role in the overall network architecture.

## 10. Distinguish Physical and Virtual Interfaces

A Linux host may expose several interfaces that appear similar at first glance.

Consider:

```text
lo
ens3
br0
veth7a92c1
```

They may represent different networking responsibilities.

### Physical Ethernet

A physical Ethernet interface is associated with actual networking hardware.

### Virtual-machine interface

A virtual machine may expose an Ethernet-style interface backed by the hypervisor's virtual networking infrastructure.

From inside the guest, it can behave like a normal Ethernet interface.

### Linux bridge

A bridge connects compatible link-layer interfaces into a software-defined bridging domain.

Conceptually:

```text
       LINUX BRIDGE
           br0
            |
       +----+----+
       |         |
       v         v
   INTERFACE  INTERFACE
```

You will encounter bridges more extensively in virtualization, containers, and advanced networking.

### Virtual Ethernet pair

A virtual Ethernet pair provides two connected virtual endpoints.

Conceptually:

```text
      veth-A <----------> veth-B
```

This is commonly used in container networking and network-namespace designs.

### Why this matters

A virtual interface may:

- Have an Ethernet-style MAC address.
- Have an MTU.
- Maintain RX/TX statistics.
- Appear in `ip link show`.
- Report operational state.

Therefore, these properties do not automatically prove that the interface is physical hardware.

### Practical Task 9 — Inspect interface backing information

Run:

```bash
ls -l /sys/class/net/
```

You may observe that interface entries are symbolic links into the sysfs device hierarchy.

For your selected interface, run:

```bash
readlink -f /sys/class/net/ens3
```

The resulting path can provide useful information about how the interface is represented within sysfs.

However, the path alone may not conclusively establish the full physical or virtual networking architecture.

Do not assume every interface has a directly associated physical device.

### Verification

Identify:

```text
Interfaces that appear to be loopback:

Interfaces that appear to be Ethernet-style:

Interfaces that appear virtual:

Interfaces whose type remains uncertain:
```

Use cautious language.

For example:

> The interface appears to be Ethernet-style and is exposed through the virtual machine's networking environment.

Avoid claiming physical hardware ownership without supporting evidence.

## 11. Connect Interfaces to IP Addressing

In JUN-044, you learned that network interfaces and IP addresses are related but different.

Now verify that relationship on your actual host.

Run:

```bash
ip link show
```

Then:

```bash
ip addr show
```

The first command emphasizes interface and link-layer information.

The second includes address information.

### Example

An interface may appear as:

```text
2: ens3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP
```

Its address information may include:

```text
inet 192.168.10.20/24 scope global ens3
```

The interface exists as a Linux networking object.

The IP address is configuration associated with that interface.

### Can an interface exist without an IP address?

Yes.

An interface may exist without an IPv4 address, an IPv6 address, or either.

This can be intentional.

For example, some interfaces participate in bridging or other networking designs without requiring an ordinary host IP address directly on every participating interface.

### Can an interface have multiple IP addresses?

Yes.

An interface can have multiple configured addresses.

Therefore:

```text
ONE INTERFACE
       ≠
EXACTLY ONE IP ADDRESS
```

### Practical Task 10 — Compare interface and address views

Run:

```bash
ip link show dev ens3
```

Then:

```bash
ip addr show dev ens3
```

Record:

```text
Interface name:

Interface state:

MAC address:

MTU:

IPv4 address(es):

IPv6 address(es):
```

### Important distinction

Do not conclude that an interface is broken merely because it lacks a particular IP address.

First establish the intended role of that interface.

A bridge member, virtual Ethernet endpoint, or isolated interface may have a different configuration from a conventional server-facing interface.

## 12. Troubleshoot Common Network Interface Problems

A network-interface investigation should begin with observable symptoms and progress toward supported conclusions.

Avoid changing configuration based on assumptions.

### Problem 1 — The expected interface name does not exist

**Symptom:**

```text
Device "eth0" does not exist.
```

**Possible explanation:**

The actual interface may use a different naming scheme.

**Investigation:**

```bash
ip link show
```

**Corrective direction:**

Identify the real interface name and verify whether the configuration or automation is referencing the intended interface.

Do not rename an active interface merely to satisfy an outdated assumption.

---

### Problem 2 — The interface is administratively down

**Evidence example:**

```text
<BROADCAST,MULTICAST> mtu 1500 state DOWN
```

The `UP` flag is absent.

**Investigation:**

Determine whether the interface is intentionally disabled.

Inspect the approved network configuration and the interface's intended operational role.

**Corrective direction:**

If the interface is required to be active, its configuration should be corrected through the supported change process.

Do not enable an unfamiliar interface without understanding its role.

---

### Problem 3 — The interface is enabled but reports no carrier

**Evidence example:**

```text
<BROADCAST,MULTICAST,UP,NO-CARRIER> mtu 1500 state DOWN
```

The interface is administratively enabled, but the lower-layer connection is not reported operational.

**Possible causes include:**

- Disconnected physical link.
- Disabled switch port.
- Virtual adapter disconnection.
- Hypervisor networking issue.
- Interface-specific lower-layer conditions.

**Investigation:**

Inspect interface state and relevant infrastructure information.

**Corrective direction:**

Resolve the confirmed underlying cause rather than repeatedly toggling the interface.

---

### Problem 4 — Loopback reports `state UNKNOWN`

**Evidence example:**

```text
lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 state UNKNOWN
```

**Interpretation:**

This can be normal for loopback.

Do not classify it as a failure based only on the word `UNKNOWN`.

---

### Problem 5 — The interface has no IPv4 address

**Evidence:**

The interface exists in:

```bash
ip link show
```

but has no IPv4 `inet` entry in:

```bash
ip -4 addr show
```

**Possible explanations include:**

- The interface is intentionally unnumbered.
- IPv4 configuration has not been applied.
- Dynamic address assignment has not completed.
- The interface serves a different networking role.

**Corrective direction:**

Confirm the intended interface design before assigning an address.

IP addressing receives dedicated treatment in JUN-046.

---

### Problem 6 — Error or drop counters are nonzero

**Evidence:**

```text
RX errors: 12
```

or:

```text
TX dropped: 8
```

**Interpretation:**

These counters require context.

A single cumulative snapshot does not prove an ongoing incident.

**Investigation:**

Compare counter values over a meaningful interval and correlate them with service impact and other evidence.

---

### Problem 7 — The MTU differs from another interface

**Evidence:**

```text
ens3 mtu 1500
```

and:

```text
lo mtu 65536
```

**Interpretation:**

Different MTU values are not automatically a problem.

Interface type and network design matter.

Do not change MTU values merely to make them identical.

## 13. Controlled Failure Investigation — Interface Enabled, Link Unavailable

This investigation uses a simulated incident.

You will not disable your real interface.

### Scenario

A production Ubuntu server is connected to an internal network.

The monitoring system reports that the server is unreachable.

The infrastructure team captures the following evidence:

```text
2: ens3: <BROADCAST,MULTICAST,UP,NO-CARRIER> mtu 1500 state DOWN
    link/ether 52:54:00:12:34:56 brd ff:ff:ff:ff:ff:ff
```

A second inspection reports:

```text
/sys/class/net/ens3/operstate

down
```

The carrier reading is:

```text
/sys/class/net/ens3/carrier

0
```

The team also confirms that the interface is connected through a virtual machine's network adapter.

### Step 1 — Identify the symptom

The server is unreachable through its expected network connection.

### Step 2 — Establish the impact

Applications depending on that network connection cannot communicate normally through the affected path.

### Step 3 — Examine the evidence

The interface reports:

```text
UP
```

This means it is administratively enabled.

However, it also reports:

```text
NO-CARRIER
```

and:

```text
state DOWN
```

The sysfs carrier reading is:

```text
0
```

These observations indicate that the lower-layer connection is not being reported operational.

### Step 4 — Form a hypothesis

The virtual network adapter may be disconnected or its backing virtual-network connection may be unavailable.

This is a hypothesis, not yet the confirmed root cause.

### Step 5 — Test the hypothesis

The infrastructure engineer should inspect the virtual machine's network-adapter configuration and its connection to the intended virtual network.

In this simulated case, the hypervisor administrator confirms that the adapter was disconnected during a maintenance operation.

### Step 6 — Identify the root cause

The confirmed root cause is the disconnected virtual network adapter.

The interface remained administratively enabled inside Linux, but the backing connection was unavailable.

### Step 7 — Determine the fix

The authorized infrastructure administrator reconnects the adapter to the approved virtual network.

This is a simulated corrective action.

Do not disconnect or reconnect your own machine's adapter to reproduce the incident.

### Step 8 — Recovery verification

After the correction, the engineer repeats:

```bash
ip link show dev ens3
```

Expected recovery evidence would include the lower-layer connection being reported operational, where supported by the virtual networking environment.

For example:

```text
<BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP
```

The engineer should also verify the original communication failure separately.

An operational interface alone does not prove complete application recovery.

### Step 9 — Prevention

The team should review:

- Virtual machine maintenance procedures.
- Network-adapter connection settings.
- Change-management requirements.
- Monitoring for unexpected interface-state changes.
- Recovery verification after infrastructure maintenance.

### Incident conclusion

A correct incident report would state:

> The interface remained administratively enabled, but its lower-layer connection was unavailable. Hypervisor inspection confirmed that the virtual network adapter had been disconnected during maintenance. The adapter was reconnected through the approved infrastructure process, and interface state was rechecked before application recovery testing.

This is more precise than:

> The network was down, so we restarted networking.

## 14. Safe Network Interface Investigation Workflow

When an interface-related incident occurs, use a structured investigation.

```text
NETWORK INTERFACE CONCERN
          |
          v
IDENTIFY THE EXPECTED INTERFACE
          |
          v
ip link show
          |
          v
CHECK ADMINISTRATIVE STATE
          |
          v
CHECK OPERATIONAL STATE
          |
          v
INSPECT MAC ADDRESS AND MTU
          |
          v
ip -s link show
          |
          v
INSPECT ERROR / DROP COUNTERS
          |
          v
CHECK SYSFS INFORMATION
          |
          v
COMPARE WITH EXPECTED DESIGN
          |
          v
FORM A SUPPORTED HYPOTHESIS
          |
          v
TEST WITHOUT UNNECESSARY CHANGES
          |
          v
DOCUMENT THE FINDINGS
```

The objective is not to run every networking command immediately.

It is to gather the evidence relevant to the reported symptom.

### Symptom → Impact → Evidence → Hypothesis → Test → Root Cause → Fix → Recovery Verification → Prevention

Use this structure when documenting an actual incident.

| Stage | Engineering question |
|---|---|
| Symptom | What exactly is failing? |
| Impact | Which services or users are affected? |
| Evidence | What does Linux actually report? |
| Hypothesis | What could explain the observations? |
| Test | How can the hypothesis be checked safely? |
| Root cause | What does the combined evidence establish? |
| Fix | What approved corrective action addresses the cause? |
| Recovery verification | Has the original failure been resolved? |
| Prevention | How can recurrence or detection be improved? |

Do not skip from symptom directly to fix.

### Interview Practice

#### 1. How do you list network interfaces on Linux?

I would use:

```bash
ip link show
```

For a concise overview:

```bash
ip -br link show
```

#### 2. What is the difference between administrative and operational interface state?

Administrative state indicates whether the interface has been enabled through operating-system controls. Operational state describes its reported ability to operate at the relevant lower layer. An interface can be administratively enabled while lacking carrier.

#### 3. What does `UP,NO-CARRIER` mean?

The interface is administratively enabled but is not reporting carrier. I would investigate the relevant physical or virtual link rather than assuming that IP configuration is the immediate cause.

#### 4. Why might loopback display `state UNKNOWN`?

Loopback is not a conventional physical network link. Its operational state may be represented as `UNKNOWN` even while the interface is functioning normally.

#### 5. How would you check an interface's MAC address?

I would inspect:

```bash
ip link show dev ens3
```

or:

```bash
cat /sys/class/net/ens3/address
```

using the actual interface name.

#### 6. What is MTU, and why does it matter?

MTU defines the maximum network-layer packet size supported for transmission over a link without requiring fragmentation at that link. It matters because different network paths and encapsulation designs may impose different packet-size constraints.

#### 7. How do you inspect interface traffic statistics?

I would use:

```bash
ip -s link show dev ens3
```

Then inspect RX/TX bytes, packets, errors, and drops.

#### 8. The RX dropped counter is nonzero. Does that mean the interface is faulty?

Not necessarily. I would determine whether the counter is increasing, consider traffic volume and interface behavior, and correlate the observation with other evidence before identifying a fault.

#### 9. Can a network interface exist without an IP address?

Yes. Interfaces and IP-address assignments are different concepts. Some interfaces intentionally operate without an ordinary host IP address.

#### 10. How would you investigate an interface that appears enabled but has no connectivity?

I would inspect administrative and operational states, carrier information where applicable, MTU, statistics, and the interface's intended physical or virtual connection. I would then examine addressing and routing as appropriate, rather than changing configuration without evidence.
