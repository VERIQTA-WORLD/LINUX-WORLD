# 1. Lab Mission — The Network Works, but the Application Cannot Find Its Database

You are a junior infrastructure engineer supporting an Ubuntu application server.

The application team reports that its service cannot connect to the database.

The configured database endpoint is:

```text
database.internal.example
```

The team suspects a networking problem.

You inspect the server and discover that:

- Its network interface is operational.
- Its IPv4 address is correctly configured.
- Its default gateway is present.
- The routing table contains the expected database-network route.
- A route lookup for the database IP selects the intended path.

Yet the application still reports:

```text
Temporary failure in name resolution
```

This is the situation you will learn to investigate in JUN-049.

In previous labs, you studied IP addresses, subnets, gateways, and routing. Those concepts explain how Linux selects a network path after it knows the destination address.

But applications frequently begin with a hostname rather than an IP address.

Something must translate that name into usable address information.

That is one of the primary responsibilities of the Domain Name System (DNS).

## 1.1 The production scenario

Your organization operates the following infrastructure:

```text
Application server:
app-server-01

Application IPv4 address:
10.20.10.25/24

Default gateway:
10.20.10.1

Approved internal DNS resolver:
10.20.10.53

Database hostname:
database.internal.example

Expected database IPv4 address:
10.20.20.30
```

The intended communication process is:

```text
                  APPLICATION SERVER
                     10.20.10.25
                           |
                           v
                  DATABASE HOSTNAME
              database.internal.example
                           |
                           v
                     DNS RESOLUTION
                           |
                           v
                  INTERNAL DNS SERVER
                     10.20.10.53
                           |
                           v
                     DNS RESPONSE
                     10.20.20.30
                           |
                           v
                  LINUX ROUTE LOOKUP
                           |
                           v
                  SELECTED NETWORK PATH
                           |
                           v
                     DATABASE SERVER
                     10.20.20.30
```

Your task is to understand each DNS-related component of this process and identify where name resolution can fail.

You will investigate actual configuration on your Ubuntu machine, perform safe queries, and analyze a supplied production incident.

**You will not modify your active DNS configuration.**

# 4. DNS Fundamentals — What Problem Does DNS Solve?

DNS stands for **Domain Name System**.

It is a distributed naming system that stores and retrieves information associated with domain names.

One of its most familiar functions is resolving hostnames into IP addresses.

Consider:

```text
www.example.com
```

An application may need an IPv4 or IPv6 address associated with this name before communicating with the destination.

A simplified process is:

```text
          HUMAN-READABLE HOSTNAME
               www.example.com
                       |
                       v
                  DNS LOOKUP
                       |
                       v
               ADDRESS INFORMATION
                       |
                       v
               NETWORK COMMUNICATION
```

## 4.1 Why not configure every application with an IP address?

Imagine three applications connecting to one database:

```text
Application A ----+
                  |
Application B ----+----> 10.20.20.30
                  |
Application C ----+
```

If the database endpoint changes, multiple configurations may require updating.

A DNS-based design can provide a naming layer:

```text
Application A ----+
                  |
Application B ----+----> database.internal.example
                  |                  |
Application C ----+                  v
                                DNS RESOLUTION
                                      |
                                      v
                                  IP ADDRESS
```

DNS does not eliminate application configuration management, network planning, or migration complexity.

However, it provides a standardized mechanism for resolving names into resource records.

## 4.2 DNS does more than return IP addresses

DNS can also provide information about:

- Mail exchangers.
- Name servers.
- Aliases.
- Zone administration.
- Reverse address mappings.
- Textual verification information.
- Other service-related records.

You will study the most important record types later in this lab.

# 5. DNS Versus Routing

This distinction is fundamental.

DNS and routing answer different questions.

| DNS | Routing |
|---|---|
| What information is associated with this name? | Which network path should be selected for this IP destination? |
| Uses DNS records and resolution mechanisms | Uses routing rules and routing tables |
| Can return IPv4 or IPv6 addresses | Selects a path toward an IP destination |
| May involve recursive resolvers | May involve connected routes and gateways |
| Does not guarantee application connectivity | Does not automatically translate hostnames |

Consider an application attempting to reach:

```text
api.example.com
```

A simplified communication sequence is:

```text
                 APPLICATION
                      |
                      v
                api.example.com
                      |
                      v
                 DNS RESOLUTION
                      |
                      v
                  IP ADDRESS
                      |
                      v
               LINUX ROUTE LOOKUP
                      |
                      v
               OUTGOING INTERFACE
                      |
                      v
                 NETWORK PATH
                      |
                      v
               DESTINATION SERVICE
```

If DNS fails, the application may never obtain the expected destination address.

If routing fails, the application may obtain the correct address but still be unable to communicate.

### Important engineering principle

A successful DNS lookup does not prove that the destination application is operational.

Likewise, a valid default gateway does not prove that DNS is working.

### Checkpoint 1

Answer:

1. Does DNS forward application packets?
2. Does a default gateway resolve domain names?
3. Can routing be correct while DNS is broken?
4. Can DNS succeed while application connectivity fails?

**Expected answers:** No, no, yes, and yes.

# 6. Hostnames, Domain Names, and FQDNs

Consider:

```text
app01.production.example.com
```

This name contains several labels separated by dots.

```text
app01 . production . example . com
```

DNS names are hierarchical.

## 6.1 Hostname

A hostname identifies a host within a naming context.

On Ubuntu, inspect the configured hostname with:

```bash
hostname
```

Representative output:

```text
ubuntu-lab
```

A configured Linux hostname does not automatically mean that a corresponding public DNS record exists.

## 6.2 Domain name

A domain name identifies a node within the DNS hierarchy.

For example:

```text
example.com
```

Additional names can exist beneath it:

```text
production.example.com

development.example.com

training.example.com
```

## 6.3 Fully Qualified Domain Name

An FQDN identifies a name within the complete DNS hierarchy.

For example:

```text
app01.production.example.com.
```

The final dot explicitly represents the DNS root.

In ordinary application configuration, the trailing dot is frequently omitted.

## 6.4 Short names and search domains

Consider:

```text
database
```

This is a short name.

A resolver configured with:

```text
production.example.com
```

as a search domain may attempt a name such as:

```text
database.production.example.com
```

The actual behavior depends on resolver configuration and the application performing the lookup.

Do not assume that every application processes short names identically.

# 7. Understand the DNS Hierarchy

DNS is distributed.

It is not one central server containing every DNS record in the world.

Consider:

```text
www.example.com
```

A simplified hierarchy looks like this:

```text
                       DNS ROOT
                          .
                          |
                          v
                   TOP-LEVEL DOMAIN
                         com
                          |
                          v
                    DOMAIN LEVEL
                     example.com
                          |
                          v
                       HOSTNAME
                    www.example.com
```

## 7.1 Root DNS infrastructure

The root DNS system provides information that helps resolvers locate authoritative infrastructure for top-level domains.

Root servers do not ordinarily provide the final address record for every hostname.

## 7.2 Top-level domains

Examples include:

```text
.com

.org

.net

.ng

.mx

.uk
```

Top-level-domain infrastructure supports delegation toward the appropriate authoritative name servers.

## 7.3 Authoritative DNS servers

An authoritative DNS server provides authoritative information for the zones it serves.

For example, a DNS zone may contain records associated with:

```text
www.example.com

api.example.com

mail.example.com
```

## 7.4 Recursive resolvers

A recursive resolver accepts client queries and works to obtain suitable answers.

It may:

- Return a cached answer.
- Query other DNS servers.
- Follow DNS referrals.
- Return an error if resolution cannot be completed.

### Simplified recursive resolution

```text
                  LINUX APPLICATION
                          |
                          v
                    DNS REQUEST
                          |
                          v
                  RECURSIVE RESOLVER
                          |
                    CACHE CHECK
                     /       \
                   HIT       MISS
                    |          |
                    |          v
                    |       DNS ROOT
                    |          |
                    |          v
                    |      TLD SERVER
                    |          |
                    |          v
                    |    AUTHORITATIVE SERVER
                    |          |
                    +-----+----+
                          |
                          v
                      DNS ANSWER
                          |
                          v
                     APPLICATION
```

This diagram illustrates a simplified cache-miss lookup.

Actual behavior depends on the queried record, cached delegation information, DNS configuration, and resolver implementation.

### Checkpoint 2

Explain:

**Recursive resolver:** Obtains DNS answers for clients.

**Authoritative server:** Supplies authoritative DNS data for the zones it serves.

These are different roles, even when a broader infrastructure supports both functions.

# 8. DNS Resource Records

DNS information is represented through resource records.

The following types are especially important for Linux, cloud, DevOps, and production engineering.

## 8.1 A record

An A record associates a DNS name with an IPv4 address.

Illustrative example:

```text
app.example.com.    A    192.0.2.20
```

## 8.2 AAAA record

An AAAA record associates a DNS name with an IPv6 address.

```text
app.example.com.    AAAA    2001:db8::20
```

## 8.3 CNAME record

A CNAME record creates an alias from one DNS name to another canonical name.

```text
portal.example.com.    CNAME    app.example.com.
```

The client may need to continue resolution to obtain usable address information.

## 8.4 MX record

An MX record identifies mail exchangers for a domain.

```text
example.com.    MX    10 mail.example.com.
```

The number represents the MX preference value.

Lower preference values are normally preferred under ordinary MX selection rules.

## 8.5 NS record

An NS record identifies name servers associated with a zone or delegation.

```text
example.com.    NS    ns1.example.net.
```

## 8.6 SOA record

SOA stands for Start of Authority.

It contains administrative information associated with a DNS zone.

Important fields include:

- Primary name-server information.
- Responsible-party mailbox representation.
- Zone serial number.
- Refresh interval.
- Retry interval.
- Expire interval.
- Negative caching-related value.

You are not required to administer DNS zones in this lab.

## 8.7 PTR record

PTR records are commonly used for reverse DNS resolution.

They associate reverse DNS names with domain names.

## 8.8 TXT record

TXT records store textual DNS information.

They are frequently encountered in:

- Domain verification.
- Email authentication.
- Infrastructure ownership verification.

TXT records are not restricted to those uses.

### DNS record reference

| Record | Main purpose | Example use |
|---|---|---|
| A | Name to IPv4 address | Application endpoint |
| AAAA | Name to IPv6 address | IPv6 application endpoint |
| CNAME | DNS alias | Friendly application name |
| MX | Mail exchanger | Email routing |
| NS | Name-server information | DNS delegation |
| SOA | Zone administrative information | DNS zone management |
| PTR | Reverse DNS | Address-to-name lookup |
| TXT | Textual information | Domain verification |

## Practical Exercise 2 — Identify the correct record

Determine which record is appropriate.

| Requirement | Answer |
|---|---|
| Associate `api.example.com` with IPv4 | A |
| Associate a hostname with IPv6 | AAAA |
| Create an alias for an existing DNS name | CNAME |
| Identify a mail exchanger | MX |
| Identify zone name servers | NS |
| Retrieve reverse DNS information | PTR |
| Publish textual verification information | TXT |

# 9. Forward and Reverse DNS Resolution

DNS lookups can operate in different directions.

## 9.1 Forward resolution

Forward resolution retrieves information associated with a hostname.

Example:

```text
app.example.com
       |
       v
     A QUERY
       |
       v
   192.0.2.20
```

An AAAA lookup can retrieve IPv6 address information.

## 9.2 Reverse resolution

Reverse DNS commonly uses PTR records to retrieve a name associated with an IP address.

For IPv4, the reverse DNS namespace is:

```text
in-addr.arpa
```

For example:

```text
192.0.2.20
```

corresponds to the reverse DNS query name:

```text
20.2.0.192.in-addr.arpa
```

IPv6 reverse DNS uses:

```text
ip6.arpa
```

## 9.3 Forward and reverse DNS are not automatically symmetrical

An A record can exist without a corresponding PTR record.

A PTR record can also point to a name whose forward DNS information does not match the original address.

Do not treat reverse DNS alone as proof of identity or trustworthiness.

### Checkpoint 3

1. Which record provides IPv4 information?
2. Which record provides IPv6 information?
3. Which record is commonly used for reverse DNS?
4. Does every valid A record require a matching PTR record?

**Answers:** A, AAAA, PTR, and no.

# 10. DNS Caching and Time to Live

DNS queries do not always require contacting authoritative infrastructure.

Resolvers may cache suitable information.

Caching can reduce repeated lookup work and improve resolution performance.

## 10.1 What is TTL?

TTL means Time to Live.

Consider an illustrative record:

```text
app.example.com.    300    IN    A    192.0.2.20
```

The TTL is:

```text
300 seconds
```

That is five minutes.

TTL influences how long caching resolvers may retain DNS information under applicable caching rules.

## 10.2 Positive caching

Positive caching stores successful DNS information.

For example:

```text
Query:
app.example.com A

Answer:
192.0.2.20
```

The resolver may retain this information according to the applicable caching behavior.

## 10.3 Negative caching

Certain negative DNS responses can also be cached.

For example, an authoritative response indicating that a requested name does not exist may be cached.

This becomes relevant when a previously missing record is created.

## 10.4 Production example

Suppose an application endpoint changes:

```text
OLD ADDRESS:
192.0.2.20
```

```text
NEW ADDRESS:
192.0.2.30
```

The DNS record is updated.

However, some clients may temporarily continue using previously cached information.

Factors affecting observed behavior include:

- Remaining TTL.
- Intermediate caches.
- Application-level caching.
- Negative caching.
- Resolver implementation.
- Existing application connections.

### Engineering principle

A DNS change does not guarantee that every application immediately observes the new record.

Do not flush caches indiscriminately during an incident. Cached information may be useful evidence.

# 11. How Linux Resolves Hostnames

This is one of the most important sections of JUN-049.

An application performing hostname resolution does not necessarily send a direct DNS query itself.

Many Linux applications use system name-resolution interfaces.

The configured Name Service Switch mechanism can influence where hostname information comes from.

Potential sources include:

- Local files.
- DNS.
- `systemd-resolved`.
- Other configured NSS modules.

A simplified architecture is:

```text
                    APPLICATION
                         |
                         v
                 SYSTEM NAME LOOKUP
                         |
                         v
                NAME SERVICE SWITCH
                         |
              +----------+----------+
              |                     |
              v                     v
          LOCAL FILES        OTHER CONFIGURED
           /etc/hosts        RESOLUTION SOURCES
                                    |
                                    v
                               DNS RESOLVER
                                    |
                                    v
                                DNS ANSWER
```

The actual path depends on the application and the host's configuration.

## 11.1 What is NSS?

NSS stands for Name Service Switch.

It provides a configurable mechanism for selecting information sources for different system databases.

Its configuration file is:

```text
/etc/nsswitch.conf
```

## 11.2 The hosts database

The `hosts` entry defines the configured hostname-resolution sources and relevant lookup behavior for NSS-aware interfaces.

A representative configuration might resemble:

```text
hosts: files resolve [!UNAVAIL=return] dns
```

Your Ubuntu host may use a different arrangement.

### Understand the fields

| Field | Meaning |
|---|---|
| `hosts:` | Hostname-resolution database |
| `files` | Local file-based resolution, commonly `/etc/hosts` |
| `resolve` | Integration with `systemd-resolved` through its NSS module |
| `dns` | DNS resolution through the NSS DNS module |
| Bracketed actions | Conditions influencing whether NSS continues to another source |

Do not assume the example is your actual configuration.

The file:

```text

```

contains local static hostname-to-address mappings.

Run:

## 13.1 Understand the structure

Consider:


The first field identifies an IP address.

The following field identifies an associated hostname.

## 13.2 Why `/etc/hosts` matters

Local mappings can support:

- Loopback hostname resolution.
- Host-specific naming.
- Controlled testing.
- Certain bootstrap configurations.

They are not automatically synchronized with authoritative DNS records.

# 14. Understand `/etc/resolv.conf`

The file:

```text
/etc/resolv.conf
```

is important in traditional Linux DNS resolver configuration.

Inspect it:

```bash
cat /etc/resolv.conf
```

On an Ubuntu system using `systemd-resolved`, representative contents may resemble:

```text
nameserver 127.0.0.53

options edns0 trust-ad

search .
```

Your actual configuration may differ.

## 14.1 The nameserver directive

Example:

```text
nameserver 127.0.0.53
```

This identifies a resolver address for traditional clients using the file.

The address `127.0.0.53` is commonly associated with the local `systemd-resolved` DNS stub listener.

It is not necessarily the organization's upstream DNS server.

## 14.2 The search directive

Example:

```text
search production.example.com
```

This can influence how certain relative names are expanded during resolution.

For example:

```text
database
```

may be attempted using the configured search-domain behavior.

## 14.3 The options directive

Example:

```text
options edns0 trust-ad
```

This supplies resolver-related options.

You are not required to configure these options in JUN-049.

## 14.4 Is `/etc/resolv.conf` always a normal file?

No.

It may be a symbolic link to a managed configuration file.

Inspect it:

```bash
ls -l /etc/resolv.conf
```

Representative output:

```text
/etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf
```

The actual target may differ.

### Important engineering rule

Do not overwrite `/etc/resolv.conf` simply because it contains a loopback resolver address.

Identify the component responsible for managing DNS first.

# 15. Understand systemd-resolved

Ubuntu Server commonly uses `systemd-resolved` as part of its name-resolution architecture.

Depending on configuration, it can provide:

- DNS query handling.
- DNS caching.
- Per-link DNS settings.
- Search-domain handling.
- A local DNS stub listener.
- Integration with system name-resolution interfaces.

## 15.1 Conceptual architecture

```text
                    APPLICATION
                         |
                         v
                NAME-RESOLUTION PATH
                         |
                         v
                  systemd-resolved
                         |
               +---------+---------+
               |                   |
               v                   v
             CACHE           DNS CONFIGURATION
                                   |
                                   v
                            UPSTREAM RESOLVER
                                   |
                                   v
                               DNS ANSWER
```

This is a simplified model.

Some applications use their own DNS libraries or query paths.

## 15.2 Local stub versus upstream resolver

Remember:

```text
LOCAL DNS STUB ADDRESS
          ≠
UPSTREAM DNS SERVER ADDRESS
```

For example:

```text
127.0.0.53
```

may represent the local listener.

The upstream DNS server could be an address supplied by DHCP, static network configuration, or another approved management mechanism.

# 19. Understand Common DNS Response Outcomes

DNS queries can produce different outcomes.

Recognizing these differences prevents incorrect troubleshooting conclusions.

## 19.1 Successful response

A successful response may contain the requested records.

Illustrative example:

```text
Name: app.example.com

Type: A

Answer: 192.0.2.20
```

## 19.2 NXDOMAIN

NXDOMAIN indicates that the queried DNS name does not exist according to the applicable DNS response.

It is not equivalent to a network timeout.

## 19.3 NOERROR without the requested record

A query can complete successfully at the DNS protocol level without returning a record of the requested type.

For example, a name may exist but have no A record.

## 19.4 SERVFAIL

SERVFAIL indicates that the DNS server could not complete the query successfully.

The underlying reason requires further investigation.

## 19.5 REFUSED

REFUSED indicates that the DNS server refused the requested operation.

This may reflect server policy or configuration.

## 19.6 Timeout

A timeout means the client did not receive an acceptable response within the relevant time window.

Possible causes include:

- Resolver unavailability.
- Network connectivity problems.
- Filtering.
- Packet loss.
- Incorrect resolver configuration.
- Other infrastructure failures.

### DNS response reference

| Outcome | Basic interpretation |
|---|---|
| Successful answer | Requested information returned |
| NXDOMAIN | Queried DNS name does not exist according to the response |
| NOERROR without requested record | Query completed without the requested answer |
| SERVFAIL | Server could not complete the query successfully |
| REFUSED | Server refused the operation |
| Timeout | No acceptable response received in time |

Do not treat all failed lookups as identical.

# 20. DNS Transport Fundamentals

DNS commonly uses:

```text
UDP port 53

TCP port 53
```

Modern DNS environments can also support encrypted transport mechanisms such as DNS over TLS and DNS over HTTPS.

You are not required to configure them in this lab.

## 20.1 Why both UDP and TCP?

Traditional DNS commonly uses UDP for many queries.

TCP is also an established DNS transport and is important for:

- Responses requiring TCP.
- Certain larger DNS exchanges.
- Appropriate DNS zone-transfer operations.
- Other supported DNS communication.

Do not assume DNS always uses UDP.

## 20.2 DNS port versus application port

Consider:

```text
APPLICATION NEEDS api.example.com
                |
                v
           DNS RESOLUTION
                |
                v
           RECEIVES IP
                |
                v
       APPLICATION CONNECTION
```

The application may subsequently use a different destination port.

For example, HTTPS commonly uses TCP port 443, with other supported transport arrangements possible.

DNS port 53 is not the destination port for every application that depends on DNS.

# 21. Common DNS Misconceptions and Failure Patterns

Before investigating the production incident, review these mistakes.

## Mistake 1 — DNS and routing are the same thing

Incorrect.

DNS resolves naming information. Routing determines network paths.

## Mistake 2 — A valid default gateway guarantees DNS resolution

Incorrect.

The resolver may be unavailable, incorrectly configured, or unable to resolve the requested name.

## Mistake 3 — `/etc/resolv.conf` always displays the actual upstream DNS server

Incorrect.

It may display a local stub resolver address.

## Mistake 4 — `127.0.0.53` is automatically a configuration error

Incorrect.

It is commonly associated with the local `systemd-resolved` stub listener.

## Mistake 5 — getent and dig always follow the same lookup path

Incorrect.

They use different resolution interfaces.

## Mistake 6 — Every hostname must exist in public DNS

Incorrect.

Organizations commonly use private DNS namespaces.

## Mistake 7 — A successful DNS lookup proves application availability

Incorrect.

Name resolution does not independently verify routing, firewall permissions, transport connectivity, or application health.

## Mistake 8 — NXDOMAIN and timeout mean the same thing

Incorrect.

They represent different conditions.

## Mistake 9 — DNS changes become visible everywhere immediately

Incorrect.

Caching can delay when clients observe updated information.

## Mistake 10 — Restarting the resolver is always the correct first troubleshooting step

Incorrect.

Inspect configuration and preserve useful evidence before considering an authorized change.

- DHCP.

# 24. DNS Troubleshooting Decision Tree

Use this decision tree when a hostname lookup fails.

The objective is to identify the failing stage before changing configuration.

```text
              HOSTNAME LOOKUP FAILED
                        |
                        v
              IDENTIFY EXACT NAME
                        |
                        v
              DOES localhost RESOLVE?
                  /           \
                YES            NO
                 |              |
                 |              v
                 |        INSPECT /etc/hosts
                 |        AND NSS CONFIGURATION
                 |
                 v
          INSPECT NSS HOSTS POLICY
                 |
                 v
          INSPECT /etc/resolv.conf
                 |
                 v
          IDENTIFY ACTIVE RESOLVER
                 |
                 v
          TEST THE REQUIRED NAME
                 |
                 v
          CLASSIFY THE RESPONSE
                 |
          +------+------+-------+
          |             |       |
          v             v       v
       NXDOMAIN      SERVFAIL  TIMEOUT
          |             |       |
          v             v       v
       CHECK NAME    INVESTIGATE INVESTIGATE
       AND RECORD    RESOLVER    RESOLVER AND
       EXPECTATION   FAILURE     NETWORK PATH
          |             |       |
          +------+------+-------+
                 |
                 v
        COMPARE WITH APPROVED DESIGN
                 |
                 v
          FORM AND TEST HYPOTHESIS
                 |
                 v
          AUTHORIZED CORRECTION
                 |
                 v
          REPEAT ORIGINAL LOOKUP
                 |
                 v
        VERIFY APPLICATION RECOVERY
```

This is a foundational decision tree, not an exhaustive diagnostic procedure.

A failed `localhost` lookup should prompt inspection of local resolution mechanisms, but it does not by itself establish that external DNS is broken.

Likewise, a DNS query can complete without returning the requested record type; that outcome should be distinguished from NXDOMAIN, SERVFAIL, and timeout.

## 24.1 Interpret the observations

| Observation | Investigation direction |
|---|---|
| `localhost` fails | Inspect local mappings and NSS configuration |
| Local resolution succeeds but external resolution fails | Inspect resolver configuration and DNS response |
| Incorrect DNS server configured | Compare with the approved resolver baseline |
| NXDOMAIN | Verify the queried name and expected DNS data |
| SERVFAIL | Investigate why the resolver could not complete the query |
| Timeout | Investigate resolver availability and relevant network path |
| `getent` succeeds but `dig` differs | Compare NSS resolution with direct DNS querying |
| DNS succeeds but the application fails | Continue beyond DNS; do not declare application recovery |

## 24.2 Safe first-response workflow

Use:

**Symptom → Impact → Evidence → Hypothesis → Test → Root Cause → Authorized Fix → Recovery Verification → Prevention**

Do not automatically:

- Restart networking.
- Flush DNS caches.
- Overwrite `/etc/resolv.conf`.
- Replace DNS servers.
- Change Netplan.
- Modify `/etc/hosts`.

Preserve the evidence, identify the configuration owner, and compare the observed configuration with the approved design.

# 27. Interview Preparation — 10 Questions with Worked Answers

## Interview Question 1 — Explain DNS to a junior engineer.

DNS is a distributed naming system that allows clients to retrieve records associated with domain names.

One common use is resolving a hostname into IPv4 or IPv6 address information.

Applications can then use that information when establishing network communication.

DNS does not replace routing or guarantee application availability.

## Interview Question 2 — What happens when a Linux application resolves a hostname?

The application uses an appropriate name-resolution interface.

Depending on the environment, resolution may involve local files, NSS modules, a local resolver, cached information, and recursive DNS infrastructure.

The exact sequence depends on the application and system configuration.

## Interview Question 3 — What is the difference between recursive and authoritative DNS?

A recursive resolver obtains DNS answers for clients.

An authoritative server supplies authoritative DNS data for the zones it serves.

A recursive resolver may contact multiple DNS servers when suitable cached information is unavailable.

## Interview Question 4 — What is the difference between A and AAAA records?

An A record contains an IPv4 address.

An AAAA record contains an IPv6 address.

## Interview Question 5 — What is `/etc/hosts` used for?

It provides local static hostname-to-address mappings.

Depending on the configured name-resolution policy, these mappings can participate in hostname resolution without requiring external DNS.

## Interview Question 6 — Why does Ubuntu sometimes display `127.0.0.53` in `/etc/resolv.conf`?

Ubuntu commonly uses `systemd-resolved`.

The address can represent its local DNS stub listener rather than the upstream DNS server.

I would inspect the actual resolver configuration using:

```bash
resolvectl status
```

and:

```bash
resolvectl dns
```

## Interview Question 7 — What is the difference between getent and dig?

`getent` uses the configured system name-service mechanisms for the requested database.

`dig` performs DNS queries.

Therefore, `getent` may return information from `/etc/hosts`, while `dig` does not reproduce the complete NSS lookup process.

## Interview Question 8 — What does DNS TTL control?

TTL influences how long DNS information may be retained by caching resolvers under applicable caching rules.

It is important when planning DNS changes and investigating stale responses.

## Interview Question 9 — An application cannot resolve an internal hostname. What would you inspect first?

I would identify the exact failing name, inspect NSS policy, check local mappings, inspect the resolver configuration, identify active DNS servers, and perform a controlled lookup.

I would compare the observations with the approved internal DNS design before making changes.

## Interview Question 10 — Can a server have correct routing and still experience DNS failure?

Yes.

A server may have valid interfaces, addresses, and routes while using an unavailable or incorrectly configured DNS resolver.

Routing and name resolution must be investigated separately.
