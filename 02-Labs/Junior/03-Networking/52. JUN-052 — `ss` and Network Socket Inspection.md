# 1. Production Mission

You are supporting an Ubuntu application server.

Monitoring reports that an internal API is intermittently unavailable.

The application should listen on:

```text
TCP 8443
```

The operations team has already established:

```text
DNS resolution: successful
Destination address: correct
Routing: present
Application process: reported as running
```

But clients are still experiencing connection failures.

You now need to investigate the Linux socket layer.

You are not going to begin by restarting the application.

You are not going to change firewall rules.

You are not going to kill processes.

You are going to answer the questions that matter:

```text
Is the expected socket present?

Which protocol is it using?

Which address is it bound to?

Which port is it using?

What state is the socket in?

Which process owns it?

Are connections reaching it?

What are the local and peer endpoints?

Are connection queues showing anything important?

Are there abnormal socket-state patterns?

Does the evidence support an application problem,
a binding problem, a port problem, or something beyond
the local socket layer?
```

The primary instrument for this investigation is:

```bash
ss
```

By the end of this lab, you should not merely know several `ss` commands.

You should be able to use `ss` as part of a disciplined production investigation.

# 9. Understand the `ss` Output Structure

Run:

```bash
ss -tn
```

You may see output resembling:

```text
State  Recv-Q Send-Q Local Address:Port    Peer Address:Port
ESTAB  0      0      10.20.10.25:22       10.20.10.100:53124
```

This is illustrative.

Your output will differ.

Focus on the columns.

## State

For TCP, this indicates the TCP socket state.

Example:

```text
ESTAB
```

means an established connection.

## Recv-Q

Represents queued receive-side data or state-specific queue information.

Its interpretation depends on the socket state.

## Send-Q

Represents queued send-side data or state-specific queue information.

Again, interpretation depends on socket state.

## Local Address:Port

The local endpoint.

## Peer Address:Port

The remote endpoint associated with a connected socket.

```text
LOCAL ADDRESS:
```

# 17. Filter the Listener by Local Port

Listing every socket becomes inefficient on busy servers.

Use an `ss` filter.

Run:

```bash

```

## Understand the filter

```text
sport
```

means source/local port in this socket-filter context.

```text
= :8080
```

matches port 8080.

For a local listening socket, this allows you to isolate the local service port.

Now try a port you are unlikely to be using:

```bash
ss -ltn 'sport = :54321'
```

If nothing appears, that is useful evidence:

```text

```

It does not prove that port 54321 can never be used.

It describes the current observation.

# 21. Understand File Descriptors

Linux processes interact with resources through file descriptors.

A socket can be associated with a process file descriptor.

When `ss -p` displays something like:

```text
fd=3
```

that does not mean:

```text
TCP port 3
```

It means the process has a file descriptor numbered `3` associated with that socket.

Keep these namespaces separate:

```text
PROCESS ID
≠
FILE DESCRIPTOR
≠
NETWORK PORT
```

# 28. Inspect Specific TCP States

Run:

```bash
ss -tan state established
```

Then:

```bash
ss -tan state time-wait
```

Then:

```bash
ss -tan state close-wait
```

Do not expect every state to contain sockets.

Record:

```text
ESTABLISHED COUNT OBSERVED:

TIME-WAIT COUNT OBSERVED:

CLOSE-WAIT COUNT OBSERVED:
```

## State interpretation

### ESTABLISHED

A TCP connection has completed connection establishment and is active at the transport layer.

### TIME-WAIT

A normal TCP state associated with connection termination and protection against delayed segments affecting later connections.

Its presence is not automatically a problem.

### CLOSE-WAIT

The remote side has closed its side of the connection, but the local application has not yet fully closed its corresponding socket.

A persistent large accumulation can justify deeper application investigation.

One `CLOSE-WAIT` socket does not automatically prove an application defect.

# 29. Count Socket States

You can combine `ss` with text-processing tools for basic analysis.

Run:

```bash
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c | sort -nr
```

Understand each stage.

```text
ss -tan
```

produces numeric TCP socket information.

```text
awk 'NR>1 {print $1}'
```

skips the header and prints the first column.

```text
sort
```

groups identical state names together.

```text
uniq -c
```

counts adjacent identical entries.

```text
sort -nr
```

sorts the counts numerically in descending order.

Illustrative output:

```text
18 TIME-WAIT
5 ESTAB
3 LISTEN
```

Your output will differ.

## Do not overdiagnose counts

A large number of sockets in one state can be important.

But the count alone does not establish a root cause.

You still need:

- Baseline.
- Workload context.
- Application architecture.
- Time trend.
- Resource impact.
- Correlated evidence.

# 33. Filter by Peer Address

For an existing authorized connection, you can filter by peer address.

The general pattern is:

```bash
ss -tn 'dst PEER_IP'
```

For example, if your own observed peer were:

```text
192.0.2.20
```

the conceptual command would be:

```bash
ss -tn 'dst 192.0.2.20'
```

Do not use the illustrative address as though it were your actual peer.

Use an address genuinely present in your authorized environment.

Likewise, local-address filtering can use:

```bash
ss -tn 'src LOCAL_IP'
```

### Why this matters

On servers with hundreds or thousands of connections, endpoint filtering can isolate traffic associated with one system.

# 35. Understand `Recv-Q` and `Send-Q`

Queue columns are often misunderstood.

Run:

```bash
ss -ltn
```

Look at:

```text
Recv-Q
Send-Q
```

Now run:

```bash
ss -tn
```

Look at the same columns for connected sockets.

## Critical distinction

Their interpretation depends on socket state.

For an established TCP connection, broadly:

```text
Recv-Q
```

can represent data received by the kernel that the application has not yet consumed.

```text
Send-Q
```

can represent data queued for transmission or not yet acknowledged, depending on the relevant context.

For listening TCP sockets, the queue fields represent listener/backlog-related information rather than ordinary application payload queues.

Therefore:

```text
Recv-Q = 100
```

does not mean the same thing for every socket state.

## Engineering rule

Before interpreting a queue value, ask:

```text
What state is this socket in?
```

| Command | Purpose |
|---|---|
| `ss` | Display socket information |

| `ss -un` | Display numeric UDP sockets |

| `ss -lun` | Display UDP service-style sockets numerically |
| `ss -lntu` | Display TCP and UDP listener/service-style sockets |
| `ss -tan` | Display TCP sockets including listening/non-listening states numerically |
| `ss -ltnp` | Display TCP listeners with process information where permitted |
| `ss -tnp` | Display TCP sockets with process information where permitted |
| `ss -s` | Display socket summary statistics |

## Core Flags

| Flag | Meaning |
|---|---|
| `-l` | Listening sockets |
| `-t` | TCP |
| `-u` | UDP |

| `-4` | IPv4 |
| `-6` | IPv6 |
| `-s` | Summary statistics |

| Command | Purpose |
|---|---|
| `ss -tan state established` | Established TCP sockets |

| `ss -tan state syn-sent` | TCP sockets in SYN-SENT |
| `ss -tan state syn-recv` | TCP sockets in SYN-RECV |

Not every state will be present when you inspect the host.

## Endpoint Filters

| Filter | Purpose |
|---|---|
| `sport = :8080` | Match local/source port 8080 |
| `dport = :8080` | Match peer/destination port 8080 |
| `src 127.0.0.1` | Match local/source address |
| `dst ADDRESS` | Match peer/destination address |


# 62. What `ss` Evidence Does and Does Not Prove

| Observation | What It Supports | What It Does Not Automatically Prove |
|---|---|---|
| TCP `LISTEN` | Local TCP listener exists | Remote reachability |
| No expected listener | Expected socket not observed | Exact reason it is absent |
| `ESTAB` | TCP connection established | Application request succeeded |
| High `TIME-WAIT` count | Many sockets observed in TIME-WAIT | Socket exhaustion |
| `CLOSE-WAIT` sockets | Peer closure received; local close incomplete | Application bug without further evidence |
| Process shown | Process associated with socket | Entire application healthy |
| Wildcard binding | Socket not limited to one specific local address in ordinary binding terms | Firewall permits remote access |
| Loopback binding | Socket bound to loopback | Service should necessarily be remotely exposed |
| Non-zero queue | Data/backlog exists in state-specific context | Network congestion by itself |
| `ss -s` high count | Many sockets exist | Root cause of incident |

# 75. Knowledge Check — 25 Questions with Answers

## 1. What is `ss` used for?

**Answer:** `ss` is used to inspect socket information on Linux, including TCP and UDP sockets, states, endpoints, queues, and process information where available.

## 2. What does `ss -ltn` show?

**Answer:** Listening TCP sockets with numeric addresses and ports.

## 3. What does `-n` do?

**Answer:** It prevents address/service-name resolution and displays numeric information where applicable.

## 4. What does `-p` request?

**Answer:** Process information associated with sockets where permissions allow.

## 5. What does `-4` do?

**Answer:** Restricts socket selection to IPv4.

## 6. What does `-6` do?

**Answer:** Restricts socket selection to IPv6.

## 7. What does `ss -s` provide?

**Answer:** A high-level socket summary.

## 8. Does a high socket count automatically identify a problem?

**Answer:** No. It must be interpreted using workload, baseline, trends, application behavior, and other evidence.

## 9. What does TCP `LISTEN` mean?

**Answer:** The socket is prepared to accept incoming TCP connection requests.

## 10. What does `ESTAB` mean?

**Answer:** The TCP connection is established at the transport layer.

## 11. Does `ESTAB` prove the application request succeeded?

**Answer:** No.

## 12. Is `TIME-WAIT` automatically an error?

**Answer:** No. It is a normal TCP connection-termination state.

## 13. What can persistent large numbers of `CLOSE-WAIT` sockets justify investigating?

**Answer:** Whether an application is failing to close sockets after receiving peer-side closure, while recognizing that additional evidence is required.

## 14. What does `sport = :8080` filter?

**Answer:** Sockets whose local/source port matches 8080 in the `ss` filtering context.

## 15. What does `dport = :443` filter?

**Answer:** Sockets whose peer/destination port matches 443.

## 16. Why prefer native `ss` filters over `grep` when practical?

**Answer:** Native filters operate on socket attributes rather than merely matching rendered text.

## 17. What does `127.0.0.1:8080` indicate?

**Answer:** An IPv4 socket bound to loopback port 8080.

## 18. Does `0.0.0.0:8443` prove remote access is possible?

**Answer:** No. Routing, firewall rules, security groups, ACLs, and other controls can still prevent access.

## 19. Can one listening socket coexist with many established sockets?

**Answer:** Yes. The listening socket accepts connections while accepted sessions are represented by connected sockets.

## 20. Why might `ss -p` not show process information?

**Answer:** Permission restrictions may limit process visibility.

## 21. What should you do when process information is unavailable?

**Answer:** Record the limitation and use approved privilege procedures if process ownership is required.

## 22. Do `Recv-Q` and `Send-Q` mean exactly the same thing for listening and established sockets?

**Answer:** No. Queue interpretation depends on socket state.

## 23. If a process is active but its expected listener is absent, what should you investigate?

**Answer:** Application startup, binding, port configuration, resource conditions, and relevant service logs or configuration.

## 24. If the expected listener exists but remote clients time out, what should you investigate next?

**Answer:** The remote path, filtering, firewall/security controls, routing context, and other infrastructure between client and listener.

## 25. What is the central rule of socket troubleshooting?

**Answer:** Use socket evidence to establish protocol, address, port, state, and ownership before claiming a root cause.

# 76. Interview Preparation — 10 Questions with Worked Answers

## Interview Question 1 — How do you check whether a TCP service is listening on Linux?

I would use `ss`, normally starting with:

```bash
ss -ltn
```

If I know the expected port, I would narrow it:

```bash
ss -ltn 'sport = :8443'
```

Where process information is required and permitted:

```bash
ss -ltnp 'sport = :8443'
```

I would verify not only the port but also the bind address and owning process.

## Interview Question 2 — What is the difference between `ss -ltn` and `ss -tn`?

`ss -ltn` selects listening TCP sockets.

`ss -tn` shows TCP sockets selected without restricting the view to listeners, which is useful for connected sockets such as established sessions.

## Interview Question 3 — How do you inspect established TCP connections?

I can use:

```bash
ss -tn state established
```

Then I can narrow by local port, peer port, address, or other relevant socket attributes.

## Interview Question 4 — Why is `ss -p` useful?

It can correlate sockets with owning processes, PIDs, and file descriptors where permissions permit.

That helps determine whether the expected application actually owns the endpoint.

## Interview Question 5 — What does it mean if an application process is running but the expected port is absent?

It means process existence has been established, but the expected listener has not.

I would investigate whether the application failed during initialization, is configured for a different port or bind address, or encountered another socket-creation problem.

I would not assume the firewall caused the missing local listener.

## Interview Question 6 — What is the difference between a listening socket and an established socket?

A listening TCP socket waits for incoming connection requests.

An established socket represents a specific TCP connection between endpoints after connection establishment.

One server listener can support many established connections.

## Interview Question 7 — What would you investigate if a service works locally but not remotely?

I would inspect its bind address first.

If it is bound only to `127.0.0.1`, that can explain local success and remote failure.

If the listener is correctly bound, I would continue into routing, filtering, host firewall, cloud security controls, load balancers, and other network-path components.

## Interview Question 8 — How would you investigate many TIME-WAIT sockets?

I would first establish the count, baseline, trend, affected endpoints, process/workload context, and whether there is actual resource impact.

TIME-WAIT itself is a normal TCP state, so I would not treat its presence alone as a failure.

## Interview Question 9 — What is wrong with using only `grep` against `ss` output?

`grep` performs text matching and can be useful for quick exploration, but native `ss` filters operate on socket attributes and can express the investigation more precisely.

I prefer native filtering when I know the socket condition I need.

## Interview Question 10 — What does a listening socket prove?

It proves that a local socket matching the observed protocol, address, port, and state exists at the time of inspection.

It does not by itself prove remote reachability or application-layer health.
