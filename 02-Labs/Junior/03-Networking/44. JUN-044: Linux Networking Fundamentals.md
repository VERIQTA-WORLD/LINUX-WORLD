## 2. Understand What a Computer Network Is

A computer network is a collection of devices that can exchange information through communication links using agreed protocols.

A device participating in a network is commonly called a **host**.

Examples include:

- Linux servers.
- Windows servers.
- Laptops.
- Virtual machines.
- Cloud instances.
- Containers with network connectivity.
- Network appliances.
- Storage systems.

Consider a simple network:

```text
                  LOCAL NETWORK

      +-------------------------------+
      |                               |
      |   Ubuntu Server A             |
      |   192.168.10.10                |
      |                               |
      +---------------+---------------+
                      |
                      |
                    SWITCH
                      |
          +-----------+-----------+
          |                       |
          |                       |
   Ubuntu Server B          Ubuntu Server C
   192.168.10.20            192.168.10.30
```

These machines can participate in the same IP network when their interfaces, addressing, link connectivity, and other relevant configuration are correct.

### What does a network actually transport?

Applications exchange information.

That information is represented as data and transmitted through the networking stack.

A simplified communication model is:

```text
APPLICATION DATA
       |
       v
TRANSPORT PROCESSING
       |
       v
IP PACKET
       |
       v
LINK-LAYER FRAME
       |
       v
NETWORK MEDIUM
```

At the receiving system, the corresponding networking layers process the incoming information and deliver it to the appropriate endpoint.

### Network communication requires cooperation

A working network connection is not determined by one configuration value.

For example:

```text
VALID IP ADDRESS
       |
       v
Does not automatically prove:
       |
       +-- interface availability
       |
       +-- correct routing
       |
       +-- destination availability
       |
       +-- DNS functionality
       |
       +-- application availability
```

This is an important engineering distinction.

A Linux server can have a valid IP address and still fail to communicate with a particular destination.

## 3. Understand the OSI and TCP/IP Networking Models

Networking involves several responsibilities.

Engineers use layered models to understand how those responsibilities relate to one another.

Two common models are:

1. OSI.
2. TCP/IP.

### The OSI model

The OSI reference model contains seven conceptual layers.

| Layer | Name | Main responsibility |
|---|---|---|
| 7 | Application | Services used by applications |
| 6 | Presentation | Data representation and transformation |
| 5 | Session | Managing communication sessions |
| 4 | Transport | Transport between communication endpoints |
| 3 | Network | Logical addressing and routing |
| 2 | Data Link | Communication over a local link |
| 1 | Physical | Transmission through physical media |

The OSI model is useful for organizing networking concepts and troubleshooting discussions.

Real-world protocols do not always fit perfectly into one isolated OSI layer.

### The TCP/IP model

A common representation of the TCP/IP model contains four layers.

```text
+--------------------------------------+
| APPLICATION                          |
| HTTP, DNS, SSH and related protocols |
+--------------------------------------+
| TRANSPORT                            |
| TCP, UDP                             |
+--------------------------------------+
| INTERNET                             |
| IPv4, IPv6                           |
+--------------------------------------+
| LINK                                 |
| Ethernet and other link technologies |
+--------------------------------------+
```

### Connect the two models

| TCP/IP layer | Approximate OSI relationship |
|---|---|
| Application | Application, Presentation, Session |
| Transport | Transport |
| Internet | Network |
| Link | Data Link and Physical |

These mappings are conceptual rather than exact protocol boundaries.

### Why this matters during troubleshooting

Imagine an engineer receives this report:

> The application cannot reach the database.

The failure could involve several different responsibilities.

```text
APPLICATION
    |
    +-- Is the application functioning?
    |
TRANSPORT
    |
    +-- Is the expected communication endpoint available?
    |
INTERNET
    |
    +-- Is there a usable IP route?
    |
LINK
    |
    +-- Is the local network interface operational?
```

You should not immediately assume that the application itself is responsible.

Likewise, you should not immediately blame networking simply because an application reports a connection failure.

The purpose of layered reasoning is to narrow the investigation using evidence.

### Checkpoint 1

Answer:

1. How many layers are in the OSI model?
2. Which OSI layer is associated with logical addressing and routing?
3. Which TCP/IP layer contains TCP and UDP?
4. Why is a layered model useful during troubleshooting?
5. Does every real-world protocol map perfectly to one OSI layer?

## 4. Understand Linux Network Interfaces

A network interface is an endpoint through which Linux participates in network communication.

Interfaces may represent physical hardware, virtual networking components, or internal operating-system mechanisms.

Examples of interface names include:

```text
lo
eth0
ens3
enp1s0
```

Your machine may use different names.

Do not assume every Ubuntu server has an interface named `eth0`.

### Physical network interfaces

A physical interface is associated with actual networking hardware.

Examples include:

- Ethernet adapters.
- Wireless adapters.
- Additional server network cards.

A physical Ethernet interface may connect to a switch or another network device.

### Virtual network interfaces

Virtual interfaces are software-defined networking components.

They are common in:

- Virtual machines.
- Cloud infrastructure.
- Container environments.
- VPNs.
- Bridges.
- Network namespaces.

A virtual machine can have a network interface even though it does not own a dedicated physical network card.

### Loopback interface

Linux provides a special interface commonly named:

```text
lo
```

This is the loopback interface.

It supports communication within the same host.

A common IPv4 loopback address is:

```text
127.0.0.1
```

The IPv6 loopback address is:

```text
::1
```

Conceptually:

```text
             LINUX HOST

       +-------------------+
       |                   |
       |   Application A   |
       |         |         |
       |         v         |
       |    LOOPBACK       |
       |         |         |
       |         v         |
       |   Application B   |
       |                   |
       +-------------------+
```

Loopback communication does not require packets to leave through an external network interface.

### Practical Task 1 — Discover your network interfaces

Run:

```bash
ip link show
```

**Purpose:** Display the network interfaces visible in the current network namespace, together with basic link-layer information.

Representative output:

```text
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 state UNKNOWN
    link/loopback 00:00:00:00:00:00

2: ens3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP
    link/ether 52:54:00:12:34:56 brd ff:ff:ff:ff:ff:ff
```

Your actual output may differ.

### Understand the important fields

**Interface name**

Examples:

```text
lo
ens3
```

**MTU**

MTU means Maximum Transmission Unit.

It describes the maximum network-layer packet size supported by the relevant link configuration without requiring fragmentation at that link.

For example:

```text
mtu 1500
```

is common for Ethernet environments.

Do not assume every interface uses MTU 1500.

**UP**

The interface has been administratively enabled.

**LOWER_UP**

The driver reports that the lower-layer link is operational.

These are related but different observations.

**state**

This reports the interface's operational state as represented by Linux.

The loopback interface may display `UNKNOWN` even while functioning normally. Do not automatically classify that as a failure.

### Verification

Identify:

```text
Loopback interface:

Non-loopback interface(s):

Interface currently marked UP:

Interface reporting LOWER_UP:

MTU of the main interface:
```

Do not change an interface state to obtain different output.

## 5. Understand MAC Addresses and Local Network Communication

A MAC address is a link-layer address associated with network interfaces in technologies such as Ethernet.

A typical Ethernet MAC address contains 48 bits.

It is commonly displayed as six hexadecimal octets.

Example:

```text
52:54:00:12:34:56
```

This example represents a possible locally administered virtual-interface address.

### MAC address versus IP address

These identifiers serve different purposes.

| MAC address | IP address |
|---|---|
| Link-layer addressing | Internet-layer addressing |
| Commonly associated with an interface | Assigned to an IP interface or endpoint |
| Used for delivery on relevant local links | Used for IP communication and routing |
| Example: `52:54:00:12:34:56` | Example: `192.168.10.20` |

Do not confuse the two.

A packet travelling between different IP networks can retain its end-to-end IP destination while being carried inside different link-layer frames along the path.

### Simplified local communication

Consider two hosts on the same Ethernet network.

```text
HOST A                         HOST B

IP: 192.168.10.10              IP: 192.168.10.20
MAC: AA:AA:AA:AA:AA:AA         MAC: BB:BB:BB:BB:BB:BB

              ETHERNET NETWORK
```

Host A needs an appropriate link-layer destination address to transmit an Ethernet frame toward Host B.

For IPv4 over Ethernet, ARP is commonly used to resolve the relevant IPv4 next-hop address to a link-layer address.

IPv6 uses Neighbor Discovery rather than IPv4 ARP.

Detailed ARP and Neighbor Discovery troubleshooting is outside this introductory lab.

### Practical Task 2 — Identify MAC addresses

Run:

```bash
ip link show
```

Look for:

```text
link/ether
```

Record the MAC address associated with your main Ethernet-style interface, if one exists.

Do not expect every interface type to expose an Ethernet MAC address.

For loopback, you may see:

```text
link/loopback
```

1. What is a MAC address?
2. What is the difference between MAC and IP addressing?
3. Why does a remote IP destination not necessarily correspond to the MAC address used on the first local Ethernet frame?
4. Why might a virtual machine have a MAC address?

## 6. Understand IPv4, IPv6, and CIDR Prefixes

IP addressing allows systems to identify endpoints and route packets across IP networks.

Two major versions are used:

```text
IPv4
IPv6
```

### IPv4

An IPv4 address contains 32 bits.

It is normally represented using dotted-decimal notation.

Example:

```text
192.168.10.20
```

Each dotted component represents eight bits.

Conceptually:

```text
192 . 168 . 10 . 20
 |     |     |    |
8-bit 8-bit 8-bit 8-bit
```

### IPv6

An IPv6 address contains 128 bits.

It is represented using hexadecimal notation separated by colons.

Example:

```text
2001:db8::20
```

IPv6 provides a much larger address space and uses a different addressing and neighbor-discovery architecture from IPv4.

### Understand CIDR notation

You will frequently encounter addresses written like:

```text
192.168.10.20/24
```

The `/24` represents the prefix length.

It means the first 24 bits form the network prefix.

For this example:

```text
Address:
192.168.10.20

Prefix:
24 bits
```

A common corresponding IPv4 subnet mask is:

```text
255.255.255.0
```

Do not interpret `/24` as a port number.

It is address-prefix information.

### Private IPv4 address ranges

Three IPv4 ranges are reserved for private internetwork use.

| Range | CIDR block |
|---|---|
| 10.0.0.0–10.255.255.255 | `10.0.0.0/8` |
| 172.16.0.0–172.31.255.255 | `172.16.0.0/12` |
| 192.168.0.0–192.168.255.255 | `192.168.0.0/16` |

Private addresses are commonly used within internal networks.

They are not globally routed as ordinary public Internet destination addresses.

### Practical Task 3 — Inspect configured IP addresses

Run:

```bash
ip addr show
```

**Purpose:** Display interface addressing information.

Representative output:

```text
2: ens3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500
    link/ether 52:54:00:12:34:56
    inet 192.168.10.20/24 scope global ens3
    inet6 fe80::5054:ff:fe12:3456/64 scope link
```

Focus on:

```text
inet
```

for IPv4 and:

```text
inet6
```

for IPv6.

The `scope` field provides additional context about the address.

For example:

```text
scope link
```

commonly appears with IPv6 link-local addresses.

### Inspect IPv4 separately

Run:

```bash
ip -4 addr show
```

### Inspect IPv6 separately

Run:

```bash
ip -6 addr show
```

### Verification

Record:

```text
Main interface:

IPv4 address:

IPv4 prefix length:

IPv6 address(es), if present:

Loopback IPv4 address:

Loopback IPv6 address, if present:
```

If your environment has no globally scoped IPv6 address, that is not automatically a configuration error.

Document what exists.

## 7. Understand Subnets, Gateways, and Local Versus Remote Communication

A subnet represents an IP network identified by a prefix.

Consider:

```text
192.168.10.0/24
```

This prefix describes an IPv4 network containing addresses from:

```text
192.168.10.0
```

through:

```text
192.168.10.255
```

In a conventional `/24` subnet, the first address identifies the network and the final address is the directed broadcast address.

Usable host-address considerations depend on the address type and network design.

Detailed subnet calculations will be covered in JUN-047.

### Local communication

Consider:

```text
Server A:
192.168.10.10/24

Server B:
192.168.10.20/24
```

Both addresses belong to:

```text
192.168.10.0/24
```

With suitable interface and link configuration, the systems can communicate through the local network.

### Remote communication

Now consider:

```text
Server A:
192.168.10.10/24

Server C:
192.168.20.20/24
```

These addresses belong to different `/24` networks.

Server A requires an appropriate route toward Server C.

That route may use a gateway.

### What is a default gateway?

A gateway is a network device or next-hop endpoint used to forward traffic toward another network.

A default route is used when no more-specific applicable route provides a different forwarding decision.

Conceptually:

```text
                 LOCAL NETWORK
                192.168.10.0/24

       +---------------------------+
       | Ubuntu Server            |
       | 192.168.10.20             |
       +-------------+-------------+
                     |
                     |
             192.168.10.1
              DEFAULT GATEWAY
                     |
                     |
               OTHER NETWORKS
```

The default gateway is not necessarily used for every packet.

For example, locally routed destinations may use a directly connected route.

### Practical Task 4 — Inspect the routing table

Run:

```bash
ip route show
```

Representative output:

```text
default via 192.168.10.1 dev ens3

192.168.10.0/24 dev ens3 proto kernel scope link src 192.168.10.20
```

Interpret the first line:

```text
default
```

This identifies the default route.

```text
via 192.168.10.1
```

This identifies the next-hop gateway.

```text
dev ens3
```

This identifies the outgoing interface.

Now examine:

```text
192.168.10.0/24 dev ens3
```

This represents a route associated with the directly connected network.

### Inspect IPv6 routing

Run:

```bash
ip -6 route show
```

Your environment may have IPv6 routes, only link-local-related entries, or no useful IPv6 default route.

Do not assume IPv4 and IPv6 routing configurations are identical.

### Verification

Answer:

```text
Is an IPv4 default route present?

What gateway does it identify?

Which interface is used?

What directly connected IPv4 network is visible?

Is an IPv6 default route present?
```

Do not add a default route merely because your lab machine does not have one.

A machine may intentionally operate on an isolated network.

## 8. Understand Packets, Frames, and Encapsulation

When applications communicate, information passes through multiple networking layers.

Three terms are particularly important:

```text
DATA
PACKET
FRAME
```

### Application data

An application produces information to transmit.

For example, a web client may generate an HTTP request.

### Transport processing

The transport layer processes application communication.

For TCP, the transport protocol works with a byte stream and produces TCP segments.

For UDP, application messages are carried in UDP datagrams.

### IP packet

The Internet layer adds IP addressing information.

Conceptually:

```text
+-----------------------------+
| IP HEADER                   |
+-----------------------------+
| TRANSPORT INFORMATION       |
+-----------------------------+
| APPLICATION DATA            |
+-----------------------------+
```

### Link-layer frame

On an Ethernet link, an IP packet is carried inside an Ethernet frame.

Conceptually:

```text
+-----------------------------+
| ETHERNET HEADER             |
+-----------------------------+
| IP PACKET                   |
|                             |
|  +-----------------------+  |
|  | IP HEADER             |  |
|  +-----------------------+  |
|  | TRANSPORT DATA        |  |
|  +-----------------------+  |
|  | APPLICATION DATA      |  |
|  +-----------------------+  |
+-----------------------------+
| ETHERNET FRAME CHECK        |
+-----------------------------+
```

This process is called encapsulation.

The reverse process occurs as the receiving system processes the incoming information.

### Why encapsulation matters

Suppose a packet must cross several routed networks.

The IP packet is forwarded according to the routing decisions made along its path.

On Ethernet-based hops, the packet is carried inside link-layer frames appropriate to each hop.

The link-layer addressing used on one hop is not necessarily the same as the addressing used on the next.

### Engineer note

Do not treat these terms as interchangeable:

```text
Ethernet frame
```

```text
IP packet
```

```text
TCP segment
```

They describe different protocol data units.

You will explore packet-level inspection in later networking and troubleshooting work.

## 9. Understand DNS, TCP, UDP, and Ports

An application often communicates using a hostname instead of a manually entered IP address.

For example:

```text
example.com
```

The system may need to obtain address information associated with that name.

This introduces DNS.

### What is DNS?

DNS stands for Domain Name System.

It provides a distributed naming system that includes mappings between domain names and various record types.

One common use is obtaining IP address information for a hostname.

Conceptually:

```text
APPLICATION
     |
     v
example.com
     |
     v
NAME RESOLUTION
     |
     v
IP ADDRESS INFORMATION
```

Linux name resolution can involve several mechanisms, including local host mappings and DNS.

DNS fundamentals receive dedicated treatment in JUN-049.

### Inspect local name-resolution configuration

Run:

```bash
cat /etc/resolv.conf
```

You may encounter:

```text
nameserver 127.0.0.53
```

On Ubuntu systems using the `systemd-resolved` stub resolver, this can represent a local resolver endpoint.

It does not necessarily identify the upstream DNS server directly.

Do not edit this file during the lab.

### Perform a basic name-resolution test

Run:

```bash
getent hosts localhost
```

This checks name resolution through the system's configured name-service mechanisms.

A typical result includes a loopback address.

Next, run:

```bash
getent hosts example.com
```

If the environment has suitable external name-resolution access, the command may return one or more addresses.

If it returns nothing, do not immediately conclude that DNS itself is broken.

Possible explanations require further investigation.

### DNS is not connectivity

Keep this distinction:

```text
NAME RESOLVES
      |
      v
IP ADDRESS OBTAINED
      |
      X
Does not prove that the
remote application is reachable.
```

A successful lookup provides address information.

It does not prove routing, transport connectivity, or application health.

### Understand TCP and UDP

TCP and UDP are transport protocols.

| TCP | UDP |
|---|---|
| Connection-oriented | Connectionless |
| Provides reliable ordered byte-stream delivery | Does not provide built-in reliable ordered delivery |
| Uses connection establishment | No TCP-style connection establishment |
| Commonly used by SSH and HTTP/HTTPS | Commonly used by DNS and NTP |

These examples are not exclusive. DNS can use TCP, and HTTP/3 uses QUIC over UDP.

### Understand ports

A port identifies a transport-layer communication endpoint.

For example:

```text
192.168.10.20:443
```

contains:

```text
192.168.10.20
```

as the IP address and:

```text
443
```

as the port number.

Some common associations are:

| Port | Common service |
|---:|---|
| 22/TCP | SSH |
| 53/TCP and UDP | DNS |
| 80/TCP | HTTP |
| 443/TCP | HTTPS |

A port number alone does not prove which application is running.

Detailed port and socket investigation belongs in JUN-051 and JUN-052.

## 10. Follow the Basic Linux Network Communication Path

Now combine the concepts.

Suppose an application on Ubuntu Server A needs to communicate with:

```text
app.example.com
```

A simplified communication sequence is:

```text
APPLICATION
     |
     v
Destination hostname
     |
     v
Name resolution, if required
     |
     v
Destination IP address
     |
     v
Transport protocol
     |
     v
Linux IP networking stack
     |
     v
Routing decision
     |
     v
Outgoing interface
     |
     v
Local link / next hop
     |
     v
Network
     |
     v
Destination system
```

This is a conceptual model, not a claim that every application performs each step in exactly this order or through identical interfaces.

For example, an application may already know the destination IP address and not require a hostname lookup.

### Local versus remote traffic

Consider:

```text
Server A:
192.168.10.20/24
```

Destination 1:

```text
192.168.10.30
```

Destination 2:

```text
192.168.20.30
```

With a conventional directly connected route for `192.168.10.0/24`, the first destination belongs to that connected network.

The second destination requires another applicable route.

A default gateway may provide that route.

### The critical troubleshooting distinction

When communication fails, ask:

```text
WHAT EXACTLY FAILED?
```

Not simply:

```text
IS THE NETWORK DOWN?
```

A failure involving a hostname may occur before the system has obtained the intended destination IP address.

A failure involving an already-known IP address does not require DNS to be the cause.

An application error can also occur after successful network delivery.

The evidence must determine which part of the communication path deserves investigation.

## 11. Build Your Linux Networking Baseline

You will now collect the host's current networking state.

This is the main guided practical exercise.

A networking baseline is a documented representation of the system's configuration and observable state at a particular point in time.

It helps engineers understand the environment before making changes or investigating incidents.

### Task 1 — Identify the host

Run:

```bash
hostname
```

Record the hostname.

Then run:

```bash
hostname -I
```

This can display the host's configured non-loopback IP addresses.

Do not assume the result contains only one address.

### Task 2 — Identify interfaces

Run:

```bash
ip link show
```

Record:

```text
Interface names:

Loopback interface:

Non-loopback interface(s):

Main interface state:

Main interface MTU:
```

### Task 3 — Inspect IPv4 configuration

Run:

```bash
ip -4 addr show
```

Record the relevant IPv4 addresses and prefix lengths.

### Task 4 — Inspect IPv6 configuration

Run:

```bash
ip -6 addr show
```

Record the visible IPv6 addresses.

If no global IPv6 address is configured, document that fact.

### Task 5 — Inspect routing

Run:

```bash
ip route show
```

Record:

```text
IPv4 default route:

Default gateway, if present:

Outgoing interface:

Directly connected IPv4 routes:
```

Then run:

```bash
ip -6 route show
```

Record whether an IPv6 default route exists.

### Task 6 — Inspect resolver configuration

Run:

```bash
cat /etc/resolv.conf
```

Record the visible nameserver information.

Do not assume a local stub address is the upstream resolver.

### Task 7 — Test local name resolution

Run:

```bash
getent hosts localhost
```

Record whether the command returns address information.

### Task 8 — Test an external hostname

Run:

```bash
getent hosts example.com
```

Record the actual result.

If the command does not return an address, document the observation rather than inventing a cause.

### Checkpoint 3 — Compare the evidence

At this stage, you should be able to answer:

1. Which interfaces exist?
2. Which interface appears to provide the main network connection?
3. What IPv4 address is configured?
4. Is IPv6 configured?

## 12. Investigate Common Linux Networking Misinterpretations

Networking incidents are often prolonged because engineers treat one observation as proof of a different condition.

The following examples demonstrate mistakes you should avoid.

### Mistake 1 — The interface exists, so it must be working

Incorrect.

An interface can exist without being administratively enabled or having an operational lower-layer connection.

Inspect:

```bash
ip link show
```

Interpret the actual state.

### Mistake 2 — The server has an IP address, so it has Internet access

Incorrect.

An IP address alone does not establish an applicable route, a working network path, or external connectivity.

### Mistake 3 — Every interface named `eth0` is physical

Incorrect.

Interface names do not universally establish whether an interface represents physical or virtual networking.

### Mistake 4 — MAC addresses and IP addresses are interchangeable

Incorrect.

They operate at different networking layers and serve different purposes.

### Mistake 5 — A default gateway is required for all communication

Incorrect.

Traffic covered by an appropriate directly connected route does not necessarily need to use a default gateway.

### Mistake 6 — A working DNS lookup proves the application is healthy

Incorrect.

DNS resolution and application availability are separate concerns.

### Mistake 7 — A failed hostname lookup proves the network interface is down

Incorrect.

Name-resolution failure does not, by itself, establish interface failure.

### Mistake 8 — IPv4 and IPv6 must always have identical connectivity

Incorrect.

They use different addressing and routing information.

One address family may have usable configuration while the other does not.

### Mistake 9 — Loopback traffic leaves the physical network interface

Incorrect.

Loopback communication is local to the host's networking environment.

### Mistake 10 — The first networking fix should be restarting services

Incorrect.

Restarting networking without evidence can disrupt connectivity and remove useful incident context.

On a remotely administered server, an unnecessary networking change can also disconnect the engineer.

## 13. Controlled Incident — Investigate a Server Without a Default Route

This is a simulated incident.

You will analyze provided evidence rather than deleting your actual default route.

### Scenario

An Ubuntu server hosts an internal application.

Its network configuration is:

```text
Interface:
ens3

IPv4 address:
192.168.10.20/24
```

The application needs to communicate with:

```text
192.168.20.30
```

The engineer reports:

> The server has an IP address, but communication with the remote application is failing.

The following routing evidence was collected:

```text
192.168.10.0/24 dev ens3 proto kernel scope link src 192.168.10.20
```

No other relevant route is present in this simulated routing table.

### Step 1 — Identify the symptom

The server cannot communicate with a destination outside its directly connected `/24` network.

### Step 2 — Identify the impact

The application cannot establish the required communication with the remote system.

### Step 3 — Examine the evidence

The host has:

```text
192.168.10.20/24
```

Its visible route covers:

```text
192.168.10.0/24
```

The required destination is:

```text
192.168.20.30
```

That destination is outside the connected `/24` network.

### Step 4 — Form a hypothesis

The routing table may lack an applicable route toward the destination.

### Step 5 — Test the hypothesis against the scenario

The supplied routing table contains only:

```text
192.168.10.0/24
```

The destination does not match that prefix.

No default or other applicable route is shown.

The evidence supports a missing-route diagnosis for this simulated case.

### Step 6 — Determine the corrective action

The engineer should identify the approved network design and confirm the intended next hop or route.

A route should not be invented merely because communication is failing.

If the architecture requires a default gateway, the approved network configuration should provide the correct gateway.

If a specific route is required instead, that route should be configured through the organization's supported network-management process.

### Step 7 — Recovery verification

After an authorized correction, the engineer should:

1. Reinspect the routing table.
2. Confirm that an applicable route now exists.
3. Verify the route selects the intended interface and next hop.
4. Repeat the original failed communication test using an approved method.
5. Confirm application recovery separately.

### Prevention

A useful operational practice is to preserve a known-good networking baseline and validate required routes during server provisioning.

### Important lesson

Do not change DNS to repair a confirmed routing problem.

Do not change an IP address merely because the destination is remote.

Identify the failed networking responsibility before selecting a corrective action.

## 15. Knowledge Check and Interview Preparation

### Knowledge Check

**1. What is a computer network?**

A collection of devices that exchange information through communication links using agreed protocols.

**2. What is a network host?**

A device participating in a network, such as a server, workstation, or virtual machine.

**3. What is a network interface?**

An endpoint through which the operating system participates in network communication.

**4. What is the Linux loopback interface commonly called?**

`lo`.

**5. What is the common IPv4 loopback address?**

`127.0.0.1`.

**6. What is the IPv6 loopback address?**

`::1`.

**7. What is a MAC address?**

A link-layer address used by technologies such as Ethernet.

**8. What is the difference between a MAC address and an IP address?**

A MAC address participates in relevant link-layer delivery, while an IP address is used for Internet-layer addressing and routing.

**9. How many bits are in IPv4?**

32 bits.

**10. How many bits are in IPv6?**

128 bits.

**11. What does `/24` represent in `192.168.10.20/24`?**

A 24-bit network prefix.

**12. What is a subnet?**

An IP network identified by a prefix.

**13. What is a default gateway?**

A next-hop router commonly used by the default route to forward traffic toward destinations not covered by more-specific applicable routes.

**14. What is a routing table?**

A collection of routing information Linux uses when making packet-forwarding decisions.

**15. What does DNS commonly help applications obtain?**

Address information associated with hostnames, among other DNS record information.

**16. Does successful DNS resolution prove that an application is reachable?**

No.

**17. Which TCP/IP layer contains IPv4 and IPv6?**

The Internet layer.

**18. Which TCP/IP layer contains TCP and UDP?**

The Transport layer.

**19. What is encapsulation?**

The process of carrying higher-layer information within the protocol data units of lower layers.

**20. Why should a Linux administrator inspect networking state before changing configuration?**

To establish evidence, identify the relevant failure, preserve useful incident information, and avoid introducing additional problems.

### Interview Practice

#### 1. Explain the basic components required for Linux network communication.

A Linux system uses network interfaces, IP addressing, routing information, and relevant transport and application protocols. Depending on the destination and how the application identifies it, name resolution may also be required.

#### 2. What is the difference between an IP address and a MAC address?

An IP address is used for Internet-layer communication and routing. A MAC address is used for addressing in link-layer technologies such as Ethernet. They serve different purposes.

#### 3. How would you inspect network interfaces on Ubuntu?

I would start with:

```bash
ip link show
```

This allows me to identify the interfaces and inspect basic link-layer information.

#### 4. How would you inspect configured IP addresses?

I would use:

```bash
ip addr show
```

For separate address-family views:

```bash
ip -4 addr show
```

```bash
ip -6 addr show
```

#### 5. How would you inspect the IPv4 routing table?

I would run:

```bash
ip route show
```

Then identify the default route, directly connected routes, next-hop information, and outgoing interfaces.

#### 6. What is the difference between local and remote network communication?

Communication with a destination covered by an appropriate directly connected route can use the local network. Communication with another network requires another applicable route, potentially through a gateway.

#### 7. A server has a valid IP address but cannot reach another network. What would you investigate?

I would inspect interface state, the configured prefix, the routing table, and the intended network architecture. A valid IP address alone does not establish a usable path toward every destination.

#### 8. What is DNS, and why is it important?

DNS is a distributed naming system. One common use is obtaining IP address information associated with hostnames, allowing applications to use names instead of requiring manually entered addresses.

#### 9. Does a successful DNS lookup mean the remote application is working?

No. DNS resolution provides address information. Routing, transport communication, and application availability require separate verification.

#### 10. Why should you avoid changing network configuration immediately during an incident?

Unnecessary changes can introduce new failures, remove useful evidence, or disconnect remote administration sessions. I would first establish the current state and identify a supported cause.
