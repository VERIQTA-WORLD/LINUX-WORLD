## 1. Mission: The Server Has an IP Address, but Where Will Linux Send the Packet?

In JUN-047, you learned how subnet boundaries determine whether an IPv4 destination belongs to a host's directly connected network.

You also learned why a default gateway is needed in many conventional network designs.

However, a default gateway is only one part of Linux routing.

A production server can have several possible paths:

- A directly connected network.
- A specific route to another subnet.
- A default route.
- Multiple routes with different metrics.
- Routes associated with different interfaces.
- Routes in different routing tables.

When an application attempts to communicate with another endpoint, Linux must determine which route applies to that destination.

This is the foundation of routing.

### Production scenario

Consider an Ubuntu application server with two network interfaces.

```text
Hostname: app-server-01

ens3:
192.168.10.20/24

ens4:
10.50.0.20/24
```

The approved network design requires:

- Internal application traffic to use the appropriate internal route.
- Database traffic for `10.60.0.0/24` to pass through `10.50.0.1`.
- Other destinations without a more specific route to use the default gateway `192.168.10.1`.

The intended routing table is:

```text
default via 192.168.10.1 dev ens3

192.168.10.0/24 dev ens3 proto kernel scope link src 192.168.10.20

10.50.0.0/24 dev ens4 proto kernel scope link src 10.50.0.20

10.60.0.0/24 via 10.50.0.1 dev ens4
```

Now imagine that an engineer removes the specific route to `10.60.0.0/24`.

The server still has:

- Operational interfaces.
- Valid IP addresses.
- Directly connected routes.
- A default gateway.

Nevertheless, database traffic may now follow the default route rather than the intended internal path.

This illustrates a critical production lesson:

**A server can have a valid default gateway and still select an incorrect path for a particular destination.**

Your mission is to understand how Linux represents routes, how route selection works, how to inspect the selected path safely, and how to identify routing discrepancies without making unnecessary changes.

## 2. Understand What Routing Means

Routing is the process of selecting a path for an IP packet toward its destination.

When a Linux application sends IP traffic, the operating system evaluates its networking configuration to determine how that traffic should be handled.

A simplified model is:

```text
                  APPLICATION
                       |
                       v
                DESTINATION IP
                       |
                       v
               LINUX ROUTE LOOKUP
                       |
             +---------+---------+
             |                   |
             v                   v
       LOCAL DELIVERY      FORWARDING PATH
                                 |
                        +--------+--------+
                        |                 |
                        v                 v
                  DIRECT LINK         NEXT HOP
                        |                 |
                        v                 v
                   DESTINATION          ROUTER
```

The selected route can identify:

- The destination network.
- An outgoing interface.
- A next-hop gateway.
- A preferred source address.
- A metric.
- Other routing attributes.

### Routing versus forwarding

These terms are related but should not be treated as identical.

**Routing** concerns path selection and the information used to make that decision.

**Forwarding** concerns moving a packet toward its next destination according to the applicable networking rules.

A Linux host uses routing information when sending its own traffic.

A Linux system configured as a router can also forward traffic received from other systems.

This lab focuses primarily on route selection for traffic originating from a Linux host.

### Routing is not DNS

DNS can resolve a hostname into an address.

Routing determines how traffic is directed toward an IP destination.

For example:

```text
Application requests:
database.example.internal
          |
          v
Name resolution supplies an IP address
          |
          v
10.60.0.30
          |
          v
Linux evaluates its routing configuration
          |
          v
Selected interface / next hop
```

A successful DNS lookup does not guarantee that a valid route exists.

Likewise, a valid route does not guarantee that DNS is working.

## 3. Understand the Linux Routing Table

A routing table contains route entries that Linux can use when making routing decisions.

On a conventional Ubuntu server, the main IPv4 routing table can be inspected with:

```bash
ip -4 route show
```

A representative routing table is:

```text
default via 192.168.10.1 dev ens3 proto dhcp metric 100

192.168.10.0/24 dev ens3 proto kernel scope link src 192.168.10.20 metric 100

10.50.0.0/24 dev ens4 proto kernel scope link src 10.50.0.20

10.60.0.0/24 via 10.50.0.1 dev ens4
```

This is illustrative output. Your actual host may have different routes, interfaces, metrics, and protocol labels.

### Break down the first route

```text
default via 192.168.10.1 dev ens3 proto dhcp metric 100
```

| Field | Meaning |
|---|---|
| `default` | The default destination prefix, equivalent to IPv4 `0.0.0.0/0` |
| `via 192.168.10.1` | The next-hop gateway |
| `dev ens3` | The outgoing interface |
| `proto dhcp` | The route is identified as originating from DHCP |
| `metric 100` | A route preference value used in applicable route selection |

### Break down a connected route

```text
192.168.10.0/24 dev ens3 proto kernel scope link src 192.168.10.20
```

| Field | Meaning |
|---|---|
| `192.168.10.0/24` | Destination network prefix |
| `dev ens3` | Associated outgoing interface |
| `proto kernel` | Route identified as kernel-originated |
| `scope link` | The destination prefix is treated as link-scoped |
| `src 192.168.10.20` | Preferred source address associated with this route |

### Break down a route through a gateway

```text
10.60.0.0/24 via 10.50.0.1 dev ens4
```

Interpretation:

For a destination matching `10.60.0.0/24`, the route directs traffic through next hop `10.50.0.1` using interface `ens4`.

### Important distinction

The destination prefix and the gateway are different fields.

In:

```text
10.60.0.0/24 via 10.50.0.1 dev ens4
```

the destination network is:

```text
10.60.0.0/24
```

The next hop is:

```text
10.50.0.1
```

Do not confuse the address of the next-hop router with the final destination.

## 4. Understand Directly Connected Routes

A directly connected route describes a destination prefix reachable through an associated interface without requiring a separate next-hop router in the route entry.

Consider:

```text
Interface: ens3

IPv4 address: 192.168.10.20/24
```

A conventional Linux configuration commonly includes a connected route similar to:

```text
192.168.10.0/24 dev ens3 proto kernel scope link src 192.168.10.20
```

### What does this mean?

The route identifies `192.168.10.0/24` as a destination prefix associated with `ens3`.

Consider a packet addressed to:

```text
192.168.10.50
```

The destination belongs to:

```text
192.168.10.0/24
```

The connected route can therefore provide an applicable path.

Conceptually:

```text
            LINUX SERVER
           192.168.10.20
                 |
                 |
                ens3
                 |
                 v
          LOCAL NETWORK
         192.168.10.0/24
                 |
                 v
           DESTINATION
          192.168.10.50
```

### Does directly connected mean guaranteed reachability?

No.

A connected route indicates a routing decision.

It does not prove that:

- The destination host exists.
- The destination is operational.
- Neighbor discovery succeeds.
- Layer-2 connectivity works.
- A firewall permits communication.
- The intended application is listening.

### Practical Exercise 1 — Identify connected routes

Run:

```bash
ip -4 route show
```

Look for entries containing:

```text
scope link
```

Record:

```text
Connected destination prefix:

Outgoing interface:

Preferred source address, if displayed:

Route metric, if displayed:
```

If your host has multiple interfaces, you may observe multiple connected routes.

Do not assume that every interface necessarily has an IPv4 connected route.

## 5. Understand Static Routes

A static route is a route intentionally configured through an administrative or infrastructure-management process.

Static routes are useful when a destination network requires a particular next hop.

Consider this network:

```text
                  APPLICATION SERVER
                    192.168.10.20
                     10.50.0.20
                          |
                          |
                         ens4
                          |
                          v
                   10.50.0.0/24
                          |
                          v
                    INTERNAL ROUTER
                      10.50.0.1
                          |
                          v
                    DATABASE SUBNET
                     10.60.0.0/24
                          |
                          v
                    DATABASE SERVER
                      10.60.0.30
```

A specific route might be represented as:

```text
10.60.0.0/24 via 10.50.0.1 dev ens4
```

### Why use a specific route?

The host may have a default gateway on another interface.

Without the specific route, traffic toward `10.60.0.0/24` might follow a less specific route, depending on the remaining routing configuration.

The specific route expresses the intended path to the database subnet.

### Static routes versus connected routes

| Connected route | Static route |
|---|---|
| Commonly associated with configured interface addressing | Intentionally supplied through configuration |
| Can identify an on-link prefix | Can direct traffic toward a particular destination or next hop |
| Often displays `proto kernel` | May display `proto static`, `proto boot`, or another origin depending on configuration |
| Usually does not require a separate `via` gateway for the directly connected prefix | May include a `via` next-hop gateway |

Do not rely exclusively on the displayed `proto` label to determine the complete history of a route.

The label is routing metadata, not a full audit trail.

### Important safety note

Static routes should normally be managed through the environment's approved persistent configuration mechanism.

For Ubuntu Server, this may involve Netplan or infrastructure automation, depending on how the host is deployed.

Adding an ad hoc runtime route without understanding persistent configuration can produce a temporary fix that disappears after network reconfiguration or reboot.

## 6. Understand Default Routes

A default route provides a path for destinations when no more specific applicable route is selected.

In IPv4, the default destination prefix is:

```text
0.0.0.0/0
```

Linux commonly displays it as:

```text
default
```

Example:

```text
default via 192.168.10.1 dev ens3
```

### Why `/0`?

An IPv4 address contains 32 bits.

A `/0` prefix specifies zero leading network bits.

Therefore, it can match every IPv4 destination.

However, matching every destination does not mean the default route always wins.

Linux normally prefers a more specific applicable destination prefix.

### Example

Consider:

```text
default via 192.168.10.1 dev ens3

10.60.0.0/24 via 10.50.0.1 dev ens4
```

For destination:

```text
10.60.0.30
```

both entries match at the destination-prefix level.

However:

```text
10.60.0.0/24
```

is more specific than:

```text
0.0.0.0/0
```

Therefore, the `/24` route takes precedence in conventional longest-prefix selection.

### A default route is not mandatory for every host

Some hosts are intentionally isolated.

They may only need communication with directly connected networks or explicitly defined destinations.

A missing default route is a configuration problem only when the approved design requires one.

## 7. Understand Longest-Prefix Matching

Longest-prefix matching is one of the most important concepts in IP routing.

When multiple destination prefixes match an address, the most specific applicable prefix is normally selected.

Consider the following routing table:

```text
default via 192.168.10.1 dev ens3

10.0.0.0/8 via 192.168.10.2 dev ens3

10.60.0.0/16 via 192.168.10.3 dev ens3

10.60.5.0/24 via 192.168.10.4 dev ens3
```

Now consider the destination:

```text
10.60.5.20
```

Which routes match?

| Route | Matches destination? |
|---|---|
| `0.0.0.0/0` | Yes |
| `10.0.0.0/8` | Yes |
| `10.60.0.0/16` | Yes |
| `10.60.5.0/24` | Yes |

The longest matching prefix is:

```text
10.60.5.0/24
```

Therefore, in this simplified example, the selected route is:

```text
10.60.5.0/24 via 192.168.10.4 dev ens3
```

### Visual explanation

```text
DESTINATION: 10.60.5.20
          |
          v
MATCHING PREFIXES
          |
          +-- /0
          |
          +-- /8
          |
          +-- /16
          |
          +-- /24
                |
                v
       MOST SPECIFIC MATCH
                |
                v
             /24 ROUTE
```

### Practical Exercise 2 — Select the route

Use the same routing table.

Determine the destination-prefix match for each address.

| Destination | Selected prefix |
|---|---|
| `10.60.5.20` | `10.60.5.0/24` |
| `10.60.8.20` | `10.60.0.0/16` |
| `10.80.1.20` | `10.0.0.0/8` |
| `198.51.100.20` | Default `/0` |

### Why this matters in production

An engineer might observe a default gateway and assume that all remote traffic follows it.

However, a specific route can redirect a subset of traffic through another interface or gateway.

This is why routing investigations must consider the destination, not merely the presence of a default route.

## 8. Understand Route Metrics

A route metric is a value that can influence preference among otherwise comparable route candidates.

In conventional Linux routing configurations, a lower metric is commonly preferred when applicable routes have the same destination-prefix specificity and other relevant selection conditions are equal.

Consider:

```text
default via 192.168.10.1 dev ens3 metric 100

default via 10.50.0.1 dev ens4 metric 200
```

Both entries represent the IPv4 default destination prefix.

The first route has metric:

```text
100
```

The second route has metric:

```text
200
```

Under an otherwise comparable conventional configuration, the lower-metric route is preferred.

### Critical distinction

A lower metric does not automatically override a more specific destination prefix.

Consider:

```text
default via 192.168.10.1 dev ens3 metric 50

10.60.0.0/24 via 10.50.0.1 dev ens4 metric 500
```

For destination:

```text
10.60.0.30
```

the `/24` route is more specific than the default `/0` route.

The metric does not make the default route more specific.

### Do not confuse metrics with health checks

A route with a low metric is not automatically healthy.

Linux may select a route whose next hop is unavailable.

Route preference and real-world connectivity are separate questions.

### Practical Exercise 3 — Compare route metrics

Run:

```bash
ip -4 route show
```

Look for:

```text
metric
```

Record any displayed values.

If your host does not display multiple routes with metrics, use the supplied examples for this exercise.

Do not add additional default routes merely to experiment with route preference.

## 9. Understand Source Address Selection

A route lookup can provide more information than the outgoing interface.

It may also identify a preferred source IP address.

Consider:

```text
192.168.10.0/24 dev ens3 proto kernel scope link src 192.168.10.20
```

The `src` field identifies a preferred source address associated with the route.

### Why source addresses matter

A Linux server may have multiple interfaces or multiple IP addresses.

For example:

```text
ens3:
192.168.10.20/24

ens4:
10.50.0.20/24
```

When sending traffic, Linux needs to determine an appropriate source address.

A route lookup can help you investigate that decision.

### Example

```bash
ip -4 route get 10.60.0.30
```

Representative output:

```text
10.60.0.30 via 10.50.0.1 dev ens4 src 10.50.0.20 uid 1000
    cache
```

This indicates:

```text
Destination:
10.60.0.30

Next hop:
10.50.0.1

Outgoing interface:
ens4

Selected source address:
10.50.0.20
```

### Important limitation

The source address displayed by a route lookup represents the result of that particular lookup context.

Applications can bind specific source addresses or interfaces, and advanced routing policies can affect route selection.

Do not assume one route lookup describes every possible application communication pattern on a complex host.

## 11. Hands-On: Investigate Route Selection with `ip route get`

The `ip route get` command asks Linux to resolve a route for a specified destination.

It is particularly useful when you need to determine:

- Which interface would be selected.
- Which next hop would be used.
- Which source address would be selected.
- Whether a usable route is available under the lookup conditions.

It does not send an application packet to the destination.

### Task 7 — Inspect a local destination

First identify your actual IPv4 subnet.

For illustration, assume:

```text
192.168.10.20/24
```

```text

```

```bash

```

Representative output:

```text
192.168.10.50 dev ens3 src 192.168.10.20 uid 1000
    cache
```

For meaningful local-route investigation, replace the example with an appropriate destination inside your configured subnet.

Run:


```text

    cache
```


|---|---|---|---|---|

## 12. Understand IPv6 Routing Basics

IPv6 uses routing concepts similar to IPv4, but its address format and some operational mechanisms differ.

An IPv6 default route is represented by:

```text
::/0
```

Linux may display it as:

```text
default
```

Consider:

```text
default via fe80::1 dev ens3
```

This identifies an IPv6 default route using a link-local next-hop address on interface `ens3`.

### Why the interface matters

IPv6 link-local addresses are scoped to a link.

Therefore, the associated outgoing interface is important when interpreting a link-local gateway.

### IPv6 connected route example

```text
2001:db8:10:20::/64 dev ens3 proto kernel metric 256
```

This identifies a connected IPv6 prefix associated with `ens3`.

### Practical Task 11 — Inspect IPv6 routes

Run:

```bash
ip -6 route show
```

Then:

```bash
ip -6 route show table local
```

Look for:

- Connected IPv6 prefixes.
- Link-local prefixes.
- Local IPv6 address routes.
- An IPv6 default route, if present.

### Practical Task 12 — Inspect IPv6 loopback routing

Run:

```bash
ip -6 route get ::1
```

Record the result.

### Important distinction

A host may have IPv4 routing without a globally usable IPv6 configuration.

Do not treat the absence of an IPv6 default route as proof that IPv4 routing is broken.

The expected configuration depends on the approved network design.

## 13. Understand Routing Tables and Policy Rules

So far, you have inspected the main routing table.

However, Linux supports multiple routing tables and routing policy rules.

A conventional Linux environment includes important tables such as:

| Table | Common purpose |
|---|---|
| `local` | Local address and related special routes |
| `main` | General routing information |
| `default` | Additional reserved routing table |
| Custom tables | Environment-specific routing policies |

### Inspect routing rules

Run:

```bash
ip -4 rule show
```

Representative output from a simple host:

```text
0:      from all lookup local
32766:  from all lookup main
32767:  from all lookup default
```

This illustrates the routing policy database.

### Why does this matter?

On a conventional host, most ordinary routing investigation begins with the main table.

However, a production system may use rules that select different tables based on conditions such as source addressing or other supported selectors.

Examples include:

- Multi-homed servers.
- VPN configurations.
- Specialized infrastructure appliances.
- Advanced cloud-networking environments.

### Practical Task 13 — Inspect routing rules

Run:

```bash
ip -4 rule show
```

Then:

```bash
ip -6 rule show
```

Record whether the output resembles the conventional rule arrangement or includes additional entries.

Do not modify any rules.

### Scope boundary

You are not expected to configure policy routing in JUN-048.

Your responsibility is to recognize that a complex Linux host may have routing behavior that cannot be explained by looking at the main table alone.

## 14. Recognize Special Route Types

Not every route forwards traffic toward a destination.

Linux supports route types that can intentionally reject or discard traffic.

Three useful types to recognize are:

### Unreachable route

An unreachable route indicates that matching destinations are unreachable.

Illustrative configuration:

```text
unreachable 203.0.113.0/24
```

### Blackhole route

A blackhole route silently discards matching traffic.

Illustrative configuration:

```text
blackhole 203.0.113.0/24
```

### Prohibit route

A prohibit route rejects matching traffic with an administratively prohibited indication.

Illustrative configuration:

```text
prohibit 203.0.113.0/24
```

These route types can be used intentionally in network designs.

Do not automatically classify every special route as an accidental misconfiguration.

### Practical Task 14 — Inspect for special routes

Run:

```bash
ip -4 route show table all
```

Look for entries containing:

```text
unreachable

blackhole

prohibit
```

Your host may not contain any of them.

That is acceptable.

### Engineering caution

Do not create blackhole or prohibit routes on your active server simply to observe their effects.

An incorrectly targeted special route can interrupt legitimate communication.

## 15. Troubleshoot Common Linux Routing Misinterpretations

Routing problems often become harder when engineers confuse a configured route with verified connectivity.

The following mistakes are worth recognizing early.

### Mistake 1 — A default gateway means all traffic uses it

Incorrect.

More specific applicable routes normally take precedence.

### Mistake 2 — A lower metric always wins

Incorrect.

Prefix specificity and the applicable routing context matter.

### Mistake 3 — An interface is UP, so routing must work

Incorrect.

Interface state and route selection are different.

### Mistake 4 — A valid IP address guarantees a default route

Incorrect.

Addressing and routing are separate configuration components.

### Mistake 5 — A successful `ip route get` proves the destination is reachable

Incorrect.

It reports a routing decision, not a successful end-to-end communication test.

### Mistake 6 — The gateway and destination are the same address

Incorrect.

The gateway is a next hop; the final destination can be another endpoint.

### Mistake 7 — Every route must have a `via` field

Incorrect.

Directly connected routes commonly identify an outgoing interface without a separate next-hop gateway.

### Mistake 8 — Every host must have a default route

Incorrect.

Some isolated hosts intentionally use only connected or specific routes.

### Mistake 9 — The main routing table explains every possible routing decision

Incorrect.

Linux supports additional routing tables and policy rules.

### Mistake 10 — Restarting networking is a safe first troubleshooting step

Incorrect.

Restarting networking on a remote server can interrupt administration and application traffic.

### Mistake 11 — A route with the correct destination prefix must be the intended route

Not necessarily.

Its next hop, interface, metric, and surrounding policy must also be considered.

### Mistake 12 — An incorrect route should immediately be replaced manually

Not necessarily.

First determine how the route is managed and what the approved configuration requires.

A manual runtime change can conflict with persistent configuration or be lost during a subsequent network-management event.

## 16. Controlled Failure Lab — The Missing Specific Route

This investigation uses a simulated production failure.

You will not modify your actual routing table.

### Scenario

An Ubuntu application server has two interfaces:

```text
ens3:
192.168.10.20/24

ens4:
10.50.0.20/24
```

The approved routing design requires:

```text
                                       10.60.0.0/24
                                            |
                                            v
                                       DB SERVER
                                       10.60.0.30
```

### Phase 1 — Establish the expected routing table

Before the incident, the server had:

```text
default via 192.168.10.1 dev ens3

192.168.10.0/24 dev ens3 proto kernel scope link src 192.168.10.20

10.50.0.0/24 dev ens4 proto kernel scope link src 10.50.0.20

10.60.0.0/24 via 10.50.0.1 dev ens4
```

For destination:

```text
10.60.0.30
```

the specific `/24` route should be selected.

### Phase 2 — Simulated failure

During a configuration deployment, the specific database route is accidentally omitted.

The current routing table becomes:

```text
default via 192.168.10.1 dev ens3

192.168.10.0/24 dev ens3 proto kernel scope link src 192.168.10.20

10.50.0.0/24 dev ens4 proto kernel scope link src 10.50.0.20
```

The interfaces remain operational.

The addresses are unchanged.

The default route is still present.

### Phase 3 — Observe the symptom

The application can no longer communicate with the database using the intended internal path.

### Phase 4 — Investigate the evidence

**Evidence A — Interface state**

Both interfaces report operational states.

**Evidence B — Address configuration**

The expected addresses remain present.

**Evidence C — Routing table**

The specific route:

```text
10.60.0.0/24 via 10.50.0.1 dev ens4
```

is missing.

**Evidence D — Route lookup**

The engineer runs:

```bash
ip -4 route get 10.60.0.30
```

In the simulated incident, the result is:

```text
10.60.0.30 via 192.168.10.1 dev ens3 src 192.168.10.20
```

This shows that Linux selected the remaining default route rather than the intended internal path.

### Phase 5 — Form a hypothesis

The database communication problem may be caused by the omission of the specific route to `10.60.0.0/24`.

### Phase 6 — Test the hypothesis

The engineer compares the current routing table with the approved routing baseline.

The baseline requires:

```text
10.60.0.0/24 via 10.50.0.1 dev ens4
```

The current configuration does not contain that route.

The deployment change record confirms that the route was accidentally removed from the managed network configuration.

### Phase 7 — Identify the root cause

The confirmed root cause is the omission of the specific database-subnet route during the configuration deployment.

The presence of a default route allowed Linux to select an alternative path, but that path did not satisfy the approved internal network design.

### Phase 8 — Determine the corrective action

An authorized engineer restores the approved specific route through the supported persistent configuration process.

The correction must be checked against:

- Existing interface addresses.
- Gateway reachability.
- Other specific routes.
- Default routes.
- Routing metrics.
- Any applicable routing policy.

Do not assume that adding a route manually at runtime is the correct permanent repair.

### Phase 9 — Verify recovery

After the approved correction, the routing table should again contain:

```text
10.60.0.0/24 via 10.50.0.1 dev ens4
```

The engineer repeats:

```bash
ip -4 route get 10.60.0.30
```

Representative expected result:

```text
10.60.0.30 via 10.50.0.1 dev ens4 src 10.50.0.20
```

This confirms the intended route selection.

The original application-to-database communication test must also be repeated.

### Phase 10 — Prevention

Recommended controls include:

- Version-controlled network configuration.
- Route-baseline validation.
- Deployment review.
- Automated post-deployment route checks.
- Application-path verification.
- Monitoring for unexpected routing changes.
- Documented rollback procedures.

### Incident conclusion

A suitable engineering conclusion is:

> The application server retained operational interfaces, valid addresses, and a default route. However, the specific route to the database subnet was absent. Route inspection showed that traffic toward the database was being directed through the default gateway rather than the approved internal gateway. Configuration records confirmed that the specific route had been omitted during deployment. The managed configuration was corrected, and route selection and application connectivity were verified afterward.

## 19. Knowledge Check and Interview Preparation

### Knowledge Check

**1. What is routing?**

The process of selecting a path for IP traffic toward its destination.

**2. What command displays the main IPv4 routing table?**

```bash
ip -4 route show
```

**3. What does `default` represent in IPv4 routing?**

The destination prefix `0.0.0.0/0`.

**4. What does `via` identify in a route?**

A next-hop gateway.

**5. What does `dev` identify?**

The associated outgoing interface.

**6. What does `src` commonly represent in a route?**

A preferred source address associated with the route.

**7. What is a directly connected route?**

A route identifying a destination prefix reachable through an associated interface without a separate next-hop gateway in the route entry.

**8. What is a static route?**

A route intentionally configured through an administrative or infrastructure-management process.

**9. What is longest-prefix matching?**

The selection principle that normally prefers the most specific applicable destination prefix among matching routes.

**10. Does a lower metric automatically override a more specific prefix?**

No.

**11. Does every route contain a gateway?**

No. Directly connected routes commonly omit a separate `via` next hop.

**12. What command investigates the selected route to an IPv4 destination?**

```bash
ip -4 route get DESTINATION
```

**13. Does a successful route lookup prove that a remote application is reachable?**

No.

**14. What IPv6 prefix represents the default route?**

`::/0`.

**15. Can an IPv6 default gateway use a link-local address?**

Yes.

**16. What command displays IPv4 routing-policy rules?**

```bash
ip -4 rule show
```

**17. What is a blackhole route?**

A route that silently discards matching traffic.

**18. Why should an engineer avoid flushing the routing table on a remote server?**

It can interrupt active connectivity and disconnect remote administration.

**19. Can a server have a valid default route but still use the wrong path for a specific destination?**

Yes.

**20. What should be verified after an authorized routing correction?**

The expected route is present, the destination lookup selects the intended path, and the original communication test succeeds.

### Interview Practice

#### 1. How does Linux decide which route to use?

Linux evaluates the applicable routing policy and route entries for the destination. In conventional routing, the most specific matching destination prefix normally takes precedence. Other attributes, including metrics, can influence selection among otherwise comparable candidates.

#### 2. What is the difference between a connected route and a static route?

A connected route is commonly associated with an interface's configured network prefix. A static route is intentionally configured to direct traffic toward a specified destination, interface, or next hop.

#### 3. What is the purpose of a default route?

It supplies a route for destinations not covered by a more specific selected route.

#### 4. How do you inspect routing on Ubuntu?

I begin with:

```bash
ip -4 route show
```

For a specific destination, I use:

```bash
ip -4 route get DESTINATION
```

I also inspect addressing and routing rules when necessary.

#### 5. What is longest-prefix matching?

It is the principle of selecting the most specific applicable destination prefix. For example, a matching `/24` route normally takes precedence over a matching `/16` or `/0` route.

#### 6. What is the difference between a route metric and a prefix length?

A prefix length defines the specificity of a destination network. A metric is a route preference value used in applicable route selection. A lower metric does not automatically override a more specific destination prefix.

#### 7. A server has two interfaces and sends traffic through the wrong gateway. What would you investigate?

I would inspect interface addresses, the main routing table, specific destination routes, route metrics, routing-policy rules, and the result of `ip route get` for the affected destination. I would compare the selected path with the approved design before making changes.

#### 8. Why is `ip route get` useful during an incident?

It reports the route Linux resolves for a destination under the lookup conditions, including information such as the selected interface, next hop, and source address. It helps distinguish route-selection problems from later connectivity failures.
