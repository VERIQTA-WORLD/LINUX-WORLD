## 1. Your Engineering Mission

A Linux server has a valid IP address, an active network interface, a working route, and functioning DNS resolution.

An application is expected to accept connections on TCP port `8080`.

However, users report that they cannot connect.

An engineer checks the server's IP address and concludes:

> The IP configuration is correct, so the network should be working.

That conclusion is incomplete.

An IP address identifies a network endpoint, but applications also use transport-layer ports and sockets to communicate.

A server can have perfectly valid network addressing while no application is listening on the required port.

Consider this example:

```text
Client
198.51.100.25
     |
     | TCP connection attempt
     | Destination: 192.0.2.20:8080
     v
Linux Server
192.0.2.20
     |
     v
Is a suitable TCP socket listening
on the destination address and port?
     |
  +--+--+
  |     |
 YES    NO
  |     |
  v     v
Connection may     No matching listener
proceed            is available
```

Even when a listening socket exists, successful remote connectivity is not guaranteed. Routing, firewall rules, application behavior, and other network conditions still matter.

Your mission is to investigate how Linux applications use ports and sockets, distinguish TCP from UDP, understand socket binding, and identify the evidence required before concluding that a service is available.

You will inspect your existing Linux environment without modifying its networking configuration.

### Learning objectives

By completing this lab, you will be able to:

- Explain the difference between an IP address and a port.
- Understand what a network socket represents.
- Identify the basic differences between TCP and UDP.
- Recognize common service port numbers.
- Understand the three IANA port-number ranges.
- Explain how applications bind sockets to local addresses and ports.
- Distinguish loopback, specific-address, and wildcard bindings.
- Understand listening and established TCP sockets.
- Identify local and peer endpoints.
- Recognize IPv4 and IPv6 socket notation.
- Understand ephemeral client ports.
- Perform basic socket observations using `ss`.
- Explain why a listening socket does not prove external reachability.
- Produce an evidence-based socket inventory.

**Lab boundary:** JUN-051 establishes the concepts of ports, sockets, endpoints, and binding. JUN-052 will investigate the `ss` utility in greater operational depth, including filtering, socket states, process associations, and targeted socket investigations.

## 2. Understand IP Addresses and Ports

An IP address and a port serve different purposes.

Consider:

```text
192.0.2.20:443
```

This represents two separate pieces of information:

```text
192.0.2.20  → IP address

443         → Port number
```

An IP address is used for identifying an IP endpoint and forwarding traffic through a network.

A transport-layer port helps identify the communication endpoint used by an application or service.

A useful conceptual model is:

```text
NETWORK PACKET
      |
      v
Destination IP address
      |
      v
Linux host
      |
      v
Transport protocol + destination port
      |
      v
Matching communication endpoint
```

Suppose a server provides several services using the same IP address.

It might have these endpoints:

| Endpoint | Conventional service |
|---|---|
| `192.0.2.20:22/TCP` | SSH |
| `192.0.2.20:80/TCP` | HTTP |
| `192.0.2.20:443/TCP` | HTTPS |
| `192.0.2.20:53/UDP` | DNS |

Notice that the IP address remains the same.

The protocol and port distinguish the transport endpoints.

### Important distinction

A port number alone does not uniquely identify a network communication endpoint.

For example:

```text
192.0.2.20:53/TCP
```

and:

```text
192.0.2.20:53/UDP
```

are different transport endpoints.

TCP and UDP have separate port-number spaces.

A host can legitimately use the same numeric port for both protocols.

2. What does a transport-layer port identify?

4. Are TCP port 53 and UDP port 53 identical endpoints?

## 3. Understand Port Numbers and Their Ranges

TCP and UDP port numbers are 16-bit unsigned values.

Their possible numeric range is:

```text
0–65535
```

IANA divides this space into three categories.

| Range | Classification | General purpose |
|---|---|---|
| 0–1023 | System / Well-Known Ports | Common standardized services |
| 1024–49151 | User / Registered Ports | Registered application and service assignments |
| 49152–65535 | Dynamic / Private Ports | Dynamic or private use |

These are allocation categories, not a guarantee of how every Linux application chooses its ports.

### Well-known ports

Examples include:

| Port | Protocol | Common association |
|---:|---|---|
| 22 | TCP | SSH |
| 25 | TCP | SMTP |
| 53 | TCP/UDP | DNS |
| 80 | TCP | HTTP |
| 123 | UDP | NTP |
| 443 | TCP | HTTPS |

These are conventional associations.

They do not prove that a particular application is running.

An application may be configured to listen on a nonstandard port.

For example, a development web server might use:

```text
127.0.0.1:8080
```

instead of port `80`.

### Registered ports

Ports between `1024` and `49151` include assignments for many application protocols.

A registered assignment does not automatically mean that the assigned application is running whenever you observe that number.

### Dynamic and ephemeral ports

When a client initiates a network connection, the operating system commonly selects a temporary source port.

This is often called an *ephemeral port*.

Consider:

```text
Client:
198.51.100.25:52744

Server:
192.0.2.20:443
```

The client uses temporary local port `52744`.

The server uses destination port `443`.

A simplified connection looks like:

```text
CLIENT                              SERVER

198.51.100.25:52744  ---------->  192.0.2.20:443
       |                                   |
 Temporary source port             Service port
```

Linux's actual automatic local-port allocation range is configurable and should not be assumed to equal the entire IANA dynamic/private range.

You can inspect the current IPv4 automatic local-port allocation range using:

```bash
cat /proc/sys/net/ipv4/ip_local_port_range
```

**Representative output:**

```text
32768 60999
```

Your system may differ.

This command is read-only.

### Engineering takeaway

Do not assume that a high-numbered port always identifies a server application.

It may be a temporary client-side port.

## 4. Understand TCP, UDP, and Network Sockets

A socket is an operating-system communication endpoint.

Applications use sockets to send and receive information.

For this lab, focus on Internet-domain sockets associated with TCP and UDP.

### TCP sockets

TCP is connection-oriented.

A TCP server typically creates a socket, binds it to an address and port, and places it into a listening state.

Conceptually:

```text
APPLICATION
     |
     v
Create TCP socket
     |
     v
Bind to local address and port
     |
     v
Listen for incoming connections
     |
     v
Accept a client connection
     |
     v
Communicate through an
established connection
```

For example:

```text
TCP
Local address: 192.0.2.20
Local port:    443
State:         LISTEN
```

A listening socket and an established connection socket serve different roles.

The listening socket waits for incoming connection attempts.

An accepted connection has its own connection context.

### UDP sockets

UDP is connectionless at the transport-protocol level.

A UDP application can bind a socket to a local address and port and receive datagrams without performing TCP's connection establishment process.

Conceptually:

```text
APPLICATION
     |
     v
Create UDP socket
     |
     v
Bind to local address and port
     |
     v
Send or receive datagrams
```

UDP sockets do not use TCP's `LISTEN` and `ESTABLISHED` state model.

An application can also connect a UDP socket at the socket API level to establish a default peer and filter received traffic, but that does not turn UDP into TCP.

### Comparison

| Characteristic | TCP | UDP |
|---|---|---|
| Transport type | Connection-oriented | Connectionless |
| Connection establishment | Yes | No TCP-style handshake |
| Ordered byte-stream delivery | Yes | No |
| Transport retransmission | Yes | No built-in retransmission |
| Typical server inspection | Listening and connection states | Bound socket information |
| Example use | SSH, HTTP/HTTPS | DNS, NTP |

DNS can also use TCP; HTTPS can use UDP through QUIC. The examples above are common associations, not exclusive protocol restrictions.

## 5. Learn How Socket Binding Works

Binding associates a socket with a local address and, for Internet transport sockets, typically a port.

The address selected during binding determines which local destination addresses the socket can match.

This is one of the most important concepts in the lab.

Consider three different TCP listeners:

```text
127.0.0.1:8080

192.0.2.20:8080

0.0.0.0:8080
```

They are not equivalent.

### Binding to loopback

Consider:

```text
127.0.0.1:8080
```

This socket is bound to IPv4 loopback.

It accepts applicable connections addressed to that local loopback endpoint.

Conceptually:

```text
LINUX SERVER
+--------------------------------+
|                                |
|  Local application             |
|         |                      |
|         v                      |
|  127.0.0.1:8080                |
|                                |
+--------------------------------+

Remote clients cannot directly
address this loopback-only listener
through the server's external IP.
```

Loopback binding is common for internal application components.

Examples include local development servers, backend services behind reverse proxies, and administrative interfaces.

A loopback-only binding is not automatically an error.

It may be an intentional security decision.

### Binding to a specific IP address

Consider:

```text
192.0.2.20:8080
```

The socket is bound to that particular local IPv4 address.

If the server has several IPv4 addresses, this binding is not equivalent to listening on all of them.

### Binding to the IPv4 wildcard address

Consider:

```text
0.0.0.0:8080
```

For a listening IPv4 socket, `0.0.0.0` represents a wildcard binding.

It allows the socket to match applicable traffic addressed to the host's local IPv4 addresses rather than restricting it to one specified IPv4 address.

However:

**A wildcard listener does not prove that the service is reachable from another machine or from the public Internet.**

Remote access can still be affected by:

- Routing.
- Host firewall rules.
- Cloud security groups.
- Network access-control lists.
- NAT.
- Upstream filtering.
- Application behavior.

### Binding comparison

| Local binding | Meaning |
|---|---|
| `127.0.0.1:8080` | IPv4 loopback |
| `192.0.2.20:8080` | Specific local IPv4 address |
| `0.0.0.0:8080` | IPv4 wildcard |
| `[::1]:8080` | IPv6 loopback |
| `[::]:8080` | IPv6 wildcard |

An IPv6 wildcard listener does not automatically guarantee IPv4 acceptance. Dual-stack behavior depends on the socket and system configuration.

## 6. Inspect the Host's Existing Network Sockets

You will now connect the concepts to your actual Ubuntu environment.

The `ss` utility displays socket information.

This lab introduces only the basic inspection commands needed to understand socket endpoints.

More detailed filtering and socket-state investigations are reserved for JUN-052.

### Step 1 — Establish the host's addresses

Run:

```bash
ip -4 addr
```

Then:

```bash

```

Identify:

- IPv4 loopback.
- IPv6 loopback, if present.
- Non-loopback interface addresses.
- Any additional configured addresses.

**Verification:** Record the actual addresses rather than copying examples from this lab.

### Step 2 — Inspect listening TCP sockets

Run:

```bash
ss -lnt
```

The options mean:

| Option | Purpose |
|---|---|
| `-l` | Display listening sockets |
| `-n` | Display numeric addresses and ports |
| `-t` | Display TCP sockets |

**Representative output — illustrative only:**

```text
State   Recv-Q Send-Q Local Address:Port Peer Address:Port
LISTEN  0      4096   127.0.0.53:53      0.0.0.0:*
LISTEN  0      128    0.0.0.0:22         0.0.0.0:*
```

Your output may contain different ports, addresses, and queue values.

Do not change the host to reproduce this example.

For now, focus on:

```text
State
Local Address:Port
Peer Address:Port
```

The queue columns will be investigated in JUN-052.

### Step 3 — Identify the bind addresses

For each listening TCP socket, classify its local address.

Example:

```text
127.0.0.53:53
```

This is an IPv4 loopback address.

Example:

```text
0.0.0.0:22
```

This is an IPv4 wildcard listener.

Example:

```text
[::1]:631
```

This is an IPv6 loopback listener.

Do not interpret the peer wildcard shown on a TCP listening row as an established remote connection. A listening socket is waiting for connections and does not represent one specific connected peer.

## 7. Inspect UDP Sockets and Existing TCP Connections

Now compare the different types of socket information.

### Step 1 — Inspect UDP sockets

Run:

```bash
ss -lnu
```

The `-u` option selects UDP.

**Representative output:**

```text
State  Recv-Q Send-Q Local Address:Port Peer Address:Port
UNCONN 0      0      127.0.0.53:53      0.0.0.0:*
```

Your output may differ.

Notice that UDP does not use the TCP `LISTEN` state.

Record the local address and port.

### Step 2 — Compare TCP and UDP

Run:

```bash
ss -lnt
```

Then:

```bash
ss -lnu
```

Look for any numeric port that appears under both protocols.

If the same number appears, remember that TCP and UDP represent different transport endpoints.

### Step 3 — Inspect non-listening TCP sockets

Run:

```bash
ss -nt
```

If established connections exist, you may encounter output resembling:

```text
State Local Address:Port     Peer Address:Port
ESTAB 192.0.2.20:22          198.51.100.25:52744
```

This is representative output, not a prediction about your host.

Interpret it as:

```text
Local endpoint:
192.0.2.20:22

Peer endpoint:
198.51.100.25:52744

TCP state:
ESTAB
```

`ESTAB` indicates an established TCP connection.

If no established connections are visible, record that fact.

Do not generate unnecessary traffic merely to populate the output.

### Important security note

Socket information can reveal internal addresses, listening services, and active communication endpoints.

Do not publish raw socket inventories from production systems without reviewing them for sensitive infrastructure information.

## 8. Understand Why a Listening Port Does Not Prove Connectivity

Consider a server expected to provide an application on TCP port `8080`.

An engineer runs:

```bash
ss -lnt
```

and sees:

```text
LISTEN 0 128 127.0.0.1:8080 0.0.0.0:*
```

The engineer reports:

> Port 8080 is open, so users should be able to connect remotely.

That conclusion ignores the bind address.

The socket is listening only on IPv4 loopback.

A more accurate report would be:

> A TCP socket is listening on `127.0.0.1:8080`. The observed binding does not provide a listener on the server's non-loopback IPv4 address.

Now consider:

```text
LISTEN 0 128 0.0.0.0:8080 0.0.0.0:*
```

This indicates an IPv4 wildcard listener.

It still does not prove external connectivity.

### Understand the complete communication path

```text
REMOTE CLIENT
      |
      v
Destination IP and port
      |
      v
Network routing
      |
      v
Network security controls
      |
      v
Linux host
      |
      v
Matching socket
      |
      v
Application
```

A failure anywhere along the relevant path can prevent successful communication.

Socket inspection establishes local socket state.

It does not replace network-path or application testing.

### Real-world example

An internal API is designed to run behind a reverse proxy.

Its configuration intentionally binds it to:

```text
127.0.0.1:8080
```

The reverse proxy accepts external connections and forwards appropriate requests to the local API.

Changing the API to:

```text
0.0.0.0:8080
```

without understanding the architecture could unnecessarily expand its exposure.

**Production principle:** Do not change a service's bind address simply because it is not externally reachable. First establish whether external access is part of the intended design.

## 9. Controlled Failure Investigation — The Missing Listener

This section uses a simulated incident.

You will break an incorrect engineering assumption rather than deliberately disrupting your Linux machine.

### Incident scenario

A development team deploys an application.

The expected endpoint is:

```text
192.0.2.20:8080/TCP
```

The deployment pipeline reports success.

However, users cannot connect.

An engineer captures this output:

```text
State   Local Address:Port
LISTEN  127.0.0.1:8080
LISTEN  0.0.0.0:22
```

### Learn

The expected application port exists, but its binding must be examined.

### Do

Identify the local address associated with TCP port `8080`.

### Break

Evaluate this incorrect assumption:

> Because port 8080 appears in the socket inventory, the application must be accessible through `192.0.2.20:8080`.

### Investigate

Use the evidence:

```text
Expected endpoint:
192.0.2.20:8080

Observed endpoint:
127.0.0.1:8080
```

These are different local address bindings.

### Root-cause hypothesis

The application may be configured to bind only to loopback when the intended design requires direct access through the server's non-loopback address.

This is a hypothesis based on the scenario, not proof that every real connection failure with a loopback listener has the same cause.

### Fix decision

The correct action depends on the approved architecture.

If direct access is required, the application owner should review its binding configuration and relevant security controls.

If a local reverse proxy is intended, the loopback binding may be correct, and the investigation should move to the proxy.

Do not change a production service's binding without confirming the intended access model.

### Recovery verification

After an authorized correction, the engineer should verify:

1. The application has the intended local socket.
2. The correct transport protocol and port are used.
3. The bind address matches the approved architecture.
4. Remote connectivity is verified separately using appropriate later-stage network and application tests.

**Lab outcome:** You have identified the configuration discrepancy without making an unnecessary change to your own machine.

### Interview Practice

**1. What is a network port?**

A network port is a numeric identifier used by transport protocols such as TCP and UDP to distinguish communication endpoints associated with applications and services.

**2. What is the difference between TCP and UDP sockets?**

TCP provides connection-oriented communication and has connection states such as `LISTEN` and `ESTAB`. UDP is connectionless at the transport layer and does not use TCP's connection establishment model.

**3. What does it mean when a TCP service listens on `127.0.0.1:8080`?**

The socket is bound to IPv4 loopback on port `8080`. It is not listening on the host's non-loopback IPv4 address through that socket.

**4. What does `0.0.0.0:443` mean?**

For an IPv4 listening socket, it represents a wildcard bind on port `443`. It does not independently prove that the service is reachable from an external network.

**5. Why might a client connection use a high-numbered local port?**

The operating system commonly assigns a temporary source port, called an ephemeral port, when a client initiates communication.

**6. How would you perform a basic inspection of listening TCP sockets?**

I would run:

```bash
ss -lnt
```

Then inspect the local addresses, port numbers, and socket states.

**7. A deployment succeeds, but the expected TCP port is absent from the socket inventory. What would you investigate?**

I would check whether the application is running, whether it is configured for the expected port, and whether it failed to create or bind its listening socket. I would not immediately assume the firewall is responsible.

**8. Why is the statement "port 8080 is open" sometimes insufficient?**

It does not identify the transport protocol, bind address, or actual accessibility. A precise report should describe the observed endpoint, such as a TCP listener bound to `127.0.0.1:8080`.

