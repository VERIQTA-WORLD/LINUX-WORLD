## 1. Mission: Understand Linux Temporary Storage

Linux applications constantly need short-lived storage.

A program may need somewhere to hold:

- intermediate data;
- temporary downloads;
- generated working files;
- installation scratch data;
- application caches used only during an operation;
- temporary communication or state files.

One of the most important locations used for this purpose is:

```text
/tmp
```

But `/tmp` is not simply “a folder where unimportant files go.”

It is normally a **shared temporary directory** with deliberately different permission behavior from ordinary private directories.

In this lab, you will investigate:

```text
/tmp
```

and answer several important questions:

```text
Who can create files there?

Can one user delete another user's files?

Why does /tmp often have mode 1777?

What does the sticky bit protect?

Is /tmp always stored on disk?

Does /tmp survive a reboot?

Can everything in /tmp be deleted safely?

```

The goal is not to memorize `/tmp`.

The goal is to understand the engineering model behind shared temporary storage.

# 2. What Is a Temporary File?

A temporary file is data created because a process needs storage for a limited period rather than permanent retention.

Conceptually:

```text
APPLICATION
     │
     ├── permanent data
     │       │
     │       └── must remain
     │
     └── temporary working data
             │
             └── needed for a limited period
```

For example, imagine an application processing a large file.

It may conceptually do this:

```text
INPUT DATA
    │
    ▼
TEMPORARY WORKING DATA
    │
    ▼
PROCESSING
    │
    ▼
FINAL OUTPUT
```

Once processing finishes, the temporary working data may no longer be required.

Temporary files are therefore different from data such as:

```text
user documents
database data
application configuration
persistent application state
long-term logs
backups
```

### Important distinction

Temporary means:

> The data is not intended to be permanent.

It does **not** automatically mean:

```text
stored in RAM
```

It also does not automatically mean:

```text
deleted immediately
```

or:

```text
safe for anyone to delete at any moment
```

Those are separate questions.

# 3. Meet `/tmp`

Inspect the directory itself:

```bash
ls -ld /tmp
```

On a typical Linux system, the permissions may resemble:

```text
drwxrwxrwt
```

Do not worry if your environment differs.

Read the permissions from left to right:

```text
d rwx rwx rwt
│ │   │   │
│ │   │   └── permissions for others + sticky bit indication
│ │   └────── group permissions
│ └────────── owner permissions
└──────────── directory
```

A common numeric mode for `/tmp` is:

```text
1777
```

You learned the underlying permission model in:

- JUN-007 — File Permissions
- JUN-009 — Symbolic and Numeric Permissions
- JUN-010 — Special Permissions: SUID, SGID and Sticky Bit

Now you are seeing one of the most important real-world uses of the sticky bit.

Check the numeric mode:

```bash
stat -c '%a %A %U %G %n' /tmp
```

Typical output may conceptually resemble:

```text
1777 drwxrwxrwt root root /tmp
```

Your system is the source of truth.

### What `1777` means

Separate the value:

```text
1 777
│ │
│ └── normal permission bits
│
└──── special permission bit
```

The:

```text
777
```

portion provides:

```text
owner  → rwx
group  → rwx
others → rwx
```

The leading:

```text
1
```

represents the sticky bit.

Therefore:

```text
1777
```

means:

```text
shared writable directory
+
sticky-bit protection
```

# 4. Why `/tmp` Needs the Sticky Bit

At first, `/tmp` presents an interesting problem.

Many users and processes need to create temporary files there.

So `/tmp` is commonly writable by everyone.

Conceptually:

```text
/tmp
├── user's temporary data
├── another user's temporary data
├── service temporary data
└── application temporary data
```

Without additional protection, a shared writable directory could create dangerous file-removal and rename behavior between users.

The sticky bit changes directory-entry removal and rename rules.

In a sticky directory such as `/tmp`, ordinary users are generally prevented from deleting or renaming entries they do not own merely because the directory itself is writable.

The relevant ownership relationships include:

- the file or directory entry owner;
- the directory owner;
- privileged users.

For your junior mental model:

```text
WORLD-WRITABLE DIRECTORY
        +
    STICKY BIT
        ↓
USERS CAN CREATE THEIR OWN ENTRIES
        +
USERS CANNOT NORMALLY REMOVE OR RENAME
OTHER USERS' ENTRIES
```

This is why:

```text
777
```

and:

```text
1777
```

are not equivalent.

### Engineer Note

The sticky bit on a directory does not make the contents secret.

It is not encryption.

It is not a substitute for file permissions.

Its important role is controlling who may remove or rename directory entries in a shared writable directory.

Now connect this lab to JUN-039 through JUN-041.

```bash
df -hT /tmp
```

Record:

```text

```

Now run:

```bash
findmnt -T /tmp
```

Inspect:

```text
TARGET
SOURCE
FSTYPE
OPTIONS
```

Your environment may show that `/tmp` is part of:

```text
/
```

Or `/tmp` may be separately mounted.

It could also be backed by:

```text
tmpfs
```

depending on the system configuration.

### Scenario A — `/tmp` is part of `/`

Conceptually:

```text
ROOT FILESYSTEM
      │
      ├── /etc
      ├── /home
      ├── /var
      └── /tmp
```

In this design, files written to `/tmp` consume capacity from the filesystem containing `/`.

---

### Scenario B — `/tmp` is separately mounted

Conceptually:

```text
ROOT FILESYSTEM
      │
      ├── /etc
      ├── /home
      └── /var

SEPARATE FILESYSTEM
      │
      └── /tmp
```

In this design, `/tmp` has a separate filesystem relationship.

---

### Scenario C — `/tmp` uses `tmpfs`

Conceptually:

```text
/tmp
 │
 ▼
tmpfs
 │
 ▼
memory-backed filesystem
```

This is why you should never say:

> `/tmp` is always on disk.

You should also never say:

> `/tmp` is always in RAM.

The correct engineering response is:

> Inspect the actual system.

Use:

```bash
df -hT /tmp
```

and:

```bash
findmnt -T /tmp
```

# 7. Understand `tmpfs`

You first encountered `tmpfs` while studying filesystems.

Now examine it in the context of temporary storage.

Run:

```bash
df -hT
```

Look for entries whose type is:

```text
tmpfs
```

Depending on your system, you may see `tmpfs` mounted at locations such as:

```text
/run
/dev/shm
```

or other locations.

Do not assume a particular list.

Use your actual output.

### What `tmpfs` means

`tmpfs` is a filesystem whose contents are primarily maintained using virtual memory.

It does not behave like an ordinary disk-backed ext4 or XFS filesystem.

A simplified model is:

```text
DISK-BACKED FILESYSTEM

block device
    │
    ▼
filesystem
    │
    ▼
files
```

versus:

```text
tmpfs

virtual memory
    │
    ▼
tmpfs
    │
    ▼
files
```

### Important nuance

Do not reduce `tmpfs` to:

> files stored only in physical RAM.

Linux virtual-memory behavior can involve memory and swap.

For junior-level reasoning, remember:

```text
tmpfs
→ memory-backed filesystem
```

rather than:

```text
tmpfs
→ normal disk filesystem
```

### Capacity

Run this against an actual `tmpfs` path visible on your system.

For example, if `/dev/shm` is `tmpfs`:

```bash
df -hT /dev/shm
```

The displayed filesystem size is a capacity limit for that `tmpfs`.

It does not mean that the entire displayed amount has already been allocated in physical memory.

# 8. `/tmp` Is Temporary — But Do Not Assume When It Disappears

A common beginner assumption is:

> Everything in `/tmp` disappears every time Linux reboots.

Do not build operational decisions around that assumption.

Temporary-file retention and cleanup depend on system configuration.

Different systems may:

- clean some temporary files during boot;
- clean files based on age;
- preserve some content across reboot;
- use automated cleanup services;
- mount `/tmp` as `tmpfs`;
- apply application-specific cleanup behavior.

Therefore:

```text
/tmp
```

means:

```text
temporary-purpose storage
```

not:

```text
guaranteed deletion at one exact moment
```

### Correct engineering question

Instead of asking:

> Does Linux always delete `/tmp` on reboot?

Ask:

> What cleanup policy is configured on this system?

You will inspect part of that mechanism shortly without modifying it.

# 9. Inspect Temporary-File Cleanup Mechanisms

Modern Linux systems may use systemd mechanisms to manage temporary files and directories.

Check whether this command exists:

```bash
command -v systemd-tmpfiles
```

If available, inspect its help:

```bash
systemd-tmpfiles --help
```

Do not run cleanup operations.

You are only establishing that Linux has a mechanism for defining and managing temporary-file behavior.

You may also inspect:

```bash
systemctl status systemd-tmpfiles-clean.timer
```

If that timer exists on your system, inspect its status.

You might also check:

```bash
systemctl status systemd-tmpfiles-clean.service
```

Do not start, stop, enable, disable, or trigger anything.

### Important distinction

Do not conclude:

```text
systemd-tmpfiles
=
/tmp only
```

It is a broader mechanism for managing files and directories according to configured rules.

The important lesson here is:

```text
TEMPORARY DATA CLEANUP
        │
        ▼
CAN BE POLICY-DRIVEN
```

rather than:

```text
someone manually deletes /tmp occasionally
```

Detailed systemd temporary-file policy administration belongs beyond this junior lab.

# 10. Inspect `/tmp` Usage Safely

Suppose an engineer receives this alert:

```text
Filesystem containing /tmp is running low on space.
```

The wrong first response is:

```bash
rm -rf /tmp/*
```

The correct first response is investigation.

### Step 1 — Identify the filesystem

Run:

```bash
df -hT /tmp
```

Ask:

```text
Which filesystem contains /tmp?

What type is it?

How full is it?

What else shares that filesystem?
```

If `/tmp` is part of `/`, then:

```text
/tmp pressure
```

may affect the root filesystem.

If `/tmp` is separately mounted, the impact boundary may be different.

---

### Step 2 — Check inode usage

Run:

```bash
df -i /tmp
```

Record:

```text
Inodes:

IUsed:

IFree:

IUse%:
```

A temporary directory containing huge numbers of tiny files can create inode pressure even when block capacity remains.

---

### Step 3 — Measure `/tmp`

Run:

```bash
du -sh /tmp
```

Depending on your permissions and system contents, you may encounter access-related diagnostics for some entries.

Do not use `sudo` simply to suppress them.

Now inspect one level beneath `/tmp`:

```bash
du -h --max-depth=1 /tmp
```

This may reveal which visible entries account for more allocated storage.

### Important distinction

From previous labs:

```text
df
→ filesystem capacity
```

```text
du
→ allocated usage attributed to traversed files/directories
```

Therefore:

```text
df /tmp
```

and:

```text
du /tmp
```

answer different questions.

# 11. Why Blind `/tmp` Cleanup Is Dangerous

A file being located in:

```text
/tmp
```

does not prove that no running process needs it.

Consider:

```text
PROCESS
   │
   ▼
creates temporary file
   │
   ▼
continues using it
```

If an administrator blindly deletes temporary content, possible consequences include:

- application errors;
- failed installations;
- broken jobs;
- lost temporary state;
- interrupted user sessions;
- service malfunction;
- race conditions;
- unpredictable application behavior.

### Location does not prove safety

This reasoning is unsafe:

```text
It is in /tmp.
        ↓
It must be useless.
        ↓
Delete it.
```

A safer model is:

```text
Identify the object
        ↓
Determine ownership
        ↓
Determine age
        ↓
Understand purpose
        ↓
Determine whether it is active
        ↓
Check configured cleanup policy
        ↓
Only then consider remediation
```

At Junior level, you are **not** going to perform aggressive cleanup.

You will remove only the lab directory that you created.

# 12. Troubleshooting Temporary Storage Correctly

Consider several common mistakes.

### Mistake 1 — `/tmp` is full, so the whole disk must be full

Not necessarily.

First run:

```bash
df -hT /tmp
```

`/tmp` might be:

- part of `/`;
- on a separate filesystem;
- backed by `tmpfs`;
- configured differently.

Determine the actual filesystem before describing the problem.

---

### Mistake 2 — `tmpfs` means physical RAM is already fully allocated

No.

The capacity reported for `tmpfs` is not the same thing as saying all of that amount has already been consumed in physical RAM.

Check actual usage.

---

### Mistake 3 — `/tmp` is temporary, so every file can be deleted

No.

Temporary data can still be actively required.

---

### Mistake 4 — `/tmp` must always be `tmpfs`

No.

Inspect:

```bash
findmnt -T /tmp
```

---

### Mistake 5 — `/tmp` must always be part of `/`

No.

Again:

```bash
findmnt -T /tmp
```

---

### Mistake 6 — `/tmp` always becomes empty after reboot

Do not assume a universal cleanup policy.

Inspect the actual system configuration.

---

### Mistake 7 — `777` and `1777` are effectively the same

They are not.

The leading:

```text
1
```

represents the sticky bit.

That difference is extremely important for shared writable directories.

---

### Mistake 8 — If `du` cannot read everything, use `sudo`

Not automatically.

Permission-denied output is information about your current visibility.

Escalate privileges only when the investigation requires it and you are authorized to do so.

# 14. Knowledge Check, Interview Practice, and Cleanup

## Knowledge Check

1. **What is the purpose of `/tmp`?**  
   It provides a conventional location for temporary working data used by users and applications.

2. **Does temporary mean unimportant?**  
   No. Temporary data may still be required by a running process.

3. **What permissions are commonly associated with `/tmp`?**  
   A common mode is `1777`: writable by all users with the sticky bit enabled.

4. **What does the leading `1` in `1777` represent?**  
   The sticky bit.

5. **Why is the sticky bit important on `/tmp`?**  
   It helps prevent ordinary users from removing or renaming entries belonging to other users merely because the directory itself is shared and writable.

6. **Does the sticky bit encrypt files?**  
   No.

7. **Is `/tmp` always backed by `tmpfs`?**  
   No. Its backing filesystem depends on system configuration.

8. **Is `/tmp` always part of the root filesystem?**  
   No. It can be separately mounted.

9. **What command can identify the filesystem containing `/tmp`?**  
   `df -hT /tmp` is one option, and `findmnt -T /tmp` can show the mount relationship.

10. **What is `tmpfs`?**  
    A memory-backed filesystem using the Linux virtual-memory system rather than an ordinary disk-backed filesystem.

11. **Does a reported 4 GiB `tmpfs` size mean 4 GiB of physical RAM has already been consumed?**  
    No. The reported size represents filesystem capacity, not necessarily current physical-memory consumption.

12. **Why should you check `df -i /tmp`?**  
    To investigate inode usage as well as block capacity where the filesystem exposes inode counts that way.

13. **Why is `rm -rf /tmp/*` unsafe as a first troubleshooting action?**  
    Existing temporary files may still be required by running applications, services, jobs, or users.

14. **Does `/tmp` guarantee that every file disappears at reboot?**  
    No. Cleanup and retention behavior depend on system configuration and policy.

15. **What should happen before temporary data is removed during an incident?**  
    Identify the affected filesystem and objects, inspect capacity, ownership, purpose and relevant cleanup policy, then remediate based on evidence.

## Interview Practice

### Why is `/tmp` commonly configured as `1777`?

`/tmp` needs to be writable by multiple users and processes. Mode `1777` provides broad write access while the sticky bit restricts ordinary users from deleting or renaming entries they do not own simply because the parent directory is writable.

---

### What is the difference between `/tmp` and `tmpfs`?

`/tmp` is a pathname used conventionally for temporary data. `tmpfs` is a filesystem type. `/tmp` may be backed by `tmpfs`, but it may instead be part of a disk-backed filesystem or another configuration.

---

### How would you determine what backs `/tmp`?

I would start with:

```bash
df -hT /tmp
```

and:

```bash
findmnt -T /tmp
```

These show the filesystem and mount relationship rather than relying on assumptions.

---

### `/tmp` is full. What would you check first?

I would identify the filesystem containing `/tmp`, inspect block capacity with `df -hT /tmp`, check inode capacity with `df -i /tmp`, confirm the mount relationship, and then investigate visible usage with `du` before considering cleanup.

---

### Why wouldn't you immediately delete old-looking files from `/tmp`?

Age and location alone do not prove that a file is unused. A running process may still depend on temporary data. I would first establish ownership, purpose, activity and system cleanup policy.

---

### Can `tmpfs` consume swap?

`tmpfs` participates in the Linux virtual-memory system, so its pages can potentially be backed by swap. It should not be described simply as a normal disk filesystem or as data that can only ever exist in physical RAM.

---

### What is the difference between `df` and `du` when investigating `/tmp`?

`df` reports capacity and usage from the filesystem perspective. `du` attributes allocated usage to files and directories it can traverse. They answer different questions.

---

### Why is the sticky bit especially useful for shared directories?

A shared writable directory needs to let multiple users create entries without giving each ordinary user unrestricted ability to remove or rename entries belonging to others. The sticky bit provides that additional directory-entry protection.
