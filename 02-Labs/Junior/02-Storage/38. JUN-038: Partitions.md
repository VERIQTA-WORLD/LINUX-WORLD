# 2. Understand the Partition Layer

A disk is a block device.

A partition is a defined region within that device.

A simplified disk might look like:

```text
+-------------------------------------------------------+
|                     /dev/sda                          |
+------------+--------------------+---------------------+
| /dev/sda1  |     /dev/sda2      |     /dev/sda3      |
|   1 GiB    |       40 GiB        |       59 GiB        |
+------------+--------------------+---------------------+
```

Those partitions can have different purposes.

For example:

```text
/dev/sda1
    │
    ▼
EFI System Partition
```

```text
/dev/sda2
    │
    ▼
Linux filesystem
    │
    ▼
/
```

A more complex system might use a partition as the foundation for another storage layer:

```text
DISK
  │
  ▼
PARTITION
  │
  ▼
LVM
  │
  ▼
FILESYSTEM
  │
  ▼
MOUNT POINT
```

The partition does not have to contain a filesystem directly.

That distinction is important.

### Partition vs filesystem

A partition defines:

> Which region of the block device belongs to this storage object?

A filesystem defines structures for:

> Organizing files and directories within storage.

Therefore:

```text
PARTITION
≠
FILESYSTEM
```

A partition can exist without a filesystem.

A filesystem can also exist on storage abstractions other than a traditional partition.

### Partition vs mount point

A partition such as:

```text
/dev/sda2
```

is not the same thing as:

```text
/
```

The first is a block-device object.

The second is a location in the Linux directory hierarchy.

The relationship might be:

```text
/dev/sda
   │
   ▼
/dev/sda2
   │
   ▼
ext4
   │
   ▼
/
```

Keep those layers separate.

# 3. Understand Partition Tables, Sectors, GPT, and MBR

A disk needs a way to describe where its partitions begin and end.

That information is represented by a **partition table**.

Conceptually:

```text
DISK
 │
 ├── partition table
 │      │
 │      ├── partition 1 starts here, ends here
 │      ├── partition 2 starts here, ends here
 │      └── partition 3 starts here, ends here
 │
 └── partition data
```

## Sectors

Storage devices expose addressable regions commonly described in sectors.

A partition is defined using boundaries corresponding to locations on the disk.

You may therefore encounter partition information such as:

```text
Start
End
Sectors
Size
```

You do not need to calculate partition geometry manually in this junior lab.

Understand the relationship:

```text
START
  │
  ▼
partition occupies a range
  │
  ▼
END
```

Partition boundaries matter because two partitions must not accidentally claim overlapping storage regions.

---

## GPT

GPT means:

**GUID Partition Table**

GPT is the modern partition-table scheme commonly used on contemporary Linux systems.

It supports:

- large storage devices;
- many partitions without the old MBR primary/extended-partition structure;
- unique partition identifiers;
- partition type identifiers;
- redundant partition-table information;
- integrity checking of partition-table structures.

GPT is commonly associated with modern UEFI-based systems.

---

## MBR

MBR means:

**Master Boot Record**

You may also see it described by tools as:

```text
dos
```

partition-table type.

MBR is an older partitioning scheme.

A traditional MBR layout supports up to four primary partition entries. Historically, extended and logical partitions were used when more partitions were required.

MBR also has legacy addressing limitations that make GPT more appropriate for modern large disks.

You do not need to build an MBR layout in this lab.

You need to recognize that both schemes exist.

### Junior comparison

| Area | GPT | MBR |
|---|---|---|
| Generation | Modern | Legacy |
| Large disks | Better suited | Legacy limitations |
| Partition count model | Many entries supported | Traditional four-primary-entry model |
| Partition identifiers | GUID-based | Older type/entry model |
| Redundant table data | Yes | No equivalent GPT-style redundancy |
| Common modern UEFI use | Yes | Legacy systems may still use MBR |

Do not conclude that every Linux system must use GPT.

Inspect the actual system.

# 5. Understand Linux Partition Names

Partition naming depends on the parent device type.

## Traditional `sdX`

A disk:

```text
/dev/sda
```

might contain:

```text
/dev/sda1
/dev/sda2
/dev/sda3
```

The number identifies the partition.

Likewise:

```text
/dev/sdb
```

might contain:

```text
/dev/sdb1
```

---

## Virtual disks

A virtual disk might appear as:

```text
/dev/vda
```

with:

```text
/dev/vda1
/dev/vda2
```

---

## NVMe

NVMe naming requires the `p` separator.

Disk:

```text
/dev/nvme0n1
```

Partition:

```text
/dev/nvme0n1p1
```

Another:

```text
/dev/nvme0n1p2
```

Conceptually:

```text
nvme0n1
│
└── p2
    │
    └── partition 2
```

---

## MMC/eMMC-style storage

A device might appear as:

```text
/dev/mmcblk0
```

with:

```text
/dev/mmcblk0p1
/dev/mmcblk0p2
```

### Important rule

Do not write software or operational procedures that assume:

```text
partition = disk name + "1"
```

That works for:

```text
sda → sda1
```

but not:

```text
nvme0n1 → nvme0n1p1
```

or:

```text
mmcblk0 → mmcblk0p1
```

Use system discovery rather than string guessing.

```text

```

On many systems, complete disk information may require authorized elevated access.

Do not escalate privileges merely to complete this section.

If your current user cannot inspect the table, use the `lsblk` evidence available to you and continue.

Depending on the device and permissions, information can include:

```text

Disklabel type
Sector size
Device
Start
End
Sectors
Size
Type
```

A GPT disk might report:

```text

```

# 8. Recognize Common Partition Roles

Partitions can serve different purposes.

Do not assume every partition is intended to hold ordinary application files.

## Root filesystem partition

A partition may contain the filesystem mounted at:

```text
/
```

You can investigate with:

```bash
findmnt /
```

Then correlate the source with:

```bash
lsblk -f
```

---

## EFI System Partition

On UEFI systems, you may see a small partition with a FAT-family filesystem mounted at:

```text
/boot/efi
```

Use:

```bash
findmnt /boot/efi
```

only if that path is actually a mount on your machine.

An EFI System Partition stores files used by UEFI boot mechanisms.

Do not delete, format, or repurpose it merely because it appears small.

---

## `/boot`

Some systems use a separate filesystem mounted at:

```text
/boot
```

Others keep `/boot` inside the root filesystem.

Inspect:

```bash
findmnt /boot
```

and compare with:

```bash
findmnt /
```

If they resolve to the same mounted filesystem, `/boot` is not a separate mount in that environment.

---

## Swap

A partition can also be used for swap rather than a mounted filesystem.

If `lsblk -f` reports:

```text
swap
```

that partition is serving a different role.

Do not expect every partition to have a normal directory mount point.

---

## Higher-level storage

A partition can also feed:

```text
LVM
encryption
RAID
other mapped storage
```

Therefore:

```text
PARTITION HAS NO MOUNT POINT
```

does not mean:

```text
PARTITION IS UNUSED
```

This is one of the most important safety lessons in Linux storage work.

# 9. Connect Partition Size to Filesystem Capacity

Suppose `lsblk` reports:

```text
/dev/sda2
SIZE = 79G
```

while:

```bash
df -h /
```

reports a somewhat different filesystem size.

That does not automatically indicate a problem.

You are comparing different layers.

### Partition size

From:

```bash
lsblk
```

you are asking:

> How large is this block-device region?

### Filesystem capacity

From:

```bash
df
```

you are asking:

> What capacity does the filesystem report?

Conceptually:

```text
DISK
100G
 │
 ▼
PARTITION
99G
 │
 ▼
FILESYSTEM
slightly different usable/reportable capacity
 │
 ▼
MOUNT POINT
/
```

Differences can involve:

- filesystem metadata;
- reserved filesystem space;
- unit representation;
- storage layering;
- filesystem implementation.

Therefore:

```text
DISK SIZE
≠
PARTITION SIZE
≠
FILESYSTEM CAPACITY
≠
AVAILABLE SPACE
```

### Verify on your system

Run:

```bash
findmnt -T ~/linux-world-labs/JUN-038
```

Then:

```bash
df -hT ~/linux-world-labs/JUN-038
```

Then:

```bash
lsblk -p -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
```

Map as much of this chain as your environment exposes:

```text
DISK:

PARTITION:

FILESYSTEM:

MOUNT POINT:

FILESYSTEM CAPACITY:
```

If another layer exists between the partition and filesystem, include it rather than hiding it.

# 10. Troubleshoot Partition Misidentification

Storage mistakes often begin with an incorrect mental model.

## Mistake 1 — Treating a whole disk as a partition

Given:

```text
sda
├─sda1
└─sda2
```

do not describe:

```text
/dev/sda
```

as "partition 0."

It is the parent disk-like block device.

---

## Mistake 2 — Assuming every disk must have partitions

Some block devices can contain a filesystem directly or participate in another storage arrangement.

A traditional partition is common.

It is not universal.

---

## Mistake 3 — Assuming every partition contains a filesystem

A partition may instead participate in:

- swap;
- LVM;
- encryption;
- RAID;
- another storage layer.

Use evidence.

---

## Mistake 4 — Assuming an unmounted partition is unused

This is dangerous.

A blank mount-point field proves only that `lsblk` is not showing a normal mount point for that entry.

Investigate its:

```text
TYPE
FSTYPE
parent/child relationships
UUID/PARTUUID
```

before drawing conclusions.

---

## Mistake 5 — Confusing partition size with free space

If:

```text
/dev/sda2
```

is:

```text
80G
```

that does not mean:

```text
80G free
```

Partition size is not available filesystem capacity.

Use:

```bash
df -h PATH
```

for mounted filesystem capacity.

---

## Mistake 6 — Modifying the wrong device

A partitioning tool can make destructive changes quickly.

Before any future partition-changing operation, you should be able to answer:

```text
What is the exact device?

Is it a disk or partition?

What are its children?

Does it contain a filesystem?

Is anything mounted from it?

Is it part of another storage layer?

Does the operating system depend on it?

Is the data backed up?

Is this really the intended target?
```

If those answers are uncertain, stop.

# 11. Safe Partition Investigation Workflow

When investigating an unfamiliar Linux server, use a read-only sequence.

### Step 1 — Discover block topology

```bash
lsblk
```

Identify:

```text
disk
part
```

relationships.

### Step 2 — Add filesystem information

```bash
lsblk -f
```

Determine whether partitions expose:

```text
FSTYPE
UUID
LABEL
MOUNTPOINTS
```

### Step 3 — Request a focused topology

```bash
lsblk -p -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
```

Record exact device paths.

### Step 4 — Start from the affected path when troubleshooting

```bash
findmnt -T /path/to/application
```

Then:

```bash
df -hT /path/to/application
```

Determine which mounted filesystem actually matters.

### Step 5 — Map upward

Conceptually:

```text
APPLICATION PATH
      │
      ▼
MOUNT POINT
      │
      ▼
FILESYSTEM SOURCE
      │
      ▼
PARTITION / MAPPED DEVICE
      │
      ▼
PARENT DISK
```

### Step 6 — Inspect the partition-table scheme when permitted

If read-only `fdisk` listing is available and authorized:

```text
fdisk -l
```

Determine whether the relevant disk reports:

```text
gpt
```

or:

```text
dos
```

Do not enter interactive modification mode.

### Step 7 — Document before changing anything

Your investigation should be able to state:

```text
Affected path:
Mount point:
Filesystem:
Filesystem type:
Partition/device:
Parent disk:
Partition-table type:
Device size:
```


# 13. Knowledge Check, Interview Practice, and Completion

## Knowledge Check

1. **What is a partition?**  
   A defined region of a block device represented as a separate block-device object.

2. **What is a partition table?**  
   Metadata describing how storage regions on a disk are divided into partitions.

3. **Is a partition the same thing as a filesystem?**  
   No. A partition defines a storage region; a filesystem provides structures for organizing files and directories.

4. **What is GPT?**  
   GUID Partition Table, a modern partition-table scheme widely used on contemporary systems.

5. **What is MBR?**  
   Master Boot Record, an older partitioning scheme that may also be described as a DOS partition table by Linux tools.

6. **Why is GPT generally preferred for modern systems?**  
   It handles modern large disks and partition layouts better, supports many partition entries, uses GUID-based identification, and includes redundant partition-table information.

7. **What is the relationship between `/dev/sda` and `/dev/sda2` in a conventional layout?**  
   `/dev/sda` is the parent disk-like block device and `/dev/sda2` is partition 2 on it.

8. **Why is an NVMe partition called something like `/dev/nvme0n1p2` instead of `/dev/nvme0n12`?**  
   NVMe naming uses the `p` separator before the partition number to distinguish the partition component from the namespace numbering.

9. **Does every partition contain a filesystem?**  
   No. A partition may be used for swap or as input to LVM, encryption, RAID, or another storage layer.

10. **Does a blank mount point prove that a partition is unused?**  
    No.

11. **What is the difference between UUID and PARTUUID?**  
    UUID commonly identifies a filesystem, while PARTUUID identifies a partition in the partition-table context.

12. **Why can partition size differ from the capacity shown by `df`?**  
    They represent different layers. `lsblk` reports block-device or partition size, while `df` reports filesystem capacity.

13. **What does `fdisk -l` do?**  
    It lists partition information without entering the normal interactive partition-editing workflow.

14. **Why should you identify the parent disk before modifying a partition?**  
    Because partition changes affect defined regions of that disk, and selecting the wrong device can destroy unrelated filesystems, boot structures, or data.

15. **What should you do if the actual topology does not match a simple disk → partition → filesystem model?**  
    Document and investigate the additional storage layers rather than forcing the system into an inaccurate model.

## Interview Practice

### What is the difference between a disk and a partition?

A disk is the parent block-device storage resource. A partition is a defined region of that device represented separately by Linux.

---

### How would you list disks and partitions on Linux?

I would begin with:

```bash
lsblk
```

For a more explicit view:

```bash
lsblk -p -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
```

---

### How would you determine which partition backs an application path?

I would begin from the path:

```bash
findmnt -T /path/to/application
```

and:

```bash
df -hT /path/to/application
```

Then I would use `lsblk` to map the reported source into the block-device topology and identify its parent device.

---

### What is the difference between GPT and MBR?

GPT is the modern GUID-based partition-table scheme with support for modern large disks, many partition entries, and redundant partition-table information. MBR is the older partitioning model with legacy structural and addressing limitations.

---

### Does an unmounted partition mean it is safe to format?

No. It could be swap, part of LVM, encrypted storage, RAID, an inactive filesystem containing important data, or another storage component. I would identify its purpose before changing it.

---

### What is the difference between filesystem UUID and PARTUUID?

A filesystem UUID identifies the filesystem, while PARTUUID identifies the partition entry itself.

---

### Why would you avoid opening `fdisk /dev/sda` simply to inspect a production server?

That enters an interactive partition-management tool capable of changing the partition table. For initial discovery I would use read-only tools such as `lsblk` and, when appropriate and authorized, `fdisk -l`.
