## 1. Mission: Attach and Detach a Filesystem Safely

You already understand the storage chain:

```text
BLOCK DEVICE
      │
      ▼
PARTITION
      │
      ▼
FILESYSTEM
      │
      ▼
MOUNT POINT
      │
      ▼
FILES + DIRECTORIES
```

But one important question remains:

**How does a filesystem actually become accessible through a Linux directory such as `/`, `/boot`, `/mnt/data`, or `/srv`?**

Through a **mount**.

Linux does not normally expose separate filesystems as independent drive letters.

Instead, filesystems are attached to locations inside one directory hierarchy.

For example:

```text
/
├── etc
├── home
├── mnt
│   └── data       ← another filesystem could be mounted here
├── srv
└── var
```

The directory:

```text
/mnt/data
```

can act as a **mount point**.

Once a filesystem is mounted there:

```text
FILESYSTEM
     │
     ▼
 /mnt/data
     │
     ▼
files from that filesystem
```

Your mission is to understand that relationship and perform a real temporary mount and unmount safely.

### Learning objectives

By the end of this lab, you should be able to:

- explain what mounting means;
- explain what a mount point is;
- distinguish a filesystem from its mount point;
- inspect active mounts with `findmnt`;
- identify which filesystem contains a path;
- use `mountpoint` to test whether a directory is itself a mount point;
- understand the basic `mount` command model;
- mount a temporary `tmpfs`;
- verify a mount using multiple sources of evidence;
- understand what happens to existing directory contents when another filesystem is mounted over that directory;
- explain why those underlying files are hidden rather than deleted;
- unmount a filesystem with `umount`;
- understand why `umount` is spelled without the first `n`;
- recognize a busy mount;
- investigate one common cause of a busy mount;
- safely recover by leaving the mounted directory before unmounting;
- distinguish temporary mounts from persistent mount configuration;
- clean up the complete lab state.

### Safety boundary

This lab performs a real mount operation, but it does **not** use a real disk or partition.

You will mount:

```text
tmpfs
```

into a disposable lab directory.

You will **not**:

- format a disk;
- create a filesystem on a block device;
- repartition storage;
- mount an unknown real partition;
- modify `/etc/fstab`;
- force an unmount;
- use lazy unmount as a shortcut;
- detach a production filesystem.

Persistent mounting belongs to:

**JUN-041 — `/etc/fstab`**

# 2. Understand Mounting Before Running `mount`

A filesystem and a mount point are different objects.

Suppose a filesystem exists on:

```text
/dev/sdb1
```

and an administrator wants its contents available at:

```text
/data
```

Conceptually:

```text
/dev/sdb1
   │
   ▼
filesystem
   │
   │ mount
   ▼
 /data
```

After the mount, applications can access the filesystem through:

```text
/data
```

### What is a mount point?

A mount point is a location in the Linux directory hierarchy where a filesystem is attached.

It is commonly a directory.

For example:

```text
/
├── home
├── var
├── data       ← possible mount point
└── mnt
```

If a filesystem is mounted at:

```text
/data
```

then accessing:

```text
/data/file.txt
```

accesses `file.txt` from the mounted filesystem.

### Mounting does not move the filesystem

A mount does not mean:

```text
copy filesystem into directory
```

It means:

```text
attach filesystem to this point
in the directory hierarchy
```

### Mounting does not normally erase the mount-point directory

This distinction matters.

Suppose:

```text
/mnt/data
```

already contains:

```text
old-file.txt
```

and another filesystem is mounted at:

```text
/mnt/data
```

The original `old-file.txt` normally becomes hidden behind the mounted filesystem.

It has not automatically been deleted.

Conceptually:

```text
BEFORE MOUNT

/mnt/data
└── old-file.txt
```

Then:

```text
FILESYSTEM B
      │
      ▼
 /mnt/data
```

While mounted:

```text
/mnt/data
└── contents of FILESYSTEM B
```

The original directory contents underneath the mount are temporarily obscured.

After the filesystem is unmounted:

```text
/mnt/data
└── old-file.txt
```

becomes visible again.

You will prove this behavior safely later.

# 4. Understand `findmnt -T` vs `mountpoint`

These two tools answer different questions.

You already used:

```bash
findmnt -T PATH
```

This determines which mounted filesystem contains a path.

Now check:

```bash
command -v mountpoint
```

On a standard Ubuntu environment, `mountpoint` should normally be available.

Test the lab mount directory:

```bash
mountpoint ~/linux-world-labs/JUN-040/mount-point
```

Before the temporary mount, it should report that the directory is not a mount point.

The command may also return a non-zero status because the test is false.

### Important distinction

This:

```bash
findmnt -T ~/linux-world-labs/JUN-040/mount-point
```

can still return a filesystem.

Why?

Because the directory exists **inside** some mounted filesystem.

But:

```bash
mountpoint ~/linux-world-labs/JUN-040/mount-point
```

asks whether that exact directory is itself a mount point.

So:

```text
findmnt -T PATH
→ Which mount contains this path?
```

while:

```text
mountpoint PATH
→ Is this path itself a mount point?
```

This distinction is extremely useful.

# 5. Understand the `mount` Command Model

A common explicit mount pattern is:

```text
mount [options] SOURCE TARGET
```

Conceptually:

```text
SOURCE
  │
  │ mount
  ▼
TARGET
```

For a disk-backed filesystem, an example might conceptually be:

```text
SOURCE
/dev/sdb1

TARGET
/mnt/data
```

But you will **not** use a real block device in this lab.

Instead, you will use:

```text
tmpfs
```

### Why `tmpfs`?

`tmpfs` gives you a real filesystem mount without requiring you to:

- partition a disk;
- create a filesystem on a disk;
- identify a disposable block device;
- risk overwriting persistent storage.

The mount exists in memory-backed storage.

When it is unmounted, its contents do not become persistent disk data.

This makes it appropriate for this controlled junior exercise.

### The command you will use

The basic form will be:

```bash
sudo mount -t tmpfs tmpfs ~/linux-world-labs/JUN-040/mount-point
```

Break it down:

```text
sudo
→ execute the privileged mount operation
```

```text
mount
→ attach a filesystem
```

```text
-t tmpfs
→ specify filesystem type tmpfs
```

```text
tmpfs
→ source name for this tmpfs mount
```

```text
~/linux-world-labs/JUN-040/mount-point
→ target mount point
```

Do not run it yet.

First you will prepare evidence showing what exists underneath the future mount.

# 7. Prove What Happens to Existing Directory Contents

Before mounting, you created:

```text
mount-point/underlying-file.txt
```

Now inspect:

```bash
ls -la ~/linux-world-labs/JUN-040/mount-point
```

The file should no longer be visible through that path.

Do **not** conclude:

> Mount deleted my file.

It did not.

The new filesystem is mounted over the directory, so the original directory contents are hidden underneath the mount.

Conceptually:

```text
BEFORE

existing filesystem
      │
      ▼
mount-point/
└── underlying-file.txt
```

After mounting:

```text
tmpfs
  │
  ▼
mount-point/
└── contents of tmpfs
```

The original:

```text
underlying-file.txt
```

still belongs to the underlying filesystem.

You simply cannot reach it through the covered directory while the new filesystem is mounted there.

---

## Create a file inside the mounted filesystem

Run:

```bash
touch ~/linux-world-labs/JUN-040/mount-point/mounted-file.txt
```

Verify:

```bash
ls -la ~/linux-world-labs/JUN-040/mount-point
```

You should now see:

```text
mounted-file.txt
```

This file belongs to the mounted `tmpfs`, not to the underlying directory's original filesystem.

You now have two different states associated with the same pathname at different times:

```text
UNDERLYING DIRECTORY CONTENT
underlying-file.txt
```

and:

```text
MOUNTED FILESYSTEM CONTENT
mounted-file.txt
```

This distinction becomes extremely important in production.

### Common operational mistake

Imagine:

```text
/var/lib/application
```

normally has a dedicated filesystem mounted there.

If that filesystem fails to mount during startup, the directory itself may still exist on the root filesystem.

An application could then write into the underlying directory.

Later, when the intended filesystem is mounted, those files become hidden.

This can produce confusing disk-usage incidents.

The key lesson is:

> A mount point is a directory path, but what you see through that path depends on which filesystem is mounted there.

```text
umount
```

Notice the spelling:

```text
umount
```

not:

```text
unmount
```

### Unmount by target

Run:

```bash

```

Again, do not treat silence as proof.

Verify.

### Check 1

```bash
mountpoint ~/linux-world-labs/JUN-040/mount-point
```

It should report that the directory is no longer a mount point.

### Check 2

```bash
findmnt ~/linux-world-labs/JUN-040/mount-point
```

The exact mount should no longer be present.

### Check 3

```bash
ls -la ~/linux-world-labs/JUN-040/mount-point
```

What has returned?

You should again see:

```text
underlying-file.txt
```

What happened to:

```text
mounted-file.txt
```

Since this lab used `tmpfs`, you should not treat its contents as persistent storage.

### What did this prove?

You demonstrated:

```text
DIRECTORY CONTENT
      │
      ▼
underlying-file.txt
```

then:

```text
MOUNT tmpfs
      │
      ▼
underlying content hidden
      │
      ▼
mounted-file.txt visible
```

then:

```text
UNMOUNT
      │
      ▼
tmpfs detached
      │
      ▼
underlying-file.txt visible again
```

This is a real filesystem namespace behavior, not just theory.

# 9. Break It Safely: Reproduce a Busy Mount

One of the most common unmount problems is:

```text
target is busy
```

A filesystem may be busy because some process still has a relationship with it.

Common causes can include:

- a process has a file open there;
- a shell has its current working directory there;
- another mount exists below it;
- an application is actively using it.

You will reproduce one simple case safely.

---

## Mount the temporary filesystem again

Run:

```bash
sudo mount -t tmpfs tmpfs ~/linux-world-labs/JUN-040/mount-point
```

Verify:

```bash
findmnt ~/linux-world-labs/JUN-040/mount-point
```

Now enter it:

```bash
cd ~/linux-world-labs/JUN-040/mount-point
```

Confirm:

```bash
pwd
```

Your shell's current working directory is now inside the mounted filesystem.

### Attempt to unmount it

Run:

```bash
sudo umount ~/linux-world-labs/JUN-040/mount-point
```

On a normal local filesystem, this should fail because your shell is actively using the mount as its current working directory.

A typical diagnostic may indicate that the target is busy.

Exact wording can vary.

### Symptom

```text
umount fails
```

### Impact

The filesystem remains mounted.

### Evidence

Your shell is currently located inside:

```text
~/linux-world-labs/JUN-040/mount-point
```

and:

```bash
findmnt ~/linux-world-labs/JUN-040/mount-point
```

still reports the mount.

### Hypothesis

Your current shell is keeping the mount busy because its current working directory is inside that filesystem.

### Test

Move outside the mount:

```bash
cd ~/linux-world-labs/JUN-040
```

Confirm:

```bash
pwd
```

Now retry:

```bash
sudo umount ~/linux-world-labs/JUN-040/mount-point
```

### Recovery verification

Run:

```bash
mountpoint ~/linux-world-labs/JUN-040/mount-point
```

Then:

```bash
ls -la ~/linux-world-labs/JUN-040/mount-point
```

The underlying file should again be visible.

### Root cause

The shell's current working directory was inside the mounted filesystem.

### Fix

Leave the filesystem and retry the normal unmount.

### Prevention

Before unmounting, check whether:

- your shell is inside the mount;
- users or applications may still be using it;
- child mounts exist below it;
- stopping access is operationally safe.

# 10. Safe Unmounting and Common Mistakes

Unmounting is not simply:

> run `umount` until it works.

The operation changes access to a filesystem and can affect applications and users.

## Mistake 1 — Deleting the mount-point directory instead of unmounting

Do not confuse:

```text
remove directory
```

with:

```text
detach filesystem
```

Use:

```bash
umount TARGET
```

to detach the filesystem.

---

## Mistake 2 — Unmounting the wrong filesystem

Before unmounting:

```bash
findmnt TARGET
```

Confirm:

```text
TARGET
SOURCE
FSTYPE
```

Never operate from memory alone.

---

## Mistake 3 — Assuming `cd` out of the directory always solves a busy mount

It solved the controlled failure in this lab.

In production, another process may still be using the filesystem.

The correct lesson is not:

```text
busy mount
→ cd away
→ always fixed
```

It is:

```text
busy mount
→ identify what is using it
→ remove the dependency safely
→ retry normal unmount
```

Later troubleshooting labs will go deeper into process and file-use investigation.

---

## Mistake 4 — Using force as the first response

Do not jump immediately to force-related or lazy-unmount options because a normal unmount failed.

Those options change semantics and can hide unresolved dependencies.

At this level:

```text
normal unmount fails
        │
        ▼
investigate why
        │
        ▼
remove dependency safely
        │
        ▼
retry normal unmount
```

---

## Mistake 5 — Mounting over a populated directory without checking it

Mounting over a non-empty directory can hide its existing contents.

Before mounting onto a directory, inspect it:

```bash
ls -la /intended/mount/point
```

and verify:

```bash
findmnt /intended/mount/point
```

Do not accidentally hide application data.

---

## Mistake 6 — Assuming `df` alone proves the intended mount is active

`df` provides useful filesystem evidence, but when verifying a mount relationship use:

```bash
findmnt TARGET
```

and:

```bash
mountpoint TARGET
```

as well.

Verification should answer the actual question.

---

## Mistake 7 — Assuming a successful temporary mount survives reboot

The mount you created manually in this lab is not persistent configuration.

A temporary command such as:

```text
mount ...
```

changes the current running system state.

Persistent mount configuration is a separate problem.

That belongs to:

```text
/etc/fstab
```

which you will study in JUN-041.

# 11. Build a Professional Mount Investigation Workflow

Suppose an application team reports:

> `/srv/data` is not showing the files we expected.

Do not immediately mount, unmount, or modify anything.

Use a structured investigation.

### 1. Inspect the path

```bash
ls -la /srv/data
```

Ask:

```text
Does the directory exist?

What is currently visible?
```

### 2. Determine whether the exact path is a mount point

```bash
mountpoint /srv/data
```

### 3. Inspect the mount relationship

```bash
findmnt /srv/data
```

If there is no exact mount, determine which filesystem contains the path:

```bash
findmnt -T /srv/data
```

This distinction matters.

### 4. Inspect filesystem capacity

```bash
df -hT /srv/data
```

### 5. Inspect storage topology when appropriate

```bash
lsblk -f
```

### 6. Compare expected and actual state

Ask:

```text
What filesystem should be mounted here?

What filesystem is actually mounted here?

Is there an exact mount at this path?

Is the path merely a directory on another filesystem?

Could underlying directory contents be exposed because the expected mount is absent?

Could existing contents be hidden because another filesystem is mounted over them?
```

### 7. Change nothing until the state is understood

The workflow is:

```text
PATH
 │
 ▼
mountpoint
 │
 ▼
IS THIS AN EXACT MOUNT POINT?
 │
 ▼
findmnt
 │
 ▼
WHAT IS MOUNTED HERE?
 │
 ▼
df
 │
 ▼
WHAT FILESYSTEM IS ACTIVE?
 │
 ▼
lsblk -f
 │
 ▼
WHAT STORAGE BACKS IT?
 │
 ▼
THEN DECIDE WHETHER CHANGE IS REQUIRED
```

# 13. Knowledge Check, Interview Practice, and Cleanup

## Knowledge Check

1. **What does mounting a filesystem mean?**  
   Attaching a filesystem to a location in the Linux directory hierarchy so its contents can be accessed through that path.

2. **What is a mount point?**  
   A directory location where a filesystem is attached to the Linux directory tree.

3. **Is a mount point the same thing as a filesystem?**  
   No. The filesystem contains and organizes data; the mount point is the directory location through which the mounted filesystem is accessed.

4. **What happens to existing files in a directory when another filesystem is mounted over it?**  
   They are normally hidden by the mounted filesystem rather than deleted.

5. **What happens to those underlying files after the mounted filesystem is unmounted?**  
   They become visible again through the directory.

6. **What does `findmnt -T PATH` answer?**  
   It identifies the mounted filesystem containing the specified path.

7. **What does `mountpoint PATH` answer?**  
   It tests whether that exact path is itself a mount point.

8. **Why did this lab use `tmpfs` instead of a real disk partition?**  
   It allows real mount/unmount practice without partitioning, formatting, or risking persistent block storage.

9. **What command detaches a mounted filesystem?**  
   `umount`.

10. **Why can an unmount fail with a busy-target error?**  
    A process may still be using the filesystem, such as by holding an open file or having its current working directory inside the mount.

11. **Why should force or lazy unmount not be the first response to a busy mount?**  
    Because the dependency should first be understood and resolved safely rather than bypassed.

12. **Does running `mount` manually make a mount persistent across reboot?**  
    Not by itself.

13. **Why should you inspect a mount-point directory before mounting over it?**  
    Existing contents can become hidden while another filesystem is mounted there.

14. **What is the difference between `findmnt`, `df`, and `lsblk`?**  
    `findmnt` describes mount relationships, `df` reports mounted filesystem capacity, and `lsblk` shows block-device topology and can display filesystem metadata.

15. **Why should an engineer verify a mount after the `mount` command returns successfully?**  
    Because operational verification should confirm the intended target, source, filesystem type, and resulting state rather than relying only on command completion.

## Interview Practice

### What does it mean to mount a filesystem in Linux?

Mounting attaches a filesystem to a directory in the Linux namespace. After the mount, the filesystem's contents are accessed through that directory.

---

### How would you check whether `/data` is actually a mount point?

I would use:

```bash
mountpoint /data
```

and inspect the exact mount relationship with:

```bash
findmnt /data
```

---

### What is the difference between `findmnt /data` and `findmnt -T /data`?

`findmnt /data` is useful for looking for a mount whose target is `/data`. `findmnt -T /data` determines which mounted filesystem contains the path, even if `/data` is only a normal directory inside a larger filesystem.

---

### What happens if you mount a filesystem over a directory that already contains files?

The mounted filesystem normally hides the directory's underlying contents while the mount is active. The underlying files are not automatically deleted and become visible again after unmounting.

---

### How would you investigate `umount: target is busy`?

I would determine what is using the filesystem rather than immediately forcing the unmount. I would check simple causes such as shells whose working directories are inside the mount, active applications, open files, or child mounts, remove the dependency safely, and retry a normal unmount.

---

### Does a successful `mount` command prove that the correct filesystem is mounted at the intended target?

I would still verify it. I can use:

```bash
findmnt TARGET
```

```bash
mountpoint TARGET
```

and, where useful:

```bash
df -hT TARGET
```

to confirm the resulting state.

---

### What is the difference between a temporary mount and a persistent mount?

A temporary mount changes the running system's current mount state. Persistent configuration defines how the filesystem should be mounted again, such as during system startup. Persistent configuration will be covered with `/etc/fstab`.

---

### Why is mounting the wrong filesystem operationally dangerous even if no data is immediately deleted?

It can hide expected directory contents, expose unexpected data at an application path, cause applications to write to the wrong storage, or make services operate against an unintended filesystem.
