## 2. Understand What a Block Device Is

Linux represents many hardware and virtual resources through objects under:

```text
/dev
```

A storage device might appear as:

```text
/dev/sda
```

or:

```text
/dev/nvme0n1
```

These are **device nodes** through which userspace programs interact with devices managed by the kernel.

### Block vs character devices

Linux broadly exposes device nodes as types including:

```text
block devices
```

and:

```text
character devices
```

A block device provides storage in addressable blocks and commonly supports operations associated with disks and disk-like storage.

Examples can include:

- HDDs;
- SSDs;
- NVMe devices;
- virtual machine disks;
- cloud block volumes;
- removable storage;
- logical storage devices.

Character devices represent a different I/O model.

You do not need to study character-device administration here.

The important model is:

```text
/dev
 │
 ├── block device nodes
 │      └── storage-related devices
 │
 └── other device nodes
```

### Inspect `/dev`

Run:

```bash
ls -l /dev
```

Do not try to interpret every entry.

The directory can contain many device-related objects.

Instead, inspect a known storage name from your machine after running `lsblk` in the next section.

### File type indicator

A block-device node shown by:

```bash
ls -l /dev/DEVICE
```

typically begins with:

```text
b
```

in the file-type position.

Conceptually:

```text
brw-rw----
^
│
block device
```

A regular file normally begins with:

```text
-
```

A directory:

```text
d
```

A symbolic link:

```text
l
```

This connects your earlier filesystem knowledge to device nodes.

## 3. Discover Storage Topology with `lsblk`

Run:

```bash
lsblk
```

`lsblk` means:

```text
list block devices
```

This is one of the most important safe discovery tools in Linux storage administration.

A typical output structure may resemble:

```text
NAME        MAJ:MIN RM   SIZE RO TYPE MOUNTPOINTS
sda           8:0    0    80G  0 disk
├─sda1        8:1    0     1G  0 part /boot
└─sda2        8:2    0    79G  0 part /
```

or:

```text
NAME        MAJ:MIN RM   SIZE RO TYPE MOUNTPOINTS
nvme0n1     259:0    0   100G  0 disk
├─nvme0n1p1 259:1    0     1G  0 part /boot/efi
└─nvme0n1p2 259:2    0    99G  0 part /
```

These are examples only.

Your environment may look completely different.

### The tree is meaningful

Notice:

```text
sda
├─sda1
└─sda2
```

or:

```text
nvme0n1
├─nvme0n1p1
└─nvme0n1p2
```

The indentation communicates parent-child relationships.

Conceptually:

```text
DISK
 │
 ├── PARTITION
 │
 └── PARTITION
```

This is far more informative than merely listing names in `/dev`.

### Engineer Note

Do not begin storage investigation by guessing device names.

Start with:

```bash
lsblk
```

and inspect what Linux actually reports.

## 4. Read the `lsblk` Columns

Run again:

```bash
lsblk
```

Now interpret the fields.

### `NAME`

Examples:

```text
sda
sda1
nvme0n1
nvme0n1p1
vda
vda1
```

This is the block-device name.

The corresponding device node normally appears beneath:

```text
/dev/
```

So:

```text
sda
```

corresponds to:

```text
/dev/sda
```

and:

```text
nvme0n1p2
```

corresponds to:

```text
/dev/nvme0n1p2
```

---

### `MAJ:MIN`

Example:

```text
8:0
```

These are the kernel's major and minor device numbers.

Conceptually:

```text
MAJOR
→ identifies the device class/driver family used by the kernel
```

```text
MINOR
→ distinguishes devices handled within that major-number context
```

At junior level, you do not need to memorize major numbers.

Recognize that:

```text
MAJ:MIN
```

is kernel device identification information, not storage capacity.

---

### `RM`

This indicates whether the device is considered removable.

Common values:

```text
0
→ not marked removable
```

```text
1
→ marked removable
```

Do not assume:

```text
RM=0
```

means:

> physical internal hard disk.

Virtual disks and cloud volumes can also be non-removable.

---

### `SIZE`

This reports the size of the block device.

For example:

```text
100G
```

For a disk, this refers to device capacity.

For a partition, it refers to partition size.

It does **not** automatically mean the filesystem has exactly that much usable capacity.

Remember the layers:

```text
DEVICE SIZE
≠
FILESYSTEM USABLE CAPACITY
```

Filesystem metadata and storage layout can affect what `df` reports.

---

### `RO`

This indicates read-only state.

Commonly:

```text
0
→ not reported read-only
```

```text
1
→ read-only
```

A read-only state can matter during troubleshooting.

But do not conclude from this field alone why a filesystem might be mounted read-only.

That requires additional evidence.

---

### `TYPE`

This is critical.

Common values can include:

```text
disk
part
rom
loop
lvm
crypt
```

depending on the environment.

For this lab, focus mainly on:

```text
disk
```

and:

```text
part
```

A:

```text
disk
```

entry represents a disk-like block device.

A:

```text
part
```

entry represents a partition.

Do not confuse the two.

---

### `MOUNTPOINTS`

This shows where filesystems associated with block devices are mounted.

Examples:

```text
/
```

```text
/boot
```

```text
/boot/efi
```

A blank mount-point field does **not** automatically mean:

> unused disk.

It means you should investigate further before drawing conclusions.

The device could be:

- unmounted;
- part of another storage layer;
- swap;
- consumed by LVM;
- encrypted;
- otherwise used.

Do not infer "safe to use" from a blank mount point.

## 5. Distinguish Disk, Partition, Filesystem, and Mount Point

This distinction is fundamental.

Suppose you observe:

```text
/dev/sda
```

```text
/dev/sda2
```

```text
ext4
```

```text
/
```

These are not four names for the same thing.

They represent different layers.

### Disk

```text
/dev/sda
```

Possible role:

```text
block device representing a disk
```

### Partition

```text
/dev/sda2
```

Possible role:

```text
defined region of /dev/sda
```

### Filesystem

```text
ext4
```

Possible role:

```text
filesystem structure stored on the partition
```

### Mount point

```text
/
```

Role:

```text
directory where that filesystem is attached to the Linux namespace
```

The relationship is:

```text
/dev/sda
   │
   ▼
/dev/sda2
   │
   ▼
ext4
   │
   ▼
/
```

Again, this is an example topology.

Your system may instead resemble:

```text
/dev/nvme0n1
       │
       ▼
/dev/nvme0n1p2
       │
       ▼
     ext4
       │
       ▼
       /
```

or something more complex.

### Critical distinctions

Keep these locked in:

```text
DISK
≠
PARTITION
```

```text
PARTITION
≠
FILESYSTEM
```

```text
FILESYSTEM
≠
MOUNT POINT
```

```text
DEVICE SIZE
≠
DIRECTORY SIZE
```

```text
MOUNT POINT
≠
BLOCK DEVICE
```

## 6. Recognize Common Linux Storage Naming Patterns

Linux storage names depend on device technology, kernel subsystems, virtualization, and platform.

Do not assume every disk is:

```text
/dev/sda
```

### `sdX`

You may encounter:

```text
/dev/sda
/dev/sdb
/dev/sdc
```

Partitions can appear as:

```text
/dev/sda1
/dev/sda2
/dev/sdb1
```

The letters and numbers identify devices and partitions.

Do not interpret:

```text
sda
```

as permanently meaning:

> the boot disk.

Discover actual relationships.

---

### NVMe

NVMe devices commonly use names such as:

```text
/dev/nvme0n1
/dev/nvme1n1
```

Partitions add:

```text
p1
p2
p3
```

For example:

```text
/dev/nvme0n1p1
/dev/nvme0n1p2
```

Break it down conceptually:

```text
nvme0
→ NVMe controller/device context
```

```text
n1
→ namespace
```

```text
p2
→ partition 2
```

Do not expect NVMe naming to look like `sda2`.

---

### Virtual disks

Virtualized environments may expose devices such as:

```text
/dev/vda
/dev/vdb
```

with partitions such as:

```text
/dev/vda1
/dev/vda2
```

These are common in some virtualization environments.

---

### MMC storage

Systems using MMC/eMMC/SD-style storage may expose:

```text
/dev/mmcblk0
```

with partitions such as:

```text
/dev/mmcblk0p1
/dev/mmcblk0p2
```

---

### Device Mapper

You may also encounter names under:

```text
/dev/mapper/
```

These can represent higher-level block-device mappings.

You will encounter some of these concepts later when studying storage technologies such as LVM and encryption.

For now:

> If the storage tree looks more complex than disk → partition, do not guess. Read the topology.

---

## 8. Inspect Filesystem Metadata with `lsblk -f`

Run:

```bash
lsblk -f
```

This adds filesystem-related information.

Depending on the system, columns can include:

```text
NAME
FSTYPE
FSVER
LABEL
UUID
FSAVAIL
FSUSE%
MOUNTPOINTS
```

### `FSTYPE`

This may show:

```text
ext4
xfs
vfat
swap
```

or another type.

A blank field does not automatically mean:

> broken device.

The device may not directly contain a filesystem.

It might be:

- a parent disk whose partitions contain filesystems;
- part of another storage layer;
- unused;
- intentionally unformatted.

Investigate topology before concluding.

---

### `FSVER`

Where available, this describes filesystem version information.

Do not assume every filesystem exposes a useful value here.

---

### `LABEL`

A filesystem may have a human-readable label.

Example conceptually:

```text
LABEL=DATA
```

Labels can help humans identify filesystems.

But labels are not guaranteed to be unique unless administrators manage them carefully.

---

### `UUID`

A filesystem can have a UUID.

Example shape:

```text
xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```

A UUID is designed to provide a persistent identifier that is more suitable than relying solely on names such as:

```text
/dev/sdb1
```

Why?

Because device names can depend on discovery and configuration.

Later, when you study `/etc/fstab`, UUIDs become especially important.

For now, understand:

```text
DEVICE NAME
and
FILESYSTEM UUID
```

are different identifiers.

## 9. Inspect Filesystem Signatures with `blkid`

First determine whether `blkid` is available:

```bash
command -v blkid
```

If available, try:

```bash
blkid
```

Depending on your permissions and environment, output may be limited.

You may see information such as:

```text
/dev/...: UUID="..." TYPE="ext4"
```

The exact result varies.

### What `blkid` is for

`blkid` can identify block-device content attributes such as filesystem type, UUID, and label.

Conceptually:

```text
BLOCK DEVICE
     │
     ▼
filesystem/signature metadata
     │
     ▼
blkid
```

### Compare with `lsblk -f`

Run:

```bash
lsblk -f
```

Then, where available:

```bash
blkid
```

They overlap in some information but are not identical tools.

A practical junior model is:

```text
lsblk
→ topology
```

```text
lsblk -f
→ topology + filesystem-oriented fields
```

```text
blkid
→ identify filesystem/signature metadata on block devices
```

### Do not force privileged access

If `blkid` does not expose every device to your current user, do not automatically use `sudo`.

The core lab can be completed using `lsblk` and other readable system information.

## 10. Connect Block Devices to Mount Points with `findmnt`

Check whether `findmnt` is available:

```bash
command -v findmnt
```

On a standard Ubuntu system it should normally be available.

Run:

```bash
findmnt
```

This shows the mount hierarchy.

The output commonly includes information such as:

```text
TARGET
SOURCE
FSTYPE
OPTIONS
```

The key relationship is:

```text
SOURCE
→ storage/filesystem source
```

```text
TARGET
→ mount point
```

### Inspect root

Run:

```bash
findmnt /
```

This asks:

> What is mounted at `/`?

Now:

```bash
findmnt /tmp
```

Depending on your system, `/tmp` may resolve within the root filesystem or be its own mount.

Inspect your home path:

```bash
findmnt -T ~
```

The:

```text
-T
```

form asks `findmnt` to determine which mounted filesystem contains the specified path.

Now:

```bash
findmnt -T ~/linux-world-labs/JUN-037
```

This is useful because it connects:

```text
PATH
   │
   ▼
MOUNT POINT
   │
   ▼
FILESYSTEM SOURCE
```

### Compare with `df`

Run:

```bash
df -hT ~/linux-world-labs/JUN-037
```

Then:

```bash
findmnt -T ~/linux-world-labs/JUN-037
```

Then:

```bash
lsblk -f
```

You are now looking at the same storage relationship from three perspectives.

```text

```

you could inspect:

```bash

```

If it reports:

```text
nvme0n1
```

inspect:

```bash
ls -l /dev/nvme0n1
```

Use your actual device name.

You may see something resembling:

```text

```

```text

```

identifies a block-device node.

### Compare with a regular file

Create:

```bash
touch ~/linux-world-labs/JUN-037/regular-file.txt
```

Inspect:

```bash
ls -l ~/linux-world-labs/JUN-037/regular-file.txt
```

```text

```

```text

b...
```

```text

-...
```

### Critical safety rule

A block-device node is not an ordinary file to experiment with.

Never decide:

> Linux says everything is a file, so I can safely redirect data into `/dev/sda`.

Do **not** run commands such as:

```text

```

or:

```text

```

in this lab.

Writing raw data to the wrong block device can destroy:

- partition tables;
- filesystems;
- boot data;
- application data;
- entire operating systems.

Today all device inspection remains read-only.

## 13. Understand Device Size vs Filesystem Capacity

Choose the filesystem containing your lab.

Inspect its device topology:

```bash
lsblk -p -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
```

Then:

```bash
df -hT ~/linux-world-labs/JUN-037
```

You may notice that a partition/device size and filesystem capacity are not presented identically.

Why?

Because these tools are looking at different layers.

### `lsblk SIZE`

Conceptually:

```text
How large is this block device or partition?
```

### `df Size`

Conceptually:

```text
What capacity does this mounted filesystem report?
```

Those are related, but not identical concepts.

A partition might be:

```text
100G
```

while the filesystem reports somewhat different usable capacity because of:

- filesystem metadata;
- reserved space;
- unit presentation;
- storage layering;
- filesystem structure.

Therefore:

```text
BLOCK DEVICE SIZE
≠
FILESYSTEM REPORTED CAPACITY
```

Do not label a difference as an error without understanding the layers.

On Ubuntu systems using Snap packages, loop devices may appear for mounted package images.

```text
loop device
=
physical disk
```

You may also encounter:

```text
lvm
crypt
raid
rom
```

or other types depending on the environment.

### Junior rule

When you see an unfamiliar type:

1. Record it.
2. Inspect the topology.
3. Determine its parent/child relationships.
4. Do not modify it.
5. Research or escalate if the storage layer is outside your current knowledge.

A professional engineer does not turn unfamiliar storage into a guessing exercise.

## 15. Understand Removable and Read-Only Indicators

Request focused columns:

```bash
lsblk -o NAME,SIZE,TYPE,RM,RO,MOUNTPOINTS
```

### `RM`

Interpret:

```text
RM=1
```

as the device being reported as removable.

Do not translate that automatically to:

```text
USB stick
```

without further evidence.

### `RO`

Interpret:

```text
RO=1
```

as the block device being reported read-only.

Again, do not immediately infer the cause.

Read-only state can arise for different reasons depending on the storage stack.

The correct junior conclusion is:

> This block device is currently reported read-only by `lsblk`; further investigation would be required to determine why.

That is evidence-based language.

## 16. Controlled Troubleshooting: Avoid Storage Misidentification

### Failure 1 — Confusing a disk with its partition

You see:

```text
sda
└─sda1
```

and describe both as "the same disk."

That is imprecise.

A better description is:

```text
/dev/sda
→ disk-like block device
```

```text
/dev/sda1
→ partition on that device
```

---

### Failure 2 — Calling `/` a disk

This:

```text
/
```

is a mount point in the directory hierarchy.

It is not a block-device name.

Use:

```bash
findmnt /
```

to determine the source mounted there.

---

### Failure 3 — Assuming `/dev/sda1` must contain ext4

Device names do not tell you the filesystem type.

Check:

```bash
lsblk -f
```

or appropriate metadata tools.

Do not infer filesystem type from the device name.

---

### Failure 4 — Assuming a blank mount point means unused

A device with no displayed mount point could be:

- an unmounted filesystem;
- swap;
- part of LVM;
- part of encryption;
- part of RAID;
- a parent device whose child is used;
- genuinely unused.

You need more evidence.

Never interpret:

```text
MOUNTPOINTS blank
```

as:

> safe to format.

---

### Failure 5 — Assuming the largest disk is the root filesystem

A system might contain:

```text
50G OS disk
2T data disk
```

or the reverse.

Size does not identify role.

Use topology and mount evidence.

---

### Failure 6 — Assuming `/dev/sda` is always the first or boot disk

Device naming depends on the environment.

NVMe, virtualization, cloud platforms, device discovery, and storage configuration can produce different names.

Use:

```bash
lsblk
```

and:

```bash
findmnt
```

rather than assumptions.

---

### Failure 7 — Treating a device node like a harmless regular file

Reading metadata about:

```text
/dev/DEVICE
```

is different from writing data to it.

Never experiment with raw writes to a block device unless you are working in a deliberately disposable environment and the procedure explicitly requires it.

## 19. Knowledge Check and Interview Practice

### Knowledge Check

1. **What is a block device?**  
   A disk-like storage device exposed through the Linux block-device interface, allowing data to be addressed in blocks.

2. **Where are Linux device nodes commonly exposed?**  
   Under `/dev`.

3. **What command provides a tree-style view of block devices?**  
   `lsblk`.

4. **What is the difference between `TYPE=disk` and `TYPE=part` in `lsblk`?**  
   `disk` identifies a disk-like block device, while `part` identifies a partition.

5. **Is a partition the same thing as a filesystem?**  
   No. A partition is a region of a block device. A filesystem may be created on a partition or another block device.

6. **Is a filesystem the same thing as a mount point?**  
   No. The filesystem stores filesystem structures and data; a mount point is where that filesystem is attached to the directory hierarchy.

7. **What does `lsblk -f` add?**  
   Filesystem-oriented information such as type, label, UUID, and mount information where available.

8. **What does `RM` indicate in `lsblk`?**  
   Whether the device is reported as removable.

9. **What does `RO` indicate?**  
   Whether the block device is reported read-only.

10. **What is a filesystem UUID?**  
    An identifier associated with a filesystem that can provide a more persistent way to identify it than relying only on a device name.

11. **Why should you not assume `/dev/sda` is the system disk?**  
    Device naming depends on hardware, virtualization, discovery order, and storage configuration.

12. **What does `findmnt -T PATH` help determine?**  
    Which mounted filesystem contains the specified path and information about that mount.

13. **Why can `lsblk SIZE` differ from `df Size`?**  
    `lsblk` reports block-device or partition size, while `df` reports filesystem-level capacity. They represent different storage layers.

14. **Does a blank `MOUNTPOINTS` field prove a device is unused?**  
    No.

15. **Why should raw block-device writes be avoided in a discovery lab?**  
    Writing to the wrong block device can corrupt or destroy partition tables, filesystems, boot data, and user data.

### Interview Practice

**How would you list block devices on a Linux server?**

```bash
lsblk
```

For a more focused view:

```bash
lsblk -p -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
```

**What is the difference between `/dev/sda` and `/dev/sda1`?**

In a conventional `sdX` layout, `/dev/sda` represents the disk-like block device and `/dev/sda1` represents partition 1 on that device.

**How do NVMe partition names differ?**

An NVMe device may be named:

```text
/dev/nvme0n1
```

with partitions such as:

```text
/dev/nvme0n1p1
```

and:

```text
/dev/nvme0n1p2
```

**How would you determine what storage backs `/var/lib/myapp`?**

I would first inspect:

```bash
df -hT /var/lib/myapp
```

then:

```bash
findmnt -T /var/lib/myapp
```

and use:

```bash
lsblk -p -o NAME,SIZE,TYPE,FSTYPE,MOUNTPOINTS
```

to map the mount source into the block-device topology.

**What is the difference between a filesystem UUID and a device name?**

A device name such as `/dev/sdb1` identifies the current device node, while a filesystem UUID identifies the filesystem itself and is generally better suited to persistent filesystem identification.

**Does an empty mount-point field in `lsblk` mean the device can be formatted?**

No. It may be used by another storage layer, swap, encryption, LVM, RAID, or simply be unmounted. I would investigate before making any change.

**What is the difference between `lsblk`, `df`, and `findmnt`?**

`lsblk` shows block-device topology. `df` reports mounted filesystem capacity. `findmnt` shows mount relationships and can map a path to the filesystem containing it.

**Why would you avoid using `sudo` automatically during storage discovery?**

Because read-only discovery should use the least privilege necessary. If information is unavailable, I first determine whether it is actually required and whether I am authorized to access it before escalating privileges.
