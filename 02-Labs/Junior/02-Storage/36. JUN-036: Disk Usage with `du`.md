## 1. Mission: Find What Is Consuming Filesystem Space

In JUN-035, you learned how to answer:

> Which filesystem contains this path, and how much capacity does that filesystem have?

Using:

```bash
df
```

you can identify:

- filesystem size;
- used capacity;
- available capacity;
- block-use percentage;
- inode capacity;
- filesystem type;
- mount point.

But `df` does not tell you which directory is responsible for the usage.

Suppose:

```text
df -h /srv/application
```

shows:

```text
Use%
94%
```

You now know the filesystem is under substantial capacity pressure.

You still do **not** know whether the space is being consumed by:

```text
logs/
backups/
uploads/
cache/
database/
temporary files/
application releases/
something else
```

That is where:

```bash
du
```

becomes useful.

The name is traditionally understood as:

```text
disk usage
```

The core distinction is:

```text
df
│
└── How much capacity is used on the filesystem?
```

versus:

```text
du
│
└── How much filesystem space is attributed to these files/directories?
```

Together:

```text
APPLICATION CANNOT WRITE
          │
          ▼
      df -h PATH
          │
          ▼
FILESYSTEM CAPACITY PRESSURE?
          │
          ▼
         YES
          │
          ▼
      du on a
   relevant scope
          │
          ▼
WHICH PATHS ACCOUNT FOR SPACE?
```

Your mission is to investigate a controlled application tree, determine where space is being consumed, distinguish summary information from recursive detail, compare apparent size with allocated disk usage, rank large directories safely, and understand why `df` and `du` answer different questions.

### Learning objectives

By the end of this lab, you should be able to:

- explain what `du` measures;
- distinguish `du` from `df`;
- inspect directory disk usage;
- use human-readable output;
- summarize a directory with `du -s`;
- combine `-s` and `-h`;
- inspect individual file usage;
- include files with `-a`;
- control reporting depth with `--max-depth`;
- understand that `du` recursively walks directory trees;
- understand the difference between apparent size and allocated disk usage;
- use `--apparent-size`;
- understand hard-link implications for usage accounting;
- avoid unintentionally crossing filesystem boundaries with `-x`;
- combine `du` with previously learned `sort`;
- identify large first-level directories;
- investigate large paths progressively rather than scanning everything blindly;
- understand permission-denied results;
- explain important reasons `df` and `du` totals may differ;
- build a safe disk-usage investigation workflow.

### Lab boundary

This lab does not teach:

- partition management;
- filesystem creation;
- mounting;
- `/etc/fstab`;
- LVM;
- RAID;
- filesystem expansion;
- deleted-open-file diagnosis tooling;
- log rotation;
- automatic cleanup;
- production deletion policies.

The focus is:

> measure first, narrow the scope, identify consumers, verify, and do not delete blindly.

## 3. Understand What Basic `du` Reports

Run:

```bash
du application
```

You will likely see multiple lines.

Why?

Because `du` recursively examines the directory hierarchy and reports usage for directories within the requested scope.

A simplified result might resemble:

```text
...
application/logs
application/cache
application/uploads
application/backups
application/config
application
```

Your exact numbers can differ because filesystem allocation depends on the environment.

### Important distinction

`du application` does **not** mean:

> Tell me the filesystem's total capacity.

It means:

> Walk this directory tree and report disk usage attributed to objects in this scope.

The mental model is:

```text
application/
     │
     ▼
recursive traversal
     │
     ├── logs/
     ├── cache/
     ├── uploads/
     ├── backups/
     └── config/
     │
     ▼
allocated usage attributed to tree
```

### Why the default numbers can look unfamiliar

Like default `df`, default GNU `du` commonly reports values in block-oriented units.

That can make output harder to interpret quickly.

For interactive investigation, you will usually want:

```bash
du -h application
```

## 4. Make `du` Human-Readable

Run:

```bash
du -h application
```

The:

```text
-h
```

option displays human-readable units.

You may see values such as:

```text
4.0M
8.0M
16M
```

depending on filesystem allocation and rounding.

### What `-h` changes

It changes presentation.

It does not change what objects `du` examines.

Think:

```text
same disk-usage information
          │
          ├── du
          │    ↓
          │ block-oriented display
          │
          └── du -h
               ↓
           readable units
```

### Check a single subdirectory

Run:

```bash
du -h application/backups
```

Then:

```bash
du -h application/logs
```

If the directories have no nested subdirectories, each output is easy to interpret.

For larger trees, however, recursive output can become noisy.

That is where summaries matter.

---

## 5. Summarize with `du -s`

Run:

```bash
du -s application
```

The:

```text
-s
```

option requests a summary.

Instead of printing usage for every nested directory, it reports the total for the specified argument.

Now combine it with human-readable output:

```bash
du -sh application
```

This is one of the most useful `du` forms.

Read it as:

```text
-s
→ summarize
```

```text
-h
→ human-readable
```

So:

```bash
du -sh application
```

asks:

> What is the summarized allocated disk usage of this application tree?

### Summarize individual first-level directories

Run:

```bash
du -sh application/logs
```

```bash
du -sh application/cache
```

```bash
du -sh application/uploads
```

```bash
du -sh application/backups
```

```bash
du -sh application/config
```

Record:

| Directory | Reported usage |
|---|---:|
| `logs` | |
| `cache` | |
| `uploads` | |
| `backups` | |
| `config` | |

Compare the result with your prediction.

### Engineer Note

`du -sh` is excellent when you already know the path you want to summarize.

It is not enough when you need to determine **which child directory** is responsible for a large parent total.

For that, you need controlled depth.

## 6. Control the Investigation Depth

Run:

```bash
du -h --max-depth=1 application
```

This asks `du` to report the first level beneath:

```text
application/
```

plus the total for `application`.

This is extremely useful for troubleshooting.

Instead of receiving every nested path, you get a high-level breakdown.

Conceptually:

```text
application/
│
├── logs/      6M
├── cache/     8M
├── uploads/  12M
├── backups/  16M
└── config/    small
```

Your actual allocated values may differ slightly.

### Why depth-first investigation works

Suppose a real application contains:

```text
/srv/application/
├── cache/
├── data/
├── logs/
├── releases/
├── tmp/
└── uploads/
```

You do not need to inspect thousands of nested objects immediately.

Start:

```text
LEVEL 1
   ↓
Which major branch is large?
   ↓
ENTER THAT BRANCH
   ↓
LEVEL 2
   ↓
Which child is large?
   ↓
CONTINUE UNTIL ROOT CAUSE SCOPE IS SMALL
```

This is much better than flooding the terminal with the entire directory tree.

### Compare deeper reporting

Run:

```bash
du -h --max-depth=2 application
```

Compare the amount of detail with:

```bash
du -h --max-depth=1 application
```

More depth provides more detail.

More detail is useful only when you need it.

The goal is:

```text
broad enough to find the large branch
+
narrow enough to remain understandable
```

## 7. Inspect Files as Well as Directories

By default, the output you commonly focus on from `du` is directory-oriented.

Use:

```text
-a
```

to include files in the reporting.

Run:

```bash
du -ah application/backups
```

You should see the backup file and the containing directory.

Now:

```bash
du -ah application/logs
```

You should see individual log files as well as the directory total.

### When `-a` is useful

Suppose you have already narrowed the investigation to:

```text
application/backups/
```

and need to know which files account for the usage.

At that point:

```bash
du -ah application/backups
```

can be useful.

### When `-a` is dangerous operationally

Not because the command is destructive—it is not—but because the output can become enormous.

Running:

```text
du -ah /
```

on a large system can:

- traverse huge directory trees;
- produce overwhelming output;
- encounter many permission errors;
- consume time and I/O;
- include irrelevant filesystems;
- make the actual evidence harder to see.

Use the narrowest useful scope.

## 8. Rank Large Paths with `sort`

You learned `sort` in JUN-029.

Now combine it with `du`.

Run:

```bash
du -h --max-depth=1 application
```

The output may not be ordered by size.

Pipe it to:

```bash
du -h --max-depth=1 application | sort -h
```

Here:

```text
sort -h
```

understands human-readable size suffixes.

This should order entries from smaller to larger.

To reverse the order:

```bash
du -h --max-depth=1 application | sort -hr
```

Now the largest entries should appear first.

### Why `sort -n` is not ideal here

Human-readable values can contain:

```text
K
M
G
T
```

Plain numeric sorting does not interpret those units the same way as:

```text
sort -h
```

Use a sorting mode that matches the data format.

### Investigation pattern

A useful pattern is:

```bash
du -h --max-depth=1 TARGET | sort -hr
```

Conceptually:

```text
TARGET
  ↓
measure first-level usage
  ↓
sort by human-readable size
  ↓
largest branch appears first
  ↓
investigate that branch
```

For your lab:

```bash
du -h --max-depth=1 application | sort -hr
```

You should expect:

```text
application
```

itself to appear near or at the top because it represents the total tree.

Among its child directories, determine which is largest.

Do not mistake the parent total for an additional independent consumer.

## 9. Drill Down Instead of Searching Everything

Suppose your first command is:

```bash
du -h --max-depth=1 application | sort -hr
```

and:

```text
application/backups
```

is the largest child directory.

Your next step should be focused:

```bash
du -ah application/backups | sort -hr
```

You have moved from:

```text
WHOLE APPLICATION
       ↓
largest branch
       ↓
BACKUPS
       ↓
individual files
```

This is a professional investigation pattern.

Do not repeatedly run increasingly broad commands.

Narrow the scope as evidence develops.

### The reasoning model

```text
SYMPTOM
  ↓
df identifies affected filesystem
  ↓
choose relevant application scope
  ↓
du --max-depth=1
  ↓
largest child
  ↓
du inside that child
  ↓
largest object
  ↓
verify what it is
  ↓
determine whether it is expected
```

Notice the final step:

```text
largest object
≠
automatically safe to delete
```

A 200 GB database file may be large because it is the production database.

Size is evidence.

It is not a deletion policy.

## 10. Apparent Size vs Allocated Disk Usage

This is one of the most important concepts in the lab.

Create a sparse training file:

```bash
truncate -s 64M application/sparse-test.img
```

Inspect it:

```bash
ls -lh application/sparse-test.img
```

You should see an apparent size around:

```text
64M
```

Now ask `du` for allocated disk usage:

```bash
du -h application/sparse-test.img
```

The reported allocated usage may be much smaller than 64 MiB.

Now run:

```bash
du -h --apparent-size application/sparse-test.img
```

This should report the apparent size.

### What happened?

A sparse file can have a large logical length without having physical storage blocks allocated for every byte in that range.

Conceptually:

```text
APPARENT FILE LENGTH
████████████████████████████████
64 MiB logical size
```

while allocated storage may resemble:

```text
ALLOCATED BLOCKS
██
much smaller
```

This gives you two different questions.

### Allocated disk usage

```bash
du -h FILE
```

asks about filesystem space allocated to the object.

### Apparent size

```bash
du -h --apparent-size FILE
```

asks about the logical length represented by the file.

### Compare with `ls`

Run:

```bash
ls -lh application/sparse-test.img
```

Then:

```bash
du -h application/sparse-test.img
```

Then:

```bash
du -h --apparent-size application/sparse-test.img
```

Record:

```text
ls apparent size:

du allocated usage:

du --apparent-size:
```

### Why this matters

If you assume:

```text
ls size
=
allocated disk consumption
```

you can misinterpret sparse files.

Sparse files can appear in:

- virtual disk images;
- database files;
- VM storage;
- application data;
- test artifacts.

At junior level, the important distinction is:

```text
APPARENT SIZE
≠
ALLOCATED DISK USAGE
```

## 11. Understand Hard Links and `du`

You learned hard links in JUN-034.

Now connect them to disk-usage accounting.

Create:

```bash
dd if=/dev/zero of=application/hardlink-source.dat bs=1M count=4 status=none
```

Create a hard link:

```bash
ln application/hardlink-source.dat application/hardlink-second-name.dat
```

Inspect:

```bash
ls -li application/hardlink-source.dat application/hardlink-second-name.dat
```

They should share an inode.

Now run:

```bash
du -h application/hardlink-source.dat application/hardlink-second-name.dat
```

GNU `du` normally counts a hard-linked file's allocated blocks only once when the same inode is encountered during a single invocation.

Why?

Because these are not two independent 4 MiB data objects.

They are two names for the same underlying inode/data.

Conceptually:

```text
hardlink-source.dat ─────┐
                         │
                         ▼
                       inode
                         │
                         ▼
                     allocated data
                         ▲
                         │
hardlink-second-name ────┘
```

If a tool naïvely counted the same inode twice, it could overstate actual allocated usage.

### Important lesson

Path count is not always data-object count.

This is another reason filesystem accounting requires more than simply adding the apparent sizes of every pathname you see.

## 12. Stay on One Filesystem When Required

A directory tree can contain mount points for other filesystems.

If `du` recursively walks into those paths, your measurement can include usage from multiple filesystems.

GNU `du` provides:

```text
-x
```

or:

```text
--one-file-system
```

to remain on one filesystem.

The form is:

```bash
du -xh --max-depth=1 PATH
```

Conceptually:

```text
START PATH
    │
    ▼
walk directory tree
    │
    ├── same filesystem → continue
    │
    └── different filesystem → do not descend
```

### Why this matters

Suppose:

```text
/application/
├── logs/
├── data/
└── archive/
```

but:

```text
/application/archive
```

is actually a mount point for another filesystem.

Without filesystem-boundary control, a recursive `du` can include the mounted archive storage.

That may be exactly what you want.

Or it may completely distort the question you are trying to answer.

The requirement determines the choice.

### Junior rule

When investigating usage on **one specific filesystem**, consider:

```bash
du -x ...
```

so your directory traversal does not unintentionally include mounted filesystems beneath the path.

You will learn mounts in detail later.

For now, understand the boundary.

## 13. Permission Errors Are Evidence

On real systems, you may run `du` against a directory tree and encounter:

```text
Permission denied
```

Do not automatically rerun:

```text
sudo du ...
```

First ask:

- Is this path actually relevant?
- Am I authorized to inspect it?
- Can I narrow the investigation?
- Does the inaccessible subtree mean my total is incomplete?
- Is privileged access genuinely required?

### Why this matters

Suppose:

```bash
du -sh /some/application
```

cannot inspect one large protected child directory.

The reported result may not represent the complete tree.

That is important evidence.

Do not report:

> `/some/application` uses exactly X.

if significant portions could not be inspected.

A more accurate statement is:

> The accessible portion measured X, but the traversal encountered inaccessible paths, so the result may be incomplete.

### Professional habit

Permission errors should affect your confidence in the result.

Do not hide them merely to produce a cleaner number.

## 14. Connect `df` and `du` Correctly

Run:

```bash
df -h application
```

This reports the filesystem containing:

```text
application/
```

Now:

```bash
du -sh application
```

These numbers answer completely different questions.

### `df`

Conceptually:

```text
FILESYSTEM
├── application/
├── other-user-data/
├── operating-system-data/
├── caches/
├── logs/
├── deleted/open allocations
├── filesystem metadata
└── other content
```

`df` reports filesystem-level allocation/capacity.

### `du`

When run against:

```text
application/
```

it walks the visible filesystem objects under that path and reports usage attributed to that scope.

Therefore:

```text
df used space
```

should not be expected to equal:

```text
du -sh application
```

unless your measurement scopes and accounting happen to line up—which they normally do not for a single application directory.

### Even broad `du` and `df` can differ

There are additional reasons the numbers may differ, including:

- deleted files still held open by running processes;
- filesystem metadata;
- reserved filesystem space;
- inaccessible paths;
- mounted filesystems and traversal choices;
- hard-link accounting;
- sparse files and apparent-size confusion;
- filesystem-specific accounting behavior.

At this stage, you do not need to diagnose every advanced discrepancy.

You do need to know:

```text
df
and
du
```

are not interchangeable.

## 15. The Deleted-but-Open File Concept

This lab does not introduce the advanced tools used to investigate open file descriptors.

But you need to understand one important concept because it explains a classic `df`/`du` discrepancy.

Imagine:

```text
application.log
```

is open by a running process.

The file is removed from the directory.

Its pathname disappears.

A directory traversal may no longer see that pathname.

But the running process may still hold the underlying file open.

Conceptually:

```text
PATHNAME
application.log
     │
     X removed
```

while:

```text
RUNNING PROCESS
      │
      ▼
open file reference
      │
      ▼
inode/data still allocated
```

Until the process releases the open file, storage may remain allocated.

That can create a situation where:

```text
df
→ still reports filesystem space in use
```

while:

```text
du
→ cannot attribute that space to the removed pathname
```

### Important boundary

Do not try to reproduce this against system services in this junior lab.

Do not restart services.

Do not delete active logs.

The lesson is conceptual:

> A missing pathname does not always mean its allocated storage has already been released.

You will investigate file descriptors and production incidents later in Linux World.

## 16. Common Mistakes and Controlled Failures

### Mistake 1 — Running `du` against `/` immediately

A filesystem is reported as full, so you run:

```text
du -ah /
```

This can create huge, noisy output and traverse areas unrelated to the incident.

Better approach:

```text
affected filesystem
      ↓
relevant application or major directory
      ↓
controlled depth
      ↓
largest branch
      ↓
drill down
```

---

### Mistake 2 — Confusing `df` with `du`

This:

```bash
df -h application
```

does not tell you the size of `application`.

This:

```bash
du -sh application
```

does not tell you the filesystem's total capacity.

Use each tool for its actual question.

---

### Mistake 3 — Assuming the largest directory is the problem

Suppose:

```text
backups/
```

is the largest directory.

That proves it consumes significant space.

It does not prove:

- it is unexpected;
- it is unnecessary;
- it can be deleted;
- it caused the incident;
- its retention policy permits removal.

Measure first.

Interpret second.

Change only after understanding purpose and policy.

---

### Mistake 4 — Using `ls -lh` as allocated disk usage

For ordinary files, apparent size and allocated usage may often appear close.

Sparse files show why that assumption is unsafe.

Compare:

```bash
ls -lh application/sparse-test.img
```

with:

```bash
du -h application/sparse-test.img
```

The tools are reporting different concepts.

---

### Mistake 5 — Ignoring hard links

Two pathnames can refer to the same inode.

Do not assume:

```text
two filenames
=
two independent allocations
```

Check inode relationships when relevant.

---

### Mistake 6 — Crossing filesystem boundaries unintentionally

If a tree contains mounted filesystems, recursive `du` can descend into them unless you constrain it.

When the question is limited to one filesystem, consider:

```text
-x
```

---

### Mistake 7 — Hiding permission failures

If `du` could not read significant portions of a tree, your result may be incomplete.

Do not present incomplete evidence as exact.

---

### Mistake 8 — Deleting before understanding

Never turn:

```text
largest file
```

directly into:

```text
rm largest-file
```

First determine:

- what created it;
- whether it is active;
- whether it is required;
- whether it is recoverable;
- whether retention rules apply;
- whether another system depends on it;
- whether deletion would actually release the expected space.

## 17. A Safe Disk-Usage Investigation Workflow

When a filesystem-capacity alert occurs, use the tools in sequence.

### Step 1 — Identify the affected path

Example:

```text
/srv/application/data
```

### Step 2 — Confirm filesystem pressure

From JUN-035:

```bash
df -hT /srv/application/data
```

and:

```bash
df -i /srv/application/data
```

Ask:

```text
block pressure?
inode pressure?
which filesystem?
which mount point?
```

### Step 3 — Choose an appropriate `du` scope

Do not automatically use `/`.

Choose the narrowest useful directory that could explain the usage.

### Step 4 — Inspect first-level usage

```bash
du -xh --max-depth=1 TARGET
```

If ranking helps:

```bash
du -xh --max-depth=1 TARGET | sort -hr
```

### Step 5 — Identify the largest relevant child

For example:

```text
TARGET/backups
```

### Step 6 — Drill down

```bash
du -xh --max-depth=1 TARGET/backups | sort -hr
```

or, once the scope is small:

```bash
du -ah TARGET/backups | sort -hr
```

### Step 7 — Verify the object

Use already learned tools such as:

```bash
ls -lh PATH
```

```bash
stat PATH
```

```bash
file PATH
```

if `file` is available and appropriate in your environment.

Do not act solely on size.

### Step 8 — Determine purpose before remediation

Ask:

```text
Who owns this data?

What process/application creates it?

Is the growth expected?

Is there a retention policy?

Is it safe to remove?

Would deletion actually solve the problem?

Should the real fix be rotation, retention, capacity expansion, or application repair?
```

Those remediation decisions extend beyond this junior `du` lab.

## 18. Challenge Mode — Find the Space Consumer

You receive this report:

> The filesystem containing an application is consuming more space than expected. Determine where the application's allocated disk usage is concentrated. Do not delete anything.

## 19. Knowledge Check and Interview Practice

### Knowledge Check

1. **What does `du` primarily report?**  
   Disk usage attributed to files and directory trees within the scope it traverses.

2. **What is the difference between `df` and `du`?**  
   `df` reports filesystem-level capacity and usage. `du` walks filesystem objects and reports usage attributed to files and directories.

3. **What does `du -h` do?**  
   Displays usage in human-readable units.

4. **What does `du -s` do?**  
   Produces a summary for each specified argument rather than recursively printing all directory totals.

5. **What does `du -sh directory` provide?**  
   A human-readable summarized disk-usage value for that directory tree.

6. **What does `du -a` do?**  
   Includes files as well as directory totals in the output.

7. **What does `--max-depth=1` help you do?**  
   View a high-level breakdown of a directory's immediate children without printing the entire nested tree.

8. **Why is `du -h --max-depth=1 PATH | sort -hr` useful?**  
   It provides a human-readable first-level usage breakdown ordered from largest to smallest.

9. **What is apparent size?**  
   The logical length of file content as represented by the file, which can differ from the amount of filesystem storage actually allocated.

10. **Why can a sparse file's apparent size be much larger than its allocated disk usage?**  
    Large logical regions can exist without corresponding storage blocks being allocated for every byte.

11. **What does `du --apparent-size` change?**  
    It reports apparent size rather than the normal allocated-disk-usage view.

12. **Why can hard links affect disk-usage accounting?**  
    Multiple pathnames can refer to the same inode and underlying allocated data, so counting each pathname independently could double-count the same allocation.

13. **What does `du -x` do?**  
    Restricts traversal to one filesystem.

14. **Why can `du` output be incomplete?**  
    Permission errors or inaccessible paths can prevent it from measuring parts of the requested tree.

15. **Why might `df` and `du` appear to disagree?**  
    They use different accounting perspectives, and differences can also involve deleted-but-open files, filesystem metadata, reserved space, inaccessible paths, mounted filesystems, hard links, and other filesystem behavior.

### Interview Practice

**What is the difference between `df -h` and `du -sh`?**

`df -h` reports capacity and usage for filesystems. `du -sh` summarizes allocated disk usage attributed to a specified file or directory tree.

**How would you find which first-level directory under `/srv/app` is using the most space?**

A common investigation command is:

```bash
du -xh --max-depth=1 /srv/app | sort -hr
```

The `-x` keeps the traversal on one filesystem, `--max-depth=1` limits the breakdown to the first level, and `sort -hr` orders human-readable sizes from largest to smallest.

**Why not start with `du -ah /`?**

It is unnecessarily broad, can traverse a huge number of files, may cross filesystem boundaries, can generate overwhelming output, and may create avoidable I/O. I would begin with the affected filesystem and the narrowest relevant application scope.

**Why can `ls -lh` and `du -h` show different sizes for a file?**

`ls -lh` commonly shows the file's apparent/logical size, while `du -h` normally reports allocated filesystem usage. Sparse files make the distinction especially visible.

**What does `du -x` protect against?**

It prevents `du` from descending into directories that belong to other filesystems beneath the starting path.

**A directory is the largest one in `du`. Is it safe to delete?**

No. Size alone does not establish whether data is unnecessary or safe to remove. I would identify its purpose, owner, producing process, retention requirements, dependencies, and recovery implications first.

**Why can `df` show more used space than you can account for with visible files in `du`?**

One possible reason is a deleted file still held open by a running process. Other reasons include filesystem metadata, reserved space, inaccessible paths, scope differences, and filesystem accounting behavior. I would not assume a single cause without further evidence.

**How would you approach a disk-full incident?**

I would identify the affected path, use `df` to confirm the relevant filesystem's block and inode capacity, use a controlled `du` scope to identify major consumers, drill down progressively, verify suspicious objects, and only then determine an appropriate remediation.
