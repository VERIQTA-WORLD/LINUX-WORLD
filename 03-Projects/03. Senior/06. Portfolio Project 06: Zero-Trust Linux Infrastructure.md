# 01. Project Title

## Zero-Trust Linux Infrastructure

Build a segmented Linux environment in which access is never granted merely because a machine or user happens to be "inside the network."

The project implements the working principle:

```text
Never trust based only on network location.

Verify identity.
Verify authentication.
Verify source.
Verify requested access.
Grant minimum required privilege.
Record security-relevant actions.
Continuously verify controls.
Revoke access when trust changes.
```

You will build:

```text
Administrator
      │
      │ WireGuard
      ▼
┌──────────────────┐
│ Access Gateway   │
│ gateway01        │
└────────┬─────────┘
         │
         │ controlled management path
         ▼
┌─────────────────────────────────────┐
│        MANAGEMENT NETWORK           │
│                                     │
│ idm01        log01                  │
└───────────┬─────────────────────────┘
            │
      controlled flows
            │
     ┌──────┴─────────┐
     ▼                ▼
┌──────────┐     ┌──────────┐
│ APP ZONE │     │ DATA ZONE│
│ app01    │────►│ db01     │
│ app02    │     │          │
└──────────┘     └──────────┘
```

The important feature is not the diagram.

It is the **policy** governing every arrow.

By completion, you must be able to prove:

```text
Admin workstation → gateway
ALLOWED

Unapproved workstation → management SSH
DENIED

Gateway → application SSH
ALLOWED for authorized administrators

Admin workstation → application SSH directly
DENIED

Application → database PostgreSQL
ALLOWED

Application → arbitrary database ports
DENIED

Database → application management services
DENIED

Application user → root
DENIED

Authorized operator → approved sudo command
ALLOWED

Authorized operator → unrestricted sudo
DENIED

Disabled user → infrastructure
DENIED

Revoked WireGuard peer → management path
DENIED

Unapproved process action → AppArmor
DENIED and logged

Security-relevant activity → audit evidence
RECORDED
```

This is what turns the project from hardening into **zero-trust-style infrastructure enforcement**.

# 02. Project Scenario

A company operates Linux infrastructure containing:

* public-facing applications;
* databases;
* administrative systems;
* sensitive credentials;
* customer data;
* privileged accounts.

Historically, administrators treated the internal network as trusted.

The old model looked like this:

```text
Internet
   │
Firewall
   │
   ▼
"Trusted Internal Network"
   │
   ├── SSH everywhere
   ├── broad subnet firewall rules
   ├── shared admin accounts
   ├── large sudo permissions
   ├── applications talking freely
   └── weak audit visibility
```

That model creates a serious problem.

If one internal system is compromised, the attacker may be able to move laterally.

Example:

```text
Compromise APP01
      │
      ▼
Discover DB01
      │
      ▼
Connect to SSH
      │
      ▼
Steal credential
      │
      ▼
Become privileged
      │
      ▼
Move to APP02
      │
      ▼
Reach management infrastructure
```

The organization therefore adopts a stronger design.

Network location alone is no longer sufficient evidence of trust.

The new questions become:

```text
Who are you?

How did you authenticate?

Which device/path are you using?

Which system are you requesting?

Which service are you requesting?

Are you authorized for this resource?

Do you need privileged access?

Which exact privileged action do you need?

Should this connection exist at all?

Can the action be audited?

Can access be revoked quickly?

Can the system prove its controls are still operating?
```

# 08. Architecture

## 8.1 Trust boundaries

Define four trust zones:

```text
ZONE 1
Administrative endpoint

ZONE 2
Management plane

ZONE 3
Application plane

ZONE 4
Data plane
```

Cross-zone communication requires an explicit reason.

---

## 8.2 Default-deny model

The conceptual network policy is:

```text
DENY everything

ALLOW only documented flows
```

Approved flows:

| Source        | Destination | Service    | Reason                     |
| ------------- | ----------- | ---------- | -------------------------- |
| admin01 VPN   | gateway01   | WireGuard  | secure admin entry         |
| gateway01     | app01       | SSH        | application administration |
| gateway01     | app02       | SSH        | application administration |
| gateway01     | db01        | SSH        | database administration    |
| app01         | db01        | PostgreSQL | application database       |
| app02         | db01        | PostgreSQL | application database       |
| managed hosts | log01       | logging    | security telemetry         |

Everything else requires explicit justification.

---

## 8.3 Identity is not IP address

An IP address is useful policy context.

It is not human identity.

This:

```text
10.99.0.10
```

does not mean:

```text
Alice
```

WireGuard authenticates possession of peer key material.

SSH authenticates the administrative identity.

Linux authorization determines permitted actions.

These controls complement rather than replace one another.

---

## 8.4 Defense in depth

```text
WireGuard
    │
    ▼
Network policy
    │
    ▼
Host firewall
    │
    ▼
OpenSSH
    │
    ▼
User/group policy
    │
    ▼
sudo
    │
    ▼
AppArmor
    │
    ▼
auditd/journal
```

Compromise of one layer should not automatically eliminate every other boundary.

# 12. Step-by-Step Implementation

## 12.1 Create security requirements

```bash
cat > requirements/SECURITY-REQUIREMENTS.md <<'EOF'
# Zero-Trust Security Requirements

ZT-01 Network location alone must not grant administrative access.

ZT-02 Administrative entry must use an authenticated encrypted path.

ZT-03 Direct administrative SSH from the external/admin network to workload
servers must be denied.

ZT-04 Root SSH login must be disabled.

ZT-05 Password-only administrative SSH must be disabled after key access has
been validated.

ZT-06 Administrative identities must be individual identities.

ZT-07 Shared administrator accounts must not be used.

ZT-08 Privileged access must follow least privilege.

ZT-09 Application servers may access only required database services.

ZT-10 Database servers must not expose unnecessary services to application
networks.

ZT-11 Host firewalls must use default-deny inbound policy.

ZT-12 Security-relevant actions must be auditable.

ZT-13 Security logs must be retained outside workload hosts.

ZT-14 Application confinement must be verified with AppArmor.

ZT-15 Access revocation must be testable.

ZT-16 VPN peer revocation must be testable.

ZT-17 SSH-key revocation must be testable.

ZT-18 sudo-policy revocation must be testable.

ZT-19 Firewall-policy violations must be testable.

ZT-20 Security controls must have automated verification.

ZT-21 Verification failure must produce a non-zero exit status.

ZT-22 Secrets and private keys must never be committed to Git.

ZT-23 Every allowed network flow must have a documented business purpose.

ZT-24 Every privileged command must have a documented operational purpose.

ZT-25 Break-glass access must be separately documented and controlled.

ZT-26 Security policy changes must be validated before deployment.

ZT-27 Security policy changes must have rollback procedures.

ZT-28 The project must distinguish prevention, detection and recovery controls.

ZT-29 The final architecture must document residual risk.

ZT-30 No security outcome may be claimed without verification evidence.
EOF
```

## 12.12 Harden SSH safely

Before changing SSH configuration:

```bash
sudo cp \
  /etc/ssh/sshd_config \
  /etc/ssh/sshd_config.pre-zero-trust
```

Create drop-in:

```bash
sudo nano \
  /etc/ssh/sshd_config.d/60-zero-trust.conf
```

Add:

```text
PermitRootLogin no
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitEmptyPasswords no
X11Forwarding no
AllowAgentForwarding no
```

Validate:

```bash
sudo sshd -t
```

If validation fails:

```text
STOP.
```

Do not reload SSH.

Investigate the reported configuration error.

If validation succeeds:

```bash
sudo systemctl reload ssh
```

Keep the existing session open.

Open a second terminal.

Test key login.

Only after successful second-session verification should the original session be closed.

# 14. Automation

## 14.1 Build security-control verification script

On ADMIN01:

```bash
cat > scripts/verification/verify-zero-trust.sh <<'EOF'
#!/usr/bin/env bash
set -u

PASS=0
FAIL=0

pass() {
    printf '[PASS] %s\n' "$1"
    PASS=$((PASS + 1))
}

fail() {
    printf '[FAIL] %s\n' "$1"
    FAIL=$((FAIL + 1))
}

expect_open() {
    local host="$1"
    local port="$2"
    local name="$3"

    if nc -z -w 3 "$host" "$port" >/dev/null 2>&1; then
        pass "$name"
    else
        fail "$name"
    fi
}

expect_closed() {
    local host="$1"
    local port="$2"
    local name="$3"

    if nc -z -w 3 "$host" "$port" >/dev/null 2>&1; then
        fail "$name"
    else
        pass "$name"
    fi
}

echo "VERIQTA Zero-Trust Verification"
echo "UTC: $(date -u +"%Y-%m-%dT%H:%M:%SZ")"
echo

expect_open \
    10.99.0.1 \
    22 \
    "Gateway SSH reachable through VPN"

expect_closed \
    10.30.30.11 \
    22 \
    "DB SSH not directly reachable from ADMIN01"

echo
echo "Passed: ${PASS}"
echo "Failed: ${FAIL}"

if (( FAIL > 0 )); then
    exit 1
fi

exit 0
EOF
```

Make executable:

```bash
chmod +x \
  scripts/verification/verify-zero-trust.sh
```

Run:

```bash
./scripts/verification/verify-zero-trust.sh
```

A failed security control must produce a non-zero result.

# 15. Security

## 15.1 Authentication hierarchy

Administrative access requires:

```text
Possession of WireGuard peer key
        +
Permitted VPN peer
        +
Network policy
        +
SSH identity
        +
Authorized account
        +
Destination policy
```

Privileged actions additionally require:

```text
sudo authorization
```

Application actions may additionally be constrained by:

```text
AppArmor
```

---

## 15.2 Optional MFA enhancement

For a stronger physical-authenticator implementation, OpenSSH on Ubuntu supports FIDO/U2F-backed SSH keys.

Where hardware is available:

```bash
ssh-keygen \
  -t ed25519-sk \
  -f ~/.ssh/alice_fido
```

If the authenticator does not support Ed25519 security-key credentials, use the compatible security-key type supported by the device.

This project does not pretend a hardware-token test was completed unless a real compatible authenticator was used.

---

## 15.3 Break-glass access

Create a local emergency account only after documenting its purpose.

Example:

```bash
sudo adduser breakglass
```

Do not make it part of ordinary daily administration.

Document:

```text
Where credentials are stored
Who may authorize use
When it may be used
How use is detected
How credentials are rotated afterward
How activity is reviewed
```

For a local lab, console-only emergency access is preferable to quietly creating another broadly reachable SSH administrator.

---

## 15.4 Secret handling

Never commit:

```text
WireGuard private keys
SSH private keys
passwords
TOTP secrets
recovery codes
private certificates
API tokens
```

Search repository:

```bash
grep -RniE \
  'PRIVATE KEY|password|secret|token' \
  . \
  --exclude-dir=.git
```

Review every result.

---

## 15.5 Principle of minimum exposure

Check listening services:

```bash
sudo ss -lntup
```

For each listener ask:

```text
What process owns it?

Why is it listening?

Which interface?

Which clients need it?

Does the firewall permit only those clients?

Can it bind to a narrower address?

Can it be removed?
```

Unknown listeners are not automatically malicious.

But they require explanation.
