# 01. Project Title

## Linux Performance Engineering Platform

Build a controlled Linux performance engineering laboratory where you deliberately create and investigate:

* CPU saturation;
* CPU contention;
* scheduler pressure;
* memory pressure;
* swapping;
* OOM risk;
* storage latency;
* storage queueing;
* random I/O pressure;
* sequential I/O pressure;
* network throughput limitations;
* network connection problems;
* process-level bottlenecks;
* system-wide resource contention.

The portfolio must demonstrate this engineering chain:

```text
BASELINE
   ↓
REPRODUCE PROBLEM
   ↓
OBSERVE SYMPTOM
   ↓
MEASURE
   ↓
FORM HYPOTHESES
   ↓
TEST HYPOTHESES
   ↓

   ↓
CHANGE ONE THING
   ↓
RE-MEASURE
   ↓
COMPARE
   ↓

   ↓
ROLL BACK IF NECESSARY
   ↓
```

The goal is not:

```text

```

The goal is to be able to explain:

> The workload became slower, these measurements prove where time was being lost, these competing explanations were eliminated, this resource became the limiting factor, this change addressed that specific bottleneck, and these before/after measurements demonstrate the result.

# 02. Project Scenario

Your organization operates a Linux-hosted application.

Users report:

```text
"The application is slow."
```

That statement tells you almost nothing.

Operations teams provide conflicting explanations:

```text
"The CPU is overloaded."

"We need more RAM."

"The disk is slow."

"The network is saturated."

"Linux is swapping."

"The database is probably the problem."

"We should increase some kernel parameters."

"Let's restart the server."
```

None has supplied evidence.

Your assignment is to investigate the system as a performance engineer.

You are prohibited from starting with random tuning.

You must establish:

1. what normal performance looks like;
2. what workload is being measured;
3. what changed;
4. which resource is saturated;
5. whether saturation actually affects the workload;
6. which process or subsystem is responsible;
7. whether the problem is utilization, contention, latency, queueing, errors, or capacity;
8. which optimization addresses the identified bottleneck;
9. whether the optimization improved the workload;
10. whether the change created a regression elsewhere.

# 08. Architecture

## 8.1 Performance model

For every investigation use four questions:

### What is the workload?

Example:

```text
100 HTTP requests
10 concurrent clients
1 GiB sequential write
4 KiB random reads
30-second CPU workload
60-second network transfer
```

### What is the metric?

Example:

```text
requests/second
mean latency
p95 latency
CPU utilization
run queue
IOPS
await
throughput
retransmissions
PSI stall percentage
```

### What is the bottleneck hypothesis?

Example:

```text
CPU saturation causes request queueing.
```

### What result would falsify the hypothesis?

Example:

```text
CPU remains mostly idle while request latency increases.
```

That last question prevents confirmation bias.

---

## 8.2 USE-style investigation

For each physical resource investigate:

```text
UTILIZATION
SATURATION
ERRORS
```

Examples:

### CPU

```text
Utilization → %user / %system / %idle
Saturation  → run queue / CPU PSI
Errors      → hardware/kernel errors where relevant
```

### Memory

```text
Utilization → working set / available memory
Saturation  → reclaim / swapping / memory PSI
Errors      → OOM events / allocation failures
```

### Storage

```text
Utilization → device activity
Saturation  → queues / latency / I/O PSI
Errors      → kernel/device/filesystem errors
```

### Network

```text
Utilization → throughput
Saturation  → queues / dropped packets / retransmission effects
Errors      → interface/TCP errors
```

---

## 8.3 Scientific tuning rule

Never do this:

```text
change swappiness
change dirty ratios
change scheduler settings
increase buffers
change application workers
restart service
run benchmark
```

You would not know which change mattered.

Instead:

```text
baseline
   ↓
one hypothesis
   ↓
one controlled change
   ↓
same workload
   ↓
same measurement
   ↓
compare
```

## 12.2 Capture live performance snapshot

Create:

```bash
cat > scripts/capture-performance.sh <<'EOF'

set -euo pipefail

LABEL="${1:-capture}"
```

# 14. Automation

## 14.1 Automated comparison utility

Create:

```bash
cat > scripts/compare.py <<'EOF'
#!/usr/bin/env python3

import argparse


def percentage_change(before, after):
    if before == 0:
        return None
    return ((after - before) / before) * 100.0


def main():
    parser = argparse.ArgumentParser(
        description="Compare before and after performance measurements."
    )

    parser.add_argument("--metric", required=True)
    parser.add_argument("--before", required=True, type=float)
    parser.add_argument("--after", required=True, type=float)
    parser.add_argument(
        "--lower-is-better",
        action="store_true",
        help="Interpret lower values as improvement, for example latency.",
    )

    args = parser.parse_args()

    change = percentage_change(args.before, args.after)

    print(f"Metric: {args.metric}")
    print(f"Before: {args.before}")
    print(f"After:  {args.after}")

    if change is None:
        print("Percentage change: undefined because baseline is zero")
        return

    print(f"Percentage change: {change:.2f}%")

    improved = (
        args.after < args.before
        if args.lower_is_better
        else args.after > args.before
    )

    print(f"Direction: {'improved' if improved else 'not improved'}")


if __name__ == "__main__":
    main()
EOF
```

Make executable:

```bash
chmod +x scripts/compare.py
```

Example:

```bash
./scripts/compare.py \
  --metric p95_latency_ms \
  --before 250 \
  --after 175 \
  --lower-is-better
```

Do not use made-up numbers in the final portfolio.

Use your measurements.

## Architecture decision

Create:

```bash
cat > adrs/ADR-001-MEASURE-BEFORE-TUNING.md <<'EOF'
# ADR-001 — Measure Before Tuning

## Status

Accepted.

## Context

Linux exposes many tunable parameters, but changing configuration without
evidence makes performance investigations difficult to reproduce and can
introduce regressions.

## Decision

No persistent performance tuning is applied until a reproducible workload and
baseline measurement exist.

Each tuning experiment changes one primary variable at a time.

## Alternatives

### Apply common performance tuning recommendations immediately

Rejected because generic tuning may not address the actual workload bottleneck.

### Change multiple parameters together

Rejected because the effect of each individual change cannot be isolated.

## Consequences

Investigations take longer initially.

However, changes become measurable, reversible and defensible.
EOF
```

---

## ADR 002

```bash
cat > adrs/ADR-002-PSI.md <<'EOF'
# ADR-002 — Pressure Stall Information

## Status

Accepted.

## Decision

CPU, memory and I/O PSI measurements are collected alongside conventional
utilization metrics.

## Reason

Utilization alone does not describe how much workload time is lost waiting for
constrained resources.

## Consequence

Performance investigations consider both resource consumption and workload
stalling.
EOF
```

---

## ADR 003

```bash
cat > adrs/ADR-003-REPRODUCIBLE-WORKLOADS.md <<'EOF'
# ADR-003 — Reproducible Workloads

## Status

Accepted.

## Decision

Before/after comparisons must use equivalent workload parameters.

## Reason

Changing both workload and configuration prevents meaningful comparison.

## Consequence

Experiment commands, duration, concurrency and dataset sizes must be recorded.
EOF
```
