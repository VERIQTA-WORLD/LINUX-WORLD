# 02. Project Scenario

Your organization operates several Linux servers.

Current administration looks like this:

```text
WEB01
├── local alice
├── local david
├── local bob
├── SSH keys
└── local sudoers

WEB02
├── local alice
├── local david
├── SSH keys
└── local sudoers

DB01
├── local bob
├── local carol
├── SSH keys
└── local sudoers
```

Every server has become its own identity database.

When Alice joins:

```bash
useradd alice
```

might be run several times.

Her SSH key might be copied manually.

Her sudo permissions might be different on WEB01 and WEB02.

If Alice transfers teams, someone must find every system on which she has access.

If Alice leaves, someone must answer:

```text
Where does Alice have an account?

Which SSH keys belong to her?

Which servers accept those keys?

Which groups contain her?

Which sudo rules apply?

Does she still possess Kerberos credentials?

Were her permissions actually revoked?

Can we prove it?
```

The company wants centralized access management.

The desired policy is:

```text
LINUX ENGINEERS
        │
        ├──── SSH ────► WEB01
        │
        └──── SSH ────► WEB02

        DB01 = DENY

        sudo:
        ├── systemctl status nginx
        └── systemctl restart nginx


DATABASE ADMINS
        │
        └──── SSH ────► DB01

        WEB01 = DENY
        WEB02 = DENY


SECURITY AUDITORS
        │
        ├──── SSH ────► WEB01
        ├──── SSH ────► WEB02
        └──── SSH ────► DB01

        unrestricted sudo = DENY
```

You have been assigned to design and implement it.

Consider:

```bash
id alice
```

If this succeeds, you have evidence of identity resolution.

It does **not** prove authentication.

Next:

```bash
kinit alice
```

If this succeeds, Kerberos authentication works.

It does **not** prove WEB01 authorization.

Next:

```bash
ssh alice@web01.lab.veriqta
```

If that succeeds, SSH access is authorized.

It still does **not** mean Alice should be able to run:

```bash
sudo cat /etc/shadow
```

The project teaches you to identify the exact layer responsible for each decision.

## 8.1 Availability model

IDM01 and IDM02 provide redundant IdM services.

But:

```text
2 VMs on one laptop
        ≠
2 datacenters
```

This project demonstrates **service redundancy**, not complete infrastructure high availability.

Shared failure domains may include:

* hypervisor;
* laptop;
* disk;
* physical network;
* electricity;

# 12. Step-by-Step Implementation

## 12.1 Document requirements

Create:

```bash
cat > REQUIREMENTS.md <<'EOF'
# Enterprise Linux IAM Requirements

REQ-01 Central identities must replace duplicated application-user accounts.

REQ-02 Clients must resolve central users and groups.

REQ-03 Central authentication must use Kerberos-backed IdM credentials.

REQ-04 SSH host access must be centrally authorized.

REQ-05 Access must follow groups rather than per-host manual user configuration.

REQ-06 Linux engineers may access web servers but not database servers.

REQ-07 Database administrators may access database servers but not web servers.

REQ-08 Auditors may access designated systems without unrestricted root access.

REQ-09 Linux engineers may execute only approved web-service sudo commands.

REQ-10 SSH public keys must be centrally manageable.

REQ-11 Authentication and privileged activity must be auditable.

REQ-12 Disabled identities must be prevented from new normal authentication.

REQ-13 Failure of one IdM server must be tested while another remains available.

REQ-14 Replication health must be observable.

REQ-15 Certificate health must be observable.

REQ-16 DNS failure must be distinguishable from identity failure.

REQ-17 Time-related Kerberos failure must be distinguishable from authorization failure.

REQ-18 Emergency local administration must exist before restrictive policy is enforced.

REQ-19 Policy outcomes must be automatically testable.

REQ-20 IdM backups must be created and inspected.

REQ-21 Backup must not be confused with replication.

REQ-22 Policy changes must include validation and rollback.

REQ-23 Operational behavior must be measured before performance claims are made.

REQ-24 Secrets, private keys and credential caches must never enter Git.
EOF
```

## 14.2 HBAC validation

```bash
cat > scripts/validate-hbac.sh <<'EOF'
#!/usr/bin/env bash
set -u

failures=0

check() {
    user="$1"
    host="$2"
    expected="$3"

    output="$(ipa hbactest \
      --user="$user" \
      --host="$host" \
      --service=sshd 2>&1)"

    if grep -qi 'Access granted' <<<"$output"; then
        actual="ALLOW"
    else
        actual="DENY"
    fi

    if [[ "$actual" == "$expected" ]]; then
        printf '[PASS] %-8s -> %-26s %s\n' \
          "$user" "$host" "$actual"
    else
        printf '[FAIL] %-8s -> %-26s expected=%s actual=%s\n' \
          "$user" "$host" "$expected" "$actual"
        failures=$((failures + 1))
    fi
}

check alice web01.lab.veriqta ALLOW
check alice web02.lab.veriqta ALLOW
check alice db01.lab.veriqta DENY

check bob web01.lab.veriqta DENY
check bob web02.lab.veriqta DENY
check bob db01.lab.veriqta ALLOW

check carol web01.lab.veriqta ALLOW
check carol web02.lab.veriqta ALLOW
check carol db01.lab.veriqta ALLOW

printf '\nFailures: %d\n' "$failures"

exit "$failures"
EOF
```

Make executable:

```bash
chmod +x scripts/validate-hbac.sh
```

Run:

```bash
./scripts/validate-hbac.sh
```

## 20.5 Recovery design

Do **not** run `ipa-restore` casually against your healthy production-style lab.

Document the recovery workflow.

Create:

```bash
cat > runbooks/IDM-DISASTER-RECOVERY.md <<'EOF'
# IdM Disaster Recovery Runbook

## Scenario A — One replica is lost

If another healthy replica remains:

1. Confirm surviving replica health.
2. Confirm clients can authenticate.
3. Confirm DNS discovery.
4. Remove failed topology references only when appropriate.
5. Rebuild the failed host cleanly.
6. Re-enroll/reinstall it as a replica.
7. Verify replication.
8. Run IdM Healthcheck.
9. Verify new authentication.
10. Record incident evidence.

Rebuilding a lost replica from the surviving environment is normally preferable
to replacing current cluster state with an old backup.

## Scenario B — Deployment data is lost

1. Identify the correct backup.
2. Verify backup integrity and storage location.
3. Verify software-version compatibility.
4. Build an isolated recovery environment.
5. Follow the supported ipa-restore procedure.
6. Validate directory data.
7. Validate CA/DNS roles.
8. Validate authentication.
9. Validate authorization.
10. Validate certificates.
11. Validate replication before reconnecting normal clients.

Never experiment with destructive restore procedures against the only healthy
copy of an identity environment.
EOF
```

The actual restoration should be practiced only in a disposable recovery environment or VM snapshot exercise.
