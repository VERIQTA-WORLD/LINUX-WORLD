# 01. Project Title

## Enterprise High-Availability Linux Infrastructure

In this project, you will build a multi-node Linux platform designed to remain available when individual components fail.

You are not going to install two web servers and call that "high availability."

You will build the complete service path:

```text
                            CLIENT
                               |
                               |
                      192.168.56.100
                        FLOATING VIP
                               |
                +--------------+--------------+
                |                             |
                v                             v
             +------+                      +------+
             | LB01 |<------ VRRP -------->| LB02 |
             +------+                      +------+
                |                             |
                +--------------+--------------+
                               |
                            HAProxy
                               |
                     Health-checked pool
                               |
                +--------------+--------------+
                |                             |
                v                             v
             +-------+                     +-------+
             | WEB01 |                     | WEB02 |
             | Nginx |                     | Nginx |
             +-------+                     +-------+

                          +---------+
                          |  MON01  |
                          |Prometheus
                          +---------+
```

You will then deliberately break components.

You will stop Nginx.

You will remove a backend.

You will stop HAProxy.

You will stop Keepalived.

You will shut down the active load balancer.

You will isolate nodes with firewall rules.

You will introduce invalid configurations.

You will perform controlled maintenance.

You will measure failover.

And, critically, you will prove the difference between:

```text
SERVICE AVAILABLE
```

and:

```text
INFRASTRUCTURE HEALTHY
```

Those are not the same thing.

If `WEB01` fails while `WEB02` continues serving traffic, your application may still be available.

But your redundancy has degraded.

That distinction is central to this project.

# 02. Project Scenario

VERIQTA Labs operates an internal HTTP service.

The first version was simple:

```text
CLIENT
   |
   v
 WEB01
   |
 Nginx
```

It worked until `WEB01` failed.

The team added another server:

```text
WEB01

WEB02
```

But clients still needed somewhere to connect.

So the architecture became:

```text
CLIENT
   |
   v
LOAD BALANCER
   |
   +----------+
   |          |
   v          v
 WEB01      WEB02
```

Now a backend could fail.

But the load balancer became the new single point of failure.

You therefore need an architecture where:

* multiple application servers exist;
* traffic is distributed automatically;
* failed application servers leave rotation;
* recovered application servers rejoin automatically;
* multiple load balancers exist;
* a stable client IP moves between load balancers;
* load-balancer failure causes automatic failover;
* local process failures are automatically recovered where appropriate;
* infrastructure health is observable;
* degraded redundancy is visible;
* planned maintenance can occur without taking down the whole service;
* configuration changes are validated;
* rollback is tested;
* recovery is measured.

# 08. Architecture

## 8.1 Failure domains

Before installing anything, identify what can fail.

| Failure             | Expected outcome                               |
| ------------------- | ---------------------------------------------- |
| WEB01 Nginx         | WEB02 serves                                   |
| WEB01 VM            | WEB02 serves                                   |
| WEB02               | WEB01 serves                                   |
| Both web servers    | Service unavailable                            |
| Standby LB          | Service remains available, redundancy degraded |
| Active HAProxy      | VIP should move                                |
| Active LB VM        | VIP should move                                |
| Both LBs            | Service unavailable                            |
| MON01               | Application continues; monitoring degraded     |
| ADMIN01             | Application continues                          |
| Physical hypervisor | Entire local lab may fail                      |

That final row matters.

Six VMs on one laptop do not provide physical high availability.

They allow you to **model and test the software architecture**.

## 13.2 Configure HAProxy

On both load balancers:

```bash
sudo tee /etc/haproxy/haproxy.cfg > /dev/null <<'EOF'
global
    log /dev/log local0
    log /dev/log local1 notice
    chroot /var/lib/haproxy
    stats socket /run/haproxy/admin.sock mode 660 level admin
    stats timeout 30s
    user haproxy
    group haproxy
    daemon

defaults
    log global
    mode http
    option httplog
    option dontlognull

    timeout connect 5s
    timeout client 30s
    timeout server 30s

frontend veriqta_frontend
    bind *:80
    default_backend veriqta_backends

backend veriqta_backends
    balance roundrobin

    option httpchk
    http-check send meth GET uri /health
    http-check expect status 200

    default-server inter 2s fall 3 rise 2

    server web01 192.168.56.31:80 check
    server web02 192.168.56.32:80 check

frontend local_health
    bind 127.0.0.1:8404
    mode http
    http-request return status 200 content-type text/plain string "OK\n"

frontend prometheus_metrics
    bind *:8405
    mode http
    http-request use-service prometheus-exporter if { path /metrics }
    no log
EOF
```

The backend health check is deliberately HTTP-aware.

HAProxy will request:

```text
GET /health
```

A successful TCP connection alone is not enough.

The separate `127.0.0.1:8404` endpoint will later tell Keepalived whether the **local HAProxy process** is capable of serving.

This distinction matters.

If both web servers fail, moving the VIP from `lb01` to `lb02` accomplishes nothing because both load balancers use the same failed backend pool.

The HAProxy Prometheus frontend uses HAProxy's native exporter, available in HAProxy 2.0 and later. ([HAProxy Technologies][2])

Validate:

```bash
sudo haproxy -c -f /etc/haproxy/haproxy.cfg
```

Do not restart HAProxy if validation fails.

If successful:

```bash
sudo systemctl restart haproxy
```

Verify:

```bash
systemctl is-active haproxy
```

Test local readiness:

```bash
curl http://127.0.0.1:8404/
```

Expected:

```text
OK
```

Test HAProxy:

```bash
for i in {1..6}; do
    curl -s http://127.0.0.1/ | grep 'Backend:'
done
```

You should see both:

```text
Backend: WEB01
Backend: WEB02
```

## 13.7 Configure Keepalived on LB01

First find your actual lab interface:

```bash
ip -brief address
```

Suppose it is:

```text
enp0s8
```

Create:

```bash
sudo tee /etc/keepalived/keepalived.conf > /dev/null <<'EOF'
global_defs {
    router_id LB01
    enable_script_security
}

vrrp_script chk_haproxy {
    script "/usr/local/sbin/check-haproxy-local"
    interval 2
    timeout 1
    fall 2
    rise 2
    weight -60
}

vrrp_instance VI_1 {
    state BACKUP
    interface enp0s8
    virtual_router_id 51
    priority 150
    advert_int 1

    unicast_src_ip 192.168.56.20

    unicast_peer {
        192.168.56.21
    }

    virtual_ipaddress {
        192.168.56.100/24
    }

    track_script {
        chk_haproxy
    }
}
EOF
```

If your interface is not `enp0s8`, replace it **before continuing**.

vrrp_script chk_haproxy {
    script "/usr/local/sbin/check-haproxy-local"
    interval 2
    timeout 1
    fall 2
    rise 2
    weight -60
}

vrrp_instance VI_1 {
    state BACKUP
    interface enp0s8
    virtual_router_id 51
    priority 100
    advert_int 1

    unicast_src_ip 192.168.56.21

    unicast_peer {
        192.168.56.20
    }

    virtual_ipaddress {
        192.168.56.100/24
    }

    track_script {
        chk_haproxy
    }
}
EOF
```

Again, correct the interface if necessary.

The preferred node has priority `150`.

The secondary has `100`.

The tracking script has a negative weight of `60`, so an unhealthy HAProxy on the preferred node lowers its effective preference sufficiently for the healthy peer to take ownership.

## 14.3 Create cluster-health.sh

```

```bash
#!/usr/bin/env bash

set -u

VIP="192.168.56.100"
LB1="192.168.56.20"
LB2="192.168.56.21"
WEB1="192.168.56.31"
WEB2="192.168.56.32"

pass() {
    printf 'PASS: %s\n' "$1"
}

warn() {
    printf 'WARN: %s\n' "$1"
}

fail() {
    printf 'FAIL: %s\n' "$1"
}

echo "============================================"
echo " VERIQTA HA CLUSTER HEALTH"
echo " $(date -u '+%Y-%m-%dT%H:%M:%SZ')"
echo "============================================"

echo
echo "[NODE REACHABILITY]"

for node in "$LB1" "$LB2" "$WEB1" "$WEB2"; do
    if ping -c 1 -W 1 "$node" > /dev/null 2>&1; then
        pass "$node reachable"
    else
        warn "$node does not answer ICMP"
    fi
done

echo
echo "[BACKEND HEALTH]"

healthy_backends=0

if curl -fsS --max-time 2 \
    "http://${WEB1}/health" > /dev/null; then
    pass "WEB01 application health"
    ((healthy_backends+=1))
else
    warn "WEB01 application health failed"
fi

if curl -fsS --max-time 2 \
    "http://${WEB2}/health" > /dev/null; then
    pass "WEB02 application health"
    ((healthy_backends+=1))
else
    warn "WEB02 application health failed"
fi

echo
echo "[VIP SERVICE]"

if response="$(curl -fsS --max-time 3 "http://${VIP}/")"; then
    pass "VIP returned HTTP successfully"

    if grep -q 'WEB01' <<< "$response"; then
        echo "Backend observed: WEB01"
    elif grep -q 'WEB02' <<< "$response"; then
        echo "Backend observed: WEB02"
    fi
else
    fail "VIP service unavailable"
fi

echo
echo "[REDUNDANCY STATE]"

case "$healthy_backends" in
    2)
        pass "Two healthy backends"
        ;;
    1)
        warn "Service may be available, but backend redundancy is degraded"
        ;;
    0)
        fail "No healthy application backends"
        ;;
esac
```

Make executable:

```bash
chmod +x ~/enterprise-ha-linux/scripts/cluster-health.sh
```

Run:

```bash
~/enterprise-ha-linux/scripts/cluster-health.sh
```

Notice the script does **not** declare the platform healthy simply because the VIP answers.

That would hide degraded redundancy.

## Failure 05 — HAProxy crash

First identify which LB owns the VIP:

```bash

```

On the active load balancer:

```bash

```

Record the main HAProxy PID.

Then deliberately kill the process:

```bash
sudo kill -9 "$(pgrep -o haproxy)"
```

Immediately observe:

```bash
systemctl status haproxy --no-pager
```

Then:

```bash
journalctl -u haproxy -n 30 --no-pager
```

Because you configured:

```text
Restart=on-failure
```

systemd should attempt local recovery.

At the same time, Keepalived's readiness check can reduce this node's VRRP priority while HAProxy is unhealthy.

You are observing two recovery mechanisms:

```text
LOCAL RECOVERY
systemd → restart HAProxy

SERVICE RECOVERY
Keepalived → move VIP when local HAProxy is unhealthy
```

Record what actually happens first in your environment.

Do not invent the result.

## 20.5 Controlled backend maintenance

HAProxy's runtime API supports three useful administrative server states:

```text
ready
drain
maint
```

`drain` removes a server from normal load balancing while continuing health checks. `maint` stops traffic and health checks. `ready` returns the server to normal operation. ([HAProxy Technologies][1])

On LB01, drain WEB01:

```bash
echo "set server veriqta_backends/web01 state drain" |
sudo socat stdio /run/haproxy/admin.sock
```

Verify:

```bash
echo "show stat" |
sudo socat stdio /run/haproxy/admin.sock |
grep web01
```

Run requests from `admin01`.

New normal traffic should move away from WEB01.

Perform your maintenance.

Then return it:

```bash
echo "set server veriqta_backends/web01 state ready" |
sudo socat stdio /run/haproxy/admin.sock
```

Verify health before continuing.

Remember: Runtime API state changes are in-memory and do not rewrite the HAProxy configuration file, so they do not automatically survive reload/restart. ([HAProxy Technologies][3])

That behavior itself belongs in your operations documentation.

# 24. Cleanup

Before destroying the VMs, preserve the repository.

On `admin01`:

```bash
cd ~/enterprise-ha-linux
```

Inspect:

```bash
git status
```

Search manually for obvious secrets:

```bash
grep -RniE \
'password|secret|token|private.key|BEGIN.*PRIVATE' \
. || true
```

Review every match.

Do not blindly delete every file containing the word `password`; documentation may legitimately discuss passwords.

Stop monitoring:

```bash
sudo systemctl stop prometheus
```

On load balancers:

```bash
sudo systemctl stop keepalived
sudo systemctl stop haproxy
```

Verify VIP disappears:

```bash
ip address | grep 192.168.56.100
```

It should no longer appear.

On backends:

```bash
sudo systemctl stop nginx
```

If these are dedicated disposable lab VMs, restoring or deleting VM snapshots is generally cleaner than manually trying to return dozens of system changes to an unknown previous state.
