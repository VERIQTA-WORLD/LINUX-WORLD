# 02. Project Scenario

Your organization operates Linux infrastructure but has poor operational visibility.

Current monitoring looks like:

```text
User reports outage
       │
       ▼
Engineer SSHs to server
       │
       ├── top
       ├── free
       ├── df
       ├── systemctl
       └── journalctl
       │
       ▼
Engineer tries to reconstruct
what happened after the fact
```

Problems include:

```text
No historical metrics
No centralized logs
No dashboards
No availability monitoring
No alert routing
No standardized thresholds
No correlation between metrics and logs
No monitoring runbooks
No monitoring evidence
No capacity trends
No clear service-health definition
```

A customer saying:

> The website was unavailable around 14:20.

should not require guesswork.

The desired investigation should look more like:

```text
14:17
CPU normal

14:18
Memory normal

14:19
nginx service stopped

14:19
HTTP probe failed

14:20
ServiceDown alert entered pending state

14:21
Alert fired

14:21
Alertmanager received notification

14:21
journald showed nginx stop event

14:24
Engineer restarted nginx

14:24
HTTP probe recovered

14:25
Alert resolved
```

Your task is to build the observability platform that makes this possible.

## 8.6 Failure domains

The reference lab intentionally places the central components on OBS01.

Therefore:

```text
OBS01 failure
     │
     ├── Prometheus unavailable
     ├── Grafana unavailable
     ├── Loki unavailable
     ├── Alertmanager unavailable
     └── Blackbox Exporter unavailable
```

That is a major failure domain.

The project does **not** pretend otherwise.

A real larger production design would separate and potentially replicate these components.

# 12. Step-by-Step Implementation

## 12.1 Document requirements

Create:

```bash
cat > REQUIREMENTS.md <<'EOF'
# Linux Observability Platform Requirements

REQ-01 Every managed Linux host must expose host metrics.

REQ-02 Prometheus must centrally scrape Linux metrics.

REQ-03 Host CPU, memory, filesystem, disk, network and load must be queryable.

REQ-04 Monitoring must distinguish host reachability from application availability.

REQ-05 HTTP availability must be actively probed.

REQ-06 Linux system logs must be centrally searchable.

REQ-07 journald must remain the local source of truth for system logs.

REQ-08 Grafana must visualize infrastructure metrics.

REQ-09 Grafana must provide access to centralized logs.

REQ-10 Prometheus alert rules must detect actionable infrastructure failures.

REQ-11 Alerts must use persistence windows where appropriate to reduce noise.

REQ-12 Alertmanager must receive and route Prometheus alerts.

REQ-13 The notification path must be tested.

REQ-14 Monitoring components must themselves be monitored where practical.

REQ-15 Failure labs must cover CPU, memory, filesystem, service, exporter,
network/availability, log pipeline and monitoring-component failures.

REQ-16 Every failure lab must establish a baseline before failure injection.

REQ-17 Recovery must be verified using the same signal that detected failure.

REQ-18 Metrics and logs must be correlated during investigation.

REQ-19 Alert changes must be validated before reload.

REQ-20 At least one alert change must be rolled back.

REQ-21 Configuration must be backed up.

REQ-22 Restore procedures must be documented and tested safely.

REQ-23 Telemetry storage consumption must be measured.

REQ-24 The lab must not claim enterprise scale from small-lab measurements.

REQ-25 Secrets must not be committed to Git.

REQ-26 Promtail must not be used because the reference architecture uses
Grafana Alloy.

REQ-27 Final evidence must contain actual observations rather than fabricated
screenshots or results.
EOF
```

global:

alerting:
  alertmanagers:

      - targets:

## 12.9 Query CPU

PromQL:

```text
100 - (
  avg by (instance) (
    rate(node_cpu_seconds_total{mode="idle"}[5m])
  ) * 100
)
```

Interpretation:

```text
100 - idle percentage
=
approximate busy CPU percentage
```

---

## 12.10 Query memory

PromQL:

```text
100 *
(
  1 -
  (
    node_memory_MemAvailable_bytes
    /
    node_memory_MemTotal_bytes
  )
)
```

Do not calculate Linux memory pressure using only `MemFree`.

---

## 12.11 Query filesystem use

## 13.5 Build a local notification receiver

The project should test actual routing without requiring a learner to own Slack, PagerDuty or an SMTP server.

Create receiver:

```bash
sudo tee /opt/veriqta-alert-receiver/receiver.py >/dev/null <<'EOF'
#!/usr/bin/env python3

from http.server import BaseHTTPRequestHandler, HTTPServer
from datetime import datetime, timezone
from pathlib import Path

LOG = Path("/var/log/veriqta-alert-receiver.log")


class Handler(BaseHTTPRequestHandler):

    def do_POST(self):
        length = int(self.headers.get("Content-Length", "0"))
        body = self.rfile.read(length).decode("utf-8", errors="replace")

        timestamp = datetime.now(timezone.utc).isoformat()

        with LOG.open("a") as handle:
            handle.write(f"{timestamp} {body}\n")

        self.send_response(200)
        self.end_headers()
        self.wfile.write(b"ok\n")

    def log_message(self, format, *args):
        return


HTTPServer(("127.0.0.1", 5001), Handler).serve_forever()
EOF
```

I understand pending, firing and resolved states.

I can prove an alert reached Alertmanager.

I can safely generate CPU, memory and filesystem pressure.

I can break an application.
