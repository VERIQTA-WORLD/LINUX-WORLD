# 02. Project Scenario

Your organization operates a critical Linux application.

The production architecture initially contains:

```text
Users
  │
  ▼
APP01
Nginx + application
  │
  ▼
DB01
PostgreSQL
```

This architecture works until something serious happens.

Possible failures include:

```text
APP01 filesystem corruption

DB01 disk failure

Accidental database deletion

Bad deployment

Ransomware

Datacenter outage

Administrator error

Network isolation

Database corruption

VM deletion

Operating-system failure

Backup corruption

Backup repository loss

Credential loss
```

A backup script returning exit code `0` yesterday does not prove that the organization can recover today.

Likewise:

```text
replication ≠ backup
```

If destructive data changes replicate from the primary database to the standby, replication faithfully reproduces the damage.

You therefore need multiple recovery mechanisms.

The organization establishes the following laboratory recovery objectives:

| Workload                   | Target RTO |                                          Target RPO | Recovery mechanism                     |
| -------------------------- | ---------: | --------------------------------------------------: | -------------------------------------- |
| Web/application tier       |     10 min |                                              15 min | replicated application state + rebuild |
| PostgreSQL                 |     10 min | ≤60 sec target during healthy streaming replication | DR standby                             |
| PostgreSQL backup fallback |     30 min |                                      24 h or better | encrypted backup                       |
| Configuration              |     30 min |                                                24 h | Restic backup                          |
| Accidental DB change       |     30 min |                      point before destructive event | WAL/PITR exercise                      |

These are **laboratory objectives**.

They are not automatically suitable business requirements.

The project will measure whether the environment actually achieves them.

## RTO

Recovery Time Objective answers:

```text
How long can the service remain unavailable?
```

Example:

```text
Disaster declared: 14:00

RTO target: 10 minutes

Required recovery deadline: 14:10
```

Actual recovery time must be measured.

---

## RPO

Recovery Point Objective answers:

```text
How much recent data can the organization tolerate losing?
```

If the last recoverable transaction occurred at:

```text
13:59:40
```

and disaster occurred at:

```text
14:00:00
```

then observed data loss is approximately:

```text
20 seconds
```

Do not claim an RPO merely because replication exists.

Measure the recovery point.

---

## Backup versus replication

Replication:

```text
Primary
   │
   ├── change
   ├── change
   ├── DELETE critical_table
   │
   ▼
Standby receives changes
```

Replication may reproduce destructive changes.

Backup provides historical recovery points.

Therefore the architecture uses both.

# 08. Architecture

## 8.1 Failure model

Design for:

```text
single service failure
single VM failure
database failure
application failure
data deletion
configuration corruption
primary-site loss
replication interruption
backup corruption
operator error
```

The lab does not claim protection against:

```text
physical host destruction
regional disaster
cloud-account compromise
backup provider failure
large-scale cyberattack
```

unless you extend the architecture accordingly.

---

## 8.2 Recovery hierarchy

Use the fastest safe recovery mechanism first.

```text
Service restart
     │
     ▼
Local repair
     │
     ▼
DR standby promotion
     │
     ▼
Backup restore
     │
     ▼
PITR
```

The correct mechanism depends on the failure.

---

## 8.3 Database replication

```text
DB01
Primary
  │
  │ WAL
  ▼
DR-DB01
Standby
```

The standby remains read-only until promoted.

---

## 8.4 Application replication

Application content will be synchronized:

```text
APP01
/srv/veriqta-app
      │
      │ rsync over SSH
      ▼
DR-APP01
/srv/veriqta-app
```

The DR application service remains stopped during normal operation.

---

## 8.5 Backup architecture

```text
Source systems
     │
     ▼
Restic
     │
     ├── encryption
     ├── snapshots
     ├── deduplication
     └── integrity verification
     │
     ▼
BACKUP01
```

BACKUP01 is deliberately separate from the primary application/database machines.

---

## 8.6 Split-brain risk

One of the most dangerous DR failures is:

```text
DB01 writable
+
DR-DB01 promoted writable
+
applications writing to both
```

That is split brain.

This project therefore requires:

```text
FENCE PRIMARY
     ↓
VERIFY PRIMARY CANNOT ACCEPT WRITES
     ↓
PROMOTE DR
```

Promotion must not be the first step.

---

## 8.7 Recovery authority

Create a simple decision model:

```text
Incident detected
     │
     ▼
Can primary recover inside RTO?
     │
 ┌───┴────┐
 │        │
YES       NO
 │        │
repair    declare DR
          │
          ▼
       fence primary
          │
          ▼
       verify DR
          │
          ▼
       promote
```

# 12. Step-by-Step Implementation

## 12.1 Define recovery requirements

Create:

```bash
cat > REQUIREMENTS.md <<'EOF'
# Disaster Recovery Requirements

REQ-01 Critical workloads must have documented RTO and RPO objectives.

REQ-02 The application tier must have a pre-provisioned DR host.

REQ-03 PostgreSQL must have a separate DR standby.

REQ-04 Database replication health must be verifiable from both primary and standby.

REQ-05 DR promotion must not occur before the failed primary is fenced.

REQ-06 Application state must be reproducibly copied to the DR application host.

REQ-07 Critical configuration must be backed up off-host.

REQ-08 Backups must be encrypted.

REQ-09 Backup jobs must be automated.

REQ-10 Backup failures must produce non-zero exit status and journal evidence.

REQ-11 Backup repositories must be checked for integrity.

REQ-12 A successful backup job is not sufficient evidence of recoverability.

REQ-13 At least one complete restore must be performed.

REQ-14 At least one individual-file restore must be performed.

REQ-15 PostgreSQL recovery must be tested independently from normal replication.

REQ-16 Destructive database change recovery must be demonstrated.

REQ-17 Recovery must be performed using documented runbooks.

REQ-18 Actual recovery duration must be measured.

REQ-19 Actual recoverable data point must be measured.

REQ-20 RTO and RPO results must be compared with objectives.

REQ-21 Failure scenarios must include backup, replication and DR failures.

REQ-22 Recovery evidence must use actual observations.

REQ-23 No fabricated recovery results are permitted.

REQ-24 Secrets must not be committed to Git.

REQ-25 The laboratory's single-physical-host limitation must be documented.

REQ-26 Failback must be treated as a separate controlled operation.

REQ-27 DR readiness must be periodically testable rather than assumed.
EOF
```

## 12.12 Create application

```bash
sudo tee /srv/veriqta-app/app.py >/dev/null <<'PY'
from flask import Flask, jsonify
import os
import socket
import uuid
import psycopg

app = Flask(__name__)

DB_HOST = os.environ.get("DB_HOST", "db01")
DB_NAME = os.environ.get("DB_NAME", "veriqta")
DB_USER = os.environ.get("DB_USER", "veriqta_app")
DB_PASSWORD = os.environ["DB_PASSWORD"]


def connection():
    return psycopg.connect(
        host=DB_HOST,
        dbname=DB_NAME,
        user=DB_USER,
        password=DB_PASSWORD,
        connect_timeout=3,
    )


@app.get("/health")
def health():
    try:
        with connection() as conn:
            with conn.cursor() as cur:
                cur.execute("SELECT pg_is_in_recovery(), now()")
                recovery, database_time = cur.fetchone()

        return jsonify(
            status="healthy",
            application_host=socket.gethostname(),
            database_host=DB_HOST,
            database_in_recovery=recovery,
            database_time=database_time.isoformat(),
        ), 200

    except Exception as exc:
        return jsonify(
            status="unhealthy",
            application_host=socket.gethostname(),
            database_host=DB_HOST,
            error=str(exc),
        ), 503


@app.post("/event")
def create_event():
    event_uuid = str(uuid.uuid4())

    with connection() as conn:
        with conn.cursor() as cur:
            cur.execute(
                """
                INSERT INTO recovery_events
                    (event_uuid, source_host, message)
                VALUES (%s, %s, %s)
                RETURNING id, created_at
                """,
                (
                    event_uuid,
                    socket.gethostname(),
                    "DR_VALIDATION_EVENT",
                ),
            )

            event_id, created_at = cur.fetchone()

    return jsonify(
        id=event_id,
        event_uuid=event_uuid,
        created_at=created_at.isoformat(),
    ), 201


@app.get("/events")
def events():
    with connection() as conn:
        with conn.cursor() as cur:
            cur.execute(
                """
                SELECT id, event_uuid, created_at, source_host, message
                FROM recovery_events
                ORDER BY id DESC
                LIMIT 20
                """
            )

            rows = cur.fetchall()

    return jsonify([
        {
            "id": row[0],
            "event_uuid": str(row[1]),
            "created_at": row[2].isoformat(),
            "source_host": row[3],
            "message": row[4],
        }
        for row in rows
    ])


if __name__ == "__main__":
    app.run(host="127.0.0.1", port=8000)
```

## 15.3 Backup encryption

Restic repository encryption protects backup contents at rest.

But encryption does not solve:

```text
credential theft
repository deletion
source compromise
backup-server compromise
loss of repository password
```

A stronger production architecture should consider:

```text
immutable storage
separate administrative credentials
MFA
object locking
offline copies
separate account/subscription
geographic separation
```

A mature backup strategy aims for multiple copies and failure domains.

This lab contains:

```text
Primary data
+
DR replica
+
BACKUP01
```

However, because all VMs may run on one physical laptop, the physical implementation does **not** satisfy true geographic separation.

State that honestly.

## Failure Lab 10 — Accidental database deletion

This tests why replication alone is insufficient.

First restore the normal laboratory topology or create an isolated recovery environment.

Take a fresh base backup before the exercise.

Create identifiable rows:

```bash

  -d veriqta \
  -c "
INSERT INTO recovery_events
(event_uuid,source_host,message)
VALUES
('$(uuidgen)','db01','PITR_KEEP_ME');
"
```

Create PostgreSQL restore point:

```bash
sudo -u postgres psql \
  -c "
SELECT pg_create_restore_point('before_destructive_change');
"
```

Force WAL switch:

```bash
sudo -u postgres psql \
  -c "SELECT pg_switch_wal();"
```

```bash

  -d veriqta \
  -c "

"
```

```text

```

```bash
Failback is not the reverse of failover.
```
