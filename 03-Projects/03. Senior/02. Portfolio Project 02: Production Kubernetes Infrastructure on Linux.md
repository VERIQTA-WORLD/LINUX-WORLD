## 8.2 Failure domains

Create:

```bash
nano FAILURE-DOMAINS.md
```

Document:

| Failure             | Expected behavior                    |
| ------------------- | ------------------------------------ |
| One application Pod | Deployment replaces it               |
| Worker01            | Workloads rescheduled where possible |
| Worker02            | Workloads rescheduled where possible |
| Both workers        | Application unavailable              |
| containerd          | Pods on affected node fail           |
| kubelet             | Node eventually becomes unhealthy    |
| CoreDNS             | DNS-based service discovery degraded |
| CNI                 | Pod networking degraded              |
| Gateway controller  | External routing affected            |
| PV backing storage  | Stateful workload affected           |
| Control-plane VM    | Cluster management unavailable       |
| Physical lab host   | Entire VM lab may fail               |

The last two reveal important limitations.

This project has **worker/workload redundancy**, but a single control-plane VM is still a control-plane failure domain.

We will document that rather than falsely calling this a fully HA Kubernetes control plane.

# 12. Step-by-Step Implementation

## 12.1 Install Kubernetes packages

The current Kubernetes documentation uses `pkgs.k8s.io`; the old `apt.kubernetes.io` repository is deprecated/frozen. Kubernetes package repositories are separated by minor version. ([Kubernetes][3])

For this project, pin the cluster to one chosen supported minor version rather than installing arbitrary versions on different nodes.

On **all Kubernetes nodes**, first create the keyring directory:

```bash
sudo mkdir -p -m 755 /etc/apt/keyrings
```

Then follow the package-repository commands for the Kubernetes minor release you are building from the official installation page:

[Kubernetes — Installing kubeadm](https://kubernetes.io/docs/setup/production-environment/tools/kubeadm/install-kubeadm/?utm_source=chatgpt.com)

After adding that repository:

```bash
sudo apt update
```

Install:

```bash
sudo apt install -y kubelet kubeadm kubectl
```

Prevent accidental package upgrades:

```bash
sudo apt-mark hold kubelet kubeadm kubectl
```

Verify:

```bash
kubeadm version
```

```bash
kubelet --version
```

```bash
kubectl version --client
```

Run on all three Kubernetes nodes and confirm the minor versions are compatible before continuing.

## 12.3 Initialize the control plane

We will use:

```text
Pod network: 10.244.0.0/16
Service network: Kubernetes default
API address: 192.168.56.50
```

Before using `10.244.0.0/16`, verify it does not overlap your host network:

```bash
ip route
```

Kubernetes explicitly warns that Pod-network address space must not overlap host networks. ([Kubernetes][4])

On `k8s-cp01`:

```bash
sudo kubeadm init \
  --apiserver-advertise-address=192.168.56.50 \
  --control-plane-endpoint=192.168.56.50:6443 \
  --pod-network-cidr=10.244.0.0/16
```

Do not close the terminal.

At the end, kubeadm prints a worker `kubeadm join` command.

Treat the bootstrap token as a secret. Kubernetes documentation specifically warns that anyone possessing a valid join token can use it to authenticate a node join. ([Kubernetes][4])

## 12.6 Install the CNI

Kubernetes requires a CNI network before Pods can communicate normally, and CoreDNS does not become fully operational until networking is available. ([Kubernetes][4])

For this project, choose a maintained CNI that supports NetworkPolicy. Calico is one of the networking/network-policy implementations listed by Kubernetes. ([Kubernetes][5])

Because CNI installation manifests and operator versions change independently of Kubernetes, use the current Calico installation procedure rather than embedding an unpinned stale manifest in the repository.

After installing Calico according to its version-specific installation procedure, verify:

```bash
kubectl get pods -A
```

Then:

```bash
kubectl get nodes
```

Wait until:

```text

```

Check CoreDNS:

```bash
kubectl get pods -n kube-system \
  -l k8s-app=kube-dns
```

Do not join workers until the control-plane networking is healthy.

## 13.3 Create the Deployment

Create:

```bash
cat > ~/production-kubernetes-linux/manifests/base/deployment.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: veriqta-web
  namespace: veriqta-prod
spec:
  replicas: 3

  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 1

  selector:
    matchLabels:
      app: veriqta-web

  template:
    metadata:
      labels:
        app: veriqta-web

    spec:
      securityContext:
        seccompProfile:
          type: RuntimeDefault

      containers:
        - name: web
          image: nginx:1.28-alpine

          ports:
            - name: http
              containerPort: 80

          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 250m
              memory: 128Mi

          readinessProbe:
            httpGet:
              path: /
              port: http
            initialDelaySeconds: 3
            periodSeconds: 5
            timeoutSeconds: 2
            failureThreshold: 3

          livenessProbe:
            httpGet:
              path: /
              port: http
            initialDelaySeconds: 10
            periodSeconds: 10
            timeoutSeconds: 2
            failureThreshold: 3

          volumeMounts:
            - name: web-content
              mountPath: /usr/share/nginx/html
              readOnly: true

      volumes:
        - name: web-content
          configMap:
            name: veriqta-web-config
EOF
```

## 13.4 Understand the health probes

The readiness probe answers:

> Should this Pod receive traffic?

The liveness probe answers:

> Should Kubernetes restart this container because it is unhealthy?

These are different operational questions.

Inspect:

```bash
kubectl describe pod \
  -n veriqta-prod \
  "$(kubectl get pods -n veriqta-prod \
  -l app=veriqta-web \
  -o jsonpath='{.items[0].metadata.name}')"
```

Look for:

```text
Readiness
Liveness
Conditions
Events
```

## 15.2 Create default-deny NetworkPolicy

Create:

```bash
cat > ~/production-kubernetes-linux/manifests/security/default-deny.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: veriqta-prod
spec:
  podSelector: {}
  policyTypes:
    - Ingress
    - Egress
EOF
```

Do **not** apply this casually yet.

A default-deny policy can also block DNS and application traffic.

That is exactly why security changes require planning.

Create DNS allowance:

```bash
cat > ~/production-kubernetes-linux/manifests/security/allow-dns.yaml <<'EOF'
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-dns
  namespace: veriqta-prod
spec:
  podSelector: {}
  policyTypes:
    - Egress
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
      ports:
        - protocol: UDP
          port: 53
        - protocol: TCP
          port: 53
EOF
```

Create application ingress policy later after you identify the labels used by your Gateway data plane.

This prevents us from pretending a generic selector will work without inspecting the controller we actually deployed.

## 19.1 Persistent storage lab

```bash

apiVersion: v1

  name: veriqta-local-pv

    - ReadWriteOnce

  persistentVolumeReclaimPolicy: Retain

  storageClassName: veriqta-local

  local:
    path: /srv/kubernetes/veriqta-data

      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values:
                - k8s-worker01
```

```bash
cat > ~/production-kubernetes-linux/manifests/storage/pvc.yaml <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: veriqta-data
  namespace: veriqta-prod
spec:
  accessModes:
    - ReadWriteOnce

  storageClassName: veriqta-local

  resources:
    requests:
      storage: 1Gi
EOF
```

```bash
~/production-kubernetes-linux/manifests/storage/pv.yaml
```


This provides persistent storage for the lab.

```text
WORKER01 STORAGE FAILURE
→ data may be unavailable
```

That limitation must appear in the final project documentation.

# 24. Cleanup

Before destroying anything, preserve your evidence.

Check:

```bash
cd ~/production-kubernetes-linux
```

Inspect:

```bash
find . -maxdepth 3 -type f | sort
```

Check cluster resources:

```bash
kubectl get all -A
```

Export useful state:

```bash
kubectl get nodes -o wide \
  > evidence/final-nodes.txt
```

```bash
kubectl get pods -A -o wide \
  > evidence/final-pods.txt
```

```bash
kubectl get events -A \
  --sort-by='.lastTimestamp' \
  > evidence/final-events.txt
```

Never commit kubeconfig credentials, bootstrap tokens, private keys or Secrets in plaintext.

If this is a disposable lab, remove workers cleanly.

On worker:

```bash
sudo kubeadm reset
```

On the control plane, after workers are no longer needed:

```bash
sudo kubeadm reset
```

Do not run cleanup until evidence has been preserved.

How quickly was it replaced?

Did deleting one Pod cause user-visible interruption?

What happened when you drained Worker01?

Where did its workloads move?

How long before Kubernetes reflected the problem?

What happened when containerd stopped?

Could existing containers continue temporarily?

What operations failed?

What happened when you deployed an invalid image tag?

What evidence led you to the root cause?

How quickly could you roll back?

Did persistent data survive Pod recreation?

What happened when the node containing the local PV became unavailable?

Which failure was Kubernetes able to recover automatically?

Which failure required human intervention?

Which failure left the application running but reduced resilience?

Which monitoring signal detected the problem first?

Which part of your architecture has the largest blast radius?

What would you change before calling this production-ready?

Those answers are far more valuable than:

> Kubernetes automatically heals applications.

You should know **what it healed, how it healed it, what it could not heal, how long recovery took, and what evidence proved it.**
