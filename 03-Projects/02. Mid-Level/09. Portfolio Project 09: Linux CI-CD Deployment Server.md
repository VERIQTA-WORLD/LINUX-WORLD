# 01. Project Title

## Linux CI/CD Deployment Server

A CI/CD pipeline that only prints:

```text
Hello World
```

is useful when you are learning pipeline syntax.

It is not enough for this project.

You are going to build a real Linux deployment path:

```text
DEVELOPER
    |
    | git push
    v

    |
    | checkout
    v
CI/CD SERVER
    |
    +--> validate source
    |
    +--> run tests

    |

    |
    +--> transfer artifact
    |
```

# 02. Project Scenario

Your engineering team maintains an internal application called:

**VERIQTA Release Portal**

The current deployment process is manual.

An engineer logs into a server, pulls or copies the newest files, installs dependencies, restarts the application, and checks whether the website still works.

The process resembles:

```text
Developer changes code
        |
        v
git push
        |
        v
Engineer SSHs into server
        |
        v
Copies files
        |
        v
Restarts application
        |
        v
Opens website
        |
        v
Hopes everything works
```

Several problems have appeared.

Nobody has a completely reproducible deployment procedure.

Different engineers perform slightly different steps.

A deployment can leave old and new files mixed together.

There is no reliable record of exactly which commit is running.

Tests can be skipped.

A broken release may be discovered only after deployment.

Rollback depends on somebody remembering what the previous version contained.

Deployment credentials are poorly separated from ordinary user access.

Your task is to replace that process with:

```text
COMMIT
   |
   v
CHECKOUT
   |
   v
VALIDATION
   |
   v
TEST
   |
   v
BUILD
   |
   v
ARTIFACT
   |
   v
TRANSFER
   |
   v
DEPLOY
   |
   v
HEALTH CHECK
   |
   +------ PASS ------> RELEASE COMPLETE
   |
   +------ FAIL ------> ROLLBACK
```

# 03. Project Difficulty

## Mid-Level

You already know how to:

```bash
git clone
```

and:

```bash
systemctl restart
```

That is not enough here.

A deployment system must answer harder questions:

```text
What commit produced this release?

Did the tests actually pass?

What exactly was deployed?

Was the artifact changed during transfer?

Which account performed the deployment?

Can that account do more than it needs?

What happens if two deployments start together?

What happens if artifact transfer fails halfway through?

What happens if the new process starts but is unhealthy?

What happens if Nginx is healthy but the application is not?

Can the previous release be restored quickly?

Can you prove what is currently running?

Can you reproduce the deployment?
```

You will treat deployment as an operational transaction:

```text
PREPARE
  ↓
VALIDATE
  ↓
BUILD
  ↓
TRANSFER
  ↓
STAGE
  ↓
ACTIVATE
  ↓
RESTART
  ↓
VERIFY
  ↓
COMMIT RELEASE

or

ROLL BACK
```

## Create the Application

Create:

```bash
nano application/app.py
```

Add:

```python
from http.server import BaseHTTPRequestHandler, HTTPServer
import json
import os
import socket

HOST = "127.0.0.1"
PORT = int(os.getenv("PORT", "8000"))

BASE_DIR = os.path.dirname(os.path.abspath(__file__))
VERSION_FILE = os.path.join(BASE_DIR, "VERSION")


def get_version():
    try:
        with open(VERSION_FILE, "r", encoding="utf-8") as file:
            return file.read().strip()
    except OSError:
        return "unknown"


class Handler(BaseHTTPRequestHandler):

    def send_json(self, status_code, payload):
        body = json.dumps(payload).encode("utf-8")

        self.send_response(status_code)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()

        self.wfile.write(body)

    def do_GET(self):
        if self.path == "/":
            self.send_json(
                200,
                {
                    "application": "VERIQTA Release Portal",
                    "version": get_version(),
                    "hostname": socket.gethostname(),
                    "status": "running",
                },
            )
            return

        if self.path == "/health":
            self.send_json(
                200,
                {
                    "status": "ok",
                    "version": get_version(),
                },
            )
            return

        self.send_json(
            404,
            {
                "status": "not-found",
            },
        )

    def log_message(self, format, *args):
        print(
            "%s - - [%s] %s"
            % (
                self.client_address[0],
                self.log_date_time_string(),
                format % args,
            ),
            flush=True,
        )


if __name__ == "__main__":
    server = HTTPServer((HOST, PORT), Handler)

    print(
        f"VERIQTA Release Portal listening on {HOST}:{PORT}",
        flush=True,
    )

    server.serve_forever()
```

# Phase 3: Build the Artifact Process

The deployment server should not receive a random working directory.

Create a release artifact.

Create:

```bash
nano scripts/build.sh
```

Add:

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

PROJECT_DIR="$(
    cd "$(dirname "${BASH_SOURCE[0]}")/.." \
    && pwd
)"

BUILD_DIR="${PROJECT_DIR}/build"
ARTIFACT_DIR="${PROJECT_DIR}/artifacts"

COMMIT_SHA="$(
    git -C "$PROJECT_DIR" rev-parse HEAD
)"

SHORT_SHA="$(
    git -C "$PROJECT_DIR" rev-parse --short=7 HEAD
)"

BUILD_TIME="$(
    date -u '+%Y-%m-%dT%H:%M:%SZ'
)"

RELEASE_ID="$(
    date -u '+%Y%m%d-%H%M%S'
)-${SHORT_SHA}"

rm -rf "$BUILD_DIR"

mkdir -p \
    "$BUILD_DIR" \
    "$ARTIFACT_DIR"

cp -a \
    "${PROJECT_DIR}/application/." \
    "$BUILD_DIR/"

cat > "${BUILD_DIR}/BUILD-INFO" <<EOF
release_id=${RELEASE_ID}
commit_sha=${COMMIT_SHA}
build_time=${BUILD_TIME}
EOF

ARTIFACT="${ARTIFACT_DIR}/${RELEASE_ID}.tar.gz"

tar \
    -C "$BUILD_DIR" \
    -czf "$ARTIFACT" \
    .

sha256sum "$ARTIFACT" \
    > "${ARTIFACT}.sha256"

printf '%s\n' "$RELEASE_ID" \
    > "${ARTIFACT_DIR}/LATEST_RELEASE"

printf '%s\n' "$ARTIFACT"
```

Make executable:

```bash
chmod 0755 scripts/build.sh
```

Run:

```bash
./scripts/build.sh
```

Inspect:

```bash
find artifacts \
  -maxdepth 1 \
  -type f \
  -print
```

You should have:

```text
RELEASE_ID.tar.gz
RELEASE_ID.tar.gz.sha256
LATEST_RELEASE
```

# Phase 6: Configure Nginx

Create:

```bash
sudo nano /etc/nginx/sites-available/veriqta-portal
```

Add:

```nginx
server {
    listen 80;
    listen [::]:80;

    server_name _;

    access_log /var/log/nginx/veriqta-portal-access.log;
    error_log /var/log/nginx/veriqta-portal-error.log warn;

    server_tokens off;

    location / {
        proxy_pass http://127.0.0.1:8000;

        proxy_http_version 1.1;

        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 5s;
        proxy_read_timeout 30s;
    }
```

# Phase 9: Build the Deployment Script on `app01`

Create:

```bash
sudo nano /usr/local/sbin/veriqta-deploy-release
```

Add:

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

BASE_DIR="/opt/veriqta-portal"
INCOMING_DIR="${BASE_DIR}/incoming"
RELEASES_DIR="${BASE_DIR}/releases"
CURRENT_LINK="${BASE_DIR}/current"
HISTORY_FILE="${BASE_DIR}/shared/deployment-history.log"
LOCK_FILE="${BASE_DIR}/shared/deployment.lock"

RELEASE_ID="${1:-}"

if [[ -z "$RELEASE_ID" ]]; then
    echo "Usage: $0 RELEASE_ID" >&2
    exit 2
fi

if [[ ! "$RELEASE_ID" =~ ^[A-Za-z0-9._-]+$ ]]; then
    echo "Invalid release ID." >&2
    exit 2
fi

ARTIFACT="${INCOMING_DIR}/${RELEASE_ID}.tar.gz"
CHECKSUM="${ARTIFACT}.sha256"
NEW_RELEASE="${RELEASES_DIR}/${RELEASE_ID}"

exec 9>"$LOCK_FILE"

if ! flock -n 9; then
    echo "Another deployment is already running." >&2
    exit 1
fi

log() {
    printf '%s %s\n' \
        "$(date -u '+%Y-%m-%dT%H:%M:%SZ')" \
        "$*" \
        | tee -a "$HISTORY_FILE"
}

[[ -f "$ARTIFACT" ]] || {
    log "ERROR release=${RELEASE_ID} artifact_missing"
    exit 1
}

[[ -f "$CHECKSUM" ]] || {
    log "ERROR release=${RELEASE_ID} checksum_missing"
    exit 1
}

cd "$INCOMING_DIR"

sha256sum -c \
    "$(basename "$CHECKSUM")"

if [[ -e "$NEW_RELEASE" ]]; then
    log "ERROR release=${RELEASE_ID} already_exists"
    exit 1
fi

PREVIOUS_RELEASE=""

if [[ -L "$CURRENT_LINK" ]]; then
    PREVIOUS_RELEASE="$(
        readlink -f "$CURRENT_LINK"
    )"
fi

mkdir -p "$NEW_RELEASE"

cleanup_failed_release() {
    rm -rf "$NEW_RELEASE"
}

trap cleanup_failed_release ERR

tar \
    -xzf "$ARTIFACT" \
    -C "$NEW_RELEASE"

chown -R \
    veriqta:veriqta \
    "$NEW_RELEASE"

find "$NEW_RELEASE" \
    -type d \
    -exec chmod 0750 {} \;

find "$NEW_RELEASE" \
    -type f \
    -exec chmod 0640 {} \;

chmod 0750 \
    "${NEW_RELEASE}/app.py"

python3 -m py_compile \
    "${NEW_RELEASE}/app.py"

ln -sfn \
    "$NEW_RELEASE" \
    "${CURRENT_LINK}.new"

mv -Tf \
    "${CURRENT_LINK}.new" \
    "$CURRENT_LINK"

log \
    "ACTIVATE release=${RELEASE_ID} previous=${PREVIOUS_RELEASE:-none}"

if ! sudo /usr/local/sbin/veriqta-service-control restart; then
    log "ERROR release=${RELEASE_ID} service_restart_failed"

    if [[ -n "$PREVIOUS_RELEASE" ]]; then
        ln -sfn \
            "$PREVIOUS_RELEASE" \
            "${CURRENT_LINK}.rollback"

        mv -Tf \
            "${CURRENT_LINK}.rollback" \
            "$CURRENT_LINK"

        sudo /usr/local/sbin/veriqta-service-control restart || true
    fi

    exit 1
fi

HEALTH_OK=0

for attempt in {1..10}; do

    if curl \
        --fail \
        --silent \
        --show-error \
        http://127.0.0.1:8000/health \
        >/dev/null; then

        HEALTH_OK=1
        break
    fi

    sleep 2
done

if (( HEALTH_OK == 0 )); then

    log "ERROR release=${RELEASE_ID} health_check_failed"

    if [[ -n "$PREVIOUS_RELEASE" ]]; then

        log \
            "ROLLBACK from=${NEW_RELEASE} to=${PREVIOUS_RELEASE}"

        ln -sfn \
            "$PREVIOUS_RELEASE" \
            "${CURRENT_LINK}.rollback"

        mv -Tf \
            "${CURRENT_LINK}.rollback" \
            "$CURRENT_LINK"

        sudo /usr/local/sbin/veriqta-service-control restart

        sleep 2

        curl \
            --fail \
            --silent \
            --show-error \
            http://127.0.0.1:8000/health \
            >/dev/null

        log "ROLLBACK_OK release=${PREVIOUS_RELEASE}"
    fi

    exit 1
fi

trap - ERR

log "SUCCESS release=${RELEASE_ID}"

rm -f \
    "$ARTIFACT" \
    "$CHECKSUM"

echo "Deployment successful: ${RELEASE_ID}"
```

Protect:

```bash
sudo chown root:root \
  /usr/local/sbin/veriqta-deploy-release
```

```bash
sudo chmod 0755 \
  /usr/local/sbin/veriqta-deploy-release
```

# SSH Host-Key Trust

Do **not** solve host-key verification problems with:

```text
StrictHostKeyChecking=no
```

That disables an important SSH identity check.

Instead, obtain and verify the target host key through a trusted channel.

On `app01`, inspect the fingerprint directly:

```bash
sudo ssh-keygen \
  -lf /etc/ssh/ssh_host_ed25519_key.pub
```

From `ci01`, retrieve the advertised key:

```bash
ssh-keyscan \
  -t ed25519 \
  APP01_IP
```

Compare the fingerprint against the one you verified on `app01`.

Only after verification should the key be trusted by the automation environment.

This distinction matters:

```text
SSH USER KEY
    proves
client identity to server

SSH HOST KEY
    proves
server identity to client
```

You need both.

# Phase 15: Create the Jenkins Pipeline

Create:

```bash
nano Jenkinsfile
```

Use a declarative pipeline:

```groovy
pipeline {

    agent any

    options {
        timestamps()
        disableConcurrentBuilds()
        buildDiscarder(
            logRotator(
                numToKeepStr: '20',
                artifactNumToKeepStr: '10'
            )
        )
    }

    environment {
        APP_HOST = 'APP01_IP'
        APP_USER = 'deploy'
    }

    stages {

        stage('Checkout') {
            steps {
                checkout scm

                sh '''
                    set -eux

                    git rev-parse HEAD
                    git status --short
                '''
            }
        }

        stage('Validate') {
            steps {
                sh '''
                    set -eux

                    python3 -m py_compile \
                        application/app.py \
                        application/test_app.py

                    bash -n scripts/test.sh
                    bash -n scripts/build.sh
                '''
            }
        }

        stage('Test') {
            steps {
                sh '''
                    set -eux

                    ./scripts/test.sh
                '''
            }
        }

        stage('Build') {
            steps {
                sh '''
                    set -eux

                    ./scripts/build.sh

                    RELEASE_ID="$(cat artifacts/LATEST_RELEASE)"

                    sha256sum -c \
                        "artifacts/${RELEASE_ID}.tar.gz.sha256"

                    tar -tzf \
                        "artifacts/${RELEASE_ID}.tar.gz"
                '''
            }
        }

        stage('Archive') {
            steps {
                archiveArtifacts(
                    artifacts: 'artifacts/*.tar.gz,artifacts/*.sha256,artifacts/LATEST_RELEASE',
                    fingerprint: true
                )
            }
        }

        stage('Deploy') {
            steps {
                sshagent(
                    credentials: ['veriqta-app01-deploy']
                ) {
                    sh '''
                        set -eux

                        RELEASE_ID="$(cat artifacts/LATEST_RELEASE)"

                        scp \
                            "artifacts/${RELEASE_ID}.tar.gz" \
                            "${APP_USER}@${APP_HOST}:/opt/veriqta-portal/incoming/"

                        scp \
                            "artifacts/${RELEASE_ID}.tar.gz.sha256" \
                            "${APP_USER}@${APP_HOST}:/opt/veriqta-portal/incoming/"

                        ssh \
                            "${APP_USER}@${APP_HOST}" \
                            "sudo /usr/local/sbin/veriqta-deploy-release '${RELEASE_ID}'"
                    '''
                }
            }
        }

        stage('Verify') {
            steps {
                sh '''
                    set -eux

                    curl \
                        --fail \
                        --silent \
                        --show-error \
                        "http://${APP_HOST}/health"

                    curl \
                        --fail \
                        --silent \
                        --show-error \
                        "http://${APP_HOST}/"
                '''
            }
        }
    }

    post {

        success {
            echo 'CI/CD deployment completed successfully.'
        }

        failure {
            echo 'Pipeline failed. Inspect the failed stage before retrying.'
        }

        always {
            sh '''
                echo "Build: ${BUILD_NUMBER}"
                echo "Commit: ${GIT_COMMIT:-unknown}"
            '''
        }
    }
}
```

Replace:

```text
APP01_IP
```

with your lab target.

# 15. Security

A CI/CD server is security-sensitive infrastructure.

Why?

Because it can often:

```text
read source code
access credentials
build artifacts
connect to servers
change production software
restart services
```

A compromised deployment server can become a path to every server it controls.

Treat Jenkins as privileged infrastructure.

---

## Security Boundary

```text
DEVELOPER
   |
   v
SOURCE CONTROL
   |
   v
JENKINS
   |
   | dedicated credential
   v
DEPLOY USER
   |
   | controlled sudo
   v
DEPLOYMENT HELPER
   |
   v
APPLICATION RELEASE
   |
   v
VERIQTA RUNTIME USER
```

Each identity has a different job.

---

## Do Not Run Jenkins as Root

Verify:

```bash

  | grep '[j]enkins'
```

You should see the Jenkins service under its dedicated account.

---

## Protect Credentials

Do not place secrets in:

```text
Jenkinsfile
Git repository
shell scripts
build artifacts
console output
BUILD-INFO
```

Use Jenkins credentials for deployment secrets.

---

## Protect SSH Host Verification

Never make this your normal automation:

```bash
ssh \
  -o StrictHostKeyChecking=no \
  ...
```

It makes automation easier by removing an important security check.

Solve trust correctly instead.

---

## Restrict Deployment Privilege

`deploy` should not be:

```text
root
```

and should not have unrestricted passwordless sudo.

Its privileged path should be small, reviewable, and purpose-built.

---

## Protect Runtime Account

Check:

```bash

```

The runtime account should not have an ordinary interactive login shell.

---

## Protect Jenkins Network Exposure

Do not expose port:

```text

```

to networks that do not need Jenkins access.

For a production design you would normally add stronger ingress controls, TLS, centralized identity, hardened authentication, authorization, patching, and monitoring.

# Rollback Engineering

A rollback is not:

```text
git pull something old
```

Your releases are immutable directories.

Example:

```text
releases/
├── release-A
├── release-B
└── release-C

current -> release-C
```

Rollback means:

```text
current -> release-B
```

followed by:

```text
restart
health check
verification
```

---

# Manual Rollback Script

Create on `app01`:

```bash
sudo nano /usr/local/sbin/veriqta-rollback
```

Add:

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

BASE_DIR="/opt/veriqta-portal"
RELEASES_DIR="${BASE_DIR}/releases"
CURRENT_LINK="${BASE_DIR}/current"
HISTORY_FILE="${BASE_DIR}/shared/deployment-history.log"
LOCK_FILE="${BASE_DIR}/shared/deployment.lock"

TARGET_RELEASE="${1:-}"

if [[ -z "$TARGET_RELEASE" ]]; then
    echo "Usage: $0 RELEASE_ID" >&2
    exit 2
fi

if [[ ! "$TARGET_RELEASE" =~ ^[A-Za-z0-9._-]+$ ]]; then
    echo "Invalid release ID." >&2
    exit 2
fi

TARGET_PATH="${RELEASES_DIR}/${TARGET_RELEASE}"

[[ -d "$TARGET_PATH" ]] || {
    echo "Release does not exist: $TARGET_RELEASE" >&2
    exit 1
}

exec 9>"$LOCK_FILE"

flock -n 9 || {
    echo "Another deployment operation is running." >&2
    exit 1
}

CURRENT_RELEASE="$(
    readlink -f "$CURRENT_LINK" 2>/dev/null \
    || true
)"

ln -sfn \
    "$TARGET_PATH" \
    "${CURRENT_LINK}.rollback"

mv -Tf \
    "${CURRENT_LINK}.rollback" \
    "$CURRENT_LINK"

sudo /usr/local/sbin/veriqta-service-control restart

for attempt in {1..10}; do

    if curl \
        --fail \
        --silent \
        http://127.0.0.1:8000/health \
        >/dev/null; then

        printf '%s ROLLBACK from=%s to=%s\n' \
            "$(date -u '+%Y-%m-%dT%H:%M:%SZ')" \
            "${CURRENT_RELEASE:-unknown}" \
            "$TARGET_PATH" \
            >> "$HISTORY_FILE"

        echo "Rollback successful."
        exit 0
    fi

    sleep 2
done

echo "Rollback target failed health validation." >&2
exit 1
```

Protect it and allow the exact command through your controlled sudo policy if Jenkins/deploy needs it.

# Important Rollback Limitation

Filesystem rollback is straightforward because releases are versioned.

Database rollback is not.

If release `1.2.0` changes a database schema incompatibly, pointing the application back to `1.1.0` may not restore service.

That introduces a deeper production principle:

> Application deployment and database migration strategy must be designed together.

For this project, the demonstration application intentionally avoids schema migrations.

Document this as a limitation.

# 23. Interview Preparation

### What is CI?

Continuous Integration is the practice of frequently integrating code changes and automatically validating them through activities such as builds and tests.

### What is continuous delivery?

A practice where software remains in a deployable state and releases can be promoted through an automated process, often with an explicit production approval step.

### What is continuous deployment?

A model where qualifying changes can be automatically released to production without a manual production deployment decision.

### Is this lab automatically a full continuous-deployment production system?

No.

It demonstrates an automated deployment pipeline in a controlled lab. Production promotion policy is a separate organizational and technical decision.

### Why separate `ci01` and `app01`?

Because build infrastructure and runtime infrastructure have different responsibilities, privileges, failure domains, and security boundaries.

### Why shouldn't Jenkins run the application?

Jenkins is the deployment system, not the application runtime.

### Why create a deployment artifact?

It gives you a defined unit that can be identified, checksummed, archived, transferred, deployed, and audited.

### Why not simply run `git pull` on `app01`?

Direct repository pulls couple the target server to source-control state and can create less controlled deployments. A built artifact provides a clearer boundary between source, build, and release.

### Why include the Git SHA in `BUILD-INFO`?

To connect the deployed release back to the exact source revision.

### Why calculate SHA-256?

To verify artifact integrity.

### Does a checksum prove who created the artifact?

No.

A checksum proves that the bytes match the expected digest. It is not by itself artifact signing or provenance verification.

### Why use versioned release directories?

They prevent old and new application files from being mixed and preserve known releases for rollback.

### Why use a `current` symlink?

It gives the runtime a stable path while allowing the target release to change quickly.

### Why use a temporary symlink followed by `mv`?

It makes activation much closer to an atomic filesystem operation than deleting and rebuilding the active application directory in place.

### Why use `flock`?

To prevent overlapping deployment operations from changing release state concurrently.

### Why does the application use systemd?

systemd provides service lifecycle management, restart behavior, startup at boot, identity configuration, and journald integration.

### Why run the application as `veriqta`?

The application does not need root privileges.

### Why have a separate `deploy` account?

Deployment and runtime are different responsibilities.

### Why not give `deploy` unrestricted sudo?

A compromised deployment credential should not automatically become unrestricted root access.

### Why use a controlled privileged helper?

It creates a smaller, auditable administrative interface for the deployment process.

### Why is SSH host-key verification important?

It helps the client verify that it is connecting to the intended server.

### What is the difference between an SSH user key and host key?

The user key authenticates the client/user to the server. The host key authenticates the server to the client.

### Why is `StrictHostKeyChecking=no` dangerous?

It removes an important server-identity check and can make man-in-the-middle or host-substitution attacks easier.

### What is a health check?

A test of whether the deployed application is functioning according to a defined condition.

### Why isn't `systemctl is-active` enough?

A process can be running while the application is unable to serve valid requests.

### Why check through Nginx after deployment?

Because users reach the application through Nginx. Testing only the backend does not validate the complete request path.

### What is rollback?

Restoring a previously known-good application release when the new release fails.

### Why can application rollback become difficult with database changes?

Because an older application version may not be compatible with a newer database schema.

### Why archive artifacts in Jenkins?

To preserve the build output associated with the pipeline execution.

### Why limit build retention?

Build logs, workspaces, and artifacts consume disk space.

### What happens if the CI server runs out of disk?

Builds, checkouts, artifact creation, Jenkins operations, or even system services may fail.

### What happens if `app01` runs out of disk?

New releases may fail to transfer or extract, logs may fail, and services may become unstable.

### What causes an Nginx 502 here?

Nginx is available but cannot successfully communicate with its upstream application.

### How would you investigate?

Check:

```text
Nginx status
Nginx error log
application status
application journal
127.0.0.1:8000 listener
direct backend health request
```

### Why should a pipeline stop after a failed test?

A known failing build should not continue toward deployment.

### What is fail-fast behavior?

Stopping a workflow as soon as a required condition fails rather than continuing with invalid state.

### What is deployment traceability?

The ability to connect a running release to the build, artifact, commit, deployment event, and relevant operational evidence.

### Why is CI/CD infrastructure a high-value security target?

Because it often has access to source code, credentials, artifacts, and deployment targets.

### What is the most important troubleshooting principle in this project?

Identify the stage where the workflow stopped before changing the system.

# Production Limitations

This is a serious mid-level CI/CD lab, but do not describe it as a complete enterprise production platform.

It still has important limitations.

The application server is a single node:

```text
             CLIENT
                |
                v
             app01
            /     \
         Nginx   Application
```

If `app01` disappears, the service disappears.

Jenkins is also a single CI/CD server.
