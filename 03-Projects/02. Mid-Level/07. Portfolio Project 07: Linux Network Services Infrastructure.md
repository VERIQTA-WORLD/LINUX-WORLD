# 01. Project Title

## Linux Network Services Infrastructure

A Linux server can have a valid IP address and still be effectively unusable.

A client can reach its default gateway and still fail to access an application.

A DNS server can be running while returning the wrong answer.

A DHCP server can be active while clients receive no addresses.

And this:

```bash
ping 8.8.8.8
```

does not prove that DNS works.

In this project, you are going to build the network-services layer that other Linux infrastructure depends on.

You will create an environment where Linux systems can:

```text
join a subnet
    ↓
receive network configuration
    ↓
learn their default gateway
    ↓
learn which DNS server to use
    ↓
resolve internal hostnames
    ↓
resolve external names
    ↓
reach other services
```

You will build and operate:

```text
DNS
DHCP
static infrastructure addressing
dynamic client addressing
forward and reverse DNS
DNS forwarding
DHCP reservations
network configuration
name resolution
firewall controls
service logging
configuration validation
network diagnostics
failure detection
recovery procedures
```

More importantly, you will deliberately break those layers.

You will troubleshoot situations such as:

```text
client receives no DHCP lease
client receives the wrong DNS server
client has an IP but no default route
DNS server is reachable but returns NXDOMAIN
forward lookup works but reverse lookup fails
internal DNS works but external resolution fails
DHCP service is active but listening on the wrong interface
DNS configuration is syntactically valid but contains the wrong record
firewall blocks DNS
duplicate IP addresses appear
client keeps using stale DNS information
```

The goal is not to memorize `dig`, `ip`, or `systemctl`.

The goal is to understand how Linux network services fit together well enough that when:

```text
"The network is broken."
```

is the only incident description you receive, you can turn that vague symptom into evidence.

# Understanding the SOA Record

This section:

```dns
@ IN SOA ns01.lab.veriqta.test. admin.lab.veriqta.test.
```

defines important administrative information about the zone.

The first hostname is the primary authoritative server.

The second represents an administrative email address using DNS zone-file notation.

For example:

```text
admin.lab.veriqta.test.
```

conceptually corresponds to an address such as:

```text
admin@lab.veriqta.test
```

---

# Understand the Serial

You used:

```text
2026092401
```

A common human-readable scheme is:

```text
YYYYMMDDNN
```

where:

```text
YYYY = year
MM   = month
DD   = day
NN   = revision number
```

If you make another zone change on the same day:

```text
2026092402
```

This becomes particularly important once secondary DNS servers exist.

---

# Why Query the Server Directly?

This:

```bash
dig @192.168.50.10 web01.lab.veriqta.test
```

tests:

```text
CLIENT
   ↓
SPECIFIC DNS SERVER
   ↓
ZONE
   ↓
RECORD
```

It bypasses the client's normal resolver selection.

That makes it extremely useful for isolating problems.

If direct query works but:

```bash
dig web01.lab.veriqta.test
```

fails, the DNS server itself may be healthy.

The problem may instead be:

```text
client resolver configuration
DHCP DNS option
systemd-resolved
/etc/resolv.conf
```

That distinction is fundamental.

# Phase 12: Build Reverse DNS


```text

```

```text

```

```text

```


```conf
zone "50.168.192.in-addr.arpa" {
    type master;
    file "/etc/bind/zones/db.192.168.50";

```


```dns
$TTL 3600

@   IN  SOA ns01.lab.veriqta.test. admin.lab.veriqta.test. (

        900
        1209600
        300
```

# Phase 13: Configure BIND Listening and Recursion Policy

Inspect:

```bash
sudo nano /etc/bind/named.conf.options
```

For this lab, you want BIND to provide internal authoritative DNS and controlled recursion for your lab network.

A conceptual configuration is:

```conf
options {
    directory "/var/cache/bind";

    listen-on {
        127.0.0.1;
        192.168.50.10;
    };

    listen-on-v6 { none; };

    allow-query {
        localhost;
        192.168.50.0/24;
    };

    recursion yes;

    allow-recursion {
        localhost;
        192.168.50.0/24;
    };

    dnssec-validation auto;
};
```

If your lab needs explicit upstream resolvers, configure only resolvers appropriate to your environment rather than blindly copying public resolver addresses.

The important security principle is:

> Do not accidentally build an unrestricted recursive DNS resolver reachable from networks that should not use it.

Validate:

```bash

```

Reload.

Inspect:

Remember DNS commonly uses:

# Phase 16: Understand Why DHCP Is Different

A client that does not yet have a valid IP configuration cannot simply send a normal unicast request to a known DHCP server.

Initial DHCP relies heavily on broadcast behavior within the local broadcast domain.

That means:

```text
client01
```

and:

```text
ns01
```

must be on the appropriate Layer-2 network unless a DHCP relay exists.

This matters because a DHCP server can be perfectly healthy and still never receive the client's request.

# Phase 28: Build a Network Validation Script

Create on `ns01`:

```bash
sudo nano \
  /opt/veriqta-network/bin/validate-network.sh
```

Add:

```bash
#!/usr/bin/env bash

set -u
set -o pipefail

DNS_SERVER="192.168.50.10"
ZONE="lab.veriqta.test"

PASS=0
FAIL=0

pass() {
    printf 'PASS: %s\n' "$1"
    PASS=$((PASS + 1))
}

fail() {
    printf 'FAIL: %s\n' "$1"
    FAIL=$((FAIL + 1))
}

check_command() {
    if command -v "$1" >/dev/null 2>&1; then
        pass "command available: $1"
    else
        fail "command missing: $1"
    fi
}

check_service() {
    local service="$1"

    if systemctl is-active --quiet "$service"; then
        pass "service active: $service"
    else
        fail "service inactive: $service"
    fi
}

check_dns_a() {
    local name="$1"
    local expected="$2"
    local actual

    actual="$(
        dig +short @"$DNS_SERVER" "$name" A \
        | tail -n 1
    )"

    if [[ "$actual" == "$expected" ]]; then
        pass "$name -> $expected"
    else
        fail "$name expected $expected, got ${actual:-NO_ANSWER}"
    fi
}

check_dns_ptr() {
    local address="$1"
    local expected="$2"
    local actual

    actual="$(
        dig +short @"$DNS_SERVER" -x "$address" \
        | tail -n 1
    )"

    if [[ "$actual" == "$expected" ]]; then
        pass "$address -> $expected"
    else
        fail "$address expected $expected, got ${actual:-NO_ANSWER}"
    fi
}

check_command dig
check_command ip
check_command ss
check_command systemctl

check_service bind9
check_service kea-dhcp4-server

check_dns_a \
    "ns01.${ZONE}" \
    "192.168.50.10"

check_dns_a \
    "web01.${ZONE}" \
    "192.168.50.20"

check_dns_a \
    "db01.${ZONE}" \
    "192.168.50.30"

check_dns_ptr \
    "192.168.50.10" \
    "ns01.${ZONE}."

check_dns_ptr \
    "192.168.50.20" \
    "web01.${ZONE}."

check_dns_ptr \
    "192.168.50.30" \
    "db01.${ZONE}."

if ss -lun | grep -q ':53 '; then
    pass "UDP/53 listener detected"
else
    fail "UDP/53 listener not detected"
fi

if ss -ltn | grep -q ':53 '; then
    pass "TCP/53 listener detected"
else
    fail "TCP/53 listener not detected"
fi

printf '\nSummary: %d passed, %d failed\n' \
    "$PASS" "$FAIL"

if (( FAIL > 0 )); then
    exit 1
fi

exit 0
```

Make executable:

```bash
sudo chmod 0750 \
  /opt/veriqta-network/bin/validate-network.sh
```

Run:

```bash
sudo /opt/veriqta-network/bin/validate-network.sh
```

If your actual BIND service unit is not `bind9`, adjust the script to the unit discovered earlier.

Do not hide environmental differences by pretending they do not exist.

```bash
#!/usr/bin/env bash

set -u
set -o pipefail

DNS_SERVER="192.168.50.10"
WEB_IP="192.168.50.20"
WEB_NAME="web01.lab.veriqta.test"

failures=0

check() {
    local description="$1"
    shift

    if "$@" >/dev/null 2>&1; then
        echo "PASS: $description"
    else
        echo "FAIL: $description"
        failures=$((failures + 1))
    fi
}

check \
    "lab interface has IPv4 address" \
    sh -c "ip -4 addr show | grep -q '192\.168\.50\.'"

check \
    "DNS server reachable by direct query" \
    dig +time=2 +tries=1 @"$DNS_SERVER" "$WEB_NAME"

resolved="$(
    dig +short @"$DNS_SERVER" "$WEB_NAME" A \
    | tail -n 1
)"

if [[ "$resolved" == "$WEB_IP" ]]; then
    echo "PASS: DNS answer is $WEB_IP"
else
    echo "FAIL: DNS returned ${resolved:-NO_ANSWER}"
    failures=$((failures + 1))
fi

check \
    "web service reachable by IP" \
    curl --fail --silent --show-error \
    "http://${WEB_IP}/"

check \
    "web service reachable by DNS name" \
    curl --fail --silent --show-error \
    "http://${WEB_NAME}/"

if (( failures > 0 )); then
    echo "NETWORK VALIDATION FAILED"
    exit 1
fi

echo "NETWORK VALIDATION PASSED"
```

Make executable:

```bash
sudo chmod 0755 \
  /usr/local/bin/network-check
```

# 15. Security

Network infrastructure deserves stricter treatment than an ordinary test service.

If DNS or DHCP is compromised, an attacker may be able to influence where clients send traffic.

---

# DNS Security Controls

Your DNS service should:

```text
listen only where required
allow queries only from intended networks
restrict recursion
avoid unnecessary exposure
run as the packaged service account
protect zone files from unauthorized modification
log service failures
validate configuration before reload
```

Inspect:

```bash
sudo ss -lntup | grep ':53'
```

Ask:

```text
Is BIND listening only where I intended?
```

---

# DHCP Security Controls

Your DHCP service should:

```text
bind only to intended interfaces
serve only intended subnets
avoid overlapping address pools
avoid infrastructure static ranges
avoid unauthorized networks
log lease activity
protect configuration files
```

A DHCP server attached to the wrong Layer-2 network can create a serious outage.

---

# Configuration Permissions

Inspect:

```bash
sudo find /etc/bind \
  -maxdepth 2 \
  -type f \
  -printf '%u:%g %m %p\n'
```

Then:

```bash
sudo find /etc/kea \
  -maxdepth 2 \
  -type f \
  -printf '%u:%g %m %p\n'
```

Look for unexpectedly writable files.

Check world-writable files:

```bash
sudo find /etc/bind /etc/kea \
  -type f \
  -perm -0002 \
  -print
```

You should not casually have world-writable service configuration.



```text

```

---

# DNS Response Interpretation

## `NOERROR`

The query was processed successfully.

It does not always mean the exact record type you requested exists.

Inspect the answer section.

## `NXDOMAIN`

The requested domain name does not exist according to the answering DNS authority.

## `SERVFAIL`

The server could not successfully complete the query.

Possible causes include:

```text
upstream failure
DNSSEC issue
broken zone
server problem
delegation problem
```

## Timeout

No usable response arrived within the query timeout.

Investigate:

```text
network path
firewall
service listener
wrong DNS server
server failure
```

# 23. Interview Preparation

### What is DNS?

DNS is a distributed naming system that maps names to information such as IP addresses.

### What is an A record?

An A record maps a hostname to an IPv4 address.

Example:

```text
web01.lab.veriqta.test → 192.168.50.20
```

### What is a PTR record?

A PTR record is commonly used for reverse DNS mapping.

Example:

```text
192.168.50.20 → web01.lab.veriqta.test
```

### What is an NS record?

It identifies an authoritative name server for a DNS zone.

### What is an SOA record?

The Start of Authority record contains administrative information about a DNS zone, including its serial and timing values.

### Why does the zone serial matter?

Secondary DNS servers use serial changes as part of determining whether zone data has changed.

### What is TTL?

Time To Live controls how long DNS information may be cached.

### What is NXDOMAIN?

It indicates that the queried domain name does not exist according to DNS.

### What is SERVFAIL?

It indicates that the DNS server could not successfully complete the request.

### Is a timeout the same as NXDOMAIN?

No.

NXDOMAIN is a DNS response.

A timeout means the client did not receive a usable response within the allowed time.

### What is authoritative DNS?

An authoritative DNS server provides authoritative answers for zones it serves.

### What is recursive DNS?

A recursive resolver obtains answers on behalf of clients by querying other DNS infrastructure or using configured forwarding behavior.

### Why restrict recursion?

An unnecessarily open recursive resolver can be abused and exposes infrastructure to unwanted external use.

### Why does DNS use both UDP and TCP?

DNS commonly uses UDP for many queries but also uses TCP in situations including larger responses and operations where TCP is required.

### What port does DNS use?

Port 53 over UDP and TCP.

### What ports does DHCPv4 use?

Typically:

```text
UDP 67 = server
UDP 68 = client
```

### What is DHCP?

DHCP dynamically provides network configuration to clients.

### What is DORA?

```text
Discover
Offer
Request
Acknowledge
```

### Why does DHCP use broadcast during initial configuration?

A new client may not yet know its own usable address, the DHCP server's address, or other network parameters.

### What information can DHCP distribute?

Examples include:

```text
IP address
subnet information
default gateway
DNS server
domain/search information
lease lifetime
```

### What is a DHCP reservation?

It associates a client identifier, commonly a MAC address in simple environments, with a predictable address assignment.

### Why separate static infrastructure addresses from the DHCP pool?

To reduce the risk of DHCP assigning an address already manually assigned to infrastructure.

### What is a DHCP lease?

A time-limited assignment of network configuration to a client.

### What happens when the DHCP server goes down?

Existing clients may continue using valid leases temporarily, while new clients or clients requiring renewal may eventually encounter problems.

### Why can that make DHCP outages confusing?

Because the failure may not affect every client immediately.

### What is Netplan?

Netplan is a configuration abstraction used by Ubuntu to define persistent network configuration and generate configuration for supported backends.

### What is `systemd-resolved`?

It is a system service that can provide local name-resolution functionality and manage per-link DNS information.

### Why might `/etc/resolv.conf` contain `127.0.0.53`?

Because applications may be using the local systemd-resolved stub resolver.

### How do you inspect the actual DNS servers?

Use:

```bash
resolvectl status
```

### Why is `dig @server name` useful?

It sends the DNS query directly to a specified DNS server, helping isolate server-side DNS from normal client resolver configuration.

### Why is `getent hosts` useful?

It uses the system's configured name-service path rather than testing only raw DNS.

### Why can `dig` work while an application still fails to resolve a name?

The application may use the system resolver path, search domains, NSS configuration, or other behavior differently from a direct `dig` query.

### Why can `ping` be a poor application-health test?

Successful ICMP does not prove that the required application protocol and port are working.

### What would you test for a web application?

At minimum:

```text
DNS
IP connectivity
TCP service
HTTP/HTTPS response
application behavior
```

### What does `ss` tell you?

It helps show sockets, including listening services and associated processes.

### What does `tcpdump` tell you?

It shows actual packets observed on an interface, helping determine whether traffic reaches or leaves a system.

### When would you use `tcpdump` for DHCP?

When you need to see whether Discover, Offer, Request and Acknowledgement traffic is actually occurring.

### When would you use `tcpdump` for DNS?

When you need to prove whether DNS queries reach the server and whether responses return.

### What is a default route?

It is the route used when no more-specific route matches a destination.

### Can same-subnet communication work without a default route?

Yes.

A host can communicate with destinations on directly connected networks without using a default gateway.

### Why might internal services work while the internet does not?

Possible causes include:

```text
missing default route
gateway failure
NAT failure
upstream routing
firewall
external DNS
```

### Why is restarting networking a poor first troubleshooting step?

It destroys useful state and may temporarily hide the actual root cause.

### What should you do first?

Collect evidence and determine which layer is failing.

# Production Limitations You Must Document

This lab gives you a strong operational network-services environment.

It is **not** a complete enterprise DNS/DHCP architecture.

Your final documentation should explicitly identify its limitations.

The biggest one is obvious:

```text
                       ns01
                        |
                  +-----+-----+
                  |           |
                 DNS         DHCP
                  |           |
                  +-----+-----+
                        |
                    FAILURE
                        X
```

`ns01` is a major single point of failure.

A stronger production architecture could introduce:

```text
+-------------------+        +-------------------+
|       ns01        |        |       ns02        |
| Primary DNS       |------->| Secondary DNS     |
+-------------------+        +-------------------+

          DHCP redundancy / HA design
                     |
          +----------+----------+
          |                     |
     DHCP node A           DHCP node B
```

You would also consider:

```text
multiple DNS servers
secondary authoritative DNS
zone transfers
TSIG
DHCP high availability
DHCP relay
multiple subnets
VLANs
monitoring
centralized logging
configuration management
automated backups
configuration version control
DNSSEC where appropriate
IPv6
capacity planning
change management
access control
```

Those are deliberate next steps.

They are not excuses to turn this Mid-Level project into an enterprise network architecture project before you have mastered the underlying Linux services.
