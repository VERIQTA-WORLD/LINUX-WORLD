# 01. Project Title

## Linux Disaster Recovery Platform

A backup is not a disaster-recovery strategy.

This:

```bash
tar -czf backup.tar.gz /srv/application
```

does not prove you can recover a failed Linux service.

It only proves that you created an archive.

In this project, you are going much further.

You will build a Linux disaster-recovery platform capable of answering the questions that matter when a server is unavailable:

```text
What must be recovered?

Where are the backups?

How recent are they?

Are they intact?

Which backup should you restore?

What dependencies must exist first?

In what order should services be recovered?

How do you restore configuration?

How do you restore application data?

How do you restore the database?

How do you verify permissions?

How do you verify services?

How do you know the application is actually working?

How much data did you lose?

How long did recovery take?

Did you meet the RPO?

Did you meet the RTO?

Can another engineer perform the recovery without you?
```

You will deliberately destroy parts of the lab environment and recover them from your backup system.

That final part matters.

A backup that has never been restored is an assumption.

A recovery process that has never been tested is a document.

You are going to test both.

# Phase 6: Define Recovery Requirements Before Backups

Before creating a single backup, decide what recovery means.

For this project, define:

### Target RPO

```text
RPO = 1 hour
```

### Target RTO

```text
RTO = 60 minutes
```

These are lab objectives, not universal production recommendations.

---

# Understanding RPO

**Recovery Point Objective** asks:

> How much data loss can the service tolerate?

Suppose:

```text
Last recoverable backup: 14:00
Disaster:                14:47
```

If you restore the 14:00 state:

```text
Potential data loss = 47 minutes
```

If your RPO is:

```text
1 hour
```

you are inside the objective.

If your RPO is:

```text
15 minutes
```

you missed it.

---

# Understanding RTO

**Recovery Time Objective** asks:

> How long can the service remain unavailable?

Suppose:

```text
Disaster declared: 14:47
Service restored:  15:25
```

Then:

```text
Actual recovery time = 38 minutes
```

With an RTO of 60 minutes:

```text
38 minutes <= 60 minutes
```

you met the target.

---

# RTO and RPO Are Different

```text
                     DISASTER
                         |
            <------------+------------>
                 DATA             TIME
                  |                 |
                  v                 v
                 RPO               RTO
```

RPO is primarily about **recoverable data age**.

RTO is primarily about **recovery duration**.

You can meet one and fail the other.

For example:

```text
Backup from 5 minutes ago
Recovery takes 4 hours
```

Excellent recovery point.

Poor recovery time.

Or:

```text
Backup from yesterday
Recovery takes 10 minutes
```

Fast recovery.

Potentially unacceptable data loss.

# 14. Automation

# Phase 16: Build the Backup Script

Create:

```bash
sudo nano /opt/veriqta-dr/bin/create-backup.sh
```

Add:

```bash
#!/usr/bin/env bash

set -Eeuo pipefail
umask 077

PROJECT_ROOT="/opt/veriqta-dr"
STAGING_ROOT="${PROJECT_ROOT}/staging"
LOG_DIR="${PROJECT_ROOT}/logs"

REMOTE_HOST="backup01"
REMOTE_ROOT="/srv/backups/prod01"

DATABASE="veriqta_portal"

LOCK_FILE="/run/lock/veriqta-dr-backup.lock"

timestamp="$(date -u '+%Y%m%dT%H%M%SZ')"
backup_name="backup-${timestamp}"
workdir="${STAGING_ROOT}/${backup_name}"
logfile="${LOG_DIR}/backup-${timestamp}.log"

mkdir -p "$STAGING_ROOT" "$LOG_DIR"

exec 9>"$LOCK_FILE"

if ! flock -n 9; then
    echo "Another backup process is already running."
    exit 1
fi

cleanup_on_error() {
    rc=$?

    if (( rc != 0 )); then
        echo "Backup failed with exit code ${rc}" >> "$logfile"
        rm -rf "$workdir"
    fi

    exit "$rc"
}

trap cleanup_on_error EXIT

log() {
    printf '%s %s\n' \
        "$(date --iso-8601=seconds)" \
        "$*" | tee -a "$logfile"
}

log "Starting backup ${backup_name}"

mkdir -p "$workdir/metadata"

log "Recording system metadata"

hostnamectl > "$workdir/metadata/hostnamectl.txt"
cp /etc/os-release "$workdir/metadata/os-release.txt"
uname -a > "$workdir/metadata/kernel.txt"
dpkg-query -W > "$workdir/metadata/packages.txt"

systemctl list-unit-files \
    > "$workdir/metadata/unit-files.txt"

systemctl list-units --type=service \
    > "$workdir/metadata/services.txt"

ss -lntup \
    > "$workdir/metadata/listeners.txt"

ufw status verbose \
    > "$workdir/metadata/firewall.txt" 2>&1 || true

stat \
    /srv/veriqta-portal \
    /srv/veriqta-portal/public \
    /etc/veriqta-portal \
    > "$workdir/metadata/permissions.txt"

log "Backing up application files"

tar \
    --numeric-owner \
    -czpf "$workdir/application.tar.gz" \
    /srv/veriqta-portal

log "Backing up configuration"

tar \
    --numeric-owner \
    -czpf "$workdir/configuration.tar.gz" \
    /etc/veriqta-portal \
    /etc/nginx/sites-available/veriqta-portal.conf

log "Creating database dump"

mariadb-dump \
    --single-transaction \
    --routines \
    --triggers \
    --databases "$DATABASE" \
    > "$workdir/database.sql"

test -s "$workdir/database.sql"

log "Creating manifest"

{
    echo "VERIQTA Linux Disaster Recovery Backup"
    echo "Backup ID: ${backup_name}"
    echo "Source host: $(hostname)"
    echo "Created UTC: $(date -u --iso-8601=seconds)"
    echo "Database: ${DATABASE}"
    echo
    echo "Contents:"
    find "$workdir" -maxdepth 2 -type f -printf '%P\n' | sort
} > "$workdir/MANIFEST.txt"

log "Generating checksums"

(
    cd "$workdir"
    find . -type f \
        ! -name SHA256SUMS \
        -print0 \
        | sort -z \
        | xargs -0 sha256sum \
        > SHA256SUMS
)

log "Verifying checksums before transfer"

(
    cd "$workdir"
    sha256sum --check SHA256SUMS
)

log "Transferring backup to ${REMOTE_HOST}"

rsync \
    -a \
    --protect-args \
    "$workdir/" \
    "${REMOTE_HOST}:${REMOTE_ROOT}/${backup_name}/"

log "Verifying remote backup exists"

ssh "$REMOTE_HOST" \
    "test -s '${REMOTE_ROOT}/${backup_name}/SHA256SUMS'"

log "Backup completed successfully: ${backup_name}"
```

# Understand the Important Parts

## `set -Eeuo pipefail`

This makes the script fail more predictably when commands fail, variables are missing, or pipelines encounter errors.

It is not a substitute for deliberate error handling.

---

## `umask 077`

New backup files should not become world-readable.

---

## `flock`

```bash
flock -n 9
```

prevents two backup jobs from running simultaneously.

Without locking:

```text
12:00 backup starts
12:01 another backup starts
```

Both could compete for resources or manipulate staging data simultaneously.

---

## UTC Backup Names

```bash
date -u '+%Y%m%dT%H%M%SZ'
```

produces identifiers similar to:

```text
20260924T120000Z
```

Using UTC reduces ambiguity when systems operate across time zones.

---

## `--numeric-owner`

When restoring Linux files, numeric ownership information can matter.

But you still need to ensure corresponding users/groups exist correctly on the recovery system.

A UID is not meaningful simply because an archive contains it.


# Build a Backup Validator

Create:

```bash
sudo nano /opt/veriqta-dr/bin/validate-backup.sh
```

Add:

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

if [[ $# -ne 1 ]]; then
    echo "Usage: $0 BACKUP_DIRECTORY" >&2
    exit 64
fi

BACKUP_DIR="$1"

required=(
    "application.tar.gz"
    "configuration.tar.gz"
    "database.sql"
    "MANIFEST.txt"
    "SHA256SUMS"
)

failures=0

if [[ ! -d "$BACKUP_DIR" ]]; then
    echo "FAIL: backup directory not found: $BACKUP_DIR"
    exit 1
fi

for item in "${required[@]}"; do
    if [[ ! -s "${BACKUP_DIR}/${item}" ]]; then
        echo "FAIL: missing or empty ${item}"
        ((failures+=1))
    else
        echo "PASS: ${item}"
    fi
done

if [[ ! -d "${BACKUP_DIR}/metadata" ]]; then
    echo "FAIL: metadata directory missing"
    ((failures+=1))
else
    echo "PASS: metadata directory"
fi

if (( failures == 0 )); then
    echo "Checking SHA-256 integrity"

    (
        cd "$BACKUP_DIR"
        sha256sum --check SHA256SUMS
    ) || failures=$((failures + 1))
fi

if (( failures > 0 )); then
    echo "BACKUP VALIDATION FAILED"
    exit 1
fi

echo "BACKUP VALIDATION PASSED"
```

Make executable:

```bash
sudo chmod 0750 \
  /opt/veriqta-dr/bin/validate-backup.sh
```

Run:

```bash
sudo /opt/veriqta-dr/bin/validate-backup.sh \
  /path/to/backup
```

# 23. Interview Preparation

### What is disaster recovery?

Disaster recovery is the planned capability to restore systems, services and data after a disruptive failure.

### Is backup the same as disaster recovery?

No.

Backup creates recoverable copies of data.

Disaster recovery includes the entire process required to restore the service.

### What is RPO?

Recovery Point Objective defines the maximum targeted amount of data loss measured in time.

### What is RTO?

Recovery Time Objective defines the targeted maximum duration for restoring service after disruption.

### Can you meet RPO and fail RTO?

Yes.

You may have a very recent backup but take too long to restore it.

### Can you meet RTO and fail RPO?

Yes.

You may restore quickly from a backup that is too old.

### Why isn't a backup on the production server enough?

A server-level failure could destroy both the production data and the local backup.

### Why use `mariadb-dump`?

It creates a logical representation of database objects and data suitable for logical restoration.

### Why use `--single-transaction`?

For transactional tables such as InnoDB, it can provide a consistent snapshot without locking tables for the entire dump in the same way as some other approaches.

It does not make every possible database workload automatically consistent, so you still need to understand your database environment.

### Why use checksums?

To detect unexpected changes or corruption in backup files.

### Does SHA-256 prove a backup is recoverable?

No.

It can prove that the file still matches the version that was hashed.

You still need restore testing.

### Why is restore testing essential?

Because archive existence and checksum validity do not prove that the backup contains everything needed to recover the service.

### Why use `flock`?

To prevent overlapping backup executions.

### Why keep a manifest?

It describes the backup set and makes recovery easier to understand and validate.

### Why store package information?

A clean recovery server may require the same software dependencies.

### Why store permissions?

An application can fail after restoration even when every file exists if ownership and access permissions are wrong.

### Why is recovery order important?

Services depend on other components.

For example:

```text
database
   ↓
application
   ↓
web server
```

may need to be recovered in a controlled sequence.

### Why validate Nginx before reloading?

A restored configuration can be syntactically invalid or incompatible with the new environment.

### Why might PHP-FPM break after a server rebuild?

The restored Nginx configuration may reference a socket path associated with a different PHP version.

### What is configuration portability?

The ability for configuration to operate correctly across the intended target environments.

### Why does disaster recovery expose configuration drift?

A rebuilt environment may not match the environment where the backup originated.

### What is a full backup?

A backup containing the complete selected dataset.

### What is an incremental backup?

A backup containing changes since a previous backup, commonly the previous backup in the chain.

### What is a differential backup?

A backup containing changes since a reference full backup.

### Why are incremental backups attractive?

They can reduce backup time and storage consumption.

### What is the trade-off?

Recovery can become more dependent on a chain of backup sets.

### What is backup retention?

The policy governing how long backup versions are preserved.

### Why isn't `find -mtime +7 -delete` automatically a complete retention strategy?

Real retention policies often require multiple recovery horizons such as hourly, daily, weekly and monthly restore points.

### What is off-site backup?

A backup stored in a different physical or failure location from the primary system.

### Why does off-site matter?

A disaster affecting the primary location could also destroy nearby backups.

### What is the difference between high availability and disaster recovery?

High availability tries to maintain service during failures.

Disaster recovery focuses on restoring service after significant disruption.

They complement each other.

### Why isn't RAID a backup?

RAID primarily provides storage redundancy and availability. It does not independently protect against many forms of deletion, corruption, compromise or site loss.

### What is a restore point?

A recoverable historical state represented by a usable backup.

### What is recovery validation?

Testing whether the recovered system satisfies technical and operational requirements.

### Why reboot after recovery?

To prove the restored environment persists and starts correctly rather than working only in the temporary state created during restoration.

# When You Can Call This Project Complete

Do not call the project complete because this exists:

```text
backup-20260924.tar.gz
```

Do not call it complete because this works:

```bash
tar -tzf backup.tar.gz
```

Do not even call it complete because:

```bash
sha256sum --check SHA256SUMS
```

returns:

```text
OK
```

Those are valuable checks.

They are not disaster recovery.

You should be able to start with:

```text
prod01
  X
  X
  X
UNAVAILABLE
```

and work from:

```text
backup01
+
clean recovery01
+
documented runbook
```

until you reach:

```text
RECOVERY SERVER
      |
      +-- OS dependencies restored
      |
      +-- application restored
      |
      +-- configuration restored
      |
      +-- permissions restored
      |
      +-- database restored
      |
      +-- credentials/grants restored
      |
      +-- services operational
      |
      +-- network listeners correct
      |
      +-- application responds
      |
      +-- expected data present
      |
      +-- logs healthy
      |
      +-- reboot successful
      |
      +-- RTO measured
      |
      +-- RPO measured
      |
      +-- evidence documented
```

When a production service fails, your recovery thinking should become:

```text
DISASTER DECLARED
        ↓
DEFINE BLAST RADIUS
        ↓
IDENTIFY SERVICE
        ↓
IDENTIFY DEPENDENCIES
        ↓
START RTO CLOCK
        ↓
IDENTIFY REQUIRED RECOVERY POINT
        ↓
LOCATE BACKUPS
        ↓
VALIDATE BACKUPS
        ↓
SELECT RECOVERY POINT
        ↓
PREPARE CLEAN TARGET
        ↓
RESTORE DEPENDENCIES
        ↓
RESTORE CONFIGURATION
        ↓
RESTORE APPLICATION
        ↓
RESTORE DATABASE
        ↓
RESTORE PERMISSIONS
        ↓
VALIDATE CONFIGURATION
        ↓
START SERVICES
        ↓
VERIFY NETWORK
        ↓
VERIFY APPLICATION
        ↓
VERIFY DATA
        ↓
VERIFY LOGS
        ↓
REBOOT
        ↓
VERIFY AGAIN
        ↓
STOP RTO CLOCK
        ↓
CALCULATE ACTUAL RTO
        ↓
CALCULATE ACTUAL RPO
        ↓
DOCUMENT GAPS
        ↓
IMPROVE THE RECOVERY PLAN
```

The central engineering lesson from this project is:

> **You do not know that you have a usable backup until you have successfully restored from it. You do not know that you have disaster recovery until you can rebuild the service from independent recovery material, verify the recovered system, and measure the result against defined recovery objectives.**

That is the difference between **creating backups** and **engineering recoverability**.
