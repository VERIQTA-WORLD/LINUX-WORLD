# 01. Project Title

## Production LEMP Web Application Platform

In this project, you are going to build and operate a complete Linux web application platform.

You will start with a clean Ubuntu server and finish with this:

```text
                         CLIENT
                            |
                            |
                     HTTP / HTTPS
                            |
                            v
                    +---------------+
                    |      UFW      |
                    |   FIREWALL    |
                    +-------+-------+
                            |
                            v
                    +---------------+
                    |     NGINX     |
                    |               |
                    | HTTP Redirect |
                    | TLS           |
                    | Static Files  |
                    | FastCGI       |
                    +-------+-------+
                            |
                       Unix Socket
                            |
                            v
                    +---------------+
                    |    PHP-FPM    |
                    |               |
                    | PHP Runtime   |
                    | Application   |
                    +-------+-------+
                            |
                            |
                       SQL Connection
                            |
                            v
                    +---------------+
                    |    MariaDB    |
                    |               |
                    | Application   |
                    | Database      |
                    +---------------+
```

You are not simply going to install Nginx, PHP, and MariaDB and confirm that a page loads.

That would be a basic LEMP tutorial.

Here, you will treat the server as a platform that you are responsible for operating.

You will configure:

* Nginx as the web server and TLS termination point.
* PHP-FPM as the application runtime.
* MariaDB as the persistent data layer.
* A dedicated application database and restricted database account.
* HTTPS using a small lab certificate authority.
* HTTP-to-HTTPS redirection.
* UFW firewall rules.
* Secure filesystem ownership and permissions.
* Application secrets outside the web root.
* Nginx, PHP-FPM, MariaDB, and application logging.
* Dependency-aware health checks.
* Automated application deployment.
* Database backup and restore verification.
* Service startup after reboot.
* Controlled failure scenarios.
* Troubleshooting runbooks.

By the end, you should be able to look at a failed web application and determine whether the problem is coming from:

```text
DNS / NAME RESOLUTION
        |
NETWORK
        |
FIREWALL
        |
TLS
        |
NGINX
        |
FASTCGI
        |
PHP-FPM
        |
APPLICATION
        |
DATABASE
        |
FILESYSTEM / PERMISSIONS
```

That ability to work across service boundaries is one of the main differences between this project and the Junior Linux World projects.

# 02. Project Scenario

You have joined the infrastructure team responsible for an internal application called:

## VERIQTA Operations Portal

The development team has written a small PHP application.

Your job is not to write a sophisticated application.

Your job is to build the Linux platform that runs it.

The application needs:

```text
Web server
PHP runtime
Database
HTTPS
Firewall
Secure application configuration
Logging
Health monitoring
Backup
Recovery
Repeatable deployment
```

The infrastructure requirements are straightforward.

The application must be available through:

```text
https://portal.veriqta.test
```

Requests arriving over HTTP must be redirected to HTTPS.

The PHP application must run through PHP-FPM.

The application must retrieve data from MariaDB.

MariaDB must not be exposed unnecessarily to the network.

The application must not connect to MariaDB as `root`.

Database credentials must not sit inside the public web directory.

You must be able to determine the health of the application without opening a browser.

You must be able to deploy application changes repeatedly without manually copying individual files.

You must also be able to recover the database from a backup.

Most importantly, when something breaks, you need to know how to investigate it.

Imagine receiving this incident report:

> The Operations Portal is down.

That tells you almost nothing.

You need to turn that vague symptom into evidence.

Is the hostname resolving?

Can the client reach the server?

Is port 443 reachable?

Is Nginx listening?

Did TLS negotiation succeed?

Did Nginx select the correct server block?

Can Nginx reach PHP-FPM?

Can PHP read the application files?

Can PHP reach MariaDB?

Can the database account authenticate?

Does the account have permission to run the required query?

Your job is to find the point where the request stops.

```text

   |
```

```text
PHP
 |
```

# 08. Architecture

## 8.1 Complete Request Path

When you eventually run:

```bash
curl https://portal.veriqta.test/
```

a lot happens behind that single command.

Conceptually:

```text
1. Client requests portal.veriqta.test
                |
                v
2. Hostname resolves to server address
                |
                v
3. Client opens TCP connection to 443
                |
                v
4. Firewall permits the connection
                |
                v
5. Nginx accepts the connection
                |
                v
6. TLS handshake occurs
                |
                v
7. Certificate is presented
                |
                v
8. Client validates certificate
                |
                v
9. Nginx selects portal.veriqta.test
                |
                v
10. Nginx processes URI
                |
                v
11. PHP request is passed through FastCGI
                |
                v
12. PHP-FPM executes PHP
                |
                v
13. PHP opens database connection
                |
                v
14. MariaDB authenticates portal_app
                |
                v
15. SQL query runs
                |
                v
16. MariaDB returns result
                |
                v
17. PHP generates response
                |
                v
18. Nginx sends HTTPS response
                |
                v
19. Client receives application page
```

This request path will become your troubleshooting map later.

---

```text
       YES
```


Good. Those TCP ports are probably not currently occupied.

### If something appears

Do not kill it.

Find out what it is.


You would need to decide whether this is truly a clean lab machine before continuing.

# 13. Configuration

# Phase 3: Build the Application Filesystem

We will install the application under:

```text
/srv/veriqta-portal
```

The structure will be:

```text
/srv/veriqta-portal/
├── public/
└── src/
```

Only `public/` becomes the Nginx document root.

Application configuration containing credentials will live elsewhere:

```text
/etc/veriqta-portal/
```

So:

```text
/srv/veriqta-portal/public
            |
            +---- Web accessible

/etc/veriqta-portal
            |
            +---- NOT web accessible
```

That separation is intentional.

---

## Step 1: Create the Application Root

```bash
sudo install \
    -d \
    -o root \
    -g root \
    -m 0755 \
    /srv/veriqta-portal
```

`install -d` creates the directory while letting you specify ownership and permissions in the same operation.

---

```bash
sudo install \

    -m 0750 \
```

The application needs persistent data.

```text
veriqta_portal

portal_app

service_status
```

The PHP application will use `portal_app`.

It will **not** use MariaDB root.

## Step 1: Generate a Password

Run:

```bash
openssl rand -base64 24
```

Save the generated password somewhere secure while you complete the lab.

Do not put it into your public GitHub repository.

In the examples below:

```text
REPLACE_WITH_YOUR_PASSWORD
```

means exactly that.

Do not use that literal string as your password.

---

## Step 2: Open MariaDB

```bash
sudo mariadb
```

Your prompt should change to the MariaDB client.

---

## Step 3: Create the Database

Run:

```sql
CREATE DATABASE veriqta_portal
CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci;
```

Verify:

```sql
SHOW DATABASES;
```

You should see:

```text
veriqta_portal
```

---

## Step 4: Create the Runtime Account

Run:

```sql
CREATE USER 'portal_app'@'localhost'
IDENTIFIED BY 'REPLACE_WITH_YOUR_PASSWORD';
```

Now grant only the permissions the application needs:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE
ON veriqta_portal.*
TO 'portal_app'@'localhost';
```

Then:

```sql
FLUSH PRIVILEGES;
```

---

## Why Not `GRANT ALL`?

Because your application is not a database administrator.

It needs to work with its own data.

It does not need permission to:

```text
Create database users
Grant privileges
Read arbitrary databases
Modify global server settings
Administer MariaDB
```

This is least privilege applied at the database layer.

---

## Step 5: Verify the Grants

While still in MariaDB:

```sql
SHOW GRANTS FOR 'portal_app'@'localhost';
```

Read the result.

Do not simply assume the previous command worked.

---

```sql
USE veriqta_portal;
```

```sql
CREATE TABLE service_status (

    updated_at TIMESTAMP NOT NULL
        DEFAULT CURRENT_TIMESTAMP
        ON UPDATE CURRENT_TIMESTAMP
);
```

Insert a row:

```sql
INSERT INTO service_status

('LEMP Platform', 'operational');
```

Query it:

```sql
SELECT * FROM service_status;
```

You should see your row.

Exit:

```sql

```

# Phase 6: Build the PHP Database Layer

Create the source directories in your project workspace:

```bash
mkdir -p \
    ~/production-lemp-platform/application/{public,src}
```

Create:

```bash
nano \
    ~/production-lemp-platform/application/src/database.php
```

Add:

```php
<?php

declare(strict_types=1);

function loadEnvironmentFile(string $path): array
{
    if (!is_readable($path)) {
        throw new RuntimeException(
            'Application configuration is not readable.'
        );
    }

    $lines = file(
        $path,
        FILE_IGNORE_NEW_LINES | FILE_SKIP_EMPTY_LINES
    );

    if ($lines === false) {
        throw new RuntimeException(
            'Unable to load application configuration.'
        );
    }

    $config = [];

    foreach ($lines as $line) {
        $line = trim($line);

        if ($line === '' || str_starts_with($line, '#')) {
            continue;
        }

        $parts = explode('=', $line, 2);

        if (count($parts) !== 2) {
            continue;
        }

        $key = trim($parts[0]);
        $value = trim($parts[1]);

        $config[$key] = $value;
    }

    return $config;
}

function databaseConnection(): PDO
{
    $config = loadEnvironmentFile(
        '/etc/veriqta-portal/portal.env'
    );

    $required = [
        'DB_HOST',
        'DB_NAME',
        'DB_USER',
        'DB_PASSWORD',
    ];

    foreach ($required as $key) {
        if (
            !isset($config[$key]) ||
            $config[$key] === ''
        ) {
            throw new RuntimeException(
                "Missing configuration value: {$key}"
            );
        }
    }

    $dsn = sprintf(
        'mysql:host=%s;dbname=%s;charset=utf8mb4',
        $config['DB_HOST'],
        $config['DB_NAME']
    );

    return new PDO(
        $dsn,
        $config['DB_USER'],
        $config['DB_PASSWORD'],
        [
            PDO::ATTR_ERRMODE =>
                PDO::ERRMODE_EXCEPTION,

            PDO::ATTR_DEFAULT_FETCH_MODE =>
                PDO::FETCH_ASSOC,

            PDO::ATTR_EMULATE_PREPARES =>
                false,
        ]
    );
}
```

---

## What This File Is Doing

`loadEnvironmentFile()` reads your protected configuration.

`databaseConnection()` then creates a PDO connection to MariaDB.

The application never needs to know the root database password.

It only knows:

```text
portal_app
```

and that account only has the permissions you granted earlier.

## Compare Firewall and Listeners

Run:

```bash
sudo ss -lntup
```

Then:

```bash
sudo ufw status verbose
```

These answer different questions.

`ss` asks:

> What is listening?

UFW asks:

> What traffic is the firewall configured to permit?

A service can listen while the firewall blocks remote access.

A firewall can allow a port while nothing is listening on it.

Understanding that distinction will save you a lot of troubleshooting time.

# Phase 21: Build an Operational Health Checker

Create:

```bash

    ~/production-lemp-platform/scripts/health-check.sh
```

Add:

```bash
#!/usr/bin/env bash

set -u
set -o pipefail

HOST="portal.veriqta.test"
IP="${PORTAL_IP:-127.0.0.1}"

PROJECT_DIR="$(
    cd -- "$(dirname -- "${BASH_SOURCE[0]}")/.." &&
    pwd
)"

CA_FILE="$PROJECT_DIR/config/tls/veriqta-lab-ca.crt"

PASS=0
FAIL=0

TMP_BODY="$(mktemp)"

cleanup() {
    rm -f "$TMP_BODY"
}

trap cleanup EXIT

pass() {
    printf '[PASS] %s\n' "$1"
    PASS=$((PASS + 1))
}

fail() {
    printf '[FAIL] %s\n' "$1"
    FAIL=$((FAIL + 1))
}

if systemctl is-active --quiet nginx; then
    pass "Nginx is active"
else
    fail "Nginx is not active"
fi

PHP_FPM_UNIT="$(
    systemctl list-unit-files \
        --type=service \
        --no-legend \
        'php*-fpm.service' \
    | awk 'NR == 1 {print $1}'
)"

if [[ -n "$PHP_FPM_UNIT" ]] &&
   systemctl is-active --quiet "$PHP_FPM_UNIT"; then
    pass "$PHP_FPM_UNIT is active"
else
    fail "PHP-FPM is not active or was not found"
fi

if systemctl is-active --quiet mariadb; then
    pass "MariaDB is active"
else
    fail "MariaDB is not active"
fi

if sudo nginx -t >/dev/null 2>&1; then
    pass "Nginx configuration is valid"
else
    fail "Nginx configuration is invalid"
fi

HTTP_CODE="$(
    curl \
        -sS \
        -o "$TMP_BODY" \
        -w '%{http_code}' \
        --resolve "$HOST:443:$IP" \
        --cacert "$CA_FILE" \
        "https://$HOST/health.php" \
        2>/dev/null \
    || true
)"

if [[ "$HTTP_CODE" == "200" ]]; then
    pass "Health endpoint returned HTTP 200"
else
    fail "Health endpoint returned HTTP ${HTTP_CODE:-unknown}"
fi

if grep -q '"database": "ok"' "$TMP_BODY"; then
    pass "Application reports database healthy"
else
    fail "Application does not report database healthy"
fi

echo
printf 'Passed: %d\n' "$PASS"
printf 'Failed: %d\n' "$FAIL"

if (( FAIL > 0 )); then
    exit 1
fi

exit 0
```

```bash
    ~/production-lemp-platform/scripts/health-check.sh
```

# Backup and Recovery

# Phase 22: Back Up MariaDB

Your database contains state.

If the PHP files disappear, you can redeploy them from Git.

If the database disappears and you have no recoverable backup, the data may be gone.

Create:

```bash
nano \
    ~/production-lemp-platform/scripts/backup-db.sh
```

Add:

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

DATABASE="veriqta_portal"
BACKUP_DIR="/var/backups/veriqta-portal"
TIMESTAMP="$(date +'%Y%m%d-%H%M%S')"

BACKUP_FILE="$BACKUP_DIR/${DATABASE}-${TIMESTAMP}.sql"
CHECKSUM_FILE="${BACKUP_FILE}.sha256"

if (( EUID != 0 )); then
    echo "Run this script with sudo." >&2
    exit 1
fi

install \
    -d \
    -o root \
    -g root \
    -m 0700 \
    "$BACKUP_DIR"

mariadb-dump \
    --single-transaction \
    --routines \
    --triggers \
    "$DATABASE" \
    > "$BACKUP_FILE"

chmod 0600 "$BACKUP_FILE"

sha256sum \
    "$BACKUP_FILE" \
    > "$CHECKSUM_FILE"

chmod 0600 "$CHECKSUM_FILE"

echo "Backup created:"
echo "$BACKUP_FILE"

echo
echo "Checksum:"
cat "$CHECKSUM_FILE"
```

Make executable:

```bash
chmod +x \
    ~/production-lemp-platform/scripts/backup-db.sh
```

Run:

```bash
sudo \
    ~/production-lemp-platform/scripts/backup-db.sh
```

Inspect:

```bash

    /var/backups/veriqta-portal/
```

# 23. Interview Preparation

## Architecture

**Walk me through your application request path.**

A request resolves the application hostname, connects to the server on TCP 443, passes the host firewall, performs TLS with Nginx, and reaches the appropriate Nginx server block. PHP requests are sent through FastCGI to PHP-FPM. PHP executes the application, connects to MariaDB using the restricted application account, performs the query, and returns the generated response through Nginx.

---

**Why did you use PHP-FPM?**

Nginx does not execute PHP directly. PHP-FPM manages PHP worker processes and accepts FastCGI requests from Nginx.

---

**Why did you use a Unix socket?**

Nginx and PHP-FPM run on the same host, so a Unix domain socket provides a local communication mechanism without exposing another TCP listener.

---

## Database

**Why didn't your application use the MariaDB root account?**

The runtime application only needs access to its own data. Giving it administrative database privileges would unnecessarily increase the impact of an application compromise.

---

**What is the difference between database authentication and authorization?**

Authentication determines whether the identity can log in. Authorization determines what that authenticated identity is permitted to do.

The failure labs demonstrate both.

---

## Networking

**What is the difference between an open firewall port and a listening socket?**

A firewall rule controls whether traffic is permitted. A listener means a process is actually accepting connections on an address and port. You can have one without the other.

---

**Why wasn't 3306 exposed?**

The database and application run on the same server, so remote database access is unnecessary for this architecture.

---

## HTTP

**What would make you investigate a 502?**

In this architecture, I would investigate the Nginx-to-PHP-FPM boundary: PHP-FPM service state, FastCGI socket existence, socket permissions, configured `fastcgi_pass`, and Nginx error logs.

---

**What about a 503 from your health endpoint?**

The application itself is reachable, but its database dependency failed. I would investigate MariaDB state, database connectivity, authentication, grants, and application configuration.

---

## TLS

**Why didn't you just use `curl -k`?**

Because `-k` disables certificate verification. It can prove that an HTTPS server responds, but it cannot prove that the certificate is trusted or valid for the requested hostname.

---

**What does SAN do?**

Subject Alternative Name identifies the hostnames or other identities for which the certificate is valid.

---

## Operations

**Why test a restore instead of simply checking that the backup file exists?**

A backup file proves that something was written. A successful restore and data validation provide evidence that the backup is usable for recovery.

---

**Why validate Nginx before reload?**

It prevents a known-invalid configuration from being deliberately applied.

---

**Can `nginx -t` prove the application works?**

No. It can validate Nginx configuration while PHP-FPM, MariaDB, application permissions, or application logic are still broken.
