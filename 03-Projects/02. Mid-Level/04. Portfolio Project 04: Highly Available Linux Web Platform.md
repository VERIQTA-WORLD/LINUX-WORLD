# 01. Project Title

## Highly Available Linux Web Platform

In the Junior Linux projects, you learned how to build and operate a Linux web server.

That server could host an application.

It could run Nginx.

It could accept HTTP requests.

It could be secured with a firewall.

It could be monitored.

But there was still a serious infrastructure problem:

```text
                    USERS
                      |
                      v
                  +-------+
                  | web01 |
                  +-------+
```

What happens when `web01` fails?

The answer is simple:

```text
                    USERS
                      |
                      v
                  +-------+
                  | web01 |
                  | DOWN  |
                  +-------+
                      |
                      X

                  APPLICATION
                  UNAVAILABLE
```

It does not matter whether the failure was caused by:

```text
Nginx crashing
a broken configuration
a failed deployment
a server reboot
a network failure
a kernel problem
hardware failure
resource exhaustion
maintenance
```

Your architecture contains one server.

Therefore, that server is a **single point of failure**.

This project changes that.

You will build a multi-server Linux web platform where:

* multiple web servers serve the same application,
* HAProxy distributes requests across those servers,
* unhealthy backend servers are automatically removed from rotation,
* redundant load balancers protect the frontend,
* Keepalived manages a shared Virtual IP,
* VRRP coordinates active and standby load balancers,
* failure of the active load balancer causes automatic failover,
* recovered servers can return to service,
* systemd keeps required services running,
* UFW restricts network access,
* logs provide operational evidence,
* Bash health checks verify the platform,
* controlled failure labs prove whether your design actually survives failures.

The final architecture will look like this:

```text
                         CLIENTS
                            |
                            |
                            v
                 192.168.56.100
                   VIRTUAL IP
                            |
                 +----------+----------+
                 |                     |
                 v                     v
          +-------------+       +-------------+
          |     lb01    |       |     lb02    |
          |             |       |             |
          |   HAProxy   |       |   HAProxy   |
          | Keepalived  |       | Keepalived  |
          |   MASTER    |       |   BACKUP    |
          +------+------+       +------+------+
                 |                     |
                 +----------+----------+
                            |
                     Backend Pool
                            |
                +-----------+-----------+
                |                       |
                v                       v
         +-------------+         +-------------+
         |    web01    |         |    web02    |
         |             |         |             |
         |    Nginx    |         |    Nginx    |
         | Application |         | Application |
         +-------------+         +-------------+
```

The important part of this project is not simply installing HAProxy.

The important part is proving that the platform behaves correctly when individual components fail.

You will deliberately create failures such as:

```text
web01 Nginx stops
web02 becomes unavailable
HAProxy stops on lb01
Keepalived stops on lb01
lb01 disappears from the network
backend health checks fail
HAProxy configuration becomes invalid
VRRP communication is disrupted
the active load balancer returns
```

For every failure, you will investigate:

```text
What failed?

What remained available?

What did the load balancer detect?

What did Keepalived detect?

Where did the Virtual IP move?

What did the client experience?

What evidence appeared in logs?

How was service restored?

Did recovery introduce another failure?
```

That is where this project becomes a real Mid-Level infrastructure project.

# 02. Project Scenario

You are responsible for a Linux-hosted web application used by customers.

The original environment contains one web server:

```text
Internet/User
     |
     v
   web01
     |
     v
 Application
```

During normal operation, everything works.

Then the operations team starts recording incidents.

### Incident 1

Nginx crashes.

Result:

```text
Website unavailable
```

### Incident 2

The server requires maintenance.

Result:

```text
Website unavailable during maintenance
```

### Incident 3

A deployment leaves the application unhealthy.

Result:

```text
Users continue reaching the unhealthy server
```

The team adds another web server:

```text
web01
web02
```

But that alone does not create high availability.

Users still need a reliable way to reach them.

So the team adds a load balancer:

```text
             lb01
               |
        +------+------+
        |             |
        v             v
      web01         web02
```

Now backend failure can be tolerated.

But a new problem appears.

What happens if `lb01` fails?

You simply moved the single point of failure:

```text
Before:

web01 = single point of failure


After:

lb01 = single point of failure
```

So you add a second load balancer:

```text
              lb01       lb02
                \         /
                 \       /
                  \     /
                 web tier
```

But clients still need one stable destination.

That is where the Virtual IP enters the architecture.

Your final requirement is:

```text
Client
  |
  v
Virtual IP
  |
  +--------------------------+
  |                          |
active LB                 standby LB
  |
  v
HAProxy
  |
  +------------+
  |            |
  v            v
web01        web02
```

If the active load balancer fails:

```text
BEFORE FAILURE

VIP
 |
 v
lb01 MASTER
 |
 +------+
 |      |
web01 web02


lb01 FAILS


AFTER FAILURE

VIP
 |
 v
lb02 MASTER
 |
 +------+
 |      |
web01 web02
```

The client continues using the same IP address.

That is the platform you will build.

# Failure Domains

You need to think in failure domains.

## Backend failure

```text
web01 X
web02 ✓
```

Expected result:

```text
HAProxy stops sending traffic to web01.
web02 continues serving requests.
```

## Load-balancer failure

```text
lb01 X
lb02 ✓
```

Expected result:

```text
Keepalived moves the VIP to lb02.
```

## Complete backend failure

```text
web01 X
web02 X
```

Expected result:

```text
Frontend may remain reachable,
but the application cannot be served.

HAProxy returns a backend-unavailable response,
commonly HTTP 503.
```

This distinction matters.

A working load balancer does not mean the application is healthy.

# Why `/health` Exists

HAProxy needs a simple way to ask:

> Can this backend currently serve the expected application endpoint?

Checking only TCP port 80 tells you:

```text
Something accepted TCP.
```

An HTTP health check can tell you more:

```text
Nginx answered
AND
the requested health endpoint returned an acceptable HTTP response
```

Later, a real application health endpoint may also check dependencies.

But be careful.

A health check that depends on too many external systems can remove otherwise useful servers unnecessarily.

Health-check design is an engineering decision.

# Phase 12: Create the HAProxy Configuration

Edit:

```bash
sudo nano /etc/haproxy/haproxy.cfg
```

Use:

```text
global
    log /dev/log local0
    log /dev/log local1 notice
    daemon

defaults
    log global
    mode http
    option httplog
    option dontlognull

    timeout connect 5s
    timeout client 30s
    timeout server 30s

frontend http_front
    bind *:80
    default_backend web_backends

backend web_backends
    balance roundrobin

    option httpchk GET /health
    http-check expect status 200

    server web01 192.168.56.31:80 check inter 2s fall 3 rise 2
    server web02 192.168.56.32:80 check inter 2s fall 3 rise 2
```

Replace the backend addresses with yours.

---

# Understand the Backend Configuration

This line:

```text
balance roundrobin
```

means HAProxy will distribute requests across available backend servers using round-robin selection.

These lines:

```text
server web01 192.168.56.31:80 check inter 2s fall 3 rise 2
server web02 192.168.56.32:80 check inter 2s fall 3 rise 2
```

contain several important controls.

### `check`

Enable active health checking.

### `inter 2s`

Attempt checks approximately every two seconds.

### `fall 3`

Require consecutive failures before marking the backend down.

### `rise 2`

Require consecutive successful checks before marking it healthy again.

This reduces flapping.

Without thresholds, a single transient failure could immediately remove a backend.

# Phase 21: Configure Keepalived on `lb01`

```text
global_defs {
    router_id LB01
    script_user root
    enable_script_security
}

    script "/usr/local/bin/check_haproxy.sh"
    interval 2
    timeout 2
    fall 2
    rise 2
    weight -60
}

    interface enp0s8

    virtual_router_id 51
    priority 150
    advert_int 1

    authentication {
        auth_type PASS
        auth_pass LABPASS1

        192.168.56.100/24
    }

        chk_haproxy
    }
}
```


with the actual interface.

---

# Understand the Important Settings

### `state MASTER`

This node begins as the preferred active node in the lab design.

### `virtual_router_id 51`

Both load balancers participating in the same VRRP instance must use the same virtual router ID.

### `priority 150`

Higher priority is preferred.

### `advert_int 1`

Controls VRRP advertisement timing.

### `virtual_ipaddress`

Defines the floating address.

### `track_script`

Ties HAProxy service health into Keepalived's decision-making.

# Phase 22: Configure `lb02`

Edit:

```bash
sudo nano /etc/keepalived/keepalived.conf
```

Use:

```text
global_defs {
    router_id LB02
    script_user root
    enable_script_security
}

vrrp_script chk_haproxy {
    script "/usr/local/bin/check_haproxy.sh"
    interval 2
    timeout 2
    fall 2
    rise 2
    weight -60
}

vrrp_instance VI_1 {
    state BACKUP
    interface enp0s8

    virtual_router_id 51
    priority 100
    advert_int 1

    authentication {
        auth_type PASS
        auth_pass LABPASS1
    }

    virtual_ipaddress {
        192.168.56.100/24
    }

    track_script {
        chk_haproxy
    }
}
```

The important difference is:

```text
lb01 priority = 150
lb02 priority = 100
```

With the configured `weight -60`, failure of HAProxy on `lb01` can reduce its effective priority enough for healthy `lb02` to take over.

That is deliberate.

If you choose priorities and tracking weights carelessly, your service-health failure may not actually trigger the behavior you intended.

# Build a Final Health Script

Create:

```bash
nano ~/high-availability-linux-platform/scripts/platform-health.sh
```

Add:

```bash
#!/usr/bin/env bash

set -u

VIP="${VIP:-192.168.56.100}"
LB01="${LB01:-192.168.56.20}"
LB02="${LB02:-192.168.56.21}"
WEB01="${WEB01:-192.168.56.31}"
WEB02="${WEB02:-192.168.56.32}"

failures=0

check_http() {
    local name="$1"
    local url="$2"
    local expected="$3"

    printf '%-20s ' "$name"

    code="$(curl \
        --silent \
        --output /dev/null \
        --write-out '%{http_code}' \
        --max-time 3 \
        "$url" 2>/dev/null || true)"

    if [[ "$code" == "$expected" ]]; then
        echo "OK ($code)"
    else
        echo "FAILED (${code:-no response})"
        ((failures++))
    fi
}

echo "VERIQTA HA Platform Health"
echo "=========================="
echo

check_http "VIP" "http://${VIP}/" "200"
check_http "lb01" "http://${LB01}/" "200"
check_http "lb02" "http://${LB02}/" "200"
check_http "web01 health" "http://${WEB01}/health" "200"
check_http "web02 health" "http://${WEB02}/health" "200"

echo

if (( failures == 0 )); then
    echo "Overall result: HEALTHY"
    exit 0
else
    echo "Overall result: DEGRADED or FAILED"
    echo "Failed checks: $failures"
    exit 1
fi
```

# Understand a Limitation of This Script

The script considers all direct endpoints mandatory.

During a deliberate load-balancer failure, this means:

```text
VIP = healthy
lb01 = failed
lb02 = healthy
backends = healthy
```

The overall script reports degraded/failed even though the customer-facing service may still be available.

That is useful.

It distinguishes:

```text
SERVICE HEALTH
```

from:

```text
REDUNDANCY HEALTH
```

A highly available platform can remain customer-facing healthy while operating in a degraded redundancy state.

That is a much more mature operational model than simply saying:

> The website is up.

# 23. Interview Preparation

## What is high availability?

High availability is the design and operation of systems so required services remain available despite expected component failures.

## What is redundancy?

Redundancy means providing additional components or paths so the system is not entirely dependent on one component.

## What is a single point of failure?

A component whose failure can make the entire required service unavailable.

## Why were two web servers necessary?

Because one backend server would otherwise be a single point of failure.

## Why weren't two web servers enough?

Clients still needed a reliable traffic-distribution and entry mechanism.

## What does HAProxy do?

In this project, HAProxy accepts frontend HTTP connections, selects healthy backend servers, forwards requests, and performs active backend health checks.

## Why did you deploy two HAProxy servers?

One HAProxy server would itself become a single point of failure.

## What is Keepalived doing?

Keepalived coordinates ownership of the Virtual IP and can change node priority based on tracked service health.

## What is the Virtual IP?

It is the stable address clients use regardless of which load-balancer node currently owns the active role.

## What is VRRP?

VRRP is a redundancy protocol used to coordinate ownership of a virtual routing/address role between participating nodes.

## What does `priority` do?

It contributes to determining which eligible node is preferred for the active role.

## Why did `lb01` have a higher priority?

It was intentionally configured as the preferred node for normal lab operation.

## Why did you track HAProxy?

Because a Linux node being alive does not necessarily mean the load-balancing service is healthy.

## What is a backend health check?

A health check tests whether a backend meets defined criteria for receiving traffic.

## Why use `/health` instead of only TCP port 80?

An HTTP endpoint verifies more application-layer behavior than simply establishing a TCP connection.

## What does `fall 3` mean conceptually?

The backend must fail several consecutive checks before being declared unhealthy.

## What does `rise 2` mean?

A failed backend must pass consecutive checks before being restored to healthy state.

## Why are rise and fall thresholds useful?

They reduce rapid state changes caused by isolated transient failures.

## What is failover?

Failover is the transition of service responsibility from a failed or unhealthy component to another capable component.

## What is failback?

Failback is the transition toward a preferred recovered component after the original failure has been resolved.

## Does automatic failover guarantee zero downtime?

No.

Detection intervals, election timing, neighbour/ARP updates, connection state, application behavior and client retry behavior can all affect observed interruption.

## What happens if one backend fails?

HAProxy should remove it from the healthy backend pool while the remaining healthy backend continues serving traffic.

## What happens if all backends fail?

The load-balancing layer may remain reachable but cannot satisfy the application request through a healthy backend.

## Why might HAProxy return 503?

One common cause is that no suitable backend server is available.

## What is the difference between service availability and redundancy health?

A service can remain available while redundancy is degraded.

For example:

```text
lb01 active
lb02 failed
```

may still serve customers, but another failure could now cause an outage.

## How would you troubleshoot a 503?

Check HAProxy backend state, health checks, backend connectivity, Nginx state, listening sockets, firewall rules and application health.

## Why validate HAProxy configuration before restarting?

A syntax error can prevent HAProxy from starting or accepting the new configuration.

## Why use `ss`?

`ss` lets you inspect sockets and determine whether expected processes are listening on expected addresses and ports.

## Why use `journalctl`?

It provides systemd journal logs for services such as HAProxy and Keepalived.

## What is split-brain-like behavior in this context?

It is an unsafe state where redundant nodes incorrectly behave as though each is active, potentially resulting in conflicting ownership of the same VIP.

## What could cause that?

Possible causes include disrupted VRRP communication, firewall problems, network segmentation, or configuration mismatch.

## Why is testing failure important?

A redundant architecture that has never been tested under failure is only an assumption.

## What is a failure domain?

A failure domain is a component, subsystem or boundary whose failure can affect a defined portion of the architecture.

## Why is this project not truly production-ready?

Because a local five-VM lab does not address every production requirement, including external DNS, TLS, certificates, multiple physical failure domains, persistent application state, database HA, real monitoring, alerting, configuration automation, DDoS protection, backups, capacity planning, external network redundancy and many other concerns.

# When You Can Call This Project Complete

Do not call this project complete because this works:

```bash
curl http://192.168.56.100/
```

That only proves the platform worked at one moment.

A highly available platform has to prove something harder:

**what happens when things stop working?**

You should be able to stand in front of this architecture:

```text
                         CLIENT
                            |
                            v
                      VIRTUAL IP
                            |
                 +----------+----------+
                 |                     |
                 v                     v
             +-------+             +-------+
             | lb01  |             | lb02  |
             |       |             |       |
             |HAProxy|             |HAProxy|
             |Keepal.|             |Keepal.|
             +---+---+             +---+---+
                 |                     |
                 +----------+----------+
                            |
                     HEALTH CHECKS
                            |
                 +----------+----------+
                 |                     |
                 v                     v
             +-------+             +-------+
             | web01 |             | web02 |
             | Nginx |             | Nginx |
             +-------+             +-------+
```

and explain exactly what happens when:

```text
web01 fails

web02 fails

both backends fail

Nginx is active but /health fails

a firewall blocks backend traffic

HAProxy marks a backend DOWN

a backend recovers

HAProxy on lb01 fails

Keepalived on lb01 fails

the entire lb01 machine disappears

lb02 becomes active

the Virtual IP moves

lb01 returns

the preferred node becomes healthy again

VRRP communication fails

the VIP exists but HTTP does not work

HAProxy works but every backend is unavailable

the website works but redundancy has been lost
```

More importantly, you should know how to investigate the platform from the outside inward:

```text

        |

        |

        |
        v
Can HAProxy reach web01?
        |
        +---- NO ----> route / firewall / backend socket
        |
       YES
        |
        v
Can HAProxy reach web02?
        |
        v
Is Nginx active?
        |
        v
Is port 80 listening?
        |
        v
Does /health return 200?
        |
        v
Does the application itself work?
```

And you should be able to investigate frontend redundancy separately:


That is the difference between simply knowing how to install HAProxy and understanding how to **operate a highly available Linux web platform**.

You are no longer protecting only a process.

You are protecting a request path:

```text

APPLICATION
```

> **Redundancy is something you build. High availability is something you have to test.**
