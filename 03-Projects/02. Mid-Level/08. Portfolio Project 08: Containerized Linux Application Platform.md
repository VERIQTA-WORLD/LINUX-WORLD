# 01. Project Title

Running this:


It does not prove that you can operate a containerized Linux platform.

In this project, you are going much further.

# 02. Project Scenario

Your engineering team has been running an internal application directly on a Linux server.

The current deployment looks roughly like this:

```text
Ubuntu Server
├── Nginx
├── PHP
├── PHP-FPM
├── MariaDB
├── application files
├── configuration files
└── application data
```

This works, but several operational problems have appeared.

Package dependencies are tightly coupled to the host.

Developers have different runtime versions.

Application deployments modify the server directly.

Rollback is difficult.

Nobody is completely sure which files belong to the application and which belong to the operating system.

Database data, application code, configuration, and runtime dependencies are mixed together.

The team wants to move the application into containers.

Your job is not simply to “Dockerize” it.

You have been asked to build an operational container platform on Linux.

The final platform must provide:

```text
repeatable container deployment
separate application components
internal service networking
controlled host exposure
persistent database storage
container health checks
restart behavior
CPU and memory controls
container logging
secure runtime configuration
non-root execution where practical
reduced Linux capabilities
read-only filesystems where practical
backup and restore
deployment validation
failure recovery
operational documentation
```

The platform will host an internal application called:

```text
VERIQTA Operations Portal
```

## Network Architecture

Create two Docker networks:

```text
frontend
backend
```

`web` joins:

```text

```

```text

```

```text

```

```text

 |

```

The web container does not need direct database connectivity.

The database does not need direct frontend connectivity.

This gives you a meaningful network boundary even on one host.

# Understand the Docker Daemon

The Docker CLI:

```bash
docker ps
```

is not the container runtime itself.

Conceptually:

```text
docker CLI
    |
    v
Docker API/socket
    |
    v
dockerd
    |
    v
containerd
    |
    v
container runtime
    |
    v
Linux kernel
```

Inspect:

```bash
ps aux | grep -E '[d]ockerd|[c]ontainerd'
```

Inspect the socket:

```bash
sudo ls -l /var/run/docker.sock
```

You will likely see a socket owned by:

```text
root:docker
```

This matters.

Access to the Docker daemon is highly privileged.

Treat membership in the Docker group as privileged administrative access, not as an ordinary convenience group.

For the lab, you can either continue using:

```bash
sudo docker ...
```

or deliberately grant Docker access to your administrative account after documenting the security implication.

# Phase 6: Build the Application

Create:

```bash
nano app/src/database.php
```

Add:

```php
<?php

declare(strict_types=1);

function database(): PDO
{
    $host = getenv('DB_HOST') ?: 'db';
    $port = getenv('DB_PORT') ?: '3306';
    $name = getenv('DB_NAME') ?: '';
    $user = getenv('DB_USER') ?: '';
    $password = getenv('DB_PASSWORD') ?: '';

    if ($name === '' || $user === '' || $password === '') {
        throw new RuntimeException(
            'Required database configuration is missing.'
        );
    }

    $dsn = sprintf(
        'mysql:host=%s;port=%s;dbname=%s;charset=utf8mb4',
        $host,
        $port,
        $name
    );

    return new PDO(
        $dsn,
        $user,
        $password,
        [
            PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION,
            PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC,
            PDO::ATTR_EMULATE_PREPARES => false,
        ]
    );
}
```

Notice:

```text
DB_HOST=db
```

will eventually be used.

Why?

Because containers on the same Docker network can discover services by Compose service name.

The application should not use:

```text
127.0.0.1
```

for MariaDB.

Inside the application container:

```text
127.0.0.1
```

means:

```text
THE APPLICATION CONTAINER ITSELF
```

not the database container.

That distinction causes many real container failures.

# Understand Every Important Instruction

## `FROM`

```dockerfile
FROM php:8.3-fpm-alpine
```

defines the base image.

For a reproducible production deployment, you would normally pin images more tightly, potentially by digest, rather than depending indefinitely on a moving tag.

---

## `RUN`

```dockerfile
RUN docker-php-ext-install pdo_mysql
```

executes during image build.

The resulting filesystem changes become part of an image layer.

---

## `WORKDIR`

```dockerfile
WORKDIR /var/www/html
```

sets the working directory for subsequent instructions and runtime commands.

---

## `COPY`

```dockerfile
COPY app/ /var/www/html/
```

copies application files into the image.

This gives you an immutable application artifact.

Later, you will decide whether the lab should run from the image or use a development-style bind mount.

For the final portfolio architecture, prefer the application code packaged into the image.

---

## `USER`

```dockerfile
USER www-data
```

means the application process should not run as container root.

This is a meaningful security improvement.

It does not magically make the container safe.

But it reduces unnecessary privilege.

```bash
set -Eeuo pipefail

    cd "$(dirname "${BASH_SOURCE[0]}")/.." \

    exit 1
}

[[ -f "$COMPOSE_FILE" ]] \

[[ -f "$ENV_FILE" ]] \

    --env-file "$ENV_FILE" \

    --env-file "$ENV_FILE" \

    "$APP_IMAGE" \
    >/dev/null

log "Starting platform."

docker compose \
    --env-file "$ENV_FILE" \
    -f "$COMPOSE_FILE" \
    up -d

log "Waiting for services."

sleep 10

log "Current service state."

docker compose \
    --env-file "$ENV_FILE" \
    -f "$COMPOSE_FILE" \
    ps

log "Deployment completed."
```

# Phase 18: Build the Health Checker

Create:

```bash
nano scripts/health-check.sh
```

Add:

```bash
#!/usr/bin/env bash

set -u
set -o pipefail

PROJECT_DIR="$(
    cd "$(dirname "${BASH_SOURCE[0]}")/.." \
    && pwd
)"

ENV_FILE="${PROJECT_DIR}/config/.env"
COMPOSE_FILE="${PROJECT_DIR}/compose.yaml"

PASS=0
FAIL=0

pass() {
    printf 'PASS: %s\n' "$1"
    PASS=$((PASS + 1))
}

fail() {
    printf 'FAIL: %s\n' "$1"
    FAIL=$((FAIL + 1))
}

check_container_running() {
    local container="$1"

    if docker inspect \
        -f '{{.State.Running}}' \
        "$container" 2>/dev/null \
        | grep -qx 'true'; then

        pass "$container is running"
    else
        fail "$container is not running"
    fi
}

check_container_health() {
    local container="$1"
    local health

    health="$(
        docker inspect \
            -f '{{if .State.Health}}{{.State.Health.Status}}{{else}}none{{end}}' \
            "$container" \
            2>/dev/null \
            || true
    )"

    if [[ "$health" == "healthy" ]]; then
        pass "$container is healthy"
    else
        fail "$container health is ${health:-unknown}"
    fi
}

if docker info >/dev/null 2>&1; then
    pass "Docker daemon available"
else
    fail "Docker daemon unavailable"
fi

check_container_running veriqta-web
check_container_running veriqta-app
check_container_running veriqta-db

check_container_health veriqta-web
check_container_health veriqta-app
check_container_health veriqta-db

HTTP_CODE="$(
    curl \
        --silent \
        --output /tmp/veriqta-health.$$ \
        --write-out '%{http_code}' \
        http://127.0.0.1:8080/health \
        2>/dev/null \
        || true
)"

if [[ "$HTTP_CODE" == "200" ]]; then
    pass "health endpoint returned HTTP 200"
else
    fail "health endpoint returned ${HTTP_CODE:-no response}"
fi

if grep -q '"database": "ok"' \
    /tmp/veriqta-health.$$ \
    2>/dev/null; then

    pass "database health is ok"
else
    fail "database health is not ok"
fi

rm -f /tmp/veriqta-health.$$

printf '\nSummary: %d passed, %d failed\n' \
    "$PASS" "$FAIL"

if (( FAIL > 0 )); then
    exit 1
fi

exit 0
```

Make executable:

```bash
chmod 0750 scripts/health-check.sh
```

Run:

```bash
sudo scripts/health-check.sh
```

# 15. Security

Container security starts with the host.

A badly secured Docker host cannot be rescued by a clever Dockerfile.

Think in layers:

```text
HOST SECURITY
     ↓
DOCKER DAEMON SECURITY
     ↓
IMAGE SECURITY
     ↓
RUNTIME SECURITY
     ↓
NETWORK SECURITY
     ↓
FILESYSTEM SECURITY
     ↓
APPLICATION SECURITY
     ↓
SECRET SECURITY
```

---

## Security Control 1: Do Not Publish MariaDB

Check:

```bash
sudo docker port veriqta-db
```

You should not see a host-published MariaDB port.

Also:

```bash
sudo ss -lntp | grep ':3306'
```

The Docker host should not expose a database listener merely because the database container listens internally.

---

## Security Control 2: Run the Application as Non-Root

Check:

```bash
sudo docker exec \
  veriqta-app \
  id
```

You should see the `www-data` identity rather than UID 0.

Also:

```bash
sudo docker inspect \
  veriqta-app \
  --format '{{.Config.User}}'
```

---

## Security Control 3: Drop Capabilities

Inspect:

```bash
sudo docker inspect \
  veriqta-app \
  --format '{{json .HostConfig.CapDrop}}'
```

The application drops:

```text
ALL
```

because it does not need broad Linux capabilities.

Do not add capabilities simply because a container fails.

First determine what operation actually requires the capability.

---

## Security Control 4: `no-new-privileges`

Inspect:

```bash
sudo docker inspect \
  veriqta-app \
  --format '{{json .HostConfig.SecurityOpt}}'
```

This helps prevent processes from gaining additional privileges through mechanisms such as setuid/setgid binaries.

---

## Security Control 5: Read-Only Root Filesystem

Test:

```bash
sudo docker exec \
  veriqta-app \
  sh -c 'touch /should-fail'
```

It should fail because the root filesystem is read-only.

But:

```bash
sudo docker exec \
  veriqta-app \
  sh -c 'touch /tmp/should-work && ls -l /tmp/should-work'
```

should work because `/tmp` is explicitly provided as temporary writable storage.

This is the principle:

```text
default filesystem = read-only

explicit runtime paths = writable only where required
```

---

## Security Control 6: Protect Secrets

Your database password is not:

```text
source code
```

It should not be:

```text
Dockerfile
Git repository
image layer
public README
screenshot
```

Check:

```bash
git status
```

before committing anything.

Add:

```bash
nano .gitignore
```

with:

```text
config/.env
backups/
evidence/private/
*.sql
*.sql.gz
*.log
```

Create:

```bash
nano config/.env.example
```

with:

```text
DB_NAME=veriqta_portal
DB_USER=portal_app
DB_PASSWORD=REPLACE_ME
DB_ROOT_PASSWORD=REPLACE_ME
```

Environment variables are useful for this lab, but they are not a perfect enterprise secrets-management system.

Document that limitation.

---

## Security Control 7: Protect Docker Socket

Inspect:

```bash
sudo ls -l /var/run/docker.sock
```

Do not mount:

```text
/var/run/docker.sock
```

into application containers.

A container with control over the Docker socket can often obtain extremely powerful control over the host.

---

## Security Control 8: Host Firewall

If the server is remotely administered, preserve SSH access before changing firewall rules.

Allow the application port from only the network that needs it.

For a lab subnet such as:

```text
192.168.60.0/24
```

an example is:

```bash
sudo ufw allow \
  from 192.168.60.0/24 \
  to any \
  port 8080 \
  proto tcp
```

Then:

```bash
sudo ufw status numbered
```

Do not assume host firewall behavior around Docker-published ports without testing it.

Docker networking can interact with Linux packet-filtering rules in ways that deserve explicit validation.

Test from another machine.

# Database Backup and Recovery

A Docker volume is persistent storage.

It is **not a backup**.

If the database is corrupted, the persistent volume can faithfully preserve the corruption.

You need an independent recovery mechanism.

---

# Build the Backup Script

Create:

```bash
nano scripts/backup-db.sh
```

Add:

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

PROJECT_DIR="$(
    cd "$(dirname "${BASH_SOURCE[0]}")/.." \
    && pwd
)"

ENV_FILE="${PROJECT_DIR}/config/.env"
BACKUP_DIR="${PROJECT_DIR}/backups"

[[ -f "$ENV_FILE" ]] || {
    echo "Environment file missing."
    exit 1
}

set -a
source "$ENV_FILE"
set +a

mkdir -p "$BACKUP_DIR"
chmod 0700 "$BACKUP_DIR"

TIMESTAMP="$(date '+%Y%m%d-%H%M%S')"
TEMP_FILE="${BACKUP_DIR}/.${DB_NAME}-${TIMESTAMP}.sql.tmp"
FINAL_FILE="${BACKUP_DIR}/${DB_NAME}-${TIMESTAMP}.sql"
CHECKSUM_FILE="${FINAL_FILE}.sha256"

cleanup() {
    rm -f "$TEMP_FILE"
}

trap cleanup EXIT

echo "Creating database backup."

docker exec \
    -e MYSQL_PWD="$DB_ROOT_PASSWORD" \
    veriqta-db \
    mariadb-dump \
    -u root \
    --single-transaction \
    --routines \
    --triggers \
    "$DB_NAME" \
    > "$TEMP_FILE"

[[ -s "$TEMP_FILE" ]] || {
    echo "Backup file is empty."
    exit 1
}

chmod 0600 "$TEMP_FILE"

mv "$TEMP_FILE" "$FINAL_FILE"

sha256sum "$FINAL_FILE" \
    > "$CHECKSUM_FILE"

chmod 0600 \
    "$FINAL_FILE" \
    "$CHECKSUM_FILE"

trap - EXIT

echo "Backup created:"
echo "$FINAL_FILE"
echo
echo "Checksum:"
cat "$CHECKSUM_FILE"
```

Make executable:

```bash
chmod 0750 scripts/backup-db.sh
```

Run:

```bash
sudo scripts/backup-db.sh
```

Check:

```bash
ls -lh backups/
```

---

# Why the Temporary File Matters

You do not want an interrupted dump to look like a completed backup.

The workflow is:

```text
dump
 ↓
temporary file
 ↓
verify non-empty
 ↓
set permissions
 ↓
atomic rename
 ↓
checksum
```

That is safer than writing directly to the final filename.

# Restore Test

Do not wait for a disaster to discover that your backup is unusable.

Find the latest dump:

```bash
LATEST_BACKUP="$(
  find backups \
    -maxdepth 1 \
    -type f \
    -name '*.sql' \
    -printf '%T@ %p\n' \
    | sort -nr \
    | head -n 1 \
    | cut -d' ' -f2-
)"
```

Check:

```bash
printf '%s\n' "$LATEST_BACKUP"
```

Verify its checksum using the corresponding checksum file.

Create a restore-test database:

```bash
sudo docker exec \
  -e MYSQL_PWD="$DB_ROOT_PASSWORD" \
  veriqta-db \
  mariadb \
  -u root \
  -e 'CREATE DATABASE veriqta_restore_test;'
```

Restore:

```bash
cat "$LATEST_BACKUP" \
  | sudo docker exec -i \
      -e MYSQL_PWD="$DB_ROOT_PASSWORD" \
      veriqta-db \
      mariadb \
      -u root \
      veriqta_restore_test
```

Query:

```bash
sudo docker exec \
  -e MYSQL_PWD="$DB_ROOT_PASSWORD" \
  veriqta-db \
  mariadb \
  -u root \
  -e 'USE veriqta_restore_test; SELECT * FROM service_status;'
```

If successful, remove the test database:

```bash
sudo docker exec \
  -e MYSQL_PWD="$DB_ROOT_PASSWORD" \
  veriqta-db \
  mariadb \
  -u root \
  -e 'DROP DATABASE veriqta_restore_test;'
```

Now you have evidence that:

```text
BACKUP EXISTS
```

and:

```text
BACKUP CAN BE RESTORED
```

are not being treated as the same thing.

# 23. Interview Preparation

### What is a container?

A container is an isolated process environment that uses operating-system mechanisms such as namespaces, cgroups, capabilities, and filesystem isolation while sharing the host kernel.

### Is a container a virtual machine?

No.

A VM normally virtualizes hardware and runs its own guest kernel.

Containers generally share the host kernel.

### What is an image?

An image is an immutable template used to create containers.

### What is a container?

A container is a runtime instance created from an image plus runtime configuration and a writable container layer.

### What happens to the writable layer when a container is deleted?

Data stored only there is normally lost with the container.

That is why important state must use persistent storage.

### What is a Docker volume?

Docker-managed persistent storage whose lifecycle can be separated from the lifecycle of an individual container.

### What is a bind mount?

It maps a specific host filesystem path into a container.

### When would you prefer a named volume?

Commonly for application-managed persistent data such as database storage where Docker-managed storage is appropriate.

### When would you use a bind mount?

When the container intentionally needs access to a specific host-managed file or directory, such as development source code or controlled configuration.

### Why should a database not store its only copy of data in the container writable layer?

Because replacing/removing the container could destroy the data.

### Is a Docker volume a backup?

No.

Persistence and backup solve different problems.

### What is Docker Compose?

A declarative way to define and operate multi-container applications, including services, networks, volumes, health checks, environment configuration, and other runtime settings.

### What is a Docker bridge network?

A software-defined network on the Docker host that allows attached containers to communicate according to their network membership and configuration.

### How does the app find the database?

Through Docker's service-name resolution:

```text
db
```

### Why not use the database container's IP?

Container IP addresses may change when containers are recreated.

The service name provides a more stable abstraction.

### What does `localhost` mean inside the app container?

The app container itself.

It does not mean the database container or Docker host.

### What is port publishing?

Mapping a host address/port to a container port so traffic can reach the container from outside its Docker network.

### Does `EXPOSE 9000` publish port 9000 to the host?

No.

`EXPOSE` documents intended container ports but does not by itself publish them to the host.

### Why was MariaDB not published?

Only the application needs database access. Publishing the database would unnecessarily increase exposure.

### Why were two Docker networks used?

To create a meaningful separation between frontend communication and database communication.

### Why does the app join both networks?

It needs to receive FastCGI traffic from Nginx and communicate with MariaDB.

### Why doesn't Nginx join the backend network?

It has no operational reason to communicate directly with MariaDB.

### What is a health check?

A runtime test used to evaluate whether a container's service is functioning according to defined criteria.

### Is `running` the same as `healthy`?

No.

A process can remain running while its service is unusable.

### Does Docker automatically restart an unhealthy container just because a health check fails?

Not simply because its health status becomes unhealthy in ordinary Docker Engine/Compose operation. Restart policies primarily react to container termination/restart conditions. Health status is evidence that orchestration or operational tooling can use.

This distinction matters.

### What is a restart policy?

It controls whether Docker attempts to restart containers after certain stops or daemon/host recovery conditions.

### Why use memory limits?

To constrain how much host memory a workload can consume.

### What is OOM?

Out Of Memory.

A process may be killed when memory cannot be provided or when enforced memory constraints are exceeded.

### How do you check whether a container was OOM-killed?

Inspect:

```bash
docker inspect CONTAINER
```

and examine the state, including `OOMKilled`.

### What are Linux capabilities?

They divide traditional root privileges into more granular privileges.

### Why drop capabilities?

A service should receive only privileges it actually requires.

### What does `cap_drop: ALL` do?

It removes the default capability set, after which required capabilities can be added deliberately.

### What does `no-new-privileges` do?

It prevents processes from gaining additional privileges through privilege-elevation mechanisms during execution.

### Why use a read-only root filesystem?

It reduces unnecessary runtime modification and can limit some classes of compromise or accidental change.

### Why provide tmpfs?

Some applications need writable temporary/runtime locations even when the main container filesystem is read-only.

### Why run the application as non-root?

It reduces unnecessary privilege if the process is compromised or behaves unexpectedly.

### Is root inside a container harmless?

No.

Container isolation changes the boundary, but root inside a container can still create substantial risk, especially with dangerous mounts, capabilities, privileged mode, kernel vulnerabilities, or Docker socket access.

### Why is Docker group membership sensitive?

Docker daemon access can effectively provide host-level administrative capabilities.

### Why should you avoid mounting the Docker socket into ordinary containers?

A process with Docker API control can potentially create highly privileged containers and gain control over the host.

### Why avoid `latest`?

It is a moving tag and does not provide a deterministic statement of exactly which image version you intended.

### Are version tags completely immutable?

Not necessarily.

For stronger supply-chain reproducibility, images can be pinned by digest.

### What is `.dockerignore`?

It prevents selected files from entering the Docker build context.

### Why does build context matter for security?

Sensitive or unnecessary files should not be sent to the build process if they are not required.

### What is the difference between build-time and runtime failure?

A build failure prevents creation of the intended image. A runtime failure occurs after an image has successfully been built and a container is started or serving traffic.

### What causes Nginx 502 in this architecture?

Common possibilities include:

```text
app container unavailable
wrong upstream hostname
wrong port
network separation
PHP-FPM unavailable
upstream connection failure
```

### How would you troubleshoot it?

Start with:

```text
Nginx logs
app state
app health
network membership
service-name resolution
upstream listener
```

### Why use `docker inspect`?

It exposes detailed runtime metadata including:

```text
state
health
networking
mounts
environment
resource settings
security settings
```

### Why use `docker stats`?

To inspect live CPU, memory, network, and I/O consumption.

### Why use `docker system df`?

To understand Docker disk usage across images, containers, volumes, and build cache.

### Why shouldn't you immediately run `docker system prune -a --volumes` during disk pressure?

Because it can delete images, caches, containers, networks, and volumes that may still be needed. Destructive cleanup requires understanding what each resource contains.

### Why can all containers be running while the application is still broken?

Because process state does not prove:

```text
network connectivity
correct configuration
dependency health
database authentication
storage availability
application correctness
```

### What is the most important troubleshooting principle from this project?

Find the failed layer before changing the system.

# Production Limitations You Must Document

This project creates a strong **single-host container platform**.

It does not create a highly available production container cluster.

Your current architecture still contains a major failure domain:

```text
                 CLIENTS
                    |
                    v
              +-----------+
              | docker01  |
              +-----+-----+
                    |
       +------------+------------+
       |            |            |
       v            v            v
      WEB          APP           DB
                                  |
                                  v
                               VOLUME
```

If:

```text
docker01
```

is lost completely, the entire application is lost until you recover or rebuild the host and restore its state.

A stronger production design could eventually introduce:

```text
               LOAD BALANCER
                    |
        +-----------+-----------+
        |                       |
        v                       v
  CONTAINER HOST 1       CONTAINER HOST 2
        |                       |
        +-----------+-----------+
                    |
                    v
          EXTERNAL DATABASE
                    |
                    v
          REDUNDANT STORAGE
```

You would also consider:

```text
private image registry
image digest pinning
vulnerability scanning
software bill of materials
signed images
central secrets management
TLS
central logging
metrics
alerting
off-host backups
backup retention
automated restore testing
multiple hosts
orchestration
rolling deployments
load balancing
service discovery
high availability
database replication
central configuration management
patch management
disaster recovery
```

Those are production improvements.

They do not reduce the value of this project.

The purpose here is to make sure you understand what is happening on the Linux host before a larger orchestration platform starts abstracting it away.
