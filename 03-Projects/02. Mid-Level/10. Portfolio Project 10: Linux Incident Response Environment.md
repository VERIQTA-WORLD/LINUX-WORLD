# 01. Project Title

## Linux Incident Response Environment

A Linux administrator can fix a broken service.

An incident responder has a harder job.

You cannot begin with:

```bash
sudo systemctl restart nginx
```

and declare victory.

During an incident, restarting or deleting things too early can destroy the evidence you need to answer:

```text
What happened?

When did it start?

Which account was involved?

What changed?

What process executed?

What files were modified?

Was persistence established?

Was the network involved?

How far did the incident spread?

What evidence supports that conclusion?

What was the root cause?

What must be contained?

What must be preserved?

Can the system be trusted afterward?

How do we prevent this from happening again?
```

You are going to build a deliberately misconfigured Linux application server and then investigate a controlled security incident from beginning to end.

The environment will contain enough evidence for you to discover the incident instead of simply being told the answer.

Your response workflow will be:

```text
PREPARE
   ↓
BASELINE
   ↓
MONITOR
   ↓
SIMULATE INCIDENT
   ↓
DETECT
   ↓
TRIAGE
   ↓
PRESERVE EVIDENCE
   ↓
BUILD TIMELINE
   ↓
INVESTIGATE
   ↓
SCOPE
   ↓
CONTAIN
   ↓
ERADICATE
   ↓
RECOVER
   ↓
VERIFY
   ↓
ROOT-CAUSE ANALYSIS
   ↓
POST-INCIDENT REVIEW
   ↓
PREVENT RECURRENCE
```

This project is not about memorizing security commands.

It is about learning to reason from Linux evidence.

# Evidence Hierarchy

During the project, classify findings.

### Observation

Something you directly observed.

Example:

```text
TCP port 9001 is listening.
```

### Evidence

Data supporting an observation.

Example:

```bash
sudo ss -lntup
```

shows a specific PID listening on `127.0.0.1:9001`.

### Hypothesis

A possible explanation.

Example:

> The process may be related to unauthorized persistence.

### Confirmed finding

Multiple evidence sources support the conclusion.

Example:

```text
The executable belongs to an unauthorized systemd service
created during the suspicious privileged session.
```

Do not promote hypotheses to facts without evidence.

# Phase 4 — Build the System Baseline

Create:

```bash
sudo mkdir -p /var/lib/veriqta-ir/baseline
```

Set:

```bash
sudo chmod 0700 /var/lib/veriqta-ir
```

Create:

```bash
sudo nano /usr/local/sbin/veriqta-collect-baseline
```

Add:

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

OUT="/var/lib/veriqta-ir/baseline"

install -d -m 0700 "$OUT"

date -u \
  > "${OUT}/collection-time.txt"

hostnamectl \
  > "${OUT}/hostname.txt"

uname -a \
  > "${OUT}/kernel.txt"

ip -brief address \
  > "${OUT}/addresses.txt"

ip route \
  > "${OUT}/routes.txt"

ss -lntup \
  > "${OUT}/listeners.txt"

ps auxww \
  > "${OUT}/processes.txt"

systemctl list-units \
  --type=service \
  --state=running \
  --no-pager \
  > "${OUT}/running-services.txt"

systemctl list-unit-files \
  --type=service \
  --no-pager \
  > "${OUT}/service-unit-files.txt"

getent passwd \
  > "${OUT}/passwd.txt"

getent group \
  > "${OUT}/group.txt"

getent group sudo \
  > "${OUT}/sudo-group.txt"

find /etc/systemd/system \
  -maxdepth 3 \
  -type f \
  -printf '%p\n' \
  | sort \
  > "${OUT}/local-systemd-files.txt"

find /etc/cron.d /etc/cron.daily /etc/cron.hourly \
  -maxdepth 2 \
  -type f \
  -printf '%p\n' 2>/dev/null \
  | sort \
  > "${OUT}/cron-files.txt"

dpkg-query \
  -W \
  -f='${Package}\t${Version}\n' \
  | sort \
  > "${OUT}/packages.txt"

ufw status verbose \
  > "${OUT}/ufw.txt"

find /var/www/veriqta \
  -type f \
  -exec sha256sum {} \; \
  | sort \
  > "${OUT}/web-hashes.txt"

find /etc/nginx \
  -type f \
  -exec sha256sum {} \; \
  | sort \
  > "${OUT}/nginx-hashes.txt"
```

Protect:

```bash
sudo chown root:root /usr/local/sbin/veriqta-collect-baseline
```

```bash
sudo chmod 0750 /usr/local/sbin/veriqta-collect-baseline
```

Run:

```bash
sudo /usr/local/sbin/veriqta-collect-baseline
```

Inspect:

```bash
sudo ls -lah /var/lib/veriqta-ir/baseline
```

# Understand the Rule

For example:

```text
-w /etc/passwd -p wa -k identity
```

means conceptually:

```text
-w
watch this path

/etc/passwd
target

-p wa
record writes and attribute changes

-k identity
```

# Audit Rule Caveat

auditd is useful, but it is not magical.

A privileged attacker may also attempt to interfere with local evidence.

That is why mature environments combine local telemetry with:

```text

remote collection
access controls
monitoring
immutable/off-host storage
```

# 14. Automation

# Build a Live-Response Collector

During an incident, you want repeatable evidence collection.

Create on `app01`:

```bash
sudo nano /usr/local/sbin/veriqta-live-response
```

Add:

```bash
#!/usr/bin/env bash

set -Eeuo pipefail

CASE_ID="${1:-}"

if [[ -z "$CASE_ID" ]]; then
    echo "Usage: $0 CASE_ID" >&2
    exit 2
fi

if [[ ! "$CASE_ID" =~ ^[A-Za-z0-9._-]+$ ]]; then
    echo "Invalid case ID." >&2
    exit 2
fi

TIMESTAMP="$(
    date -u '+%Y%m%dT%H%M%SZ'
)"

OUT="/var/lib/veriqta-ir/evidence/${CASE_ID}/${TIMESTAMP}"

install \
  -d \
  -m 0700 \
  "$OUT"

date -u \
  > "${OUT}/collection-time.txt"

hostnamectl \
  > "${OUT}/hostname.txt"

uname -a \
  > "${OUT}/kernel.txt"

who \
  > "${OUT}/who.txt"

w \
  > "${OUT}/w.txt"

last \
  -F \
  > "${OUT}/last.txt"

lastlog \
  > "${OUT}/lastlog.txt"

ps auxww \
  > "${OUT}/ps-auxww.txt"

ps -eo \
  pid,ppid,user,lstart,etime,%cpu,%mem,args \
  --sort=pid \
  > "${OUT}/process-tree-data.txt"

ss -lntup \
  > "${OUT}/listening-sockets.txt"

ss -tunap \
  > "${OUT}/network-connections.txt"

ip -brief address \
  > "${OUT}/addresses.txt"

ip route \
  > "${OUT}/routes.txt"

ip neigh \
  > "${OUT}/neighbors.txt"

systemctl list-units \
  --type=service \
  --all \
  --no-pager \
  > "${OUT}/services.txt"

systemctl list-unit-files \
  --type=service \
  --no-pager \
  > "${OUT}/service-unit-files.txt"

systemctl --failed \
  --no-pager \
  > "${OUT}/failed-units.txt" || true

getent passwd \
  > "${OUT}/passwd.txt"

getent group \
  > "${OUT}/group.txt"

getent group sudo \
  > "${OUT}/sudo-group.txt"

find /etc/systemd/system \
  -type f \
  -printf '%TY-%Tm-%TdT%TH:%TM:%TS %u %g %m %p\n' \
  2>/dev/null \
  | sort \
  > "${OUT}/systemd-files.txt"

find /etc/cron.d /etc/cron.daily /etc/cron.hourly \
  -type f \
  -printf '%TY-%Tm-%TdT%TH:%TM:%TS %u %g %m %p\n' \
  2>/dev/null \
  | sort \
  > "${OUT}/cron-files.txt"

find /var/www/veriqta \
  -type f \
  -exec sha256sum {} \; \
  2>/dev/null \
  | sort \
  > "${OUT}/web-hashes.txt"

journalctl \
  --since "-24 hours" \
  --no-pager \
  > "${OUT}/journal-24h.txt"

journalctl \
  -u ssh \
  --since "-24 hours" \
  --no-pager \
  > "${OUT}/ssh-journal-24h.txt" || true

journalctl \
  -u nginx \
  --since "-24 hours" \
  --no-pager \
  > "${OUT}/nginx-journal-24h.txt" || true

ausearch \
  --start today \
  > "${OUT}/audit-today.txt" || true

ufw status verbose \
  > "${OUT}/ufw.txt"

dpkg-query \
  -W \
  -f='${Package}\t${Version}\n' \
  | sort \
  > "${OUT}/packages.txt"

(
    cd "$OUT"

    find . \
      -type f \
      ! -name SHA256SUMS \
      -exec sha256sum {} \; \
      | sort \
      > SHA256SUMS
)

echo "$OUT"
```

Protect:

```bash
sudo chown root:root /usr/local/sbin/veriqta-live-response
```

```bash
sudo chmod 0750 /usr/local/sbin/veriqta-live-response
```

# Important Forensic Limitation

This is a **live-response lab**, not full forensic acquisition.

Every command you run changes the live system to some degree.

For example:

```text
log access timestamps may change
process state changes continuously
network connections disappear
shell history may change
journals continue receiving events
```

Therefore, your report should say:

> Evidence was collected from a live Linux system. Collection actions and continued system operation may have altered some volatile state.

That is more accurate than pretending your collection was forensically pristine.

Separate:

```text
Observed timestamp
```

from:


# 17. Failure Simulation

In addition to the main incident, perform focused investigation exercises.

---

## Failure Lab 01 — Authentication Noise Without Compromise

Generate several failed lab SSH logins.

Do nothing else.

Investigate.

Your conclusion should **not** be:

> Server compromised.

It should be something closer to:

> Failed authentication attempts were observed. No corresponding successful unauthorized login or post-authentication activity was identified in the evidence examined.

This teaches restraint.

---

## Failure Lab 02 — Legitimate Administrator Change

Make a documented authorized Nginx change.

Record it in:

```text
CHANGE-RECORD.md
```

Then detect the changed file.

Your investigation should distinguish:

```text
unexpected technically
```

from:

```text
unauthorized operationally
```

---

## Failure Lab 03 — Deleted Suspicious Process

Start a harmless process.

Collect its PID.

Stop it before investigation.

Now:

```bash
ps
```

cannot show it.

Can logs or audit evidence still reveal it?

This teaches the volatility of process evidence.

---

## Failure Lab 04 — Service Exists but Is Inactive

Create a harmless unauthorized systemd unit but do not start it.

Investigation should detect persistence capability even without an active process.

---

## Failure Lab 05 — Process Exists Without Listening Socket

Run:

```bash
sleep 3600
```

from a controlled lab account.

The process exists.

No port exists.

This teaches:

```text
process investigation
```

and:

```text
network investigation
```

are related but not interchangeable.

---

## Failure Lab 06 — Listening Socket From Legitimate Service

Use a legitimate service on a known port.

Detect it.

Compare with baseline.

Do not classify it as suspicious merely because it listens.

---

## Failure Lab 07 — Hash Mismatch From Authorized Deployment

Make a legitimate documented web update.

The hash changes.

Your baseline detector reports it.

The correct conclusion is:

```text
integrity change detected
```

not automatically:

```text
security compromise
```

---

## Failure Lab 08 — Deleted File Still Referenced by Process

In a disposable lab, open a temporary file with a harmless process and remove its directory entry while the process keeps it open.

Investigate:

```bash

```

This teaches why deleted-but-open files matter during investigations.

Do not use this technique to conceal software.

## Failure Lab 09 — Cron Persistence

Create a harmless logger job.

Detect:

```text
execution evidence
```

Remove it.

Verify no further scheduled messages appear.

## Failure Lab 10 — systemd Persistence

Create a harmless service.

```text
listener
logs
```

Remove it correctly.

Verify:

```text

process gone
listener gone
```

## Failure Lab 12 — Modified SSH Configuration

Create an authorized but unexpected drop-in.

Detect it.

```text

```

versus:

```text

```

Those are different questions.

## Failure Lab 13 — Nginx Configuration Tampering

Change a harmless Nginx directive.

Use:

```bash

```

Restore from trusted configuration.

---

## Failure Lab 14 — Firewall Drift

Add a temporary lab firewall rule.


against baseline.

Identify the change.

Do not run:

```bash

```

just to fix one rule.

## Failure Lab 15 — Account Locked but Session Still Exists

In a controlled VM, establish a session with a disposable account, then lock the account from another administrative session.

Observe whether locking the account automatically terminates the already-running session.

This teaches:

```text

```

is not always equivalent to:

```text

```

## Failure Lab 16 — Log Gap

Temporarily stop a nonessential lab logging component in a disposable snapshot.

Generate harmless activity.

Restore logging.

Investigate what evidence is absent.

This teaches:

> Logs only contain what was collected.

Do not assume missing logs mean missing activity.

## Failure Lab 18 — Reboot Removes Volatile Evidence

```text

Which logs survived?
```

This demonstrates why volatile evidence is collected early.

## Example RCA Structure

### Incident

Unauthorized changes were identified on `app01`.

### Initial access

Evidence indicated anomalous authentication activity around the incident window.

### Privilege

### Persistence


### Application impact

### Network impact

# Five Whys Exercise

Ask:

**Why was unauthorized software running?**

Because an unauthorized service had been created and enabled.

**Why could that service be enabled?**

Because privileged access was available.

**Why did an unauthorized identity have privilege?**

Because the account had been added to an administrative group.

Continue until you reach the control/process weakness your simulated scenario was designed to represent.

Do not force exactly five questions if the causal chain requires fewer or more.

---

# Rebuild Versus Clean

A critical incident-response question is:

> Should this server be trusted after remediation?

In this training lab, you clean the machine because the goal is to practice eradication.

In a serious real-world compromise involving privileged access, rebuilding from a known-good image may be safer than attempting to identify and remove every unauthorized change.

Why?

Because privileged compromise can affect:

```text
binaries
libraries
services
kernel modules
boot configuration
accounts
credentials
logs
scheduled tasks
SSH configuration
package state
application code
```

Your ability to prove that every change was found may be limited.

Therefore your report should explicitly discuss:

```text
clean in place
versus
rebuild from trusted source
```

as a risk decision.

# 23. Interview Preparation

### What is incident response?

A structured process for detecting, investigating, containing, eradicating, recovering from, and learning from security incidents.

### What is triage?

The initial assessment used to understand the alert, affected systems, urgency, potential impact, and immediate evidence requirements.

### What is containment?

Limiting continued unauthorized activity or damage.

### What is eradication?

Removing the confirmed cause and unauthorized artifacts.

### What is recovery?

Returning systems to an acceptable operational state and verifying that they remain healthy and secure.

### Why not immediately kill a suspicious process?

Because the process may contain valuable volatile evidence about its command line, parent, user, files, network connections, and runtime state.

### What is volatile evidence?

Evidence that can disappear or change quickly, such as running processes, active connections, logged-in sessions, and memory-resident state.

### What is persistent evidence?

Evidence that usually survives longer, such as files, logs, configuration, account databases, and scheduled tasks.

### Why collect volatile evidence early?

Because it may disappear when a process exits, a connection closes, or a server reboots.

### Why establish a baseline?

Because you need a reference for normal accounts, services, ports, packages, files, and configuration.

### Does “not in the baseline” mean malicious?

No.

It means the difference requires explanation.

### What does `ps` tell you?

Current process state.

### What does `/proc` provide?

Kernel-exposed information about running processes and system state.

### Why inspect PPID?

It helps identify what started a process.

### What does `ss` provide?

Information about sockets, listeners, and network connections.

### Why map a socket to a PID?

To connect network behavior to the responsible process.

### Why map a PID to systemd?

To determine whether a service manager created or supervises the process.

### Why is systemd relevant to incident response?

Unauthorized services can provide persistence, while legitimate services also explain many unfamiliar processes.

### Why inspect cron?

Scheduled jobs can provide legitimate automation or unauthorized persistence.

### Why inspect `authorized_keys`?

SSH keys can provide persistent remote authentication.

### Why inspect `/etc/passwd`?

It defines local account information.

### Why inspect `/etc/group`?

It helps identify group membership and privilege changes.

### Why is the `sudo` group important on Ubuntu?

Membership commonly grants administrative privilege through the configured sudo policy.

### Why search for UID 0?

UID 0 has root-equivalent identity semantics.

### What does auditd provide?

Kernel auditing of configured security-relevant activity.

### What is an audit key?

A label attached to audit rules that helps retrieve related events.

### Why isn't auditd sufficient by itself?

It only records what its configuration and kernel audit system capture, and local evidence may be incomplete or tampered with during sufficiently privileged compromise.

### Why use SHA-256?

To create and compare cryptographic digests of files or evidence.

### Does a matching hash prove a file is safe?

No.

It proves the compared bytes match the reference digest. The trustworthiness of the reference still matters.

### What is evidence integrity?

Confidence that evidence has not changed unexpectedly between collection and analysis.

### Why hash evidence before and after transfer?

To detect accidental or unauthorized changes during handling.

### What is chain of custody?

Documentation of how evidence was collected, handled, transferred, stored, and accessed.

### Is this lab full digital forensics?

No.

It is a Linux live-response and incident-investigation lab.

### What is the limitation of live response?

Investigation occurs on a running system, so the system and collection actions continue to change state.

### What does `stat` show?

Filesystem metadata including ownership, permissions, size, and timestamps.

### Is Linux `ctime` creation time?

Generally no. `ctime` records inode metadata change time.

### What is an indicator of compromise?

An observable artifact associated with potentially unauthorized or malicious activity.

### Is every IOC proof of compromise?

No. Indicators require context and validation.

### What is root cause?

The underlying condition or event that enabled or produced the incident, not merely one visible symptom.

### What is a contributing factor?

A condition that increased likelihood, impact, or detection difficulty without necessarily being the primary cause.

### Why distinguish fact from hypothesis?

Because incident conclusions must be evidence-supported.

### Why build a timeline?

It helps correlate events across different evidence sources and understand sequence.

### Why use UTC?

It reduces timezone ambiguity when correlating multiple systems.

### What is incident scope?

The systems, accounts, data, services, and activities affected or potentially affected by the incident.

### Why is “no evidence found” different from “did not happen”?

Because collection may be incomplete and evidence can be absent, overwritten, unavailable, or outside the investigated sources.

### Why might you rebuild instead of clean?

With sufficiently privileged compromise, you may not be able to establish that every unauthorized modification was discovered and removed.

### What must happen after remediation?

Validation.

### Why reboot after eradication?

To identify persistence that reappears during boot and verify legitimate services recover correctly.

### Why collect post-remediation evidence?

To demonstrate how the recovered state differs from the incident state and compare it with the trusted baseline.

# Final Incident Architecture

By the end of the project, you should be able to reconstruct the investigation from evidence:

```text
                  SECURITY ALERT
                       |
                       v
                +--------------+
                |    app01     |
                +------+-------+
                       |
        +--------------+--------------+
        |              |              |
        v              v              v
 AUTHENTICATION     PROCESS        FILESYSTEM
   EVIDENCE         EVIDENCE        EVIDENCE
        |              |              |
        +------+-------+------+-------+
               |              |
               v              v
            ACCOUNT       PERSISTENCE
            CHANGES          DATA
               |              |
               +------+-------+
                      |
                      v
                  TIMELINE
                      |
                      v
               INCIDENT SCOPE
                      |
                      v
                 ROOT CAUSE
                      |
        +-------------+-------------+
        |             |             |
        v             v             v
    CONTAIN       ERADICATE      RECOVER
        |             |             |
        +-------------+-------------+
                      |
                      v
                   VERIFY
                      |
                      v
             POST-INCIDENT REVIEW
                      |
                      v
             PREVENT RECURRENCE
```

The project is complete when you can look at an unfamiliar Linux server and resist the temptation to immediately “fix” what looks wrong.

Instead, your thinking should become:

```text
What exactly did I observe?
        ↓
What evidence supports it?
        ↓
What is normal for this server?
        ↓
What changed?
        ↓
When did it change?
        ↓
Who or what made the change?
        ↓
What other activity occurred nearby?
        ↓
What is the blast radius?
        ↓
What evidence must I preserve?
        ↓
What can I safely contain?
        ↓
What must be removed?
        ↓
What must be restored?
        ↓
How do I prove recovery?
        ↓
Why was this possible?
        ↓
What prevents recurrence?
```

That is the real skill this project is designed to build.

**Troubleshooting asks, “Why is the server behaving this way?”**

**Incident response adds, “What happened to the server, what evidence proves it, how far did it go, and can I trust the system afterward?”**
