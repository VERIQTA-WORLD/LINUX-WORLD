# 01. Project Title

## Linux Security Monitoring Platform

A Linux server can appear completely healthy while something dangerous is happening inside it.

CPU usage may look normal.

The website may still load.

The server may still respond to SSH.

`systemctl` may report every important service as active.

And yet:

```text
someone may be repeatedly guessing SSH passwords

an unexpected user account may have appeared

a privileged group may have changed

a protected configuration file may have been modified

an unknown process may be listening on a network port

a service may have started unexpectedly

sudo may be used unusually

an executable may have changed

a scheduled task may have been added

an authentication failure pattern may be developing
```

That is the problem you will solve in this project.

You are going to build a Linux security monitoring platform that watches several categories of system activity and turns raw operating-system evidence into useful security signals.

The goal is not:

> Install a security tool and assume the server is secure.

The goal is to understand how Linux itself exposes security evidence, how that evidence can be collected, how suspicious activity can be detected, and how an operator investigates it.

Your platform will monitor:

```text
Authentication activity
        |
        +---- Failed SSH authentication
        +---- Successful SSH authentication
        +---- sudo activity
        +---- account activity
        |
        v
File integrity
        |
        +---- protected configuration changes
        +---- unexpected file modifications
        +---- monitored identity files
        |
        v
Processes
        |
        +---- unusual processes
        +---- unexpected command execution
        +---- suspicious process characteristics
        |
        v
Network exposure
        |
        +---- listening ports
        +---- unexpected listeners
        +---- service exposure changes
        |
        v
Services
        |
        +---- failed services
        +---- newly active services
        +---- unexpected service state
        |
        v
Security events
        |
        +---- audit events
        +---- integrity violations
        +---- threshold violations
        +---- correlated observations
        |
        v
Detection
        |
        v
Evidence
        |
        v
Investigation
        |
        v
Response
```

By the end, you will have something much more useful than a collection of grep commands.

You will have a small security-monitoring system.

# 03. Project Difficulty

## Mid-Level

This is not a beginner project where you run:

```bash
grep Failed /var/log/auth.log
```

and call that security monitoring.

You will work through a more realistic pipeline:

```text
EVENT
  ↓
LOG/EVIDENCE GENERATION
  ↓
COLLECTION
  ↓
CENTRALIZATION
  ↓
NORMALIZATION
  ↓
BASELINE
  ↓
DETECTION RULE
  ↓
THRESHOLD
  ↓
ALERT
  ↓
TRIAGE
  ↓
CORRELATION
  ↓
INVESTIGATION
  ↓
RESPONSE
  ↓
RECOVERY
  ↓
DOCUMENTATION
```

You will also learn an important distinction:

```text
EVENT ≠ ALERT ≠ INCIDENT
```

An **event** is something that happened.

An **alert** is something your monitoring logic determined deserves attention.

An **incident** is a security situation that has been investigated and classified accordingly.

Your scripts should not claim that every failed login or file modification is an attack.

They should produce evidence for investigation.

# Configure `security01` as the Log Receiver

Create:

```bash
sudo nano /etc/rsyslog.d/20-veriqta-receiver.conf
```

Add:

```text
module(load="imtcp")

input(
    type="imtcp"
    port="514"
)

template(
    name="RemoteHostLogs"
    type="string"
    string="/var/log/remote/%HOSTNAME%/%PROGRAMNAME%.log"
)

if $fromhost-ip != "127.0.0.1" then {
    action(
        type="omfile"
        dynaFile="RemoteHostLogs"
        createDirs="on"
        dirCreateMode="0750"
        fileCreateMode="0640"
    )
    stop
}
```

This lab uses TCP rather than UDP so the transport has connection-oriented delivery behavior.

For a real environment, you would also evaluate authenticated and encrypted log transport.

# Phase 5: Monitor Identity and Privilege Files


```text
-w /etc/passwd -p wa -k identity
```


watches a path.

# Phase 6: Add Process Execution Auditing

Execution monitoring can generate substantial audit volume.

That is precisely why you should not add broad audit rules without understanding their effect.

For this lab, create a rule focused on interactive user execution rather than pretending that every process event is automatically malicious.

Add to the audit rules:

```text
-a always,exit -F arch=b64 -S execve -F auid>=1000 -F auid!=unset -k user_exec
```

On a 64-bit Ubuntu system, this captures relevant `execve` activity for login users with AUIDs in the normal user range.

Load:

```bash
sudo augenrules --load
```

Verify:

```bash
sudo auditctl -l
```

Generate an event:

```bash
whoami
```

```bash
id
```

```bash
/usr/bin/curl --version
```

Search:

```bash
sudo ausearch -k user_exec -i
```

Do not label every captured command suspicious.

The audit record is evidence.

Your detection logic decides what deserves investigation.

# 14. Automation

# Phase 7: Build Authentication Monitoring

On `security01`, create:

```bash
sudo nano /opt/veriqta-security-monitor/bin/auth-monitor.sh
```

Add:

```bash
#!/usr/bin/env bash

set -Eeuo pipefail
umask 027

REMOTE_LOG_ROOT="/var/log/remote"
REPORT_DIR="/opt/veriqta-security-monitor/reports"
ALERT_DIR="/opt/veriqta-security-monitor/alerts"
THRESHOLD="${AUTH_FAILURE_THRESHOLD:-5}"

mkdir -p "$REPORT_DIR" "$ALERT_DIR"

timestamp="$(date '+%Y%m%d-%H%M%S')"
report="${REPORT_DIR}/auth-${timestamp}.txt"
alert="${ALERT_DIR}/auth-${timestamp}.alert"

tmp="$(mktemp)"
trap 'rm -f "$tmp"' EXIT

{
    echo "VERIQTA Authentication Security Report"
    echo "Generated: $(date --iso-8601=seconds)"
    echo "Threshold: $THRESHOLD"
    echo
} > "$report"

if [[ ! -d "$REMOTE_LOG_ROOT" ]]; then
    echo "Remote log directory does not exist: $REMOTE_LOG_ROOT" >> "$report"
    exit 1
fi

grep -RhsE \
    'Failed password|Invalid user|authentication failure' \
    "$REMOTE_LOG_ROOT" > "$tmp" || true

failure_count="$(wc -l < "$tmp")"

{
    echo "Authentication failure records found: $failure_count"
    echo
    echo "Sample evidence:"
    head -n 20 "$tmp"
} >> "$report"

if (( failure_count >= THRESHOLD )); then
    {
        echo "VERIQTA SECURITY ALERT"
        echo "Generated: $(date --iso-8601=seconds)"
        echo "Type: Authentication Failure Threshold"
        echo "Observed records: $failure_count"
        echo "Configured threshold: $THRESHOLD"
        echo
        echo "This alert requires investigation."
        echo "It does not by itself prove malicious activity."
    } > "$alert"

    echo "ALERT: authentication threshold reached"
    exit 2
fi

echo "OK: authentication threshold not reached"
exit 0
```

Make executable:

```bash
sudo chmod 0750 \
  /opt/veriqta-security-monitor/bin/auth-monitor.sh
```

Run:

```bash
sudo /opt/veriqta-security-monitor/bin/auth-monitor.sh
```

# Important Limitation

The first version searches the stored remote logs rather than a precise rolling time window.

That means the count can grow indefinitely.

That is not good enough for a mature detection.

So you will improve the design.

The lesson is important:

```text
"5 failures exist in stored logs"
```

is not the same detection as:

```text
"5 failures occurred from one source within 5 minutes"
```

Security detections need:

```text
event definition
+
scope
+
time window
+
threshold
+
context
```

# Phase 8: Analyze Failed SSH Sources

Depending on your OpenSSH log format, failed password records may resemble:

```text
Failed password for invalid user example from 192.168.56.99 port 42111 ssh2
```

Extract candidate source addresses:

```bash
sudo grep -Rhs 'Failed password' /var/log/remote \
  | awk '{
      for (i=1; i<=NF; i++) {
          if ($i == "from") {
              print $(i+1)
          }
      }
    }' \
  | sort \
  | uniq -c \
  | sort -nr
```

Representative result:

```text
12 192.168.56.99
3 192.168.56.10
```

Interpret carefully.

A high failure count is a signal.

It is not automatic proof of an attack.

Possible explanations include:

```text
password guessing
old credentials in automation
a user mistyping a password
misconfigured monitoring
stale deployment credentials
security testing
```

Investigation establishes context.

# Phase 11: Build File Integrity Monitoring with AIDE

Install on both monitored servers:

```bash
sudo apt install -y aide
```

AIDE creates a known-state database and later compares the filesystem against it.

Conceptually:

```text
KNOWN STATE
    |
    v
AIDE DATABASE
    |
    v
filesystem changes
    |
    v
AIDE CHECK
    |
    v
DIFFERENCES
```

Initialize the database using the packaging workflow available on your Ubuntu installation.

Start by inspecting:

```bash
aide --version
```

and the installed AIDE configuration/documentation.

On Ubuntu, the package may provide helper tooling around database initialization. Use the installed package's supported initialization path rather than blindly assuming another distribution's file locations.

After initialization, run a check:

```bash
sudo aide --check
```

# Understanding the Baseline Problem

Suppose you establish an AIDE baseline while the system is already compromised.

```text

        ≠
proof that every baseline file is legitimate
```

A baseline should be created from a known-good state.

# Unusual Process Investigation

# Create a Listener Monitor

Create:

```bash
sudo nano /usr/local/sbin/veriqta-listener-monitor
```

Add:

```bash
#!/usr/bin/env bash

set -Eeuo pipefail
umask 027

EXPECTED="/var/lib/veriqta-security/expected-tcp-ports.txt"
LOG="/var/log/veriqta-listener-monitor.log"

tmp_expected="$(mktemp)"
tmp_current="$(mktemp)"

trap 'rm -f "$tmp_expected" "$tmp_current"' EXIT

grep -Ev '^[[:space:]]*(#|$)' "$EXPECTED" \
  | sort -n -u > "$tmp_expected"

ss -H -lnt \
  | awk '{print $4}' \
  | awk '
      {
          n=split($0,a,":")
          print a[n]
      }
    ' \
  | grep -E '^[0-9]+$' \
  | sort -n -u > "$tmp_current"

unexpected="$(
    comm -13 "$tmp_expected" "$tmp_current" || true
)"

{
    echo "=== $(date --iso-8601=seconds) ==="

    if [[ -n "$unexpected" ]]; then
        echo "ALERT: unexpected listening TCP ports"
        printf '%s\n' "$unexpected"
    else
        echo "OK: no unexpected TCP listeners"
    fi
} >> "$LOG"

if [[ -n "$unexpected" ]]; then
    exit 2
fi

exit 0
```

Make executable:

```bash
sudo chmod 0750 /usr/local/sbin/veriqta-listener-monitor
```

Run:

```bash
sudo /usr/local/sbin/veriqta-listener-monitor
```

Inspect:

```bash
sudo tail -n 50 /var/log/veriqta-listener-monitor.log
```

# Protect Baselines

On monitored servers:

```bash
sudo chown -R root:root /var/lib/veriqta-security
```

```bash
sudo chmod 0700 /var/lib/veriqta-security
```

Why?

Because if an ordinary user can modify both:

```text

```

and:

```text
the expected baseline
```

they can potentially make the comparison useless.

---

# Principle: Separate Observation from Modification

Where practical:

```text
monitored host
      |
      | generates evidence
      v
security01
      |
      | stores another copy
      v
investigator
```

Centralized logging improves evidence resilience because an attacker who compromises one monitored host may have a harder time altering copies already forwarded elsewhere.

It does **not** make logs tamper-proof by itself.

# 23. Interview Preparation

You should be able to explain the platform without opening the README.

### What is Linux security monitoring?

It is the continuous or periodic collection and analysis of Linux system evidence to identify activity that may require security investigation.

### What is the difference between prevention and detection?

Prevention attempts to stop unwanted activity.

Detection attempts to identify activity that occurred or is occurring.

You need both.

### What is the difference between an event and an alert?

An event is an observed occurrence.

An alert is a detection output indicating that an event or pattern deserves attention.

### Is an alert automatically an incident?

No.

It needs investigation and context.

### Why centralize logs?

Centralization improves cross-host visibility, investigation and evidence availability.

It can also make it harder for activity on one compromised server to erase every available copy of relevant logs.

### Does centralized logging make logs tamper-proof?

No.

Additional controls are required for stronger evidence integrity.

### Why use auditd?

Auditd provides kernel-level auditing capabilities that can record security-relevant system activity based on defined audit rules.

### Why monitor `/etc/passwd`?

Changes can indicate account creation, deletion or modification.

### Why monitor `/etc/group`?

Group changes can alter access and privilege relationships.

### Why monitor `/etc/sudoers`?

Changes can modify administrative authorization.

### Why monitor SSH configuration?

Changes can affect remote authentication and access controls.

### What is file integrity monitoring?

Comparing protected files against a trusted baseline to identify unexpected changes.

### What is the biggest weakness of an integrity baseline?

If the baseline itself is untrusted or compromised, later comparisons can give misleading confidence.

### Why monitor listening ports?

A new listener may indicate an intentionally deployed service, a configuration mistake, development tooling, or unwanted software.

The change deserves explanation.

### Why isn't an unknown process automatically malicious?

Linux systems run many legitimate processes. Classification requires evidence about ownership, executable path, parent, command line, service relationship and behavior.

### Why monitor successful authentication?

Because unauthorized access can produce successful authentication records.

### Why not alert on every sudo command?

Legitimate administrators routinely use sudo.

Context and expected behavior matter.

### What does `ausearch` do?

It searches Linux audit records.

### What does `aureport` do?

It produces summaries from audit data.

### What does `ss` help you investigate?

Sockets, listeners and network connections.

### What does `ps` tell you?

Process identity and runtime information.

### Why use `journalctl`?

It queries the systemd journal and can filter evidence by service, time and other fields.

### What is a false positive?

An alert that matches the detection logic but does not represent the unwanted security condition the detection is intended to identify.

### What is a false negative?

Relevant malicious or unwanted activity that the monitoring system fails to detect.

### Why are false negatives dangerous?

They create missing visibility.

### Why are excessive false positives dangerous?

They consume analyst attention and can cause important alerts to be ignored.

### What is detection engineering?

Designing, implementing, validating and improving logic that identifies meaningful patterns in security evidence.

### Why should detections have time windows?

Because frequency over a defined period often matters more than total historical count.

### Why should monitoring-service failure generate an alert?

If the system responsible for visibility fails, you may become blind to subsequent activity.

### Why is central log-server security important?

It contains potentially sensitive evidence and is part of the monitoring trust boundary.

### What is event correlation?

Combining related events from multiple sources or times to build a more useful understanding of activity.

### Give an example.

```text
Repeated SSH failures
        +
successful SSH login
        +
sudo activity
        +
identity file modification
```

is more informative than examining each event independently.

It still requires investigation before assigning cause.

# When You Can Call This Project Complete

Do not call this project complete because this works:

```bash
grep "Failed password" /var/log/auth.log
```

That is log searching.

You are building something larger.

You should understand the full monitoring path:

```text
ACTIVITY
   ↓
LINUX
   ↓
LOG / AUDIT / PROCESS / FILE / NETWORK EVIDENCE
   ↓
COLLECTION
   ↓
CENTRALIZATION
   ↓
BASELINE
   ↓
DETECTION
   ↓
ALERT
   ↓
TRIAGE
   ↓
CORRELATION
   ↓
INVESTIGATION
   ↓
CLASSIFICATION
   ↓
RESPONSE
   ↓
RECOVERY
   ↓
DOCUMENTATION
```

When somebody tells you:

> We received an alert for suspicious activity on `web01`.

you should no longer jump directly to:

> The server was hacked.

You should know how to ask:

```text
What exactly triggered the alert?

Which host generated the evidence?

When did it happen?

Which account was involved?

Where did the connection originate?

Were there failed authentications?

Was there a successful authentication?

Was sudo used afterward?

Were accounts or groups changed?

Were protected files modified?

Did an unexpected process appear?

Did a new network listener appear?

Did a service change?

Did the monitoring system itself remain healthy?

What other events occurred around the same time?

Does the activity match an approved administrative change?

What evidence supports the conclusion?
```

You should also understand that a security-monitoring platform has its own failure modes:

```text
auditd stopped
       ↓
audit visibility lost

rsyslog stopped
       ↓
forwarding interrupted

security01 unavailable
       ↓
central visibility degraded

disk full
       ↓
logging may fail

bad detection rule
       ↓
false positives / false negatives

bad baseline
       ↓
integrity results become misleading

monitoring scripts modified
       ↓
detection trust weakened
```

That is why the platform must monitor not only the servers, but also the health of the monitoring pipeline itself.

The Mid-Level engineering lesson behind this project is:

> **Security monitoring is not about collecting the most logs. It is about collecting the right evidence, detecting meaningful changes, correlating what happened, and giving an investigator enough trustworthy context to decide what it means.**

That is the difference between reading Linux logs and **operating a Linux security monitoring platform**.
