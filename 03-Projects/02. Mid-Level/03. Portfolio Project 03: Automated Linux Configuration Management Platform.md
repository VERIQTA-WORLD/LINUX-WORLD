# 01. Project Title

## Automated Linux Configuration Management Platform

Managing one Linux server manually is straightforward.

You SSH into the machine:

```bash
ssh admin@server01
```

Install a package:

```bash
sudo apt install nginx
```

Create a user:

```bash
sudo useradd alice
```

Edit a configuration file:

```bash
sudo nano /etc/nginx/nginx.conf
```

Restart a service:

```bash
sudo systemctl restart nginx
```

Then you repeat the same work on another server.

And another.

And another.

Eventually your environment looks like this:

```text
server01
├── nginx 1.x
├── user alice
├── UFW enabled
└── SSH configured

server02
├── nginx 1.x
├── user alice
├── UFW enabled
└── SSH configured

server03
├── nginx ???
├── alice missing
├── different firewall rules
└── SSH configuration changed manually
```

At that point, the problem is no longer:

> How do I configure Linux?

The problem becomes:

> How do I make sure every Linux server has the correct configuration, and how do I prove that configuration remains consistent?

That is configuration management.

In this project, you will stop administering servers as isolated machines and start managing them as a fleet.

You will build an Ansible control environment capable of managing multiple Ubuntu servers from one control node.

Your platform will automate:

```text
Package installation
Package updates
User creation
Group membership
SSH keys
Directory creation
File permissions
Configuration files
Nginx deployment
systemd services
Firewall rules
Security settings
Application deployment
Configuration validation
Service restarts
Health checks
Configuration drift correction
```

The finished architecture will look like this:

```text
                    ADMINISTRATOR
                         |
                         v
                 +----------------+
                 |    control01   |
                 |                |
                 |    Ansible     |
                 |    Git         |
                 |    YAML        |
                 |    Jinja2      |
                 +-------+--------+
                         |
                         | SSH
              +----------+----------+
              |          |          |
              v          v          v
        +----------+ +----------+ +----------+
        | server01 | | server02 | | server03 |
        |          | |          | |          |
        |  Web     | |  Web     | |  App     |
        +----------+ +----------+ +----------+
```

But this project is not going to be a collection of disconnected Ansible commands.

You will build a real configuration-management repository with:

```text

Playbooks

Templates
```

By the end, you should be able to deliberately break the configuration of a managed server, run Ansible, and watch the platform restore the declared state.

That is the core idea behind this project:

# 02. Project Scenario

You have joined the infrastructure team responsible for a growing Linux environment.

The team currently manages servers manually.

A typical deployment looks like this:

```text
Engineer logs into server01
Engineer installs packages
Engineer edits configuration
Engineer restarts services

Engineer logs into server02
Engineer tries to repeat the same steps

Engineer logs into server03
Engineer forgets one step
```

Several months later:

```text
server01 != server02 != server03
```

Nobody is completely sure which machine contains the correct configuration.

This is **configuration drift**.

Your assignment is to replace that workflow with a centralized configuration-management platform.

You will manage four machines:

| Host        | Role                       |      Example IP |
| ----------- | -------------------------- | --------------: |
| `control01` | Ansible control node       | `192.168.56.10` |
| `web01`     | Web server                 | `192.168.56.21` |
| `web02`     | Web server                 | `192.168.56.22` |
| `app01`     | Application/utility server | `192.168.56.23` |

Your control node will define what those servers should look like.

You will divide configuration into reusable roles:

```text
common
users
security
webserver
application
```

The desired relationship is:

```text
                         site.yml
                            |
            +---------------+---------------+
            |               |               |
            v               v               v
          common          security         users
            |
      +-----+-----+
      |           |
      v           v
  webservers   appservers
      |           |
      v           v
  webserver   application
```

Your automation must be repeatable.

Running it once should configure the environment.

Running it again should normally produce little or no change.

That property is called:

# Idempotency

It is one of the most important concepts in this project.

# Ansible Is Agentless

You are not going to install an Ansible agent on every managed machine.

The basic model is:

```text
control01
   |
   | SSH
   v
managed host
   |
   | Python/modules
   v
configuration change
```

The managed machines need the requirements necessary for Ansible's modules, but there is no permanently running Ansible agent.

---

# Desired State

Suppose your automation declares:

```text
Package nginx = installed
Service nginx = enabled
Service nginx = running
File /etc/nginx/sites-available/veriqta = specific content
Firewall HTTP rule = present
```

Ansible examines the machine.

If it already matches:

```text
ok
```

If it differs:

```text
changed
```

If something prevents the operation:

```text
failed
```

That distinction will become important throughout the project.

Edit:

```bash

```

Add:

```yaml
---
- name: Refresh APT package cache
  ansible.builtin.apt:
    update_cache: true
    cache_valid_time: 3600

- name: Install common administration packages
  ansible.builtin.apt:
    name: "{{ common_packages }}"
    state: present

- name: Create VERIQTA operations directory
  ansible.builtin.file:
    path: /opt/veriqta
    state: directory
    owner: root
    group: root
    mode: "0755"

- name: Create VERIQTA configuration directory
  ansible.builtin.file:
    path: /etc/veriqta
    state: directory
    owner: root
    group: root
    mode: "0755"
```

Notice what you are **not** doing:

```yaml

```

when a dedicated package module already exists.

Prefer purpose-built modules because they understand state.

# Check Mode

Run:

```bash
ansible-playbook \
    playbooks/common.yml \
    --check \
    --diff
```

This asks Ansible to predict changes where supported.

Important:

**Check mode is useful, but it is not a perfect simulation.**

Some modules cannot completely predict future state.

A later task may also depend on something an earlier task would have created.

Use check mode as a safety tool, not as proof that deployment will succeed.

# Phase 21: Manage SSH Configuration Safely

Do not start by replacing the entire `/etc/ssh/sshd_config`.

Use a managed drop-in.

Create:

```bash
mkdir -p roles/security/templates
```

Create:

```bash
nano roles/security/templates/99-veriqta-hardening.conf.j2
```

Add:

```text
# Managed by Ansible.
# Manual changes may be overwritten.

PermitRootLogin no
MaxAuthTries 4
X11Forwarding no
```

We are deliberately **not** disabling password authentication yet.

Why?

Because you should first prove that key-based access works for every required administrative account before removing fallback access.

Security automation should not turn into self-inflicted lockout automation.

---

# Add SSH Tasks

Append to `roles/security/tasks/main.yml`:

```yaml
- name: Install managed SSH hardening drop-in
  ansible.builtin.template:
    src: 99-veriqta-hardening.conf.j2
    dest: /etc/ssh/sshd_config.d/99-veriqta-hardening.conf
    owner: root
    group: root
    mode: "0644"
    validate: "/usr/sbin/sshd -t -f %s"
  notify: Restart SSH
```

---

# Why `validate` Matters

The template is written to a temporary location first.

Ansible runs:

```text
sshd -t -f TEMPORARY_FILE
```

before accepting it.

The exact behavior of configuration validation deserves testing because SSH configurations can include other files and depend on surrounding configuration.

For critical services, do not assume template syntax alone proves the complete live configuration is valid.

Your post-deployment validation will still run:

```bash
sudo sshd -t
```

on the actual host.

# Create the Handler

Edit:

```bash
nano roles/security/handlers/main.yml
```

Add:

```yaml
---
- name: Restart SSH
  ansible.builtin.service:
    name: ssh
    state: restarted
```

A handler runs only when notified by a changed task.

So:

```text
template unchanged
        |
        v
no restart


template changed
        |
        v
handler notified
        |
        v
SSH restarted
```

This is much better than restarting SSH every time the playbook runs.

# Phase 23: Understand Secret Management

Sooner or later configuration management encounters secrets:

```text
database passwords
API tokens
TLS private keys
service credentials
application secrets
```

Do not place them directly in plaintext Git-tracked YAML files.

Bad:

```yaml
database_password: SuperSecretPassword123
```

Instead, Ansible provides Vault.

Create a lab vault file:

```bash
ansible-vault create \
    inventories/production/group_vars/vault.yml
```

Enter a lab-only secret such as:

```yaml
vault_demo_secret: "replace-with-lab-secret"
```

Inspect the file:

```bash
cat \
    inventories/production/group_vars/vault.yml
```

You should see encrypted vault content rather than plaintext.


# Edit It

```bash

    inventories/production/group_vars/vault.yml
```

---

# Important Vault Limitation

Ansible Vault protects encrypted content at rest.

It does not solve every secrets-management problem.

Once a secret is decrypted for use:

```text
processes
temporary files
application configuration
logs
permissions
backup systems
```

can still become part of your threat model.

Production environments may use dedicated secret-management systems.

For this project, you need to understand the principle:

```text
Secret
   |
   X
plaintext Git


Secret
   |
   v
encrypted storage
   |
   v
controlled runtime use
```

# Nginx Handler

Create:

```bash
nano roles/webserver/handlers/main.yml
```

Add:

```yaml
---
- name: Validate Nginx configuration
  ansible.builtin.command:
    cmd: nginx -t
  changed_when: false
  listen: Validate and reload Nginx

- name: Reload Nginx
  ansible.builtin.service:
    name: nginx
    state: reloaded
  listen: Validate and reload Nginx
```

Now a changed configuration triggers:

```text
Template changed
      |
      v
handler notification
      |
      v
nginx -t
      |
      +------ failure ------> stop
      |
    success
      |
      v
reload nginx
```

That is much safer than blindly restarting Nginx after every file change.

# Create the Application Script

Create:

```bash
nano roles/application/templates/veriqta-status-server.py.j2
```

Add:

```python
#!/usr/bin/env python3

from http.server import BaseHTTPRequestHandler, HTTPServer
import json
import socket
from datetime import datetime, timezone

HOST = "127.0.0.1"
PORT = {{ application_port }}

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/health":
            payload = {
                "status": "ok",
                "host": socket.gethostname(),
                "service": "veriqta-status",
                "time": datetime.now(timezone.utc).isoformat()
            }

            body = json.dumps(payload).encode()

            self.send_response(200)
            self.send_header("Content-Type", "application/json")
            self.send_header("Content-Length", str(len(body)))
            self.end_headers()
            self.wfile.write(body)
            return

        self.send_response(404)
        self.end_headers()

    def log_message(self, format, *args):
        print(
            "%s - %s" %
            (
                self.address_string(),
                format % args
            ),
            flush=True
        )

HTTPServer((HOST, PORT), Handler).serve_forever()
```

The service listens only on:

```text
127.0.0.1
```

It is not intended to be exposed externally.

# 23. Interview Preparation

### What is configuration management?

Configuration management is the systematic definition, application, and maintenance of desired system state across infrastructure.

### What is configuration drift?

Drift occurs when the actual configuration of a system diverges from the intended configuration.

### Why is manual configuration dangerous at scale?

Because repeated human changes become inconsistent, difficult to audit, difficult to reproduce, and prone to omission.

### What is Ansible?

Ansible is an automation and configuration-management platform that can manage remote systems, commonly through SSH.

### Does Ansible require an agent?

Its common Linux management model is agentless. The control node connects to managed hosts, typically through SSH.

### What is an inventory?

An inventory defines the hosts and groups Ansible manages.

### Why use groups?

Groups let you apply shared configuration to machines with common responsibilities.

For example:

```text
webservers
appservers
database_servers
```

### What is a playbook?

A playbook is YAML describing plays and tasks that Ansible should execute against selected hosts.

### What is a role?

A role packages related:

```text
tasks
handlers
templates
files
variables
defaults
```

into a reusable structure.

### What is idempotency?

An idempotent operation can be repeated without unnecessarily changing a system that already matches the desired state.

### Why is idempotency important?

Because automation should converge systems toward a desired state rather than repeatedly disrupting already-correct resources.

### What is a handler?

A handler is a task normally triggered by a change notification.

A common example is reloading Nginx only when its configuration changes.

### What is Jinja2?

Jinja2 is a templating engine Ansible uses to generate configuration from variables and templates.

### What is `become`?

`become` allows Ansible to perform tasks using privilege escalation, commonly through sudo.

### What is check mode?

Check mode attempts to predict changes without applying them.

It is useful but not guaranteed to perfectly simulate every module or dependency.

### What is diff mode?

Diff mode shows differences for supported resources, especially managed text files and templates.

### Why use `serial`?

`serial` limits how many hosts are processed at once.

It reduces deployment blast radius.

### Why validate Nginx before reloading it?

A malformed configuration can cause a reload or restart to fail. Validation catches the problem before disrupting the live service.

### Why should Ansible not use `shell` for everything?

Dedicated modules understand resource state and are usually more idempotent, structured, and predictable.

### What is Ansible Vault?

Vault encrypts sensitive Ansible data at rest.

### Does Vault solve all secrets-management problems?

No. Secrets still need protection when decrypted and used by applications or automation.

### What is the difference between `failed` and `unreachable`?

`unreachable` generally indicates Ansible could not establish the management connection.

`failed` indicates a task reached execution but did not complete successfully.

### How would you troubleshoot one unreachable host?

Start with inventory, name/IP resolution, routing, TCP 22, SSH authentication, host keys, and then Ansible-specific configuration.

### Why should automation be stored in Git?

It provides version history, reviewability, collaboration, rollback context, and an auditable record of intended infrastructure configuration.

### Why is manual modification of Ansible-managed files dangerous?

Because Ansible may overwrite those changes the next time the declared state is applied.

### What is infrastructure as code?

It is the practice of representing infrastructure configuration and desired state in version-controlled machine-readable definitions.

This project is primarily configuration management, but it applies many infrastructure-as-code principles.

# Build a Cleanup Playbook

Create:

```bash

```

```yaml

  hosts: webservers

  tasks:

    - name: Remove VERIQTA Nginx site symlink
      ansible.builtin.file:
        path: /etc/nginx/sites-enabled/veriqta
        state: absent

    - name: Remove VERIQTA Nginx configuration
      ansible.builtin.file:
        path: /etc/nginx/sites-available/veriqta
        state: absent

    - name: Remove VERIQTA website
      ansible.builtin.file:
        path: /var/www/veriqta
        state: absent

- name: Remove project application
  hosts: appservers
  become: true

  tasks:

    - name: Stop and disable project application
      ansible.builtin.systemd_service:
        name: veriqta-status
        state: stopped
        enabled: false
      failed_when: false

    - name: Remove project systemd unit
      ansible.builtin.file:
        path: /etc/systemd/system/veriqta-status.service
        state: absent

    - name: Reload systemd
      ansible.builtin.systemd_service:
        daemon_reload: true

    - name: Remove project application directory
      ansible.builtin.file:
        path: /opt/veriqta/status-service
        state: absent
```

Do not immediately automate removal of users unless you are certain their accounts were created only for the disposable lab.

The same applies to packages and firewall rules.

Cleanup automation must be just as deliberate as deployment automation.

# When You Can Call This Project Complete

Do not call this project complete because this works:

```bash
ansible all -m ping
```

That proves connectivity and basic module execution.

It does not prove configuration management.

You should be able to explain and operate this complete lifecycle:

```text
                DESIRED STATE
                     |
                     v
                  Git
                     |
                     v
                 Ansible
                     |
          +----------+----------+
          |          |          |
          v          v          v
        web01      web02      app01
          |          |          |
          v          v          v
      packages     users     services
      configs      groups    application
      firewall     keys      permissions
          |          |          |
          +----------+----------+
                     |
                     v
                 VALIDATION
                     |
          +----------+----------+
          |                     |
          v                     v
       CORRECT                 DRIFT
          |                     |
          v                     v
       NO CHANGE             CORRECT
          |                     |
          +----------+----------+
                     |
                     v
                 TEST AGAIN
```

And when automation fails, you should be able to reason through the management path:

```text
Is the inventory correct?

Is the host address correct?

Can the control node reach the host?

Is TCP 22 reachable?

Does SSH authentication work?

Is the expected SSH host key present?

Can Ansible execute Python modules?

Can the automation user escalate privileges?

Did YAML parse correctly?

Were all variables defined?

Did the template render correctly?

Did the module perform the intended operation?

Did the generated configuration validate?

Did the service accept the configuration?

Did the service start?

Is the firewall allowing the required traffic?

Does the application actually work?

Does a second automation run remain idempotent?

Can Ansible detect and correct deliberate drift?
```

That is what makes this a **Mid-Level configuration-management project**.

You are no longer proving that you know how to install Ansible or write a YAML file.

You are proving that you can take a collection of Linux machines and turn them into a **controlled, repeatable, versioned, testable, security-aware infrastructure platform where desired state is defined centrally, configuration drift is detectable and correctable, deployments have a controlled blast radius, service changes are validated before activation, and the environment can be rebuilt consistently without manually configuring every server.**
