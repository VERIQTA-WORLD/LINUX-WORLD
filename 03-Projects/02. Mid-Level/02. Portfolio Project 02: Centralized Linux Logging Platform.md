# 01. Project Title

## Centralized Linux Logging Platform

A single Linux server is easy to investigate.

You SSH into it, run:

```bash
journalctl
```

or:

```bash
tail -f /var/log/syslog
```

and start looking for the problem.

That approach begins to break down when you have several servers.

Imagine receiving this alert:

> Users cannot access the application.

Your environment looks like this:

```text
                  USERS
                    |
                    v
              +-----------+
              |   WEB01   |
              |   Nginx   |
              +-----+-----+
                    |
                    v
              +-----------+
              |   APP01   |
              |   App     |
              +-----+-----+
                    |
                    v
              +-----------+
              |    DB01   |
              | Database  |
              +-----------+
```

The failure could be anywhere.

You could SSH into `web01`, inspect logs, SSH into `app01`, inspect more logs, SSH into `db01`, inspect those logs, copy timestamps into a text file, and manually reconstruct what happened.

That might work with three machines.

It does not scale well.

In this project, you are going to build a centralized Linux logging platform.

Your final environment will look more like this:

```text
                         CENTRALIZED LOGGING

 +----------------+                               +----------------------+
 |     web01      |                               |                      |
 |                |                               |                      |
 | journald       |                               |                      |
 | rsyslog        |------ TCP/514 -------------->|                      |
 | Nginx logs     |                               |                      |
 +----------------+                               |                      |
                                                  |                      |
 +----------------+                               |       log01          |
 |     app01      |                               |                      |
 |                |                               |   rsyslog server     |
 | journald       |------ TCP/514 -------------->|                      |
 | rsyslog        |                               |   filtering          |
 | app logs       |                               |   organization       |
 +----------------+                               |   retention          |
                                                  |   investigation      |
 +----------------+                               |                      |
 |      db01      |                               |                      |
 |                |                               |                      |
 | journald       |------ TCP/514 -------------->|                      |
 | rsyslog        |                               |                      |
 | DB logs        |                               |                      |
 +----------------+                               +----------+-----------+
                                                             |
                                                             v
                                                  /var/log/remote/
                                                  ├── web01/
                                                  ├── app01/
                                                  └── db01/
```

But you are not going to stop at forwarding logs.

You will build the platform so you can answer questions such as:

```text
Which server generated this event?

Which service generated it?

When did it happen?

Was the message informational, warning, error, or critical?

Did several machines experience the same problem?

Did authentication failures increase?

Did a service restart before the incident?

Did logs stop arriving from one server?

Can I trace an event from source to collector?

How long are centralized logs retained?

What happens if the collector becomes unavailable?

What happens when it returns?

Can an ordinary user alter centralized logs?
```

By the end of the project, your centralized log server will become part of your troubleshooting workflow rather than simply another machine storing text files.

# 02. Project Scenario

You are responsible for a small Linux environment supporting an internal service.

There are four servers:

| Server  | Role                  |  Example Lab IP |
| ------- | --------------------- | --------------: |
| `log01` | Central log collector | `192.168.56.10` |
| `web01` | Web server            | `192.168.56.21` |
| `app01` | Application server    | `192.168.56.22` |
| `db01`  | Database server       | `192.168.56.23` |

These addresses are examples.

**Use the addresses actually assigned to your VMs.**

The team currently investigates incidents by logging into each machine separately.

That creates several problems.

Logs are fragmented.

Engineers lose time switching between servers.

Events are harder to correlate.

A compromised or failed machine may become unavailable along with its local logs.

Retention is inconsistent.

There is no simple way to determine whether every server is still sending logs.

Your assignment is to build a central logging platform on `log01`.

The platform must:

* receive logs from multiple Linux servers;
* use reliable TCP transport for the core lab;
* restrict collector access with firewall rules;
* preserve the original source hostname;
* separate remote logs by source host;
* support facility and severity filtering;
* collect selected application logs;
* protect centralized logs with sensible ownership and permissions;
* rotate and retain collected logs;
* detect stale or missing log sources;
* provide Bash-based investigation tools;
* survive server reboots;
* tolerate temporary collector outages using rsyslog queues;
* support controlled failure simulations;
* provide documented troubleshooting runbooks.

You will also deliberately create events on different servers and reconstruct an incident from the centralized evidence.

That last part is important.

A logging platform is useful only if it helps you investigate something.

# 08. Architecture

## 8.1 Logging Data Flow

A simplified event path might look like this:

```text
EVENT OCCURS
    |
    v
SERVICE / APPLICATION
    |
    v
LOCAL LOGGING SYSTEM
    |
    v
RSYSLOG CLIENT
    |
    | TCP 514
    v
NETWORK
    |
    v
UFW ON LOG01
    |
    v
RSYSLOG LISTENER
    |
    v
FILTERING / TEMPLATES
    |
    +-----------------------+
    |                       |
    v                       v
HOST LOGS              SPECIAL LOGS
    |                       |
    v                       v
/var/log/remote/      /var/log/central/
```

---

## 8.2 Why TCP?

Traditional syslog commonly uses UDP 514.

UDP is simple and low-overhead, but it does not provide connection-oriented delivery.

For this project, you will use TCP.

Conceptually:

```text
UDP

Sender ---- message ----> Collector

No session
No delivery acknowledgement at transport layer
Datagrams may be lost
```

Compared with:

```text
TCP

Sender <==== connection ====> Collector
              |
              +-- ordered byte stream
              +-- retransmission
              +-- connection state
```

TCP still does **not** magically guarantee that every message has been safely persisted forever.

The collector can run out of disk.

Configuration can be wrong.

Queues can fill.

Applications can fail before logging.

But TCP gives you a stronger transport foundation for this lab.

---

## 8.3 Reliability Design

Later, you will add a disk-assisted rsyslog action queue.

The intended behavior becomes:

```text
                  COLLECTOR AVAILABLE

Source
  |
  v
rsyslog
  |
  v
TCP
  |
  v
log01


                  COLLECTOR UNAVAILABLE

Source
  |
  v
rsyslog
  |
  v
Memory / Disk Queue
  |
  | waits
  |
  +-------------------+
                      |
              collector returns
                      |
                      v
                  TCP/514
                      |
                      v
                    log01
```

That gives you a much more realistic reliability exercise than simply forwarding messages and hoping the collector never fails.

# Understanding journald and rsyslog

Do not think of them as two commands doing exactly the same job.

A simplified view is:

```text
             SYSTEMD SERVICES
                    |
                    v
                JOURNALD
                    |
                    +--------> journalctl
                    |
                    |
             syslog integration
                    |
                    v
                 RSYSLOG
                    |
          +---------+----------+
          |                    |
          v                    v
    Local text logs      Remote forwarding
```

Real Linux logging paths can be more nuanced than this diagram. Applications may write directly to files, send to syslog, write to stdout/stderr captured by journald, or use other mechanisms.

Your job is to know which path the service you are investigating actually uses.

# Phase 5: Learn Syslog Facility and Severity

A syslog message has metadata that can be used for routing.

## Facilities

Common facilities include:

```text
auth
authpriv
cron
daemon
kern
mail
syslog
user
local0
local1
local2
local3
local4
local5
local6
local7
```

The `local0`–`local7` facilities are especially useful when you want applications or lab services to have dedicated routing rules.

---

## Severities

From most severe to least severe:

| Numeric | Severity |
| ------: | -------- |
|       0 | emerg    |
|       1 | alert    |
|       2 | crit     |
|       3 | err      |
|       4 | warning  |
|       5 | notice   |
|       6 | info     |
|       7 | debug    |

Do not make the common mistake of assuming a larger number means a more serious event.

It is the opposite.

# Phase 8: Configure the Collector Firewall

Before enabling UFW remotely, protect your SSH access.

Run:

```bash
sudo ufw allow OpenSSH
```

Now allow logging traffic from your lab network.

For example:

```bash
sudo ufw allow \
    from 192.168.56.0/24 \
    to any port 514 \
    proto tcp
```

Replace the subnet with your actual lab subnet.

Do not simply write:

```bash
sudo ufw allow 514/tcp
```

unless you intentionally want every reachable host to be able to send logs.

Enable UFW if it is not already enabled:

```bash
sudo ufw enable
```

Inspect:

```bash
sudo ufw status numbered
```

Now compare:

```bash
sudo ss -lntp | grep ':514'
```

with:

```bash
sudo ufw status verbose
```

Again:

```text
ss
→ Is a process listening?

UFW
→ Is traffic permitted?
```

Those are separate questions.

# Phase 9: Organize Remote Logs by Host

We do not want every incoming event dumped into one enormous file.

Create:

```bash
sudo nano /etc/rsyslog.d/20-remote-storage.conf
```

Add:

```text
template(
    name="RemoteHostFile"
    type="string"
    string="/var/log/remote/%HOSTNAME%/syslog.log"
)

if ($fromhost-ip != "127.0.0.1") then {
    action(
        type="omfile"
        dynaFile="RemoteHostFile"
        dirCreateMode="0750"
        fileCreateMode="0640"
    )

    stop
}
```

---

## What This Does

The template dynamically creates paths based on the hostname contained in the message.

For example:

```text
web01
→ /var/log/remote/web01/syslog.log

app01
→ /var/log/remote/app01/syslog.log

db01
→ /var/log/remote/db01/syslog.log
```

The `stop` instruction prevents those matched remote messages from continuing through later local rules in the collector's rsyslog processing chain.

That helps avoid unintentionally mixing remote events into unrelated collector outputs.

---

## Important Trust Boundary

`%HOSTNAME%` is message metadata.

Do not treat it as cryptographically verified machine identity.

In this lab, the environment is controlled and the sender list is restricted by network policy.

In a stronger production design you would consider authenticated and encrypted transport, such as TLS, and a more deliberate identity model.

That is an important limitation to document.

```bash
LOG_ROOT="/var/log/remote"

usage() {
    cat <<'EOF'
Usage:
  search-logs.sh --all PATTERN
  search-logs.sh --host HOST PATTERN

Examples:
  search-logs.sh --all "authentication failure"
  search-logs.sh --host web01 "nginx"
  search-logs.sh --host app01 "req-2001"

}

    usage
    exit 1
fi

MODE="$1"

case "$MODE" in

    --all)

        PATTERN="$2"

        grep \
            -RniF \
            -- \
            "$PATTERN" \
            "$LOG_ROOT"

        ;;

    --host)

        if (( $# < 3 )); then
            usage
            exit 1
        fi

        HOST="$2"
        PATTERN="$3"

        if [[ ! "$HOST" =~ ^[A-Za-z0-9._-]+$ ]]; then
            echo "Invalid host name." >&2
            exit 1
        fi

        HOST_DIR="$LOG_ROOT/$HOST"

        if [[ ! -d "$HOST_DIR" ]]; then
            echo "Unknown host directory: $HOST_DIR" >&2
            exit 1
        fi

        grep \
            -RniF \
            -- \
            "$PATTERN" \
            "$HOST_DIR"

        ;;

    *)

        usage
        exit 1

        ;;

esac
```

# Phase 20: Build a Source Freshness Checker

A logging platform can appear healthy while one client silently stops sending events.

You need to detect that.

Create:

```bash
nano \
    ~/centralized-linux-logging-platform/scripts/source-freshness.sh
```

Add:

```bash
#!/usr/bin/env bash

set -u
set -o pipefail

LOG_ROOT="/var/log/remote"
MAX_AGE_MINUTES="${MAX_AGE_MINUTES:-15}"

HOSTS=(
    "web01"
    "app01"
    "db01"
)

PASS=0
FAIL=0

now_epoch="$(date +%s)"

pass() {
    printf '[PASS] %s\n' "$1"
    PASS=$((PASS + 1))
}

fail() {
    printf '[FAIL] %s\n' "$1"
    FAIL=$((FAIL + 1))
}

for host in "${HOSTS[@]}"; do

    log_file="$LOG_ROOT/$host/syslog.log"

    if [[ ! -f "$log_file" ]]; then
        fail "$host has no centralized syslog file"
        continue
    fi

    modified_epoch="$(
        stat -c '%Y' "$log_file"
    )"

    age_seconds=$((now_epoch - modified_epoch))
    age_minutes=$((age_seconds / 60))

    if (( age_minutes <= MAX_AGE_MINUTES )); then

        pass \
            "$host log age is ${age_minutes} minute(s)"

    else

        fail \
            "$host log is stale: ${age_minutes} minute(s)"

    fi

done

echo
printf 'Passed: %d\n' "$PASS"
printf 'Failed: %d\n' "$FAIL"

if (( FAIL > 0 )); then
    exit 1
fi

exit 0
```

Make executable:

```bash
chmod +x \
    ~/centralized-linux-logging-platform/scripts/source-freshness.sh
```

---

## Important Limitation

File modification time only changes when an event arrives.

A quiet server may be healthy but produce no logs for a while.

So a stale file is not absolute proof of failure.

To make freshness checks meaningful, you will later generate periodic heartbeat events.

## Principle 4: Understand Transport Security

Your core lab currently uses:

```text

```

That gives you reliable connection-oriented transport.

It does **not** give you encryption.

It also does not provide strong sender authentication.

That means the lab design is appropriate for an isolated trusted network, but it is not the final design you would blindly expose across an untrusted network.

A production improvement would be:

```text
rsyslog client

      | TLS

rsyslog collector
```

commonly using a TLS-enabled syslog design such as TCP 6514.

Do not confuse:

```text

```

with:

```text
encrypted TCP
```

They are not the same thing.

# Phase 24: Configure logrotate

Create:

```bash
sudo nano \
    /etc/logrotate.d/veriqta-central-logs
```

Add:

```text
/var/log/remote/*/*.log
/var/log/central/*/*.log
{
    daily
    rotate 14
    compress
    delaycompress
    missingok
    notifempty
    dateext
    create 0640 syslog adm
    sharedscripts

    postrotate
        /usr/bin/systemctl kill -s HUP rsyslog.service >/dev/null 2>&1 || true
    endscript
}
```

---

## What This Policy Means

### `daily`

Evaluate rotation daily.

### `rotate 14`

Retain 14 rotated generations.

This is approximately two weeks under normal daily rotation, but think in terms of retained rotations rather than assuming exact wall-clock retention under every circumstance.

### `compress`

Compress older logs.

### `delaycompress`

Delay compression of the newest rotated file by one cycle.

### `missingok`

Do not fail because one expected file does not exist.

### `notifempty`

Do not rotate empty files.

### `dateext`

Use date-based suffixes.

### `create`

Create a replacement active log with controlled ownership and permissions.

### `postrotate`

Signal rsyslog after rotation so file handling is refreshed appropriately.

# 23. Interview Preparation

## What problem does centralized logging solve?

It gives operators a common place to investigate events from multiple machines, making cross-host correlation and historical analysis easier and preserving remote copies of logs when a source becomes unavailable.

---

## What is journald?

`systemd-journald` collects and stores journal events from the kernel, systemd services, and other supported logging paths.

---

## What is rsyslog?

rsyslog is a logging system capable of receiving, processing, filtering, writing, and forwarding log messages.

---

## Why use both?

They solve overlapping but not identical problems. journald integrates closely with systemd and provides structured journal querying. rsyslog provides flexible text-file routing and network forwarding/collection capabilities.

---

## Why TCP rather than UDP?

TCP provides connection-oriented, ordered transport with retransmission. UDP has lower overhead but does not provide the same transport reliability.

TCP alone still does not guarantee durable storage.

---

## Does TCP 514 encrypt the logs?

No.

TCP and encryption are different concerns.

For untrusted networks, authenticated TLS transport should be considered.

---

## Why separate logs by hostname?

It makes source-specific investigation easier and prevents all remote events from becoming one unmanageable file.

---

## Can you completely trust the hostname inside a syslog message?

Not necessarily.

In the basic lab, network controls and a trusted environment provide the practical boundary. A production system should use stronger sender authentication and transport security where required.

---

## What is a syslog facility?

A facility categorizes the source or type of a message and can be used for routing.

---

## What is severity?

Severity represents the importance or urgency of the event, from emergency through debug.

---

## Why is `severity <= 3` error-and-higher?

Syslog uses lower numeric values for more severe messages:

```text
0 emergency
1 alert
2 critical
3 error
```

---

## Why does configuration order matter?

rsyslog evaluates rules in order. If a rule processes a message and calls `stop`, later filters will never see that message.

---

## Why use a queue on the forwarding action?

It allows rsyslog to buffer forwarding work when the destination is temporarily unavailable, improving resilience.

---

## What happens if the queue fills?

The exact behavior depends on the queue configuration and resource limits. That is why queue capacity, disk availability, retry behavior, and failure monitoring all matter.

---

## How do you know a client stopped forwarding?

One signal is the absence of expected heartbeat events. A freshness checker can identify sources whose last centralized event is older than the expected interval.

---

## Why isn't file modification time alone enough?

A healthy but quiet system might simply have no new events. Periodic heartbeat messages make freshness expectations explicit.

---

## Why does time synchronization matter?

Without synchronized clocks, cross-host event ordering can become misleading, making incident reconstruction much harder.

---

## Why rotate centralized logs?

Central collectors can accumulate data rapidly. Rotation, compression, retention, and capacity monitoring prevent unbounded disk consumption.

---

## What is the difference between rotation and retention?

Rotation creates new active files and archives older ones. Retention determines how much historical data is kept before old generations are removed.

---

## What would you investigate if every client stopped logging?

Start with shared dependencies:

```text
collector rsyslog
collector listener
collector firewall
collector storage
shared network path
```

---

## What if only one server stopped logging?

Investigate that server's path first:

```text
local event generation
client rsyslog
client configuration
name resolution
routing
TCP reachability
queue state
```

The fact that other clients work is evidence that the collector is probably not experiencing a complete outage.

# When You Can Call This Project Complete

Do not call the project complete because this works:

```bash
logger "hello"
```

and the message appears on `log01`.

You should understand the complete pipeline:

```text
EVENT
  |
  v
SOURCE SERVICE
  |
  v
LOCAL LOGGING
  |
  v
RSYSLOG CLIENT
  |
  v
ACTION QUEUE
  |
  v
NAME RESOLUTION
  |
  v
ROUTING
  |
  v
TCP CONNECTION
  |
  v
FIREWALL
  |
  v
RSYSLOG COLLECTOR
  |
  v
FILTERS
  |
  v
TEMPLATES
  |
  +---------------------+
  |                     |
  v                     v
HOST HISTORY        OPERATIONAL VIEWS
  |                     |
  +----------+----------+
             |
             v
        LOG ROTATION
             |
             v
          RETENTION
             |
             v
       INVESTIGATION
```

And when a log disappears, you should be able to work in the opposite direction:

```text
Is the event actually being generated?

Does it exist locally?

Is the client logging service healthy?

Is the forwarding configuration valid?

Can the client resolve the collector?

Is there a route?

Can it establish TCP/514?

Does the firewall permit it?

Is the collector listening?

Is the collector configuration valid?

Did the event match the expected rule?

Did a previous rule stop processing?

Can rsyslog write the destination?

Is the collector out of disk or inodes?

Did rotation affect the file?

Is the event simply stored somewhere other than where I expected?
```

That is the real project.

You are not learning how to copy `/var/log/syslog` from one Linux machine to another.

You are learning how to build a **multi-server logging pipeline, reason about its reliability and trust boundaries, operate its storage lifecycle, detect missing telemetry, and use centralized evidence to troubleshoot Linux systems across an environment.**
