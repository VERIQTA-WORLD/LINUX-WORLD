# 12. Step-by-Step Implementation

# Phase 1: Understand Linux Identity

Before creating users, inspect how Linux represents them.

## Step 1: Inspect `/etc/passwd`

Run:

```bash
head /etc/passwd
```

A line generally follows this structure:

```text
username:x:UID:GID:comment:home:shell
```

For example:

```text
student:x:1000:1000:Student:/home/student:/bin/bash
```

Fields are separated by colons.

They represent:

```text
student       username
x             password information stored elsewhere
1000          UID
1000          primary GID
Student       descriptive field
/home/student home directory
/bin/bash     login shell
```

The actual password hash is not stored directly in `/etc/passwd`.

---

## Step 2: Understand `/etc/shadow`

Do not print password hashes unnecessarily.

Instead, inspect metadata for your own account through supported tools:

```bash
sudo chage -l "$USER"
```

This displays password-aging information.

The protected `/etc/shadow` database contains authentication-related information and is normally readable only by privileged processes/users.

Verify its permissions:

```bash
ls -l /etc/shadow
```

The exact group and mode can vary, but ordinary users should not have unrestricted read access.

---

## Step 3: Inspect groups

Run:

```bash
head /etc/group
```

A group entry resembles:

```text
group-name:x:GID:members
```

Check your groups:

```bash

```

Then:

```bash

```

# Phase 2: Design the Access Model

Do not create accounts until you know what access they require.

Our design is:

| User  | Team        | Primary role | Admin privilege |
| ----- | ----------- | ------------ | --------------- |
| Alice | Development | Developer    | No              |
| Bob   | Development | Developer    | No              |
| Carol | Operations  | Operator     | Limited         |
| David | Operations  | Operator     | Limited         |
| Erin  | Audit       | Auditor      | No              |

The group model will be:

```text
developers
operations
auditors
```

Why groups?

Imagine 50 developers.

Managing permissions separately for every employee becomes difficult.

Instead:

```text
resource
   |
developers group
   |
all authorized developers
```

When someone joins:

```text
add user -> developers
```

When someone leaves:

```text
remove user -> developers
```

This is easier to audit.

# Phase 8: Understand Permissions Before Changing Them

Run:

```bash
ls -ld /srv/veriqta/development
```

Permissions may look similar to:

```text
drwxr-xr-x
```

Break it apart:

```text
d | rwx | r-x | r-x
    user  group other
```

For a directory:

```text
r = list directory names
w = create/delete directory entries, subject to directory semantics
x = traverse/access entries through the directory
```

Numeric permissions use:

```text
r = 4
w = 2
x = 1
```

Therefore:

```text
7 = rwx
6 = rw-
5 = r-x
4 = r--
0 = ---
```

---

# Phase 9: Secure Team Directories

We want the owning group to collaborate.

We do not want unrelated users casually entering team directories.

Run:

```bash
sudo chmod 2770 /srv/veriqta/development
sudo chmod 2770 /srv/veriqta/operations
sudo chmod 2750 /srv/veriqta/audit
```

Why four digits?

Consider:

```text
2770
```

The leading `2` enables the setgid bit on the directory.

The remaining:

```text
770
```

means:

```text
owner = rwx
group = rwx
other = ---
```

For audit:

```text
2750
```

means:

```text
setgid
owner = rwx
group = r-x
other = ---
```

This gives auditors read/traverse access without ordinary group write permission.

---

# Why Setgid Matters

Without careful shared-directory design, files created by different users can receive ownership or permissions that make collaboration awkward.

A setgid directory causes newly created files and subdirectories to inherit the directory's group ownership.

Let's prove it.

Run a command as Alice:

```bash
sudo -u alice touch /srv/veriqta/development/alice-test.txt
```

Inspect it:

```bash
ls -l /srv/veriqta/development/alice-test.txt
```

The group should be:

```text
developers
```

rather than simply Alice's primary group.

That is the important behavior.

---

# Phase 10: Understand `umask`

Group ownership alone does not guarantee group write access.

Check Alice's effective `umask`:

```bash
sudo -iu alice bash -c 'umask'
```

A common value is:

```text
0022
```

If a regular file starts from a base mode such as `666`, a `0022` umask normally removes group and other write bits, producing:

```text
644
```

That means a new shared file may become:

```text
rw-r--r--
```

The group can read it but cannot modify it.

This is an important difference between:

```text
group ownership
```

and:

```text
group permissions
```

For this lab, set the existing shared file to group writable:

```bash

```

Verify:

```bash

```

```bash

```

```bash

```

### What did we learn?

The setgid bit solved group inheritance.

It did not automatically make every file group writable.

Shared environments require both ownership and permission design.

For a larger environment, you might use a carefully managed collaborative `umask`, default ACLs, application-specific access controls, or another policy appropriate to the workload.

# 14. Automation

Manual account inspection becomes tedious as environments grow.

We will build a simple audit tool.

# Phase 14: Create the Access Audit Script

Return to your project:

```bash
cd ~/linux-user-access-management
```

Create:

```bash
nano scripts/access-audit.sh
```

Add:

```bash
#!/usr/bin/env bash

set -u

USERS=("alice" "bob" "carol" "david" "erin")
GROUPS=("developers" "operations" "auditors")
DIRECTORIES=(
    "/srv/veriqta/development"
    "/srv/veriqta/operations"
    "/srv/veriqta/audit"
)

echo "=========================================="
echo " Linux User & Access Management Audit"
echo "=========================================="
echo
echo "Date: $(date)"
echo "Host: $(hostname)"
echo

echo "---- USER AUDIT ----"

for user in "${USERS[@]}"; do
    if id "$user" >/dev/null 2>&1; then
        echo
        echo "[FOUND] $user"
        id "$user"
        passwd -S "$user" 2>/dev/null || true
    else
        echo
        echo "[MISSING] $user"
    fi
done

echo
echo "---- GROUP AUDIT ----"

for group in "${GROUPS[@]}"; do
    if getent group "$group" >/dev/null; then
        echo
        getent group "$group"
    else
        echo "[MISSING] $group"
    fi
done

echo
echo "---- DIRECTORY AUDIT ----"

for directory in "${DIRECTORIES[@]}"; do
    if [[ -d "$directory" ]]; then
        stat -c '%A %a %U %G %n' "$directory"
    else
        echo "[MISSING] $directory"
    fi
done

echo
echo "---- SUDO AUDIT ----"

for user in "${USERS[@]}"; do
    echo
    echo "Privileges for $user:"
    sudo -n -l -U "$user" 2>/dev/null || echo "Unable to query or no sudo privileges found."
done

echo
echo "Audit complete."
```

Save the file.

# 15. Security

# Phase 15: Delegate Administrative Access

Giving everyone unrestricted root access would defeat our access model.

Development users do not need administrative privileges for this lab.

Operations users will receive a deliberately narrow sudo policy.

We will allow them to inspect and restart the SSH service.

This is only a lab example. Production sudo policy should be based on actual operational duties and reviewed carefully because command-level sudo delegation can have security implications.

---

## Step 1: Never casually edit `/etc/sudoers`

A syntax error in sudo configuration can create serious administrative problems.

Use:

```bash
visudo
```

or validate a drop-in before depending on it.

We will create a dedicated file.

Run:

```bash
sudo visudo -f /etc/sudoers.d/operations-lab
```

Add:

```text
%operations ALL=(root) /usr/bin/systemctl status ssh, /usr/bin/systemctl restart ssh
```

Save and exit.

# Build the Automated Access Test

We created the file earlier.

Open:

```bash
nano tests/test-access.sh
```

Add:

```bash
#!/usr/bin/env bash

set -u

PASS=0
FAIL=0

pass() {
    echo "[PASS] $1"
    PASS=$((PASS + 1))
}

fail() {
    echo "[FAIL] $1"
    FAIL=$((FAIL + 1))
}

test_read() {
    local user="$1"
    local file="$2"
    local description="$3"

    if sudo -u "$user" test -r "$file"; then
        pass "$description"
    else
        fail "$description"
    fi
}

test_denied_read() {
    local user="$1"
    local file="$2"
    local description="$3"

    if sudo -u "$user" test -r "$file"; then
        fail "$description"
    else
        pass "$description"
    fi
}

test_write() {
    local user="$1"
    local file="$2"
    local description="$3"

    if sudo -u "$user" test -w "$file"; then
        pass "$description"
    else
        fail "$description"
    fi
}

test_denied_write() {
    local user="$1"
    local file="$2"
    local description="$3"

    if sudo -u "$user" test -w "$file"; then
        fail "$description"
    else
        pass "$description"
    fi
}

echo "=========================================="
echo " Access Control Test Suite"
echo "=========================================="

test_read alice /srv/veriqta/development/dev-data.txt \
    "Alice can read Development data"

test_write bob /srv/veriqta/development/dev-data.txt \
    "Bob can write Development data"

test_denied_read erin /srv/veriqta/development/dev-data.txt \
    "Erin cannot read Development data"

test_denied_read alice /srv/veriqta/operations/ops-data.txt \
    "Alice cannot read Operations data"

test_read carol /srv/veriqta/operations/ops-data.txt \
    "Carol can read Operations data"

test_read erin /srv/veriqta/audit/audit-data.txt \
    "Erin can read Audit data"

test_denied_write erin /srv/veriqta/audit/audit-data.txt \
    "Erin cannot modify Audit data"

echo
echo "Passed: $PASS"
echo "Failed: $FAIL"

if (( FAIL > 0 )); then
    exit 1
fi

exit 0
```

Save.

Make executable:

```bash
chmod +x tests/test-access.sh
```

Run:

```bash
sudo ./tests/test-access.sh
```

A correctly configured lab should report all tests as PASS.

If not, do not modify the script simply to make the tests green.

Investigate the failed control.

That is how tests should be used.

# 23. Interview Preparation

## Basic Question 1

**What is a Linux UID?**

A UID is a numeric user identifier used by Linux to identify a user account internally.

---

## Basic Question 2

**What is a GID?**

A GID is a numeric identifier associated with a group.

---

## Basic Question 3

**What is the difference between a primary and supplementary group?**

A user has a primary group associated with their account and may also belong to additional supplementary groups used to grant access to other resources.

---

## Technical Question 1

**What does `chmod 2770 directory` mean?**

Answer:

```text
2 = setgid
7 = owner rwx
7 = group rwx
0 = no permissions for others
```

For a directory, setgid causes new entries to inherit the directory's group ownership.

---

## Technical Question 2

**Why did you use groups rather than assigning permissions individually?**

Good answer:

Group-based access reduces repeated per-user permission management and makes authorization easier to administer and audit as users join or leave teams.

---

## Technical Question 3

**Why not use `chmod 777`?**

Because it grants read, write, and execute permissions to everyone covered by those mode bits, usually violating least privilege and exposing resources unnecessarily.

---

## Technical Question 4

**What does `usermod -aG` do?**

`-G` specifies supplementary groups.

`-a` appends those groups without replacing the user's existing supplementary memberships.

---

## Troubleshooting Question

**A developer suddenly receives Permission denied. What do you check?**

A strong investigation might include:

```bash
id username
namei -l /path/to/resource
ls -ld /path/to/resource
getent group expected-group
```

Then inspect ownership, group membership, directory traversal permissions, target permissions, ACLs if present, and relevant security mechanisms before making changes.

---

## Scenario Question

**Alice was added to `developers`, but her existing terminal still does not show the membership. Why?**

Her current login session may have been created before the membership change. A new authenticated session will obtain the updated supplementary group set.

---

## Deep-Dive Question

**Why isn't setgid alone enough for shared collaboration?**

Setgid on a directory controls inherited group ownership.

It does not automatically guarantee that the resulting file mode gives that group write access.

`umask`, explicit modes, ACLs, and application behavior can affect the final permissions.

---

## Deep-Dive Question

**Why is password locking only part of deprovisioning?**

Because access may involve mechanisms beyond password authentication, including SSH keys, existing sessions, sudo privileges, scheduled jobs, service credentials, application accounts, and other authorization paths.

---

## Scenario Question

**Why validate SSH configuration before restarting SSH?**

Because an invalid configuration may prevent the daemon from restarting successfully and could cause remote-access disruption.

Use:

```bash
sudo sshd -t
```

before applying changes.
