# 08. Architecture

## 8.1 Understand the Linux Logging Path

On a modern Ubuntu system, applications and services can send events into the systemd journal.

Conceptually:

```text
SSH daemon
    |
    +----------------+
                     |
sudo                 |
    |                |
    +----------------+
                     |
systemd services     |
    |                |
    +----------------+
                     |
kernel               |
    |                |
    +----------------+
                     |
applications         |
    |                |
    +--------+-------+
             |
             v
      systemd-journald
             |
             v
       System Journal
             |
             v
         journalctl
             |
             v
        Analyzer Tool
```

---

## 8.2 Logs Are Evidence, Not Conclusions

Suppose the journal contains:

```text
Failed password for invalid user admin from 192.0.2.50
```

What can you conclude?

You can conclude that an authentication attempt matching that logged event failed.

You should **not** automatically conclude:

```text
The server was hacked.
```

A failed login is not proof of compromise.

Your tool should therefore use language such as:

```text
Repeated authentication failures detected
```

rather than:

```text
Attacker compromised server
```

This distinction is fundamental to responsible security analysis.

# PHASE 9: Extract Source Addresses

Suppose an SSH log contains:

```text
Failed password for invalid user admin from 192.0.2.25 port 44000 ssh2
```

We want:

```text
192.0.2.25
```

One simple parser for typical OpenSSH messages is:

```bash
sudo journalctl -u ssh --since today --no-pager |
grep -F 'Failed password' |
awk '{
    for (i=1; i<=NF; i++) {
        if ($i == "from") {
            print $(i+1)
        }
    }
}'
```

### How it works

`awk` examines each field.

When a field equals:

```text
from
```

it prints the next field.

This is more flexible than assuming the IP is always field 11.

---

# Count Sources

Add:

```bash
sort |
uniq -c |
sort -nr
```

Full command:

```bash
sudo journalctl -u ssh --since today --no-pager |
grep -F 'Failed password' |
awk '{
    for (i=1; i<=NF; i++) {
        if ($i == "from") {
            print $(i+1)
        }
    }
}' |
sort |
uniq -c |
sort -nr
```

Representative output:

```text
18 192.0.2.25
7 198.51.100.14
2 203.0.113.9
```

This tells you:

```text
source address
+
number of matching failures
```

It does **not** tell you the identity or intent of the person behind the address.

# PHASE 10: Analyze Invalid User Attempts

Run:

```bash

grep -F 'Invalid user'
```

Extract attempted usernames from typical OpenSSH messages:

```bash
sudo journalctl -u ssh --since today --no-pager |
grep -F 'Invalid user' |
awk '{
    for (i=1; i<=NF; i++) {
        if ($i == "user") {
            print $(i+1)

sort |
uniq -c |
```

Again, output depends entirely on your lab events.

# PHASE 16: Find Recurring System Problems

A useful analyst asks:

> Which messages occur repeatedly?

Raw journal messages contain timestamps, hostnames, process IDs, and other changing fields, so exact whole-line counting can be misleading.

For a beginner exercise, start by reviewing recent error messages:

```bash
sudo journalctl -p err --since "1 hour ago" \
-o cat --no-pager
```

`-o cat` removes much of the journal metadata and displays the message itself.

Count identical messages:

```bash
sudo journalctl -p err --since "1 hour ago" \
-o cat --no-pager |
sort |
uniq -c |
sort -nr |
head -n 20
```

This is simple frequency analysis.

It has limitations because dynamic values can make logically identical errors appear different.

Document that limitation.

# Why Thresholds Matter

Suppose:

```text
1 failed login
```

occurred because a legitimate user mistyped a password.

That is different from:

```text
50 failures
```

in a short period.

Thresholds let us detect repetition.

But thresholds also create trade-offs:

```text
Threshold too low
        ↓
too many alerts
        ↓
alert fatigue

Threshold too high
        ↓
important activity may be missed
```

---

# Detection States

Use:

```text
INFO
WARNING
CRITICAL
UNKNOWN
```

### INFO

An event worth recording but not necessarily abnormal.

### WARNING

Activity crossed the configured warning threshold.

### CRITICAL

Activity crossed a higher threshold requiring investigation.

### UNKNOWN

The tool could not reliably perform a check.

Notice what is deliberately absent:

```text
HACKED
ATTACKER
COMPROMISED
MALICIOUS
```

Those conclusions require evidence beyond a simple threshold.

```bash
REPORT_DIR="$PROJECT_DIR/reports"

ANALYZER_LOG="$LOG_DIR/analyzer.log"
ALERT_LOG="$ALERT_DIR/security-alerts.log"

mkdir -p "$LOG_DIR" "$ALERT_DIR" "$REPORT_DIR"

if [[ ! -r "$CONFIG_FILE" ]]; then
    echo "ERROR: Cannot read configuration file: $CONFIG_FILE" >&2
    exit 2
fi

# shellcheck disable=SC1090
source "$CONFIG_FILE"

TIMESTAMP="$(date '+%Y-%m-%d %H:%M:%S')"
REPORT_TIMESTAMP="$(date '+%Y%m%d_%H%M%S')"
HOSTNAME_SHORT="$(hostname -s)"

REPORT_FILE="$REPORT_DIR/security-report_${HOSTNAME_SHORT}_${REPORT_TIMESTAMP}.txt"

OVERALL_STATE="INFO"
WARNING_COUNT=0
CRITICAL_COUNT=0
UNKNOWN_COUNT=0

log_message() {
    local level="$1"
    local category="$2"
    local message="$3"

    printf '%s | %s | %s | %s | %s\n' \
        "$TIMESTAMP" \
        "$HOSTNAME_SHORT" \
        "$level" \
        "$category" \
        "$message" |
        tee -a "$ANALYZER_LOG" >> "$REPORT_FILE"
}

alert_message() {
    local level="$1"
    local category="$2"
    local message="$3"

    printf '%s | %s | %s | %s | %s\n' \
        "$TIMESTAMP" \
        "$HOSTNAME_SHORT" \
        "$level" \
        "$category" \
        "$message" >> "$ALERT_LOG"
}

update_state() {
    local level="$1"

    case "$level" in
        WARNING)
            WARNING_COUNT=$((WARNING_COUNT + 1))

            if [[ "$OVERALL_STATE" == "INFO" ]]; then
                OVERALL_STATE="WARNING"
            fi
            ;;

        CRITICAL)
            CRITICAL_COUNT=$((CRITICAL_COUNT + 1))
            OVERALL_STATE="CRITICAL"
            ;;

        UNKNOWN)
            UNKNOWN_COUNT=$((UNKNOWN_COUNT + 1))

            if [[ "$OVERALL_STATE" == "INFO" ]]; then
                OVERALL_STATE="UNKNOWN"
            fi
            ;;
    esac
}

evaluate_count() {
    local category="$1"
    local count="$2"
    local warning="$3"
    local critical="$4"

    if ! [[ "$count" =~ ^[0-9]+$ ]]; then
        log_message \
            "UNKNOWN" \
            "$category" \
            "Unable to parse event count"

        alert_message \
            "UNKNOWN" \
            "$category" \
            "Unable to parse event count"

        update_state "UNKNOWN"
        return
    fi

    if (( count >= critical )); then
        log_message \
            "CRITICAL" \
            "$category" \
            "count=$count threshold=$critical"

        alert_message \
            "CRITICAL" \
            "$category" \
            "count=$count threshold=$critical"

        update_state "CRITICAL"

    elif (( count >= warning )); then
        log_message \
            "WARNING" \
            "$category" \
            "count=$count threshold=$warning"

        alert_message \
            "WARNING" \
            "$category" \
            "count=$count threshold=$warning"

        update_state "WARNING"

    else
        log_message \
            "INFO" \
            "$category" \
            "count=$count"
    fi
}

collect_ssh_logs() {
    sudo journalctl \
        -u ssh \
        --since "$LOOKBACK_MINUTES minutes ago" \
        --no-pager 2>/dev/null
}

check_ssh_failures() {
    local logs count

    logs="$(collect_ssh_logs)" || {
        log_message \
            "UNKNOWN" \
            "SSH_FAILURES" \
            "Unable to read SSH journal"

        update_state "UNKNOWN"
        return
    }

    count="$(
        printf '%s\n' "$logs" |
        grep -Ec 'Failed password|authentication failure' || true
    )"

    evaluate_count \
        "SSH_FAILURES" \
        "$count" \
        "$SSH_FAILURE_WARNING" \
        "$SSH_FAILURE_CRITICAL"
}

check_invalid_users() {
    local logs count

    logs="$(collect_ssh_logs)" || {
        log_message \
            "UNKNOWN" \
            "INVALID_USERS" \
            "Unable to read SSH journal"

        update_state "UNKNOWN"
        return
    }

    count="$(
        printf '%s\n' "$logs" |
        grep -c 'Invalid user' || true
    )"

    evaluate_count \
        "INVALID_USERS" \
        "$count" \
        "$INVALID_USER_WARNING" \
        "$INVALID_USER_CRITICAL"
}

analyze_failed_sources() {
    local logs source_table top_count

    logs="$(collect_ssh_logs)" || {
        log_message \
            "UNKNOWN" \
            "SSH_SOURCE_ANALYSIS" \
            "Unable to read SSH journal"

        update_state "UNKNOWN"
        return
    }

    source_table="$(
        printf '%s\n' "$logs" |
        grep -E 'Failed password|Invalid user' |
        awk '{
            for (i=1; i<=NF; i++) {
                if ($i == "from") {
                    print $(i+1)
                    break
                }
            }
        }' |
        sort |
        uniq -c |
        sort -nr || true
    )"

    {
        echo
        echo "Top Sources Associated With Matching SSH Failures"
        echo "------------------------------------------------"
        if [[ -n "$source_table" ]]; then
            printf '%s\n' "$source_table" |
                head -n "$TOP_RESULTS"
        else
            echo "No matching source addresses found."
        fi
        echo
    } >> "$REPORT_FILE"

    top_count="$(
        printf '%s\n' "$source_table" |
        awk 'NR==1 {print $1}'
    )"

    if [[ -z "$top_count" ]]; then
        top_count=0
    fi

    evaluate_count \
        "TOP_SSH_FAILURE_SOURCE" \
        "$top_count" \
        "$SOURCE_FAILURE_WARNING" \
        "$SOURCE_FAILURE_CRITICAL"
}

report_successful_ssh() {
    local logs count

    logs="$(collect_ssh_logs)" || {
        log_message \
            "UNKNOWN" \
            "SUCCESSFUL_SSH" \
            "Unable to read SSH journal"

        update_state "UNKNOWN"
        return
    }

    count="$(
        printf '%s\n' "$logs" |
        grep -Ec 'Accepted (password|publickey)' || true
    )"

    log_message \
        "INFO" \
        "SUCCESSFUL_SSH" \
        "count=$count"

    {
        echo
        echo "Recent Successful SSH Authentication"
        echo "------------------------------------"

        printf '%s\n' "$logs" |
            grep -E 'Accepted (password|publickey)' |
            tail -n "$TOP_RESULTS" || true

        echo
    } >> "$REPORT_FILE"
}

check_sudo_failures() {
    local count

    count="$(
        sudo journalctl \
            _COMM=sudo \
            --since "$LOOKBACK_MINUTES minutes ago" \
            --no-pager 2>/dev/null |
        grep -Eic 'authentication failure|incorrect password' || true
    )"

    evaluate_count \
        "SUDO_FAILURES" \
        "$count" \
        "$SUDO_FAILURE_WARNING" \
        "$SUDO_FAILURE_CRITICAL"
}

report_sudo_commands() {
    {
        echo
        echo "Recent sudo Command Activity"
        echo "----------------------------"

        sudo journalctl \
            _COMM=sudo \
            --since "$LOOKBACK_MINUTES minutes ago" \
            --no-pager 2>/dev/null |
        grep 'COMMAND=' |
        tail -n "$TOP_RESULTS" || true

        echo
    } >> "$REPORT_FILE"
}

check_system_errors() {
    local count

    count="$(
        sudo journalctl \
            -p err \
            --since "$LOOKBACK_MINUTES minutes ago" \
            --no-pager 2>/dev/null |
        awk 'NF {count++} END {print count+0}'
    )"

    evaluate_count \
        "SYSTEM_ERRORS" \
        "$count" \
        "$SYSTEM_ERROR_WARNING" \
        "$SYSTEM_ERROR_CRITICAL"
}

report_recurring_errors() {
    {
        echo
        echo "Most Frequent Error Messages"
        echo "----------------------------"

        sudo journalctl \
            -p err \
            --since "$LOOKBACK_MINUTES minutes ago" \
            -o cat \
            --no-pager 2>/dev/null |
        awk 'NF' |
        sort |
        uniq -c |
        sort -nr |
        head -n "$TOP_RESULTS"

        echo
    } >> "$REPORT_FILE"
}

check_failed_units() {
    local count

    count="$(
        systemctl \
            --failed \
            --no-legend \
            --plain 2>/dev/null |
        awk 'NF {count++} END {print count+0}'
    )"

    evaluate_count \
        "FAILED_SYSTEMD_UNITS" \
        "$count" \
        "$FAILED_UNIT_WARNING" \
        "$FAILED_UNIT_CRITICAL"

    {
        echo
        echo "Failed systemd Units"
        echo "--------------------"

        systemctl --failed --no-pager || true

        echo
    } >> "$REPORT_FILE"
}

report_kernel_errors() {
    {
        echo
        echo "Recent Kernel Errors"
        echo "--------------------"

        sudo journalctl \
            -k \
            -p err \
            --since "$LOOKBACK_MINUTES minutes ago" \
            --no-pager 2>/dev/null |
        tail -n "$TOP_RESULTS"

        echo
    } >> "$REPORT_FILE"
}

write_report_header() {
    {
        echo "============================================================"
        echo " VERIQTA LINUX LOG ANALYSIS & SECURITY REPORT"
        echo "============================================================"
        echo
        echo "Host:             $HOSTNAME_SHORT"
        echo "Generated:        $TIMESTAMP"
        echo "Lookback window:  $LOOKBACK_MINUTES minutes"
        echo
    } > "$REPORT_FILE"
}

write_summary() {
    {
        echo
        echo "============================================================"
        echo " ANALYSIS SUMMARY"
        echo "============================================================"
        echo
        echo "Overall state:     $OVERALL_STATE"
        echo "Warnings:          $WARNING_COUNT"
        echo "Critical findings: $CRITICAL_COUNT"
        echo "Unknown checks:    $UNKNOWN_COUNT"
        echo
        echo "Important:"
        echo "A threshold finding identifies activity requiring review."
        echo "It does not by itself prove malicious activity or compromise."
        echo
    } >> "$REPORT_FILE"

    log_message \
        "INFO" \
        "SUMMARY" \
        "state=$OVERALL_STATE warnings=$WARNING_COUNT critical=$CRITICAL_COUNT unknown=$UNKNOWN_COUNT"
}

main() {
    write_report_header

    log_message \
        "INFO" \
        "ANALYZER" \
        "Starting log analysis"

    check_ssh_failures
    check_invalid_users
    analyze_failed_sources
    report_successful_ssh
    check_sudo_failures
    report_sudo_commands
    check_system_errors
    report_recurring_errors
    check_failed_units
    report_kernel_errors

    write_summary

    echo
    echo "Report created:"
    echo "$REPORT_FILE"

    case "$OVERALL_STATE" in
        CRITICAL)
            exit 2
            ;;

        WARNING|UNKNOWN)
            exit 1
            ;;

        *)
            exit 0
            ;;
    esac
}

main
```

# PHASE 27: Automate Analysis

A security tool that runs only when somebody remembers to execute it provides limited value.

Use cron.

First determine your absolute home path:

```bash
echo "$HOME"
```

Example:

```text
/home/student
```

Open:

```bash
crontab -e
```

Add, replacing `/home/student` with your actual path:

```cron
*/10 * * * * flock -n /tmp/veriqta-project07.lock PROJECT_DIR=/home/student/linux-log-security-tool /home/student/linux-log-security-tool/scripts/log-security-analyzer.sh >/dev/null 2>&1
```

However, because the script currently uses `sudo` for protected journal queries, unattended cron execution should **not** depend on an interactive sudo password prompt.

For this junior project, the safer learning approach is:

1. Run the full security analyzer manually when privileged journal access is required.
2. Use cron only after the required journal access model has been deliberately designed.
3. Do not add broad passwordless `sudo` merely to make the lab convenient.

An alternative is to grant the monitoring account appropriate journal-reading access according to the system's security policy, then remove unnecessary `sudo` calls from the scheduled version.

This teaches an important production principle:

> Automation should not be solved by casually granting unlimited privilege.

# 23. Interview Preparation

## What is a Linux log?

A recorded event generated by the kernel, service, application, authentication subsystem, or another system component.

---

## What is `systemd-journald`?

It is the systemd logging service responsible for collecting and storing journal events from multiple system sources.

---

## What is `journalctl`?

The command-line utility used to query the systemd journal.

---

## How do you view recent events?

```bash
journalctl -n 50
```

---

## How do you inspect a service?

```bash
journalctl -u ssh
```

---

## How do you search by time?

```bash
journalctl --since "1 hour ago"
```

---

## How do you inspect error-level messages?

```bash
journalctl -p err
```

---

## How do you inspect kernel messages?

```bash
journalctl -k
```

---

## What does `-o cat` do?

It outputs primarily the message content without the normal journal metadata.

This can be useful when performing simple message-frequency analysis.

---

## What does a failed SSH authentication prove?

It proves that a logged authentication attempt failed.

It does not by itself prove that the system was compromised.

---

## Why count repeated failures?

Frequency can reveal patterns that a single event would not show.

---

## Why group failures by source address?

It helps determine whether many matching failures are associated with the same source.

---

## Does an IP address identify a person?

Not necessarily.

Addresses can be shared, translated, reassigned, proxied, compromised, or otherwise not directly attributable to a specific individual.

---

## Why inspect successful authentication?

Because security investigation is not only about failures.

A successful login can provide important context.

---

## Why inspect sudo activity?

Because privileged actions can explain important system changes.

---

## What is a false positive?

An event flagged as suspicious or abnormal that turns out to have a legitimate explanation.

---

## What is a false negative?

Relevant activity that the detection system fails to identify.

---

## Why can simple grep-based detection fail?

Because:

```text
log formats change
messages vary
patterns can be too broad
patterns can be too narrow
events can be missing
permissions can hide data
structured fields may be ignored
```

---

## Why use time windows?

They limit analysis to events relevant to the investigation and make frequency meaningful.

---

## Why use thresholds?

To distinguish isolated events from repeated activity requiring greater attention.

---

## Why are static thresholds imperfect?

Normal activity differs between systems and workloads.

---

## What is correlation?

Examining multiple related events together to understand a larger sequence.

Example:

```text
Repeated SSH failures
       ↓
Successful login
       ↓
sudo command
       ↓
service configuration changed
```

Each event individually provides limited context.

Together they create an investigation timeline.

They still require interpretation.

---

## What is the difference between an event and an incident?

An event is something recorded by the system.

An incident is a situation determined to require response based on evidence, impact, policy, and context.

Not every event is an incident.

---

## What would a production solution add?

Potential improvements include:

```text
centralized log collection
structured parsing
event normalization
remote storage
tamper-resistant retention
SIEM integration
host identity
time synchronization monitoring
log rotation
dashboards
correlation rules
behavioral baselines
alert deduplication
ticket integration
on-call routing
audit trails
retention policies
role-based access
```

Common platforms may include technologies such as Elasticsearch/OpenSearch stacks, Splunk, Loki, or other security/log-management systems, depending on organizational requirements.

By completing **Junior Project 07: Linux Log Analysis & Security Tool**, you should be able to navigate the systemd journal, investigate authentication and system events, analyze failed and successful SSH authentication, inspect privileged activity, extract and count repeated sources, identify recurring errors, investigate failed services, create configurable Bash detection rules, generate security reports and alerts, test those rules using controlled failures, troubleshoot missed or noisy detections, protect operational evidence, and document the investigation.

The most important principle from this project is:

```text
LOG
 ↓
EVENT
 ↓
PATTERN
 ↓
ALERT
 ↓
CONTEXT
 ↓
EVIDENCE
 ↓
INVESTIGATION
 ↓
CONCLUSION
```

**A log entry is evidence. An alert is a signal. Neither is automatically proof of compromise.**
