# 08. Architecture

## Monitoring Pipeline

Every useful monitoring system performs roughly this process:

```text
COLLECT
   ↓
NORMALIZE
   ↓
COMPARE
   ↓
CLASSIFY
   ↓
RECORD
   ↓
ALERT
   ↓
INVESTIGATE
   ↓
RECOVER
   ↓
VERIFY
```

### Collect

Obtain a measurement.

Example:

```text
Disk usage = 72%
```

### Compare

Compare against policy:

```text
Warning  = 80%
Critical = 90%
```

### Classify

```text
72% → OK
84% → WARNING
96% → CRITICAL
```

### Alert

If the state is abnormal, create an alert record.

### Investigate

An administrator determines **why** the threshold was exceeded.

That last distinction is critical:

> Monitoring tells you that something may be wrong. It does not automatically tell you the root cause.

# PHASE 4: Understand Memory Monitoring

Run:

```bash
free -m
```

Do not simply treat:

```text
free memory
```

as the only usable memory.

Linux deliberately uses memory for caching.

For basic monitoring, the `available` value is generally more useful than looking only at `free`.

---

## Calculate Memory Usage Percentage

Run:

```bash
free | awk '/^Mem:/ {
    printf "%.2f\n", (($2-$7)/$2)*100
}'
```

Here:

```text
$2 = total memory
$7 = available memory
```

The calculation is:

```text
used-for-monitoring =
total - available
```

Then:

```text
percentage =
(total - available) / total × 100
```

---

## Inspect Swap

```bash
free -h
```

Swap usage is context.

Some swap usage does not automatically mean the server is failing.

Investigate trends and workload behavior rather than declaring any non-zero value critical.

# 13. Configuration

# Understand Health States

We will use:

```text
OK
WARNING
CRITICAL
UNKNOWN
```

Meaning:

```text
OK
Metric is inside configured operating range.

WARNING
Metric crossed the warning threshold.

CRITICAL
Metric crossed the critical threshold or a required service failed.

UNKNOWN
The monitoring system could not obtain or interpret the metric.
```

`UNKNOWN` matters.

A monitoring tool should not report:

```text
Everything is healthy
```

when it actually failed to collect data.

---

# Threshold Logic

For CPU:

```text
CPU < 70
    ↓
OK

CPU >= 70 and < 90
    ↓
WARNING

CPU >= 90
    ↓
CRITICAL
```

The same model applies to memory, disk, and inodes.

# PHASE 10: Build the Main Monitoring Script

Create:

```bash
nano ~/linux-server-monitoring/scripts/server-monitor.sh
```

Add the following complete script:

```bash
#!/usr/bin/env bash

set -u

PROJECT_DIR="$HOME/linux-server-monitoring"
CONFIG_FILE="$PROJECT_DIR/config/monitor.conf"
LOG_DIR="$PROJECT_DIR/logs"
ALERT_DIR="$PROJECT_DIR/alerts"

MONITOR_LOG="$LOG_DIR/monitor.log"
ALERT_LOG="$ALERT_DIR/alerts.log"

mkdir -p "$LOG_DIR" "$ALERT_DIR"

if [[ ! -r "$CONFIG_FILE" ]]; then
    echo "ERROR: Cannot read configuration: $CONFIG_FILE" >&2
    exit 2
fi

# shellcheck disable=SC1090
source "$CONFIG_FILE"

HOSTNAME=$(hostname)
TIMESTAMP=$(date '+%Y-%m-%d %H:%M:%S')

OVERALL_STATE="OK"
WARNING_COUNT=0
CRITICAL_COUNT=0
UNKNOWN_COUNT=0

log_line() {
    local message="$1"
    printf '%s | %s | %s\n' \
        "$TIMESTAMP" "$HOSTNAME" "$message" |
        tee -a "$MONITOR_LOG"
}

alert() {
    local severity="$1"
    local metric="$2"
    local message="$3"

    printf '%s | %s | %s | %s | %s\n' \
        "$TIMESTAMP" \
        "$HOSTNAME" \
        "$severity" \
        "$metric" \
        "$message" >> "$ALERT_LOG"
}

set_state() {
    local state="$1"

    case "$state" in
        WARNING)
            WARNING_COUNT=$((WARNING_COUNT + 1))

            if [[ "$OVERALL_STATE" == "OK" ]]; then
                OVERALL_STATE="WARNING"
            fi
            ;;

        CRITICAL)
            CRITICAL_COUNT=$((CRITICAL_COUNT + 1))
            OVERALL_STATE="CRITICAL"
            ;;

        UNKNOWN)
            UNKNOWN_COUNT=$((UNKNOWN_COUNT + 1))

            if [[ "$OVERALL_STATE" == "OK" ]]; then
                OVERALL_STATE="UNKNOWN"
            fi
            ;;
    esac
}

check_integer_metric() {
    local name="$1"
    local value="$2"
    local warning="$3"
    local critical="$4"
    local unit="$5"

    if ! [[ "$value" =~ ^[0-9]+$ ]]; then
        log_line "UNKNOWN | $name | Unable to parse value: $value"
        alert "UNKNOWN" "$name" "Unable to parse metric value"
        set_state "UNKNOWN"
        return
    fi

    if (( value >= critical )); then
        log_line "CRITICAL | $name | ${value}${unit} | threshold=${critical}${unit}"
        alert "CRITICAL" "$name" "${value}${unit} >= ${critical}${unit}"
        set_state "CRITICAL"

    elif (( value >= warning )); then
        log_line "WARNING | $name | ${value}${unit} | threshold=${warning}${unit}"
        alert "WARNING" "$name" "${value}${unit} >= ${warning}${unit}"
        set_state "WARNING"

    else
        log_line "OK | $name | ${value}${unit}"
    fi
}

get_cpu_usage() {
    local cpu user nice system idle iowait irq softirq steal guest guest_nice
    local idle1 total1 idle2 total2
    local total_delta idle_delta usage

    read -r cpu user nice system idle iowait irq softirq steal guest guest_nice \
        < /proc/stat

    idle1=$((idle + iowait))
    total1=$((user + nice + system + idle + iowait + irq + softirq + steal))

    sleep 1

    read -r cpu user nice system idle iowait irq softirq steal guest guest_nice \
        < /proc/stat

    idle2=$((idle + iowait))
    total2=$((user + nice + system + idle + iowait + irq + softirq + steal))

    total_delta=$((total2 - total1))
    idle_delta=$((idle2 - idle1))

    if (( total_delta <= 0 )); then
        echo "UNKNOWN"
        return
    fi

    usage=$(( (100 * (total_delta - idle_delta)) / total_delta ))

    echo "$usage"
}

check_cpu() {
    local usage

    usage=$(get_cpu_usage)

    check_integer_metric \
        "CPU_USAGE" \
        "$usage" \
        "$CPU_WARNING" \
        "$CPU_CRITICAL" \
        "%"
}

check_memory() {
    local usage

    usage=$(free | awk '
        /^Mem:/ {
            if ($2 > 0) {
                printf "%.0f", (($2-$7)/$2)*100
            }
        }
    ')

    check_integer_metric \
        "MEMORY_USAGE" \
        "$usage" \
        "$MEMORY_WARNING" \
        "$MEMORY_CRITICAL" \
        "%"
}

check_disk() {
    local filesystem mount usage

    while read -r filesystem mount usage; do

        usage="${usage%\%}"

        check_integer_metric \
            "DISK_${mount}" \
            "$usage" \
            "$DISK_WARNING" \
            "$DISK_CRITICAL" \
            "%"

    done < <(
        df -P -x tmpfs -x devtmpfs |
        awk 'NR>1 {print $1, $6, $5}'
    )
}

check_inodes() {
    local filesystem mount usage

    while read -r filesystem mount usage; do

        usage="${usage%\%}"

        check_integer_metric \
            "INODE_${mount}" \
            "$usage" \
            "$INODE_WARNING" \
            "$INODE_CRITICAL" \
            "%"

    done < <(
        df -Pi -x tmpfs -x devtmpfs |
        awk 'NR>1 {print $1, $6, $5}'
    )
}

check_load() {
    local load1 cpu_count warning critical state

    load1=$(awk '{print $1}' /proc/loadavg)
    cpu_count=$(nproc)

    warning=$(awk \
        -v cpu="$cpu_count" \
        -v factor="$LOAD_WARNING_PER_CPU" \
        'BEGIN {printf "%.2f", cpu * factor}')

    critical=$(awk \
        -v cpu="$cpu_count" \
        -v factor="$LOAD_CRITICAL_PER_CPU" \
        'BEGIN {printf "%.2f", cpu * factor}')

    state=$(awk \
        -v load="$load1" \
        -v warning="$warning" \
        -v critical="$critical" '
        BEGIN {
            if (load >= critical)
                print "CRITICAL"
            else if (load >= warning)
                print "WARNING"
            else
                print "OK"
        }')

    case "$state" in
        CRITICAL)
            log_line "CRITICAL | LOAD_1M | $load1 | critical=$critical"
            alert "CRITICAL" "LOAD_1M" "$load1 >= $critical"
            set_state "CRITICAL"
            ;;

        WARNING)
            log_line "WARNING | LOAD_1M | $load1 | warning=$warning"
            alert "WARNING" "LOAD_1M" "$load1 >= $warning"
            set_state "WARNING"
            ;;

        OK)
            log_line "OK | LOAD_1M | $load1 | CPUs=$cpu_count"
            ;;

        *)
            log_line "UNKNOWN | LOAD_1M | Unable to classify load"
            alert "UNKNOWN" "LOAD_1M" "Unable to classify load"
            set_state "UNKNOWN"
            ;;
    esac
}

check_zombies() {
    local count

    count=$(ps -eo state= |
        awk '$1 ~ /^Z/ {count++} END {print count+0}')

    if ! [[ "$count" =~ ^[0-9]+$ ]]; then
        log_line "UNKNOWN | ZOMBIE_PROCESSES | Unable to determine count"
        set_state "UNKNOWN"
        return
    fi

    if (( count >= ZOMBIE_CRITICAL )); then
        log_line "CRITICAL | ZOMBIE_PROCESSES | $count"
        alert "CRITICAL" "ZOMBIE_PROCESSES" "Detected $count zombie processes"
        set_state "CRITICAL"

    elif (( count >= ZOMBIE_WARNING )); then
        log_line "WARNING | ZOMBIE_PROCESSES | $count"
        alert "WARNING" "ZOMBIE_PROCESSES" "Detected $count zombie processes"
        set_state "WARNING"

    else
        log_line "OK | ZOMBIE_PROCESSES | $count"
    fi
}

check_services() {
    local service

    for service in "${CRITICAL_SERVICES[@]}"; do

        if systemctl is-active --quiet "$service"; then
            log_line "OK | SERVICE_$service | active"

        else
            log_line "CRITICAL | SERVICE_$service | not active"
            alert "CRITICAL" "SERVICE_$service" "Required service is not active"
            set_state "CRITICAL"
        fi

    done
}

check_failed_units() {
    local count

    count=$(systemctl --failed --no-legend --plain 2>/dev/null |
        awk 'NF {count++} END {print count+0}')

    if ! [[ "$count" =~ ^[0-9]+$ ]]; then
        log_line "UNKNOWN | FAILED_SYSTEMD_UNITS | Unable to determine count"
        set_state "UNKNOWN"
        return
    fi

    if (( count > 0 )); then
        log_line "WARNING | FAILED_SYSTEMD_UNITS | $count"
        alert "WARNING" "FAILED_SYSTEMD_UNITS" "$count failed units detected"
        set_state "WARNING"

    else
        log_line "OK | FAILED_SYSTEMD_UNITS | 0"
    fi
}

show_top_processes() {
    log_line "INFO | TOP_CPU_PROCESSES"

    ps -eo pid,user,comm,%cpu,%mem \
        --sort=-%cpu |
        head -n 6 |
        tee -a "$MONITOR_LOG"

    log_line "INFO | TOP_MEMORY_PROCESSES"

    ps -eo pid,user,comm,%cpu,%mem \
        --sort=-%mem |
        head -n 6 |
        tee -a "$MONITOR_LOG"
}

show_uptime() {
    local uptime_value

    uptime_value=$(uptime -p)

    log_line "INFO | UPTIME | $uptime_value"
}

main() {
    log_line "INFO | MONITOR_START"

    check_cpu
    check_memory
    check_disk
    check_inodes
    check_load
    check_zombies
    check_services
    check_failed_units
    show_uptime
    show_top_processes

    log_line \
        "SUMMARY | state=$OVERALL_STATE warnings=$WARNING_COUNT critical=$CRITICAL_COUNT unknown=$UNKNOWN_COUNT"

    case "$OVERALL_STATE" in
        CRITICAL)
            exit 2
            ;;

        WARNING|UNKNOWN)
            exit 1
            ;;

        *)
            exit 0
            ;;
    esac
}

main
```

# PHASE 11: Understand the Script

Do not treat this script as magic.

## Configuration Loading

```bash
source "$CONFIG_FILE"
```

loads variables such as:

```text
CPU_WARNING
CPU_CRITICAL
DISK_WARNING
CRITICAL_SERVICES
```

This separates:

```text
program logic
```

from:

```text
monitoring policy
```

That is better than burying every threshold throughout the code.

---

## CPU Collection

The script samples `/proc/stat` twice.

```text
Sample 1
   ↓
sleep 1
   ↓
Sample 2
   ↓
calculate delta
```

This provides CPU activity during the interval rather than treating cumulative boot counters as instantaneous percentages.

---

## Memory Calculation

The script uses:

```text
total - available
```

rather than treating caches as automatically unavailable memory.

---

## Disk Loop

The script checks multiple persistent filesystems instead of assuming `/` is the only filesystem worth monitoring.

---

## Alert Function

Alerts are written separately:

```text
logs/monitor.log
```

contains general monitoring output.

```text
alerts/alerts.log
```

contains abnormal events.

This makes alerts easier to review.

# 14. Automation

# PHASE 12: Prevent Overlapping Runs

Suppose monitoring executes every minute but a previous run has not finished.

You do not necessarily want:

```text
monitor #1
monitor #2
monitor #3
monitor #4
```

running simultaneously.

Use `flock`.

Test:

```bash
flock -n /tmp/veriqta-monitor.lock \
"$HOME/linux-server-monitoring/scripts/server-monitor.sh"
```

`-n` means do not wait if another process already holds the lock.

# 15. Security

A monitoring script can become a security problem if designed badly.

## Principle 1: Do Not Store Secrets

Do not place:

```text
passwords
SSH private keys
API tokens
cloud credentials
database passwords
```

inside `monitor.conf`.

---

## Principle 2: Avoid Running Everything as Root

The script currently gathers mostly non-destructive system information.

Run it as your normal account unless a specific metric genuinely requires elevated privileges.

---

## Principle 3: Protect Configuration

Check:

```bash
ls -l ~/linux-server-monitoring/config/monitor.conf
```

Set:

```bash
chmod 640 ~/linux-server-monitoring/config/monitor.conf
```

Verify:

```bash
stat -c '%A %a %U:%G %n' \
~/linux-server-monitoring/config/monitor.conf
```

---

## Principle 4: Protect Monitoring Logs

Set directories:

```bash
chmod 750 ~/linux-server-monitoring/logs
chmod 750 ~/linux-server-monitoring/alerts
```

Monitoring output can reveal:

```text
hostnames
process names
services
resource usage
filesystem layout
operational failures
```

Treat operational information appropriately.

---

## Principle 5: Never Let Monitoring Perform Destructive "Fixes" Automatically

This junior tool should **detect and report**.

It should not automatically execute:

```bash
kill -9
rm -rf
systemctl restart
reboot
```

simply because a threshold is exceeded.

Detection and remediation are separate concerns.

# 18. Troubleshooting

Use this investigation model:

```text
ALERT
  ↓
What metric triggered?
  ↓
Is the measurement valid?
  ↓
What changed?
  ↓
What is the blast radius?
  ↓
Which processes/services are involved?
  ↓
What do system metrics show?
  ↓
What do logs show?
  ↓
Form hypothesis
  ↓
Test hypothesis
  ↓
Identify root cause
  ↓
Mitigate
  ↓
Recover
  ↓
Re-run monitoring
  ↓
Confirm alert cleared
```

---

## Scenario 1: CPU Critical

Start:

```bash
uptime
```

Then:

```bash
top
```

Then:

```bash
ps -eo pid,user,comm,%cpu,%mem \
--sort=-%cpu | head -n 15
```

With `sysstat`:

```bash
pidstat 1 5
```

Investigate before killing anything.

Ask:

```text
Which process?
Expected workload?
How long has it been high?
One CPU or all CPUs?
Recent deployment?
Infinite loop?
Background job?
Compilation?
Compression?
Backup?
```

---

## Scenario 2: Memory Critical

Run:

```bash
free -h
```

Then:

```bash
ps -eo pid,user,comm,%mem,rss \
--sort=-%mem | head -n 15
```

Then:

```bash
vmstat 1 5
```

Look at:

```text
available memory
swap activity
largest processes
system responsiveness
```

Do not automatically conclude:

> Memory is bad because free memory is low.

---

## Scenario 3: Disk Critical

Run:

```bash
df -hT
```

Identify affected mount.

Then investigate major directories.

For root filesystem:

```bash
sudo du -xhd1 / |
sort -h
```

If `/var` is large:

```bash
sudo du -xhd1 /var |
sort -h
```

If `/var/log` is large:

```bash
sudo du -xhd1 /var/log |
sort -h
```

Do not immediately run destructive cleanup commands.

Find the cause first.

---

## Scenario 4: Disk Space Looks Fine but Files Cannot Be Created

Check:

```bash
df -h
```

Then:

```bash
df -i
```

Possible cause:

```text
inode exhaustion
```

This is exactly why Project 06 monitors both.

---

## Scenario 5: Load Is High but CPU Is Not

Check:

```bash
uptime
```

Then:

```bash
vmstat 1 10
```

Then:

```bash
ps -eo pid,state,comm,wchan:32 |
head -n 30
```

High Linux load can involve runnable tasks and tasks waiting in uninterruptible sleep, often associated with I/O.

Therefore:

```text
high load
```

does not always mean:

```text
CPU is 100%
```


Then:

```bash
sudo journalctl -u SERVICE -n 100 --no-pager
```

Check recent changes before restarting blindly.

```text
command exists?
permission?
output format?
configuration valid?
filesystem mounted?
script syntax?
```

# 23. Interview Preparation

## What is monitoring?

Monitoring is the systematic collection and evaluation of system information to understand health, performance, availability, and abnormal conditions.

## What is a metric?

A numeric measurement observed over time, such as CPU utilization, memory usage, or filesystem capacity.

## What is a threshold?

A configured boundary used to classify a measurement.

## What is an alert?

A notification or recorded event indicating that a defined condition has occurred.

## Is 90% CPU automatically an incident?

Not necessarily. Duration, workload, latency, capacity, system behavior, and business impact matter.

## Why monitor available memory instead of only free memory?

Linux uses otherwise unused memory for caches. Available memory provides a more useful estimate of memory that can be made available to applications.

## Why monitor inodes?

Because a filesystem can exhaust file metadata entries even when storage blocks remain available.

## What is load average?

It represents the average system load over time. On Linux, it reflects runnable tasks and tasks in uninterruptible sleep, so it should not be interpreted as simply "CPU percentage."

## Why consider CPU count when interpreting load?

A load of `2` means something different on a one-CPU system than on a sixteen-CPU system.

## What is a zombie process?

A terminated process whose parent has not yet collected its exit status.

## Why is `systemctl is-active` useful?

It provides a concise service-state result that works well in automation.

## What is the difference between monitoring and troubleshooting?

Monitoring identifies symptoms or abnormal states.

Troubleshooting investigates the cause.

```text
Monitoring:
"Disk is 94% full."

Troubleshooting:
"Why is the disk 94% full?"
```

## Why shouldn't monitoring automatically `kill -9` a high-CPU process?

Because high utilization does not prove the process is faulty. Automatic destructive remediation can create a larger outage.

## Why use exit codes?

Other programs can interpret them programmatically.

In this project:

```text
0 = OK
1 = WARNING/UNKNOWN
2 = CRITICAL
```

## Why use `flock`?

To prevent multiple scheduled copies of the monitoring script from overlapping.

## What is a monitoring blind spot?

An important system condition that the monitoring design does not observe.

For example, this project could report CPU and memory as healthy while a real web application is unavailable if application-level checks are absent.

## What would you add in production?
