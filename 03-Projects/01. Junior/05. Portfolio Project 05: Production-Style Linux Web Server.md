# 13. Configuration

# PHASE 7: Create a Dedicated Nginx Server Block

Do not simply replace the default website and pretend the server has been properly structured.

Create a dedicated configuration.

Run:

```bash
sudo nano /etc/nginx/sites-available/veriqta
```

Add:

```nginx
server {
    listen 80;
    listen [::]:80;

    server_name _;

    root /var/www/veriqta;
    index index.html;

    access_log /var/log/nginx/veriqta_access.log;
    error_log /var/log/nginx/veriqta_error.log;

    location / {
        try_files $uri $uri/ =404;
    }
}
```

---

# Understand Every Directive

## `server`

```nginx
server {
}
```

Defines a virtual server.

---

## `listen 80`

```nginx
listen 80;
```

Tells Nginx to accept IPv4 HTTP requests on TCP port 80.

---

## IPv6 listener

```nginx
listen [::]:80;
```

Provides the corresponding IPv6 listener where IPv6 is available.

---

## `server_name`

```nginx
server_name _;
```

For this lab, `_` acts as a catch-all style value rather than requiring a real domain.

With a real domain, you could use:

```nginx
server_name example.com www.example.com;
```

---

## `root`

```nginx
root /var/www/veriqta;
```

Tells Nginx where the website files live.

---

## `index`

```nginx
index index.html;
```

Defines the default index file.

---

## `access_log`

Records HTTP requests for this site.

---

## `error_log`

Records Nginx errors related to the site.

---

## `try_files`

```nginx
try_files $uri $uri/ =404;
```

Nginx checks whether the requested resource exists.

If it cannot find the resource, it returns HTTP 404.

# Why Reload Instead of Restart?

A reload asks Nginx to apply configuration changes while minimizing interruption.

A restart stops and starts the service.

For routine configuration changes, a validated reload is generally preferable.

# PHASE 10: Configure Ownership and Permissions

A common beginner response to permission problems is:

```bash
chmod -R 777 /var/www
```

Do **not** do this.

---

## Understand the Requirement

Nginx must be able to read static website files.

It does not require every user on the system to have write access.

For this static lab:

```text
root
  |
  | manages deployed content
  v
/var/www/veriqta

Nginx worker
  |
  | read/traverse
  v
website content
```

---

## Set Ownership

Run:

```bash
sudo chown -R root:root /var/www/veriqta
```

Set directories:

```bash
sudo find /var/www/veriqta -type d -exec chmod 755 {} \;
```

Set files:

```bash
sudo find /var/www/veriqta -type f -exec chmod 644 {} \;
```

---

## Why 755 for directories?

Directories require execute permission to be traversed.

Conceptually:

```text
Owner: read + write + execute
Group: read + execute
Other: read + execute
```

---

## Why 644 for files?

```text
Owner: read + write
Group: read
Other: read
```

The web server can read static files without receiving unnecessary write access.

---

## Verify

Run:

```bash
stat -c '%A %a %U %G %n' /var/www/veriqta
```

Then:

```bash
stat -c '%A %a %U %G %n' /var/www/veriqta/index.html
```

Expected modes:

```text
755 directory
644 file
```

---

# Test Nginx's Effective Access

On Ubuntu, Nginx commonly runs workers as `www-data`.

Check:

```bash
ps -eo user,group,pid,cmd | grep '[n]ginx'
```

Test file readability:

```bash
sudo -u www-data test -r /var/www/veriqta/index.html \
&& echo "PASS: www-data can read index.html" \
|| echo "FAIL: www-data cannot read index.html"
```

# PHASE 13: Build the Web Health Script

Create:

```bash
nano ~/production-web-server/scripts/web-health.sh
```

Add:

```bash
#!/usr/bin/env bash

set -u

URL="http://127.0.0.1/"
EXPECTED_TEXT="VERIQTA Production-Style Linux Web Server"

PASS=0
FAIL=0

pass() {
    echo "[PASS] $1"
    PASS=$((PASS + 1))
}

fail() {
    echo "[FAIL] $1"
    FAIL=$((FAIL + 1))
}

section() {
    echo
    echo "=================================================="
    echo "$1"
    echo "=================================================="
}

section "WEB SERVER HEALTH REPORT"

echo "Timestamp: $(date)"
echo "Hostname: $(hostname)"

section "NGINX SERVICE"

if systemctl is-active --quiet nginx; then
    pass "Nginx service is active"
else
    fail "Nginx service is not active"
fi

section "NGINX STARTUP"

if systemctl is-enabled --quiet nginx 2>/dev/null; then
    pass "Nginx is enabled at boot"
else
    fail "Nginx is not enabled at boot"
fi

section "CONFIGURATION"

if sudo nginx -t >/dev/null 2>&1; then
    pass "Nginx configuration test passed"
else
    fail "Nginx configuration test failed"
fi

section "TCP PORT 80"

if ss -lnt | grep -q ':80 '; then
    pass "TCP port 80 is listening"
else
    fail "TCP port 80 is not listening"
fi

section "HTTP STATUS"

HTTP_CODE=$(curl -s \
    -o /tmp/veriqta-web-health-body.$$ \
    -w "%{http_code}" \
    "$URL" || true)

if [[ "$HTTP_CODE" == "200" ]]; then
    pass "Website returned HTTP 200"
else
    fail "Website returned HTTP ${HTTP_CODE:-unknown}"
fi

section "CONTENT VALIDATION"

if grep -q "$EXPECTED_TEXT" \
    /tmp/veriqta-web-health-body.$$ 2>/dev/null; then
    pass "Expected website content found"
else
    fail "Expected website content not found"
fi

rm -f /tmp/veriqta-web-health-body.$$

section "DOCUMENT ROOT"

if [[ -r /var/www/veriqta/index.html ]]; then
    pass "Homepage exists and is readable"
else
    fail "Homepage is missing or unreadable"
fi

section "DISK CAPACITY"

df -hT /var/www/veriqta

section "NGINX LOGS"

if [[ -f /var/log/nginx/veriqta_access.log ]]; then
    pass "Access log exists"
else
    fail "Access log not found"
fi

if [[ -f /var/log/nginx/veriqta_error.log ]]; then
    pass "Error log exists"
else
    fail "Error log not found"
fi

section "SUMMARY"

echo "Passed: $PASS"
echo "Failed: $FAIL"

if (( FAIL > 0 )); then
    exit 1
fi

exit 0
```

Make executable:

```bash
chmod +x ~/production-web-server/scripts/web-health.sh
```

Run:

```bash

```

# Control 2: Add Basic Security Headers

Edit:

```bash
sudo nano /etc/nginx/sites-available/veriqta
```

Use:

```nginx

    listen 80;
    listen [::]:80;

    server_name _;

    root /var/www/veriqta;
    index index.html;

    access_log /var/log/nginx/veriqta_access.log;
    error_log /var/log/nginx/veriqta_error.log;

    add_header X-Frame-Options "SAMEORIGIN" always;
    add_header Referrer-Policy "strict-origin-when-cross-origin" always;

    location / {

    }
}
```

```bash

```

Verify:



```text
purpose
expected owner of port
```


Add:

```bash
#!/usr/bin/env bash

set -u

PASS=0
FAIL=0

URL="http://127.0.0.1/"
EXPECTED="VERIQTA Production-Style Linux Web Server"

pass() {
    echo "[PASS] $1"
    PASS=$((PASS + 1))
}

fail() {
    echo "[FAIL] $1"
    FAIL=$((FAIL + 1))
}

echo "=============================================="
echo " Production Web Server Validation"
echo "=============================================="

if systemctl is-active --quiet nginx; then
    pass "Nginx is active"
else
    fail "Nginx is inactive"
fi

if systemctl is-enabled --quiet nginx 2>/dev/null; then
    pass "Nginx starts automatically"
else
    fail "Nginx is not enabled"
fi

if sudo nginx -t >/dev/null 2>&1; then
    pass "Nginx configuration is valid"
else
    fail "Nginx configuration is invalid"
fi

if ss -lnt | grep -q ':80 '; then
    pass "TCP port 80 is listening"
else
    fail "TCP port 80 is not listening"
fi

HTTP_CODE=$(curl -s -o /tmp/web-validation.$$ \
    -w '%{http_code}' "$URL" || true)

if [[ "$HTTP_CODE" == "200" ]]; then
    pass "Homepage returns HTTP 200"
else
    fail "Homepage returned HTTP ${HTTP_CODE:-unknown}"
fi

if grep -q "$EXPECTED" /tmp/web-validation.$$ 2>/dev/null; then
    pass "Expected homepage content found"
else
    fail "Expected homepage content missing"
fi

rm -f /tmp/web-validation.$$

NOT_FOUND=$(curl -s -o /dev/null \
    -w '%{http_code}' \
    "${URL}this-page-should-not-exist" || true)

if [[ "$NOT_FOUND" == "404" ]]; then
    pass "Missing resources correctly return 404"
else
    fail "Expected 404, received ${NOT_FOUND:-unknown}"
fi

if sudo -u www-data test -r /var/www/veriqta/index.html; then
    pass "Nginx worker identity can read homepage"
else
    fail "Nginx worker identity cannot read homepage"
fi

if sudo find /var/www/veriqta -xdev -perm -0002 -print |
grep -q .; then
    fail "World-writable website content detected"
else
    pass "No world-writable website content detected"
fi

if sudo ufw status |
grep -q 'Nginx HTTP'; then
    pass "UFW contains Nginx HTTP rule"
else
    fail "Expected Nginx HTTP firewall rule not found"
fi

if [[ -f /var/log/nginx/veriqta_access.log ]]; then
    pass "Dedicated access log exists"
else
    fail "Dedicated access log missing"
fi

if [[ -f /var/log/nginx/veriqta_error.log ]]; then
    pass "Dedicated error log exists"
else
    fail "Dedicated error log missing"
fi

echo
echo "=============================================="
echo " RESULTS"
echo "=============================================="
echo "Passed: $PASS"
echo "Failed: $FAIL"

if (( FAIL > 0 )); then
    exit 1
fi

exit 0
```

# 24. Interview Preparation

## What happens when a user enters a website address?

At a simplified level:

```text
Domain
  ↓
DNS resolution
  ↓
Destination IP
  ↓
Network connection
  ↓
TCP port
  ↓
Web server
  ↓
Virtual host/server block
  ↓
Application/static content
  ↓
HTTP response
```

---

## What is Nginx?

Nginx is software commonly used as a web server, reverse proxy, load balancer, and HTTP gateway.

In this project it operates as a static web server.

---

## What is HTTP port 80?

Port 80 is the conventional TCP port for unencrypted HTTP traffic.

---

## What is port 443?

Port 443 is conventionally used for HTTPS.

---

## What is a server block?

An Nginx server block defines how Nginx should handle requests for a particular virtual server, including listening ports, names, document roots, logging, and request handling.

---

## Difference between `sites-available` and `sites-enabled`?

On Ubuntu's Nginx packaging, `sites-available` commonly stores potential site configurations.

`sites-enabled` commonly contains links to configurations that should be loaded.

---

## What does `nginx -t` do?

It validates Nginx configuration before reload/start operations.

It helps catch syntax and configuration problems before applying them.

---

## Difference between restart and reload?

A restart stops and starts the service.

A reload asks the running service to apply configuration changes, generally with less disruption.

---

## Why shouldn't website files be `777`?

Because that grants write permission far more broadly than a static web server normally requires.

Permissions should reflect actual access requirements.

---

## What does UFW do?

UFW provides a simplified interface for managing host firewall rules on Ubuntu.

---

## Why permit SSH before enabling UFW?

If the machine is being administered remotely through SSH, enabling a firewall without allowing the SSH path can lock the administrator out.

---

## Difference between 403 and 404?

Generally:

```text
403 = request understood but access forbidden
404 = requested resource not found
```

Exact causes depend on configuration and application behavior.

---

## Nginx is active but website does not load. What next?

Do not assume that an active process proves end-to-end health.

Check:

```text
configuration
listening socket
local HTTP
firewall
network
server block
files
permissions
logs
```

---

## Local curl works but remote browser fails. What does that tell you?

It is evidence that the web service itself may be healthy locally.

Focus investigation on:

```text
listening interface
firewall
VM networking
routing
external firewall
client path
```

---

## How do you identify what owns port 80?

```bash
sudo ss -lntp | grep ':80 '
```

or:

```bash
sudo lsof -iTCP:80 -sTCP:LISTEN
```

---

## How do you troubleshoot an Nginx configuration failure?

A strong sequence:

```bash
sudo nginx -t
systemctl status nginx --no-pager
sudo journalctl -u nginx -n 100 --no-pager
```

Then inspect the referenced configuration.

---

## Why monitor both HTTP status and content?

Because a different page can still return HTTP 200.

A stronger health check verifies that the expected application content is actually being served.

---

## What logs would you inspect?

For this project:

```text
/var/log/nginx/veriqta_access.log
/var/log/nginx/veriqta_error.log
systemd journal for nginx
```

---

## What would change for a real internet-facing production website?

A stronger architecture would normally consider:

```text
real DNS
HTTPS/TLS
certificate automation
stronger SSH controls
backup/recovery
configuration management
centralized logging
external monitoring
alerting
rate limiting where appropriate
application-specific security
vulnerability/patch management
redundancy
reverse proxy/application architecture
load balancing when required
```

This project intentionally establishes the foundation before introducing those systems.
