# 02. Project Scenario

You are a junior Linux administrator supporting a growing internal application server.

The original server was deployed with only its operating-system disk.

The application team now needs additional storage.

Three storage requirements have been identified:

### Application data

The application requires a dedicated filesystem mounted at:

```text
/srv/app-data
```

### Team archive

Operations requires another dedicated filesystem mounted at:

```text
/srv/archive
```

### Flexible application storage

The company also expects application data to grow.

Instead of allocating all future storage using fixed traditional partitions, the infrastructure team wants you to build an LVM environment containing separate logical volumes for:

```text
/srv/lvm-app
/srv/lvm-logs
```

Later, the application logical volume will deliberately run low on capacity.

You will expand it without rebuilding the storage environment.

You will also simulate common failures:

* Incorrect filesystem identification
* Failed persistent mounts
* Permission problems
* Full filesystem conditions
* Missing or incorrect mount configuration
* LVM capacity pressure

Your final environment should be understandable enough that another junior administrator can inspect it and explain how storage flows from physical disk to application directory.

# 08. Architecture

## Storage Stack

Understanding this stack is essential.

### Physical/virtual disk

Example:

```text
/dev/sdb
```

This represents the entire disk.

### Partition

Example:

```text
/dev/sdb1
```

This represents a defined region of the disk.

### Filesystem

Example:

```text
ext4
```

The filesystem organizes files and directories inside storage.

### Mount point

Example:

```text
/srv/app-data
```

This is where the filesystem becomes accessible through the Linux directory tree.

The relationship is:

```text
/dev/sdb
   |
   v
/dev/sdb1
   |
   v
ext4 filesystem
   |
   v
mounted at /srv/app-data
   |
   v
applications read/write files
```

## Step 2: Create a GPT partition table

⚠️ **DESTRUCTIVE OPERATION**

This changes the disk's partition metadata.

```bash
sudo parted /dev/sdb --script mklabel gpt
```

### What is GPT?

GPT stands for GUID Partition Table.

It is a modern partition-table format used to describe partitions on a disk.

## Step 3: Create the partition

Run:


Why start at `1MiB`?

It provides normal alignment space rather than beginning the partition at the very first disk sector.

# PHASE 5: Understand Mount Points

This concept causes confusion for many beginners.

Linux does not normally expose separate disks as:

```text
C:
D:
E:
```

Instead, filesystems are attached to the existing directory tree.

Before mounting:

```text
/
└── srv
    └── app-data
```

After mounting:

```text
/
└── srv
    └── app-data
          |
          +-- contents of /dev/sdb1
```

The directory becomes the access point for that filesystem.

## Step 3: Understand the fstab entry

The intended structure is:

```text
UUID=YOUR-UUID /srv/app-data ext4 defaults 0 2
```

Fields:

```text
UUID=...        filesystem identifier
/srv/app-data   mount point
ext4            filesystem type
defaults        standard mount options
0               dump field
2               filesystem check order
```

```bash
sudo nano /etc/fstab
```

Add:

```text
UUID=YOUR-ACTUAL-UUID /srv/app-data ext4 defaults 0 2
```

Do not write `YOUR-ACTUAL-UUID` literally.

# PHASE 10: LVM Foundations

Now we build the flexible storage layer.

The third lab disk is represented as:

```text
/dev/sdd
```

LVM introduces three core layers.

## Physical Volume

```text
PV
```

Storage device made available to LVM.

## Volume Group

```text
VG
```

A pool of storage assembled from one or more physical volumes.

## Logical Volume

```text
LV
```

A virtual block device allocated from the volume group's capacity.

Architecture:

```text
/dev/sdd
   |
   v
/dev/sdd1
   |
   v
Physical Volume
   |
   v
+-------------------------+
|        vg_app           |
|                         |
|   +---------+---------+ |
|   |         |         | |
|   v         v         | |
| lv_app    lv_logs     | |
|   |         |         | |
+---|---------|---------+-+
    |         |
    v         v
  ext4      ext4
    |         |
    v         v
/srv/lvm-app /srv/lvm-logs
```

```bash
#!/usr/bin/env bash

set -u

WARNING_THRESHOLD=80
CRITICAL_THRESHOLD=90

section() {
    echo
    echo "=================================================="
    echo "$1"
    echo "=================================================="
}

section "LINUX STORAGE HEALTH REPORT"

echo "Date: $(date)"
echo "Hostname: $(hostname)"

section "BLOCK DEVICES"

lsblk -o NAME,SIZE,TYPE,FSTYPE,FSVER,LABEL,MOUNTPOINTS

section "FILESYSTEM CAPACITY"

df -hT

section "INODE CAPACITY"

df -i

section "PROJECT MOUNTS"

for mountpoint in \
    /srv/app-data \
    /srv/archive \
    /srv/lvm-app \
    /srv/lvm-logs
do
    if findmnt -rn "$mountpoint" >/dev/null 2>&1; then
        echo "[OK] $mountpoint is mounted"
    else
        echo "[FAIL] $mountpoint is not mounted"
    fi
done

section "FILESYSTEM USAGE ALERTS"

df -P -x tmpfs -x devtmpfs |
awk -v warn="$WARNING_THRESHOLD" -v crit="$CRITICAL_THRESHOLD" '
NR > 1 {
    usage=$5
    gsub("%","",usage)

    if (usage >= crit)
        printf "[CRITICAL] %s is %s%% full\n", $6, usage
    else if (usage >= warn)
        printf "[WARNING] %s is %s%% full\n", $6, usage
    else
        printf "[OK] %s is %s%% full\n", $6, usage
}'

section "LVM PHYSICAL VOLUMES"

if command -v pvs >/dev/null 2>&1; then
    pvs
else
    echo "LVM tools not installed."
fi

section "LVM VOLUME GROUPS"

if command -v vgs >/dev/null 2>&1; then
    vgs
fi

section "LVM LOGICAL VOLUMES"

if command -v lvs >/dev/null 2>&1; then
    lvs
fi

section "PROJECT DIRECTORY USAGE"

for path in \
    /srv/app-data \
    /srv/archive \
    /srv/lvm-app \
    /srv/lvm-logs
do
    if [[ -d "$path" ]]; then
        du -sh "$path" 2>/dev/null || true
    fi
done

section "FSTAB VALIDATION"

findmnt --verify --verbose || true

section "REPORT COMPLETE"
```

Save.

Make executable:

```bash
chmod +x scripts/storage-health.sh
```

Run:


# 15. Security

Storage administration is also a security responsibility.

## Principle 1: Do not use `chmod 777`

If an application cannot write, diagnose:

```text
owner
group
mode
ACL
mount state
read-only status
application identity
```

Do not remove all access control.

---

## Principle 2: Protect mount configuration

Inspect:

```bash
ls -l /etc/fstab
```

Ordinary users should not be able to modify system mount configuration.

---

## Principle 3: Restrict sensitive storage

For example, archive storage may require:

```bash
sudo chown root:storage-team /srv/archive
sudo chmod 2750 /srv/archive
```

This provides more restrictive access than application data.

---

## Principle 4: Understand mount options

Mount options can affect behavior and security.

Examples include:

```text
ro
rw
noexec
nosuid
nodev
```

Do not apply these blindly.

For example, `noexec` may be useful for some data filesystems but could break legitimate applications that need to execute files from that filesystem.

Security controls must match workload requirements.

# Alternative Combined Operation

LVM can combine logical-volume extension with supported filesystem resizing using:


The `-r` requests filesystem resizing along with the logical-volume resize.

You manually separated the steps first because understanding the two layers is important.

# Automated Validation Script

Create:

```bash
cd ~/linux-storage-management
nano tests/storage-validation.sh
```

Add:

```bash
#!/usr/bin/env bash

set -u

PASS=0
FAIL=0

pass() {
    echo "[PASS] $1"
    PASS=$((PASS + 1))
}

fail() {
    echo "[FAIL] $1"
    FAIL=$((FAIL + 1))
}

check_mount() {
    local mountpoint="$1"

    if findmnt -rn "$mountpoint" >/dev/null 2>&1; then
        pass "$mountpoint is mounted"
    else
        fail "$mountpoint is not mounted"
    fi
}

echo "=============================================="
echo " Linux Storage Management Validation"
echo "=============================================="

check_mount "/srv/app-data"
check_mount "/srv/archive"
check_mount "/srv/lvm-app"
check_mount "/srv/lvm-logs"

if findmnt --verify >/dev/null 2>&1; then
    pass "/etc/fstab validation passed"
else
    fail "/etc/fstab validation failed"
fi

if pvs 2>/dev/null | grep -q 'vg_app'; then
    pass "LVM physical volume belongs to vg_app"
else
    fail "Expected LVM physical volume not found"
fi

if vgs vg_app >/dev/null 2>&1; then
    pass "Volume group vg_app exists"
else
    fail "Volume group vg_app is missing"
fi

if lvs vg_app/lv_app >/dev/null 2>&1; then
    pass "Logical volume lv_app exists"
else
    fail "Logical volume lv_app is missing"
fi

if lvs vg_app/lv_logs >/dev/null 2>&1; then
    pass "Logical volume lv_logs exists"
else
    fail "Logical volume lv_logs is missing"
fi

APP_FS=$(findmnt -rn -o FSTYPE /srv/app-data 2>/dev/null || true)

if [[ "$APP_FS" == "ext4" ]]; then
    pass "/srv/app-data uses ext4"
else
    fail "/srv/app-data expected ext4, found: ${APP_FS:-none}"
fi

LVM_APP_FS=$(findmnt -rn -o FSTYPE /srv/lvm-app 2>/dev/null || true)

if [[ "$LVM_APP_FS" == "ext4" ]]; then
    pass "/srv/lvm-app uses ext4"
else
    fail "/srv/lvm-app expected ext4, found: ${LVM_APP_FS:-none}"
fi

if touch /srv/app-data/.storage-write-test 2>/dev/null; then
    rm -f /srv/app-data/.storage-write-test
    pass "Current user can write to /srv/app-data"
else
    fail "Current user cannot write to /srv/app-data"
fi

echo
echo "Passed: $PASS"
echo "Failed: $FAIL"

if (( FAIL > 0 )); then
    exit 1
fi

exit 0
```

Make executable:

```bash
chmod +x tests/storage-validation.sh
```

Run as your normal user after group membership is active:

```bash
./tests/storage-validation.sh
```

Do not change legitimate configuration merely to make the test pass.

Investigate failures.

# 23. Interview Preparation

## What is a block device?

A block device is a storage device that Linux accesses in blocks, such as a disk, partition, or logical volume.

---

## What is the difference between `/dev/sdb` and `/dev/sdb1`?

Typically:

```text
/dev/sdb
```

represents the entire disk.

```text
/dev/sdb1
```

represents the first partition on that disk.

---

## What is a filesystem?

A filesystem defines how files, directories, metadata, and allocation are organized on a storage device.

Examples include:

```text
ext4
XFS
Btrfs
```

This project uses ext4.

---

## What is mounting?

Mounting attaches a filesystem to a location in Linux's directory hierarchy.

For example:

```text
/dev/sdb1
```

can be mounted at:

```text
/srv/app-data
```

---

## What is `/etc/fstab`?

`/etc/fstab` describes filesystems that the system should know how to mount using defined devices or identifiers, mount points, filesystem types, and options.

---

## Why use UUID instead of `/dev/sdb1`?

Device names can vary depending on hardware discovery and configuration.

A filesystem UUID identifies the filesystem itself and is generally more appropriate for persistent mount configuration.

---

## What does `lsblk` do?

It displays block devices and their relationships.

It is useful for understanding:

```text
disk
partition
LVM
filesystem
mount point
```

relationships.

---

## Difference between `df` and `du`?

`df` reports filesystem-level space usage.

`du` calculates space used by files and directories that it can traverse.

They answer different questions.

---

## What is LVM?

LVM is the Linux Logical Volume Manager.

It adds an abstraction layer between physical storage and filesystems, allowing storage to be pooled and allocated as logical volumes.

---

## Explain PV, VG and LV.

```text
PV = Physical Volume
VG = Volume Group
LV = Logical Volume
```

Conceptually:

```text
Physical storage
      ↓
     PV
      ↓
storage pool = VG
      ↓
virtual block device = LV
```

A filesystem can then be created on the LV.

---

## Why leave free space in a volume group?

It provides capacity that can later be allocated to logical volumes when workloads grow.

---

## You extended an LV but `df -h` still reports the old capacity. Why?

The block device may have grown while the filesystem has not.

For ext4, the filesystem can be expanded using an appropriate operation such as:

```bash
resize2fs /dev/vg_app/lv_app
```

Alternatively, supported LVM operations can request filesystem resizing with `lvextend -r`.

---

## What happens when a filesystem reaches 100%?

Applications may fail to:

* Write files
* Create logs
* Save data
* Create temporary files
* Complete updates
* Operate correctly

A full filesystem can become an availability incident.

---

## Can a filesystem have free GB but still refuse new files?

Yes.

One cause is inode exhaustion.

Check:

```bash
df -i
```

---

## Why shouldn't you run `chmod 777` when an application receives Permission Denied?

Because it removes meaningful access restrictions without identifying the actual cause.

Investigate ownership, groups, permission bits, ACLs, mount options, and application identity.

---

## Scenario: Server reboots and application storage disappears. What do you check?

A strong investigation:

```text
1. lsblk
2. lsblk -f
3. blkid
4. findmnt
5. /etc/fstab
6. findmnt --verify
7. mount -a
8. system logs
```

Determine whether:

* Disk exists.
* Partition exists.
* Filesystem exists.
* UUID matches.
* Mount point exists.
* fstab is correct.
* Mount operation succeeds.

---

## Scenario: `/srv/app-data` looks empty. Is the data lost?

Not necessarily.

First check:

```bash
findmnt /srv/app-data
```

The filesystem may simply not be mounted.

---

## Scenario: `umount` says target is busy.

Identify processes using the mount:

```bash
sudo fuser -vm /srv/archive
```

A shell whose working directory is inside the mount can keep it busy.

---

## Scenario: LVM volume group has no free space.

Check:

```bash
pvs
vgs
lvs
```

If additional capacity is required, one option is:

```text
attach disk
   ↓
create partition
   ↓
pvcreate
   ↓
vgextend
   ↓
lvextend
   ↓
grow filesystem
```
