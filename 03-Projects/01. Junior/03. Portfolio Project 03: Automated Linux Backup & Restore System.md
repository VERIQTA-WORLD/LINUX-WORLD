# 12. Step-by-Step Implementation

# Phase 1: Understand the Backup Problem

Before creating scripts, understand what you are protecting.

A backup answers:

```text
Something was lost.
Can we recover an earlier copy?
```

Synchronization answers a different question:

```text
How do we make two locations match?
```

These are not identical.

Suppose:

```text
SOURCE
report.pdf
```

is accidentally deleted.

A synchronization process might propagate that deletion.

A backup system with retained historical versions may still contain yesterday's copy.

---

# Backup Terminology

## Backup

A separate recoverable copy of data.

## Restore

Returning backed-up data to a usable location.

## Retention

How long backup versions are kept.

## Integrity

Confidence that backup data has not unexpectedly changed or become corrupted.

## RPO

Recovery Point Objective.

Conceptually:

```text
How much recent data could the organization tolerate losing?
```

If backups occur every 24 hours, a failure immediately before the next backup could potentially mean losing nearly 24 hours of changes.

## RTO

Recovery Time Objective.

Conceptually:

```text
How quickly must the service/data be restored?
```

This Junior project does not implement enterprise RPO/RTO guarantees.

You are learning the concepts.

# Phase 4: Perform the First Backup Manually

Before automating anything, understand the manual process.

Run:

```bash
sudo tar -czf /var/backups/company-app/manual-backup.tar.gz \
-C /srv company-app
```

Let's break this down.

```text
tar
```

creates or manipulates archives.

```text
-c
```

creates a new archive.

```text
-z
```

compresses it with gzip.

```text
-f
```

specifies the archive filename.

```text
-C /srv
```

changes tar's working directory to `/srv` before adding files.

```text
company-app
```

is the directory being archived.

Using `-C` avoids embedding a long absolute-style path into the archive.

# Phase 9: Build the Production-Style Lab Script

Replace the contents of:

```text
scripts/backup.sh
```

with:

```bash
#!/usr/bin/env bash

set -uo pipefail

PROJECT_DIR="${PROJECT_DIR:-$HOME/linux-backup-restore-system}"
CONFIG_FILE="$PROJECT_DIR/config/backup.conf"

if [[ ! -r "$CONFIG_FILE" ]]; then
    echo "ERROR: Cannot read configuration file: $CONFIG_FILE" >&2
    exit 1
fi

# shellcheck source=/dev/null
source "$CONFIG_FILE"

TIMESTAMP=$(date '+%Y%m%d_%H%M%S')
HOSTNAME_SHORT=$(hostname -s)

BACKUP_NAME="company-app_${HOSTNAME_SHORT}_${TIMESTAMP}.tar.gz"
BACKUP_FILE="$BACKUP_DIR/$BACKUP_NAME"
CHECKSUM_FILE="$BACKUP_FILE.sha256"

log() {
    local level="$1"
    shift
    local message="$*"

    printf '%s [%s] %s\n' \
        "$(date '+%Y-%m-%d %H:%M:%S')" \
        "$level" \
        "$message" | tee -a "$LOG_FILE"
}

fail() {
    log "ERROR" "$*"
    exit 1
}

if [[ "$EUID" -ne 0 ]]; then
    echo "ERROR: Run this backup script with sudo/root privileges." >&2
    exit 1
fi

mkdir -p "$(dirname "$LOG_FILE")"

log "INFO" "Starting backup job."

[[ -d "$SOURCE_DIR" ]] ||
    fail "Source directory does not exist: $SOURCE_DIR"

[[ -r "$SOURCE_DIR" ]] ||
    fail "Source directory is not readable: $SOURCE_DIR"

mkdir -p "$BACKUP_DIR" ||
    fail "Unable to create backup directory: $BACKUP_DIR"

[[ -w "$BACKUP_DIR" ]] ||
    fail "Backup directory is not writable: $BACKUP_DIR"

SOURCE_PARENT=$(dirname "$SOURCE_DIR")
SOURCE_NAME=$(basename "$SOURCE_DIR")

log "INFO" "Source: $SOURCE_DIR"
log "INFO" "Destination: $BACKUP_FILE"

if tar -czf "$BACKUP_FILE" \
    -C "$SOURCE_PARENT" \
    "$SOURCE_NAME"; then
    log "INFO" "Archive creation completed."
else
    rm -f "$BACKUP_FILE"
    fail "Archive creation failed."
fi

if [[ ! -s "$BACKUP_FILE" ]]; then
    rm -f "$BACKUP_FILE"
    fail "Backup archive is missing or empty."
fi

if (
    cd "$BACKUP_DIR" &&
    sha256sum "$BACKUP_NAME" > "$BACKUP_NAME.sha256"
); then
    log "INFO" "Checksum created: $CHECKSUM_FILE"
else
    rm -f "$CHECKSUM_FILE"
    fail "Checksum creation failed."
fi

if (
    cd "$BACKUP_DIR" &&
    sha256sum -c "$BACKUP_NAME.sha256" >/dev/null
); then
    log "INFO" "Checksum verification passed."
else
    fail "Checksum verification failed."
fi

if tar -tzf "$BACKUP_FILE" >/dev/null; then
    log "INFO" "Archive readability test passed."
else
    fail "Archive readability test failed."
fi

log "INFO" "Applying retention policy: $RETENTION_DAYS days."

find "$BACKUP_DIR" \
    -maxdepth 1 \
    -type f \
    -name 'company-app_*.tar.gz' \
    -mtime "+$RETENTION_DAYS" \
    -print \
    -delete >> "$LOG_FILE" 2>&1

find "$BACKUP_DIR" \
    -maxdepth 1 \
    -type f \
    -name 'company-app_*.tar.gz.sha256' \
    -mtime "+$RETENTION_DAYS" \
    -print \
    -delete >> "$LOG_FILE" 2>&1

BACKUP_SIZE=$(du -h "$BACKUP_FILE" | awk '{print $1}')

log "INFO" "Backup size: $BACKUP_SIZE"
log "INFO" "Backup completed successfully."
log "INFO" "Backup file: $BACKUP_FILE"

exit 0
```

# Phase 10: Understand the Script

Do not move forward without understanding it.

## `set -uo pipefail`

```text
-u
```

treats use of unset variables as errors.

```text
-o pipefail
```

helps pipelines report failures rather than silently reporting only the final command's status.

We deliberately do not use `set -e` as a substitute for explicit error handling. The script checks important operations directly.

---

## `source "$CONFIG_FILE"`

This loads the variables defined in:

```text
config/backup.conf
```

Again, only source configuration you control.

---

## Timestamp

```bash
TIMESTAMP=$(date '+%Y%m%d_%H%M%S')
```

A run might produce:

```text
20260924_051500
```

Your actual timestamp will depend on when the script runs.

---

## Hostname

```bash
HOSTNAME_SHORT=$(hostname -s)
```

Including the hostname helps distinguish backups when a design later expands to multiple systems.

---

## `log()`

The logging function gives every event:

```text
timestamp
severity
message
```

Example:

```text
2026-09-24 05:15:00 [INFO] Starting backup job.
```

Do not expect this exact timestamp.

---

## `fail()`

Instead of silently continuing after a serious error:

```bash
fail "Archive creation failed."
```

logs the failure and returns a non-zero exit code.

This matters for automation.

# 13. Configuration

# Phase 12: Understand Retention

Our configuration says:

```text
RETENTION_DAYS=7
```

The script searches only:

```text
/var/backups/company-app
```

and only files matching:

```text
company-app_*.tar.gz
company-app_*.tar.gz.sha256
```

This is deliberate.

A dangerous retention command would be something vague like:

```text
find /var/backups -type f -delete
```

Never build deletion automation without narrow boundaries.

---

# Safe Retention Principle

Retention should identify:

```text
WHERE?
```

```text
WHAT FILE PATTERN?
```

```text
HOW OLD?
```

```text
WHAT ACTION?
```

before deletion occurs.

# Understand the Cron Schedule

```text
0 2 * * *
```

means approximately:

```text
minute   0
hour     2
day      every
month    every
weekday  every
```

# Build the Restore Script

Return:

```bash

```

Open:

```bash

```

Add:

```bash
#!/usr/bin/env bash

set -uo pipefail

if [[ "$EUID" -ne 0 ]]; then
    echo "ERROR: Run this restore script with sudo/root privileges." >&2
    exit 1
fi

if [[ $# -lt 2 ]]; then
    echo "Usage:"
    echo "  $0 BACKUP_FILE RESTORE_DIRECTORY"
    exit 1
fi

BACKUP_FILE="$1"
RESTORE_DIR="$2"
CHECKSUM_FILE="$BACKUP_FILE.sha256"

log() {
    printf '%s [RESTORE] %s\n' \
        "$(date '+%Y-%m-%d %H:%M:%S')" \
        "$*"
}

if [[ ! -f "$BACKUP_FILE" ]]; then
    echo "ERROR: Backup file not found: $BACKUP_FILE" >&2
    exit 1
fi

if [[ ! -f "$CHECKSUM_FILE" ]]; then
    echo "ERROR: Checksum file not found: $CHECKSUM_FILE" >&2
    exit 1
fi

BACKUP_DIR=$(dirname "$BACKUP_FILE")
BACKUP_NAME=$(basename "$BACKUP_FILE")

log "Verifying checksum."

if ! (
    cd "$BACKUP_DIR" &&
    sha256sum -c "$(basename "$CHECKSUM_FILE")"
); then
    echo "ERROR: Backup integrity verification failed." >&2
    exit 1
fi

log "Checksum passed."

log "Testing archive readability."

if ! tar -tzf "$BACKUP_FILE" >/dev/null; then
    echo "ERROR: Archive cannot be read." >&2
    exit 1
fi

log "Archive test passed."

mkdir -p "$RESTORE_DIR"

log "Restoring $BACKUP_NAME to $RESTORE_DIR"

if tar -xzf "$BACKUP_FILE" -C "$RESTORE_DIR"; then
    log "Restore completed."
else
    echo "ERROR: Restore failed." >&2
    exit 1
fi

log "Review restored files before replacing live data."

exit 0
```

Make executable:

```bash
chmod +x scripts/restore.sh
```

# 23. Interview Preparation

## Basic Question: What is a backup?

A backup is a separate recoverable copy of data created so that information can be restored after loss, corruption, deletion, or another failure.

---

## What is the difference between backup and synchronization?

Synchronization attempts to keep locations aligned.

A backup preserves recoverable copies, often including historical versions.

A destructive change can propagate through synchronization, while a retained backup may still provide an earlier copy.

---

## What does `tar -czf` mean?

```text
-c    create archive
-z    gzip compression
-f    archive filename follows
```

---

## Why did you use timestamps?

They make each backup identifiable and prevent normal scheduled backups from repeatedly overwriting the same archive.

---

## Why generate SHA-256 checksums?

Checksums provide a way to detect whether the backup archive has changed since the digest was created.

They are an integrity check, not encryption.

---

## Does a valid checksum prove the backup contains the right data?

No.

It proves the file matches the recorded checksum.

You must still inspect and test the archive contents and perform restoration testing.

---

## Why test restoration?

Because successful archive creation does not guarantee useful recovery.

The purpose of a backup is restoration.

---

## What is retention?

Retention determines how long backup versions are preserved before they become eligible for removal.

---

## Why is retention necessary?

Without retention:

```text
backups
  ↓
more backups
  ↓
more backups
  ↓
disk fills
  ↓
future backups fail
```

Retention controls storage growth while preserving the versions required by policy.

---

## What is RPO?

Recovery Point Objective describes the acceptable amount of data loss measured in time.

---

## What is RTO?

Recovery Time Objective describes how quickly a system or data must be restored after disruption.

---

## Why is storing backups on the same server insufficient?

A complete server, disk, filesystem, ransomware, or infrastructure failure could affect both the source and the backup.

Production designs should include independent copies.

---

## Why restore to a temporary location first?

It lets you inspect and validate recovered data before overwriting live data.

This reduces the risk of making the incident worse.

---

## Why use absolute paths with cron?

Cron runs with a limited environment and does not necessarily use the same working directory or environment as your interactive shell.

Absolute paths reduce ambiguity.

## Deep-Dive Question

**Why isn't RAID a backup?**

RAID can improve availability or tolerate certain disk failures depending on its design.

It does not inherently provide historical recovery from:

* Accidental deletion.
* Application corruption.
* Malicious modification.
* Ransomware.
* Administrative mistakes.

Availability and backup solve different problems.
