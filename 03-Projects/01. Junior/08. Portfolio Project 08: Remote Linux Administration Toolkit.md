# 08. Architecture

# 8.1 Understand SSH Before Building the Toolkit

SSH stands for:

**Secure Shell**

It provides encrypted remote communication between systems.

Basic model:

```text
SSH CLIENT                               SSH SERVER
admin01                                  server01
   |                                        |
   | TCP connection                         |
   |--------------------------------------->|
   |                                        |
   | Server host key                        |
   |<---------------------------------------|
   |                                        |
   | Verify server identity                 |
   |                                        |
   | Authentication request                 |
   |--------------------------------------->|
   |                                        |
   | Password or public-key authentication  |
   |                                        |
   | Encrypted session                      |
   |<======================================>|
```

The administration machine runs:

```text
SSH client
```

The managed server runs:

```text
SSH server daemon
sshd
```

---

# 8.2 Authentication vs Encryption

These are related but different concepts.

**Encryption** protects communication in transit.

**Authentication** answers questions such as:

```text
Is this really the intended server?

Is this client/user allowed to connect?
```

SSH performs both.

---

# 8.3 Two Different Key Concepts

Beginners often confuse:

```text
User SSH key
```

with:

```text
Server host key
```

They solve different problems.

### User Key

Used to authenticate the user to the server.

```text
private key → remains with administrator

public key → installed on server
```

### Host Key

Used to help the client verify the identity of the SSH server.

The client records trusted host-key information in:

```text
~/.ssh/known_hosts
```

Do not treat these as interchangeable.

---

# 8.4 Key-Based Authentication

Conceptually:

```text
admin01
│
├── PRIVATE KEY
│   ~/.ssh/id_ed25519
│
└── PUBLIC KEY
    ~/.ssh/id_ed25519.pub
              |
              | copy public key
              v
          server01
              |
              v
~/.ssh/authorized_keys
```

The private key must remain private.

**Never copy the private key to the managed server.**

---

# 8.5 Remote Administration Flow

A reliable toolkit should not immediately run administrative commands.

Use:

```text
Load inventory
      |
      v
Validate host
      |
      v
Attempt SSH connection
      |
   +--+--+
   |     |
 FAIL   PASS
   |     |
   v     v
Record  Execute operation
failure      |
             v
        Capture status
             |
        +----+----+
        |         |
      FAIL       PASS
        |         |
        +----+----+
             |
             v
            Log
             |
             v
      Continue next host
```

This is much safer than assuming every machine is available.

# PHASE 3: Verify Network Connectivity

From `admin01`:

```bash
ping -c 3 192.168.56.21
```

Then:

```bash
ping -c 3 192.168.56.22
```

### Command explanation

`ping`

Tests ICMP reachability.

`-c 3`

Sends three requests and stops.

### Expected result

Representative:

```text
64 bytes from 192.168.56.21 ...
```

### Important

Successful ping means:

> ICMP communication succeeded.

It does **not** prove SSH works.

Likewise, failed ping does not always prove the server is unreachable because ICMP may be blocked while SSH remains allowed.

This distinction matters.

# PHASE 8: Test Password-Based SSH First

From `admin01`:

```bash
ssh remoteadmin@192.168.56.21
```

On first connection, SSH may display a host authenticity prompt.

You may see something similar to:

```text
The authenticity of host ... can't be established.
...

```

Do not develop the habit of blindly typing:

```text

```

The prompt exists because SSH is asking whether you trust the server identity represented by that host key.

In a real environment, verify the fingerprint using a trusted source.

# PHASE 14: Understand SSH Agent

If your private key uses a passphrase, repeatedly entering it can make automation inconvenient.

`ssh-agent` can hold unlocked key material for the current session.

Start if necessary:

```bash
eval "$(ssh-agent -s)"
```

Add:

```bash
ssh-add ~/.ssh/veriqta_project08
```

List:

```bash
ssh-add -l
```

This allows you to use a passphrase-protected key without typing the passphrase for every connection during the agent session.

Do not confuse:

```text
no passphrase
```

with:

```text
ssh-agent
```

They are different approaches.

---

# PHASE 15: Create SSH Client Configuration

Typing this repeatedly:

```bash
ssh -i ~/.ssh/veriqta_project08 remoteadmin@192.168.56.21
```

is unnecessary.

Edit:

```bash
nano ~/.ssh/config
```

Add:

```sshconfig
Host server01
    HostName 192.168.56.21
    User remoteadmin
    IdentityFile ~/.ssh/veriqta_project08
    IdentitiesOnly yes
    ConnectTimeout 5

Host server02
    HostName 192.168.56.22
    User remoteadmin
    IdentityFile ~/.ssh/veriqta_project08
    IdentitiesOnly yes
    ConnectTimeout 5
```

Replace addresses with actual lab addresses.

Protect:

```bash
chmod 600 ~/.ssh/config
```

Now connect:

```bash
ssh server01
```

And:

```bash
ssh server02
```

This is significantly cleaner.

# PHASE 16: Test Batch Mode

Automation should not hang waiting for an interactive password.

Test:

```bash
ssh \
-o BatchMode=yes \
-o ConnectTimeout=5 \
server01 \
'hostname'
```

Expected:

```text
server01
```

### Why `BatchMode=yes`?

It prevents interactive password/passphrase prompts.

For automation, this is important.

If authentication cannot complete non-interactively, SSH fails instead of waiting for input.

If using a passphrase-protected key, ensure the key is loaded into `ssh-agent`.

# PHASE 18: Understand Quoting

Compare:

```bash
ssh server01 "echo $HOME"
```

with:

```bash
ssh server01 'echo $HOME'
```

With double quotes, your local shell may expand `$HOME` before SSH sends the command.

With single quotes, `$HOME` is sent to the remote shell for expansion.

Check local:

```bash
echo "$HOME"
```

Then:

```bash
ssh server01 'echo "$HOME"'
```

This concept becomes extremely important when writing remote automation.

# Important rsync Trailing-Slash Lesson

These are not conceptually identical:

```bash
rsync -av source/ destination/
```

and:

```bash
rsync -av source destination/
```

The trailing slash affects whether you copy:

```text
contents of source
```

or:

```text
source directory itself
```

Always use `--dry-run` before destructive or large synchronization operations.

# PHASE 30: Build the Main Remote Administration Toolkit

Create:

```bash
nano ~/remote-linux-admin-toolkit/scripts/remote-admin.sh
```

Add:

```bash
#!/usr/bin/env bash

set -u
set -o pipefail

PROJECT_DIR="${PROJECT_DIR:-$HOME/remote-linux-admin-toolkit}"

HOSTS_FILE="$PROJECT_DIR/config/hosts.conf"
CONFIG_FILE="$PROJECT_DIR/config/toolkit.conf"

if [[ ! -r "$HOSTS_FILE" ]]; then
    echo "ERROR: Cannot read host inventory: $HOSTS_FILE" >&2
    exit 2
fi

if [[ ! -r "$CONFIG_FILE" ]]; then
    echo "ERROR: Cannot read configuration: $CONFIG_FILE" >&2
    exit 2
fi

# shellcheck disable=SC1090
source "$CONFIG_FILE"

LOG_FILE="$PROJECT_DIR/$LOG_RELATIVE_PATH"
REPORT_DIR="$PROJECT_DIR/$REPORT_RELATIVE_DIR"

mkdir -p "$(dirname "$LOG_FILE")"
mkdir -p "$REPORT_DIR"

TIMESTAMP="$(date '+%Y-%m-%d %H:%M:%S')"

PASS_COUNT=0
FAIL_COUNT=0

log() {
    local level="$1"
    local host="$2"
    local action="$3"
    local message="$4"

    printf '%s | %-7s | %-12s | %-18s | %s\n' \
        "$TIMESTAMP" \
        "$level" \
        "$host" \
        "$action" \
        "$message" |
        tee -a "$LOG_FILE"
}

load_hosts() {

    while IFS='|' read -r host role; do

        [[ -z "$host" ]] && continue
        [[ "$host" == \#* ]] && continue

        printf '%s|%s\n' "$host" "$role"

    done < "$HOSTS_FILE"
}

ssh_check() {
    local host="$1"

    ssh \
        -o BatchMode=yes \
        -o ConnectTimeout="$SSH_CONNECT_TIMEOUT" \
        "$host" \
        'true' \
        >/dev/null 2>&1
}

check_hosts() {

    echo
    echo "============================================================"
    echo " SSH CONNECTIVITY CHECK"
    echo "============================================================"

    while IFS='|' read -r host role; do

        echo
        echo "Checking: $host ($role)"

        if ssh_check "$host"; then

            log \
                "PASS" \
                "$host" \
                "ssh-check" \
                "SSH connection successful"

            PASS_COUNT=$((PASS_COUNT + 1))

        else

            log \
                "FAIL" \
                "$host" \
                "ssh-check" \
                "SSH connection failed"

            FAIL_COUNT=$((FAIL_COUNT + 1))
        fi

    done < <(load_hosts)
}

show_inventory() {

    echo
    echo "============================================================"
    echo " MANAGED HOST INVENTORY"
    echo "============================================================"
    echo

    printf '%-15s %-20s\n' "HOST" "ROLE"
    printf '%-15s %-20s\n' "----" "----"

    while IFS='|' read -r host role; do
        printf '%-15s %-20s\n' "$host" "$role"
    done < <(load_hosts)
}

collect_health() {

    local health_script="$PROJECT_DIR/scripts/server-health.sh"

    if [[ ! -r "$health_script" ]]; then
        echo "ERROR: Missing health script: $health_script" >&2
        return 1
    fi

    echo
    echo "============================================================"
    echo " COLLECTING SERVER HEALTH"
    echo "============================================================"

    while IFS='|' read -r host role; do

        echo
        echo "Processing $host..."

        if ! ssh_check "$host"; then

            log \
                "FAIL" \
                "$host" \
                "health-report" \
                "Skipped because SSH check failed"

            FAIL_COUNT=$((FAIL_COUNT + 1))
            continue
        fi

        local report
        report="$REPORT_DIR/${host}_health_$(date '+%Y%m%d_%H%M%S').txt"

        if timeout "$SSH_COMMAND_TIMEOUT" \
            ssh \
            -o BatchMode=yes \
            -o ConnectTimeout="$SSH_CONNECT_TIMEOUT" \
            "$host" \
            'bash -s' \
            < "$health_script" \
            > "$report" 2>&1; then

            log \
                "PASS" \
                "$host" \
                "health-report" \
                "Report saved: $report"

            PASS_COUNT=$((PASS_COUNT + 1))

        else

            log \
                "FAIL" \
                "$host" \
                "health-report" \
                "Remote health command failed or timed out"

            FAIL_COUNT=$((FAIL_COUNT + 1))
        fi

    done < <(load_hosts)
}

show_summary() {

    echo
    echo "============================================================"
    echo " EXECUTION SUMMARY"
    echo "============================================================"
    echo
    echo "Successful operations: $PASS_COUNT"
    echo "Failed operations:     $FAIL_COUNT"

    if (( FAIL_COUNT > 0 )); then
        return 1
    fi

    return 0
}

usage() {

    cat <<'EOF'
Usage:
  remote-admin.sh inventory
  remote-admin.sh check
  remote-admin.sh health

Commands:
  inventory   Display managed hosts
  check       Test SSH connectivity
  health      Collect remote health reports
EOF
}

main() {

    local action="${1:-}"

    case "$action" in

        inventory)
            show_inventory
            ;;

        check)
            check_hosts
            show_summary
            ;;

        health)
            collect_health
            show_summary
            ;;

        *)
            usage
            exit 2
            ;;
    esac
}

main "$@"
```

# PHASE 38: Build Remote Command Capability Safely

There is a major security consideration here.

A tempting implementation is:

```bash
ssh "$host" "$*"
```

This allows arbitrary shell strings and creates quoting and command-injection complexity.

For a junior toolkit, use **predefined operations** rather than accepting arbitrary unvalidated remote commands.

Add operations such as:

```text
hostname
uptime
disk
memory
failed-services
kernel
```

Create:

```bash
nano ~/remote-linux-admin-toolkit/scripts/run-check.sh
```

Add:

```bash
#!/usr/bin/env bash

set -u

PROJECT_DIR="${PROJECT_DIR:-$HOME/remote-linux-admin-toolkit}"
HOSTS_FILE="$PROJECT_DIR/config/hosts.conf"

ACTION="${1:-}"

case "$ACTION" in

    hostname)
        REMOTE_COMMAND='hostname'
        ;;

    uptime)
        REMOTE_COMMAND='uptime'
        ;;

    disk)
        REMOTE_COMMAND='df -h /'
        ;;

    memory)
        REMOTE_COMMAND='free -h'
        ;;

    failed-services)
        REMOTE_COMMAND='systemctl --failed --no-pager'
        ;;

    kernel)
        REMOTE_COMMAND='uname -r'
        ;;

    *)
        echo "Usage: $0 {hostname|uptime|disk|memory|failed-services|kernel}"
        exit 2
        ;;
esac

while IFS='|' read -r host role; do

    [[ -z "$host" ]] && continue
    [[ "$host" == \#* ]] && continue

    echo
    echo "============================================================"
    echo "$host ($role)"
    echo "============================================================"

    if ! ssh \
        -o BatchMode=yes \
        -o ConnectTimeout=5 \
        "$host" \
        "$REMOTE_COMMAND"; then

        echo "[FAIL] Remote command failed on $host"
    fi

done < "$HOSTS_FILE"
```

```bash

~/remote-linux-admin-toolkit/scripts/run-check.sh
```

Then:

```bash

```

Then:

# PHASE 39: Add Connection Timeouts

Without timeouts:

```text
server unavailable
       ↓
SSH waits
       ↓
```

```bash

```

# PHASE 40: Add Command Timeout

Connection timeout and command timeout are different.

A server might accept SSH immediately but then execute a command that hangs.

Example:

```text
SSH connects
    ↓
remote command starts
    ↓
command never returns
```

Use GNU `timeout` around SSH:

```bash
timeout 30 \
ssh \
-o BatchMode=yes \
-o ConnectTimeout=5 \
server01 \
'COMMAND'
```

The main health-collection script already demonstrates this.

Bad automation:

```text

```

Better:

```text
server01 → PASS
server02 → FAIL → record failure
server03 → continue
server04 → continue
        ↓
final summary
```

This pattern appears in the toolkit.

# 15. Security

Remote administration is powerful because one machine can control many others.

That also makes it security-sensitive.

---

# 15.1 Protect the Private Key

Check:

```bash
stat -c '%A %a %n' \
~/.ssh/veriqta_project08
```

Expected:

```text
-rw------- 600 ...
```

Correct:

```bash
chmod 600 ~/.ssh/veriqta_project08
```

---

# 15.2 Never Copy the Private Key to Managed Servers

Correct:

```text
admin01
PRIVATE KEY stays here

server01
PUBLIC KEY only

server02
PUBLIC KEY only
```

Incorrect:

```text
server01
id_ed25519 private key
```

---

# 15.3 Protect SSH Configuration

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/config
```

---

# 15.4 Protect authorized_keys

On managed servers:

```bash
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
```

Ownership:

```bash
ls -ld ~/.ssh
ls -l ~/.ssh/authorized_keys
```

Both should belong to the remote user.

---

# 15.5 Never Disable Host-Key Verification for Convenience

Do **not** build your toolkit around:

```bash
-o StrictHostKeyChecking=no
```

That weakens an important server-identity control.

Instead, establish and verify host keys properly.

---

# 15.6 Never Commit Private Keys

Create:

```bash
nano ~/remote-linux-admin-toolkit/.gitignore
```

Add:

```gitignore
# SSH private keys
*.pem
*.key
id_rsa
id_ed25519
veriqta_project08

# Runtime logs
logs/*.log

# Generated reports
reports/*.txt

# Sensitive evidence
evidence/*.txt
evidence/*.log

# Temporary files
*.tmp
*.backup
```

Your SSH key is outside the repository anyway, but defense in depth is useful.

---

# 15.7 Do Not Put Passwords in Scripts

Never:

```bash
PASSWORD="MyPassword123"
```

Do not build:

```bash
sshpass -p "$PASSWORD" ...
```

for this project.

Use SSH keys.

---

# 15.8 Avoid Root SSH Login

Use a normal administrative account:

```text
remoteadmin
```

Then elevate privileges deliberately when required.

This provides better separation than routinely logging in remotely as root.

---

# 15.9 Do Not Disable Password Authentication Yet

A common security-hardening recommendation is disabling SSH password authentication after keys are verified.

But do not combine that change casually with this project if it could lock the learner out.

Project 02 covers SSH hardening in greater depth.

For Project 08, the key goal is:

```text
Build and verify secure key-based administration.
```

Any password-authentication change should occur only after:

```text
console access exists
+
key authentication tested
+
recovery path understood
+
configuration validated
```

---

# 15.10 Understand Administrative Blast Radius

If `admin01` can access many servers:

```text
Compromise of admin01
          |
          v
Potential access to
multiple managed servers
```

Therefore the administration host and its private keys are high-value assets.

# PHASE 44: Build Toolkit Tests

Create:

Add:

```bash
#!/usr/bin/env bash

set -u

PROJECT_DIR="${PROJECT_DIR:-$HOME/remote-linux-admin-toolkit}"

HOSTS_FILE="$PROJECT_DIR/config/hosts.conf"
MAIN_SCRIPT="$PROJECT_DIR/scripts/remote-admin.sh"
HEALTH_SCRIPT="$PROJECT_DIR/scripts/server-health.sh"

PASS=0
FAIL=0

pass() {
    echo "[PASS] $1"
    PASS=$((PASS + 1))
}

fail() {
    echo "[FAIL] $1"
    FAIL=$((FAIL + 1))
}

echo "============================================================"
echo " VERIQTA REMOTE ADMIN TOOLKIT TESTS"
echo "============================================================"
echo

for command in ssh scp sftp rsync awk grep sed timeout flock; do

    if command -v "$command" >/dev/null 2>&1; then
        pass "$command available"
    else
        fail "$command unavailable"
    fi

done

if [[ -r "$HOSTS_FILE" ]]; then
    pass "Host inventory readable"
else
    fail "Host inventory unavailable"
fi

if [[ -x "$MAIN_SCRIPT" ]]; then
    pass "Main toolkit executable"
else
    fail "Main toolkit not executable"
fi

if [[ -x "$HEALTH_SCRIPT" ]]; then
    pass "Health script executable"
else
    fail "Health script not executable"
fi

while IFS='|' read -r host role; do

    [[ -z "$host" ]] && continue
    [[ "$host" == \#* ]] && continue

    echo
    echo "Testing $host ($role)"

    if ssh \
        -o BatchMode=yes \
        -o ConnectTimeout=5 \
        "$host" \
        'true' \
        >/dev/null 2>&1; then

        pass "$host SSH authentication"

    else

        fail "$host SSH authentication"
        continue
    fi

    REMOTE_HOSTNAME="$(
        ssh \
        -o BatchMode=yes \
        -o ConnectTimeout=5 \
        "$host" \
        'hostname' 2>/dev/null
    )"

    if [[ -n "$REMOTE_HOSTNAME" ]]; then
        pass "$host returned hostname: $REMOTE_HOSTNAME"
    else
        fail "$host hostname unavailable"
    fi

    if ssh \
        -o BatchMode=yes \
        "$host" \
        'command -v bash >/dev/null'; then

        pass "$host has Bash"
    else
        fail "$host Bash unavailable"
    fi

    if ssh \
        -o BatchMode=yes \
        "$host" \
        'systemctl is-system-running >/dev/null 2>&1 || true'; then

        pass "$host accepted systemd query"
    else
        fail "$host systemd query failed"
    fi

done < "$HOSTS_FILE"

echo
echo "============================================================"
echo " TEST SUMMARY"
echo "============================================================"
echo
echo "Passed: $PASS"
echo "Failed: $FAIL"

if (( FAIL > 0 )); then
    exit 1
fi

exit 0
```

# FAILURE LAB 9: Host-Key Mismatch

Instead, understand the scenario:

```text

```

Possible explanations include:

```text

DNS points elsewhere
configuration mistake
unexpected intermediary
security problem
```

The wrong response is:

```bash

```

followed immediately by blindly trusting the new key.

First verify why the identity changed.

Only after independently confirming the new server identity should stale host-key information be updated.

# 23. Interview Preparation

## What is SSH?

SSH is a protocol used for encrypted remote access and communication between systems.

---

## What is `sshd`?

`sshd` is the OpenSSH server daemon that accepts SSH connections.

---

## What port does SSH normally use?

TCP port:

```text
22
```

But it can be configured differently.

---

## Does successful ping prove SSH works?

No.

Ping typically tests ICMP reachability.

SSH requires the SSH service to be reachable over its configured TCP port.

---

## What is an SSH key pair?

A cryptographic key pair consisting of:

```text
private key
public key
```

The private key remains protected by the client.

The public key can be installed on authorized servers.

---

## Where are authorized SSH public keys commonly stored?

For a user:

```text
~/.ssh/authorized_keys
```

---

## Where does the client store known host keys?

Typically:

```text
~/.ssh/known_hosts
```

---

## What is the difference between a user key and host key?

User keys help authenticate a user to a server.

Host keys help clients verify the server's identity.

---

## Why should a private key use restrictive permissions?

Because the private key is authentication material and should not be readable by unauthorized users. OpenSSH also refuses some insecure private-key permission configurations.

---

## What does `ssh-copy-id` do?

It helps install a public SSH key into the remote user's authorized-key configuration.

---

## What does `BatchMode=yes` do?

It disables interactive authentication prompts.

This is useful for automation because failed authentication returns an error instead of waiting for password input.

---

## What does `ConnectTimeout` do?

It limits how long SSH waits while establishing the connection.

It does not necessarily limit the duration of the remote command after connection.

---

## Why use GNU `timeout` around SSH?

To place a time limit on the overall SSH command execution.

---

## What is SCP?

A secure file-copy mechanism using SSH transport.

---

## What is SFTP?

The SSH File Transfer Protocol, which provides an interactive or programmatic file-transfer interface over SSH.

---

## What is rsync?

A file synchronization utility that efficiently transfers and synchronizes file trees. It can use SSH as its transport.

---

## Why use `rsync --dry-run`?

To preview proposed synchronization changes before modifying the destination.

---

## Why does the trailing slash matter in rsync?

It changes whether rsync treats the source as the directory itself or the contents of that directory.

---

## Why use an inventory?

It separates the list of managed systems from automation logic.

Instead of hardcoding servers throughout scripts, the toolkit can read them from one source.

---

## Why should one unreachable host not necessarily stop the whole script?

Because other managed hosts may still be available and need to be checked.

The script should record the host-specific failure and continue where appropriate.

---

## What does `ssh -vvv` do?

Enables detailed SSH debugging output.

It is useful for investigating:

```text
configuration
host selection
key selection
authentication
connection establishment
```

---

## What does "connection refused" usually suggest?

The destination responded but the requested TCP port was not accepting the connection.

Possible causes include:

```text
service stopped
wrong port
listener absent
firewall behavior
```

---

## What does a connection timeout suggest?

Possible causes include:

```text
network path issue
firewall dropping traffic
wrong address
unreachable server
routing issue
```

Further evidence is required.

---

## What does `Permission denied (publickey)` mean?

SSH reached the authentication stage but the offered authentication was not accepted.

Potential causes include:

```text
wrong key
wrong username
missing public key
permissions
ownership
SSH configuration
```

---

## Why shouldn't you use `StrictHostKeyChecking=no` everywhere?

Because host-key verification helps detect unexpected server identity changes.

Blindly disabling it weakens that protection.

---

## Why should remote administration avoid root login where possible?

Using named administrative accounts with deliberate privilege elevation can provide stronger separation, accountability, and least-privilege opportunities.

---

## What is administrative blast radius?

The scope of systems or resources that could be affected if an administrative credential, key, host, or automation system is compromised or misused.

---

## Why can an administration workstation be highly sensitive?

Because it may contain credentials or keys capable of accessing many managed systems.

---

## Why is arbitrary remote command input dangerous?

Improperly constructed shell commands can create command-injection, quoting, and validation problems.

A restricted set of predefined operations is easier to secure.

---

## How would this architecture change at larger scale?

For a few servers:

```text
Bash
+
SSH
+
inventory
```

can be useful.

As the environment grows, you may need:

```text
configuration management
orchestration
centralized identity
secret management
role-based access
centralized logging
asset inventory
parallel execution
audit systems
```

Tools such as Ansible may become more appropriate for configuration and orchestration.

The lesson is not:

```text
Bash is bad.
```

The lesson is:

```text
Choose tooling appropriate to scale, complexity, risk, and repeatability.
```
