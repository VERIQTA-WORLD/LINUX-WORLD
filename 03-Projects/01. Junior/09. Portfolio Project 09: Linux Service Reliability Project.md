VERIQTA Labs operates a Linux application server.

The problem is that simply running an application from a terminal is not sufficient.


What happens when:

```text
The administrator closes the terminal?

The process crashes?

The server reboots?

The application exits unexpectedly?

A required directory disappears?

A configuration file becomes invalid?

Another service it depends on is unavailable?

```

A production-style Linux system needs a service manager.

On Ubuntu 24.04, that role is normally handled by:

```text
systemd
```

Your job is to transform manually executed applications into managed Linux services.

# 08. Architecture

## 8.1 What Is a Service?

A service is normally a program designed to operate in the background and provide some ongoing capability.

Examples include:

```text
Web server
Database
SSH server
Monitoring agent
API
Queue worker
Scheduler
Logging agent
Backup agent
```

Examples on Linux:

```text
nginx
ssh
cron
systemd-journald
```

---

## 8.2 What Is systemd?

systemd is a Linux system and service manager.

Among other responsibilities, it manages:

```text
System startup
Services
Dependencies
Sockets
Timers
Mounts
Targets
Logging integration
Process supervision
Shutdown
```

For this project, the focus is service management.

---

## 8.3 What Is a Unit?

systemd manages resources using **units**.

Unit types include:

```text
.service
.socket
.target
.timer
.mount
.automount
.path
.device
.slice
.scope
```

Examples:

```text
nginx.service
ssh.service
multi-user.target
apt-daily.timer
```

This project concentrates on:

```text
.service
```

units.

---

## 8.4 Unit File Architecture

A basic service unit resembles:

```ini
[Unit]
Description=Example Service
After=network.target

[Service]
Type=simple
User=example
ExecStart=/path/to/program
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

Conceptually:

```text
[Unit]
    ↓
Relationship to system and other units

[Service]
    ↓
How the process runs

[Install]
    ↓
How the unit participates in enablement
```

---

## 8.5 Service Lifecycle

```text
                    inactive
                        |
                     start
                        |
                        v
                    activating
                        |
                        v
                     active
                        |
            +-----------+-----------+
            |                       |
          stop                    process
            |                      exits
            v                       |
       deactivating                 v
            |                  failed/inactive
            v                       |
         inactive             Restart policy?
                                    |
                             +------+------+
                             |             |
                            YES            NO
                             |             |
                             v             v
                          restart       remains
                                         failed/
                                        inactive
```

The exact state transition depends on service type and exit reason.

## 8.6 Reliability Layers

A service being installed does not mean it is reliable.

Think in layers:

```text
Application exists
        ↓
Application runs manually
        ↓
Valid systemd unit exists
        ↓
systemd can start application
        ↓
Service runs as correct identity
        ↓
Permissions are correct
        ↓
Configuration is correct
        ↓
Service starts at boot
        ↓
Failure is detected
        ↓
Recovery policy is appropriate
        ↓
Logs explain failure
        ↓
Health can be verified
        ↓
Operator can troubleshoot and recover
```

# PHASE 5: Understand `daemon-reload`

systemd loads unit definitions into the manager.

When you create or modify a unit file, run:

```bash
sudo systemctl daemon-reload
```

This tells systemd:

> Unit definitions on disk may have changed. Reload them.

It does **not** mean:

```text
restart every service
```

After changing a service unit, you commonly need:

```text
edit unit
   ↓
daemon-reload
   ↓
restart affected service
   ↓
verify
```

## Step 3: Create API Application

Run:

```bash
sudo nano /opt/veriqta-api/app.py
```

Add:

```python
#!/usr/bin/env python3

import json
import os
import signal
import socket
import sys
import time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

HOST = os.environ.get("VERIQTA_API_HOST", "127.0.0.1")
PORT = int(os.environ.get("VERIQTA_API_PORT", "8080"))
SERVICE_NAME = os.environ.get("VERIQTA_SERVICE_NAME", "veriqta-api")

START_TIME = time.time()


class Handler(BaseHTTPRequestHandler):
    def _send_json(self, status_code, payload):
        body = json.dumps(payload, indent=2).encode("utf-8")

        self.send_response(status_code)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()

        self.wfile.write(body)

    def do_GET(self):
        if self.path == "/":
            self._send_json(
                200,
                {
                    "service": SERVICE_NAME,
                    "status": "running",
                    "hostname": socket.gethostname(),
                },
            )
            return

        if self.path == "/health":
            self._send_json(
                200,
                {
                    "service": SERVICE_NAME,
                    "status": "healthy",
                    "uptime_seconds": round(time.time() - START_TIME, 2),
                },
            )
            return

        if self.path == "/crash":
            self._send_json(
                200,
                {
                    "service": SERVICE_NAME,
                    "status": "intentional crash requested",
                },
            )

            sys.stdout.flush()
            sys.stderr.flush()

            os.kill(os.getpid(), signal.SIGTERM)
            return

        self._send_json(
            404,
            {
                "error": "not found",
                "path": self.path,
            },
        )

    def log_message(self, format, *args):
        print(
            f'client={self.client_address[0]} '
            f'method={self.command} '
            f'path={self.path} '
            f'message="{format % args}"',
            flush=True,
        )


if __name__ == "__main__":
    print(
        f"Starting {SERVICE_NAME} on {HOST}:{PORT}",
        flush=True,
    )

    server = ThreadingHTTPServer((HOST, PORT), Handler)

    try:
        server.serve_forever()
    except KeyboardInterrupt:
        pass
    finally:
        print(f"Stopping {SERVICE_NAME}", flush=True)
        server.server_close()
```

# PHASE 10: Understand Every Important Directive

## `[Unit]`

### `Description=`

Human-readable service description.

### `Documentation=`

Points operators toward documentation.

### `After=network.target`

Defines an **ordering relationship**.

It says:

> If both units are being started, start this unit after `network.target`.

It does **not** by itself guarantee that a remote network dependency is reachable.

This distinction becomes important later.

---

## `[Service]`

### `Type=simple`

systemd considers the service started after the `ExecStart` process is launched.

This works well for a foreground application.

### `User=veriqta-api`

Run the service as the dedicated user.

### `Group=veriqta-api`

Run using the dedicated group.

### `WorkingDirectory=/opt/veriqta-api`

Sets the process working directory.

### `EnvironmentFile=`

Loads variables from:

```text
/etc/default/veriqta-api
```

### `ExecStart=`

Defines the main process:

```text
/usr/bin/python3 /opt/veriqta-api/app.py
```

Use absolute executable paths in service definitions.

### `Restart=on-failure`

Requests restart after qualifying abnormal failures.

It does not mean every clean exit should automatically restart.

### `RestartSec=3s`

Wait three seconds before restart attempts.

### `StandardOutput=journal`

Send stdout into the journal.

### `StandardError=journal`

Send stderr into the journal.

### `NoNewPrivileges=true`

Prevents the service and its children from gaining additional privileges through mechanisms such as setuid/setgid execution.

### `PrivateTmp=true`

Provides the service with a private `/tmp` and `/var/tmp` view managed by systemd.

---

## `[Install]`

### `WantedBy=multi-user.target`

Defines how the service participates when enabled.

Enabling creates appropriate links so the service is pulled in by the target.

# PHASE 19: Understand `After=` vs `Wants=`

This is critical.

```ini
After=veriqta-api.service
```

primarily describes ordering.

```ini
Wants=veriqta-api.service
```

creates a weaker requirement relationship causing systemd to try to start the API when the worker is started.

These are different concepts.

```text
After=
    ↓
Ordering

Wants=
    ↓
Weak requirement relationship
```

Another directive is:

```ini
Requires=
```

which creates a stronger requirement relationship.

Do not use `Requires=` automatically just because one application communicates with another.

The correct dependency semantics depend on how the applications should behave when another component fails.

```bash
#!/usr/bin/env bash

set -u
set -o pipefail

SERVICES=(
    "nginx"
    "veriqta-api"
    "veriqta-worker"
    "veriqta-heartbeat"
)

API_URL="http://127.0.0.1:8080/health"

PASS=0

    echo "[WARN] $1"

}

    echo "[FAIL] $1"
    FAIL=$((FAIL + 1))
}

echo "Timestamp: $(date --iso-8601=seconds)"
echo "Hostname:  $(hostname)"
echo

    echo "------------------------------------------------------------"

        pass "$service is active"
    else
        fail "$service is not active"
    fi

    if systemctl is-enabled --quiet "$service"; then
        pass "$service is enabled"
    else
        warn "$service is not enabled"
    fi

        systemctl show "$service" \
        -p MainPID \
        --value \
        2>/dev/null
    )"

    echo "Main PID: ${main_pid:-unknown}"

    restarts="$(
        systemctl show "$service" \
        -p NRestarts \
        --value \
        2>/dev/null
    )"

    echo "Restart count: ${restarts:-unknown}"
    echo

done

echo "------------------------------------------------------------"
echo "API Functional Check"

if curl \
    --fail \
    --silent \
    --show-error \
    --max-time 5 \
    "$API_URL" \
    >/dev/null; then

    pass "veriqta-api health endpoint responded successfully"
else
    fail "veriqta-api health endpoint failed"
fi

echo
echo "------------------------------------------------------------"
echo "Heartbeat Freshness Check"

if [[ -f "$HEARTBEAT_FILE" ]]; then

    heartbeat_mtime="$(
        stat -c %Y "$HEARTBEAT_FILE"
    )"

    current_time="$(date +%s)"
    heartbeat_age=$((current_time - heartbeat_mtime))

    echo "Heartbeat age: ${heartbeat_age}s"

    if (( heartbeat_age <= HEARTBEAT_MAX_AGE )); then
        pass "Heartbeat is fresh"
    else
        fail "Heartbeat is stale"
    fi

else
    fail "Heartbeat file does not exist"
fi

echo
echo "------------------------------------------------------------"
echo "Failed systemd units"

failed_units="$(
    systemctl --failed \
    --no-legend \
    --plain
)"

if [[ -z "$failed_units" ]]; then
    pass "No failed systemd units detected"
else
    warn "Failed systemd units exist"
    printf '%s\n' "$failed_units"
fi

echo
echo "============================================================"
echo " SUMMARY"
echo "============================================================"
echo "PASS: $PASS"
echo "WARN: $WARN"
echo "FAIL: $FAIL"

if (( FAIL > 0 )); then
    exit 1

exit 0
```

# FAILURE LAB 7: Restart Loop and Start Rate Limiting

This lab demonstrates why automatic restart is not magic.

A permanently broken application with:

```ini
Restart=on-failure
```

can repeatedly fail.

systemd includes start-rate limiting to prevent uncontrolled restart storms.

First inspect current properties:

```bash
systemctl show veriqta-api \
-p Restart \
-p RestartUSec \
-p NRestarts
```

Back up unit:

```bash
sudo cp \
/etc/systemd/system/veriqta-api.service \
/etc/systemd/system/veriqta-api.service.rate-limit-backup
```

Create a drop-in:

```bash
sudo systemctl edit veriqta-api
```

Add:

```ini
[Unit]
StartLimitIntervalSec=30s
StartLimitBurst=3

[Service]
RestartSec=1s
```

Save.

Reload:

```bash
sudo systemctl daemon-reload
```

Now deliberately break the environment:

```bash
sudo cp \
/etc/default/veriqta-api \
/etc/default/veriqta-api.rate-limit-backup
```

Set invalid port:

```bash
sudo sed -i \
's/^VERIQTA_API_PORT=.*/VERIQTA_API_PORT=not-a-number/' \
/etc/default/veriqta-api
```

Restart:

```bash
sudo systemctl restart veriqta-api
```

Wait:

```bash
sleep 10
```

Inspect:

```bash
systemctl status veriqta-api --no-pager
```

Then:

```bash
systemctl show veriqta-api \
-p NRestarts \
-p Result
```

Logs:

```bash
journalctl \
-u veriqta-api \
--since "2 minutes ago" \
--no-pager
```

You should observe repeated failure attempts and potentially rate limiting depending on timing.

### Recover

Restore environment:

```bash
sudo cp \
/etc/default/veriqta-api.rate-limit-backup \
/etc/default/veriqta-api
```

Remove drop-in using:

```bash
sudo systemctl revert veriqta-api
```

### Important

`systemctl revert` removes administrator drop-ins/overrides for the unit and restores vendor/default unit configuration where applicable. For this custom unit, use it carefully and verify the result.

Inspect:

```bash
systemctl cat veriqta-api
```

If your custom primary unit remains correctly installed, continue.

Reload:

```bash
sudo systemctl daemon-reload
```

Clear failed/rate-limit state:

```bash
sudo systemctl reset-failed veriqta-api
```

Restart:

```bash
sudo systemctl restart veriqta-api
```

Verify:

```bash
curl http://127.0.0.1:8080/health
```

# FAILURE LAB 9: Worker Dependency Experiment

Stop both:

```bash
sudo systemctl stop \
veriqta-worker \

```

```bash

```


Because the worker contains:

```ini
Wants=veriqta-api.service
After=veriqta-api.service
```

systemd should also attempt to activate the API and order the worker after its startup transaction.

Now stop API:

```bash
sudo systemctl stop veriqta-api
```

```bash
systemctl is-active veriqta-worker
```

The worker may remain active.

Because `Wants=` does not mean:

> If the API later stops, terminate the worker.

This is exactly why dependency semantics need to be understood rather than guessed.

**Technologies:** Linux, Ubuntu Server, systemd, systemctl, journald, journalctl, Bash, Python, Nginx, systemd unit files, Linux permissions, process management

### Resume Bullets

* Built a multi-service Ubuntu reliability lab using systemd to manage Nginx and custom API, background-worker, and heartbeat services with boot activation, dedicated service identities, dependency ordering, and automated restart policies.

* Implemented Bash-based service validation covering runtime state, boot enablement, process metadata, HTTP health checks, heartbeat freshness, restart counts, and failed systemd units.

# 23. Interview Preparation

## What is systemd?

systemd is a system and service manager used by many Linux distributions to manage startup, services, dependencies, and other system resources.

---

## What is PID 1?

PID 1 is the first userspace process started by the kernel and has special responsibility for system initialization and process management.

On this Ubuntu environment:

```text
systemd
```

runs as PID 1.

---

## What is a systemd unit?

A resource systemd knows how to manage.

Examples:

```text
.service
.socket
.timer
.target
.mount
```

---

## What is a service unit?

A `.service` unit describes how systemd should manage a service process.

---

## What does `systemctl start` do?

Starts the unit now.

---

## What does `systemctl enable` do?

Configures the unit's installation relationships so it can be pulled in through targets or other units, commonly during boot.

---

## Is enabled the same as running?

No.

```text
enabled
```

describes enablement configuration.

```text
active
```

describes current runtime state.

---

## What does `daemon-reload` do?

Reloads systemd manager configuration after unit files are added or modified.

---

## Does daemon-reload restart the application?

No.

A service restart is a separate operation.

---

## What does `ExecStart=` do?

Defines the command systemd starts for the service.

---

## Why use absolute paths in ExecStart?

A service should not depend on an interactive user's shell PATH or environment to locate critical executables.

---

## What does `Type=simple` mean?

For a simple service, systemd treats the process started by `ExecStart` as the main service process and does not wait for an additional readiness notification.

---

## What does `Restart=on-failure` do?

It tells systemd to restart the service after qualifying failures.

---

## Why not use `Restart=always` everywhere?

Different service semantics require different policies.

A deliberate clean exit may be valid. Automatically restarting everything can hide application design problems or interfere with intended shutdown behavior.

---

## What is `RestartSec=`?

The delay before attempting a restart.

---

## What is a restart loop?

A pattern where:

```text
start
↓
fail
↓
restart
↓
fail
↓
restart
```

continues repeatedly.

Restart policies do not repair broken applications.

---

## What is systemd start-rate limiting?

A mechanism that can stop repeated rapid service-start attempts after configured limits are exceeded.

---

## What does `systemctl reset-failed` do?

Clears failed state and associated start-rate-limit counters.

It does not repair the root cause.

---

## What does `After=` mean?

It establishes ordering relative to another unit.

It does not automatically mean the other unit is required.

---

## What does `Wants=` mean?

It creates a weaker requirement relationship. Starting one unit can pull in the wanted unit, but failure behavior is less strict than `Requires=`.

---

## What does `Requires=` mean?

It creates a stronger requirement relationship between units.

The exact lifecycle behavior should still be understood before using it.

---

## Does `After=network.target` prove the Internet is available?

No.

It is an ordering relationship with the network target.

It does not prove DNS, Internet access, or a specific remote dependency is available.

---

## Why run services under dedicated users?

To reduce privileges and limit the damage possible if the service is compromised or misbehaves.

---

## Why not run every service as root?

Root has extensive system privileges. Most applications do not require them.

Least privilege reduces risk.

---

## What is journald?

The systemd journal service collects structured system and service logs.

---

## How do you view logs for one service?

```bash
journalctl -u SERVICE
```

---

## How do you see logs from the current boot?

```bash
journalctl -b
```

For one unit:

```bash
journalctl -b -u SERVICE
```

---

## How do you follow logs live?

```bash
journalctl -f -u SERVICE
```

---

## How do you see the last 50 messages?

```bash
journalctl \
-u SERVICE \
-n 50 \
--no-pager
```

---

## How do you inspect failed units?

```bash
systemctl --failed
```

---

## How do you inspect a service's main PID?

```bash
systemctl show SERVICE \
-p MainPID \
--value
```

---

## How do you inspect the effective unit?

```bash
systemctl cat SERVICE
```

---

## Why use `systemd-analyze verify`?

To detect unit-file problems before relying on the unit.

---

## What is a drop-in?

An administrator-supplied configuration fragment that modifies a unit without directly editing the original package-provided unit.

---

## Why is editing package-owned units directly undesirable?

Package upgrades may replace them, and it makes administrator modifications harder to separate from vendor configuration.

---

## Can an active process still be unhealthy?

Yes.

A process may exist while the application is:

```text
Hung
Returning errors
Unable to serve requests
Unable to reach dependencies
Functionally broken
```

This is why functional health checks matter.

---

## How would you troubleshoot a service that fails immediately?

A good sequence:

```text
systemctl status
↓
journalctl
↓
systemctl cat
↓
systemctl show
↓
verify unit
↓
check executable
↓
check identity
↓
check permissions
↓
check environment
↓
check dependencies
↓
run application manually as service user
↓
form hypothesis
↓
fix
↓
restart
↓
verify
```

# Project 09 Completion Standard

You have **not** completed this project merely because you can type:



You should understand that **service reliability is not simply "keep restarting the process."**

A reliable Linux service requires:

```text
Correct application
+
Correct service definition
+
Correct identity
+
Correct permissions
+
Correct configuration
+
Correct dependencies
+
Boot persistence
+
Failure detection
+
Appropriate restart policy
+
Rate limiting
+
Useful logs
+
Functional health checks
+
Troubleshooting procedures
+
Recovery verification
```

The operational habit carried into later Linux, DevOps, Platform Engineering, Cloud, Kubernetes, and SRE work should be:

**Define → validate → start → observe → fail deliberately → collect evidence → diagnose → recover → verify → prevent recurrence.**
