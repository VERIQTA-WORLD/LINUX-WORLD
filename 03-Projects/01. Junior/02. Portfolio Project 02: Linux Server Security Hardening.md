# 01. Project Title

## Linux Server Security Hardening

You have been given a freshly installed Ubuntu Linux server.

It works, but "working" and "securely configured" are not the same thing.

Your assignment is to transform it into a deliberately hardened server while preserving legitimate administrative access.

You will:

```text
Baseline
   ↓
Discover exposure
   ↓
Patch
   ↓
Reduce services
   ↓
Harden accounts
   ↓
Harden sudo
   ↓
Harden SSH
   ↓
Configure firewall
   ↓
Protect files
   ↓
Review AppArmor
   ↓
Improve logging
   ↓
Build security audit
   ↓
Test
   ↓
Break controls safely
   ↓
Troubleshoot
   ↓
Validate
   ↓
Document
   ↓
Clean up
```

The objective is not to produce a server with every port blocked.

The objective is to understand **why each exposed service, account, privilege, configuration, and network path exists**.

# 02. Project Scenario

You have joined a small company as a junior Linux administrator.

A new Ubuntu server has been provisioned for an internal application team.

Before applications are deployed, your senior administrator asks you to perform baseline security hardening.

The server currently has several concerns:

* Its security baseline has not been documented.
* Available package updates have not been reviewed.
* Listening network services have not been inventoried.
* Firewall policy has not been established.
* SSH configuration has not been reviewed.
* Administrative access needs validation.
* Unnecessary services may be running.
* Important configuration permissions need inspection.
* Security logging has not been reviewed.
* There is no repeatable hardening audit.
* Nobody has demonstrated what happens when a security configuration is wrong.

Your job is to secure the server without blindly disabling functionality.

# 12. Step-by-Step Implementation

# Phase 1: Establish the Baseline

You should not start changing security settings before understanding the current state.

A professional hardening process begins with evidence.

---

## Step 1: Record system information

Run:

```bash
hostnamectl
```

Then:

```bash
uname -a
```

Then:

```bash
cat /etc/os-release
```

Record the important values in:

```text
docs/baseline.md
```

Do not blindly publish real infrastructure identifiers from a real environment.

This is a lab, but learning to sanitize evidence is still useful.

---

## Step 2: Record uptime

Run:

```bash
uptime
```

This helps establish basic system context.

---

## Step 3: Review disk usage

Run:

```bash
df -h
```

A server with a nearly full filesystem can fail in ways that affect updates, logging, services, and security tooling.

---

## Step 4: Review memory

Run:

```bash
free -h
```

This is not directly a hardening control, but baseline health matters before making changes.

---

## Step 5: Inventory listening sockets

Run:

```bash
sudo ss -tulpn
```

Understand the options:

```text
-t    TCP
-u    UDP
-l    listening
-p    process information
-n    numeric addresses/ports
```

You may see SSH listening on port 22.

Do not assume every listening socket is dangerous.

Ask:

```text
What process owns it?
Why is it listening?
Does it need network exposure?
Which interface is it bound to?
Should the firewall permit it?
```

---

## Step 6: Record the listening-port baseline

Run:

```bash
sudo ss -tulpn | tee evidence/listening-before.txt
```

Review the file:

```bash
cat evidence/listening-before.txt
```

Sanitize it before publishing if necessary.

---

## Step 7: List running services

Run:

```bash
systemctl --type=service --state=running
```

Do not disable unfamiliar services just because you do not recognize their names.

Research or inspect their purpose first.

---

## Step 8: List enabled service units

Run:

```bash
systemctl list-unit-files --type=service --state=enabled
```

Running and enabled are different concepts.

A service may be running now without being enabled at boot.

A service may be enabled but not currently running.

---

# Phase 2: Review Accounts

## Step 1: Inspect accounts

Run:

```bash
getent passwd
```

Do not assume every account is a human login account.

Linux systems contain service accounts.

---

## Step 2: Find accounts with common interactive shells

Run:

```bash
getent passwd | awk -F: '$7 ~ /(bash|sh|zsh)$/ {print $1, $3, $6, $7}'
```

Review the result.

Ask:

* Which accounts belong to administrators?
* Which accounts are expected?
* Are any unfamiliar interactive accounts present?

Do not delete accounts solely because you do not recognize them.

---

## Step 3: Review UID 0 accounts

Run:

```bash
awk -F: '$3 == 0 {print $1 ":" $3 ":" $7}' /etc/passwd
```

Normally you should expect:

```text
root:0:...
```

Additional UID 0 accounts deserve investigation.

---

## Step 4: Review sudo group membership

Run:

```bash
getent group sudo
```

Ask:

```text
Does every listed user genuinely need broad administrative privileges?
```

Do not remove your own administrative access during the lab.

---

## Step 5: Review locked account status

For a specific account:

```bash
sudo passwd -S username
```

Replace `username` with a real lab account.

Do not make assumptions from one field alone. Account access can depend on passwords, SSH keys, shells, expiration, and other authentication mechanisms.

---

## Step 1: Refresh package metadata

Run:

```bash
sudo apt update
```

---

## Step 2: See what can be upgraded

Run:

```bash
apt list --upgradable
```

Review the output.

---

## Step 3: Apply normal available upgrades in the lab

Run:

```bash

```

Review the proposed changes before confirming.

Using `-y` everywhere can hide useful learning opportunities.

---

## Step 4: Determine whether reboot may be required

After upgrades, check:

```bash
test -f /var/run/reboot-required && cat /var/run/reboot-required
```

If the file does not exist, the command may produce no output.

If a reboot is required in your lab, reboot:

```bash
sudo reboot
```

Reconnect after the server returns.

Then:

```bash
uptime
```

and:

```bash
uname -r
```

# Phase 4: Reduce the Attack Surface

An unnecessary network service is additional software that must be configured, patched, monitored, and protected.

But do not confuse:

```text
fewer services
```

with:

```text
disable random services
```

---

## Step 1: Inspect listening services again

Run:

```bash
sudo ss -tulpn
```

Choose any unfamiliar listening service and investigate it.

For example:

```bash
systemctl status SERVICE_NAME
```

Then:

```bash
systemctl cat SERVICE_NAME
```

where appropriate.

---

## Step 2: Practice service reduction safely

Install a disposable lab service:

```bash
sudo apt install nginx -y
```

Start it:

```bash
sudo systemctl enable --now nginx
```

Verify:

```bash
systemctl is-active nginx
```

Check listening ports:

```bash
sudo ss -ltnp | grep ':80'
```

Now imagine this server is not intended to host a web service.

The correct question becomes:

```text
Why is Nginx here?
```

If there is no business requirement, remove the exposure.

Stop it:

```bash
sudo systemctl stop nginx
```

Disable automatic startup:

```bash
sudo systemctl disable nginx
```

Verify:

```bash
systemctl is-active nginx
```

Expected:

```text
inactive
```

Check port 80:

```bash
sudo ss -ltnp | grep ':80'
```

No matching Nginx listener should remain.

### What did we learn?

Hardening is often about removing unnecessary capability rather than adding another security product.

# 13. Configuration

# Phase 5: Review sudo Security

Run:

```bash
sudo -l
```

This shows what your current user may execute through sudo.

Validate the sudo configuration:

```bash
sudo visudo -cf /etc/sudoers
```

Do not directly edit `/etc/sudoers` with an ordinary text editor.

Use:

```bash
sudo visudo
```

or carefully managed files under:

```text
/etc/sudoers.d/
```

### Security principle

Administrative privileges should be granted because they are required for a role, not because giving someone full sudo is convenient.

SSH hardening can lock you out.

Before changing it, preserve the configuration.

Run:

```bash
cd ~/linux-server-security-hardening
sudo cp -a /etc/ssh/sshd_config backups/sshd_config.before
```

Because the copy was created using sudo, adjust ownership of the portfolio backup:

```bash

```

Verify:

```bash
ls -l backups/sshd_config.before
```

Do not automatically publish configuration backups. Review them first.

# Phase 7: Inspect Effective SSH Configuration

Ubuntu/OpenSSH configuration may involve include files.

Instead of relying only on `grep`, inspect effective configuration:

```bash
sudo sshd -T | grep -E '^(permitrootlogin|passwordauthentication|pubkeyauthentication|maxauthtries|x11forwarding)'
```

Your result may differ.

Document the baseline.

---

# Phase 8: Establish Key-Based Authentication

Do this **before** considering password authentication changes.

From the SSH client you will use to administer the VM, generate a key if you do not already have an appropriate lab key:

```bash
ssh-keygen -t ed25519 -C "project02-admin"
```

Do not overwrite an existing key unless you deliberately intend to.

Normally this creates:

```text
~/.ssh/id_ed25519
~/.ssh/id_ed25519.pub
```

The private key:

```text
id_ed25519
```

must remain private.

Never upload it to GitHub.

---

## Install the public key

From the client:

```bash
ssh-copy-id YOUR_USER@SERVER_IP
```

Replace:

```text
YOUR_USER
SERVER_IP
```

with your actual values.

If `ssh-copy-id` is unavailable, the public key can be installed manually, but ensure correct ownership and permissions.

---

## Test key authentication

Open a **new terminal**.

Do not close your existing working administrative session.

Run:

```bash
ssh YOUR_USER@SERVER_IP
```

Confirm you can connect.

Inside the remote session:

```bash
whoami
```

Then:

```bash
id
```

Only continue with stronger SSH restrictions after key authentication has been proven.

---

# Phase 9: Harden SSH with a Drop-In

Rather than rewriting the entire main SSH configuration, create a small hardening file.

Run:

```bash
sudo nano /etc/ssh/sshd_config.d/99-project02-hardening.conf
```

Start with:

```text
PermitRootLogin no
PubkeyAuthentication yes
MaxAuthTries 3
X11Forwarding no
```

Do **not** disable password authentication yet.

Save.

---

## Validate

Run:

```bash
sudo sshd -t
```

No output generally means syntax validation succeeded.

Now inspect effective values:

```bash
sudo sshd -T | grep -E '^(permitrootlogin|pubkeyauthentication|maxauthtries|x11forwarding)'
```

---

## Apply without blindly restarting

Run:

```bash
sudo systemctl reload ssh
```

Check:

```bash
systemctl status ssh --no-pager
```

Keep the existing session open.

Test another new SSH session.

Only after confirming new connections work should you continue.

---

# Phase 10: Password Authentication Decision

For this controlled lab, once key authentication is confirmed, we will demonstrate disabling SSH password authentication.

Edit:

```bash
sudo nano /etc/ssh/sshd_config.d/99-project02-hardening.conf
```

Add:

```text
PasswordAuthentication no
```

Save.

Validate:

```bash
sudo sshd -t
```

Check effective configuration:

```bash
sudo sshd -T | grep '^passwordauthentication'
```

You want:

```text
passwordauthentication no
```

If the effective result does not match, inspect included SSH configuration and ordering instead of assuming the line was applied.

Reload:

```bash
sudo systemctl reload ssh
```

Keep your original session open.

Test a fresh key-authenticated connection.

### Why this order matters

Unsafe sequence:

```text
Disable password authentication
        ↓
Reload SSH
        ↓
Discover key authentication does not work
        ↓
Locked out
```

Safer sequence:

```text
Create key
   ↓
Install public key
   ↓
Test key login
   ↓
Keep recovery session
   ↓
Change SSH policy
   ↓
Validate syntax
   ↓
Reload
   ↓
Test fresh session
```

# Phase 11: Configure the Firewall

Ubuntu commonly uses UFW as a convenient frontend for host firewall management.

Check status:

```bash
sudo ufw status verbose
```

If inactive, do **not** enable it immediately on a remotely administered system.

First permit required management traffic.

---

## Step 1: Establish default policy

Run:

```bash
sudo ufw default deny incoming
```

Then:

```bash
sudo ufw default allow outgoing
```

This establishes:

```text
Inbound: deny unless allowed
Outbound: allow unless denied
```

---

## Step 2: Permit SSH

Run:

```bash
sudo ufw allow OpenSSH
```

Verify the rule before enabling:

```bash
sudo ufw show added
```

Look for the OpenSSH rule.

---

## Step 3: Enable UFW

Run:

```bash
sudo ufw enable
```

Read the warning.

Because we allowed SSH first, the lab should retain SSH access.

---

## Step 4: Verify

Run:

```bash
sudo ufw status verbose
```

You should see an active firewall with default incoming deny policy and an SSH allow rule.

---

## Step 5: Test a new SSH connection

Do not assume the firewall is correct because `ufw status` looks correct.

From another terminal:

```bash
ssh YOUR_USER@SERVER_IP
```

Successful connection provides functional evidence.

---

# Important Firewall Concept

A firewall rule and a listening service are different things.

Run:

```bash
sudo ss -ltnp
```

SSH may still be listening on port 22.

UFW controls whether traffic is permitted through the host firewall.

The service controls whether something is listening.

You need to understand both.

# Phase 13: Review Sensitive File Permissions

Check:

```bash
ls -l /etc/passwd
ls -l /etc/shadow
ls -l /etc/group
ls -l /etc/gshadow
```

Do not modify these files merely to make their modes resemble an online tutorial.

Distribution defaults matter.

The objective here is to understand which data is public account metadata and which data is protected authentication information.

Test ordinary-user access to `/etc/shadow`:

```bash
cat /etc/shadow
```

As a non-root user, this should be denied.

Do not use sudo for this test because that would defeat the purpose.

---

# Phase 14: Find Potentially Dangerous World-Writable Files

Search the local root filesystem:

```bash
sudo find / -xdev -type f -perm -0002 -print 2>/dev/null
```

This finds regular files writable by "other."

Do not automatically change everything returned.

Some unusual permissions may be intentional.

The correct workflow is:

```text
Find
 ↓
Identify owner/package/application
 ↓
Understand purpose
 ↓
Determine expected mode
 ↓
Correct only when justified
```

---

# Phase 15: Review World-Writable Directories

Run:

```bash
sudo find / -xdev -type d -perm -0002 -print 2>/dev/null
```

You will likely find legitimate writable directories such as `/tmp`.

Inspect:

```bash
ls -ld /tmp
```

You may see:

```text
drwxrwxrwt
```

The final `t` represents the sticky bit.

In a shared writable directory, the sticky bit restricts who can delete or rename entries.

This is why:

```bash
chmod 777 /tmp
```

would not be equivalent to the normal secure design.

---

# Phase 16: Review AppArmor

Check status:

```bash
sudo aa-status
```

If the command is unavailable:

```bash
sudo apt install apparmor-utils -y
```

Then:

```bash
sudo aa-status
```

AppArmor provides mandatory access-control profiles that can restrict applications beyond ordinary Unix permissions.

At Junior level, you are not writing a complex AppArmor policy yet.

You are learning to recognize another security layer.

Document:

* Is AppArmor loaded?
* How many profiles are present?
* Are profiles enforcing or complaining?

Do not disable AppArmor simply to make troubleshooting easier.

---

# Phase 17: Review Security Logging

Linux hardening without visibility is incomplete.

Inspect SSH logs:

```bash
sudo journalctl -u ssh --no-pager -n 50
```

Inspect recent high-priority system messages:

```bash
sudo journalctl -p warning --since today --no-pager
```

Output depends on your environment.

Do not fabricate events for your portfolio.

---

# Phase 18: Inspect Authentication Events

On Ubuntu systems using traditional auth logs, you may have:

```bash
sudo tail -n 50 /var/log/auth.log
```

If that file is not present or your environment primarily relies on the journal, use:

```bash
sudo journalctl _COMM=sshd --since today --no-pager
```

The exact logging path can vary with system configuration.

This is why administrators should know both files and `journalctl`.

# 14. Automation

# Phase 19: Build the Server Security Audit Script

Return to your repository:

```bash
cd ~/linux-server-security-hardening
```

Create:

```bash
nano scripts/security-audit.sh
```

Add:

```bash
#!/usr/bin/env bash

set -u

section() {
    echo
    echo "=================================================="
    echo "$1"
    echo "=================================================="
}

section "LINUX SERVER SECURITY AUDIT"

echo "Date: $(date)"
echo "Hostname: $(hostname)"
echo "Kernel: $(uname -r)"

section "OPERATING SYSTEM"

grep -E '^(NAME|VERSION|VERSION_ID)=' /etc/os-release

section "UID 0 ACCOUNTS"

awk -F: '$3 == 0 {print $1 ":" $3 ":" $7}' /etc/passwd

section "INTERACTIVE-SHELL ACCOUNTS"

getent passwd |
awk -F: '$7 ~ /(bash|sh|zsh)$/ {print $1 ":" $3 ":" $6 ":" $7}'

section "SUDO GROUP"

getent group sudo || true

section "LISTENING SOCKETS"

ss -tulpn 2>/dev/null || true

section "UFW STATUS"

if command -v ufw >/dev/null 2>&1; then
    ufw status verbose
else
    echo "UFW is not installed."
fi

section "SSH EFFECTIVE SECURITY SETTINGS"

if command -v sshd >/dev/null 2>&1; then
    sshd -T 2>/dev/null |
    grep -E '^(permitrootlogin|passwordauthentication|pubkeyauthentication|maxauthtries|x11forwarding)' ||
    true
else
    echo "sshd not found."
fi

section "SSH SERVICE"

systemctl is-active ssh 2>/dev/null || true
systemctl is-enabled ssh 2>/dev/null || true

section "SENSITIVE FILE PERMISSIONS"

for file in /etc/passwd /etc/shadow /etc/group /etc/gshadow; do
    if [[ -e "$file" ]]; then
        stat -c '%A %a %U %G %n' "$file"
    fi
done

section "TEMP DIRECTORY"

stat -c '%A %a %U %G %n' /tmp

section "APPARMOR"

if command -v aa-status >/dev/null 2>&1; then
```

# Build the Automated Security Test

Open:

```bash
nano tests/security-tests.sh
```

Add:

```bash
#!/usr/bin/env bash

set -u

PASS=0
FAIL=0

pass() {
    echo "[PASS] $1"
    PASS=$((PASS + 1))
}

fail() {
    echo "[FAIL] $1"
    FAIL=$((FAIL + 1))
}

check_equals() {
    local actual="$1"
    local expected="$2"
    local description="$3"

    if [[ "$actual" == "$expected" ]]; then
        pass "$description"
    else
        fail "$description (expected: $expected, actual: $actual)"
    fi
}

echo "=========================================="
echo " Linux Security Hardening Test Suite"
echo "=========================================="

if sshd -t 2>/dev/null; then
    pass "SSH configuration syntax is valid"
else
    fail "SSH configuration syntax is invalid"
fi

ROOT_LOGIN=$(sshd -T 2>/dev/null |
    awk '$1=="permitrootlogin" {print $2}')

check_equals "$ROOT_LOGIN" "no" \
    "Direct root SSH login is disabled"

PUBKEY=$(sshd -T 2>/dev/null |
    awk '$1=="pubkeyauthentication" {print $2}')

check_equals "$PUBKEY" "yes" \
    "SSH public-key authentication is enabled"

PASSWORD_AUTH=$(sshd -T 2>/dev/null |
    awk '$1=="passwordauthentication" {print $2}')

check_equals "$PASSWORD_AUTH" "no" \
    "SSH password authentication is disabled"

if ufw status 2>/dev/null | grep -q '^Status: active'; then
    pass "UFW is active"
else
    fail "UFW is not active"
fi

if ufw status verbose 2>/dev/null |
    grep -qi 'deny (incoming)'; then
    pass "Default incoming firewall policy is deny"
else
    fail "Default incoming firewall policy is not deny"
fi

if systemctl is-active --quiet ssh; then
    pass "SSH service is active"
else
    fail "SSH service is not active"
fi

UID0_COUNT=$(awk -F: '$3 == 0 {count++} END {print count+0}' /etc/passwd)

if [[ "$UID0_COUNT" -eq 1 ]]; then
    pass "Only one UID 0 account exists"
else
    fail "Unexpected number of UID 0 accounts: $UID0_COUNT"
fi

TMP_MODE=$(stat -c '%a' /tmp)

if [[ "$TMP_MODE" == "1777" ]]; then
    pass "/tmp has expected sticky-bit permissions"
else
    fail "/tmp mode requires review: $TMP_MODE"
fi

echo
echo "Passed: $PASS"
echo "Failed: $FAIL"

if (( FAIL > 0 )); then
    exit 1
fi

exit 0
```

Make executable:

```bash
chmod +x tests/security-tests.sh
```

Run:

```bash
sudo ./tests/security-tests.sh
```

Do not alter a legitimate security control just to make a test say PASS.

If a test fails:

```text
FAIL
 ↓
Inspect
 ↓
Determine why
 ↓
Decide expected state
 ↓
Correct configuration if necessary
 ↓
Run test again
```

That is the correct workflow.

# 23. Interview Preparation

## Basic: What is server hardening?

Server hardening is the process of reducing unnecessary exposure and configuring a system so that required functionality operates with appropriate security controls.

---

## Why use default-deny inbound firewall policy?

It changes the model from:

```text
Everything is reachable unless blocked
```

to:

```text
Inbound traffic is denied unless explicitly permitted
```

This makes allowed exposure deliberate.

---

## Why is a firewall not enough?

A firewall addresses network traffic.

It does not replace:

* Authentication
* Authorization
* File permissions
* Patch management
* Secure service configuration
* Privilege management
* Logging
* Application security

---

## What is attack surface?

Attack surface is the set of reachable interfaces, services, accounts, software, privileges, and other entry points through which a system could potentially be attacked.

---

## Why disable unnecessary services?

Every unnecessary service can add software, configuration, privileges, listening sockets, dependencies, vulnerabilities, and operational maintenance.

---

## What does `ss -tulpn` help you investigate?

It shows listening TCP and UDP sockets and, with sufficient privileges, the processes associated with them.

It helps answer:

```text
What is listening on this server?
```

---

## Why disable direct root SSH login?

Using individual administrative accounts improves accountability and avoids exposing direct root authentication as the normal remote administration path.

Administrative elevation can then occur through controlled mechanisms such as sudo.

---

## Why use SSH keys?

Properly managed SSH keys provide strong cryptographic authentication and avoid transmitting reusable account passwords as the authentication secret.

Key security still matters because stolen private keys can create serious risk.

---

## Why shouldn't you immediately disable SSH password authentication?

Because you should first establish and verify an alternative authentication method.

Otherwise, you may lock yourself out.

---

## What does `sshd -t` do?

It validates SSH daemon configuration syntax.

It should be run before applying configuration changes.

---

## What is the difference between stopping and disabling a service?

Stopping affects its current running state.

Disabling generally prevents normal automatic startup through the enabled systemd unit relationship.

For an unnecessary service, you may need both.

---

## What is the sticky bit on `/tmp` for?

It allows a shared writable directory while restricting deletion or renaming of entries by users who do not own them, subject to the directory's rules.

---

## What is AppArmor?

AppArmor is a Linux mandatory access-control system that restricts applications according to security profiles.

It provides an additional control layer beyond traditional Unix permissions.

---

## Scenario Question

**SSH stops working immediately after a configuration change. What do you do?**

A strong answer:

1. Use console or retained administrative access.
2. Run `sshd -t`.
3. Inspect SSH service status.
4. Review SSH logs.
5. Review the most recent configuration change.
6. Restore or correct the bad configuration.
7. Validate again.
8. Reload/restart appropriately.
9. Test a new connection before closing the recovery session.

---

## Scenario Question

**The firewall allows port 443, but the website still cannot be reached. Is the firewall definitely broken?**

No.

Investigate whether:

* The application is running.
* Something is listening on 443.
* It is bound to the correct interface.
* Routing is correct.
* DNS is correct.
* TLS configuration is valid.
* Upstream firewalls or network controls exist.

An allow rule does not create a listening service.

---

## Deep-Dive Question

**Why can security hardening itself create outages?**

Security controls change access and behavior.

Incorrect firewall rules, SSH policies, file permissions, service settings, authentication rules, or privilege configuration can block legitimate activity.

Therefore hardening requires:

```text
Baseline
Change
Validate
Test
Observe
Rollback capability
```

not merely configuration changes.

# Project 02 Completion Standard

Do not consider the project finished simply because UFW says `active`.

You should be able to explain the complete security chain:

```text
              LINUX SERVER
                    |
          +---------+---------+
          |                   |
       ACCOUNTS            NETWORK
          |                   |
      privilege            firewall
          |                   |
        sudo              allowed ports
          |                   |
          +---------+---------+
                    |
                 SERVICES
                    |
             required only
                    |
                    v
                   SSH
                    |
          key authentication
          root login disabled
          validated config
                    |
                    v
                FILESYSTEM
                    |
          ownership + modes
                    |
                    v
                 APPARMOR
                    |
                    v
                  LOGS
                    |
                    v
                 AUDIT
                    |
                    v
                  TEST
                    |
                    v
             SIMULATE FAILURE
                    |
                    v
                DIAGNOSE
                    |
                    v
                 RECOVER
                    |
                    v
                 VERIFY
```

The final portfolio should prove not merely that you know commands such as `ufw`, `ss`, `systemctl`, and `sshd`.

It should prove that you can take a Linux server, establish its initial state, identify unnecessary exposure, apply security controls carefully, preserve legitimate administrative access, validate each change, deliberately test failure conditions, troubleshoot using evidence, verify recovery, and document the entire hardening process.

That completes **Junior Project 02: Linux Server Security Hardening**.
