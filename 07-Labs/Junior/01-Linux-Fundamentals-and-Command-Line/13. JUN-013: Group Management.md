# JUN-013: Group Management

- **Level:** Junior  
- **Difficulty:** 2/5  
- **Estimated time:** 90–120 minutes  
- **Environment:** Ubuntu Server 24.04 LTS or a similar Debian/Ubuntu system  
- **Privileges:** Administrative privileges required for group-management changes  
- **Primary skills:** Group creation, GID inspection, primary and supplementary group administration, membership changes, shared-access reasoning, group deletion, verification and troubleshooting  
- **Prerequisites:** JUN-001 through JUN-012

---

## Lab Mission

You already know that Linux access control connects three things:

```text
PROCESS IDENTITY
        +
FILE OWNERSHIP
        +
PERMISSIONS
```

You also know that a user can have:

```text
one primary group
+
zero or more supplementary groups
```

Now you will administer those groups.

Groups are one of Linux's main mechanisms for providing shared access without:

- transferring file ownership between users,
- making files world-readable or world-writable,
- giving every user administrative privilege,
- maintaining separate permissions for every individual.

Imagine three engineers:

```text
alice
bob
carol
```

All three need access to application deployment files.

A poor design might repeatedly change ownership or grant broad access.

A better design can be:

```text
deployers
├── alice
├── bob
└── carol
```

with resources assigned to the appropriate group.

That gives you an access-control relationship:

```text
USER
  ↓
GROUP MEMBERSHIP
  ↓
RESOURCE GROUP OWNERSHIP
  ↓
GROUP PERMISSIONS
  ↓
ACCESS
```

In this lab, you will create dedicated practice users and groups, modify memberships, change a user's primary group, test supplementary-group access, investigate stale session credentials, remove memberships safely, and clean up the environment.

You will work only with identities created specifically for this lab.

Do not modify:

- your normal login account's groups,
- `root`,
- production accounts,
- service accounts,
- administrative groups,
- `sudo`,
- `adm`,
- `systemd-journal`,
- `docker`,
- or any existing group you did not create for this exercise.

The operating principle is:

> Understand the access requirement first. Change group membership second. Verify effective identity and actual access afterward.

# 2. Reconnect the Identity Model

From JUN-011:

```text
username ↔ UID
group name ↔ GID
```

A group therefore has both:

```text
human-readable name
```

and:

```text
numeric GID
```

Linux filesystem objects store group ownership numerically.

Tools normally resolve that GID into a readable group name.

For example:

```text
-rw-r----- 1 alice engineers 2048 application.conf
```

may internally correspond to:

```text
owner UID: 1001
group GID: 2000
```

where:

```text
GID 2000 → engineers
```

Group administration changes the identity relationships that determine whether a process qualifies for the file's:

```text
group
```

permission class.

That means group management is part of access control—not simply account organization.

# 5. Automatic GID Allocation

You did not explicitly choose a GID when creating:

```text

```

The system selected an available GID according to its configuration.

Do not assume that every machine will assign the same number.

Inspect relevant configuration:

```bash
grep -E '^(GID_MIN|GID_MAX|SYS_GID_MIN|SYS_GID_MAX)' /etc/login.defs
```

Some values may vary or be absent depending on the distribution.

The engineering lesson is:

> If the numeric GID matters across systems, shared storage, containers, or centralized environments, do not rely blindly on whatever number happens to be allocated locally.

For this junior lab, automatic allocation is appropriate.

# 8. Primary vs Supplementary Groups in Practice

Inspect:

```bash
id veriqta-dev1
```

Identify:

```text
UID
primary GID
primary group
all groups
```

Now:

```bash
id -gn veriqta-dev1
```

This reports the primary group name.

Then:

```bash
id -Gn veriqta-dev1
```

This shows the group names associated with the account.

The distinction is:

```text
PRIMARY GROUP
one primary group identity configured for the account

SUPPLEMENTARY GROUPS
additional group memberships
```

Both can contribute to group-based access.

But they are administered differently.

# 9. Add a Supplementary Group Membership

The requirement is:

```text
veriqta-dev1 needs engineering-team access
```

Before changing anything:

```bash
id veriqta-dev1
```

Now add:

```bash
sudo usermod -aG veriqta-engineers veriqta-dev1
```

Break down the important part:

```text
-G
```

specifies the supplementary group list being modified.

```text
-a
```

means append.

Together:

```text
-aG
```

means:

> Add these group memberships while preserving the user's existing supplementary memberships.

Verify:

```bash
id veriqta-dev1
```

Then:

```bash
getent group veriqta-engineers
```

You should now see `veriqta-dev1` associated with the group.

# 10. Why `-aG` Matters

This is one of the most important safety lessons in junior Linux account administration.

Consider:

```bash
sudo usermod -G veriqta-engineers USER
```

without:

```text
-a
```

`-G` specifies the user's supplementary group list.

Using it without `-a` can replace the existing supplementary-group list rather than simply adding one membership.

That means a careless command can remove memberships the user still needs.

For example, imagine:

```text
Before:

alice
├── developers
├── monitoring
└── deployment
```

An administrator intends to add:

```text
database
```

but runs:

```text
usermod -G database alice
```

The resulting supplementary membership could become only:

```text
database
```

instead of:

```text
developers
monitoring
deployment
database
```

That can break:

- application access,
- shared-directory access,
- operational tooling,
- administrative workflows.

For additive membership changes, the safe mental model is:

```text
INSPECT EXISTING MEMBERSHIP
        ↓
usermod -aG GROUP USER
        ↓
VERIFY COMPLETE MEMBERSHIP
```

Do not run a destructive `usermod -G` experiment on your normal account.

# 15. `-g` vs `-G`

Do not confuse them.

```text
-g
```

means:

```text
primary group
```

```text
-G
```

means:

```text
supplementary groups
```

And:

```text
-aG
```

means:

```text
append supplementary membership
```

A useful mental model:

```text
-g
ONE primary group

-G
THE supplementary group list

-aG
ADD to supplementary groups
```

This is not just syntax trivia.

Using the wrong option can alter the account's access model.

# 22. Account Membership vs Running Process Credentials

There is an important subtlety.

Suppose a user already has a shell session open.

An administrator then adds the account to a new supplementary group.

The account database can show the new membership, while an already-running shell may still have the group credentials established when that session began.

Conceptually:

```text
SESSION STARTS
     ↓
process receives group credentials
     ↓
administrator changes membership database
     ↓
old process continues with existing credentials
```

A new login session commonly obtains the updated membership.

This explains the production situation:

```text
Administrator:
"I added you to the group."

User:
"I still get Permission denied."
```

Both observations can be true.

# 23. Inspect the Identity of the Actual Process

When troubleshooting access, do not only inspect the intended account from another administrative shell.

Inside the affected session, inspect:

```bash
id
```

That tells you the group credentials available to that session.

Compare this with administrative database resolution:

```bash
id USER
```

and:

```bash
getent group GROUP
```

The important troubleshooting distinction is:

```text
configured account membership
```

versus:

```text
credentials held by the process experiencing the problem
```

If the account was recently added to a group, a new login session may be required.

Do not solve stale session credentials with:

```text
chmod 777
```

# 27. Group Membership Does Not Automatically Guarantee Write Access

Suppose:

```text
user belongs to veriqta-engineers
```

but a file has:

```text
-rw-r-----
```

The group has:

```text
r--
```

Membership qualifies the process for the group class.

It does not invent permissions that are not present.

So:

```text
member of group
```

does **not** mean:

```text
full access
```

The correct model is:

```text
GROUP MEMBERSHIP
determines whether group class can apply

        ↓

GROUP PERMISSION BITS
determine what that class can do
```

You always need both.

# 31. Changing a GID Is Different From Renaming a Group

`groupmod` can also change a group's numeric GID.

That is a much more consequential operation.

Suppose:

```text
group:
engineers

old GID:
2000

new GID:
3000
```

Files already carrying:

```text
GID 2000
```

may require ownership remediation.

Changing the group database does not mean every filesystem object everywhere is automatically rewritten to the new GID.

Therefore this lab will **not** change the GID of the main shared group.

The safe reasoning is:

```text
GID CHANGE REQUEST
        ↓
inventory files using old GID
        ↓
understand shared/mounted storage
        ↓
understand applications and services
        ↓
change identity
        ↓
reassign ownership where required
        ↓
verify
```

The command is easy.

The migration is the real work.

# 34. A Primary Group Cannot Be Treated Like an Unused Group

You changed:

```text
veriqta-dev2
```

to use:

```text
veriqta-engineers
```

as its primary group.

Confirm:

```bash
id -gn veriqta-dev2
```

Now think about this command:

```text
sudo groupdel veriqta-engineers
```

Do **not** run it yet.

The group is actively used as a primary group.

Linux account-management tools are designed to protect against deleting a group that is still the primary group of an existing user.

Before deleting any group, investigate:

```text
Does a user have this as primary GID?
Does the group have supplementary members?
Does it own files?
Does a service depend on it?
Does application configuration reference it?
```

Deletion begins with dependency analysis.

# 39. Controlled Failure — Correct Group, Wrong Permissions

Create:

```bash
sudo touch SHARED_PATH/read-only-group-file.txt
sudo chgrp veriqta-engineers SHARED_PATH/read-only-group-file.txt
sudo chmod 640 SHARED_PATH/read-only-group-file.txt
```

Verify:


Confirm:

```bash

```

The user belongs to:

```text
veriqta-engineers
```

Now test reading:

```bash
sudo -u veriqta-dev1 cat SHARED_PATH/read-only-group-file.txt
```

Reading should be permitted if the path is traversable.

Now test writing with a provided command:

```bash
sudo -u veriqta-dev1 sh -c 'printf "test\n" >> "$1"' _ SHARED_PATH/read-only-group-file.txt
```

This command is supplied only to test write access. You are not being assessed on shell redirection syntax here; formal redirection is covered later in JUN-026.

```text
r--
```

The root cause is not missing membership.

The user already qualifies for the group class.

The problem is:

```text
group class lacks write permission
```

This distinction is essential.

# 40. Group Troubleshooting Model

When group-based access fails:

```text
SYMPTOM
What operation failed?

        ↓

PROCESS IDENTITY
Which user/process attempted it?

        ↓

CURRENT PROCESS GROUPS
What does id show in the affected session?

        ↓

TARGET GROUP
Which group is supposed to grant access?

        ↓

GROUP RESOLUTION
Does the group exist?

        ↓

CONFIGURED MEMBERSHIP
Is the user supposed to belong to it?

        ↓

SESSION FRESHNESS
Was membership changed after the session started?

        ↓

RESOURCE GROUP OWNERSHIP
Does the file/directory actually use that group?

        ↓

GROUP PERMISSIONS
Does the group class provide the required r/w/x?

        ↓

PATH
Can the user traverse every required directory?

        ↓

SPECIAL PERMISSIONS
Is SGID or Sticky Bit relevant?

        ↓

ROOT CAUSE
Membership?
Stale credentials?
Wrong group ownership?
Wrong mode?
Wrong path?
Different layer?

        ↓

FIX
Change only the incorrect layer.

        ↓

VERIFY
Identity + ownership + permissions + behavior.
```

Never reduce the investigation to:

```text
Permission denied
→ add user to random group
```

or:

```text
Permission denied
→ chmod 777
```

# 42. One More Collaboration Detail: File Modes Still Matter

SGID preserves group ownership.

It does not automatically guarantee that every new file is group-writable.

New file permissions can also be influenced by the creating process's requested mode and `umask`.

You will study default permission behavior formally in later Linux administration material.

For this junior lab, remember:

```text
SGID directory
→ helps preserve shared group ownership
```

but:

```text
SGID directory
≠
guarantee every new file has every desired group permission
```

Always inspect the actual result:

```bash
ls -l DEPLOYMENT_PATH
```

This prevents another common assumption.

# 46. Common Mistakes to Avoid

### Adding users to groups without inspecting existing memberships

Establish the starting state first.

### Using `usermod -G` when you intended `usermod -aG`

A non-append supplementary-group update can remove existing memberships.

### Confusing `-g` and `-G`

Lowercase `-g` changes the primary group.

Uppercase `-G` controls supplementary groups.

### Assuming `/etc/group`'s member list shows every primary-group relationship

It does not.

### Changing your own administrative groups for practice

Use dedicated lab accounts.

### Adding users to privileged groups casually

Membership in groups can have major security consequences.

### Assuming membership changes automatically update every existing process

Existing sessions may still have older group credentials.

### Fixing stale credentials with broad file permissions

Start a fresh session or investigate the process identity.

### Assuming membership guarantees write access

The group permission bits still control what group members can do.

### Assuming SGID makes every new file group-writable

SGID helps preserve group ownership; resulting file modes are a separate matter.

### Using `chmod 777` to solve a group-access problem

That destroys the intended access boundary.

### Deleting a group without checking primary-group users

Investigate dependencies first.

### Deleting a group without checking file ownership

Files can continue carrying the old numeric GID.

### Changing a GID casually

Existing filesystem ownership may require migration.

### Confusing removing a user from a group with deleting the group

They are different administrative actions.

# 51. Knowledge Check

### 1. What is a Linux group?

A named identity represented by a numeric GID that can be used to associate multiple user/process identities with shared access controls.

### 2. What is a GID?

A numeric Group ID.

### 3. What command creates a group?

```bash
groupadd GROUP
```

with appropriate administrative privilege.

### 4. How can you query a group through the configured identity database?

```bash
getent group GROUP
```

### 5. What command can show a user's complete group context?

```bash
id USER
```

### 6. What is a primary group?

The group represented by the user's configured primary GID.

### 7. What is a supplementary group?

An additional group associated with the user beyond the primary group.

### 8. What does this do?

```bash
usermod -g GROUP USER
```

It changes the user's primary group.

### 9. What does `-G` refer to in `usermod`?

The supplementary group list.

### 10. What does `-aG` do?

It appends specified supplementary group memberships while preserving existing supplementary memberships.

### 11. Why can `usermod -G` be dangerous if used carelessly?

Because it can replace the existing supplementary-group list and remove memberships the user still requires.

### 12. How can you add a user to a group with `gpasswd`?

```bash
gpasswd -a USER GROUP
```

with appropriate administrative privilege.

### 13. How can you remove a supplementary member with `gpasswd`?

```bash
gpasswd -d USER GROUP
```

with appropriate administrative privilege.

### 14. Why might a primary group member not appear in `/etc/group`'s explicit member list?

Primary membership is represented through the user's primary GID.

### 15. Does group membership automatically give full access to a group-owned file?

No. The resource's group permission bits still determine the capabilities available through that class.

### 16. If a user belongs to a file's group but the group mode is `r--`, can group membership alone provide write access?

No.

### 17. Why might a user still receive `Permission denied` immediately after being added to a group?

An existing session may still hold the group credentials established before the membership change.

### 18. What should you inspect inside the affected session?

```bash
id
```

### 19. What does SGID on a directory help accomplish?

New objects created within the directory normally inherit the directory's group ownership.

### 20. Does SGID guarantee all new files are group-writable?

No.

### 21. What command changes a group's name?

```bash
groupmod -n NEW_NAME OLD_NAME
```

with appropriate privilege.

### 22. Does renaming a group necessarily change its GID?

No.

### 23. Why is changing a GID more consequential than renaming a group?

Existing filesystem objects can still carry the old numeric GID and may require ownership migration.

### 24. How can you find files belonging to a named group?

```bash
find PATH -group GROUP -ls
```

### 25. How can you search using a numeric GID?

```bash
find PATH -gid GID -ls
```

### 26. What command deletes a group?

```bash
groupdel GROUP
```

with appropriate privilege.

### 27. What should you investigate before deleting a group?

Primary-group users, supplementary members, files owned by the group, services, applications, shared storage and other dependencies.

### 28. Is removing one user from a group the same as deleting the group?

No.

### 29. Why is `chmod 777` usually a poor fix for a missing group membership?

It broadens access to users who were not intended to receive it instead of correcting the identity relationship.

### 30. What four elements should you connect when investigating group-based filesystem access?

```text
process identity/group credentials
group membership
resource group ownership
permission bits
```

with path permissions and other security layers considered where relevant.

# 52. Interview Practice

### What is the difference between a primary group and a supplementary group?

A user's primary group is represented by the account's primary GID. Supplementary groups are additional group memberships available to the user's processes. Both can contribute to group-based filesystem access.

### How do you add a user to a supplementary group without removing existing memberships?

A common approach is:

```bash
sudo usermod -aG GROUP USER
```

I would inspect the existing membership first and verify the complete membership afterward.

### Why is `usermod -G` risky?

Because `-G` defines the supplementary group list. Without append behavior, existing supplementary memberships not included in the new list can be removed.

### What is the difference between `usermod -g` and `usermod -G`?

Lowercase `-g` changes the primary group. Uppercase `-G` manages the supplementary group list.

### How can you remove a user from one supplementary group?

One common approach is:

```bash
sudo gpasswd -d USER GROUP
```

followed by verification with `id USER` and `getent group GROUP`.

### Why can a user still get `Permission denied` after being added to the correct group?

The process experiencing the failure may have been started before the membership changed and may still have old group credentials. I would inspect `id` inside the affected session and test again from a fresh session where appropriate.

### Does being in the correct group guarantee access?

No. The resource must also have the intended group ownership, the group permission bits must provide the required operation, and required path components must be traversable. Other security mechanisms can also affect access.

### What is a common use for SGID on a directory?

It is useful for collaborative directories because newly created objects normally inherit the directory's group, helping maintain consistent shared group ownership.

### Does SGID automatically make files writable by the group?

No. Group ownership inheritance and the resulting permission mode are separate concerns.

### What happens when a group is renamed?

If only the name changes, the GID can remain the same. Files storing that GID continue to have the same numeric group ownership while tools display the new resolved group name.

### Why should a GID change be planned carefully?

Existing files and other resources may still carry the old numeric GID. Shared storage and applications may also depend on that identity, so ownership and dependencies must be inventoried and migrated.

### What would you check before deleting a group?

I would verify the group and GID, identify users for whom it is a primary or supplementary group, search relevant storage for group-owned files, inspect service/application dependencies, decide how ownership should be handled, then delete only when the dependency review shows it is safe.

### A deployment directory returns `Permission denied`. How would you investigate?

I would identify the process/user experiencing the problem, inspect its current groups, verify the intended group exists and the account is a member, inspect the directory's group ownership and mode, check traversal permissions on the path, determine whether the session has stale credentials, inspect relevant special permissions such as SGID, and change only the layer that is actually incorrect.
