# 1. From Shell Jobs to System Services

In JUN-019, you learned:

```bash
sleep 300 &
```

This creates a background shell job.

That is useful for interactive work.

It is not a production service-management architecture.

Imagine an application that must:

```text
start automatically when the server boots
run without an engineer logged in
run under a controlled identity
start after required dependencies
stop predictably
be discoverable by administrators
participate in system shutdown
have a defined lifecycle
```

Running:

```bash
application &
```

from someone's terminal does not provide that operational model.

A system manager is needed.

On Ubuntu Server, that role is performed by systemd.

---

# 2. What Is systemd?

systemd is a Linux system and service manager.

It manages far more than individual application processes.

Depending on the system configuration, systemd participates in areas including:

```text
system startup
service management
service dependencies
sockets
mounts
automounts
timers
device-related units
system targets
resource organization
shutdown
```

A simplified model is:

```text
LINUX KERNEL
      ↓
SYSTEMD
      ↓
UNITS
      ↓
SERVICES / SOCKETS / TARGETS / MOUNTS / TIMERS / ...
```

systemd gives Linux a structured way to describe and manage system resources.

# 3. PID 1

You already know from JUN-017 that every process has a PID.

Inspect PID 1:

```bash
ps -p 1 -o pid,ppid,user,stat,comm,args
```

On a normal Ubuntu Server 24.04 system using systemd, you should see that PID 1 is systemd.

A representative result might resemble:

```text
PID  PPID USER  STAT COMMAND  COMMAND
1    0    root  Ss   systemd  /sbin/init
```

or systemd may appear directly in the command representation.

Exact output can vary.

The important relationship is:

```text
PID 1
  ↓
systemd
```

Check the command name directly:

```bash
ps -p 1 -o comm=
```

You should normally see:

```text
systemd
```

---

# 4. Why PID 1 Is Special

PID 1 is the first userspace process started by the kernel during a normal Linux boot.

Other userspace processes ultimately descend from the system initialization environment.

A simplified boot model is:

```text
FIRMWARE / BOOT PROCESS
        ↓
LINUX KERNEL
        ↓
PID 1
        ↓
systemd
        ↓
system units
        ↓
services and other resources
```

PID 1 also has special responsibilities in Linux process management.

For this lab, the important lesson is:

> systemd is not simply another background program.

It occupies a central position in the operating system's userspace lifecycle.

# 6. What Is a systemd Unit?

A **unit** is a resource that systemd knows how to manage or represent.

Think:

```text
SYSTEMD
   ↓
UNIT
   ↓
defined resource / behavior
```

A unit might represent:

- a service,
- a socket,
- a mount,
- a timer,
- a target,
- an automount,
- a path,
- a slice,
- or another supported systemd resource type.

Units are identified by names such as:

```text
ssh.service
multi-user.target
systemd-journald.service
apt-daily.timer
```

The suffix tells you the unit type.

---

# 7. Common Unit Types

You do not need to memorize every systemd unit type today.

You should recognize the major ones.

| Unit suffix | Represents |
|---|---|
| `.service` | A service or managed process workload |
| `.socket` | A socket used for socket-based activation or communication |
| `.target` | A grouping/synchronization point for other units |
| `.timer` | Time-based activation |
| `.mount` | A filesystem mount |
| `.automount` | An automount point |
| `.path` | Path-based activation/monitoring |
| `.slice` | Resource-management grouping |
| `.device` | A device exposed to systemd |
| `.swap` | Swap resource |

You will work much more deeply with some of these later.

For now:

> systemd manages units, not merely services.

# 10. Understanding `LOAD`, `ACTIVE`, and `SUB`

Suppose you see something structurally similar to:

```text
UNIT         LOAD    ACTIVE  SUB      DESCRIPTION
ssh.service  loaded  active  running  OpenBSD Secure Shell server
```

The important fields are:

### LOAD

Whether systemd successfully loaded the unit definition.

For example:

```text
loaded
```

### ACTIVE

The high-level activation state.

Examples include:

```text
active
inactive
failed
activating
deactivating
```

### SUB

A more specific unit-type-dependent state.

For a service you might see:

```text
running
exited
dead
failed
```

The exact substate depends on the type of unit.

Therefore:

```text
ACTIVE
```

and:

```text
SUB
```

should not be treated as identical fields.

# 13. Loaded Units Are Not the Same as Installed Unit Files

Run:

```bash
systemctl list-units --type=service
```

Now compare:

```bash
systemctl list-unit-files --type=service
```

These commands answer different questions.

### `list-units`

Answers approximately:

> What units are currently loaded into systemd's manager state?

### `list-unit-files`

Answers approximately:

> What installed unit files does systemd know about, and what is their enablement-related state?

This distinction matters.

A service can have an installed unit file without currently being active.

---

# 14. Unit vs Unit File

These two concepts are related but not identical.

A **unit** is systemd's managed representation of a resource.

A **unit file** is configuration that defines or influences a unit.

Conceptually:

```text
UNIT FILE
configuration on disk

        ↓

SYSTEMD LOADS / INTERPRETS

        ↓

UNIT
manager's runtime representation
```

A unit's effective configuration may also be influenced by:

- drop-in configuration,
- generated units,
- aliases,
- dependencies,
- runtime configuration.

So avoid thinking:

```text
one unit = always one simple file
```

The real system can be more layered.

# 18. Inspect Whether a Unit Is Enabled

Run:

```bash
systemctl is-enabled ssh.service
```

Possible results can include states such as:

```text
enabled
disabled
static
masked
indirect
generated
```

depending on the unit and systemd configuration.

This command answers an enablement-related question.

It does **not** simply answer:

> Is the service running right now?

This distinction is one of the most important concepts in the lab.

---

# 19. Active Is Not the Same as Enabled

Consider:

```text
ACTIVE
```

versus:

```text
ENABLED
```

These describe different dimensions.

### Active

Runtime state.

Conceptually:

```text
Is this unit currently active?
```

### Enabled

Boot/activation configuration relationship.

Conceptually:

```text
Has this unit been configured through systemd's enablement mechanism so that it is pulled in by the relevant activation target or relationship?
```

Therefore, a unit can conceptually be:

| Runtime | Enablement |
|---|---|
| active | enabled |
| active | disabled |
| inactive | enabled |
| inactive | disabled |

Not every unit fits neatly into only those four labels because systemd has additional unit-file states.

But the central rule is:

> Running now and configured for future activation are different questions.

---

# 20. Why an Active Service Might Be Disabled

Imagine:

```text
service is disabled
```

An administrator manually starts it.

Now it may be:

```text
active
+
disabled
```

There is no contradiction.

The first state describes:

```text
now
```

The second describes:

```text
enablement configuration
```

Likewise, an enabled service may currently be inactive because:

- it was stopped,
- its activation conditions have not occurred,
- the system has not reached the relevant state,
- it failed,
- or its unit behavior is more specialized.

Never use:

```text
enabled
```

as a synonym for:

```text
running
```

# 23. Common Unit-File Locations

On a modern Ubuntu system, important locations include:

```text
/usr/lib/systemd/system/
/etc/systemd/system/
/run/systemd/system/
```

At a high level:

### `/usr/lib/systemd/system/`

Common location for unit files supplied by installed packages.

### `/etc/systemd/system/`

Common location for administrator-controlled system configuration, overrides, locally created units, aliases and enablement links.

### `/run/systemd/system/`

Runtime configuration that does not persist across reboot in the same way as `/etc`.

A strong rule is:

> Do not casually edit vendor-supplied unit files under `/usr/lib/systemd/system/`.

Administrator changes normally belong under:

```text
/etc/systemd/system/
```

using systemd-supported mechanisms.

You will work with that more deeply later.

# 27. What Is a Target?

A `.target` unit groups or coordinates other units.

Targets help systemd represent useful system states or synchronization points.

Examples commonly include:

```text
multi-user.target
graphical.target
network.target
rescue.target
emergency.target
```

Not every server uses every target in the same way.

Conceptually:

```text
TARGET
   ↓
groups / coordinates related units
```

Targets are somewhat analogous in purpose to historical runlevel concepts, but systemd targets are more flexible and dependency-oriented.

Do not treat them as merely renamed runlevels.

# 31. Dependencies Are Central to systemd

Real systems cannot start everything independently.

For example:

```text
APPLICATION
    ↓
may need another resource

SERVICE
    ↓
may need filesystem state

SYSTEM STATE
    ↓
may require groups of units
```

systemd models relationships between units.

These relationships can express concepts such as:

```text
requirement
preference
ordering
conflict
activation
```

This is one of the reasons systemd is more powerful than simply running startup commands sequentially.

# 34. Requirement and Ordering Are Different Concepts

This is a very important systemd principle.

Suppose unit A has:

```text
Requires=B.service
```

That expresses a requirement-style relationship.

Now suppose unit A has:

```text
After=B.service
```

That expresses ordering.

These are not the same thing.

Conceptually:

```text
REQUIREMENT
Should another unit be pulled in / required?

ORDERING
If both jobs are being started, which ordering relationship applies?
```

Therefore:

```text
Requires=
```

does not by itself mean:

```text
start after
```

and:

```text
After=
```

does not by itself mean:

```text
automatically require this unit
```

systemd separates these concerns deliberately.

---

# 35. `Requires=` and `Wants=`

At a junior level:

### `Requires=`

Represents a stronger requirement relationship.

### `Wants=`

Represents a weaker relationship.

A simplified mental model is:

```text
Requires=
strong dependency relationship

Wants=
preferred / weaker dependency relationship
```

The exact behavior also depends on other unit relationships and transaction state.

Do not reduce the full systemd dependency model to:

```text
Requires = mandatory forever
Wants = optional forever
```

That oversimplifies real behavior.

For now, understand relative strength.

---

# 36. `After=` and `Before=`

These directives concern ordering.

For example:

```text
After=network.target
```

means the unit is ordered after the specified unit when both participate in the relevant transaction.

Similarly:

```text
Before=example.service
```

creates the opposite ordering relationship.

The key lesson is:

> Ordering does not automatically create a requirement dependency.

You may need both dependency and ordering directives when defining a real relationship.

Custom unit authoring comes later.

# 40. What Does `static` Mean?

You may encounter:

```text
static
```

when running:

```bash
systemctl is-enabled UNIT
```

A static unit generally lacks the installation information used for normal direct enablement.

That does **not** mean:

```text
broken
```

and it does **not** mean:

```text
can never run
```

A static unit may be started because another unit depends on it or through another activation mechanism.

This reinforces:

> Enablement state and runtime state are different dimensions.

---

# 41. What Does `masked` Mean?

A masked unit is prevented from being started through the normal systemd unit-start mechanism because its unit configuration is linked in a way that blocks activation, commonly to `/dev/null`.

Conceptually:

```text
MASKED
        ↓
stronger than disabled
        ↓
normal activation blocked
```

Do not mask or unmask services in this foundational lab.

You only need to recognize the state.

---

# 42. Disabled Is Not Masked

These states are different.

### Disabled

The unit is not configured through normal enablement links for automatic activation in that context.

It may still be manually startable.

### Masked

Normal systemd activation of the unit is blocked.

Therefore:

```text
disabled
≠
masked
```

This distinction becomes important during troubleshooting.

---

# 43. What Is `daemon-reload`?

You will frequently encounter:

```bash
sudo systemctl daemon-reload
```

Do not run it merely because you are learning systemd.

Its purpose is to tell the systemd manager to reload unit-file configuration and rebuild its view after relevant unit configuration has changed.

Conceptually:

```text
UNIT FILE CHANGED
        ↓
systemd may still have previous manager configuration
        ↓
daemon-reload
        ↓
systemd reloads unit definitions/configuration
```

It does **not** mean:

```text
restart every service
```

and it does not itself mean:

```text
reboot the machine
```

You have not modified unit files in this lab, so there is no reason to run it.

---

# 44. `daemon-reload` Does Not Restart the Service

This distinction is worth learning now.

Suppose a unit file changes.

Running:

```bash
sudo systemctl daemon-reload
```

updates systemd's understanding of unit configuration.

That does not automatically mean the already-running application process has restarted with the new configuration.

Think:

```text
daemon-reload
        ↓
reload systemd unit definitions

service restart
        ↓
service lifecycle action
```

Different operations.

You will work with service lifecycle actions in JUN-021.

```text
/etc/systemd/system
/run/systemd/system
/usr/local/lib/systemd/system
/usr/lib/systemd/system
```

This is better than memorizing one path and assuming it applies universally.

---

# 46. Administrator Configuration Has Priority

At a high level, administrator-controlled configuration under:

```text
/etc/systemd/system/
```

can override or supplement vendor configuration.

This design allows:

```text
PACKAGE
        ↓
vendor unit

ADMINISTRATOR
        ↓
local override
```

without requiring the administrator to permanently modify the package's original file.

That matters because package upgrades can replace vendor-managed files.

The operational principle is:

> Keep local administrative policy separate from package-owned configuration whenever possible.

You will apply this principle when you learn custom unit management later.

---

# 47. Do Not Edit Vendor Unit Files Casually

Suppose:

```bash
systemctl show ssh.service -p FragmentPath
```

shows:

```text
/usr/lib/systemd/system/ssh.service
```

Do not conclude:

```text
I should edit that file directly.
```

Direct changes to package-owned unit files can:

- be overwritten by package upgrades,
- make maintenance harder,
- obscure administrative intent,
- create configuration drift.

systemd provides mechanisms for administrator overrides.

For now, inspect only.

# 48. Safe Unit Inspection Workflow

When you encounter an unfamiliar systemd unit, use a workflow such as:

```text
1. IDENTIFY

What is the exact unit name?


2. CLASSIFY

.service?
.socket?
.target?
.timer?
.mount?


3. CHECK LOAD/RUNTIME STATE

systemctl status UNIT
systemctl is-active UNIT


4. CHECK ENABLEMENT WHEN RELEVANT

systemctl is-enabled UNIT


5. INSPECT CONFIGURATION

systemctl cat UNIT


6. LOCATE SOURCE

systemctl show UNIT -p FragmentPath


7. INSPECT RELATIONSHIPS

systemctl list-dependencies UNIT


8. INSPECT SELECTED PROPERTIES

systemctl show UNIT -p ...


9. UNDERSTAND BEFORE CHANGING

Do not start/stop/enable/disable unfamiliar units casually.
```

That is a much safer model than:

```text
service looks weird
        ↓
restart it
```

# 53. A Unit Can Be Active Without a Long-Running Process

Do not assume:

```text
active unit
=
always has a continuously running daemon
```

Some service units perform an action and remain logically active after the process exits.

This can produce a service state such as:

```text
active (exited)
```

depending on the unit design.

Therefore:

```text
SUB=exited
```

does not automatically mean:

```text
service failed
```

You must interpret unit state according to the unit's design.

This is one reason systemd state should not be reduced to:

```text
process exists / process absent
```

Do not treat:


as automatically broken.

# 56. Do Not Restart Things Just to "See What Happens"

A common beginner habit is:

```text
systemctl status something
        ↓
systemctl restart something
```

without evidence.

Restarting can:

- interrupt users,
- terminate active connections,
- hide useful failure evidence,
- temporarily mask the underlying problem,
- cause dependency effects,
- create a second incident.

The correct habit is:

```text
INSPECT
        ↓
UNDERSTAND
        ↓
DECIDE
        ↓
CHANGE ONLY IF JUSTIFIED
        ↓
VERIFY
```

JUN-020 emphasizes the first two steps.

# 58. Common Mistakes

### Thinking systemd only manages services

It manages multiple unit types.

### Thinking every process is a systemd service

Processes can originate from many contexts.

### Thinking `active` means `enabled`

Runtime and enablement are different dimensions.

### Thinking `inactive` means `disabled`

It does not.

### Thinking `enabled` means currently running

It does not.

### Thinking `disabled` means the unit cannot be started

A disabled unit can often still be manually activated.

### Thinking `static` means broken

It does not.

### Thinking `masked` means merely disabled

Masking is a stronger activation block.

### Treating `.target` as just another service

Targets have a different role.

### Assuming all unit files live in `/etc/systemd/system/`

They do not.

### Editing `/usr/lib/systemd/system/` casually

Those files are commonly package/vendor managed.

### Running `daemon-reload` after every systemctl command

It is for reloading unit definitions after relevant configuration changes.

### Thinking `daemon-reload` restarts services

It does not.

### Assuming `After=` means "requires"

Ordering and requirement are different relationships.

### Assuming `Requires=` automatically means "starts after"

Requirement and ordering are separate concepts.

### Restarting a service before understanding the problem

Inspection should come first.

### Using `sudo` for every inspection command

Use only the privilege required.

### Assuming a missing unit means systemd is broken

The unit name may simply be wrong or absent.

### Assuming `active (exited)` is necessarily failure

Some unit designs legitimately produce that state.

# 65. Interview Practice

### What is systemd?

systemd is the system and service manager used by many Linux distributions. It commonly runs as PID 1 and manages system startup and resources represented as units.

### What is a systemd unit?

A unit is a resource systemd knows how to manage or represent, such as a service, socket, target, timer or mount.

### What is the difference between a unit and a unit file?

A unit is systemd's runtime representation of a managed resource. A unit file is configuration on disk that can define or influence that unit.

### What is the difference between `systemctl list-units` and `systemctl list-unit-files`?

`list-units` shows units loaded into the manager's current runtime view, while `list-unit-files` shows installed unit files and their enablement-related states.

### What is the difference between active and enabled?

Active describes current runtime state. Enabled describes systemd enablement configuration for future activation relationships. A service can be active but disabled or inactive but enabled.

### What is a static unit?

A static unit generally lacks normal installation metadata for direct enablement and is commonly activated through dependencies or another activation mechanism.

### What is the difference between disabled and masked?

A disabled unit is not configured through normal enablement for automatic activation in that context but may often still be manually started. A masked unit has normal systemd activation blocked.

### Where are systemd unit files stored?

Common system locations include `/usr/lib/systemd/system/` for package/vendor units, `/etc/systemd/system/` for administrator-controlled persistent configuration, and `/run/systemd/system/` for runtime configuration. I verify the actual unit using systemd tools rather than assuming its path.

### How do you find the source file for a unit?

I can use:

```bash
systemctl show UNIT -p FragmentPath
```

and inspect its effective configuration sources with:

```bash
systemctl cat UNIT
```

### What is a systemd target?

A target is a unit used to group or coordinate other units and represent useful synchronization or system-state points.

### How do you find the default target?

```bash
systemctl get-default
```

### What is the difference between `Requires=` and `After=`?

`Requires=` expresses a dependency relationship. `After=` expresses ordering. Requirement and ordering are separate concepts in systemd.

### What is the difference between `Requires=` and `Wants=`?

`Requires=` is a stronger dependency relationship, while `Wants=` is weaker.

### What does `systemctl daemon-reload` do?

It reloads systemd's unit-file configuration after relevant definitions change. It does not by itself restart the service.

### Why shouldn't you edit files under `/usr/lib/systemd/system/` directly?

They are commonly package-managed vendor files and may be replaced during upgrades. Administrator-specific configuration should normally use systemd's supported override mechanisms under `/etc/systemd/system/`.

### Why might a service show `active (exited)`?

Some service units perform work and then exit while systemd continues to consider the unit logically active according to its configuration.

### How would you investigate an unfamiliar unit before changing it?

I would identify the exact unit, inspect its type, status, runtime state, enablement state, configuration source, relevant properties and dependencies, understand its purpose and impact, and only then decide whether a change is justified.

### Why is restarting a service not a good first troubleshooting step?

A restart can interrupt workloads, remove useful evidence or temporarily hide the actual failure. I inspect and establish evidence before making lifecycle changes.
