## Lab Mission

You already understand the standard Linux permission model:

```text
user   group   other
rwx    rwx     rwx
```

You also know how to represent those permissions numerically:

```text
r = 4
w = 2
x = 1
```

and how to change them with commands such as:

```bash
chmod u+x file
chmod g-w file
chmod 640 file
chmod 750 directory
```

Linux also has three **special permission bits**:

```text
SUID
SGID
Sticky Bit
```

These bits extend the standard permission model.

They answer different operational questions:

```text
SUID:
When this executable runs, should its effective user identity be influenced by the file owner?

SGID on an executable:
When this executable runs, should its effective group identity be influenced by the file's group?

SGID on a directory:
Should newly created objects inherit the directory's group?

Sticky Bit on a directory:
In a shared writable directory, who should be allowed to remove or rename entries?
```

These are not ordinary read, write, and execute permissions.

They change how Linux interprets access and identity in specific situations.

You will learn how to recognize them, calculate them, apply them safely inside your own lab workspace, investigate them, and explain why they exist.

You will also learn an important engineering rule:

> Special permissions should be understood before they are changed.

# 2. Where Special Permissions Appear

A normal executable might look like:

```text
-rwxr-xr-x
```

Break the permissions into classes:

```text
user     group    other
rwx      r-x      r-x
```

Special permission bits reuse the positions normally occupied by execute characters.

SUID appears in the **user execute position**.

SGID appears in the **group execute position**.

Sticky Bit appears in the **other execute position**.

For example:

```text
-rwsr-xr-x
```

contains SUID.

```text
-rwxr-sr-x
```

contains SGID.

```text
drwxrwxrwt
```

contains the Sticky Bit.

A useful map is:

```text
user         group        other
r w x        r w x        r w x
    ↑            ↑            ↑
   SUID         SGID         Sticky
```

The special bits do not create extra visible character positions.

They alter the representation of the execute positions.

# 4. SUID — Set User ID

SUID means:

```text
Set User ID
```

Its special numeric value is:

```text
4
```

SUID is primarily meaningful on executable files.

When an eligible SUID executable runs, the process can run with an **effective user ID derived from the executable file's owner**, rather than only the user who launched it.

That is a significant change in execution behavior.

Suppose:

```text
user alice launches a program
```

and the executable is owned by:

```text
root
```

with SUID set.

Under the normal SUID execution model, the resulting process may have:

```text
real user identity:
alice

effective user identity:
root
```

The real identity helps represent who started the process.

The effective identity is important when the kernel performs many permission checks.

This is why SUID deserves careful security attention.

# 5. A Real System Example: `passwd`

A classic use of SUID is the password-changing utility.

Find it:

```bash
command -V passwd
```

On a typical Ubuntu system, the executable is:

```text
/usr/bin/passwd
```

Inspect it:

```bash
ls -l /usr/bin/passwd
```

A typical installation may show something similar to:

```text
-rwsr-xr-x
```

The exact owner, group, size, date, and mode can vary by distribution and system configuration.

Focus on:

```text
rws
```

in the owner field.

The lowercase:

```text
s
```

occupies the owner's execute position.

That tells you:

```text
SUID is set
and
owner execute is set
```

Check the owner:

```bash
stat /usr/bin/passwd
```

On a typical Linux installation, the executable is owned by `root`.

Ordinary users need to change their own passwords, but password management requires controlled interaction with protected authentication data.

A carefully designed privileged executable can perform the necessary operation without giving the user unrestricted root access.

That is one legitimate reason SUID exists.

Do not modify `/usr/bin/passwd`.

This portion of the lab is inspection only.

# 7. Important SUID Limitation

You used a shell script to observe the permission bit.

Do **not** conclude that setting SUID on an ordinary shell script gives it reliable SUID execution behavior.

Modern Linux systems generally do not honor SUID on interpreted scripts in the same way as supported binary executables, largely because doing so safely introduces serious security problems and race conditions.

The script in this lab is useful for learning:

```text
how the bit is represented
how chmod changes it
how stat reports it
```

It is **not** being used to demonstrate privileged SUID script execution.

That distinction matters.

# 9. SGID — Set Group ID

SGID means:

```text
Set Group ID
```

Its special numeric value is:

```text
2
```

SGID has important behavior on both:

```text
executable files
```

and:

```text
directories
```

The behavior is different in those two contexts.

On an eligible executable, SGID can cause the process's effective group identity to be derived from the executable's owning group.

On a directory, SGID affects group inheritance for newly created objects.

The directory behavior is especially useful for shared working areas.

# 13. Why SGID Directory Inheritance Matters

Without SGID directory inheritance, newly created files normally receive group ownership according to the creator's normal group-selection rules.

That may not always match the group assigned to a shared project directory.

Imagine a shared engineering directory:

```text
/srv/project
```

owned by:

```text
owner: root
group: developers
```

Several members of `developers` create files there.

You may want new objects to continue belonging to:

```text
developers
```

rather than unexpectedly using different group ownership.

SGID on the directory helps preserve that group relationship.

Conceptually:

```text
shared directory
        │
        ├── owning group: developers
        ├── SGID enabled
        │
        ↓
new files/directories
        │
        └── inherit developers group
```

This supports collaborative directory design.

It does **not** automatically guarantee that every new file will be group-writable.

Group ownership and permission bits are separate concepts.

The permissions assigned to new objects can also be affected by mechanisms such as `umask`, which you will study later.

# 15. Sticky Bit

The Sticky Bit has special numeric value:

```text
1
```

Today its most important use is on directories.

It is commonly used for directories that are writable by multiple users but where users should not normally be able to remove or rename each other's entries merely because the directory itself is writable.

The classic example is:

```text
/tmp
```

Inspect it:

```bash
ls -ld /tmp
```

A typical Linux system shows a mode similar to:

```text
drwxrwxrwt
```

Focus on the final character:

```text
t
```

That is the Sticky Bit.

Do not modify `/tmp`.

---

# 16. Why `/tmp` Needs More Than Write Permission

`/tmp` is commonly used as a shared temporary location.

Many users and processes need to create temporary objects there.

If a shared directory were broadly writable without additional protection, directory write permission could allow users to interfere with entries belonging to other users.

The Sticky Bit changes deletion and rename rules within the directory.

In a sticky directory, removal or renaming of an entry is restricted beyond ordinary directory write access. In simplified terms, the operation is normally permitted only to an appropriate privileged user, the owner of the directory, or the owner of the entry, subject to the rest of the system's access-control rules.

This supports a design like:

```text
many users can create entries
        │
        ↓
shared writable directory
        │
        + Sticky Bit
        │
        ↓
users cannot simply remove one another's entries
```

That is why:

```text
1777
```

has historically been associated with directories such as `/tmp`.

# 19. The Fourth Numeric Digit

You already know three-digit permission modes:

```text
755
640
600
```

Special permissions add a leading digit.

The special values are:

| Special permission | Value |
|---|---:|
| SUID | `4` |
| SGID | `2` |
| Sticky Bit | `1` |

The structure becomes:

```text
SPECIAL   USER   GROUP   OTHER
```

For example:

```text
4755
```

means:

```text
4     7     5     5
│     │     │     │
│     │     │     └── other
│     │     └──────── group
│     └────────────── user
└──────────────────── SUID
```

Therefore:

```text
4755
```

means:

```text
SUID
+
rwxr-xr-x
```

---

# 20. Calculate `2755`

Break it apart:

```text
2 7 5 5
```

Special digit:

```text
2 = SGID
```

Standard permissions:

```text
7 = rwx
5 = r-x
5 = r-x
```

So:

```text
2755
```

means:

```text
SGID
+
rwxr-xr-x
```

The displayed permission string would normally include:

```text
rwxr-sr-x
```

because SGID occupies the group execute position and group execute is enabled.

---

# 21. Calculate `1777`

Break it apart:

```text
1 7 7 7
```

Special digit:

```text
1 = Sticky Bit
```

Standard permissions:

```text
7 = rwx
7 = rwx
7 = rwx
```

So:

```text
1777
```

represents:

```text
Sticky Bit
+
rwxrwxrwx
```

For a directory, `ls -ld` commonly displays:

```text
drwxrwxrwt
```

This is the familiar pattern seen on `/tmp`.

---

# 22. Special Bits Can Be Combined

The special digit is itself a sum.

You already know:

```text
SUID   = 4
SGID   = 2
Sticky = 1
```

Therefore:

```text
4 + 2 = 6
```

means:

```text
SUID + SGID
```

```text
4 + 1 = 5
```

means:

```text
SUID + Sticky
```

```text
2 + 1 = 3
```

means:

```text
SGID + Sticky
```

and:

```text
4 + 2 + 1 = 7
```

means all three special bits are set.

For example:

```text
6755
```

means:

```text
SUID + SGID
+
rwxr-xr-x
```

Do not treat four-digit permission values as arbitrary codes.

Calculate the leading digit just as you calculate the standard permission digits.

# 26. Investigate Real Special-Permission Files Safely

Linux provides tools that can locate files by permission characteristics.

Your JUN-003 and JUN-031 material develops file discovery in greater depth, but for this lab you can use a focused inspection command to observe real system state.

To look for SUID files on the root filesystem:

```bash
find / -xdev -type f -perm -4000 2>/dev/null
```

Do not modify anything returned.

To look for SGID files:

```bash
find / -xdev -type f -perm -2000 2>/dev/null
```

The exact results depend on:

- distribution,
- installed packages,
- container or VM environment,
- system configuration,
- security hardening.

Do not assume that another machine will return the same list.

Pick one SUID result and inspect it:

```bash
ls -l PATH
```

Then:

```bash
stat PATH
```

Ask:

```text
Who owns it?
Which group owns it?
Which special bit is present?
Is the corresponding execute bit also present?
What is the complete numeric mode?
What program is this?
Why might it require special behavior?
```

Do not remove special permissions from system files merely because they appear unusual.

Investigation comes before remediation.

# 27. Why Special Permissions Matter to Security

A standard permission mistake may expose a file.

A special-permission mistake can sometimes affect **process identity** or shared-directory behavior.

For example, an SUID executable owned by a privileged account deserves attention because defects in that program could potentially be exercised with elevated effective privileges.

That does not mean:

```text
SUID = malicious
```

or:

```text
SUID = misconfiguration
```

Legitimate operating-system utilities can use SUID intentionally.

The correct question is:

> Is this special permission expected, necessary, correctly owned, and applied to the correct object?

Likewise, SGID may be intentionally used for:

- controlled executable group identity,
- shared project directories,
- collaborative storage.

The Sticky Bit may be intentionally used for:

- shared writable temporary directories,
- multi-user work areas.

Security engineering requires context.

# 34. Common Mistakes to Avoid

### Thinking the fourth digit is part of the ordinary `rwx` calculation

It represents special permission bits.

### Forgetting the values

```text
SUID   = 4
SGID   = 2
Sticky = 1
```

### Confusing SUID with SGID

SUID relates to the user-ID behavior of eligible executables.

SGID relates to group-ID behavior on eligible executables and group inheritance on directories.

### Thinking Sticky Bit makes a directory writable

It does not grant ordinary write permission.

The standard permission bits still determine normal access.

### Thinking SGID automatically makes files group-writable

It does not.

SGID directory inheritance controls group ownership behavior; newly created permission modes are a separate matter.

### Assuming every SUID file is malicious

Legitimate system utilities may intentionally use SUID.

### Removing a special bit without understanding why it exists

Investigate first.

### Treating uppercase `S` and `T` as cosmetic

They indicate that the special bit exists while the corresponding execute bit is absent.

### Assuming SUID on a shell script behaves like SUID on an eligible binary

Modern Linux generally does not honor SUID scripts in the same way.

### Using `chmod 755` on an object that intentionally requires `4755` or `2755`

A three-digit replacement can remove special bits.

### Modifying `/tmp` during practice

Use the controlled lab directory instead.

### Using `sudo` unnecessarily

This lab is designed to teach special-bit mechanics without altering privileged system objects.

# 39. Interview Practice

### What is SUID?

SUID, or Set User ID, is a special permission primarily used on executable files. On an eligible SUID executable, the resulting process can obtain an effective user identity derived from the executable's owner. It is commonly associated with controlled privileged operations and should be reviewed carefully because it affects execution identity.

### What is SGID?

SGID, or Set Group ID, has two important uses. On eligible executable files, it can affect the process's effective group identity. On directories, it causes newly created objects to inherit the directory's owning group, which is useful for shared working directories.

### What is the Sticky Bit?

The Sticky Bit is primarily used on shared writable directories. It adds restrictions to removing or renaming entries so that broad directory write access does not automatically allow users to interfere with entries owned by others.

### What does `4755` mean?

The leading `4` enables SUID. The remaining `755` gives the owner `rwx`, group `r-x`, and other `r-x`.

### What does `2775` mean?

The leading `2` enables SGID. The standard permissions are owner `rwx`, group `rwx`, and other `r-x`.

### What does `1777` mean?

The leading `1` enables the Sticky Bit, while the standard `777` permissions give user, group, and other read, write, and execute/traversal permissions.

### What is the difference between lowercase `s` and uppercase `S`?

Lowercase `s` means the relevant special bit is set and the corresponding execute bit is also present. Uppercase `S` means the special bit is set but the corresponding execute bit is absent.

### What is the difference between `t` and `T`?

Lowercase `t` means Sticky Bit and other execute are both present. Uppercase `T` means Sticky Bit is present but other execute is absent.

### Why is SGID useful on a shared directory?

It helps new files and directories inherit the shared directory's group ownership, reducing inconsistent group ownership in collaborative directory trees.

### Why does SGID not guarantee collaborative write access by itself?

Because group inheritance determines group ownership, not the complete permission mode assigned to newly created objects. Other mechanisms, including the creator's `umask`, influence new permissions.

### Why should SUID executables receive security attention?

Because SUID can affect the effective identity under which an eligible executable runs. A vulnerable or incorrectly configured privileged SUID program can therefore have greater security impact than an ordinary executable.

### Would you remove an unfamiliar SUID bit immediately?

No. I would first inspect the object's path, type, ownership, complete mode, package or purpose, and whether the special permission is expected. Removing legitimate special permissions can break system functionality.

### How would you investigate a special-permission regression?

I would inspect the object's type, owner, group, symbolic and numeric modes, identify which special bit is required, compare the current state with the intended policy, make the smallest justified change, and verify both the resulting mode and the intended behavior.
