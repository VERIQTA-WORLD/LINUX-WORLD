## 1. Lab Mission

Until now, most commands you have used have displayed their results directly in the terminal.

For example:

```bash
pwd
```

prints your current directory.

```bash
ls
```

prints directory contents.

```bash
cat file.txt
```

prints file contents.

But production Linux work frequently requires something different.

You may need to:

- save command output to a file,
- append new output without destroying existing data,
- provide file content as command input,
- capture error messages separately,
- capture normal output and errors together,
- determine whether a message came from stdout or stderr,
- protect an existing file from accidental overwrite.

This requires understanding Linux's standard I/O streams.

The core model is:

```text
                 PROCESS
              ┌───────────┐
stdin  ------>│           │------> stdout
FD 0           │  COMMAND  │        FD 1
               │           │------> stderr
              └───────────┘        FD 2
```

By default, your terminal is commonly connected to these streams.

Redirection changes those connections.

For example:

```text
command > output.txt
```

means:

```text
command
   │
 stdout
   │
   ▼
output.txt
```

The command itself has not necessarily changed.

You changed where its output goes.

### Learning objectives

By the end of this lab, you should be able to:

- explain standard input, standard output, and standard error;
- identify file descriptors `0`, `1`, and `2`;
- distinguish stdout from stderr;
- redirect stdout with `>`;
- append stdout with `>>`;
- redirect stdin with `<`;
- redirect stderr with `2>`;
- append stderr with `2>>`;
- explicitly redirect stdout with `1>`;
- send stdout and stderr to different files;
- combine stderr with stdout using `2>&1`;
- explain why redirection order matters;
- explain why `>` can destroy existing file contents;
- verify redirected data instead of assuming success;
- troubleshoot common redirection mistakes.

This lab uses only:

```text

```

for writable practice data.

Do not practice destructive redirection against important configuration files, logs, scripts, SSH keys, application data, or anything you cannot replace.

## 2. Build the Standard I/O Mental Model

Every running process can work with open file descriptors.

For this lab, the three standard descriptors matter most:

| File Descriptor | Standard Name | Common Purpose |
|---:|---|---|
| `0` | stdin | input |
| `1` | stdout | normal output |
| `2` | stderr | errors and diagnostic output |

Think of them as numbered channels:

```text
0 = input channel
1 = normal-output channel
2 = error-output channel
```

### Standard input — stdin

Standard input is the default input stream.

A command may receive input from your terminal:

```text
keyboard
   │
   ▼
 stdin
   │
   ▼
command
```

Later in this lab, you will redirect a file into stdin:

```text
file
 │
 ▼
stdin
 │
 ▼
command
```

### Standard output — stdout

Standard output carries normal command output.

For example:

```bash
pwd
```

normally writes the resulting pathname to stdout.

### Standard error — stderr

Standard error is a separate stream intended for diagnostic and error messages.

For example, request a file that does not exist:

```bash
cat definitely-not-here.txt
```

Bash starts `cat`, and `cat` reports an error.

That error is normally written to stderr.

This separation is extremely useful because Linux can handle:

```text
successful output
```

and:

```text
diagnostic/error output
```

independently.

```text
stdout → location.txt
```

### What `>` means

In:

```bash
pwd > location.txt
```

Bash processes the redirection and connects the command's stdout to the file.

Conceptually:

```text
pwd
 │
 │ stdout (FD 1)
 ▼
location.txt
```

The explicit form is:

```bash
pwd 1> location.txt
```

Try it:

```bash
pwd 1> explicit-stdout.txt
```

Verify:

```bash
cat explicit-stdout.txt
```

For output redirection:

```text
>
```

is shorthand for redirecting:

```text
FD 1
```

when no other descriptor is specified.

### Critical warning: `>` overwrites

Create:

```bash
echo "first value" > overwrite-test.txt
```

Inspect:

```bash
cat overwrite-test.txt
```

Now run:

```bash
echo "second value" > overwrite-test.txt
```

Inspect again:

```bash
cat overwrite-test.txt
```

You should now see only:

```text
second value
```

The first content was replaced.

Your safety model should therefore be:

```text
>
↓
destination exists?
↓
its previous contents may be replaced
```

Before redirecting into an important existing file, verify the destination.

## 4. Append Output Without Replacing Existing Content

Create:

```bash
echo "entry one" > activity.log
```

Inspect:

```bash
cat activity.log
```

Now append:

```bash
echo "entry two" >> activity.log
```

Then:

```bash
echo "entry three" >> activity.log
```

Inspect:

```bash
cat activity.log
```

You should see:

```text
entry one
entry two
entry three
```

The distinction is fundamental:

```text
>   overwrite/truncate destination

>>  append to destination
```

Both redirect stdout.

The difference is how the destination file is opened.

### Existing file

```bash
echo "new" > file.txt
```

replaces its previous contents.

But:

```bash
echo "new" >> file.txt
```

preserves existing contents and adds the new output at the end.

### Missing file

If the destination does not exist, both forms can create it when permissions allow.

Do not therefore interpret:

```text
>>
```

as meaning:

> append only if a file already exists.

It can create the destination as well.

### Engineer habit

Before choosing between `>` and `>>`, ask:

```text
Do I want to replace existing content?

or

Do I want to preserve it and add more?
```

That question matters far more than memorizing the symbols.

## 5. Redirect Standard Input with `<`

Create a small input file:

```bash
nano input.txt
```

Enter:

```text
alpha
bravo
charlie
delta
```

Save and exit.

Verify:

```bash
cat input.txt
```

Now run:

```bash
wc -l < input.txt
```

A typical result is:

```text
4
```

Here, Bash opens `input.txt` and connects it to the command's standard input.

Conceptually:

```text
input.txt
    │
    │ stdin (FD 0)
    ▼
   wc
    │
    │ stdout
    ▼
 terminal
```

The `<` operator therefore changes the command's input source.

Compare:

```bash
wc -l input.txt
```

with:

```bash
wc -l < input.txt
```

The first passes:

```text
input.txt
```

as a command argument.

The second redirects the file into stdin.

These are not the same shell operation, even if both allow `wc` to process the same data.

That distinction becomes increasingly important as your command-line skills grow.

You can also redirect the result:

```bash
wc -l < input.txt > line-count.txt
```

Now the flow is:

```text
input.txt
   │
   │ stdin
   ▼
  wc
   │
   │ stdout
   ▼
line-count.txt
```

Verify:

```bash
cat line-count.txt
```

You have now redirected both the input and output of one command.

## 6. Separate Standard Output from Standard Error

This is where the standard-stream model becomes especially useful.

First create a file that exists:

```bash
echo "VERIQTA Linux World" > exists.txt
```

Run:

```bash
cat exists.txt
```

You get normal output.

Now run:

```bash
cat missing.txt
```

You get an error.

The first command writes useful data to stdout.

The second reports its problem through stderr.

### Redirect stdout only

Run:

```bash
cat exists.txt > success.txt
```

Verify:

```bash
cat success.txt
```

Now deliberately request the missing file while redirecting stdout:

```bash
cat missing.txt > attempted-output.txt
```

The error should still appear in the terminal.

Why?

Because:

```text
>
```

redirected stdout.

It did not redirect stderr.

Inspect:

```bash
ls -l attempted-output.txt
```

The file may exist but contain no useful stdout because the command failed before producing normal file content.

### Redirect stderr

Now run:

```bash
cat missing.txt 2> errors.txt
```

The diagnostic should no longer normally appear in your terminal.

Inspect:

```bash
cat errors.txt
```

You should see the error message.

The syntax:

```text
2>
```

means:

```text
redirect file descriptor 2
```

which is stderr.

Conceptually:

```text
cat missing.txt
       │
       │ stderr (FD 2)
       ▼
   errors.txt
```

### Append stderr

Run:

```bash
cat another-missing-file.txt 2>> errors.txt
```

Then:

```bash
cat errors.txt
```

The new diagnostic should appear after the earlier one.

So:

```text
2>   overwrite stderr destination

2>>  append stderr destination
```

## 7. Control stdout and stderr Independently

Now create a command invocation that has both a successful file and a missing file:

```bash
cat exists.txt missing.txt
```

You should receive:

- the content of `exists.txt`;
- an error concerning `missing.txt`.

Those outputs belong to different streams.

Redirect stdout:

```bash
cat exists.txt missing.txt > normal.txt
```

The error should remain visible in the terminal.

Inspect:

```bash
cat normal.txt
```

You should find the successful file content there.

Now separate both streams:

```bash
cat exists.txt missing.txt > normal.txt 2> errors.txt
```

Inspect normal output:

```bash
cat normal.txt
```

Then inspect errors:

```bash
cat errors.txt
```

You have created:

```text
                    cat
                 ┌────┴────┐
                 │         │
              stdout     stderr
                FD 1       FD 2
                 │         │
                 ▼         ▼
            normal.txt  errors.txt
```

This is a powerful operational pattern.

A command can partially succeed and still produce diagnostic information.

Capturing the two streams separately lets you investigate each one clearly.

### Important lesson

A quiet terminal does not prove that a command produced no information.

Its streams may have been redirected elsewhere.

## 8. Combine stdout and stderr Deliberately

Sometimes you want one file containing both streams.

Start with:

```bash
cat exists.txt missing.txt > combined.txt 2>&1
```

Inspect:

```bash
cat combined.txt
```

You should find both the successful output and the error message.

### Understanding `2>&1`

Read:

```text
2>&1
```

as:

```text
make file descriptor 2 go to the same destination currently used by file descriptor 1
```

The command:

```bash
cat exists.txt missing.txt > combined.txt 2>&1
```

is processed conceptually as:

```text
1. stdout → combined.txt

2. stderr → wherever stdout is now going
```

Result:

```text
                    cat
                 ┌────┴────┐
                 │         │
              stdout     stderr
                 │         │
                 └────┬────┘
                      ▼
                 combined.txt
```

### Append both streams

If you want to preserve an existing combined log:

```bash
cat exists.txt missing.txt >> combined.log 2>&1
```

Run it again:

```bash
cat exists.txt missing.txt >> combined.log 2>&1
```

Inspect:

```bash
cat combined.log
```

The later output should have been appended rather than replacing the earlier content.

---

### Redirection order matters

Compare:

```bash
cat exists.txt missing.txt > order-a.txt 2>&1
```

with:

```bash
cat exists.txt missing.txt 2>&1 > order-b.txt
```

These are **not equivalent**.

In the first command:

```text
stdout → order-a.txt
stderr → current stdout destination
```

so both streams go to `order-a.txt`.

In the second:

```text
stderr → current stdout destination
stdout → order-b.txt
```

At the moment `2>&1` is processed, stdout still points to the terminal.

Then stdout is redirected to `order-b.txt`.

As a result, stderr can remain connected to the terminal while stdout goes to the file.

The core principle is:

> Bash processes redirections in the order they are written.

This is why you should understand redirection rather than memorizing symbols blindly.

## 9. Controlled Failures and Troubleshooting

You will now diagnose three common redirection mistakes.

### Failure A — Existing data disappears

Create:

```bash
echo "important first record" > records.txt
```

Append:

```bash
echo "important second record" >> records.txt
```

Verify:

```bash
cat records.txt
```

Now accidentally run:

```bash
echo "replacement record" > records.txt
```

Inspect:

```bash
cat records.txt
```

### Investigation

**Symptom:** Earlier records disappeared.

**Evidence:** The destination still exists, but only the newest output remains.

**Root cause:** `>` was used instead of `>>`.

**Prevention:** Decide whether the destination must be replaced or preserved before executing the command.

Do not pretend the overwritten content can always be recovered. Without another copy, backup, snapshot, application-specific recovery mechanism, or filesystem-level recovery capability, the original content may be lost.

---

### Failure B — Error still appears on screen

Run:

```bash
cat missing-again.txt > captured.txt
```

The error remains visible.

Ask:

> Which stream did I redirect?

Answer:

```text
stdout
```

But the diagnostic was written to:

```text
stderr
```

Correct the operation:

```bash
cat missing-again.txt 2> captured-error.txt
```

Verify:

```bash
cat captured-error.txt
```

The problem was not that redirection failed.

The wrong stream was redirected.

---

### Failure C — Two streams do not go where expected

Run:

```bash
cat exists.txt missing.txt 2>&1 > order-test.txt
```

You may still see the error in the terminal.

Inspect:

```bash
cat order-test.txt
```

Now compare with:

```bash
cat exists.txt missing.txt > order-test.txt 2>&1
```

Inspect again:

```bash
cat order-test.txt
```

### Root cause

Redirections are processed left to right.

The position of:

```text
2>&1
```

therefore changes what stderr is connected to.

### Troubleshooting model

When redirection behaves unexpectedly, investigate:

```text
SYMPTOM
   ↓
WHICH STREAM CONTAINS THE DATA?
   ↓
stdin / stdout / stderr
   ↓
WHICH FILE DESCRIPTOR?
   ↓
0 / 1 / 2
   ↓
WHICH OPERATOR WAS USED?
   ↓
< / > / >> / 2> / 2>> / 2>&1
   ↓
WHAT WAS THE REDIRECTION ORDER?
   ↓
WHAT FILE WAS CREATED OR MODIFIED?
   ↓
INSPECT ACTUAL CONTENT
   ↓
ROOT CAUSE
   ↓
MINIMUM FIX
   ↓
VERIFY AGAIN
```

Do not repeat a redirection command against important data until you understand why the first attempt behaved unexpectedly.

## 10. Engineer Notes and Common Mistakes

### `>` is destructive to existing file content

Before running:

```bash
command > important-file
```

know whether replacing that file is acceptable.

If preservation is required, `>` may be the wrong operation.

---

### `>>` does not mean "safer in every situation"

Appending preserves existing contents, but endlessly appending can create:

- duplicate data,
- misleading logs,
- large files,
- stale information mixed with current results.

Choose the operator based on the intended result.

---

### stdout and stderr are different

This:

```bash
command > file
```

does not automatically capture stderr.

Use the correct stream.

---

### `2>` does not mean "redirect two files"

The `2` identifies file descriptor 2:

```text
stderr
```

Likewise:

```text
1
```

means stdout and:

```text
0
```

means stdin.

---

### `<` is not the same as a filename argument

These:

```bash
wc -l input.txt
```

and:

```bash
wc -l < input.txt
```

give `wc` access to the same file data in different ways.

One passes a filename argument.

The other connects the file to stdin.

---

### Redirection is handled by the shell

In:

```bash
pwd > location.txt
```

`pwd` does not need to understand the `>` syntax.

Bash interprets the redirection and establishes the file-descriptor connection before executing the command.

---

### Redirection happens before useful command output is produced

This matters because:

```bash
command > existing-file
```

can truncate the destination as the redirection is established.

Do not assume a later command failure guarantees the old destination contents remain intact.

---

### Do not hide errors blindly

Sending stderr somewhere else can make the terminal look clean while the command is failing.

If you redirect errors, inspect the destination.

A quiet terminal is not a verification method.

---

### Verify the artifact

After:

```bash
command > result.txt
```

do not stop because the file exists.

Inspect:

```bash
ls -l result.txt
```

and when appropriate:

```bash
cat result.txt
```

or:

```bash
less result.txt
```

Testing means proving that the result contains what you intended.

---

### Do not use `sudo` unnecessarily

Everything in this lab belongs inside your home directory.

No privilege elevation is required.

---

### Pipes are deliberately excluded

You may have seen:

```text
|
```

in Linux commands elsewhere.

Do not use it in this lab.

A pipe connects the output of one process to the input of another.

That belongs to:

**JUN-027 — Pipes and Command Chaining**

First master file-based redirection.

## 12. Final Practical — Capture a Command Without Losing the Error

A teammate runs:

```bash
cat exists.txt missing-production-file.txt
```

The terminal displays valid content followed by an error.

They need:

```text
successful output → service-output.txt

diagnostic output → service-errors.txt
```

without mixing the two.

### Starting state

Confirm:

```bash
cat exists.txt
```

Now run the problematic command normally:

```bash
cat exists.txt missing-production-file.txt
```

Observe the two kinds of output.

### Investigate

Before redirecting anything, answer:

```text
Which part is stdout?

Which part is stderr?

Which file descriptor represents stdout?

Which file descriptor represents stderr?
```

Now capture them separately:

```bash
cat exists.txt missing-production-file.txt > service-output.txt 2> service-errors.txt
```

Verify normal output:

```bash
cat service-output.txt
```

Verify diagnostics:

```bash
cat service-errors.txt
```

Your investigation record should contain:

```text
SYMPTOM:

EXPECTED RESULT:

STDOUT CONTENT:

STDERR CONTENT:

STDOUT FILE DESCRIPTOR:

STDERR FILE DESCRIPTOR:

REDIRECTION COMMAND:

OUTPUT FILE:

ERROR FILE:

OUTPUT VERIFICATION:

ERROR VERIFICATION:

ROOT CAUSE OF THE COMMAND ERROR:

DID REDIRECTION FIX THE MISSING FILE?
Yes / No

WHAT DID REDIRECTION ACTUALLY CHANGE?
```

The final question matters.

Redirection did **not** fix the missing file.

It changed where the command's streams went.

That distinction is important:

```text
REDIRECTING AN ERROR
≠
FIXING THE ERROR
```

### Production connection

The same model appears in:

- administration scripts,
- scheduled jobs,
- application launchers,
- deployment tooling,
- backup commands,
- monitoring tools,
- CI/CD jobs,
- troubleshooting sessions.

Engineers frequently need to know whether useful output and diagnostic output are being captured, discarded, displayed, or mixed together.

## 13. Knowledge Check, Interview Practice, and Cleanup

### Knowledge Check

1. What are the three standard I/O streams?

   Standard input, standard output, and standard error.

2. What are their standard file descriptor numbers?

   `0` = stdin, `1` = stdout, `2` = stderr.

3. What does `>` do?

   Redirects stdout to a file by default and normally replaces the file's existing contents.

4. What does `>>` do?

   Redirects stdout while appending to the destination.

5. What does `<` do?

   Connects a file to a command's standard input.

6. What does `2>` do?

   Redirects stderr to a file, replacing existing destination content.

7. What does `2>>` do?

   Appends stderr to a file.

8. What does `1>` mean?

   Explicitly redirects file descriptor 1, stdout.

9. Why does an error still appear after `command > output.txt`?

   Because `>` redirects stdout, while the diagnostic may be written to stderr.

10. What does `2>&1` mean?

    It redirects file descriptor 2 to the destination currently associated with file descriptor 1.

11. Why does redirection order matter?

    Bash processes redirections from left to right, so earlier redirections affect what later descriptor duplication refers to.

12. What is the difference between `wc -l file.txt` and `wc -l < file.txt`?

    The first gives `wc` a filename argument. The second supplies the file's contents through stdin.

13. Does redirecting an error fix the underlying failure?

    No. It only changes where the diagnostic output is sent.

14. Why should `>` be treated carefully?

    It can truncate an existing file and destroy its previous contents.

15. Why should redirected files be inspected?

    Successful redirection syntax does not prove the captured content is correct or complete.

### Interview Practice

**Explain stdin, stdout, and stderr.**

They are the three standard process streams. stdin is standard input and normally uses file descriptor 0. stdout is normal output and uses descriptor 1. stderr is diagnostic/error output and uses descriptor 2.

**What is the difference between `>` and `>>`?**

`>` redirects output while replacing the destination's previous contents. `>>` appends output to the existing contents.

**How do you capture stderr separately from stdout?**

For example:

```bash
command > output.txt 2> errors.txt
```

This sends stdout to `output.txt` and stderr to `errors.txt`.

**How do you capture both streams in one file?**

One form is:

```bash
command > combined.txt 2>&1
```

stdout is redirected to the file, then stderr is directed to stdout's current destination.

**Why are `command > file 2>&1` and `command 2>&1 > file` different?**

Because Bash processes the redirections left to right. In the first form, stderr is attached after stdout already points to the file. In the second, stderr is attached to stdout while stdout still points to its earlier destination, then stdout is moved separately.

**Why might a command appear silent after redirection?**

Its output may have been redirected away from the terminal. Silence does not prove that the command produced no output or no errors.

**Who interprets the `>` operator?**

The shell interprets the redirection syntax and establishes the file-descriptor connections for the command.

**What would you check if an output file unexpectedly became empty?**

I would inspect the command, determine whether `>` was used against an existing file, identify which stream was redirected, inspect the resulting file, and determine whether truncation occurred before or during the failed operation.

# Lab Complete

You have completed **JUN-026 — Input, Output and Redirection**.

Your mental model should now be:

```text
                 PROCESS
              ┌───────────┐
              │           │
FD 0 -------->│  COMMAND  │--------> FD 1
stdin         │           │          stdout
              │           │
              └─────┬─────┘
                    │
                    ▼
                   FD 2
                  stderr
```

The terminal is only the usual starting destination.

The shell can reconnect those streams:

```text
<      file → stdin

>      stdout → file, replace

>>     stdout → file, append

1>     explicit stdout → file

2>     stderr → file, replace

2>>    stderr → file, append

2>&1   stderr → stdout's current destination
```

You also established several distinctions that matter in real Linux work:

```text
stdout
≠
stderr
```

```text
>
≠
>>
```

```text
filename argument
≠
stdin redirection
```

```text
quiet terminal
≠
successful command
```

```text
captured error
≠
resolved error
```

```text
file created
≠
correct result verified
```

```text
command > file 2>&1
≠
command 2>&1 > file
```

