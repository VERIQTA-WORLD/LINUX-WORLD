## Lab Mission

In JUN-015, you used commands such as:

```bash
sudo apt update
apt search sl
apt show sl
apt policy sl
sudo apt install sl
```

But one important question remains:

> Where did APT get the information and software?

APT does not invent packages.

It works with software sources configured on the system.

Those sources determine:

- which packages APT knows about,
- which package versions are available,
- where packages are downloaded from,
- which Ubuntu components are enabled,
- which release the packages belong to,
- which package version becomes a candidate,
- and which repository metadata the system is willing to trust.

A useful mental model is:

```text
SOFTWARE REPOSITORY
        ↓
SIGNED REPOSITORY METADATA
        ↓
apt update
        ↓
LOCAL PACKAGE METADATA
        ↓
APT POLICY
        ↓
PACKAGE CANDIDATE
        ↓
apt install
        ↓
PACKAGE DOWNLOAD
        ↓
INSTALLATION
```

Repository configuration is therefore part of the software supply chain.

A bad repository decision can expose a system to:

```text
untrusted software
unexpected package versions
dependency conflicts
failed updates
unsupported packages
repository outages
future maintenance problems
```

Your goal in this lab is not to collect random repositories.

Your goal is to understand the repository system well enough to inspect it, reason about it, and troubleshoot it safely.

The operating principle is:

> Know where software comes from before allowing it onto the system.

## 1. Build the Repository Mental Model

Start with the package lifecycle you already know.

When you run:

```bash
apt search PACKAGE
```

APT usually searches local metadata previously obtained from configured repositories.

When you run:

```bash
sudo apt update
```

APT contacts those configured sources and refreshes metadata.

When you run:

```bash
sudo apt install PACKAGE
```

APT uses that information to select and retrieve an appropriate package.

Conceptually:

```text
APT SOURCE CONFIGURATION
        ↓
defines
        ↓
REPOSITORIES
        ↓
provide
        ↓
SIGNED METADATA + PACKAGES
        ↓
apt update
        ↓
LOCAL PACKAGE INFORMATION
        ↓
apt policy / search / show
        ↓
CANDIDATE SELECTION
        ↓
apt install
```

If the repository layer is wrong, everything above it can be affected.

## 4. Traditional `.list` vs Modern `.sources`

APT supports more than one source format.

### Traditional one-line format

You may encounter entries resembling:

```text
deb URI SUITE COMPONENT...
```

For example, structurally:

```text
deb https://example.invalid/ubuntu noble main
```

That example is intentionally not a usable repository.

The important fields are:

```text
deb
→ binary package repository

URI
→ repository location

SUITE
→ distribution/release or repository suite

COMPONENT
→ repository section
```

### DEB822 `.sources` format

Modern systems may instead use a stanza resembling:

```text
Types: deb
URIs: https://example.invalid/ubuntu
Suites: noble noble-updates
Components: main universe
Signed-By: /path/to/keyring.gpg
```

This format uses named fields and can describe multiple suites or components clearly.

For Ubuntu 24.04, this format is especially important to recognize.

## 6. Understand Suites

A repository source can expose different suites.

On an Ubuntu system you may encounter names conceptually similar to:

```text
noble
noble-updates
noble-backports
noble-security
```

The exact values depend on the release.

Think of suites as distinct package publication streams associated with the distribution release.

A simplified model is:

```text
RELEASE
noble

UPDATES
noble-updates

SECURITY
noble-security

BACKPORTS
noble-backports
```

These streams exist for different package-maintenance purposes.

Do not treat every suite as interchangeable.

Repository suite selection influences what package versions APT can see.

## 7. Understand Ubuntu Repository Components

Ubuntu repositories can divide software into components.

You will commonly encounter:

```text
main
restricted
universe
multiverse
```

At a practical junior level:

### `main`

Contains software supported within Ubuntu's primary supported component.

### `restricted`

Contains supported software that has licensing or other restrictions affecting how it can be distributed or modified.

### `universe`

Contains a much larger body of community-maintained software.

### `multiverse`

Contains software whose licensing, legal or redistribution status prevents it from fitting the other components.

Do not interpret:

```text
universe
```

as:

```text
unsafe
```

or:

```text
multiverse
```

as:

```text
malware
```

The components represent support, licensing and distribution classifications—not a simple safe/unsafe ranking.

## 8. Repository Configuration Is Not the Package Cache

Keep these layers separate.

Repository configuration tells APT:

```text
where to obtain package metadata and packages
```

For example:

```text
/etc/apt/sources.list
/etc/apt/sources.list.d/*.list
/etc/apt/sources.list.d/*.sources
```

Downloaded package-list metadata is stored elsewhere under APT's state directories.

Inspect:

```bash
ls -la /var/lib/apt/lists/
```

Do not modify these files manually.

Conceptually:

```text
SOURCE CONFIGURATION
        ↓
sudo apt update
        ↓
DOWNLOADED METADATA
        ↓
apt search / show / policy
```

Changing a source file does not automatically refresh package metadata.

That is why repository changes are normally followed by:

```bash
sudo apt update
```

## 10. Multiple Sources and Candidate Selection

A system can know about a package from more than one source.

Conceptually:

```text
Repository A
package-x 1.0

Repository B
package-x 1.2

Installed
package-x 1.0

        ↓

APT POLICY
        ↓

Candidate selected
```

APT does not simply choose packages based on whichever source file appears first.

Candidate selection can involve:

- package versions,
- repository metadata,
- APT priorities,
- pinning policy,
- package state.

Advanced APT pinning is beyond this junior lab.

The important lesson is:

> Adding another repository can change package candidates.

That means repository additions can affect existing software, not just provide one new package.

## 11. Repository Trust and Package Signing

Downloading software from a repository creates a supply-chain question:

> How does APT determine whether repository metadata is authenticated by a trusted signing key?

APT uses cryptographic signatures on repository metadata as part of its trust model.

A simplified flow is:

```text
REPOSITORY
        ↓
publishes metadata
        ↓
metadata is cryptographically signed
        ↓
APT obtains metadata + signature information
        ↓
APT checks against trusted/configured signing key
        ↓
verification succeeds?
      ↙       ↘
    YES        NO
     ↓          ↓
metadata      warning/error
accepted      repository not trusted normally
```

The purpose is not merely to encrypt traffic.

The purpose is to authenticate repository metadata against configured trust.

---

## 12. HTTPS and Repository Signing Solve Different Problems

A repository may use:

```text
https://
```

HTTPS protects the network connection between your machine and the server.

Repository signing addresses a different question:

```text
Is this repository metadata authenticated by a key I have configured to trust for this source?
```

A simplified distinction is:

```text
HTTPS
protects transport

REPOSITORY SIGNATURE
authenticates repository metadata
```

One does not make the other unnecessary.

A secure package-management design can use both.

## 13. Inspect Repository Keyrings

Inspect common keyring locations:

```bash
ls -la /usr/share/keyrings/
```

and, if present:

```bash
ls -la /etc/apt/keyrings/
```

Do not modify existing keyrings.

A third-party repository may use a dedicated keyring such as:

```text
/etc/apt/keyrings/vendor.gpg
```

or another appropriate location.

A corresponding DEB822 source might reference it:

```text
Signed-By: /etc/apt/keyrings/vendor.gpg
```

This creates a clearer relationship:

```text
REPOSITORY
        ↓
SIGNED-BY
        ↓
SPECIFIC KEYRING
```

rather than treating every imported key as globally trusted for every repository.

## 14. Understand `Signed-By`

Suppose a source contains:

```text
Signed-By: /usr/share/keyrings/example-archive-keyring.gpg
```

This tells APT to use the referenced keyring when authenticating that repository's metadata.

Conceptually:

```text
SOURCE A
        ↓
KEYRING A

SOURCE B
        ↓
KEYRING B
```

This is a stronger trust design than casually expanding a global pool of repository keys.

When reviewing third-party repository instructions, look for a clearly scoped signing-key mechanism.

## 15. Why Old `apt-key` Tutorials Deserve Caution

You may encounter older tutorials using commands such as:

```text
apt-key add
```

Do not automatically copy them.

Modern APT repository management favors repository-specific keyring configuration rather than indiscriminately adding keys to a global trusted keyring.

When following third-party instructions, prefer:

```text
dedicated keyring
        +
Signed-By
        +
explicit repository definition
```

where supported.

The lesson is not:

```text
old command = instant disaster
```

The lesson is:

> Repository trust practices evolve. Use current distribution and vendor guidance rather than copying old setup commands blindly.

## 16. Third-Party Repositories Expand Your Trust Boundary

Suppose you add:

```text
Vendor Repository
```

to a server.

You are not merely adding a URL.

You may be allowing that repository to provide software packages that APT can install and potentially prefer under its policy.

Before adding a third-party repository, ask:

```text
Who operates it?
Is it the official vendor repository?
Does it support this Ubuntu release?
Does it support this architecture?
How is repository metadata authenticated?
Where is the signing key obtained?
Is the key scoped to this repository?
What packages will the repository provide?
Could it replace existing system packages?
How will this repository be removed later?
What happens if the vendor stops maintaining it?
```

Repository configuration is a security decision.

## 17. Do Not Blindly Pipe Repository Setup Scripts into a Shell

You will encounter installation instructions resembling:

```text
curl SOME_URL | sudo bash
```

Do not run that pattern merely because a website tells you to.

It combines:

```text
download remote content
        ↓
immediately execute it
        ↓
with administrative privilege
```

without requiring you to inspect what the script will do first.

A safer engineering mindset is:

```text
obtain official instructions
        ↓
verify source
        ↓
inspect commands/script
        ↓
understand repository + key changes
        ↓
execute deliberate steps
        ↓
verify resulting configuration
```

This does not mean every vendor setup script is malicious.

It means privileged remote execution deserves inspection.

## 21. Controlled Failure — Duplicate Repository Configuration

Run:

```bash
sudo apt update
```

APT may report warnings that some repository targets are configured multiple times.

Exact wording depends on APT version and how your existing sources are structured.

Do not panic.

Do not delete random repository files.

Investigate.

List:

```bash
ls -la /etc/apt/sources.list.d/
```

Inspect the original source:

```bash
less /etc/apt/sources.list.d/ubuntu.sources
```

Inspect the lab source:

```bash
cat /etc/apt/sources.list.d/veriqta-jun016.sources
```

Compare:

```text
URI
suite
component
```

You intentionally configured overlapping repository targets.

### Root Cause

```text
The same repository target is represented by more than one source definition.
```

### Correct Fix

Remove the controlled duplicate:

```bash
sudo rm /etc/apt/sources.list.d/veriqta-jun016.sources
```

Verify:

```bash
ls -l /etc/apt/sources.list.d/veriqta-jun016.sources
```

It should no longer exist.

Refresh:

```bash
sudo apt update
```

The duplicate-source warning caused by the lab entry should disappear.

You have now completed:

```text
CREATE FAILURE
        ↓
OBSERVE
        ↓
INSPECT SOURCES
        ↓
IDENTIFY OVERLAP
        ↓
REMOVE ONLY BAD ENTRY
        ↓
REFRESH
        ↓
VERIFY RECOVERY
```

## 22. Disable a Repository Without Deleting Its Configuration

In real administration, you may want to preserve repository configuration while disabling it temporarily.

One simple operational approach for a separate source file is to move it so it no longer has an active APT source filename.

For example, if the lab source still existed:

```bash
sudo mv \
/etc/apt/sources.list.d/veriqta-jun016.sources \
/etc/apt/sources.list.d/veriqta-jun016.sources.disabled
```

APT does not treat arbitrary filenames as active source definitions.

You would then run:

```bash
sudo apt update
```

and verify behavior.

For this lab, if you already removed the duplicate source, do not recreate it merely to perform this command.

Understand the method.

Disabling can be preferable to immediate deletion when troubleshooting because it preserves the original configuration for review or rollback.

## 23. Controlled Failure — Malformed Repository Definition

Do not deliberately damage your real Ubuntu source.

Instead, reason about this malformed DEB822 example:

```text
Types: deb
URIs:
Suites: noble
Components: main
```

The repository location is missing.

APT cannot use a repository definition that lacks required information.

Another malformed example could contain invalid field structure.

The troubleshooting principle is:

```text
APT reports source parsing/configuration problem
        ↓
identify named file
        ↓
inspect that file
        ↓
compare against valid source syntax
        ↓
repair or disable only the broken source
        ↓
apt update
        ↓
verify
```

Do not rewrite every repository file because one source is malformed.

## 24. Controlled Failure — Unsupported or Wrong Suite

Imagine a third-party repository configuration contains:

```text
Suites: noble
```

but the vendor does not publish packages for that suite.

During:

```bash
sudo apt update
```

you may receive errors indicating that expected repository metadata or a release definition is unavailable.

The root cause may be:

```text
repository exists
but
requested distribution suite does not
```

Investigate:

```text
What Ubuntu release am I running?
What suite is configured?
Does the repository officially support it?
Was the codename typed correctly?
```

Do not "fix" the issue by choosing a random older Ubuntu codename merely because that path exists.

Packages built for another release may have incompatible dependencies or assumptions.

## 25. Controlled Failure — Repository Cannot Be Reached

Repository access can fail even when configuration syntax is correct.

Possible layers include:

```text
DNS
routing
internet connectivity
proxy
TLS
remote repository outage
firewall
incorrect URI
```

Suppose `apt update` reports that a repository hostname cannot be resolved.

Your investigation should distinguish:

```text
SOURCE SYNTAX PROBLEM
```

from:

```text
NETWORK NAME-RESOLUTION PROBLEM
```

At this point in the curriculum, use the error evidence you have.

You will build deeper networking troubleshooting skills in JUN-044 onward.

Do not rewrite source configuration simply because DNS is failing.

## 26. Repository Signing Failure

APT may reject or warn about repository metadata when it cannot establish the expected trust relationship.

Possible causes include:

```text
missing signing key
wrong keyring path
expired/replaced vendor key
incorrect Signed-By configuration
repository signing changes
tampered or invalid metadata
```

Do not respond by disabling signature verification.

Do not search for random commands that make the warning disappear.

Investigate:

```text
Which repository failed?
Which key does the vendor officially document?
Where should that key be stored?
What does Signed-By reference?
Has the vendor rotated its signing key?
Am I following current instructions?
```

A trust failure is a security signal.

Treat it as one.

---

## 27. Never "Fix" Trust by Disabling Verification

You may find online suggestions that effectively tell APT:

```text
trust this repository without normal authentication
```

Do not use insecure trust bypasses merely to make `apt update` succeed.

The wrong goal is:

```text
Make the error disappear.
```

The correct goal is:

```text
Establish why verification failed
        ↓
restore a valid trust relationship
        ↓
verify repository metadata normally
```

Security controls are not bugs to bypass.

## 30. Repository Changes Can Affect Existing Packages

This deserves emphasis.

Suppose a server already has:

```text
package-x 1.0
```

from Ubuntu.

You add a third-party repository that publishes:

```text
package-x 2.0
```

Depending on APT policy, that new version may become the candidate.

Therefore:

```text
I only added the repository for package-y
```

does not prove:

```text
Only package-y can be affected.
```

Before adding a repository, understand its package scope.

After adding it, inspect relevant package candidates.

## 32. Common Mistakes

### Editing repository files before inspecting them

Always establish the current configuration first.

### Assuming `/etc/apt/sources.list` contains everything

Modern Ubuntu systems may use `.sources` files under `sources.list.d`.

### Copying repository instructions written for another Ubuntu release

Repository suites must match supported releases.

### Adding repositories without understanding what packages they provide

A repository can affect package candidate selection.

### Treating a repository URL as the entire trust model

Signing-key configuration matters too.

### Blindly using old `apt-key` instructions

Prefer current repository-specific trust guidance.

### Downloading arbitrary signing keys from unrelated sites

Use authoritative vendor/distribution sources.

### Piping unknown remote setup scripts directly into a privileged shell

Inspect what will change first.

### Disabling signature verification to make an error disappear

Investigate the trust failure.

### Deleting repository files randomly after `apt update` fails

Identify the exact failing source.

### Changing multiple source files simultaneously

Small changes are easier to verify and roll back.

### Forgetting `apt update` after changing source configuration

APT needs refreshed metadata.

### Ignoring warnings because packages still install

Warnings may reveal duplicate or degraded repository configuration.

### Using an older distribution suite because the current release is unsupported

That can introduce incompatible packages.

## 38. Knowledge Check

### 1. What is a software repository?

A software repository is a source that publishes package metadata and software packages for package-management systems such as APT.

### 2. What tells APT which repositories to use?

APT source configuration, commonly under `/etc/apt/sources.list` and `/etc/apt/sources.list.d/`.

### 3. What source formats may you encounter?

Traditional one-line `.list` entries and DEB822-style `.sources` files.

### 4. Which format is commonly seen on modern Ubuntu installations such as Ubuntu 24.04?

DEB822-style `.sources` configuration is commonly used.

### 5. What does `Types: deb` indicate?

The source provides binary Debian packages.

### 6. What does `URIs:` identify?

The repository location.

### 7. What does `Suites:` identify?

The distribution/release or repository suites requested from that source.

### 8. What does `Components:` identify?

The repository components enabled for that source.

### 9. Name four common Ubuntu repository components.

```text
main
restricted
universe
multiverse
```

### 10. Is `universe` simply another word for unsafe software?

No.

### 11. What does `apt update` do after a repository change?

It retrieves fresh repository metadata and updates APT's local package information.

### 12. Does editing a source file automatically refresh APT metadata?

No.

### 13. Where can downloaded APT package-list metadata commonly be found?

Under:

```text
/var/lib/apt/lists/
```

### 14. Should those metadata files normally be edited manually?

No.

### 15. What command can help identify which repository versions APT knows about for a package?

```bash
apt policy PACKAGE
```

### 16. What is an APT candidate?

The package version APT currently prefers for installation or upgrade under its available metadata and policy.

### 17. Can adding a repository change the candidate version of an already known package?

Yes.

### 18. Why is that important?

A new repository may affect existing package decisions, not merely add one new package.

### 19. Why are repository signatures used?

To authenticate repository metadata against trusted/configured signing keys.

### 20. Does HTTPS make repository signing unnecessary?

No.

### 21. What does HTTPS primarily protect?

The network transport connection.

### 22. What does repository signing primarily provide?

Authentication and integrity checking for repository metadata within APT's trust model.

### 23. What is `Signed-By` used for?

It associates a repository source with a specific signing key or keyring.

### 24. Why is repository-specific key scoping useful?

It limits which configured key is trusted for a particular source rather than unnecessarily expanding global repository trust.

### 25. Why should old `apt-key add` tutorials be treated cautiously?

Modern APT practice favors repository-specific keyring configuration, and older instructions may no longer reflect recommended trust management.

### 26. What should you verify before adding a third-party repository?

Its operator, official documentation, supported OS release and architecture, signing-key method, package scope and removal procedure.

### 27. Why is `curl URL | sudo bash` risky?

It immediately executes downloaded remote content with administrative privilege without requiring prior inspection.

### 28. Does that prove every remote installation script is malicious?

No. The concern is the execution model and the need to inspect privileged changes.

### 29. What can duplicate repository configuration cause?

APT can report warnings that repository targets are configured multiple times.

### 30. What should you do first after such a warning?

Identify and compare the source files that define the same target.

### 31. Should you randomly delete repository files?

No.

### 32. What can happen if a repository does not support your Ubuntu suite?

APT may fail to retrieve the expected repository metadata for that suite.

### 33. Should you solve that by selecting an arbitrary older Ubuntu suite?

No.

### 34. Why not?

Packages built for another release may have incompatible dependencies or assumptions.

### 35. What can cause repository connectivity failures?

DNS, routing, proxy configuration, firewall policy, TLS issues, incorrect URIs or remote repository outages.

### 36. Does a DNS failure automatically mean the repository configuration is wrong?

No.

### 37. What should you do when repository signature verification fails?

Identify the affected repository and investigate its signing key, `Signed-By` configuration and current official vendor guidance.

### 38. Should signature verification simply be disabled?

No.

### 39. Why is repository configuration security-sensitive?

Repositories influence which software and versions the package manager can trust, download and install.

### 40. What is the safe repository-change workflow?

```text
inspect
→ verify source
→ back up
→ change one thing
→ apt update
→ inspect warnings/errors
→ verify package policy
→ document
```

## 39. Interview Practice

### What is an APT repository?

An APT repository is a software source that publishes Debian package metadata and packages that APT can discover and retrieve.

### Where is repository configuration stored on Ubuntu?

Common locations are `/etc/apt/sources.list` and files under `/etc/apt/sources.list.d/`. Modern Ubuntu installations may use DEB822 `.sources` files.

### What is the difference between a `.list` file and a `.sources` file?

A `.list` file commonly uses one-line source definitions. A `.sources` file uses DEB822-style named fields such as `Types`, `URIs`, `Suites`, `Components` and `Signed-By`.

### What happens after you add a repository?

I inspect the configuration and run `apt update` to retrieve fresh metadata. I then review warnings or errors and inspect package policy where relevant before installing software.

### What does `Signed-By` do?

It associates a repository definition with a specific signing key or keyring used by APT when authenticating repository metadata.

### Why is adding a repository a security decision?

Because the repository becomes part of the software supply chain and may influence which packages and versions APT can install.

### Why isn't HTTPS enough?

HTTPS protects the connection to the server. Repository signing authenticates repository metadata against configured trust. They solve different problems.

### Why should you avoid blindly using `apt-key add` from old tutorials?

Current APT practice favors scoped repository keyrings and `Signed-By`. I prefer current Ubuntu and vendor instructions rather than outdated global-trust patterns.

### How would you troubleshoot a duplicate repository warning?

I would identify the target mentioned by APT, inventory the source files, compare their URI, suite and components, determine which definitions overlap, remove or disable only the redundant configuration, then run `apt update` again.

### What would you do if a third-party repository does not support your Ubuntu release?

I would verify the vendor's supported releases and use a supported installation method. I would not point the system at an arbitrary older distribution suite just to make the repository respond.

### What would you do if repository signature verification failed?

I would identify the repository, verify its official signing-key instructions, inspect the configured keyring and `Signed-By` path, check for legitimate key rotation or configuration errors, and restore valid verification rather than bypassing the security check.

### How can a newly added repository affect packages that were already available?

It may introduce different versions of existing package names, which can influence APT's candidate selection according to package versions and policy.

### Why should repository changes be made one at a time?

It makes failures easier to attribute, verify and roll back.
