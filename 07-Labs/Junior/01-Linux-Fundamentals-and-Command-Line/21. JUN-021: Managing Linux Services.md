# 1. Service Management Is State Management

A service operation changes state.

Before you execute:

```bash
sudo systemctl start UNIT
```

you should know:

```text
What unit am I changing?

What is its current runtime state?

What is its enablement state?

What depends on it?

Could stopping or restarting it affect my access?

What result do I expect?

How will I verify success?

How will I restore the original state?
```

This is especially important on remote servers.

For example, experimenting with:

```text
ssh.service
```

while connected through SSH is unnecessary risk.

Likewise, avoid casually manipulating:

- networking services,
- firewall services,
- storage services,
- authentication services,
- logging infrastructure,
- production databases,
- production web servers,
- monitoring agents,
- security tooling.

This lab will instead create a controlled service whose only purpose is to stay alive using `sleep`.

# 3. Create the Lab Unit Safely

The unit must be installed under the systemd administrator configuration area.

Use:

```bash
sudo systemctl edit --force --full veriqta-jun021.service
```

Your configured editor will open.

Enter the following unit definition exactly:

```ini
[Unit]
Description=VERIQTA JUN-021 Service Management Lab

[Service]
Type=simple
ExecStart=/usr/bin/sleep 3600

[Install]
WantedBy=multi-user.target
```

Save the file and exit the editor.

Your editor may differ from another learner's environment.

The important result is the unit file—not which editor was used.

Now inspect it:

```bash
systemctl cat veriqta-jun021.service
```

You should see the unit configuration you created.

Determine its path:

```bash
systemctl show veriqta-jun021.service -p FragmentPath
```

It should resolve to administrator-controlled systemd configuration, normally under:

```text
/etc/systemd/system/
```

# 4. Understand the Unit Before Running It

The unit contains three sections.

## `[Unit]`

```ini
[Unit]
Description=VERIQTA JUN-021 Service Management Lab
```

This provides general unit metadata.

`Description=` gives the unit a human-readable description.

---

## `[Service]`

```ini
[Service]
Type=simple
ExecStart=/usr/bin/sleep 3600
```

`Type=simple` tells systemd to treat the process started by `ExecStart=` as the main service process under this service model.

`ExecStart=` defines the command systemd starts:

```text
/usr/bin/sleep 3600
```

---

## `[Install]`

```ini
[Install]
WantedBy=multi-user.target
```

This provides information used when the unit is enabled.

At a junior level, think:

```text
enable service
        ↓
systemd uses [Install] information
        ↓
creates enablement relationship
        ↓
multi-user.target can pull service in
```

This does not mean the service is currently running.

# 12. Restart the Service

Start the service again:

```bash
sudo systemctl start veriqta-jun021.service
```

Verify:

```bash
systemctl is-active veriqta-jun021.service
```

Record the main PID:

```bash
systemctl show veriqta-jun021.service -p MainPID
```

Now restart it:

```bash
sudo systemctl restart veriqta-jun021.service
```

Verify again:

```bash
systemctl is-active veriqta-jun021.service
```

Then:

```bash
systemctl show veriqta-jun021.service -p MainPID
```

For this service, you should normally observe a different PID after restart.

Why?

Because restart performs a stop/start lifecycle for the service.

Conceptually:

```text
OLD SERVICE PROCESS
        ↓
STOP
        ↓
NEW START
        ↓
NEW SERVICE PROCESS
```

A restart can therefore interrupt active work.

That is why:

```text
restart
```

should never mean:

```text
generic troubleshooting button
```

---

# 13. Restart Has Operational Impact

Imagine restarting:

```text
database.service
```

or:

```text
web-api.service
```

A restart may:

- terminate active connections,
- interrupt requests,
- stop in-memory work,
- trigger reconnects,
- affect dependent applications,
- create a temporary outage.

The exact effect depends on the application.

Before a real restart, ask:

```text
Is restart actually required?

Does the application support reload?

Will users be affected?

Are dependencies ready?

Is this an approved change?

How will I verify recovery?
```

Your lab service is disposable.

Production services are not.

---

# 14. Reload Is Different from Restart

Some services can reload configuration without a complete process restart.

The command is:

```bash
sudo systemctl reload UNIT
```

But this only works when the unit/application supports a reload operation.

A simplified model:

```text
RESTART
        ↓
stop existing service
        ↓
start service again
```

versus:

```text
RELOAD
        ↓
ask running service to reload supported configuration
        ↓
service may continue without full restart
```

Not every service supports reload.

Never assume it does.

---

# 16. `reload-or-restart`

systemctl also provides:

```bash
sudo systemctl reload-or-restart UNIT
```

Its purpose is useful when your operational requirement is:

```text
reload if supported
otherwise restart
```

For your lab service:

```bash
sudo systemctl reload-or-restart veriqta-jun021.service
```

Because the service does not support reload, systemd should restart it.

Before running it, record:

```bash
systemctl show veriqta-jun021.service -p MainPID
```

Run:

```bash
sudo systemctl reload-or-restart veriqta-jun021.service
```

Then:

```bash
systemctl show veriqta-jun021.service -p MainPID
```

The PID should normally change for this lab service.

Do not use `reload-or-restart` casually on production workloads.

The fallback may be a full restart.

# 21. `--now`

Sometimes you deliberately want to change both:

```text
runtime state
```

and:

```text
enablement state
```

systemctl provides:

```text
--now
```

For example:

```bash
sudo systemctl enable --now UNIT
```

means, conceptually:

```text
enable
+
start now
```

Likewise:

```bash
sudo systemctl disable --now UNIT
```

means, conceptually:

```text
disable
+
stop now
```

The combined behavior is convenient—but because it changes two dimensions, you should use it only when that is exactly what you intend.

# 24. Masking a Service

Sometimes an administrator needs to prevent a unit from being started through normal systemd activation.

That is where masking is relevant.

A mask commonly causes the unit configuration name to resolve to:

```text
/dev/null
```

Conceptually:

```text
DISABLED
        ↓
not configured for normal automatic enablement

MASKED
        ↓
normal activation blocked
```

Masking is stronger.

Use it carefully.

# 28. Disabled and Masked Are Not Interchangeable

You should now be able to explain:

| State | Can normally be started manually? | Normal enablement relationship? |
|---|---:|---:|
| Enabled | Yes | Present |
| Disabled | Usually yes | Not enabled |
| Masked | No, normal activation is blocked | Blocked |

The table is a simplified operational model.

The key lesson is:

```text
disable
```

and:

```text
mask
```

solve different administrative problems.

Do not mask a service merely because you do not want it starting automatically.

Usually:

```text
disable
```

addresses that requirement.

```bash

```

```bash

```

# 31. Failed Start Is Not the Same as Failed Unit State in Every Situation

A lifecycle command can fail for different reasons.

Examples include:

```text

authorization denied

```

Do not reduce every failure to:

```text

```

First classify what actually failed.

Your masked-service exercise demonstrated an **activation-policy failure**, not an application crash.

# 34. Runtime State Is Temporary System State

Suppose you run:

```bash
sudo systemctl start veriqta-jun021.service
```

but leave it disabled.

The service is active now.

That does not mean the enablement relationship will cause it to start during a future normal boot.

Likewise:

```bash
sudo systemctl stop veriqta-jun021.service
```

does not necessarily alter whether it is enabled.

Think in two axes:

```text
             ENABLEMENT

             ENABLED     DISABLED
             ┌───────────┬───────────┐
ACTIVE       │ possible  │ possible  │
             ├───────────┼───────────┤
INACTIVE     │ possible  │ possible  │
             └───────────┴───────────┘
```

Masking introduces another policy state beyond this simple grid.

---


Boot validation is important in real change testing, but reboots should be deliberate, planned operations—not casual lab habits on an unknown system.

# 36. Service Reload vs systemd `daemon-reload`

These operations are commonly confused.

## Service reload

```bash
sudo systemctl reload UNIT
```

Meaning:

```text
ask the running service to reload supported application configuration
```

## systemd manager reload

```bash
sudo systemctl daemon-reload
```

Meaning:

```text
tell systemd to reload unit definitions
```

They operate at different layers.

```text
APPLICATION CONFIGURATION
        ↓
systemctl reload UNIT

SYSTEMD UNIT DEFINITIONS
        ↓
systemctl daemon-reload
```

Neither should be run merely out of habit.

# 37. When Is `daemon-reload` Appropriate?

You used it after creating:

```text
/etc/systemd/system/veriqta-jun021.service
```

That was appropriate because systemd's unit configuration changed.

Typical reasons include:

```text
new unit file
changed unit definition
changed relevant drop-in configuration
removed unit definition
```

It is not required simply because you:

```text
started a service
stopped a service
restarted a service
enabled a service
disabled a service
```

unless some separate unit-file change requires it.

# 39. Service Management and Process Management Are Related

When you start:

```bash
sudo systemctl start veriqta-jun021.service
```

systemd creates and manages the service process according to the unit configuration.

You could see the process with:

```bash
ps -p PID -o pid,ppid,user,stat,etime,cmd
```

But once systemd owns the workload as a service, your normal administrative interface should be the service manager.

Avoid making this your routine:

```text
systemd-managed service
        ↓
find PID manually
        ↓
kill process manually
```

when the correct lifecycle operation is:

```bash
sudo systemctl stop UNIT
```

The service manager understands the unit context.

A raw process signal does not represent the entire service lifecycle policy.

# 40. Service Management and Shell Job Control Are Different

Compare:

```bash
sleep 3600 &
```

with:

```bash
sudo systemctl start veriqta-jun021.service
```

The first is associated with your shell's job-control environment.

The second is managed by systemd as a service unit.

Conceptually:

```text
INTERACTIVE SHELL
        ↓
jobs / fg / bg

SYSTEM SERVICE
        ↓
systemd / systemctl
```

Do not try:

```bash
jobs
```

and expect it to list systemd's service as one of your shell jobs.

These are different management layers.

# 43. Common Mistakes

### Restarting before investigating

A restart may hide the original problem.

### Using `start` when the service is already active

Understand current state first.

### Assuming `start` enables a service

It does not.

### Assuming `enable` starts a service immediately

Not unless runtime activation is also requested, such as with `--now`.

### Assuming `stop` disables a service

It does not.

### Assuming `disable` stops a running service

It does not inherently do so.

### Confusing `disable` with `mask`

Masking is a stronger activation block.

### Masking when disabling would meet the requirement

Use the least disruptive policy change that satisfies the need.

### Forgetting to unmask before trying to start a masked service

Inspect enablement state first.

### Assuming every service supports reload

Check:

```bash
systemctl show UNIT -p CanReload
```

### Confusing service reload with `daemon-reload`

They affect different layers.

### Running `daemon-reload` after every service command

Use it when unit definitions have changed.

### Assuming no command output means success

Verify state.

### Using `sudo` without understanding the operation

Privilege does not make an unsafe action safe.

### Practicing on SSH or networking services

Use a disposable unit.

### Killing a systemd-managed process manually without reason

Use the service manager when the task is service lifecycle management.

### Treating `active` as proof the application works correctly

Active service state is important evidence, but functional application testing may require additional checks.

### Forgetting the original state

If you do not record the baseline, you may not know how to restore it.

# 50. Interview Practice

### What is the difference between starting and enabling a service?

Starting changes its current runtime state. Enabling configures systemd enablement relationships so the unit can be pulled in through the relevant activation structure in future system states such as boot.

### Can a service be running but disabled?

Yes. It may have been manually started while remaining disabled.

### Can a service be enabled but stopped?

Yes. Enablement does not guarantee the service is currently active.

### What is the difference between `disable` and `disable --now`?

`disable` changes enablement configuration. `disable --now` also requests that the unit be stopped immediately.

### What is the difference between restart and reload?

Restart replaces the service through a stop/start lifecycle. Reload asks a running service to reload supported configuration without necessarily replacing the process.

### How do you know whether a service supports reload?

I can inspect:

```bash
systemctl show UNIT -p CanReload
```

and also consult the unit/application documentation.

### What does `reload-or-restart` do?

It requests a reload where supported and otherwise performs a restart.

### What is the difference between disabled and masked?

Disabled means the service is not enabled for its normal automatic activation relationship, but it can often still be manually started. Masked blocks normal activation and is therefore stronger.

### When would you use masking?

When I intentionally need to prevent a unit from being activated, rather than merely preventing normal automatic startup.

### Why should you not mask everything you disable?

Because masking is a stronger control with different operational consequences. I use the least restrictive state that satisfies the requirement.

### How do you verify a service after starting it?

I check runtime state with `systemctl is-active`, inspect `systemctl status` or relevant `systemctl show` properties, and perform an appropriate functional test for the actual application.

### Why isn't `active` always enough?

It tells me systemd's runtime state, but the application could still be functionally unhealthy from a user's perspective. Functional verification depends on the service.

### What is `systemctl daemon-reload`?

It reloads systemd unit definitions after relevant unit configuration changes.

### Is `daemon-reload` the same as `systemctl reload UNIT`?

No. `daemon-reload` updates systemd's view of unit definitions. `reload UNIT` asks a running service to reload supported application configuration.

### Why shouldn't restart be your first troubleshooting action?

Because it can cause disruption and destroy useful evidence without identifying the root cause.

### How would you safely restart a production service?

I would identify the exact unit, capture baseline state, understand dependencies and user impact, confirm the change is justified and authorized, verify rollback or recovery options, perform the restart, and verify both systemd state and application behavior afterward.

### Why should you record a service's original state?

So I can restore it correctly after testing or roll back a change without guessing.

### Why use systemctl instead of manually killing a service process?

systemctl operates through the service manager and respects the unit's lifecycle model. Killing a process directly may bypass the intended service-management behavior.
