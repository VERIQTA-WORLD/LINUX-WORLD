# JUN-014: Sudo and Privilege Management

- **Level:** Junior  
- **Difficulty:** 2/5  
- **Estimated time:** 90–120 minutes  
- **Environment:** Ubuntu Server 24.04 LTS or a similar Debian/Ubuntu system  
- **Privileges:** A standard user account with working `sudo` authorization  
- **Primary skills:** Privilege boundaries, `sudo`, root identity, authorization inspection, `sudo -l`, `sudo -u`, sudoers safety, least privilege, auditing and troubleshooting  
- **Prerequisites:** JUN-001 through JUN-013

---

## Lab Mission

Linux administration constantly creates a tension:

```text
A normal user should not have unrestricted administrative power.

But...

Some legitimate tasks require elevated privilege.
```

Examples include:

- managing users and groups,
- changing ownership of protected files,
- administering services,
- modifying system configuration,
- installing software,
- inspecting protected resources,
- managing networking,
- maintaining storage.

Running permanently as `root` would solve the privilege problem by removing the boundary entirely.

That is precisely why it is dangerous.

A better administrative model is:

```text
NORMAL USER
    ↓
requests a privileged operation
    ↓
SUDO POLICY
    ↓
authorization decision
    ↓
approved command executes
    ↓
activity can be attributed to the invoking user
```

In this lab, you will learn what actually happens when you use `sudo`, how Linux distinguishes your normal identity from an elevated process, how to inspect your authorization before attempting changes, how to execute commands as another user, why `sudo` is not the same thing as logging in as root, how sudo policy is configured safely, and how to investigate privilege failures without weakening the system.

The operating principle for this lab is:

> Use ordinary privilege by default. Elevate only the operation that requires it. Verify what identity actually executed the command.

# 2. Understand the Privilege Boundary

The root account has extremely broad authority over the system.

Root can normally perform operations ordinary users cannot, including:

```text
modify protected system configuration
change ownership of files
manage accounts
control many system services
access protected resources
change system-wide settings
```

This power is necessary for administration.

It is also dangerous.

A mistake performed as an ordinary user may affect:

```text
your own files
your own processes
resources you are allowed to control
```

The same mistake performed with root privilege can potentially affect:

```text
the operating system
other users
services
security controls
application data
the entire machine
```

This is why:

```text
Can I run this as root?
```

is not the right first question.

Ask:

```text
Does this operation actually require elevated privilege?
```

---

# 3. Authentication and Authorization Are Different

Privilege management makes more sense when you separate two concepts.

## Authentication

Authentication asks:

```text
Who are you?
```

Examples include proving identity using:

- a password,
- an SSH key,
- another configured authentication mechanism.

## Authorization

Authorization asks:

```text
What are you allowed to do?
```

A successfully authenticated user is not automatically authorized to perform every administrative operation.

The model is:

```text
AUTHENTICATION
Who are you?

        ↓

AUTHORIZATION
What may this identity do?

        ↓

EXECUTION
Run the approved operation.
```

`sudo` participates primarily in the authorization and controlled execution of commands under another identity, commonly root.

---

# 4. What `sudo` Actually Does

The name `sudo` is historically associated with "superuser do," but modern `sudo` can execute commands as identities other than root as well.

The common form is:

```text
sudo COMMAND
```

When policy permits it, the command is normally executed with root privileges.

For example:

```bash
sudo id
```

Compare that with:

```bash
id
```

Your normal command should report your ordinary identity.

The command executed through `sudo` should show an effective identity of root, including:

```text
uid=0(root)
```

You have just demonstrated an important principle:

```text
YOUR SHELL
ordinary user

        ↓ sudo

CHILD COMMAND
privileged identity
```

`sudo` did not permanently transform your entire existing shell into root.

It elevated the requested command.

# 6. Do Not Use `sudo` Automatically

Create a normal file:

```bash
touch ~/linux-world-labs/JUN-014/normal-file.txt
```

Inspect:

```bash
ls -l ~/linux-world-labs/JUN-014/normal-file.txt
```

You own the file.

Therefore, ordinary operations such as:

```bash
rm ~/linux-world-labs/JUN-014/normal-file.txt
```

do not require `sudo`.

Recreate it:

```bash
touch ~/linux-world-labs/JUN-014/normal-file.txt
```

The correct habit is:

```text
Can my normal identity legitimately perform this operation?

YES
→ do not use sudo

NO
→ investigate why

Administrative operation legitimately requires elevation
→ use the minimum required privilege
```

Do not turn:

```bash
sudo
```

into a prefix you add whenever something fails.

A permission error is evidence.

Investigate it.

# 7. Inspect Your Sudo Authorization Before Using It

Run:

```bash
sudo -l
```

Depending on configuration, `sudo` may ask you to authenticate.

The output describes what your account is authorized to run through `sudo`.

On a typical Ubuntu administrative account, you may see broad authorization.

Do not assume your output will exactly match another machine.

Read your actual result.

Look for information such as:

```text
user
host
run-as identity
allowed commands
policy tags/options
```

The engineering workflow is:

```text
INSPECT AUTHORIZATION
        ↓
UNDERSTAND SCOPE
        ↓
EXECUTE REQUIRED OPERATION
        ↓
VERIFY RESULT
```

not:

```text
TRY RANDOM SUDO COMMANDS UNTIL SOMETHING WORKS
```

# 8. The `sudo` Group on Ubuntu

Inspect your groups:

```bash
id
```

Then:

```bash
getent group sudo
```

On Ubuntu, administrative users are commonly granted sudo capability through membership in the:

```text
sudo
```

group together with the system's sudoers policy.

If your account appears in that group, that membership helps explain why the configured sudo policy authorizes you.

But remember:

```text
group membership
```

and:

```text
sudo policy
```

are related but distinct concepts.

The `sudo` command evaluates configured policy.

Do not assume that every Linux distribution uses the same administrative group name or identical policy.

Create:

```bash
mkdir -p ~/linux-world-labs/JUN-014/privilege-test
```

Now create a file as root:

```bash
sudo touch ~/linux-world-labs/JUN-014/privilege-test/root-owned.txt
```

Inspect:

```bash

```

The owner should normally be:

```text
root
```

Why?

Because the `touch` process was executed through `sudo` as root.

This demonstrates something important from JUN-008:

> Unnecessary use of `sudo` can create root-owned objects where you expected user-owned objects.

That can create future permission problems.

# 10. Diagnose the Root-Owned File

Inspect:

```bash

```

Ask:

```text
Who owns it?
Which group owns it?
What permissions are set?
Which identity created it?
Was sudo actually necessary?
```

For a file inside your own lab directory, using `sudo touch` was unnecessary.

It was done only to demonstrate the consequence.

Repair ownership:

```bash
sudo chown "$USER":"$(id -gn)" ~/linux-world-labs/JUN-014/privilege-test/root-owned.txt
```

Verify:

```bash
ls -l ~/linux-world-labs/JUN-014/privilege-test/root-owned.txt
```

The important lesson is:

```text
sudo can solve privilege requirements

but

unnecessary sudo can create new ownership problems
```

# 11. Sudo Authentication and Credential Caching

When you run an authorized sudo command, you may be asked for a password.

On a typical configuration, this is usually the password of the invoking user—not the root password.

After successful authentication, `sudo` can cache that authentication for a limited period according to policy.

That is why:

```bash
sudo id
```

may ask for authentication initially, while another sudo command shortly afterward may not.

This does **not** mean:

```text
sudo no longer checks authorization
```

Authentication caching and authorization are different.

The policy still determines whether the requested command is permitted.

---

# 12. Invalidate Cached Sudo Credentials

Run:

```bash
sudo -k
```

This invalidates the current cached sudo authentication timestamp.

Now run:

```bash
sudo id
```

Depending on your configuration, you should be prompted to authenticate again.

The useful mental model is:

```text
sudo -k
→ invalidate cached authentication
```

This can be useful after completing privileged work, especially on systems where leaving an active authentication timestamp is undesirable.

---

# 13. `sudo -v` — Validate or Refresh Credentials

Inspect:

```bash
sudo --help
```

You may notice:

```text
-v
```

You can run:

```bash
sudo -v
```

This validates or refreshes the user's cached sudo credentials according to policy without running the administrative command you ultimately intend to perform.

This can be useful in controlled workflows where privileged operations will follow.

Do not confuse:

```text
sudo -v
```

with proof that every possible sudo command is authorized.

Use:

```bash
sudo -l
```

to inspect authorization.

# 14. Run a Command as Another User

`sudo` is not limited to root.

The form:

```text
sudo -u USER COMMAND
```

requests execution as another user.

You used this pattern indirectly in JUN-013 to test group-based access.

Create a dedicated practice account:

```bash
getent passwd veriqta-sudo-test
```

If it does not exist, create it:

```bash
sudo useradd -m -s /bin/bash veriqta-sudo-test
```

Verify:

```bash
id veriqta-sudo-test
```

Now run:

```bash
sudo -u veriqta-sudo-test whoami
```

Expected identity:

```text
veriqta-sudo-test
```

Then:

```bash
sudo -u veriqta-sudo-test id
```

You have now demonstrated:

```text
sudo COMMAND
normally requests root execution

sudo -u USER COMMAND
requests execution as USER
```

subject to sudo policy.

# 15. Why `sudo -u` Matters

Imagine an application runs as:

```text
appuser
```

An administrator wants to determine whether that identity can read:

```text
application.conf
```

Testing as root can produce a misleading result because root has privileges the application process does not.

A better diagnostic test can be:

```text
run the operation as the application identity
```

For example:

```bash
sudo -u appuser cat FILE
```

when authorized and appropriate.

This helps answer:

```text
Can the actual service identity perform this operation?
```

rather than:

```text
Can root perform it?
```

Those are very different questions.

# 16. Root Shells vs Single Privileged Commands

You may encounter:

```bash
sudo -i
```

This requests a login-style shell as the target user, root by default.

You may also encounter:

```bash
sudo -s
```

which requests a shell under sudo according to its configured behavior.

These are different from:

```bash
sudo COMMAND
```

A single-command elevation creates a narrower operational boundary:

```text
ordinary shell
    ↓
one privileged command
    ↓
back to ordinary shell
```

A privileged shell creates:

```text
ordinary shell
    ↓
privileged shell
    ↓
many commands now run with elevated privilege
```

The second model increases the chance that an ordinary command is accidentally executed with administrative power.

For routine administration, prefer narrowly scoped commands when practical.

# 17. Recognize When You Are Root

Do not rely only on the appearance of the shell prompt.

Check:

```bash
whoami
```

and:

```bash
id
```

If:

```bash
id -u
```

returns:

```text
0
```

you are operating as the superuser.

A prompt may traditionally use:

```text
$
```

for ordinary users and:

```text
#
```

for root, but prompt appearance can be customized.

Identity commands are stronger evidence.

# 18. Understand `/etc/sudoers`

The primary sudo policy file is commonly:

```text
/etc/sudoers
```

Inspect its metadata:

```bash
sudo ls -l /etc/sudoers
```

You may safely inspect its content using:

```bash
sudo less /etc/sudoers
```

Do not modify it with a normal text editor during this lab.

The sudoers policy can define:

- which users may use sudo,
- which groups may use sudo,
- which hosts rules apply to,
- which identities commands may run as,
- which commands are permitted,
- policy options,
- authentication behavior and tags.

This makes sudo much more than:

```text
become root
```

It is a policy-controlled privilege delegation system.

# 19. Basic Sudoers Syntax

You may encounter a rule resembling:

```text
USER HOST=(RUNAS) COMMANDS
```

A broad example is:

```text
alice ALL=(ALL:ALL) ALL
```

Conceptually:

```text
alice
→ rule applies to this user

ALL
→ applicable hosts in this context

(ALL:ALL)
→ permitted run-as user/group scope

ALL
→ command scope
```

You do not need to memorize every sudoers grammar feature in this junior lab.

The key idea is:

```text
WHO
can run

WHAT
command

AS WHOM
under

WHICH POLICY
```

---

# 20. Group-Based Sudoers Rules

In sudoers syntax, a group is typically referenced with `%`.

For example, Ubuntu commonly includes a rule conceptually resembling:

```text
%sudo ALL=(ALL:ALL) ALL
```

The `%` indicates:

```text
sudo group
```

rather than a user named `sudo`.

This connects directly to JUN-013:

```text
USER
    ↓
GROUP MEMBERSHIP
    ↓
SUDOERS GROUP RULE
    ↓
AUTHORIZED PRIVILEGED ACTION
```

This is one reason group management is security-sensitive.

Adding a user to an administrative group can significantly change that user's capabilities.

---

# 21. `/etc/sudoers.d/`

Modern sudo configurations can also include policy fragments from a directory such as:

```text
/etc/sudoers.d/
```

Inspect:

```bash
sudo ls -la /etc/sudoers.d/
```

Your system's contents may differ.

Do not modify existing files.

The directory allows sudo policy to be organized into separate files instead of placing every rule directly inside:

```text
/etc/sudoers
```

This is useful for:

- configuration management,
- role-specific policy,
- application-specific administration,
- easier maintenance,
- reducing direct edits to the primary file.

But a separate file is still security-sensitive policy.

It must be managed carefully.

---

# 22. Why `visudo` Matters

Never casually edit sudoers configuration with an ordinary editor.

The standard tool is:

```bash
sudo visudo
```

Its major safety advantage is that it validates sudoers syntax before accepting changes.

A syntax error in privilege policy can cause serious administrative problems, including loss of expected sudo access.

For this lab, do **not** make changes to the main sudoers file.

Instead inspect the tool:

```bash
man visudo
```

and:

```bash
visudo --help
```

The principle is:

```text
SUDO POLICY CHANGE
        ↓
use sudoers-aware validation
        ↓
syntax check
        ↓
install valid policy
```

not:

```text
open /etc/sudoers
        ↓
type something
        ↓
hope sudo still works
```

# 23. Validate Sudoers Syntax

You can ask `visudo` to check sudoers configuration rather than interactively editing it.

Run:

```bash
sudo visudo -c
```

A healthy configuration should report successful parsing for the relevant sudoers files.

Exact output depends on the system.

This is an important verification habit:

```text
configuration exists
```

is not enough.

You want:

```text
configuration parses correctly
```

# 24. Least Privilege

Least privilege means:

> Give an identity only the privileges required to perform its legitimate function, and no more than necessary.

Compare:

```text
Engineer needs to restart one approved service.
```

with:

```text
Give engineer unrestricted root access.
```

The second grants far more capability than the requirement describes.

A least-privilege design asks:

```text
What exact operation is required?
Who needs it?
As which identity?
On which systems?
Under what conditions?
How will it be audited?
Can the scope be reduced?
```

This becomes increasingly important in:

- production servers,
- CI/CD systems,
- cloud environments,
- shared administration,
- regulated systems,
- security-sensitive infrastructure.

---

# 25. `sudo` Does Not Mean "Safe"

A command does not become safe because it starts with:

```text
sudo
```

In fact, elevation increases its potential impact.

For example:

```text
ordinary destructive command
```

may be limited by ordinary permissions.

The same operation with root privilege may bypass those boundaries.

Therefore:

```text
sudo
```

should make you **more careful**, not less.

Before an unfamiliar privileged command, ask:

```text
What will this command change?
Which files/processes/services are affected?
Is the target exact?
Can I inspect first?
Can I make the change more narrowly?
How will I verify it?
How will I recover if it is wrong?
```

# 26. Controlled Failure — No Privilege

Create a root-owned directory in the lab's temporary area:

```bash
sudo mkdir -p /tmp/veriqta-jun014/protected
sudo chown root:root /tmp/veriqta-jun014/protected

Inspect:

```

Now attempt as your normal identity:

```bash
touch /tmp/veriqta-jun014/protected/test.txt
```

It should fail.

Do not immediately rerun it with sudo.

Investigate first:

```bash
whoami
id
ls -ld /tmp/veriqta-jun014/protected
```

Your evidence should show:

```text
directory owner:
root

directory group:
root

owner mode:
rwx

group:
---

other:
---
```

Your ordinary process qualifies for neither root ownership nor an allowed permission class.

The failure is expected.

# 29. Controlled Failure — Sudo Authorization Is Policy-Based

Run:

```bash
sudo -l
```

Study what your account is actually allowed to execute.

On many personal Ubuntu lab systems, the administrative account may have broad sudo access.

On managed production systems, a user may instead be authorized for only selected commands.

Therefore:

```text
sudo installed
```

does not mean:

```text
every user can run every command as root
```

Authorization depends on policy.

A user may be authenticated successfully and still be denied a requested sudo operation.

That is an authorization failure.

# 30. Inspect Sudo Activity

On Ubuntu systems using systemd journal logging, try:

```bash
sudo journalctl _COMM=sudo
```

If your environment does not expose useful results through that filter, inspect authentication-related logs using the facilities available on your system.

Ubuntu systems may record sudo-related events in locations such as:

```text
/var/log/auth.log
```

depending on logging configuration.

For example:

```bash
sudo grep sudo /var/log/auth.log
```

may show relevant records if that file exists and sudo events are routed there.

Do not assume every distribution logs sudo activity in the same location.

Look for evidence that can answer questions such as:

```text
Which user invoked sudo?
When?
What command was requested?
Was the operation accepted or denied?
Which session or terminal was involved?
```

This is why controlled privilege delegation improves accountability compared with casually sharing direct root access.

# 31. Privilege Troubleshooting Model

When a privileged operation fails, use this sequence:

```text
SYMPTOM
What failed?

        ↓

CURRENT IDENTITY
whoami
id

        ↓

REQUIRED OPERATION
Does this genuinely require elevation?

        ↓

RESOURCE STATE
ownership
permissions
path
service/configuration state

        ↓

SUDO AVAILABILITY
Is sudo installed and callable?

        ↓

AUTHORIZATION
sudo -l

        ↓

AUTHENTICATION
Did authentication succeed?

        ↓

TARGET IDENTITY
Root?
Another user?

        ↓

COMMAND
Is the command itself valid?

        ↓

POLICY
Does sudo policy permit it?

        ↓

LOGS
What evidence was recorded?

        ↓

ROOT CAUSE
filesystem permission?
sudo authorization?
authentication?
wrong target user?
invalid command?
application/security layer?

        ↓

FIX
Change only the incorrect layer.

        ↓

VERIFY
Prove the required operation works.
```

Do not treat every privilege failure as a sudo problem.

# 32. Production Scenario — "Just Give Me Root"

A developer reports:

> My deployment task cannot update the application directory. Give me root access.

Do not begin with the requested solution.

Investigate the requirement.

Ask:

```text
Which process needs access?
Which directory?
What exact operation?
Which user runs the deployment?
Which group owns the directory?
What permissions exist?
Does the user already belong to the correct group?
Is root actually required?
```

You may discover the real problem is:

```text
wrong group membership
```

or:

```text
wrong group ownership
```

or:

```text
missing group write permission
```

In that case, unrestricted sudo access would not be the appropriate fix.

Privilege escalation should not replace proper ownership and permission design.

# 33. Engineer Notes

### Use normal privilege first

Ordinary work should remain ordinary.

### Investigate `Permission denied`

It tells you a boundary was enforced.

### Do not use `sudo` as a troubleshooting reflex

Find the root cause first.

### Prefer one elevated command over an unnecessary root shell

Smaller privilege windows reduce accidental impact.

### Inspect authorization

Use:

```bash
sudo -l
```

### Verify target identity

Use:

```bash
whoami
id
```

and, where appropriate:

```bash
sudo -u USER id
```

### Protect sudoers configuration

Use `visudo` and syntax validation.

### Do not grant unrestricted administrative privilege merely for convenience

Design access around actual operational requirements.

### Remember that administrative groups are security-sensitive

Changing group membership can change privilege.

### Keep evidence

Privileged changes should be attributable and verifiable.

# 37. Knowledge Check

### 1. What is special about UID `0`?

UID `0` represents the Linux superuser identity, traditionally called `root`.

### 2. What does `sudo COMMAND` normally request?

Execution of the command as root, subject to sudo policy.

### 3. Does using `sudo` permanently turn your current shell into root?

No. A normal `sudo COMMAND` executes the requested command under the authorized target identity.

### 4. What command shows your current username?

```bash
whoami
```

### 5. What command shows detailed identity information?

```bash
id
```

### 6. How can you prove a command executed as root?

Inspect its execution identity, for example:

```bash
sudo id
```

and verify UID `0`.

### 7. What is authentication?

The process of establishing or proving identity.

### 8. What is authorization?

The decision about what an authenticated identity is permitted to do.

### 9. Does successful authentication guarantee sudo authorization?

No.

### 10. What command lists your sudo privileges?

```bash
sudo -l
```

### 11. Why should you inspect `sudo -l`?

It helps you understand the sudo policy applicable to your account instead of assuming unrestricted privilege.

### 12. What does `sudo -u USER COMMAND` do?

It requests execution of the command as the specified user, subject to policy.

### 13. Why might you test a command as an application user rather than root?

Because root may succeed where the real application identity fails, producing misleading troubleshooting results.

### 14. What does `sudo -k` do?

It invalidates the user's cached sudo authentication timestamp.

### 15. Does `sudo -k` remove the user's sudo authorization?

No. Authorization comes from policy.

### 16. What does `sudo -v` do?

It validates or refreshes cached sudo credentials according to policy without running the intended administrative command.

### 17. What is `/etc/sudoers`?

A primary sudo policy configuration file.

### 18. What is `/etc/sudoers.d/` commonly used for?

Additional sudo policy fragments.

### 19. Why should `visudo` be used for sudoers changes?

It understands sudoers configuration and validates syntax, reducing the risk of installing invalid policy.

### 20. How can you validate sudoers syntax?

```bash
sudo visudo -c
```

### 21. What does `%groupname` represent in sudoers syntax?

A Unix/Linux group referenced by the sudo policy.

### 22. Why is membership in an administrative group security-sensitive?

Because sudo policy can grant privileges based on group membership.

### 23. What is least privilege?

Granting only the access and capabilities required for a legitimate function, rather than broader authority.

### 24. Why is `sudo` not a universal solution to `Permission denied`?

The actual problem may be ownership, permissions, group membership, stale credentials, an incorrect path, application policy, or another security layer. Elevation can hide rather than repair the real issue.

### 25. Why can unnecessary sudo create ownership problems?

Files or directories created by elevated processes may become owned by root instead of the intended normal user.

### 26. What is the difference between `sudo COMMAND` and `sudo -i`?

`sudo COMMAND` elevates a specific command. `sudo -i` requests a login-style shell as the target user, root by default.

### 27. Why can a long-lived root shell be riskier?

Subsequent commands are executed with elevated privilege, increasing the potential impact of mistakes.

### 28. Should shell prompt appearance alone be trusted to determine whether you are root?

No. Verify with commands such as `whoami`, `id`, or `id -u`.

### 29. Why are sudo logs useful?

They can provide evidence about privilege use, including who invoked sudo, when it happened, and potentially what command was requested.

### 30. What is the preferred response when an ordinary command fails with `Permission denied`?

Inspect the identity, target ownership, permissions, path and actual operational requirement before deciding whether elevation is appropriate.

# 38. Interview Practice

### What is `sudo`?

`sudo` is a policy-controlled mechanism that allows an authorized user to execute commands as another identity, commonly root, without requiring the user to operate permanently as that identity.

### What is the difference between root and sudo?

Root is the superuser identity with UID `0`. `sudo` is a mechanism and policy system used to authorize and execute particular commands as another identity, often root.

### What is the difference between authentication and authorization?

Authentication establishes who the user is. Authorization determines what that identity is permitted to do.

### How do you determine what sudo commands you are allowed to run?

I inspect:

```bash
sudo -l
```

and interpret the applicable run-as and command scope rather than assuming unrestricted access.

### Why should you not automatically use sudo after `Permission denied`?

Because the error may indicate an intentional access boundary or a configuration problem involving ownership, permissions, group membership, path traversal or another security mechanism. I investigate the cause first and elevate only if the operation legitimately requires administrative privilege.

### What does `sudo -u` do?

It requests command execution as a specified user. This is useful for administrative operations and for testing behavior under the identity that actually runs an application or service.

### Why can unnecessary sudo cause file ownership problems?

An elevated process may create files owned by root. The normal user can then encounter access problems with files that should have been created under their own identity.

### Why use `visudo`?

Because sudo policy is security-critical. `visudo` provides sudoers-aware editing and syntax validation, reducing the risk of installing invalid configuration.

### What is least privilege?

It is the principle of granting an identity only the privileges necessary to perform its required function and avoiding unnecessary authority.

### Why is giving a developer full sudo access not automatically the right solution to a deployment permission problem?

The deployment may only require correct group membership, group ownership or limited administrative capability. Full sudo would grant authority far beyond the stated requirement. I would investigate the actual operation and design the narrowest appropriate access.

### How would you investigate a sudo failure?

I would establish the invoking identity, determine the required operation, inspect `sudo -l`, distinguish authentication from authorization, verify the requested target identity and command, inspect relevant sudo logs, identify the failed layer, then change only the configuration that is actually incorrect.

### How would you prove a service account can access a file?

Where authorized, I would test the relevant operation as that account, for example with `sudo -u SERVICE_USER`, rather than testing as root and assuming the service will behave the same way.
