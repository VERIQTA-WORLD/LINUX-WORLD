## 1. Lab Mission

In JUN-026, you learned that Linux processes commonly work with three standard streams:

```text
stdin   = file descriptor 0
stdout  = file descriptor 1
stderr  = file descriptor 2
```

You also redirected those streams between commands and files.

For example:

```bash
wc -l < input.txt > count.txt
```

creates this flow:

```text
input.txt
    │
    │ stdin
    ▼
   wc
    │
    │ stdout
    ▼
 count.txt
```

But Linux commands become much more powerful when you can connect **processes directly**.

Instead of:

```text
command
   ↓
temporary file
   ↓
another command
```

you can often create:

```text
command A
    │
    │ stdout
    ▼
    |
    │
    │ stdin
    ▼
command B
```

That is a **pipeline**.

Bash also lets you control whether another command should run:

```text
after the first command regardless
```

or:

```text
only if the previous command succeeded
```

or:

```text
only if the previous command failed
```

These are related shell skills, but they solve different problems.

Your core distinction for this lab is:

```text
PIPELINES
move data between commands
```

versus:

```text
COMMAND CHAINING
controls whether commands execute
```

By the end of this lab, you should be able to read a compound command and explain both:

1. **where the data flows**, and
2. **why each command executes**.

### Learning objectives

You will learn to:

- explain what a pipe does;
- connect stdout from one command to stdin of another;
- build simple multi-stage pipelines;
- distinguish pipes from redirection;
- understand what happens to stderr in a normal pipeline;
- use `;` for unconditional sequencing;
- use `&&` for success-dependent execution;
- use `||` for failure-dependent execution;
- connect chaining decisions to command exit status;
- explain short-circuit behavior;
- combine pipelines with redirection safely;
- distinguish data flow from execution control;
- troubleshoot common pipeline and chaining mistakes.

### Lab boundary

This lab deliberately does **not** teach:

```text
grep
sed
awk
find
xargs
tee
shell scripting
advanced pipeline status handling
```

Those concepts either have their own later labs or require foundations you have not yet completed.

## 2. Understand the Two Models

Create the lab workspace:

```bash
mkdir -p ~/linux-world-labs/JUN-027
```

Enter it:

```bash
cd ~/linux-world-labs/JUN-027
```

Verify:

```bash
pwd
```

Now create a small practice file:

```bash
nano engineers.txt
```

Enter:

```text
Ada
Grace
Linus
Ken
Margaret
Dennis
```

Save and exit.

Verify:

```bash
cat engineers.txt
```

You are now ready to distinguish the two models used throughout this lab.

### Model A — Data flow

Consider:

```bash
cat engineers.txt | wc -l
```

The pipe:

```text
|
```

connects stdout from the command on its left to stdin of the command on its right.

Conceptually:

```text
engineers.txt
     │
     ▼
    cat
     │
     │ stdout
     ▼
     |
     │
     │ stdin
     ▼
    wc -l
     │
     ▼
  terminal
```

### Model B — Execution control

Now consider:

```bash
pwd && echo "pwd succeeded"
```

This does not mean:

```text
send pwd output into echo
```

Instead:

```text
run pwd
   │
   ▼
did it succeed?
   │
  yes
   │
   ▼
run echo
```

So keep this distinction throughout the lab:

| Syntax | Primary purpose |
|---|---|
| `|` | Connect data streams |
| `;` | Run next command afterward |
| `&&` | Run next command if previous command succeeds |
| `||` | Run next command if previous command fails |

## 3. Build Your First Pipeline

Run:

```bash
cat engineers.txt
```

`cat` writes the file contents to stdout.

Now run:

```bash
cat engineers.txt | wc -l
```

A typical result is:

```text
6
```

What happened?

The shell created both commands and connected them:

```text
cat engineers.txt
       │
       │ stdout
       ▼
      PIPE
       │
       │ stdin
       ▼
     wc -l
       │
       │ stdout
       ▼
    terminal
```

The output from `cat` does not need to be written to a temporary file first.

The pipe carries the data directly to `wc`.

### Compare with redirection

In JUN-026 you could write:

```bash
cat engineers.txt > temporary.txt
```

followed by:

```bash
wc -l < temporary.txt
```

That uses a file as an intermediate destination.

The pipeline:

```bash
cat engineers.txt | wc -l
```

connects the processes directly.

The key distinction is:

```text
>
stdout → file
```

while:

```text
|
stdout → another command's stdin
```

## 4. Pipelines Can Have Multiple Stages

A pipeline is not limited to two commands.

Create:

```bash
nano numbers.txt
```

Enter:

```text
40
10
30
20
50
```

Save and exit.

Inspect:

```bash
cat numbers.txt
```

You learned `sort` in JUN-029's future curriculum, but you have not formally reached that lab yet. Therefore, we will **not** depend on `sort` here.

Instead, use commands already established.

Run:

```bash
cat engineers.txt | head -n 4
```

You should see the first four lines.

Now:

```bash
cat engineers.txt | head -n 4 | wc -l
```

A typical result is:

```text
4
```

The flow is:

```text
engineers.txt
     │
     ▼
    cat
     │
     ▼
     |
     │
     ▼
 head -n 4
     │
     ▼
     |
     │
     ▼
   wc -l
     │
     ▼
 terminal
```

Each stage receives data through stdin and produces output for the next stage where the command supports that model.

### Read pipelines from left to right

When investigating:

```bash
cat engineers.txt | head -n 4 | wc -l
```

read:

```text
1. cat produces the file contents

2. head receives those contents and keeps the first four lines

3. wc receives those four lines and counts them
```

Do not treat a pipeline as one mysterious command.

It is several commands connected by data streams.

## 5. The Pipe Normally Carries stdout, Not stderr

This is one of the most important rules in the lab.

Run:

```bash
cat missing-file.txt | wc -l
```

You should normally still see an error from `cat`.

You may also see a line count from `wc`.

Why?

A normal pipe connects:

```text
left command stdout
        │
        ▼
right command stdin
```

It does not automatically send the left command's stderr through the same pipe.

Conceptually:

```text
                cat missing-file.txt
                    /          \
                   /            \
              stdout            stderr
                 │                │
                 ▼                ▼
                PIPE           terminal
                 │
                 ▼
               wc -l
```

Because the missing file produced no normal file content, `wc` may receive no useful stdout from `cat`.

But `cat`'s diagnostic remains on stderr.

This connects directly to JUN-026:

```text
stdout
≠
stderr
```

and therefore:

```text
pipe stdout
≠
automatically pipe stderr
```

More advanced manipulation of pipeline error streams is outside this junior lab.

For now, always ask:

> Which stream is actually entering the pipe?

## 6. Combine a Pipeline with Redirection

The final command in a pipeline still has stdout.

That output can be redirected.

Run:

```bash
cat engineers.txt | wc -l > engineer-count.txt
```

Inspect:

```bash
cat engineer-count.txt
```

You should see:

```text
6
```

The flow is:

```text
engineers.txt
     │
     ▼
    cat
     │ stdout
     ▼
     |
     │ stdin
     ▼
   wc -l
     │ stdout
     ▼
engineer-count.txt
```

The pipe and redirection are doing different jobs:

```text
|
connects process → process
```

while:

```text
>
connects stdout → file
```

You can also append the final output:

```bash
cat engineers.txt | wc -l >> counts.log
```

Run it again:

```bash
cat engineers.txt | wc -l >> counts.log
```

Inspect:

```bash
cat counts.log
```

You should now have two recorded counts.

This is where the previous lab becomes part of your working command-line model rather than an isolated topic.

## 7. Sequence Commands with `;`

A semicolon separates commands.

Run:

```bash
pwd ; echo "second command"
```

Both commands run in sequence.

Now deliberately make the first command fail:

```bash
cat definitely-missing.txt ; echo "second command still ran"
```

You should see the `cat` error and then:

```text
second command still ran
```

The model is:

```text
COMMAND A
    │
    ▼
 finishes
    │
    ▼
COMMAND B
```

The second command does not require the first one to succeed.

So:

```text
;
```

means approximately:

> After this command finishes, continue with the next command.

It does **not** mean:

> Run the next command only if this one succeeds.

That distinction matters when the second operation depends on the first.

## 8. Run the Next Command Only After Success with `&&`

You learned exit codes in JUN-024's command-resolution context only indirectly, but formal exit-code treatment comes later in JUN-064. For this lab, you need one foundational rule:

```text
commands report completion status
```

At this stage, treat:

```text
successful command
```

as a condition Bash can use to decide whether to continue through `&&`.

Run:

```bash
cat engineers.txt && echo "File read succeeded"
```

Because `cat` successfully reads the file, the second command should run.

Now:

```bash
cat missing-file.txt && echo "File read succeeded"
```

The second command should not run.

Conceptually:

```text
COMMAND A
    │
    ▼
success?
 ┌──┴──┐
yes    no
 │      │
 ▼      ▼
run B   stop this && chain
```

This is **short-circuit execution**.

The right-hand command is skipped when the left side does not meet the required success condition.

### Why this matters

Compare:

```bash
mkdir demo ; cd demo
```

with:

```bash
mkdir demo && cd demo
```

The second form expresses an important dependency:

```text
create directory successfully
        ↓
only then enter it
```

That is often safer when command B only makes sense if command A succeeded.

For the lab, use a disposable directory:

```bash
mkdir success-test && cd success-test
```

Verify:

```bash
pwd
```

Return:

```bash
cd ..
```

Remove it:

```bash
rmdir success-test
```

## 9. Run a Command Only After Failure with `||`

The opposite conditional operator is:

```text
||
```

Run:

```bash
cat missing-file.txt || echo "The file could not be read"
```

Because `cat` fails, the second command runs.

Now:

```bash
cat engineers.txt || echo "The file could not be read"
```

Because `cat` succeeds, the second command should be skipped.

The model is:

```text
COMMAND A
    │
    ▼
failed?
 ┌──┴──┐
yes    no
 │      │
 ▼      ▼
run B   skip B
```

A useful interpretation is:

```text
&& = continue on success

|| = continue on failure
```

### Operational use

This allows patterns such as:

```bash
cat configuration.txt || echo "Configuration could not be read"
```

The second command is not processing `cat`'s output.

It is responding to whether `cat` succeeded.

That is execution control, not data flow.

## 10. Read Compound Commands Correctly

Consider:

```bash
cat engineers.txt | wc -l && echo "Count completed"
```

There are two different mechanisms here.

First:

```text
cat engineers.txt | wc -l
```

is a pipeline.

Then:

```text
&& echo "Count completed"
```

is conditional execution.

Conceptually:

```text
engineers.txt
     │
     ▼
    cat
     │
     ▼
     |
     │
     ▼
   wc -l
     │
     ▼
pipeline completes
     │
     ▼
success condition satisfied?
     │
    yes
     │
     ▼
echo "Count completed"
```

Do not interpret:

```text
|
```

and:

```text
&&
```

as interchangeable separators.

They represent different relationships.

### Another example

Run:

```bash
cat engineers.txt | head -n 2 > preview.txt && cat preview.txt
```

Break it down:

```text
cat engineers.txt
        ↓
pipe data to head
        ↓
head keeps two lines
        ↓
redirect result to preview.txt
        ↓
if the pipeline command list is considered successful
        ↓
cat preview.txt
```

Inspect the result yourself.

The goal is to learn to decompose compound commands rather than memorize them as strings.

## 11. Controlled Failures and Troubleshooting

### Failure 1 — Using `;` when the second command depends on success

Create:

```bash
mkdir deployment-test
```

Now deliberately try:

```bash
mkdir deployment-test ; echo "Directory creation complete"
```

`mkdir` should report that the directory already exists, but the `echo` command still runs.

That message can be misleading.

You told Bash:

```text
run the second command regardless
```

A better dependency expression is:

```bash
mkdir another-test && echo "Directory creation complete"
```

The message appears only when `mkdir` succeeds.

Remove the test directory:

```bash
rmdir another-test
```

### Failure 2 — Expecting stderr to enter a normal pipe

Run:

```bash
cat missing-pipeline-file.txt | wc -l
```

**Symptom:** The error still appears in the terminal.

**Evidence:** `wc` receives the normal output stream, while `cat` reports its failure separately.

**Root cause:** `|` connects stdout to the next command's stdin. stderr is a separate stream.

**Lesson:** Identify the stream before deciding how data should move.

### Failure 3 — Confusing `||` with a pipe

These are visually similar:

```text
|
||
```

but their meanings are completely different.

```text
|
```

means:

```text
send stdout into another command's stdin
```

while:

```text
||
```

means:

```text
run the next command if the previous command fails
```

Never read shell syntax only by shape.

### Failure 4 — Hiding an earlier problem behind later output

Run:

```bash
cat missing.txt ; echo "Operation finished"
```

You see:

```text
an error
```

followed by:

```text
Operation finished
```

The second message does not prove the first operation succeeded.

This is why command sequencing must reflect actual dependencies.

### Failure 5 — Assuming a pipeline proves every stage succeeded

A pipeline can involve several processes.

Seeing useful-looking final output does not automatically prove that every stage behaved exactly as intended.

At this level, inspect:

- input,
- each command's purpose,
- visible errors,
- resulting output.

Advanced pipeline status behavior and `pipefail` belong to later Bash/error-handling work.

### Troubleshooting model

When a compound command behaves unexpectedly:

```text
SYMPTOM
   ↓
SPLIT THE COMMAND INTO STAGES
   ↓
WHICH SYMBOL CONNECTS THEM?
   ↓
|  ;  &&  ||
   ↓
DATA FLOW OR EXECUTION CONTROL?
   ↓
IF PIPE:
which stdout enters which stdin?
   ↓
IF CHAIN:
what condition controls the next command?
   ↓
RUN COMPONENTS INDIVIDUALLY
   ↓
VERIFY INPUT AND OUTPUT
   ↓
IDENTIFY FAILURE
   ↓
MAKE MINIMUM CORRECTION
   ↓
RETEST COMPLETE COMMAND
```

This is more reliable than repeatedly changing symbols until the command appears to work.

### Knowledge Check

1. **What does a pipe do?**  
   It connects stdout from the command on its left to stdin of the command on its right.

2. **Which standard stream normally enters a pipe?**  
   stdout.

3. **Does stderr automatically enter a normal `|` pipeline?**  
   No.

4. **What is the difference between `>` and `|`?**  
   `>` redirects stdout to a file. `|` connects stdout to another command's stdin.

5. **Can a pipeline contain more than two commands?**  
   Yes.

6. **What does `;` do?**  
   It separates commands so the next command runs after the previous one finishes, without requiring the previous command to succeed.

7. **What does `&&` do?**  
   It runs the next command only when the preceding command/list satisfies the shell's success condition.

8. **What does `||` do?**  
   It runs the next command when the preceding command/list satisfies the shell's failure condition.

9. **What is short-circuit execution?**  
   It is the behavior where Bash skips part of an `&&` or `||` list because the previous result already determines whether that next command should execute.

10. **Is `|` the same as `||`?**  
    No. `|` creates a pipeline; `||` controls execution after failure.

11. **Does `&&` send one command's output into another command?**  
    No. It controls whether the next command executes.

12. **Can pipeline output still be redirected to a file?**  
    Yes.

13. **Why can `command ; echo "success"` be misleading?**  
    Because the `echo` runs even if the first command fails.

14. **Why should compound commands be broken into stages during troubleshooting?**  
    It lets you identify which command, data stream, or execution condition is causing the unexpected behavior.

15. **Does useful-looking final pipeline output automatically prove every pipeline stage succeeded?**  
    No. Pipeline status behavior requires careful interpretation, and more advanced handling is covered later.

### Interview Practice

**What is a Linux pipeline?**

A pipeline connects the standard output of one command to the standard input of another, allowing processes to exchange data directly.

**What is the difference between a pipe and output redirection?**

A pipe sends stdout to another process. Output redirection sends stdout to another destination such as a file.

**Does a normal pipe include stderr?**

No. A standard `|` pipeline connects stdout from the left command to stdin of the right command. stderr remains separate unless explicitly handled.

**What is the difference between `;` and `&&`?**

`;` runs the next command after the previous command finishes regardless of success. `&&` runs the next command only when the preceding command or list meets the success condition.

**What is the difference between `&&` and `||`?**

`&&` continues when the previous result is successful. `||` continues when the previous result represents failure.

**Why are `|` and `||` fundamentally different?**

`|` controls data flow between processes. `||` controls execution based on failure status.

**How would you troubleshoot a long pipeline?**

I would identify each stage, run the components separately when practical, determine what each stage receives and produces, watch stderr separately from stdout, and then rebuild the pipeline progressively.

**Why can command chaining improve operational safety?**

It can express real dependencies. For example, `command-a && command-b` prevents command B from running when command A does not complete successfully.
