# JUN-022: Service Status and Logs

- **Level:** Junior  
- **Difficulty:** 2/5  
- **Estimated time:** 90–120 minutes  
- **Environment:** Ubuntu Server 24.04 LTS with systemd  
- **Privileges:** Standard user for most inspection; authorized `sudo` only where required  
- **Primary skills:** service status interpretation, systemd state evidence, failed-unit investigation, service process correlation, targeted service logs, controlled service failure, recovery verification  
- **Prerequisites:** JUN-001 through JUN-021

---

## Lab Mission

In JUN-020, you learned how systemd represents services as units.

In JUN-021, you learned how to deliberately change a service lifecycle:

```text
start
stop
restart
reload
enable
disable
mask
unmask
```

Now the question changes.

Instead of:

> How do I change this service?

you need to answer:

> What state is this service actually in, and what evidence explains that state?

That distinction matters.

A production engineer should not see:

```text
service failed
```

and immediately respond with:

```bash
sudo systemctl restart service
```

A restart may restore service temporarily.

It may also destroy useful evidence without explaining the failure.

The investigation should begin with evidence:

```text
SERVICE PROBLEM
      ↓
IDENTIFY EXACT UNIT
      ↓
READ CURRENT STATE
      ↓
INSPECT SERVICE PROCESS
      ↓
READ RELEVANT SERVICE LOGS
      ↓
BUILD HYPOTHESIS
      ↓
TEST HYPOTHESIS
      ↓
IDENTIFY ROOT CAUSE
      ↓
FIX
      ↓
VERIFY RECOVERY
```

In this lab, you will deliberately create a disposable service, observe it while healthy, break it safely, investigate its failure, repair it, and prove recovery.

You will use `journalctl`, but only for **targeted service evidence**.

The full Linux logging and `journalctl` curriculum comes later.

---

## Learning Objectives

By the end of this lab, you should be able to:

- Explain what `systemctl status` tells you.
- Identify a service's load state.
- Identify its active state.
- Identify its substate.
- Distinguish `active`, `inactive`, and `failed`.
- Explain why `loaded` does not mean healthy.
- Explain why `active` does not prove application correctness.
- Identify the service's MainPID where applicable.
- Correlate systemd service information with `ps`.
- Use `systemctl show` for precise state properties.
- Use `systemctl is-active` as a focused state check.
- Use `systemctl --failed` to identify failed units.
- Explain what a failed unit state means.
- Use `journalctl -u UNIT` to inspect logs for one service.
- Use `journalctl -u UNIT -n NUMBER` to limit displayed records.
- Use `journalctl -u UNIT --since` for a simple time-bounded investigation.
- Use `journalctl -u UNIT -b` to focus on the current boot.
- Explain why logs are evidence rather than automatic root-cause conclusions.
- Establish a healthy service baseline.
- Create a controlled service failure.
- Distinguish symptom, evidence, hypothesis, root cause, fix, and verification.
- Repair a broken service safely.
- Use `daemon-reload` after changing a unit definition.
- Verify service recovery independently.
- Understand what `reset-failed` does.
- Avoid clearing failure state before collecting evidence.
- Document a basic service incident investigation.

# 1. Status Is Evidence, Not a Diagnosis

Consider this output conceptually:

```text
● example.service - Example Service
     Loaded: loaded (...)
     Active: failed (...)
```

You know something important:

```text
the unit failed
```

But you do not yet know:

```text
why it failed
```

The status is evidence.

It is not automatically the root cause.

A useful mental model is:

```text
STATUS
  ↓
WHAT STATE IS THE SERVICE IN?

LOGS
  ↓
WHAT EVENTS DID THE SERVICE OR SYSTEM RECORD?

PROCESS EVIDENCE
  ↓
WHAT PROCESS EXISTS OR DISAPPEARED?

CONFIGURATION
  ↓
WHAT WAS THE SERVICE ASKED TO DO?

ENGINEERING REASONING
  ↓
WHAT BEST EXPLAINS THE EVIDENCE?
```

The goal is not to collect commands.

The goal is to construct an evidence-supported explanation.

# 2. Build a Safe Investigation Service

You will not intentionally break:

```text
ssh.service
networking
logging infrastructure
firewall services
storage services
production applications
```

Instead, create:

```text
veriqta-jun022.service
```

Create the lab workspace:

```bash
mkdir -p ~/linux-world-labs/JUN-022
```

Move into it:

```bash
cd ~/linux-world-labs/JUN-022
```

Verify:

```bash
pwd
```

Now create the service:

```bash
sudo systemctl edit --force --full veriqta-jun022.service
```

Your configured editor will open.

Enter:

```ini
[Unit]
Description=VERIQTA JUN-022 Service Status and Logs Lab

[Service]
Type=simple
ExecStart=/usr/bin/sleep 3600

[Install]
WantedBy=multi-user.target
```

Save and exit.

You used the same systemd editing workflow in JUN-021.

Inspect the result:

```bash
systemctl cat veriqta-jun022.service
```

Now reload systemd's unit definitions:

```bash
sudo systemctl daemon-reload
```

Do not confuse this with:

```bash
sudo systemctl reload veriqta-jun022.service
```

They operate at different layers.

# 4. Read `systemctl status` Deliberately

Run:

```bash
systemctl status veriqta-jun022.service
```

Instead of scanning randomly, read the output in layers.

## Identity

At the top, identify:

```text
unit name
description
```

Ask:

> Am I investigating the correct service?

A perfect diagnosis of the wrong unit is still wrong.

---

## Loaded Information

You should see information beginning with:

```text
Loaded:
```

This tells you whether systemd successfully loaded the unit definition and may also show its source and enablement information.

A unit can be:

```text
loaded
```

and still:

```text
failed
```

Therefore:

```text
loaded
≠
healthy
```

---

## Active Information

You should see:

```text
Active:
```

This gives the high-level runtime state.

Possible states include:

```text
active
inactive
failed
activating
deactivating
```

You learned these concepts in JUN-020.

Now you are using them during an investigation.

---

## Main PID

For a running service with a main process, status may display:

```text
Main PID:
```

That lets you connect:

```text
SYSTEMD SERVICE
       ↓
MAIN PROCESS
```

This is useful evidence, but remember:

```text
unit
≠
process
```

systemd is managing the service as a larger lifecycle object.

---

## Recent Journal Messages

`systemctl status` commonly displays a limited set of recent journal records associated with the unit.

This gives you immediate context.

But it is not necessarily the complete history.

That distinction matters:

```text
systemctl status
        ↓
useful service summary + recent evidence

journalctl
        ↓
deeper journal inspection
```

# 5. Use `systemctl show` for Precise Properties

`status` is designed for human reading.

`show` can retrieve specific structured properties.

Run:

```bash
systemctl show veriqta-jun022.service -p Id -p LoadState -p ActiveState -p SubState -p MainPID
```

A healthy service might produce values conceptually like:

```text
Id=veriqta-jun022.service
LoadState=loaded
ActiveState=active
SubState=running
MainPID=1234
```

The PID will differ.

Record the values from your system.

This gives you a precise baseline.

---

# 6. Understand the State Layers

A service does not have one universal field called:

```text
status
```

systemd tracks multiple dimensions.

For this lab, focus on:

| Property | Question |
|---|---|
| `LoadState` | Did systemd load the unit definition? |
| `ActiveState` | What is the high-level runtime state? |
| `SubState` | What more specific state applies? |
| `MainPID` | What main process is associated with the service, if applicable? |

A service might be:

```text
LoadState=loaded
ActiveState=failed
SubState=failed
```

That means:

```text
systemd understands the unit
```

but:

```text
the service did not remain successfully active
```

Do not collapse those into one concept.

---

# 7. Correlate the Service with Its Process

Retrieve:

```bash
systemctl show veriqta-jun022.service -p MainPID
```

Record the numeric PID.

Now inspect that PID:

```bash
ps -p PID -o pid,ppid,user,stat,etime,cmd
```

Replace `PID` with the actual number.

You should see the running `sleep` process.

Compare:

```text
systemctl
```

with:

```text
ps
```

Ask:

```text
Does systemd report the service as active?

Does the expected main process exist?

Does the command match the unit's ExecStart?
```

You now have evidence from two layers.

# 8. Inspect the Service Definition

Run:

```bash
systemctl cat veriqta-jun022.service
```

Pay particular attention to:

```ini
ExecStart=/usr/bin/sleep 3600
```

This tells you what systemd has been instructed to start.

Now inspect:

```bash
systemctl show veriqta-jun022.service -p FragmentPath
```

Record:

```text
FragmentPath:
```

During troubleshooting, configuration is evidence.

If the service is attempting to execute the wrong command, the process layer cannot fix the configuration for you.

---

# 9. Targeted Service Logs

Now introduce the journal.

Run:

```bash
journalctl -u veriqta-jun022.service
```

The `-u` option selects records associated with the specified systemd unit.

Think:

```text
journalctl
        ↓
system journal

-u UNIT
        ↓
focus on one unit
```

Your output may contain service lifecycle events such as start or stop activity.

The exact records depend on what has happened on your machine.

Do not expect identical timestamps, process IDs, or wording across systems.

---

# 10. Limit the Number of Records

A journal may contain many entries.

For a concise recent view:

```bash
journalctl -u veriqta-jun022.service -n 20
```

This asks for the most recent 20 matching journal entries.

The number is not special.

For example:

```bash
journalctl -u veriqta-jun022.service -n 10
```

asks for a smaller recent sample.

Use enough context to understand the event without dumping unnecessary history.

---

# 11. Focus on the Current Boot

Run:

```bash
journalctl -u veriqta-jun022.service -b
```

For this lab, understand:

```text
-b
```

as focusing the journal query on the current boot.

This can help separate:

```text
what happened during this boot
```

from:

```text
older service history
```

Full boot-selection features belong in the dedicated journal curriculum later.

---

# 12. Use a Simple Time Boundary

You can also ask for recent records using a time expression.

For example:

```bash
journalctl -u veriqta-jun022.service --since "10 minutes ago"
```

This is useful when you know approximately when an event occurred.

The question becomes:

```text
What did this service record during the period relevant to my incident?
```

rather than:

```text
Show me everything forever.
```

That is a better troubleshooting habit.

---

# 13. Logs Are Evidence, Not Automatic Truth About Root Cause

Suppose a log contains a message indicating:

```text
failed to start
```

That confirms failure behavior.

It may not explain the underlying cause.

A log message could describe:

- a symptom,
- an application error,
- a dependency failure,
- a configuration problem,
- a permission problem,
- a missing resource,
- a secondary effect.

Your job is to ask:

```text
What does this message prove?

What does it only suggest?

What additional evidence do I need?
```

Good troubleshooting separates observation from conclusion.

# 15. Create a Controlled Failure

Now you will deliberately introduce a bad executable path.

Edit the unit:

```bash
sudo systemctl edit --force --full veriqta-jun022.service
```

Change:

```ini
ExecStart=/usr/bin/sleep 3600
```

to:

```ini
ExecStart=/usr/bin/veriqta-command-does-not-exist
```

Do not change anything else.

Save and exit.

Inspect:

```bash
systemctl cat veriqta-jun022.service
```

Confirm that the incorrect path is present.

Because the unit definition changed, run:

```bash
sudo systemctl daemon-reload
```

Now you have intentionally created a service configuration that asks systemd to execute a nonexistent program.

Do not fix it yet.

You need the failure evidence.

---

# 16. Trigger the Failure

Attempt to start:

```bash
sudo systemctl start veriqta-jun022.service
```

The operation should fail.

Exact terminal behavior and wording can vary.

Do not immediately edit the file.

Begin the investigation.

Run:

```bash
systemctl is-active veriqta-jun022.service
```

You should normally see:

```text

```

Now:

```bash

```


# 18. Symptom vs Evidence

At this point:

### Symptom

```text
The service did not start successfully.
```

### Evidence

You may have:

```text
ActiveState=failed
```

and status output showing failure.

Do not yet write:

```text
Root cause: bad ExecStart
```

even though you created the failure and know what you changed.

The exercise is about following the same evidence process you would use when you **didn't** already know the answer.

---

# 19. Check the Process Layer

Inspect:

```bash
systemctl show veriqta-jun022.service -p MainPID
```

A failed service that never successfully launched its configured executable may report:

```text
MainPID=0
```

or otherwise have no running main service process.

Now compare that with the healthy baseline.

Healthy:

```text
active
running
nonzero MainPID
expected process present
```

Failed:

```text
failed
no healthy running service process
```

This strengthens the investigation.

---

# 20. Read the Recent Service Logs

Run:

```bash
journalctl -u veriqta-jun022.service -n 20
```

Look for entries around the failed start.

The exact wording depends on systemd version and environment.

You may see evidence indicating that systemd could not execute the configured command or that the service process failed to start.

Do not copy a memorized error message.

Read what **your** system reports.

Record the most relevant evidence in your own words:

```text

Service:

Observed message:

What it proves:
```

# 21. Narrow the Evidence to This Boot

Run:

```bash
journalctl -u veriqta-jun022.service -b -n 20
```

Now your query combines:

```text
unit filter
+
current boot
+
recent records
```

This is a useful junior-level troubleshooting pattern.

You are narrowing the evidence rather than reading unrelated system logs.

# 22. Inspect the Configuration

Now inspect:

```bash
systemctl cat veriqta-jun022.service
```

You should see:

```ini
ExecStart=/usr/bin/veriqta-command-does-not-exist
```

Ask:

> Does that executable actually exist?

Use a tool you already know:

```bash
ls -l /usr/bin/veriqta-command-does-not-exist
```

The path should not exist.

Now you have connected:

```text
SERVICE FAILURE
       ↓
journal evidence
       ↓
unit configuration
       ↓
configured executable path
       ↓
filesystem evidence
```

That is evidence-based troubleshooting.

---

# 23. Build the Hypothesis

Your evidence now supports a hypothesis:

```text
The service cannot start because ExecStart references an executable that does not exist.
```

Why is this stronger than:

```text
systemd is broken
```

?

Because you have specific evidence:

```text
systemd loaded the unit

the start failed

the service entered failed state

there is no healthy main process

journal records correspond to the failed start

ExecStart references a path

the referenced path does not exist
```

Your hypothesis explains all observed evidence.

---

# 24. Identify the Root Cause

At this point, the root cause is supported:

```text
The unit's ExecStart directive points to a nonexistent executable.
```

Separate that from the symptom:

```text
SYMPTOM
Service failed to start.

ROOT CAUSE
ExecStart points to a nonexistent executable.
```

This distinction is fundamental.

Production troubleshooting often fails when engineers stop at the symptom.

# 29. Failed State Can Persist as Recorded State

systemd tracks failed units.

Run:

```bash
systemctl --failed
```

Depending on the service's current state and systemd behavior after successful restart, your lab unit may or may not still appear in the failed list.

The important concept is that systemd maintains unit state information that can be inspected.

There is also a command:

```bash
sudo systemctl reset-failed UNIT
```

This clears systemd's recorded failed state for the specified unit.

Do **not** treat it as a repair command.

It does not fix:

```text
bad configuration
missing executable
permission problem
broken application
dependency failure
```

It clears failure state bookkeeping.

---

# 30. Do Not Clear Failure Evidence Too Early

Imagine this workflow:

```text
service fails
    ↓
reset-failed
    ↓
restart
    ↓
problem temporarily disappears
```

You may have made the investigation harder.

A better pattern is:

```text
FAILURE
    ↓
CAPTURE STATE
    ↓
CAPTURE RELEVANT LOGS
    ↓
INSPECT CONFIGURATION / PROCESS
    ↓
IDENTIFY ROOT CAUSE
    ↓
FIX
    ↓
VERIFY
    ↓
CLEAR STALE FAILURE STATE IF NEEDED
```

Evidence first.

Cleanup later.

---

# 31. Use `reset-failed` Deliberately

To understand the operation, stop the recovered lab service first:

```bash
sudo systemctl stop veriqta-jun022.service
```

Now:

```bash
sudo systemctl reset-failed veriqta-jun022.service
```

Inspect:

```bash

```

The important lesson is not a particular status string.

The lesson is:

```text
reset-failed
```

does not start the service.

It does not repair configuration.

It clears recorded failure state.

# 32. `inactive` Is Not the Same as `failed`

With the service intentionally stopped, run:

```bash
systemctl is-active veriqta-jun022.service
```

You should normally see:

```text
inactive
```

Compare:

```text
INACTIVE
```

with the earlier:

```text
FAILED
```

An inactive service may simply be intentionally stopped.

A failed service indicates a recorded failure condition.

Never report:

```text
service is down, therefore it failed
```

without checking state and context.

---

# 33. `loaded` Is Not the Same as Healthy

Inspect:

```bash
systemctl show veriqta-jun022.service -p LoadState -p ActiveState -p SubState
```

An intentionally stopped service can be:

```text
LoadState=loaded
ActiveState=inactive
```

Earlier, the broken service could be:

```text
LoadState=loaded
ActiveState=failed
```

Therefore:

```text
loaded
```

means systemd successfully loaded the unit definition.

It does not mean:

```text
application is healthy
```

---

# 34. `active` Is Important but Not Complete Application Health

Start the repaired service again:

```bash
sudo systemctl start veriqta-jun022.service
```

Verify:

```bash
systemctl is-active veriqta-jun022.service
```

You should see:

```text
active
```

For this lab service, that is strong evidence because its only purpose is to keep `sleep` running.

But imagine a web application.

systemd might report:

```text
active
```

while:

- the application returns HTTP 500,
- the database connection is broken,
- a dependency is unavailable,
- requests time out,
- the application is serving incorrect data.

Therefore:

```text
systemd active
```

means:

```text
systemd considers the unit active according to its unit model
```

It does not universally mean:

```text
users are receiving a healthy application
```

Application-level testing comes from the application's own expected behavior.

# 35. The Investigation Model

Use this model whenever a service behaves unexpectedly.

## Symptom

What was observed?

Example:

```text
The service did not start.
```

---

## Impact

What stopped working?

In this lab:

```text
The disposable lab service was unavailable.
```

In production, this might be:

```text
API requests failing
SSH unavailable
monitoring agent offline
web traffic failing
```

Do not invent impact.

Measure it.

---

## Evidence

What facts can you prove?

Examples:

```text
ActiveState=failed

MainPID=0

journal contains failed-start evidence

ExecStart references a specific path

that path does not exist
```

---

## Hypothesis

What explanation fits the evidence?

```text
The configured executable path is invalid.
```

---

## Test

How can you safely test the hypothesis?

```text
inspect unit configuration
inspect referenced path
```

---

## Root Cause

What underlying condition actually caused the failure?

```text
ExecStart referenced a nonexistent executable.
```

---

## Fix

What change addresses that cause?

```text
restore the correct ExecStart path
```

---

## Recovery Verification

How do you prove recovery?

```text
is-active
status
show
MainPID
ps
relevant journal evidence
```

---

## Prevention

How could this type of issue be reduced?

Examples include:

```text
validate unit configuration before deployment
verify executable paths
use controlled change review
test service changes before production rollout
verify service state after deployment
```

# 36. What Not to Do During Service Investigation

Avoid:

```text
restart first, investigate later
```

Avoid:

```text
assume inactive means failed
```

Avoid:

```text
assume loaded means healthy
```

Avoid:

```text
assume active means the application works for users
```

Avoid:

```text
read unrelated system logs before identifying the service
```

Avoid:

```text
clear failed state before capturing evidence
```

Avoid:

```text
edit several things at once
```

Avoid:

```text
change permissions randomly
```

Avoid:

```text
use sudo as a troubleshooting strategy
```

Avoid:

```text
guess the unit name
```

Avoid:

```text
blame systemd merely because systemd reported the failure
```

systemd may simply be the component exposing a failure elsewhere.

# 38. Engineer Notes — Read Evidence in Order

A useful first-pass sequence is:

```text
1. exact unit
2. systemctl status
3. is-active
4. structured state with systemctl show
5. process evidence if applicable
6. targeted service journal
7. unit configuration
```

# 44. Knowledge Check

### 1. What does `systemctl status UNIT` provide?

A human-oriented summary of the unit, including important state information and commonly some recent journal records.

### 2. Does `Loaded: loaded` mean the service is healthy?

No. It means systemd successfully loaded the unit definition.

### 3. What does `ActiveState` describe?

The high-level runtime activation state of the unit.

### 4. What does `SubState` describe?

A more specific state whose meaning depends on the unit type.

### 5. What does `MainPID` represent?

The process ID systemd identifies as the unit's main process when applicable.

### 6. Can a loaded service be failed?

Yes.

### 7. Can an inactive service be completely normal?

Yes. It may simply be intentionally stopped.

### 8. Is `inactive` the same as `failed`?

No.

### 9. What command provides a focused runtime-state answer?

```bash
systemctl is-active UNIT
```

### 10. What command can retrieve precise unit properties?

```bash
systemctl show UNIT
```

### 11. How can you request selected properties?

For example:

```bash
systemctl show UNIT -p LoadState -p ActiveState -p SubState -p MainPID
```

### 12. What command lists failed units?

```bash
systemctl --failed
```

### 13. Does a failed unit state tell you the root cause?

No.

### 14. What command displays journal records for one unit?

```bash
journalctl -u UNIT
```

### 15. What does `-u` do here?

It selects records associated with the specified systemd unit.

### 16. How can you limit the output to recent records?

For example:

```bash
journalctl -u UNIT -n 20
```

### 17. What does `-b` do in this lab?

It limits the journal query to the current boot.

### 18. How can you request records from a recent time period?

For example:

```bash
journalctl -u UNIT --since "10 minutes ago"
```

### 19. Are logs automatically the root cause?

No. They are evidence that must be interpreted.

### 20. Why inspect the service configuration?

Because the service may be failing because of what systemd has been instructed to execute or how the unit is configured.

### 21. What directive defined the executable in this lab?

```text
ExecStart=
```

### 22. What caused the controlled failure?

`ExecStart` referenced an executable path that did not exist.

### 23. What was the symptom?

The service failed to start.

### 24. Why are symptom and root cause different?

The symptom describes the observed failure. The root cause identifies the underlying condition that produced it.

### 25. What command was used to verify whether the configured executable existed?

```bash
ls -l PATH
```

with the exact path substituted manually.

### 26. Why was `daemon-reload` required after repairing the unit?

Because the systemd unit definition changed.

### 27. Does `daemon-reload` repair a failed service?

No.

### 28. What must happen after the repair?

The service must be started or otherwise activated as appropriate, then its recovery must be verified.

### 29. Why verify MainPID after recovery?

It helps prove that the service once again has the expected running main process.

### 30. Why use `ps` as well as systemctl?

It provides process-layer evidence that can be correlated with systemd's service view.

### 31. Does `active` guarantee that every application function works?

No.

### 32. Why not?

systemd's active state describes the unit according to its service model; application-level functionality may require separate testing.

### 33. What does `reset-failed` do?

It clears systemd's recorded failed state for the specified unit.

### 34. Does `reset-failed` repair configuration?

No.

### 35. Does `reset-failed` start the service?

No.

### 36. Why should failure state not be cleared immediately?

Because you should collect and understand failure evidence before removing useful state information.

### 37. What is a hypothesis?

A proposed explanation that fits the observed evidence and can be tested.

### 38. What makes a hypothesis stronger?

Multiple independent pieces of evidence supporting it.

### 39. What is recovery verification?

Evidence that the intended service behavior has returned after the fix.

### 40. What is the basic troubleshooting sequence taught here?

```text
symptom
→ impact
→ evidence
→ hypothesis
→ test
→ root cause
→ fix
→ recovery verification
→ prevention
```

# 45. Interview Practice

### How do you investigate a failed systemd service?

I first confirm the exact unit and capture its current state with `systemctl status`, `is-active`, and relevant `systemctl show` properties. I inspect the service's process state where applicable, review targeted journal records for the unit, inspect its configuration, form a hypothesis from the evidence, test that hypothesis, fix the root cause, and independently verify recovery.

### What is the difference between `loaded` and `active`?

Loaded means systemd successfully loaded the unit definition. Active describes the unit's current runtime activation state. A loaded unit can still be inactive or failed.

### What is the difference between inactive and failed?

Inactive may be a normal stopped state. Failed indicates systemd recorded a failure condition for the unit.

### What does `systemctl status` show?

It gives a human-oriented summary of a unit, including load and runtime state, process information where applicable, and commonly recent journal messages.

### Why would you use `systemctl show`?

It lets me retrieve specific structured properties such as `LoadState`, `ActiveState`, `SubState`, and `MainPID`.

### How do you view logs for one systemd service?

```bash
journalctl -u UNIT
```

### How would you avoid reading an unnecessarily large service history?

I can limit the number of records, focus on the current boot, or use an appropriate time boundary.

### Why aren't logs automatically the root cause?

A log message may describe a symptom or secondary effect. I correlate it with service state, configuration, process evidence, and relevant system resources before concluding root cause.

### Why shouldn't you immediately restart a failed service?

A restart may interrupt workloads or destroy useful evidence without explaining why the service failed. I collect evidence first unless immediate restoration is required by the incident response plan.

### What is MainPID?

It is the PID systemd identifies as the service's main process when applicable.

### What does `systemctl --failed` do?

It lists units currently recorded in a failed state.

### What does `systemctl reset-failed` do?

It clears systemd's recorded failed state. It does not fix the underlying problem or start the service.

### Why might a service be active but still unhealthy for users?

systemd may consider the service process active while the application itself is returning errors, cannot reach a dependency, is timing out, or is otherwise functionally unhealthy.

### What was the root cause in this lab's controlled incident?

The service unit's `ExecStart` directive referenced an executable path that did not exist.

### How did you prove that?

The service entered failed state, no healthy main process remained, targeted journal evidence corresponded to the failed start, the unit configuration showed the configured executable path, and filesystem inspection confirmed that the path did not exist.

### What did you do after correcting `ExecStart`?

I reloaded systemd's unit definitions with `daemon-reload`, started the service, verified its active state and substate, confirmed a valid MainPID and expected process, and reviewed relevant journal evidence for recovery.
