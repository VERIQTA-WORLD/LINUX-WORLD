# JUN-005: Viewing and Inspecting Files

- **Level:** Junior  
- **Difficulty:** 1/5  
- **Estimated time:** 60–75 minutes  
- **Environment:** Ubuntu Server 24.04 LTS or a similar Linux system  
- **Privileges:** Standard user account  
- **Primary skills:** Safely viewing and inspecting file contents  
- **Prerequisites:** JUN-001 through JUN-004

---

## Lab Mission

You have learned how to navigate the Linux filesystem, understand files and directories, and create, copy, move, rename and remove filesystem objects.

Now you need to look inside files.

That sounds simple until you are working on a real server.

A configuration file may contain hundreds of lines. A log may contain thousands. Some files should be read from the beginning, while others are more useful from the end. Sometimes you need only the first few lines. Sometimes you need to watch a file as new data is written to it. And sometimes the most important decision is recognizing that a file should not be dumped directly into your terminal at all.

In this lab, you will work with the core tools used to inspect text files safely:

```text
cat
less
head
tail
```

You will also use the skills from earlier labs to inspect a file before deciding how to view it.

The goal is not simply to learn four commands.

The goal is to develop a reliable inspection process:

**Identify the file → understand what it is → choose an appropriate viewing method → inspect the relevant content → verify what you observed.**

---

## What you will learn

By the end of this lab, you should be able to:

- Display small text files with `cat`.
- Understand when `cat` is useful and when it is a poor choice.
- Read longer files interactively with `less`.
- Navigate and search inside `less`.
- Inspect the beginning of a file with `head`.
- Control how many lines `head` displays.
- Inspect the end of a file with `tail`.
- Control how many lines `tail` displays.
- Follow a file as new lines are appended with `tail -f`.
- Stop a foreground command with `Ctrl+C`.
- Inspect a file's type and metadata before viewing it.
- Recognize that not every file should be treated as plain text.
- Distinguish between file metadata and file contents.
- Investigate common viewing errors.
- Choose an inspection tool based on the problem you are trying to solve.
- Verify observations without modifying the file.

---

# 5. What `cat` actually means

The name `cat` comes from **concatenate**.

Its job is broader than simply "view a file."

It can take file contents and write them to standard output, including multiple files in sequence.

For example:

```bash
cat configs/app.conf configs/database.conf
```

You should see the contents of the first file followed by the contents of the second.

The files themselves are not merged or modified by this command.

Their contents are simply being written to your terminal one after another.

Verify that both files still exist:

```bash
ls -l configs/
```

---

# 6. `cat` is not always the best viewer

A three-line file is easy to display with:

```bash
cat FILE
```

A file containing thousands of lines is different.

If you use `cat` on a large file, the terminal may fill rapidly with output, pushing useful information out of view.

The command may still technically work.

That does not make it the best tool for the job.

This is an important distinction in Linux:

**A command can be valid without being the most useful choice.**

When a file is long and you want to read it interactively, `less` is usually a better choice.

# 9. Read a file interactively with `less`

Run:

```bash
less reports/numbered-lines.txt
```

Instead of dumping the entire file and returning immediately to your shell prompt, `less` opens an interactive viewer.

You can move through the file while remaining inside `less`.

Try the following keys:

```text
Down Arrow     move down
Up Arrow       move up
Space          move forward approximately one screen
b              move backward approximately one screen
g              go to the beginning
G              go to the end
q              quit
```

The exact number of lines visible at once depends on your terminal size.

Spend a moment moving through the file.

Then press:

```text
q
```

to return to your shell.

# 15. `head` and `tail` answer different questions

Suppose a log contains 50,000 lines.

You may not want:

```bash
cat huge.log
```

If you want to know how it begins:

```bash
head huge.log
```

If you want to know what happened most recently:

```bash
tail huge.log
```

If you want a specific number of lines:

```bash
head -n 20 huge.log
tail -n 20 huge.log
```

The tool should match the question you are asking.

# 17. Follow a file as it changes

One particularly useful `tail` option is:

```text
-f
```

It follows the file and displays new data as it is appended.

Run:

```bash
tail -f logs/application.log
```

You should see the existing end of the file, and the command will remain running instead of returning to your normal prompt.

That is expected.

`tail` is waiting for new data.

To stop it, press:

```text
Ctrl+C
```

Do that now.

You should return to your shell prompt.

---

# 18. Understanding `Ctrl+C`

When:

```bash
tail -f FILE
```

is running in the foreground, your shell is waiting for that command.

Pressing:

```text
Ctrl+C
```

normally sends an interrupt signal to the foreground process.

For now, think of it as a common way to stop a foreground command that is still running.

Signals and process control receive dedicated treatment later in the Junior curriculum.

You do not need the deeper mechanics yet.

# 22. Inspect before using `cat` on an unfamiliar file

Suppose you discover:

```text
some-file
```

on a server.

Do not build the habit of immediately running:

```text
cat some-file
```

First ask what it is.

A useful sequence might be:

```bash
ls -l some-file
file some-file
stat some-file
```

Then decide how to inspect it.

If `file` reports ordinary text, tools such as:

```text
cat
less
head
tail
```

may be appropriate.

If it reports binary data, compressed data, an executable, an image or another non-text format, another inspection tool may be more suitable.

The right tool depends on the object.

# 23. Not every file is plain text

You already saw this idea in JUN-003.

Inspect:

```bash
file /bin/ls
```

On a typical Ubuntu system, this should identify an executable binary, although the exact wording depends on the system.

Now compare:

```bash
file /etc/hostname
```

These are both files in the broad filesystem sense, but they contain very different kinds of data.

That matters when choosing a viewing tool.

Commands such as:

```bash
cat /bin/ls
```

are poor choices for ordinary terminal inspection because binary data can produce unreadable output and may include control characters that affect terminal display.

Do not run that command for this exercise.

The lesson is:

**Identify the file before deciding how to display it.**

# 25. Metadata is not content

Compare:

```bash
stat reports/system-report.txt
```

with:

```bash
cat reports/system-report.txt
```

`stat` tells you about the filesystem object.

`cat` displays its contents.

Those are different layers of information.

For example:

```text
stat
```

can help answer questions such as:

- How large is the file?
- Who owns it?
- What permissions does it have?
- What timestamps are associated with it?

Whereas:

```text
cat
```

can answer:

- What text is actually inside this small file?

A good investigation often uses more than one kind of evidence.

# 31. Do not automatically use `sudo` to read something

If a file returns:

```text

```

do not assume the next command should be:

```text
sudo cat ...
```

First ask:

- Should you have access to this file?
- Why is access restricted?
- Are you using the correct account?
- Is this actually the file you intended to inspect?
- Would elevated access violate the least-privilege principle?

In this lab, the correct response to the controlled failure was not privilege escalation.

It was understanding why the failure occurred and restoring the lab file's intended test state.

# 33. Inspect the end of a log first

Suppose an application failed a few seconds ago and its log is:

```text
application.log
```

If new events are appended to the end, starting with:

```bash
tail application.log
```

may give you more relevant information than:

```bash
head application.log
```

That does not mean `tail` is always correct for logs.

> Am I interested in how this file begins, or what happened most recently?

Engineering tools become more useful when you connect them to the question you are trying to answer.

# 34. Viewing a file does not mean understanding it

Imagine you run:

```bash
cat application.log
```

and receive 500 lines of output.

Technically, you viewed the file.

That does not mean you found the information you needed.

Good inspection is purposeful.

Before opening a file, ask:

- What am I looking for?
- Is the beginning likely to matter?
- Is the end likely to matter?
- Is the file small enough to display completely?
- Would interactive navigation be easier?
- Is the file actually text?
- Is the path correct?
- Do I have permission to read it?

This is the difference between running commands and investigating a system.

# 35. Compare the four main viewing tools

You now know four important approaches.

## `cat`

Useful when you want the complete contents of a relatively small text file written directly to standard output.

```bash
cat FILE
```

## `less`

Useful when you want to navigate through longer text interactively.

```bash
less FILE
```

## `head`

Useful when you want the beginning of a file.

```bash
head FILE
```

or:

```bash
head -n NUMBER FILE
```

## `tail`

Useful when you want the end of a file.

```bash
tail FILE
```

or:

```bash
tail -n NUMBER FILE
```

For ongoing appended data:

```bash
tail -f FILE
```

There is no universal "best" viewing command.

The right choice depends on what you need to learn from the file.

# 44. A practical inspection workflow

When you encounter an unfamiliar file, a reasonable beginner workflow is:

```text
1. Confirm your location when the path is relative.
        ↓
2. Confirm the path exists.
        ↓
3. Determine what kind of object it is.
        ↓
4. Determine what kind of data it contains.
        ↓
5. Check useful metadata such as size.
        ↓
6. Decide what information you need.
        ↓
7. Choose an appropriate viewing tool.
        ↓
8. Inspect the relevant content.
        ↓
9. Record or explain what the evidence tells you.
```

For example:

```bash
pwd
ls -l PATH
file PATH
stat PATH
```

Then, depending on the situation:

```bash
cat PATH
```

or:

```bash
less PATH
```

or:

```bash
head PATH
```

or:

```bash
tail PATH
```

Do not treat this as a rigid command sequence that must always be run exactly this way.

It is a reasoning model.

Use the parts that help answer the question in front of you.

# 45. Common mistakes to avoid

### Using `cat` on everything

`cat` is useful, but dumping a large file into your terminal is often less helpful than using `less`, `head` or `tail`.

### Trusting the extension

A `.txt` file is not guaranteed to contain text, and a `.jpg` filename is not proof of JPEG data.

Inspect the file.

### Confusing metadata with contents

`stat` and `cat` answer different questions.

### Ignoring the path

A correct viewing command with an incorrect path still fails.

### Treating a directory as a regular file

Inspect the object type when you are unsure.

### Ignoring error messages

`No such file or directory`, `Permission denied`, and errors indicating a directory are different problems.

### Using `sudo` automatically

Access restrictions should be understood before privileges are elevated.

### Reading an entire log when you only need recent events

Start with the part that is relevant to your question.

### Forgetting how to exit `less`

Use:

```text
q
```

### Forgetting how to stop `tail -f`

Use:

```text
Ctrl+C
```

# 51. Interview Practice

### How would you display a small text file in Linux?

A common method is:

```bash
cat FILE
```

For larger files or interactive reading, I would choose a more appropriate viewer such as `less`.

### What is the difference between `cat` and `less`?

`cat` writes file contents directly to standard output. `less` provides an interactive interface for navigating through text without dumping the entire file into the terminal at once.

### How do you display the first 20 lines of a file?

```bash
head -n 20 FILE
```

### How do you display the final 20 lines?

```bash
tail -n 20 FILE
```

### How would you watch a log for newly appended entries?

```bash
tail -f FILE
```

### How do you stop `tail -f` when it is running in the foreground?

Normally with `Ctrl+C`.

### Why would you use `file` before opening an unfamiliar file?

To determine what kind of data or filesystem object I am dealing with instead of assuming based on the filename or extension.

### Why might `cat` be a poor choice for a large log?

Because it can send a large amount of output to the terminal when I may only need the latest entries or interactive navigation.

### How would you inspect a large text file interactively?

```bash
less FILE
```

### A command says a file does not exist. What would you check?

I would read the error, verify my current directory if the path is relative, inspect the relevant directory, check spelling and capitalization, and confirm the actual path before retrying.

### What is the difference between a missing-file error and a permission error?

A missing-file error means the requested path could not be found as specified. A permission error means the operation is not allowed under the current access.

### Why is selecting the right viewing command more important than simply knowing several commands?

Because the purpose of inspection is to answer a question efficiently. The best command depends on the file, its size, its type, and whether I need the beginning, end, full contents, interactive navigation or ongoing updates.
