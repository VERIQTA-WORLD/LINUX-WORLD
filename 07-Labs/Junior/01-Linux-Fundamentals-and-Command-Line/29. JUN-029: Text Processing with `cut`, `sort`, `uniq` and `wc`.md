## 1. Lab Mission

In JUN-028, you learned how to use `grep` to answer:

> Which lines contain the evidence I need?

That is only one part of text investigation.

Once you have the relevant records, you often need to answer different questions:

- Which field do I actually need?
- Which users appear in this data?
- Which service generated the most records?
- How many lines are in this file?
- Which values are duplicated?
- Which values are unique?
- How should these records be ordered?
- Which source appears most frequently?

Linux provides several small tools that work extremely well together:

```text
cut   → extract selected parts of text
sort  → arrange lines
uniq  → compare adjacent lines
wc    → count lines, words, or bytes
```

The real power appears when they are connected with the pipeline model from JUN-027:

```text
INPUT
  │
  ▼
cut
  │
  ▼
sort
  │
  ▼
uniq
  │
  ▼
wc / terminal / file
```

This is a core Unix/Linux idea:

> Use small tools for focused jobs, then connect them deliberately.

By the end of this lab, you should be able to:

- extract delimiter-separated fields with `cut`;
- extract character positions when appropriate;
- sort text alphabetically;
- sort numeric data numerically;
- reverse a sort;
- explain why lexical and numeric sorting differ;
- remove adjacent duplicate lines with `uniq`;
- explain why `uniq` commonly follows `sort`;
- count repeated values with `uniq -c`;
- identify only repeated or only non-repeated values;
- count lines, words, and bytes with `wc`;
- combine these tools in pipelines;
- use `grep` before later processing when filtering is needed;
- verify intermediate stages instead of trusting a long pipeline blindly;
- recognize when simple delimiter-based tools are not appropriate for structured data.

## 3. Extract Fields with `cut`

The basic delimiter-based form is:

```text
cut -d 'DELIMITER' -f FIELD FILE
```

Here:

```text
-d
```

specifies the delimiter, while:

```text
-f
```

selects one or more fields.

Extract the service field:

```bash
cut -d '|' -f 2 activity.log
```

You should see values such as:

```text
api
worker
api
auth
...
```

Now extract the log level:

```bash
cut -d '|' -f 3 activity.log
```

Extract the message:

```bash
cut -d '|' -f 4 activity.log
```

### Extract multiple fields

You can select more than one field:

```bash
cut -d '|' -f 2,3 activity.log
```

This selects:

```text
SERVICE | LEVEL
```

You can also select a range:

```bash
cut -d '|' -f 2-4 activity.log
```

This selects fields 2 through 4.

### Extract character positions

`cut` can also select character positions.

Run:

```bash
cut -c 1-8 activity.log
```

Because each record begins with an eight-character timestamp such as:

```text
09:00:01
```

the result contains the time portion.

The distinction is:

```text
-d + -f
→ delimiter-based fields
```

versus:

```text
-c
→ character positions
```

Character positions are useful when the text is genuinely fixed-position.

Do not assume every data format has stable character widths.

### Important limitation

`cut` is a simple delimiter-based tool.

It does **not** understand complex formats merely because they look tabular.

For example, a real CSV file may contain quoted fields with commas inside them. A command such as:

```text
cut -d ',' ...
```

does not become a full CSV parser.

The engineering habit is:

> Understand the data format before choosing the parser.

## 4. Sort Text Correctly

Inspect:

```bash
cat hosts.txt
```

Now sort it:

```bash
sort hosts.txt
```

The original file is not changed.

`sort` writes the ordered result to stdout.

Verify that:

```bash
cat hosts.txt
```

still shows the original ordering.

This distinction matters:

```text
sort FILE
```

does not mean:

```text
rewrite FILE in sorted order
```

It means:

```text
read FILE
    ↓
sort records
    ↓
write sorted result to stdout
```

If you want to save the result:

```bash
sort hosts.txt > sorted-hosts.txt
```

Verify:

```bash
cat sorted-hosts.txt
```

### Reverse the order

Use:

```bash
sort -r hosts.txt
```

`-r` reverses the resulting order.

### Text sorting is not numeric sorting

Inspect:

```bash
cat latency.txt
```

Now run:

```bash
sort latency.txt
```

Look carefully at the result.

You may see an order beginning like:

```text
10
120
250
35
...
```

Why?

Because the default sort is not treating those lines as numerical quantities in the way you intend.

Now run:

```bash
sort -n latency.txt
```

`-n` requests numeric comparison.

You should now get values ordered numerically from smallest to largest.

Reverse the numeric order:

```bash
sort -nr latency.txt
```

This is a common operational mistake:

```text
numbers present in text
≠
numeric sort automatically selected
```

Choose the comparison mode that matches the data.

## 5. Understand Why `uniq` Usually Needs Sorted Input

Inspect the original host file again:

```bash
cat hosts.txt
```

Now run:

```bash
uniq hosts.txt
```

Notice that repeated hostnames can remain.

This surprises many new Linux users.

`uniq` does **not** search the entire file and build a global set of values.

It compares neighboring lines.

Its mental model is closer to:

```text
current line
    ↓
compare with previous adjacent line
    ↓
same?
```

So:

```text
api-02
worker-01
api-02
```

contains two `api-02` lines, but they are not adjacent.

A plain:

```bash
uniq hosts.txt
```

does not remove the second occurrence merely because the value appeared earlier.

### Sort first

Run:

```bash
sort hosts.txt
```

The duplicate values are now grouped together.

Connect the commands:

```bash
sort hosts.txt | uniq
```

Now you should receive one copy of each hostname.

The pipeline is:

```text
hosts.txt
    │
    ▼
  sort
    │
    │ grouped stdout
    ▼
    |
    ▼
  uniq
    │
    ▼
one line per adjacent value group
```

This produces one occurrence per value for this dataset because sorting brought identical lines together.

The important rule is:

> `uniq` operates on adjacent repeated lines. If identical values may be scattered through the input, sort them first when global grouping is your goal.

## 6. Count and Classify Repeated Values

Once identical lines are grouped, `uniq` can do more than remove duplicates.

Run:

```bash
sort hosts.txt | uniq -c
```

You should see each value with a count.

The output may be visually indented. That is normal.

The important information is:

```text
count + value
```

This transforms:

```text
api-02
worker-01
api-01
api-02
...
```

into evidence answering:

> How often does each hostname occur?

### Show only repeated values

Run:

```bash
sort hosts.txt | uniq -d
```

`-d` reports values that occur more than once in the grouped input.

### Show only values that occur once

Run:

```bash
sort hosts.txt | uniq -u
```

`-u` reports values that appear only once in the grouped input.

Remember that the usefulness of these operations depends on identical records being adjacent when you want whole-input frequency analysis.

### Apply the same model to services

Extract service names:

```bash
cut -d '|' -f 2 activity.log
```

Now group them:

```bash
cut -d '|' -f 2 activity.log | sort
```

Now count them:

```bash
cut -d '|' -f 2 activity.log | sort | uniq -c
```

Read the pipeline stage by stage:

```text
activity.log
      │
      ▼
cut field 2
      │
      ▼
service names
      │
      ▼
sort
      │
      ▼
identical services grouped
      │
      ▼
uniq -c
      │
      ▼
frequency per service
```

You have turned raw records into a small service-frequency summary without writing a program.

## 7. Measure Text with `wc`

`wc` stands for word count, but it can report several measurements.

Run:

```bash
wc activity.log
```

The default output reports multiple measurements.

For focused questions, select what you actually need.

### Count lines

```bash
wc -l activity.log
```

This answers:

> How many newline-delimited lines are present?

### Count words

```bash
wc -w activity.log
```

This counts whitespace-delimited words.

### Count bytes

```bash
wc -c activity.log
```

This reports the byte count.

Do not casually describe:

```text
wc -c
```

as a character count.

GNU `wc` has different concepts for bytes and characters; `-c` specifically reports bytes.

For this lab, focus on:

```text
wc -l → lines
wc -w → words
wc -c → bytes
```

### `wc` also reads stdin

Run:

```bash
grep "ERROR" activity.log
```

Now count those matching lines:

```bash
grep "ERROR" activity.log | wc -l
```

This pipeline answers:

> How many lines contain `ERROR`?

The stages are:

```text
activity.log
     │
     ▼
grep ERROR
     │
     ▼
matching lines
     │
     ▼
wc -l
     │
     ▼
number of matching lines
```

Notice that JUN-028 already provides:

```bash
grep -c "ERROR" activity.log
```

for this simple question.

Both can be useful, but do not build a longer pipeline merely to look sophisticated.

Prefer the clearest tool for the job.

## 8. Build Useful Text-Processing Pipelines

Now combine what you have learned.

### Which services appear in the log?

```bash
cut -d '|' -f 2 activity.log | sort | uniq
```

### How many distinct service names appear?

```bash
cut -d '|' -f 2 activity.log | sort | uniq | wc -l
```

### Which log levels appear?

```bash
cut -d '|' -f 3 activity.log | sort | uniq
```

### How often does each log level appear?

```bash
cut -d '|' -f 3 activity.log | sort | uniq -c
```

### Which services generated ERROR records?

First verify the error records:

```bash
grep "ERROR" activity.log
```

Then extract the service field:

```bash
grep "ERROR" activity.log | cut -d '|' -f 2
```

Then group the services:

```bash
grep "ERROR" activity.log | cut -d '|' -f 2 | sort
```

Finally count them:

```bash
grep "ERROR" activity.log | cut -d '|' -f 2 | sort | uniq -c
```

This is an important workflow.

Do not immediately type the longest command.

Build it progressively:

```text
1. FILTER
   grep

2. EXTRACT
   cut

3. GROUP
   sort

4. COUNT GROUPS
   uniq -c
```

At each stage, inspect whether the data still means what you think it means.

That is how you troubleshoot pipelines.

## 9. Controlled Failures and Common Mistakes

### Mistake 1 — `uniq` appears not to remove duplicates

You run:

```bash
uniq hosts.txt
```

and repeated values remain.

Do not conclude:

> `uniq` is broken.

Inspect the input.

The repeated values are separated.

Correct the data flow:

```bash
sort hosts.txt | uniq
```

**Root cause:** `uniq` compares adjacent lines.

---

### Mistake 2 — Numbers appear in the wrong order

You run:

```bash
sort latency.txt
```

and the ordering does not match numerical magnitude.

Correct it:

```bash
sort -n latency.txt
```

**Root cause:** default text ordering was used for data you intended to compare numerically.

---

### Mistake 3 — Wrong field extracted

You run:

```bash
cut -d '|' -f 3 activity.log
```

while expecting service names.

Inspect the record structure:

```text
1 → time
2 → service
3 → level
4 → message
```

The command behaved correctly.

Your field selection was wrong.

Correct it:

```bash
cut -d '|' -f 2 activity.log
```

---

### Mistake 4 — Wrong delimiter

If you tell `cut` that the data uses a delimiter it does not actually contain, the result may not match your expectation.

Do not keep changing field numbers blindly.

Inspect the input first:

```bash
head activity.log
```

Determine the real structure, then choose `-d` and `-f`.

---

### Mistake 5 — Counting before extracting the right data

Suppose you want:

> How many different services appear?

This:

```bash
wc -l activity.log
```

counts records, not distinct services.

Your question requires transformation first:

```bash
cut -d '|' -f 2 activity.log | sort | uniq | wc -l
```

The tool sequence must match the question.

---

### Mistake 6 — Trusting a long pipeline without inspecting stages

If:

```bash
grep "ERROR" activity.log | cut -d '|' -f 2 | sort | uniq -c
```

produces an unexpected result, do not rewrite everything at once.

Test progressively:

```bash
grep "ERROR" activity.log
```

Then:

```bash
grep "ERROR" activity.log | cut -d '|' -f 2
```

Then:

```bash
grep "ERROR" activity.log | cut -d '|' -f 2 | sort
```

Then:

```bash
grep "ERROR" activity.log | cut -d '|' -f 2 | sort | uniq -c
```

Your troubleshooting model should be:

```text
QUESTION
   ↓
INPUT
   ↓
FILTER
   ↓
EXTRACT
   ↓
ORDER / GROUP
   ↓
COUNT
   ↓
VERIFY
```

When the final result is wrong, find the **first stage** where the data stops matching your expectation.

## 11. Final Practical — Find the Most Active Error Sources Without Guessing

A teammate says:

> The worker service is obviously responsible for most of the errors.

Do not accept the claim without checking the data.

Start with the raw error evidence:

```bash
grep "ERROR" activity.log
```

Now extract only the service names:

```bash
grep "ERROR" activity.log | cut -d '|' -f 2
```

Group identical services:

```bash
grep "ERROR" activity.log | cut -d '|' -f 2 | sort
```

Count them:

```bash
grep "ERROR" activity.log | cut -d '|' -f 2 | sort | uniq -c
```

You now have evidence showing how many `ERROR` records are associated with each service in this training dataset.

But keep the conclusion precise.

You can say:

> In the provided `activity.log`, the frequency summary shows how many lines marked `ERROR` belong to each service.

You cannot automatically conclude:

> The service with the most ERROR lines caused the incident.

Frequency is evidence.

It is not automatic causation.

### Investigation record

Document:

```text
CLAIM:

RAW ERROR RECORDS:

SERVICES EXTRACTED:

GROUPING METHOD:

ERROR COUNT BY SERVICE:

WHAT THE DATA PROVES:

WHAT THE DATA DOES NOT PROVE:

WHAT WOULD YOU INVESTIGATE NEXT?
```

This is the difference between command-line manipulation and engineering investigation.

## 12. Knowledge Check and Interview Practice

### Knowledge Check

1. **What is `cut` primarily used for?**  
   Extracting selected fields or character positions from text.

2. **What does `cut -d '|' -f 2` mean?**  
   Use `|` as the field delimiter and output field 2.

3. **What does `cut -c 1-8` do?**  
   It outputs character positions 1 through 8 from each input line.

4. **Does `sort FILE` normally rewrite the original file?**  
   No. It writes the sorted result to stdout.

5. **What does `sort -n` do?**  
   It performs numeric comparison.

6. **What does `sort -r` do?**  
   It reverses the sort result.

7. **Why can plain `sort` produce surprising results for numbers?**  
   Because the default comparison is not numeric magnitude. Numeric data should use an appropriate numeric sort such as `sort -n`.

8. **What does `uniq` compare?**  
   Adjacent lines.

9. **Why is `sort | uniq` common?**  
   Sorting places identical lines next to one another so `uniq` can group them across the dataset.

10. **What does `uniq -c` do?**  
    It prefixes each adjacent group with its occurrence count.

11. **What is the difference between `uniq -d` and `uniq -u`?**  
    `-d` reports repeated groups; `-u` reports groups that occur only once.

12. **What does `wc -l` report?**  
    The line count.

13. **What does `wc -w` report?**  
    The word count.

14. **What does `wc -c` report?**  
    The byte count.

15. **What is the safest way to troubleshoot a long text-processing pipeline?**  
    Run and verify each stage progressively until you find the first stage producing unexpected data.

### Interview Practice

**How would you extract the second field from pipe-delimited data?**

For example:

```bash
cut -d '|' -f 2 file
```

**Why do engineers commonly use `sort` before `uniq`?**

Because `uniq` compares adjacent lines. Sorting groups identical values together so `uniq` can correctly summarize duplicates scattered throughout the original input.

**What is the difference between `sort` and `sort -n`?**

Default `sort` performs text-oriented ordering. `sort -n` compares values numerically.

**How would you count how often each value occurs in a file?**

If each line represents one value:

```bash
sort file | uniq -c
```

**How would you count ERROR lines in a log?**

A direct solution is:

```bash
grep -c "ERROR" file
```

Another pipeline-based form is:

```bash
grep "ERROR" file | wc -l
```

I would normally choose the simpler form when it answers the question directly.

**How would you determine how many distinct values appear in one delimited field?**

For example:

```bash
cut -d '|' -f 2 file | sort | uniq | wc -l
```

**Why might `cut -d ','` be unsafe as a general CSV parser?**

Because `cut` only understands the delimiter relationship requested; it does not implement full CSV parsing rules such as quoted fields containing commas.

**How do you troubleshoot a pipeline that returns the wrong count?**

I inspect the raw input and then execute the pipeline incrementally, verifying the output after filtering, extraction, sorting, and grouping until I identify the first incorrect assumption.
