- **Level:** Junior

- **Environment:** Ubuntu Server 24.04 LTS or a similar Debian/Ubuntu system  
- **Privileges:** Standard user with working `sudo` authorization

- **Prerequisites:** JUN-001 through JUN-014

---

## Lab Mission

Linux servers depend on software packages.

A web server needs software.

Monitoring agents need software.

Troubleshooting tools need software.

Security updates arrive as software packages.

Applications depend on libraries supplied by other packages.

Administrators therefore need a controlled way to answer questions such as:

```text
Is this package available?
Is it already installed?
Which version is installed?
Which version would be installed?
Where would it come from?
What dependencies will be added?
What will this command change?
Did installation actually succeed?
Can it be removed safely?
```

On Ubuntu, APT is one of the primary systems used to manage software packages.

A weak package-management habit looks like this:

```text
Need a tool
    ↓
copy an install command
    ↓
run it with sudo
    ↓
assume everything worked
```

A stronger engineering workflow is:

```text
DEFINE REQUIREMENT
        ↓
REFRESH PACKAGE METADATA WHEN APPROPRIATE
        ↓
SEARCH
        ↓
INSPECT PACKAGE
        ↓
INSPECT VERSION/CANDIDATE
        ↓
REVIEW PLANNED CHANGE
        ↓
INSTALL OR CHANGE
        ↓
VERIFY PACKAGE STATE
        ↓
VERIFY ACTUAL FUNCTION
        ↓
DOCUMENT
```

This lab teaches that workflow.

You will work primarily with a small disposable package selected for the lab:

```text
sl
```

`sl` is useful here because it is small, nonessential, easy to verify, and safe to remove afterward.

If `sl` is unavailable in your configured repositories, choose another small, nonessential package available on your system and use that package consistently throughout the lab.

Do not use this lab to remove:

- `sudo`,
- `apt`,
- `systemd`,
- SSH packages,
- the kernel,
- networking packages,
- critical libraries,
- production applications,
- or packages you do not understand.

The operating principle is:

> Inspect first. Preview impact. Change deliberately. Verify both package state and actual behavior.

# 2. What Is a Linux Package?

A package is a structured software distribution unit.

A Debian-format package can contain:

```text
program files
libraries
configuration files
documentation
metadata
dependency information
installation/removal instructions
```

Ubuntu and Debian-based systems commonly use:

```text
.deb
```

packages.

A package is more than one executable file.

For example, installing an application may place files in several locations:

```text
/usr/bin/
/usr/lib/
/etc/
/usr/share/
```

depending on the package.

The package-management system tracks those files and the package's state.

This allows Linux to answer questions such as:

```text
Which package installed this?
Which version is installed?
What does it depend on?
Can it be upgraded?
Can it be removed?
```

---

# 3. APT and `dpkg` Are Related but Different

You will encounter both:

```text
apt
```

and:

```text
dpkg
```

They operate at different layers.

A useful simplified model is:

```text
APT
high-level package management
        ↓
repository metadata
dependency resolution
package acquisition
upgrade planning
        ↓
DPKG
lower-level Debian package installation database and package operations
```

APT can:

- search available packages,
- retrieve repository metadata,
- resolve dependencies,
- download packages,
- plan installations,
- coordinate upgrades,
- remove packages.

`dpkg` manages installed Debian package state at a lower level.

In this lab, APT is the primary interface.

You will use `dpkg` mainly as an independent verification source.

---

# 4. Understand the APT Information Flow

APT does not normally search remote repository servers from scratch every time you type:

```bash
apt search something
```

Your system maintains local package metadata obtained from configured repositories.

Conceptually:

```text
CONFIGURED REPOSITORIES
        ↓
apt update
        ↓
LOCAL PACKAGE METADATA
        ↓
apt search / apt show / apt policy
        ↓
PACKAGE DECISION
        ↓
apt install
        ↓
DOWNLOAD PACKAGE(S)
        ↓
DPKG INSTALLATION
        ↓
INSTALLED SOFTWARE
```

This explains why:

```bash
sudo apt update
```

is an important operation.

---

# 5. `apt update` Does Not Upgrade Your Software

This distinction must be clear.

Run:

```bash
sudo apt update
```

APT contacts the configured package sources and refreshes package metadata.

Typical output may contain lines resembling:

```text
Hit:
Get:
Reading package lists... Done
```

Exact repositories, URLs, package counts and output will vary.

The command:

```bash
sudo apt update
```

does **not** mean:

```text
upgrade every installed package
```

It means, conceptually:

```text
Refresh my local knowledge of packages available from configured sources.
```

Think of it as:

```text
REPOSITORY INFORMATION
        ↓
REFRESH
        ↓
LOCAL PACKAGE INDEX
```

not:

```text
INSTALLED SOFTWARE
        ↓
UPGRADE EVERYTHING
```

---

# 6. Why Fresh Metadata Matters

Suppose your local metadata says:

```text
package version available:
1.2
```

but the repository now provides:

```text
1.3
```

Until metadata is refreshed, your system may still reason from older package information.

This is why administrators commonly refresh package metadata before making installation or upgrade decisions.

However, avoid developing the habit of running:

```bash
sudo apt update
```

blindly before every single package-inspection command.

Understand why you are refreshing the metadata.

On production systems, package operations may be controlled by:

- maintenance windows,
- automation,
- configuration management,
- patch-management systems,
- change-control procedures.

# 7. Search for a Package

Search for the lab package:

```bash
apt search '^sl$'
```

You can also perform a broader search:

```bash
apt search sl
```

The broader search may return many unrelated packages because the text can appear in package names or descriptions.

The exact-match-style search is more useful when you already know the likely package name.

You are trying to establish:

```text
Does this package exist in the metadata currently available to APT?
```

Do not install it yet.

Run:

```bash
apt show sl
```

Inspect fields such as:

```text
Package
Version
Priority
Section
Maintainer
Installed-Size
Depends
Description
```

Available fields vary by package.

Do not treat:

```text
apt show
```

as decoration before the "real command."

Package metadata helps answer:

```text
What am I about to install?
What does it do?
Which version is available?
What dependencies does it declare?
How large is it?
```

This is part of change review.

# 9. Inspect Package Version Policy

Run:

```bash
apt policy sl
```

A typical result may conceptually resemble:

```text
Installed: (none)
Candidate: VERSION
Version table:
   VERSION ...
```

Do not copy the example version into your notes.

Record your system's actual result.

The important fields are:

```text
Installed
Candidate
```

`Installed` tells you the installed package version, if any.

`Candidate` is the version APT currently considers the installation candidate under its configured sources and policy.

Before installation, you may see:

```text
Installed: (none)
```

if the package is not already installed.

---

# 10. Verify Installation State Independently

Do not assume a package is absent merely because you do not remember installing it.

Query `dpkg`:

```bash
dpkg -s sl
```

If `sl` is not installed, `dpkg` should report that no installed package matching that query is available.

Exact wording may vary.

You can also inspect:

```bash
dpkg -l sl
```

Interpret the actual output carefully.

The engineering principle is:

```text
MEMORY
"I don't think this is installed."
```

is weaker than:

```text
SYSTEM EVIDENCE
"Package database shows it is not installed."
```

---

# 11. Find Out What APT Would Do Before Doing It

APT supports simulation.

Run:

```bash
apt -s install sl
```

or:

```bash
apt --simulate install sl
```

Do not use `sudo` for this simulation unless your environment specifically requires it.

Review the proposed action.

Look for:

```text
new packages
dependencies
upgrades
removals
```

For a small package like `sl`, the transaction should be simple.

But the habit scales to larger operations.

The question before a package change should be:

> What does APT plan to change?

not merely:

> What command did I type?

# 14. Verify the Actual Program

Package-state verification proves the package manager considers the package installed.

You should also verify functionality.

Try:

```bash
sl
```

On some Ubuntu environments, the executable installed by `sl` may not be in a directory included in your normal `PATH`.

If:

```text
sl
```

returns:

```text
command not found
```

do not conclude immediately that installation failed.

Investigate the package's installed files.

Run:

```bash
dpkg -L sl
```

Look for the executable path.

On many systems, it may be installed under a location such as:

```text
/usr/games/sl
```

If so, run the actual path:

```bash
/usr/games/sl
```

Your environment may differ.

This is a valuable troubleshooting lesson:

```text
PACKAGE INSTALLED
```

does not always mean:

```text
COMMAND NAME RESOLVES THROUGH CURRENT PATH
```

Those are separate questions.

# 16. Find Which Package Owns an Installed File

Suppose you identify the executable:

```text
/usr/games/sl
```

Ask the package database:

```bash
dpkg -S /usr/games/sl
```

If that exact path exists on your environment, the result should identify the owning package.

Conceptually:

```text
FILE PATH
        ↓
dpkg -S
        ↓
PACKAGE OWNER
```

This becomes extremely useful when troubleshooting unfamiliar binaries or configuration files.

If your system installed `sl` elsewhere, substitute the actual path found with:

```bash

```

Run:

```bash

```

Compare:

```text
Installed:
Candidate:
```

If they are the same, the installed package matches APT's current candidate.

If they differ, that difference deserves investigation.

You can also inspect:

```bash
dpkg-query -W sl
```

or:

```bash
dpkg-query -W -f='${Package} ${Version}\n' sl
```

This is useful when scripts or operational checks need concise package-version evidence.

You are not expected to master `dpkg-query` formatting yet.

The command is supplied here as an inspection tool.

# 18. Dependencies

Software frequently depends on other packages.

Inspect:

```bash
apt show sl
```

Look for:

```text
Depends:
```

A dependency means another package or capability is required for the package to operate correctly.

APT's major value is dependency resolution.

Conceptually:

```text
YOU REQUEST PACKAGE A
        ↓
APT READS DEPENDENCIES
        ↓
PACKAGE A REQUIRES B
PACKAGE B REQUIRES C
        ↓
APT PLANS TRANSACTION
        ↓
REQUIRED PACKAGES INSTALLED
```

Without dependency management, administrators would have to resolve many package relationships manually.

---

# 19. Direct and Automatically Installed Packages

APT tracks reasons packages were installed.

Some packages are installed because you explicitly requested them.

Others may be installed automatically because another package required them.

Conceptually:

```text
You request:
application-A

APT installs:
application-A
library-B
library-C
```

Later, if:

```text
application-A
```

is removed, some automatically installed dependencies may no longer be required.

That is where:

```text
autoremove
```

becomes relevant.

Do not interpret:

```text
automatically installed
```

as:

```text
safe to delete without review
```

Always inspect the proposed transaction.

```bash
apt list --upgradable
```

# 21. `apt upgrade`

The command:

```bash
sudo apt upgrade
```

requests upgrades for installed packages under APT's upgrade rules.

For this lab:

> Do not approve a system-wide upgrade merely to practice the command.

Instead simulate it:

```bash
apt -s upgrade
```

Review the plan.

Look for:

```text
packages that would be upgraded
packages kept back or otherwise not changed
additional operations
```

The goal is to understand the transaction before changing the system.

On real infrastructure, upgrades can affect:

- services,
- libraries,
- kernels,
- application compatibility,
- maintenance windows,
- reboot requirements.

Package upgrades are operational changes.

---

# 22. `upgrade` vs `full-upgrade`

You may encounter:

```bash
sudo apt upgrade
```

and:

```bash
sudo apt full-upgrade
```

They are not identical.

At a junior level, the important distinction is:

```text
upgrade
```

performs available upgrades while avoiding certain dependency changes that would require removing installed packages.

```text
full-upgrade
```

can make broader dependency-resolution decisions, including removing installed packages when necessary to complete the upgrade.

Therefore:

```text
full-upgrade
```

deserves particularly careful transaction review.

Do not run a real `full-upgrade` for this lab.

If you want to inspect the planned action safely:

```bash
apt -s full-upgrade
```

Never assume:

```text
"full" means "better"
```

It means the dependency resolver is allowed broader changes.

# 23. Package Installation Is a System Change

After installing `sl`, ask:

```text
What changed?
```

At minimum:

```text
APT package state changed
package files were installed
disk usage changed
package database changed
```

For other packages, installation may also:

- create users or groups,
- install configuration files,
- start services,
- enable services,
- add scheduled tasks,
- create directories,
- trigger system hooks.

This is why production package installation should be treated as a change, not merely as a download.

# 25. `remove` and Configuration Files

APT distinguishes between removing package software and purging package configuration state.

Conceptually:

```text
apt remove PACKAGE
```

removes the package's installed software while potentially preserving package configuration files that are designated as configuration files.

This can be useful if you expect to reinstall later and want configuration retained.

However, whether meaningful configuration remains depends on the package.

`sl` is a simple teaching package and may not provide an interesting persistent configuration example.

The important concept is the package-management distinction.

---

# 26. `purge`

The command:

```text
apt purge PACKAGE
```

requests package removal together with package-managed configuration files that `remove` would preserve.

Simulate first:

```bash
apt -s purge sl
```

If the package has already been removed, APT may show little or nothing left to do depending on its state.

If appropriate, run:

```bash
sudo apt purge sl
```

Then verify:

```bash
dpkg -s sl
```

and:

```bash
apt policy sl
```

The key distinction is:

```text
REMOVE
software removed
package-managed configuration may remain

PURGE
software removed
package-managed configuration targeted for removal too
```

Do not interpret purge as:

```text
delete every file this application has ever caused to exist
```

Application-generated data, user data, external files or manually created files may not be removed by package purge.

# 27. Inspect Package State Codes

Run:

```bash
dpkg -l sl
```

The left side of `dpkg -l` output contains compact package-state indicators.

The header explains the meaning of those positions.

Do not memorize unexplained letters.

Read the header and connect the package's current state to the lifecycle you performed:

```text
not installed
    ↓
installed
    ↓
removed
    ↓
possibly residual configuration
    ↓
purged
```

This teaches you to read package state rather than guessing from command history.

# 28. `autoremove`

APT can identify packages that were installed automatically as dependencies and are no longer considered required.

Inspect safely:

```bash
apt -s autoremove
```

Do not automatically run the real command.

Read every proposed removal.

If your lab system has nothing eligible, that is fine.

The important operational rule is:

> `autoremove` is a proposal to review, not a cleanup button to press blindly.

On long-lived systems, packages may have operational importance that is not obvious from their names alone.

---

# 29. Why Blind `autoremove` Can Be Dangerous

Imagine APT proposes:

```text
package-A
package-B
package-C
```

for removal.

The wrong response is:

```text
APT says unused, therefore delete everything.
```

A stronger response is:

```text
Why were these installed?
What depends on them?
Are they part of an application?
Is this a production server?
Is this removal expected?
What services or tooling could be affected?
```

Package metadata is important evidence.

It does not remove the need for operational judgment.

# 30. Reinstall a Package

Install `sl` again if it is currently absent:

```bash
sudo apt install sl
```

Verify:

```bash
dpkg -s sl
```

APT also supports reinstalling an installed package:

```bash
sudo apt reinstall sl
```

For this lab, simulate first:

```bash
apt -s reinstall sl
```

A reinstall can be useful when package-managed files are missing or damaged.

But it is not a universal repair mechanism.

It does not automatically fix:

- incorrect application configuration,
- bad permissions on unrelated data,
- external dependencies,
- network problems,
- service design problems.

Use it when evidence points to package installation state.

# 31. Download Without Installing

APT can also retrieve a package without installing it.

For example:

```bash
apt download sl
```

This downloads the `.deb` file to the current directory.

This command normally does not require `sudo` because it writes into your current user-controlled directory.

Inspect:

```bash
ls -lh
```

You should see a `.deb` file if the download succeeded.

This demonstrates another important distinction:

```text
DOWNLOAD PACKAGE
```

is not the same as:

```text
INSTALL PACKAGE
```

Remove the downloaded lab package afterward:

```bash
rm ./*.deb
```

Only run that cleanup command inside the controlled JUN-015 workspace after verifying what `.deb` files are present.

# 33. `apt clean` and `apt autoclean`

You may encounter:

```bash
sudo apt clean
```

and:

```bash
sudo apt autoclean
```

Conceptually:

```text
apt clean
```

removes downloaded package archive files from APT's cache.

```text
apt autoclean
```

removes cached package files that can no longer be downloaded under the current package metadata/policy.

These commands manage cached package archives.

They do not uninstall installed packages.

For this lab, understanding the distinction is sufficient.

Do not run cache cleanup merely to create activity.

---

# 34. Package Manager Locks

APT and `dpkg` protect package-management state from unsafe concurrent modification.

If another package operation is already active, you may encounter a lock-related error.

Conceptually:

```text
PROCESS A
modifying package database

PROCESS B
tries to modify package database

        ↓

LOCK PREVENTS CONCURRENT CHANGE
```

The lock is protecting package-management consistency.

A dangerous reaction is:

```text
APT is locked
→ delete lock file immediately
```

Do not do that.

First determine:

```text
Is another apt process running?
Is unattended maintenance active?
Is dpkg active?
Did another package operation recently start?
```

---

# 35. Investigate a Package Lock Safely

You do not need to manufacture a package-manager lock failure.

If one occurs naturally, begin with process inspection.

For example:

```bash
ps aux | grep -E '[a]pt|[d]pkg'
```

This uses `grep` to look for relevant processes while avoiding matching the `grep` command itself through the bracket pattern.

You can also inspect:

```bash
ps -ef
```

and identify package-management activity.

Do not kill package processes merely because you see them.

Determine whether they are legitimately working.

A package operation interrupted at the wrong moment can leave the system requiring recovery.

---

# 36. Interrupted Package Operations

If an earlier package operation was interrupted, APT may report that package configuration is incomplete.

A commonly recommended recovery command in that specific situation is:

```bash
sudo dpkg --configure -a
```

Do **not** run it simply because you learned it.

Use it when package-manager evidence indicates interrupted/unconfigured package state.

The command asks `dpkg` to configure packages that have been unpacked but not yet fully configured.

The engineering principle is:

```text
RECOVERY COMMAND
must correspond to
OBSERVED FAILURE STATE
```

not:

```text
memorize recovery command
→ run whenever APT looks strange
```

---

# 37. Dependency Repair

You may encounter guidance using:

```bash
sudo apt --fix-broken install
```

This asks APT to attempt correction of broken dependency state.

Again, do not run it routinely.

It belongs in a troubleshooting flow where evidence shows package dependencies are broken.

The correct pattern is:

```text
APT reports dependency problem
        ↓
read exact error
        ↓
inspect package state
        ↓
understand proposed repair
        ↓
use appropriate recovery operation
        ↓
verify package database
```

Do not turn:

```text
--fix-broken
```

into a universal package repair button.

---

# 38. Network and Repository Failures

`apt update` and package downloads depend on access to configured package sources.

Failures may result from:

```text
DNS problems
network connectivity
proxy configuration
repository availability
TLS/certificate problems
incorrect system time
invalid repository configuration
unsupported release state
```

If:

```bash
sudo apt update
```

fails, do not immediately edit repository configuration.

Read the error.

Classify it.

For example:

```text
Could not resolve host
```

points toward name resolution or connectivity.

A repository returning an HTTP error points toward a different layer.

Repository configuration itself is the subject of **JUN-016 — Software Repositories**.

# 39. Package Not Found

Suppose:

```bash
sudo apt install package-that-does-not-exist
```

fails because APT cannot locate the package.

Do not assume:

```text
APT is broken
```

Investigate:

```bash
apt search package-name
```

and consider:

```text
Was metadata refreshed?
Is the package name correct?
Is the required repository configured?
Is the package available for this Ubuntu release?
Is the package available for this architecture?
```

The error:

```text
Unable to locate package
```

describes a package-discovery problem.

It is not automatically a network failure or privilege failure.


# 42. Common Mistakes to Avoid

### Confusing `apt update` with `apt upgrade`

`update` refreshes package metadata.

It does not upgrade installed packages.

### Installing before inspecting

Search and inspect the package first.

### Typing `Y` without reading the transaction

APT may propose more changes than expected.

### Running every APT command with `sudo`

Read-only package inspection often does not require elevation.

### Running a system-wide upgrade merely for practice

Simulate instead.

### Treating `full-upgrade` as simply a "better upgrade"

It allows broader dependency changes and deserves careful review.

### Assuming installation success means the command is available through `PATH`

Verify package files and command resolution separately.

### Using `autoremove` blindly

Review the proposed removals.

### Removing unfamiliar packages

Understand their role first.

### Deleting APT lock files as a first response

Investigate active package-management processes.

### Killing APT or `dpkg` without understanding what they are doing

Interrupting package state changes can create additional problems.

### Running recovery commands without matching them to the failure

Use evidence first.

### Confusing `remove` with `purge`

They have different configuration-retention behavior.

### Assuming purge deletes all application data

It does not necessarily remove user-created or application-generated data.

### Assuming package names are command names

They often correspond, but not always.

# 49. Knowledge Check

### 1. What is APT?

APT is a high-level package-management system used on Debian-based Linux distributions such as Ubuntu to work with package metadata, repositories, dependencies, installations, upgrades and removals.

### 2. What package format is commonly used on Ubuntu?

Debian packages, commonly represented by `.deb` files.

### 3. What is the relationship between APT and `dpkg`?

APT provides higher-level package management, including repository interaction and dependency resolution, while `dpkg` manages Debian package installation state at a lower level.

### 4. What does `sudo apt update` do?

It refreshes local package metadata from configured package sources.

### 5. Does `apt update` upgrade installed packages?

No.

### 6. How can you search for a package?

```bash
apt search SEARCH_TERM
```

### 7. How can you inspect package metadata?

```bash
apt show PACKAGE
```

### 8. How can you inspect installed and candidate versions?

```bash
apt policy PACKAGE
```

### 9. What does `Installed: (none)` normally indicate?

APT does not currently consider that package installed.

### 10. What is the candidate version?

The package version APT currently considers the preferred installation/upgrade candidate according to configured sources and policy.

### 11. How can you query installed package state with `dpkg`?

```bash
dpkg -s PACKAGE
```

### 12. How can you simulate an APT operation?

For example:

```bash
apt -s install PACKAGE
```

### 13. Why should you simulate a package change?

To inspect the transaction and identify dependencies, upgrades, removals or other unexpected changes before modifying the system.

### 14. How do you install a package?

```bash
sudo apt install PACKAGE
```

### 15. Why should you read the transaction summary before confirming?

Because APT may change more packages than the one explicitly requested.

### 16. How can you list files installed by a package?

```bash
dpkg -L PACKAGE
```

### 17. How can you determine which installed package owns a file?

```bash
dpkg -S FILE_PATH
```

### 18. What is a package dependency?

Another package or capability required by a package.

### 19. What does `apt list --upgradable` show?

Installed packages for which APT currently knows an upgrade candidate.

### 20. What does `apt upgrade` do?

It requests upgrades for installed packages according to APT's upgrade rules.

### 21. Why should a system-wide upgrade not be run casually?

It may change important services, libraries, kernels and application dependencies and may require operational planning.

### 22. What is an important difference between `upgrade` and `full-upgrade`?

`full-upgrade` allows broader dependency-resolution changes, including package removals when necessary.

### 23. What does `apt remove PACKAGE` do?

It removes the package while potentially retaining package-managed configuration files.

### 24. What does `apt purge PACKAGE` do?

It removes the package and targets package-managed configuration files that ordinary removal may retain.

### 25. Does purge necessarily remove all application data?

No.

### 26. What does `apt autoremove` target?

Packages marked as automatically installed that APT now considers unnecessary.

### 27. Why should `autoremove` be reviewed before approval?

Because the administrator should understand the operational role of proposed removals rather than deleting packages blindly.

### 28. Why do APT and `dpkg` use locks?

To protect package-management state from unsafe concurrent modifications.

### 29. Should deleting a lock file be your first response to a lock error?

No.

### 30. What should you investigate first?

Whether another legitimate APT or `dpkg` process is active.

### 31. What can `dpkg --configure -a` help with?

It can configure unpacked but not fully configured packages, which may be relevant after an interrupted package operation.

### 32. Should you run `dpkg --configure -a` routinely?

No. Use it when evidence indicates that package configuration is incomplete.

### 33. What does `apt --fix-broken install` address?

Broken package dependency state.

### 34. Is `--fix-broken` a universal repair command?

No.

### 35. Why can `apt install` succeed while the shell still reports `command not found`?

The package may install an executable under a different name or into a directory not included in the current `PATH`.

### 36. How can you investigate that?

Verify package state with `dpkg -s`, list package files with `dpkg -L`, identify the executable and inspect command resolution.

### 37. What does `apt download PACKAGE` do?

It downloads the package archive without installing it.

### 38. Does downloading a package mean it is installed?

No.

### 39. What does `apt clean` primarily clean?

Downloaded package archives in APT's cache.

### 40. What is the safest basic package-management pattern?

```text
inspect
→ simulate/review
→ change
→ verify package state
→ verify function
```

# 50. Interview Practice

### What is the difference between `apt update` and `apt upgrade`?

`apt update` refreshes local package metadata from configured repositories. `apt upgrade` uses package metadata to upgrade installed packages according to APT's upgrade rules.

### How do you determine whether a package is already installed?

I can inspect `apt policy PACKAGE` and verify installed state using `dpkg -s PACKAGE` or another package-database query.

### How do you check what version APT would install?

I use:

```bash
apt policy PACKAGE
```

and inspect the candidate version.

### What do you do before installing an unfamiliar package?

I search for it, inspect its metadata and candidate version, review dependencies, simulate the transaction when appropriate, then inspect the actual proposed changes before approving installation.

### Why use `apt -s`?

It allows me to inspect the planned package transaction without applying it, which is useful for identifying unexpected installations, upgrades or removals.

### What is the difference between APT and `dpkg`?

APT operates at a higher level, working with repositories and dependency resolution. `dpkg` manages Debian packages and installed package state at a lower level.

### What is the difference between `apt remove` and `apt purge`?

`remove` removes package software while potentially retaining package-managed configuration. `purge` additionally targets configuration files that ordinary removal would retain.

### What does `apt autoremove` do?

It proposes removal of automatically installed packages that APT considers no longer required. I review the proposed transaction before approving it.

### You get "Could not get lock." What do you do?

I first investigate whether another APT or `dpkg` process is legitimately active. I do not immediately delete lock files or kill package processes.

### A package installed successfully but the command is not found. What do you investigate?

I verify the package is installed, list its files with `dpkg -L`, locate the executable, check whether its directory is in `PATH`, and verify that the expected command name is correct.

### How do you identify which package installed a particular file?

For an installed file, I can use:

```bash
dpkg -S FILE_PATH
```

### Why is a package installation a production change?

Because it can modify system files, dependencies, configuration, services, users, groups and runtime behavior. It should therefore be reviewed and verified like other system changes.

### Would you run `apt full-upgrade` automatically because updates are available?

No. I would review the proposed transaction and follow the system's maintenance and change-management process because `full-upgrade` can make broader dependency changes, including removals.

### How do you verify a package installation?

I verify both package state and actual functionality. For example, I inspect `apt policy`, query `dpkg`, inspect installed files when needed, and execute an appropriate functional check.
