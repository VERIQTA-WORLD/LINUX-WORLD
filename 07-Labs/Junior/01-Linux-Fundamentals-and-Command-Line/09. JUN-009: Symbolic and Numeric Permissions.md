- **Level:** Junior

- **Environment:** Ubuntu Server 24.04 LTS or a similar Linux system  
- **Privileges:** Standard user account; no `sudo` required for normal lab tasks

- **Prerequisites:** JUN-001 through JUN-008

---

## Lab Mission

You already know how to read a permission string such as:

```text
-rwxr-x---
```

You know that it can be separated into:

```text
user   group   other
rwx    r-x     ---
```

You also know from JUN-008 that those permission classes interact with file ownership.

Now you need to control them deliberately.

Linux gives you two major ways to express traditional permission changes:

```text
symbolic notation
```

and:

```text
numeric notation
```

Symbolic notation lets you express changes such as:

```text
add execute permission for the owner
remove write permission from the group
set other permissions to read only
```

Numeric notation represents complete permission sets using values such as:

```text
600
640
644
700
750
755
```

These are not magic Linux numbers.

They are compact representations of combinations of:

```text
read
write
execute
```

A production engineer should be able to look at:

```bash
chmod 640 app.conf
```

and understand exactly what access model it creates.

You should also be able to look at:

```bash
chmod g-w deployment.sh
```

and understand exactly what changes and what remains untouched.

This lab teaches both models from first principles.

More importantly, it teaches you to answer three questions before changing permissions:

> What is the current state?

> What is the intended state?

> What is the smallest correct change?

---

## What You Will Learn

By the end of this lab, you should be able to:

- Use `chmod` to change standard Linux permissions.
- Understand the symbolic classes `u`, `g`, `o`, and `a`.
- Understand the symbolic permissions `r`, `w`, and `x`.
- Use `+`, `-`, and `=` correctly.
- Add permissions without replacing unrelated permissions.
- Remove specific permissions.
- Set a permission class explicitly.
- Combine multiple symbolic changes.
- Understand the numeric values `4`, `2`, and `1`.
- Calculate numeric permission values.
- Translate symbolic modes into numeric modes.
- Translate numeric modes into symbolic modes.
- Understand common modes such as `600`, `640`, `644`, `700`, `750`, and `755`.
- Explain why `777` is not a generic solution.
- Apply different modes appropriately to files and directories.
- Understand why execute permission means different things for files and directories.
- Recognize when a permission change does not solve the real problem.
- Verify permission changes instead of assuming they worked.
- Diagnose and repair a controlled permission incident.
- Apply least-privilege reasoning to permission changes.

# Meet `chmod`

The primary command for changing traditional Linux permission modes is:

```text
chmod
```

The name comes from:

```text
change mode
```

Before using it extensively, inspect its help:

```bash
chmod --help
```

Then:

```bash
man chmod
```

Find the basic syntax.

A common form is:

```text
chmod MODE FILE
```

The `MODE` describes the permission change.

That mode can be expressed symbolically:

```bash
chmod u+x script.sh
```

or numerically:

```bash
chmod 755 script.sh
```

Both manipulate permission bits.

They simply express the desired state differently.

---

# The Symbolic Permission Language

Symbolic notation has three major pieces:

```text
WHO     OPERATION     PERMISSION
```

For example:

```text
u       +             x
```

Together:

```text
u+x
```

This means:

> Add execute permission for the user/owner class.

The possible classes are:

| Symbol | Meaning |
|---|---|
| `u` | user/owner |
| `g` | group |
| `o` | other |
| `a` | all three classes |

The permissions are:

| Symbol | Meaning |
|---|---|
| `r` | read |
| `w` | write |
| `x` | execute |

The operators you will use are:

| Operator | Meaning |
|---|---|
| `+` | add specified permission |
| `-` | remove specified permission |
| `=` | set the class to exactly the specified permissions |

That gives you a compact language for expressing permission changes.

---

# Add a Permission With `+`

Inspect:

```bash
ls -l scripts/hello.sh
```

Depending on your environment, a newly created text file commonly does not have execute permission.

Try running it:

```bash
./scripts/hello.sh
```

If execute permission is absent, Bash should report an access-related failure such as:

```text
Permission denied
```

Now inspect again:

```bash
ls -l scripts/hello.sh
```

Do not fix anything until you understand the evidence.

If the owner execute bit is missing, add it:

```bash
chmod u+x scripts/hello.sh
```

Verify:

```bash
ls -l scripts/hello.sh
```

You should now see `x` in the owner permission triplet.

Run:

```bash
./scripts/hello.sh
```

Expected output:

```text
VERIQTA permission lab
```

You have just made a targeted permission change.

You did not replace the entire mode.

You added one capability to one permission class.

---

# `+` Preserves Other Permissions

Suppose a file begins as:

```text
-rw-r--r--
```

and you run:

```bash
chmod u+x file
```

The intended transformation is:

```text
before:
rw- r-- r--

after:
rwx r-- r--
```

The group and other fields were not requested to change.

The owner's existing read and write permissions were not requested to disappear.

That is the value of `+`.

It means:

> Add this capability to the specified class.

---

# Remove a Permission With `-`

Inspect:

```bash
ls -l scripts/hello.sh
```

Now remove the owner's execute permission:

```bash
chmod u-x scripts/hello.sh
```

Verify:

```bash
ls -l scripts/hello.sh
```

Try:

```bash
./scripts/hello.sh
```

It should no longer execute directly if no applicable execute permission remains for your identity.

Restore the permission:

```bash
chmod u+x scripts/hello.sh
```

Verify:

```bash
./scripts/hello.sh
```

This demonstrates the second symbolic operation:

```text
-
```

means:

> Remove the specified permission.

---

# Set a Permission Class With `=`

The `=` operator behaves differently.

Create a controlled file:

```bash
touch files/equal-test.txt
```

Give the owner read and write access:

```bash
chmod u=rw files/equal-test.txt
```

Inspect:

```bash
ls -l files/equal-test.txt
```

Now run:

```bash
chmod u=r files/equal-test.txt
```

Inspect again:

```bash
ls -l files/equal-test.txt
```

The owner's permission class should now contain read permission but not write or execute permission.

Why?

Because:

```text
u=r
```

does not mean:

> Add read.

It means:

> Set the user permission class to exactly read.

This distinction is important.

Compare:

```text
u+r
```

with:

```text
u=r
```

The first adds.

The second replaces the specified class's permission set.

---

# Set Multiple Permissions at Once

You can specify more than one permission:

```bash
chmod u=rw files/equal-test.txt
```

This means:

```text
user:
read + write
```

You can also write:

```bash
chmod g=rx scripts/hello.sh
```

which means:

```text
group:
read + execute
```

Or:

```bash
chmod o= configs/app.conf
```

This sets the `other` class to no permissions.

Verify every change with:

```bash
ls -l TARGET
```

Do not rely only on command success.

---

# `a` Means All Permission Classes

The symbolic class:

```text
a
```

means:

```text
u + g + o
```

Create:

```bash
touch files/all-test.txt
```

Set:

```bash
chmod a=r files/all-test.txt
```

Inspect:

```bash
ls -l files/all-test.txt
```

You should see a mode equivalent to:

```text
r-- r-- r--
```

Now:

```bash
chmod a+w files/all-test.txt
```

Inspect again.

Each class should now include write permission as well.

Be careful with `a`.

A command affecting all permission classes can broaden access substantially.

Restore a conservative mode for the practice file:

```bash
chmod u=rw,g=r,o= files/all-test.txt
```

Verify:

```bash
ls -l files/all-test.txt
```

---

# Combine Symbolic Changes

You do not always need separate commands.

Create:

```bash
touch files/combined-test.txt
```

Set a known starting state:

```bash
chmod u=rw,g=r,o= files/combined-test.txt
```

Inspect:

```bash
ls -l files/combined-test.txt
```

Now run:

```bash
chmod u+x,g+w files/combined-test.txt
```

Verify:

```bash
ls -l files/combined-test.txt
```

You requested two changes:

```text
u+x
```

and:

```text
g+w
```

The comma separates symbolic clauses.

You can therefore express precise multi-class changes without using several commands.

---

# A Better Way to Read Symbolic Modes

When you see:

```text
g-w
```

read it as a sentence:

> From the group class, remove write permission.

When you see:

```text
o=r
```

read:

> Set other permissions to read only.

When you see:

```text
u+x
```

read:

> Add execute permission for the owner.

When you see:

```text
u=rw,g=r,o=
```

read:

> Give the owner read and write, give the group read, and give everyone else no permissions.

Do not memorize strings without translating them into access decisions.

# Numeric Permissions Begin With Three Values

Traditional numeric permission notation is based on three values:

```text
read    = 4
write   = 2
execute = 1
```

Remember:

```text
r = 4
w = 2
x = 1
```

A permission class can contain combinations of those capabilities.

The values are added together.

For example:

```text
r--
```

is:

```text
4
```

because only read is enabled.

```text
-w-
```

is:

```text
2
```

```text
--x
```

is:

```text
1
```

---

# Calculate Every Standard Permission Combination

There are eight possible combinations for one traditional permission class.

| Symbolic | Calculation | Numeric |
|---|---:|---:|
| `---` | 0 | `0` |
| `--x` | 1 | `1` |
| `-w-` | 2 | `2` |
| `-wx` | 2 + 1 | `3` |
| `r--` | 4 | `4` |
| `r-x` | 4 + 1 | `5` |
| `rw-` | 4 + 2 | `6` |
| `rwx` | 4 + 2 + 1 | `7` |

This table is the foundation of numeric permissions.

You do not need to memorize arbitrary three-digit numbers if you understand these eight combinations.

---

# Why There Are Three Permission Digits

A traditional permission mode such as:

```text
640
```

has one digit for each class:

```text
6    4    0
│    │    │
│    │    └── other
│    └─────── group
└──────────── user
```

So:

```text
640
```

means:

```text
user  = 6
group = 4
other = 0
```

Translate each digit:

```text
6 = rw-
4 = r--
0 = ---
```

Therefore:

```text
640
```

means:

```text
rw-r-----
```

That is all the three-digit notation is doing.

It compresses three permission triplets into three numbers.

---

# Translate `644`

Break it apart:

```text
6 4 4
```

User:

```text
6 = 4 + 2 = rw-
```

Group:

```text
4 = r--
```

Other:

```text
4 = r--
```

Therefore:

```text
644
```

means:

```text
rw-r--r--
```

Set a practice file:

```bash
chmod 644 files/report.txt
```

Verify:

```bash
ls -l files/report.txt
```

You should see:

```text
-rw-r--r--
```

The first `-` identifies the object type as a regular file.

The remaining nine characters are the standard permission bits.

# Translate `600`

Run:

```bash
chmod 600 files/notes.txt
```

Verify:

```bash
ls -l files/notes.txt
```

Calculate:

```text
6 = rw-
0 = ---
0 = ---
```

Therefore:

```text
600
```

means:

```text
rw-------
```

The owner can read and write.

The group receives no traditional permissions.

Other receives no traditional permissions.

This kind of restrictive mode is commonly appropriate for user-private data, depending on the system and application requirements.

---

# Translate `640`

Run:

```bash
chmod 640 configs/app.conf
```

Verify:

```bash
ls -l configs/app.conf
```

Calculate:

```text
6 = rw-
4 = r--
0 = ---
```

So:

```text
640
```

becomes:

```text
rw-r-----
```

This expresses:

```text
owner:
read + write

group:
read

other:
none
```

This is a useful example of a permission model where an owner manages a file while a group receives read access.

Whether it is appropriate for a real configuration file depends on the intended users, groups, application, and sensitivity of the data.

# Translate `750`

Run:

```bash
chmod 750 scripts/health-check.sh
```

Inspect:

```bash
ls -l scripts/health-check.sh
```

Calculate:

```text
7 = rwx
5 = r-x
0 = ---
```

Therefore:

```text
750
```

means:

```text
rwxr-x---
```

The owner receives:

```text
read + write + execute
```

The group receives:

```text
read + execute
```

Other receives:

```text
none
```

# Translate `755`

Set:

```bash
chmod 755 scripts/hello.sh
```

Inspect:

```bash
ls -l scripts/hello.sh
```

Calculate:

```text
7 = rwx
5 = r-x
5 = r-x
```

Therefore:

```text
755
```

means:

```text
rwxr-xr-x
```

This is a common mode for executable files and directories where broad read/traversal or execution access is intentionally required.

That does **not** mean every executable should automatically receive `755`.

The intended access model still determines the correct mode.

---

# Numeric Notation Sets the Complete Standard Permission Mode

This is an important difference.

Suppose a file currently has:

```text
rwxrwxrwx
```

and you run:

```bash
chmod 640 file
```

You are not saying:

> Modify one bit.

You are defining the standard permission state as:

```text
rw-r-----
```

Numeric notation is therefore convenient when you know the complete desired mode.

Symbolic notation can be more expressive when you want a targeted change.

For example:

```bash
chmod g-w file
```

means:

> Remove group write while leaving unrelated permissions alone.

While:

```bash
chmod 640 file
```

means:

> Set the standard user/group/other mode according to `640`.

Choose the notation that most clearly expresses your intended change.

# Translate Symbolic Permissions Into Numbers

Suppose you see:

```text
rwxr-----
```

Split it:

```text
rwx | r-- | ---
```

Calculate:

```text
rwx = 4 + 2 + 1 = 7
r-- = 4
--- = 0
```

Therefore:

```text
740
```

Now:

```text
rw-rw----
```

becomes:

```text
rw- = 6
rw- = 6
--- = 0
```

Therefore:

```text
660
```

And:

```text
r-xr-xr-x
```

becomes:

```text
555
```

```text
symbolic → numeric
numeric → symbolic
```

# Do Not Memorize `777` as "Full Permission"

You will often encounter advice online such as:

```bash
chmod 777 something
```

because it can make certain access problems disappear.

Calculate it:

```text
7 = rwx
7 = rwx
7 = rwx
```

Therefore:

```text
777
```

means:

```text
rwxrwxrwx
```

The owner, group, and other classes all receive read, write, and execute.

That is a very broad traditional permission mode.

The important question is not:

> Will `777` make the error disappear?

The important question is:

> Does every applicable user really need all of these capabilities?

If the answer is no, `777` is broader than the intended access model.

---

# Why `777` Is a Poor Generic Troubleshooting Strategy

Imagine an application cannot read:

```text
app.conf
```

Someone runs:

```bash
chmod 777 app.conf
```

The application may now read it.

But the command also granted:

```text
write
```

and:

```text
execute
```

permissions to every traditional class.

Those capabilities may have nothing to do with the original problem.

Worse, the root cause might have been:

- wrong ownership,
- wrong group,
- inaccessible parent directory,
- incorrect path,
- wrong service identity,
- or another access-control mechanism.

A successful command does not prove it was the correct fix.

# File Permissions and Directory Permissions Are Not Interchangeable

You learned this distinction in JUN-007.

Now you will configure it deliberately.

For a regular file:

```text
r
```

allows reading file contents.

```text
w
```

allows modifying file contents, subject to other filesystem conditions.

```text
x
```

allows the file to be considered executable through the normal permission model when the file is otherwise a valid executable/script.

For a directory:

```text
r
```

relates to reading directory entries.

```text
w
```

relates to modifying directory entries.

```text
x
```

allows traversal/search through the directory.

This is why a mode should never be interpreted without knowing the object type.

Create:

```bash
mkdir -p directories/path-test/parent/child
```

Create:

```bash

```


The file appears readable:


```bash

```


Expected:

```text

```

**Inspect the entire access path, not only the final file.**

# Symbolic Notation Is Excellent for Targeted Repairs

Suppose:

```text
-rw-rw-r--
```

is correct except the group should not have write permission.

You could calculate an entire numeric replacement.

But the intended change is naturally expressed as:

```bash
chmod g-w FILE
```

That says exactly what you mean:

> Remove group write permission.

Likewise:

```bash
chmod u+x SCRIPT
```

expresses:

> Make the script executable for its owner without changing unrelated classes.

Symbolic notation can make the operational intent very clear.

---

# Numeric Notation Is Excellent for Known Complete States

Suppose your design says a private file must be:

```text
owner:
read + write

group:
none

other:
none
```

That complete state translates to:

```text
600
```

So:

```bash
chmod 600 FILE
```

clearly establishes the complete standard mode.

Likewise, if a directory should be:

```text
owner:
rwx

group:
r-x

other:
---
```

then:

```text
750
```

expresses the complete mode compactly.

Neither notation is inherently "better."

Use the one that most clearly and safely expresses your intention.

# Do Not Confuse `chmod` With `chown`

You now know both commands.

```text
chmod
```

changes permission mode.

```text
chown
```

changes ownership.

Compare:

```bash
chmod 640 app.conf
```

with:

```bash
chown deploy:webteam app.conf
```

The first changes what permission classes can do.

The second changes which user/group identities are associated with ownership.

These are different operations.

When troubleshooting:

```text
Permission denied
```

you may need to inspect both.

Do not substitute one for the other.

When an operation fails, use evidence before `chmod`.

```text

        ↓

ERROR

        ↓

IDENTITY

        ↓

PATH
Is the path correct?

        ↓

OBJECT TYPE

Directory?
Something else?

        ↓

OWNERSHIP

        ↓

CURRENT MODE

        ↓

        ↓

        ↓

        ↓

        ↓

        ↓
```

# Engineer Note — Know the Required Capability

Do not ask:

> What chmod command fixes this?

Ask:

> What operation is failing, and what permission does that operation actually require?

Examples:

Reading a regular file generally requires:

```text
r
```

Directly executing an executable file requires:

```text
x
```

Traversing a directory requires:

```text
x
```

Listing directory entries requires:

```text
r
```

Creating or removing entries inside a directory depends heavily on the directory's permissions, particularly write and execute, not merely the permissions of an existing file inside it.

Reason from the operation.

Then decide the mode.

# Engineer Note — File Deletion Is a Directory Operation

Create:

```bash
mkdir -p directories/delete-test
```

Create:

```bash
touch directories/delete-test/protected.txt
```

Set the file itself to:

```bash
chmod 400 directories/delete-test/protected.txt
```

Inspect:

```bash
ls -l directories/delete-test/protected.txt
```

The file is not writable through its owner mode.

Yet deletion of a directory entry is primarily controlled by permissions on the containing directory.

This is an important Linux concept:

> The ability to modify a file's contents and the ability to remove its directory entry are not the same operation.

Do not delete the file yet.

Inspect:

```bash
ls -ld directories/delete-test
```

This distinction becomes increasingly important in administration and security work.

---

# Engineer Note — `x` Does Not Mean the Same Thing Everywhere

For a regular file:

```text
x
```

relates to execution.

For a directory:

```text
x
```

relates to traversal/search.

Therefore:

```text
755
```

on a script and:

```text
755
```

on a directory contain the same bit pattern but support different filesystem behavior because the objects are different types.

Always interpret:

```text
mode + object type
```

together.

---

# Engineer Note — Do Not Add Execute Permission to Every File

A common beginner habit is assuming:

```text
755 = good
```

and applying it to everything.

A configuration file usually does not need to be executable merely because a script does.

A data file usually does not need execute permission.

Permission design should reflect the object's function.

Ask:

```text
Does this object need to be read?
Does it need to be modified?
Does it need to be executed?
Is it a directory that needs traversal?
Who needs each capability?
```

Then construct the mode.

---

# Engineer Note — `chmod` Can Operate Recursively

Check:

```bash
chmod --help
```

You will find recursive support, commonly:

```text
-R
```

A recursive permission change can modify an entire directory tree.

That can be useful.

It can also be dangerous.

Do not practice commands such as:

```text
chmod -R ...
```

against system directories or your entire home directory.

A recursive permission change can unintentionally make:

- sensitive files readable,
- files writable,
- data inaccessible,
- scripts executable,
- directories untraversable,
- applications unusable.

In this junior lab, focus on precise targets.

Later administration labs will give you larger permission-management scenarios.

# Engineer Note — `sudo chmod` Is Not the Default

All normal files in this lab belong to your user.

Therefore you should not need:


to change their modes.

If `chmod` unexpectedly reports:

```text

```

do not automatically add `sudo`.


- Am I operating on the expected file?

# Symbolic vs Numeric: Choose by Intent

Suppose a file currently has:

```text

```

and your only requirement is:

This is very clear:

Suppose instead the security standard says:

This is very clear:

The first expresses a relative change.

Good engineers choose commands that make their intent understandable.

# Common Mistakes to Avoid

### Memorizing permission numbers without understanding them

Calculate them from `r`, `w`, and `x`.

### Using `777` whenever something fails

Investigate the actual required capability.

### Forgetting that directories need execute permission for traversal

A directory with `600` behaves very differently from a regular file with `600`.

### Treating execute permission as identical for files and directories

Object type changes the meaning.

### Changing permissions before checking ownership

The problem may belong to JUN-008's ownership layer.

### Looking only at the final file

Parent-directory permissions can block access.

### Assuming successful owner access proves the mode is correct

A file can work for you while being dangerously broad or too restrictive for intended users.

### Adding execute permission to configuration and data files without reason

Permissions should reflect function.

### Using `sudo chmod` automatically

Investigate ownership and identity first.

### Applying recursive permission changes casually

The blast radius can be much larger than expected.

### Confusing `chmod` with `chown`

One changes mode; the other changes ownership.

### Verifying only the command exit status

Inspect the resulting mode and test the intended behavior.

### 23. What does this do?


### 24. What does this do?

```bash

```

It removes group write permission.

### 25. What is the major conceptual difference between `u+x` and `u=x`?

`u+x` adds execute while preserving the owner's other permissions.

`u=x` sets the owner's class to execute only.

### 26. Why is `600` often unsuitable for a directory you need to enter?

Because the owner lacks directory execute/traversal permission.

### 27. Why can a readable file still be inaccessible?

A required parent directory may lack execute/traversal permission, ownership may be wrong, or another access-control layer may block the operation.

It grants read, write, and execute permissions to all traditional classes, which is often much broader than required and may hide the actual cause.

### 29. What is the difference between `chmod` and `chown`?

`chmod` changes permission mode. `chown` changes ownership.

### 30. What should you do after changing permissions?

Inspect the resulting mode and repeat the original operation or other appropriate tests to verify the intended behavior.

# Interview Practice

### Explain Linux numeric permissions.

Traditional numeric permissions represent the `r`, `w`, and `x` bits using values `4`, `2`, and `1`. The values enabled for each permission class are added together, producing one digit each for user, group, and other. For example, `640` means owner `rw-`, group `r--`, and other `---`.

### What is the difference between symbolic and numeric `chmod`?

Symbolic notation expresses permission changes using classes such as `u`, `g`, and `o`, operators such as `+`, `-`, and `=`, and permissions such as `r`, `w`, and `x`. Numeric notation expresses a complete traditional permission mode using calculated digits such as `640` or `755`.

### What does `chmod u+x file` do?

It adds execute permission to the user/owner class without intentionally replacing unrelated permission bits.

### What does `chmod 750 file` mean?

It sets the standard permission mode to owner `rwx`, group `r-x`, and other `---`.

### Why is `chmod 777` usually a poor troubleshooting response?

Because it grants every traditional permission to every permission class, often far beyond what the failing operation requires. It can also hide problems involving ownership, parent directories, identity, or other access controls.

### Why does execute permission matter on a directory?

For a directory, execute permission controls traversal/search access through that directory. Without it, knowing that a file exists inside the directory does not necessarily allow you to access that file.

### What is the difference between read permission on a file and read permission on a directory?

For a regular file, read permission allows reading its contents. For a directory, read permission relates to reading its directory entries.

### Can a file have `644` and still be inaccessible?

Yes. A required parent directory may not allow traversal, the relevant ownership/class may differ from what is assumed, or another access-control mechanism may apply.

### When would you prefer symbolic notation?

When expressing a targeted change such as removing group write or adding owner execute while preserving unrelated permission bits.

### When would numeric notation be useful?

When the complete desired traditional mode is known, such as establishing a policy of `640`, `600`, or `750`.

### Why should permissions be derived from requirements instead of memorized defaults?

Because different files, directories, users, services, and applications require different capabilities. A mode is correct only when it matches the intended access model.

### How would you troubleshoot a permission-denied error?

I would identify the failing operation and process identity, verify the path and object type, inspect ownership and current permissions, inspect required parent-directory traversal, determine the intended access model, make the smallest justified change, and repeat the original operation to verify recovery.
