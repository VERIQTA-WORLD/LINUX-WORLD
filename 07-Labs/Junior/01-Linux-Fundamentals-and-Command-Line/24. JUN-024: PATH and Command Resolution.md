# JUN-024: PATH and Command Resolution

- **Level:** Junior  
- **Difficulty:** 2/5  
- **Estimated time:** 75–100 minutes  
- **Environment:** Ubuntu Server 24.04 LTS with Bash  
- **Privileges:** No `sudo` required  
- **Primary skills:** command resolution, `PATH`, absolute paths, relative paths, `type`, `command -V`, `which`, shell builtins, executable lookup, PATH ordering, command-not-found troubleshooting  
- **Prerequisites:** JUN-001 through JUN-023

---

## Lab Mission

You type:

```bash
ls
```

and Linux runs a program.

But you did not type:

```bash
/usr/bin/ls
```

So how did the shell know what `ls` meant?

And why can this happen?

```text
$ mytool
bash: mytool: command not found
```

even when a file named `mytool` exists in your current directory?

Or this?

```text
two directories contain commands with the same name
```

yet one is selected before the other?

The answer begins with **command resolution**.

When Bash receives a command name, it must determine what that name represents.

Depending on the command and shell state, it may resolve to something such as:

```text
alias
shell function
shell builtin
executable file found through PATH
```

An explicit pathname changes the situation because you have already told the shell where the file is.

Your investigation model for this lab is:

```text
COMMAND ENTERED
      ↓
WHAT DOES THE SHELL THINK IT IS?
      ↓
type / command -V
      ↓
EXPLICIT PATH PROVIDED?
      ↓
if not, is PATH search relevant?
      ↓
INSPECT PATH
      ↓
CHECK SEARCH ORDER
      ↓
VERIFY SELECTED COMMAND
      ↓
RUN
```

By the end of this lab, `command not found` should no longer mean:

```text
Linux is broken.
```

It should trigger a structured investigation.

# 2. A Command Name Is Not Necessarily a File Path

Compare:

```bash
ls
```

with:

```bash
/usr/bin/ls
```

The first is a command name without a slash.

The second is an explicit pathname.

Verify the executable:

```bash
ls -l /usr/bin/ls
```

Now run:

```bash
/usr/bin/ls
```

The program runs directly from the path you specified.

Conceptually:

```text
ls
 ↓
shell must resolve the name
 ↓
PATH may be involved
 ↓
/usr/bin/ls
```

But:

```text
/usr/bin/ls
      ↓
explicit pathname supplied
      ↓
shell does not need PATH to discover that file
```

This distinction is fundamental.

# 3. Absolute and Relative Command Paths

You already learned absolute and relative paths earlier in Linux World.

Now apply them to command execution.

An absolute executable path might be:

```bash
/usr/bin/ls
```

A relative executable path might look like:

```bash
./bin/tool
```

The key difference is:

```text
tool
```

contains no slash.

But:

```text
./tool
```

contains a slash and explicitly identifies a path relative to the current directory.

This becomes important later in the lab.

# 4. Inspect PATH

From JUN-023, you already know that `PATH` is an environment variable.

Inspect it:

```bash
printenv PATH
```

You may see something resembling:

```text
/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```

Your actual value may differ.

The colon:

```text
:
```

separates directory entries.

Conceptually:

```text
PATH=
directory 1
:
directory 2
:
directory 3
:
directory 4
```

For external command lookup, Bash can search these directories in order.

Think:

```text
COMMAND NAME
      ↓
first PATH directory
      ↓
usable command found?
   ┌───────┴───────┐
   │               │
  yes              no
   │               │
   ▼               ▼
 use it       next directory
```

The order matters.

# 12. Why Bash Did Not Automatically Search `.`

When you typed:

```bash
veriqta-tool
```

you gave Bash a command name without a slash.

For an external executable lookup, PATH matters.

When you typed:

```bash
./veriqta-tool
```

you supplied a relative pathname.

The prefix:

```text
./
```

means:

```text
from the current directory
```

So:

```text
veriqta-tool
```

asks the shell to resolve a command name.

While:

```text
./veriqta-tool
```

explicitly identifies a filesystem path.

This behavior has an important security benefit.

If the current directory were always searched automatically before trusted command directories, an attacker could potentially place a malicious program with a familiar command name in a directory you enter.

You type:

```text
ls
```

expecting the trusted command.

A malicious local file named:

```text
ls
```

could become dangerous if unsafe command-search rules caused it to take precedence.

PATH ordering is therefore not merely convenience.

It is part of execution security.

# 16. PATH Order Matters

Your temporary PATH starts with:

```text
$HOME/linux-world-labs/JUN-024/bin
```

That means Bash can consider this directory before later PATH directories when searching for an external command.

Think:

```text
PATH=A:B:C
```

For an external executable lookup:

```text
search A
   ↓
found?
 ┌─┴─┐
yes  no
 │    ↓
use   search B
      ↓
     found?
```

The first suitable match found through PATH wins for that lookup.

This means PATH order can change which executable runs.

# 23. Command Resolution Is Broader Than PATH

A common beginner model is:

```text
I type a command
      ↓
Bash searches PATH
```

That model is incomplete.

A better introductory model is:

```text
COMMAND NAME
      ↓
Bash interprets the name
      ↓
shell constructs may resolve it
      ↓
if external executable lookup is needed
      ↓
PATH becomes relevant
```

For this lab, recognize these important command forms:

```text
alias
function
builtin
external executable
explicit pathname
```

You do not need to memorize Bash's complete internal resolution algorithm yet.

You do need to stop assuming PATH explains every command.

# 26. Troubleshoot `command not found` Systematically

When a command cannot be found, do not immediately edit PATH.

Start with questions.

### 1. Did you type the name correctly?

Linux command names are case-sensitive.

```text
veriqta-tool
```

is not:

```text
VERIQTA-TOOL
```

---

### 2. Does the shell know the command?

```bash
type COMMAND
```

or:

```bash
command -V COMMAND
```

---

### 3. Do you know where the executable is supposed to be?

If you know the exact path:

```bash
ls -l /expected/path/COMMAND
```

---

### 4. Can it run through its explicit path?

```bash
/expected/path/COMMAND
```

### 5. Is the directory represented in PATH?

```bash
printenv PATH
```

Read the entries.

---

### 6. Does the file have execute permission?

```bash
ls -l /expected/path/COMMAND
```

---

### 7. Is another command with the same name resolving first?

```bash
type -a COMMAND
```

---

### 8. Are you testing the same shell environment?

Remember JUN-023.

Different processes can have different environments.

# 30. PATH Ordering Is a Security Boundary

Imagine this unsafe search order:

```text
untrusted-writable-directory
:
trusted-system-directories
```

If an attacker can create files in the first directory, they may create an executable with the same name as a command someone expects to run.

The search order could then select the malicious file first.

That is why you should not casually place:

```text
.
```

Remember JUN-023.

# 40. Knowledge Check

### 1. What is command resolution?

The process by which the shell determines what a command name represents and what should be executed.

### 2. What is PATH?

An environment variable containing an ordered list of directories used when external executable lookup through PATH is required.

### 3. How are PATH directories separated?

By colons.

### 4. Does PATH order matter?

Yes. Earlier matching executable locations take precedence during PATH search.

### 5. What does `type COMMAND` tell you?

How Bash resolves or interprets the command name.

### 6. What does `type -a COMMAND` help show?

Multiple available resolutions or matches for the command name.

### 7. What does `command -V COMMAND` do?

It provides shell-aware information about how the command name resolves.

### 8. Why isn't `which` always enough?

Because command resolution can involve shell constructs such as builtins, aliases, or functions, while `which` is primarily associated with executable-path lookup.

### 9. Is `cd` normally an external executable?

No. In Bash it is a shell builtin.

### 10. Why does `./program` work when `program` may not?

`./program` supplies an explicit relative pathname. `program` requires the shell to resolve the bare command name.

### 11. Does `./program` require the current directory to be in PATH?

No.

### 12. Does file existence guarantee execution?

No. The correct path and required execute permission also matter.

### 13. Does file existence guarantee bare command-name resolution?

No.

### 14. What happens when two external executables with the same name are found in different PATH directories?

The executable in the earlier applicable PATH directory is selected for that PATH lookup.

### 15. Why can PATH ordering be a security issue?

An untrusted executable earlier in PATH can shadow a trusted command name.

### 16. Why is putting `.` first in PATH risky?

The current directory changes as you navigate, so an untrusted directory could contain a malicious command that shadows a familiar name.

### 17. What is safer when deliberately running a program from the current directory?

Use an explicit relative path such as:

```bash
./program
```

### 18. Does changing PATH in your shell change every process on the system?

No.

### 19. Why not?

Environment state belongs to processes and is inherited according to the parent-child model learned in JUN-023.

### 20. If an explicit pathname works but the bare command does not, what should you investigate?

Command resolution and PATH are strong investigation targets.

### 21. If a command runs but it is the wrong executable, what should you inspect?

`type`, `type -a`, `command -V`, and PATH ordering.

### 22. Should you permanently modify shell configuration in this lab?

No. Persistent shell configuration belongs to JUN-025.

# 41. Interview Practice

### What happens when you type a command such as `ls` in Bash?

Bash resolves the command name. Depending on what the name represents, it may resolve through shell constructs such as aliases, functions, or builtins, or it may locate an external executable using PATH.

### What is PATH?

PATH is an environment variable containing an ordered list of directories used when the shell needs to locate an external executable by command name.

### How do you determine what Bash will run for a command?

I start with:

```bash
type COMMAND
```

or:

```bash
command -V COMMAND
```

I can use:

```bash
type -a COMMAND
```

to inspect additional matches.

### What is the difference between `command` and `./command`?

`command` is a bare command name that Bash must resolve. `./command` is an explicit relative pathname referring to a file in the current directory.

### What is the difference between `command` and `/path/to/command`?

The first requires command resolution. The second explicitly identifies the file to execute and does not require PATH to discover it.

### Why might a file exist but produce `command not found` when its name is typed?

Its directory may not be in PATH, or the shell may otherwise be unable to resolve that bare command name.

### Why might the wrong version of a command run?

Multiple commands with the same name may exist, and shell resolution or PATH ordering may select a different one than expected.

### Why use `type` instead of relying only on `which`?

`type` is shell-aware and can identify aliases, functions, builtins, and external command paths, making it more useful for understanding Bash command resolution.

### Why is PATH order important?

When PATH search is used, earlier directories are searched before later ones, so order can determine which executable is selected.

### Why is PATH also a security concern?

A malicious or untrusted executable placed in an earlier searchable directory can shadow a trusted command name.

### Why shouldn't the current directory casually be placed first in PATH?

Because the current directory may be untrusted and changes as you navigate. A malicious executable could then shadow a familiar command.

### How would you troubleshoot `command not found`?

I verify the exact command name, ask the shell how it resolves the name, determine where the executable is expected, verify the file exists and is executable, test the explicit path, inspect PATH and its ordering, and confirm that I'm testing the relevant process environment.

### How would you troubleshoot a command that runs but behaves like the wrong program?

I would use `type`, `type -a`, and `command -V` to identify what Bash resolves, inspect PATH ordering, test candidate executables by explicit path, identify the resolution cause, apply the minimum change, and verify again.

### Does changing PATH in one shell update all running applications?

No. PATH is part of process environment state. Other processes may have different environments.

### How would you make a PATH change permanent?

That requires shell or environment configuration, which is handled separately rather than treating a temporary export as permanent configuration.
