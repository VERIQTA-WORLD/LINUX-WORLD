- **Level:** Junior  
- **Difficulty:** 2/5  
- **Estimated time:** 75–95 minutes  
- **Environment:** Ubuntu Server 24.04 LTS with GNU `grep`  
- **Privileges:** No `sudo` required

- **Prerequisites:** JUN-001 through JUN-027

## 1. Lab Mission

Linux systems generate and store enormous amounts of text.

Configuration files, application output, inventories, reports, logs, command output, and troubleshooting evidence may contain hundreds or thousands of lines when you need only a few.

Reading everything manually does not scale.

You need to answer questions such as:

```text
Which lines contain ERROR?

Where does api-server appear?

Which file contains timeout?

How many matching lines exist?

Which lines do NOT contain healthy?

Where is this exact string used?

What happened immediately before and after this match?
```

One of the foundational Linux tools for these tasks is:

```bash
grep
```

At its simplest:

```bash
grep "ERROR" application.log
```

means:

> Search `application.log` and print lines that match `ERROR`.

But `grep` becomes much more useful when you understand what it is actually doing.

The core model is:

```text
TEXT INPUT
    │
    ▼
  grep
    │
    ▼
PATTERN MATCHING
    │
 ┌──┴──┐
 │     │
match  no match
 │
 ▼
selected output
```

`grep` can receive text from:

```text
a file
multiple files
stdin
a pipeline
a directory tree when recursive search is requested
```

and can change what it reports depending on the options you choose.

Your mission is not to memorize a list of flags.

Your mission is to learn how to turn a troubleshooting question into a precise text search.

### Learning objectives

By the end of this lab, you should be able to:

- explain what `grep` does;
- search a file for matching lines;
- understand that matching is case-sensitive by default;
- use `-i` for case-insensitive matching;
- use `-n` to display line numbers;
- use `-c` to count matching lines;
- use `-v` to invert a match;
- search multiple files;
- understand filename prefixes in multi-file results;
- use `-l` to identify files containing matches;
- use `-w` when whole-word matching is appropriate;
- use `-F` for fixed-string searching;
- understand that default `grep` patterns are regular expressions;
- use basic context options such as `-A`, `-B`, and `-C`;
- search directory trees with `-r`;
- use `grep` in a pipeline;
- use `-q` for a quiet match check;
- distinguish "no match" from an operational search error;
- avoid searching binary, sensitive, or enormous directory trees carelessly;
- choose search options based on the question you are trying to answer.

### Lab boundary

This lab does not attempt to teach:

```text
advanced regular expressions
sed
awk
find
xargs
shell scripting
large-scale log analytics
full exit-code engineering
```

You will use simple patterns here.

## 3. Search for Matching Lines

Start with:

```bash
grep "ERROR" logs/api.log
```

You should find the uppercase `ERROR` lines.

The basic syntax is:

```text
grep PATTERN FILE
```

For example:

```bash
grep "timeout" logs/api.log
```

should find the database timeout line.

Search for:

```bash
grep "health check" logs/api.log
```

Because the pattern contains a space, quoting it keeps the words together as one shell argument.

### `grep` prints matching lines

A crucial point:

```bash
grep "ERROR" logs/api.log
```

does not normally print only the word:

```text
ERROR
```

It prints each **line** containing a match.

The model is:

```text
read line
   ↓
does pattern match somewhere on this line?
   │
 yes
   ↓
print matching line
```

### No match is different from an error message

Run:

```bash
grep "CRITICAL" logs/api.log
```

There may be no output.

That can simply mean:

```text
the search completed
but no line matched
```

Now run:

```bash
grep "ERROR" logs/does-not-exist.log
```

That is different.

`grep` should report that the file cannot be read because it does not exist.

Do not confuse:

```text
no matching evidence
```

with:

```text
the search itself could not be performed correctly
```

That distinction is important in troubleshooting.

## 4. Control Case, Line Numbers, Counts, and Inverse Matches

By default, `grep` matching is case-sensitive.

Run:

```bash
grep "ERROR" logs/api.log
```

Now:

```bash
grep "error" logs/api.log
```

These searches are not equivalent.

Your dataset contains:

```text
ERROR
```

and:

```text
error
```

as different text.

### Ignore case with `-i`

Run:

```bash
grep -i "error" logs/api.log
```

Now uppercase and lowercase forms can match.

Use this when capitalization is not part of the question.

Do not automatically use `-i` for every search. Sometimes case differences are meaningful.

---

### Add line numbers with `-n`

Run:

```bash
grep -n "ERROR" logs/api.log
```

Typical output will include the source line number before each matching line.

This is useful when you need to:

- return to a specific location;
- discuss evidence with another engineer;
- inspect nearby lines;
- document where a setting or event appears.

Combine options:

```bash
grep -in "error" logs/api.log
```

This means:

```text
-i  ignore case
-n  show line numbers
```

GNU command-line options can often be combined when appropriate.

---

### Count matching lines with `-c`

Run:

```bash
grep -c "ERROR" logs/api.log
```

This reports how many **lines** match.

That wording matters.

`grep -c` counts matching lines, not necessarily every individual occurrence of the pattern.

If one line contained `ERROR` three times, that line would still count as one matching line for `grep -c`.

Try:

```bash
grep -ic "error" logs/api.log
```

Now the count includes matching lines regardless of case.

---

### Invert the search with `-v`

Sometimes the useful question is:

> Which lines do not match this pattern?

Run:

```bash
grep -v "INFO" logs/api.log
```

This selects lines that do **not** match `INFO`.

You can combine it with case-insensitive matching:

```bash
grep -iv "info" logs/api.log
```

Think:

```text
normal grep
    ↓
show matching lines
```

versus:

```text
grep -v
    ↓
show non-matching lines
```

Use inverse matching carefully. It answers a different question rather than making the search "better."

## 5. Search Precisely: Words, Fixed Strings, and Patterns

A simple command such as:

```bash
grep "api" logs/api.log
```

can match `api` wherever the pattern occurs.

That may include text such as:

```text
api-server
customer-api
```

Sometimes that is exactly what you want.

Sometimes it is too broad.

### Whole-word matching with `-w`

Create:

```bash
nano components.txt
```

Enter:

```text
api
api-server
customer-api
api worker
database
```

Save and exit.

Run:

```bash
grep "api" components.txt
```

Then compare:

```bash
grep -w "api" components.txt
```

`-w` requires the match to form a word according to `grep`'s word-boundary rules.

Notice that punctuation such as a hyphen is not itself a word character, so whole-word behavior may not always match your intuitive idea of a "component name."

Use `-w` when its definition matches the question you are asking.

---

### Default patterns are not always literal text

By default, GNU `grep` interprets its pattern as a **basic regular expression**.

That means some characters can have pattern meaning.

You do not need to master regular expressions in this lab.

You do need to know that:

```text
grep pattern matching
```

is not always identical to:

```text
search these characters literally
```

### Fixed-string searching with `-F`

Create:

```bash
nano versions.txt
```

Enter:

```text
release=1.2.3
release=1x2x3
release=2.0.0
```

Save and exit.

Run:

```bash
grep "1.2.3" versions.txt
```

The dot has special meaning in a regular expression: it can match any single character.

Your search may therefore match more than the literal version string you intended.

Now run:

```bash
grep -F "1.2.3" versions.txt
```

`-F` treats the pattern as a fixed string.

For literal operational values such as:

```text
1.2.3
db.internal
service[01]
a+b
```

fixed-string mode can make your intent clearer when you do not want regular-expression interpretation.

The engineering question is:

```text
Am I searching for a pattern?

or

Am I searching for this exact sequence of characters?
```

For the second case, consider `-F`.

## 6. Search Multiple Files and Directory Trees

Search both log files:

```bash
grep "ERROR" logs/api.log logs/worker.log
```

When searching multiple files, `grep` normally identifies which file produced each matching line.

That immediately answers:

```text
Where did this evidence come from?
```

Now ignore case:

```bash
grep -i "error" logs/api.log logs/worker.log
```

### Find only the filenames with `-l`

Suppose you do not need every matching line yet.

You only need to know:

> Which files contain `timeout`?

Run:

```bash
grep -l "timeout" logs/api.log logs/worker.log
```

The result lists matching filenames.

This is useful for narrowing an investigation before reading detailed evidence.

---

### Recursive search with `-r`

You can ask `grep` to search files beneath a directory recursively:

```bash
grep -r "timeout" logs
```

Add line numbers:

```bash
grep -rn "timeout" logs
```

Or ignore case:

```bash
grep -rin "error" logs
```

This is useful when you know:

```text
the text I need is somewhere under this directory
```

but not exactly which file contains it.

### Recursive search deserves a scope

Avoid casually running searches such as:

```text
grep -r PATTERN /
```

A broad filesystem search can encounter:

- permission errors;
- virtual filesystems;
- device-related paths;
- enormous directory trees;
- binary data;
- sensitive files;
- network-mounted content;
- irrelevant results.

Start with the narrowest reasonable directory.

For this lab:

```text
~/linux-world-labs/JUN-028/
```

is the correct scope.

## 7. Add Context Around a Match

A matching log line is not always enough.

Suppose you find:

```text
ERROR database connection timeout
```

You may need to know what happened immediately before or after it.

GNU `grep` provides context options.

### Lines after the match

Run:

```bash
grep -A 2 "database connection timeout" logs/api.log
```

`-A 2` means:

```text
show the matching line
+
2 lines After it
```

### Lines before the match

Run:

```bash
grep -B 2 "database connection timeout" logs/api.log
```

`-B 2` means:

```text
2 lines Before
+
matching line
```

### Lines on both sides

Run:

```bash
grep -C 2 "database connection timeout" logs/api.log
```

`-C 2` provides context on both sides.

Think:

```text
-A = After
-B = Before
-C = Context around
```

Context is especially useful during incident investigation because the line containing the word `ERROR` may not contain the whole story.

But context is still evidence.

Do not automatically assume:

```text
line before error
=
root cause
```

or:

```text
line after error
=
successful recovery
```

Interpret what the surrounding lines actually say.

## 8. Filter Pipeline Output with `grep`

JUN-027 taught you:

```text
COMMAND A
    │
    │ stdout
    ▼
    |
    │
    │ stdin
    ▼
COMMAND B
```

`grep` is especially useful as the command on the right side of a pipe because it can read stdin.

Run:

```bash
cat logs/api.log | grep "ERROR"
```

The data flow is:

```text
api.log
  │
  ▼
 cat
  │ stdout
  ▼
  |
  │ stdin
  ▼
 grep
  │
  ▼
matching lines
```

This works.

But there is an important engineering lesson:

```bash
grep "ERROR" logs/api.log
```

is simpler when `grep` can read the file directly.

Do not add a pipeline when it provides no benefit.

The pipeline becomes more useful when the left command is producing data that `grep` needs to filter.

For example:

```bash
ls -la | grep "log"
```

Here:

```text
ls -la
   │
   │ stdout
   ▼
 grep "log"
```

`grep` filters the text produced by `ls`.

Remember from JUN-027:

A normal pipe carries stdout.

stderr remains separate unless explicitly handled.

---

### Filter a pipeline and redirect the result

Run:

```bash
cat logs/api.log | grep -i "error" > api-errors.txt
```

Verify:

```bash
cat api-errors.txt
```

The flow is:

```text
api.log
  │
  ▼
 cat
  │
  ▼
  |
  │
  ▼
grep -i "error"
  │
  │ stdout
  ▼
api-errors.txt
```

You have now combined three earlier concepts:

```text
file input
+
pipeline
+
output redirection
```

## 9. Quiet Checks with `grep -q`

Sometimes you do not need the matching line.

You only need to ask:

> Does this text appear?

Run:

```bash
grep -q "database_host" service.conf
```

Nothing should normally be printed.

That is intentional.

`-q` means quiet mode.

Now combine it with the conditional execution you learned in JUN-027:

```bash
grep -q "database_host" service.conf && echo "Database configuration found"
```

Because the pattern exists, the message should appear.

Now:

```bash
grep -q "redis_host" service.conf || echo "Redis configuration not found"
```

Because the pattern does not exist, the failure-side command should run.

At this stage, understand the behavior conceptually:

```text
grep found a match
      ↓
success condition
```

```text
grep found no match
      ↓
different completion condition
```

Formal numeric exit-code analysis belongs to JUN-064.

### Important limitation

Do not treat every `||` branch after `grep -q` as automatically meaning:

```text
pattern definitely absent
```

A search can also fail operationally.

For example:

```bash
grep -q "ERROR" missing-file.txt || echo "No ERROR found"
```

The message:

```text
No ERROR found
```

would be misleading because the file itself could not be searched.

This is a valuable engineering distinction:

```text
NO MATCH
≠
SEARCH FAILURE
```

Later exit-code work will let you distinguish those states more precisely.

For now, verify that the input exists and is readable before drawing strong conclusions.

## 10. Controlled Investigation: A Service Appears Unhealthy

You receive this report:

> The customer API showed a problem around 09:01. Determine whether the available logs contain errors, identify which services recorded them, find timeout-related evidence, and inspect the surrounding API events.

You have:

```text
logs/api.log
logs/worker.log
```

### Start broad enough to find relevant evidence

Search both files without assuming capitalization:

```bash
grep -in "error" logs/api.log logs/worker.log
```

Record:

```text
Which files contain errors?

How many matching lines appear in each file?

Which error messages are present?
```

Now count separately:

```bash
grep -ic "error" logs/api.log
```

```bash
grep -ic "error" logs/worker.log
```

Next, identify files containing timeout evidence:

```bash
grep -l "timeout" logs/api.log logs/worker.log
```

Then inspect timeout matches with line numbers:

```bash
grep -n "timeout" logs/api.log logs/worker.log
```

Now investigate the database timeout in context:

```bash
grep -C 2 "database connection timeout" logs/api.log
```

### Evidence

You can now establish from the practice dataset that:

- the API log contains error evidence;
- the worker log also contains error evidence;
- timeout-related text appears in the logs;
- the API database timeout has events around it that can be inspected.

But be careful with the next step.

The presence of:

```text
WARN response latency increased
```

before:

```text
ERROR database connection timeout
```

does not by itself prove that the warning caused the timeout.

Likewise:

```text
INFO retry completed
```

after the error does not by itself prove every affected request recovered.

The correct reasoning is:

```text
SEARCH
  ↓
LOCATE EVIDENCE
  ↓
ADD CONTEXT
  ↓
FORM HYPOTHESIS
  ↓
SEEK MORE EVIDENCE
  ↓
THEN DETERMINE CAUSE
```

`grep` helps you find evidence.

It does not perform root-cause analysis for you.

## 11. Common Mistakes and Troubleshooting

### Mistake: Wrong capitalization

You run:

```bash
grep "error" logs/worker.log
```

and get no result even though the file contains:

```text
ERROR
```

Investigate the exact text.

If case does not matter:

```bash
grep -i "error" logs/worker.log
```

---

### Mistake: Pattern is too broad

You search:

```bash
grep "api" components.txt
```

and receive several lines.

The search is not necessarily wrong.

Your question may be imprecise.

Ask whether you need:

```text
substring match
whole word
fixed string
different pattern
```

Then choose the appropriate option.

---

### Mistake: Treating regex characters literally

You search:

```bash
grep "1.2.3" versions.txt
```

while intending the literal version number.

Because default `grep` patterns are regular expressions, `.` has pattern meaning.

Use:

```bash
grep -F "1.2.3" versions.txt
```

when fixed-string behavior matches your intent.

---

### Mistake: Searching the wrong file

A correct pattern against the wrong input still produces an unhelpful investigation.

Before changing the pattern repeatedly, verify:

```bash
ls -l FILE
```

and inspect the source when appropriate:

```bash
less FILE
```

---

### Mistake: Assuming no output means command failure

A valid search can produce no output because nothing matched.

That differs from:

```text
file does not exist
permission denied
invalid operation
```

Read diagnostics.

---

### Mistake: Assuming every `grep -q ... || ...` means "not found"

`grep` may be unable to search the input.

Do not convert all search failures into absence claims.

---

### Mistake: Recursing from an enormous directory

Use the smallest reasonable search scope.

Prefer:

```bash
grep -r "timeout" ~/linux-world-labs/JUN-028/logs
```

over an uncontrolled filesystem-wide search.

---

### Mistake: Forgetting that matching output may contain sensitive information

Searching files containing:

```text
credentials
tokens
customer data
private keys
personal information
```

can expose those values in terminals, screenshots, logs, or copied evidence.

Know what you are searching.

---

### Mistake: Using unnecessary pipelines

This:

```bash
cat logs/api.log | grep "ERROR"
```

works.

But:

```bash
grep "ERROR" logs/api.log
```

is simpler when the source is already a file.

Use pipelines when they improve the data flow, not because every Linux command needs one.

---

### Troubleshooting model

When `grep` does not produce the result you expected:

```text
WHAT QUESTION AM I ASKING?
        ↓
WHAT INPUT AM I SEARCHING?
        ↓
DOES THAT INPUT EXIST?
        ↓
CAN I READ IT?
        ↓
WHAT EXACT PATTERN AM I USING?
        ↓
IS CASE IMPORTANT?
        ↓
PATTERN OR FIXED STRING?
        ↓
SUBSTRING OR WHOLE WORD?
        ↓
ONE FILE OR MULTIPLE FILES?
        ↓
DO I NEED CONTEXT?
        ↓
MATCH / NO MATCH / SEARCH ERROR?
        ↓
VERIFY AGAINST SOURCE DATA
```

Do not immediately make the pattern more complicated.

First determine which assumption is wrong.

## 13. Final Practical, Knowledge Check, and Cleanup

### Final Practical — Search Before You Diagnose

You are told:

> `customer-api` is configured incorrectly because the logs contain the word `timeout`.

Do not accept that conclusion automatically.

Investigate.

First confirm the service name:

```bash
grep -F "service_name=customer-api" service.conf
```

Then inspect timeout configuration:

```bash
grep -n "timeout" service.conf
```

Search runtime evidence:

```bash
grep -rn "timeout" logs
```

Inspect API timeout context:

```bash
grep -C 2 "database connection timeout" logs/api.log
```

Now answer:

```text
Does service.conf contain a timeout setting?

What is its configured value?

Which logs contain timeout evidence?

What runtime events surround the database timeout?

Does the existence of timeout_seconds=30 prove the configuration caused the incident?

Does the log line alone prove why the database connection timed out?

What additional evidence would you want before declaring root cause?
```

The expected engineering conclusion is not:

```text
grep found timeout
therefore configuration is wrong
```

The correct model is:

```text
grep found relevant evidence
        ↓
evidence narrows investigation
        ↓
cause still requires validation
```

### Knowledge Check

1. **What does `grep` do?**  
   It searches input for lines matching a pattern and, by default, prints matching lines.

2. **Is `grep` case-sensitive by default?**  
   Yes.

3. **What does `grep -i` do?**  
   It performs case-insensitive matching.

4. **What does `grep -n` do?**  
   It displays line numbers with matching lines.

5. **What does `grep -c` count?**  
   Matching lines.

6. **What does `grep -v` do?**  
   It selects lines that do not match the pattern.

7. **What does `grep -l` do?**  
   It lists filenames containing at least one match.

8. **What does `grep -w` do?**  
   It restricts matching to whole words according to `grep`'s word-boundary rules.

9. **What does `grep -F` do?**  
   It treats patterns as fixed strings instead of regular expressions.

10. **Why can `grep "1.2.3"` differ from `grep -F "1.2.3"`?**  
    In regular-expression matching, `.` has special meaning. `-F` searches for the literal dots.

11. **What does `grep -r` do?**  
    It searches recursively beneath directories.

12. **What do `-A`, `-B`, and `-C` provide?**  
    Lines after, before, or around a matching line.

13. **Can `grep` read from a pipeline?**  
    Yes. It can read text from stdin.

14. **Does no output always mean `grep` failed?**  
    No. A valid search may simply find no matching lines.

15. **Why is finding a matching log line not the same as proving root cause?**  
    The match is evidence. Root cause requires additional reasoning and supporting evidence.

### Interview Practice

**What is `grep` used for in Linux?**

`grep` searches text input for lines matching a pattern. It is commonly used with files, logs, configuration, command output, and pipelines.

**How do you search case-insensitively and include line numbers?**

For example:

```bash
grep -in "error" application.log
```

**What is the difference between `grep` and `grep -F`?**

Normal `grep` interprets its pattern as a basic regular expression. `grep -F` treats the pattern as a fixed string.

**How would you search an entire directory tree for a text value?**

For example:

```bash
grep -rn "timeout" logs
```

I would keep the search scope as narrow as practical.

**How do you see lines surrounding a match?**

I can use `-A` for lines after, `-B` for lines before, or `-C` for context on both sides.

**What is `grep -q` useful for?**

It performs a quiet match check without printing normal matching lines, which is useful when another shell operation only needs to know whether the search matched.

**Why is `grep -q PATTERN FILE || echo "not found"` potentially misleading?**

Because the `||` branch can also run when the search encounters an operational problem, such as an unreadable or missing file. "No match" and "search error" are not the same state.

**How would you troubleshoot a `grep` search that returns unexpected results?**

I would verify the input source, inspect the actual text, check capitalization, determine whether I need a fixed string or pattern, consider whole-word requirements, confirm the search scope, and distinguish no match from an actual search error.
