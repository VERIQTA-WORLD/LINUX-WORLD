## 1. Mission: Package Data and Prove You Can Recover It

Linux administrators regularly need to package data for:

- backups;
- migrations;
- deployments;
- log collection;
- configuration snapshots;
- troubleshooting evidence;
- file transfer;
- long-term storage.

Two different operations are involved:

```text
ARCHIVING
```

and:

```text
COMPRESSION
```

They are related, but they are not the same thing.

Suppose you have:

```text
application/
├── config/
├── logs/
└── reports/
```

An archive can combine those objects into one file:

```text
application/
   │
   ▼
tar
   │
   ▼
application.tar
```

Compression attempts to reduce the amount of storage used:

```text
application.tar
      │
      ▼
compression
      │
      ▼
application.tar.gz
```

The critical distinction is:

```text
archive
→ package multiple filesystem objects together
```

```text
compression
→ encode data to reduce its size
```

A compressed tar archive performs both jobs:

```text
FILES + DIRECTORIES
        │
        ▼
      tar
        │
        ▼
     archive
        │
        ▼
   compression
        │
        ▼
compressed archive
```

Your mission is to create a small application dataset, archive it, compress data using common Linux formats, inspect archives before extraction, restore the files into a separate location, and verify that recovery actually worked.

### By the end of this lab, you should be able to:

- explain the difference between archiving and compression;
- create a `.tar` archive;
- list archive contents without extracting them;
- extract an archive safely;
- understand the essential `tar` options `-c`, `-t`, `-x`, `-f`, and `-v`;
- compress and decompress individual files with `gzip`;
- work with `bzip2` and `xz`;
- create `.tar.gz`, `.tar.bz2`, and `.tar.xz` archives;
- inspect compressed tar archives;
- extract compressed archives into a controlled destination;
- compare file sizes;
- verify restored files rather than assuming extraction succeeded;
- recognize dangerous archive-extraction practices;
- choose an appropriate archive/compression workflow.

### Lab boundary

This lab does not cover:

- enterprise backup platforms;
- incremental backups;
- remote backup systems;
- encryption;
- retention policies;
- cloud object storage;
- automated backup scripts;
- disaster recovery architecture.

Those require additional concepts.

The focus here is the archive/compression foundation.

## 3. Create and Inspect a `tar` Archive

The traditional Linux archive tool you will use is:

```text
tar
```

Historically, the name comes from "tape archive," but `tar` remains widely used for packaging filesystem content today.

Create an archive:

```bash
tar -cf archives/application.tar source
```

Break the options down:

```text
-c
→ create an archive

-f
→ the next argument identifies the archive file
```

So:

```bash
tar -cf archives/application.tar source
```

means:

> Create `archives/application.tar` containing `source`.

Verify that the archive exists:

```bash
ls -lh archives/application.tar
```

The original directory should still exist:

```bash
ls -ld source
```

Creating the archive did not move or delete the source.

---

### Inspect before extracting

Do not immediately extract an unfamiliar archive.

First inspect it:

```bash
tar -tf archives/application.tar
```

Here:

```text
-t
→ list archive contents
```

and:

```text
-f
→ specify the archive file
```

You should see entries representing:

```text
source/
source/config/
source/config/app.conf
source/config/database.conf
source/logs/
...
```

This is an important operational habit:

```text
RECEIVE ARCHIVE
      ↓
INSPECT CONTENTS
      ↓
UNDERSTAND PATHS
      ↓
CHOOSE DESTINATION
      ↓
EXTRACT
      ↓
VERIFY
```

not:

```text
RECEIVE ARCHIVE
      ↓
EXTRACT IMMEDIATELY
```

---

### Verbose output

You can add:

```text
-v
```

for verbose reporting.

For example:

```bash
tar -tvf archives/application.tar
```

This provides more metadata about archived entries.

Use verbose output when it helps you inspect the archive.

Do not assume more output automatically means better verification.

## 4. Extract into a Controlled Destination

You already created:

```text
restore/
```

Do not extract over your original source data.

Extract into the dedicated restore location:

```bash
tar -xf archives/application.tar -C restore
```

Here:

```text
-x
→ extract
```

```text
-f
→ archive file
```

```text
-C restore
→ change to this destination before extraction
```

Inspect:

```bash
find restore -type f -print
```

Because the archive contains the top-level `source` directory, the restored files should appear beneath:

```text
restore/source/
```

Inspect a restored configuration:

```bash
cat restore/source/config/app.conf
```

Inspect a restored log:

```bash
cat restore/source/logs/api.log
```

Count restored files:

```bash
find restore/source -type f -print | wc -l
```

Compare this with the source count you recorded earlier.

### What extraction success actually means

A command completing without an obvious error is useful evidence.

It is not sufficient recovery verification.

You should verify:

```text
expected paths exist
+
expected file count
+
important content is readable
+
important content matches expectations
```

This is the beginning of an important engineering principle:

> A backup or archive is useful only if the required data can be recovered correctly.

## 5. Compress Individual Files

Now separate compression from archiving.

Copy one log so the source remains untouched:

```bash
cp source/logs/api.log api-compression-test.log
```

Inspect its size:

```bash
ls -lh api-compression-test.log
```

Compress it:

```bash
gzip api-compression-test.log
```

Inspect the directory:

```bash
ls -lh
```

You should now see:

```text
api-compression-test.log.gz
```

The original uncompressed test file is normally replaced by the compressed version.

That behavior matters.

The model is:

```text
file
 │
 ▼
gzip
 │
 ▼
file.gz
```

### Decompress it

Run:

```bash
gunzip api-compression-test.log.gz
```

Verify:

```bash
ls -lh api-compression-test.log
```

Inspect:

```bash
cat api-compression-test.log
```

You have now completed:

```text
uncompressed file
      ↓
gzip
      ↓
.gz file
      ↓
gunzip
      ↓
restored uncompressed file
```

---

### `bzip2`

Create another copy:

```bash
cp source/logs/api.log api-bzip-test.log
```

Compress:

```bash
bzip2 api-bzip-test.log
```

Inspect:

```bash
ls -lh api-bzip-test.log.bz2
```

Decompress:

```bash
bunzip2 api-bzip-test.log.bz2
```

Verify:

```bash
cat api-bzip-test.log
```

---

### `xz`

Create another copy:

```bash
cp source/logs/api.log api-xz-test.log
```

Compress:

```bash
xz api-xz-test.log
```

Inspect:

```bash
ls -lh api-xz-test.log.xz
```

Decompress:

```bash
unxz api-xz-test.log.xz
```

Verify:

```bash
cat api-xz-test.log
```

### Important observation

Do not make universal claims such as:

```text
xz is always smallest
```

or:

```text
gzip always saves space
```

Compression effectiveness depends on the data and compression settings.

Tiny files may even produce compressed files that are not smaller because compression formats require metadata and structural overhead.

Measure the actual result instead of assuming.

## 6. Create Compressed `tar` Archives

A `.tar` archive packages filesystem objects.

A compressed tar archive packages them **and** compresses the archive stream.

Three common combinations are:

```text
.tar.gz
.tar.bz2
.tar.xz
```

### gzip-compressed tar archive

Create:

```bash
tar -czf archives/application.tar.gz source
```

The additional option is:

```text
-z
→ use gzip compression
```

So:

```text
-czf
```

can be read as:

```text
create
gzip
archive-file follows
```

Inspect:

```bash
ls -lh archives/application.tar.gz
```

List its contents:

```bash
tar -tzf archives/application.tar.gz
```

---

### bzip2-compressed tar archive

Create:

```bash
tar -cjf archives/application.tar.bz2 source
```

Here:

```text
-j
→ use bzip2 compression
```

Inspect:

```bash
ls -lh archives/application.tar.bz2
```

List:

```bash
tar -tjf archives/application.tar.bz2
```

---

### xz-compressed tar archive

Create:

```bash
tar -cJf archives/application.tar.xz source
```

Notice:

```text
-J
```

is uppercase.

It means:

```text
use xz compression
```

Inspect:

```bash
ls -lh archives/application.tar.xz
```

List:

```bash
tar -tJf archives/application.tar.xz
```

### Core mapping

Keep this distinction clear:

```text
-z
→ gzip
→ .tar.gz
```

```text
-j
→ bzip2
→ .tar.bz2
```

```text
-J
→ xz
→ .tar.xz
```

Do not memorize only filenames.

Understand which compression method the option requests.

## 7. Compare Archives Without Guessing

Inspect all generated archives:

```bash
ls -lh archives
```

You should have:

```text
application.tar
application.tar.gz
application.tar.bz2
application.tar.xz
```

Now compare sizes more precisely:

```bash
ls -l archives
```

Ask:

```text
Which archive is largest?

Which compressed archive is smallest for this dataset?

How much difference exists?

Is the difference operationally meaningful for such a small dataset?
```

The point is not to declare a universal winner.

The point is to measure.

Compression choices can involve tradeoffs among:

```text
compressed size
CPU usage
compression speed
decompression speed
compatibility
tool availability
workflow requirements
```

At junior level, your responsibility is to recognize that:

```text
smallest file
≠
automatically best operational choice
```

A widely supported format that is slightly larger may be more appropriate for one workflow, while stronger compression may matter more in another.

The requirement determines the choice.

## 8. Restore a Compressed Archive and Verify Recovery

Create a separate destination:

```bash
mkdir -p restore-gzip
```

Before extracting, inspect:

```bash
tar -tzf archives/application.tar.gz
```

Now extract:

```bash
tar -xzf archives/application.tar.gz -C restore-gzip
```

Inspect:

```bash
find restore-gzip -type f -print
```

Count restored files:

```bash
find restore-gzip/source -type f -print | wc -l
```

Inspect important content:

```bash
cat restore-gzip/source/config/app.conf
```

```bash
cat restore-gzip/source/logs/api.log
```

Now compare an original file with its restored copy:

```bash
cmp source/config/app.conf restore-gzip/source/config/app.conf
```

If the files are identical, `cmp` normally produces no output.

Check another:

```bash
cmp source/logs/api.log restore-gzip/source/logs/api.log
```

### Why `cmp` matters

Checking that:

```text
app.conf exists
```

does not prove:

```text
app.conf contains the same data
```

A stronger recovery verification is:

```text
archive exists
       ↓
archive contents inspect correctly
       ↓
extraction completes
       ↓
expected files exist
       ↓
expected count is present
       ↓
critical restored content matches source
```

That is much stronger evidence than:

> `tar` returned me to the prompt.

## 9. Safe Archive Handling and Controlled Failures

Archive work can modify many filesystem paths in one operation.

That means inspection and destination control matter.

### Mistake 1 — Confusing archive with compression

This:

```bash
tar -cf archives/application.tar source
```

creates an archive.

It does not request gzip, bzip2, or xz compression.

This:

```bash
tar -czf archives/application.tar.gz source
```

creates a gzip-compressed tar archive.

Keep the concepts separate.

---

### Mistake 2 — Extracting before inspecting

Avoid immediately running an extraction command against an unfamiliar archive.

First:

```bash
tar -tf archives/application.tar
```

or for gzip:

```bash
tar -tzf archives/application.tar.gz
```

Inspect the paths.

Then choose a controlled destination.

---

### Mistake 3 — Extracting over important files

You have:

```text
source/
```

and:

```text
restore/
```

for a reason.

A safer training pattern is:

```bash
tar -xf archive.tar -C restore
```

rather than extracting blindly into a working directory containing important data.

---

### Mistake 4 — Using the wrong compression option

These are different:

```text
-z → gzip
-j → bzip2
-J → xz
```

If the format and option do not agree, the command may fail or behave differently from what you intended.

Inspect the filename and understand the actual format.

---

### Mistake 5 — Assuming compression always makes files smaller

Check:

```bash
ls -lh FILE*
```

Small files can gain overhead.

Some data compresses extremely well.

Other data may already be compressed or contain patterns that offer little additional reduction.

Measure.

---

### Mistake 6 — Assuming archive creation proves recoverability

This:

```bash
ls -lh archives/application.tar.gz
```

proves that an object with that pathname exists.

It does not prove:

- the archive contains everything required;
- the archive can be read;
- extraction succeeds;
- the restored content is correct.

Inspect and test recovery.

---

### Mistake 7 — Ignoring paths stored inside an archive

Before extraction, examine:

```bash
tar -tf ARCHIVE
```

Ask:

```text
Where will these paths be placed?

Is there a top-level directory?

Could they collide with existing paths?

Am I extracting into the intended location?
```

Archive contents are not merely filenames to glance at.

They describe filesystem changes extraction may create.

---

### Mistake 8 — Treating compression as encryption

A file such as:

```text
application.tar.gz
```

is compressed.

That does **not** mean its contents are confidential.

Compression and encryption solve different problems.

Do not store sensitive information under the assumption that a compressed extension protects it from reading.

---

### Troubleshooting model

When archive or compression work behaves unexpectedly:

```text
WHAT FORMAT AM I WORKING WITH?
          ↓
ARCHIVE, COMPRESSED FILE, OR BOTH?
          ↓
DOES THE SOURCE EXIST?
          ↓
WHICH TOOL / OPTION MATCHES THE FORMAT?
          ↓
CAN I LIST THE ARCHIVE?
          ↓
WHAT PATHS DOES IT CONTAIN?
          ↓
WHERE AM I EXTRACTING?
          ↓
DID EXPECTED FILES APPEAR?
          ↓
DOES IMPORTANT CONTENT MATCH?
```

Do not respond to every archive problem by repeatedly adding options until a command works.

Understand the format first.

## 11. Knowledge Check and Interview Practice

### Knowledge Check

1. **What is the difference between archiving and compression?**  
   Archiving packages filesystem objects together. Compression attempts to reduce the amount of storage needed to represent data.

2. **What does `tar -cf archive.tar directory` do?**  
   It creates an uncompressed tar archive containing the specified directory.

3. **What does `-c` mean in `tar`?**  
   Create an archive.

4. **What does `-t` mean?**  
   List archive contents.

5. **What does `-x` mean?**  
   Extract archive contents.

6. **What does `-f` mean?**  
   Use the following argument as the archive filename.

7. **What does `-v` do?**  
   Enables verbose reporting.

8. **What does `-C` do during extraction?**  
   Changes to the specified directory before performing the extraction operation, allowing you to control the destination.

9. **What compression method does `tar -z` use?**  
   gzip.

10. **What compression method does `tar -j` use?**  
    bzip2.

11. **What compression method does `tar -J` use?**  
    xz.

12. **Why should you inspect an archive before extracting it?**  
    To understand the paths and contents it will create and reduce the risk of extracting unexpected data into an inappropriate location.

13. **Why is successful archive creation not enough to prove recoverability?**  
    The archive may be incomplete, unreadable, incorrectly structured, or fail to restore the expected content. Recovery should be tested.

14. **Does compression protect sensitive data from unauthorized reading?**  
    No. Compression is not encryption.

15. **Why should restored files be compared with known source data?**  
    File existence alone does not prove the restored content is correct.

### Interview Practice

**What is the difference between `.tar` and `.tar.gz`?**

A `.tar` file is a tar archive. A `.tar.gz` file is a tar archive whose data has been compressed with gzip.

**How would you create a gzip-compressed archive of a directory?**

```bash
tar -czf application.tar.gz application/
```

**How would you inspect a gzip-compressed tar archive without extracting it?**

```bash
tar -tzf application.tar.gz
```

**How would you extract an archive into a specific directory?**

For example:

```bash
tar -xf application.tar -C restore/
```

assuming the destination exists.

**Why would you inspect an archive before extracting it?**

Because extraction creates filesystem paths. I want to understand the archive structure, destination, and potential path collisions before making those changes.

**What is the difference between `gzip file` and `tar -czf archive.tar.gz directory`?**

`gzip file` compresses an individual file stream and normally replaces the source file with its `.gz` form. `tar -czf` first packages filesystem objects into a tar archive stream and applies gzip compression to that archive.

**How would you verify that a restored file matches the original?**

For a direct byte comparison, I can use:

```bash
cmp original restored
```

No output normally indicates identical content.

**Does the smallest compressed archive automatically represent the best format?**

No. Format choice can also depend on compatibility, CPU cost, compression and decompression speed, operational requirements, and tool availability.
