## 1. Your Engineering Mission

A Linux server has an active network interface, a valid IP address, and an appropriate route to an external network.

An engineer tries to access an application using its domain name:

```text
app.example.com
```

The connection fails.

Does that automatically mean the server has a routing problem?

No.

Before an application can communicate with a service identified by a hostname, the hostname normally needs to be resolved into an address.

That introduces another important networking component: **DNS — the Domain Name System**.

Consider this simplified process:

```text
APPLICATION
     |
     | Requests app.example.com
     v
NAME RESOLUTION
     |
     | Returns an IP address
     v
IP ROUTING
     |
     | Selects the network path
     v
DESTINATION
```

DNS and routing work together, but they perform different jobs.

Your mission is to investigate how Linux resolves names, recognize common DNS record types, inspect the host's resolver configuration, and distinguish hostname resolution from IP connectivity.

You will not modify DNS configuration.

### Learning objectives

By completing this lab, you will be able to:

- Explain what DNS does.
- Distinguish a domain name, hostname, and fully qualified domain name.
- Describe the basic DNS resolution process.
- Identify common DNS record types.
- Understand recursive and authoritative DNS roles.
- Recognize DNS caching and TTL.
- Explain the purpose of `/etc/hosts`.
- Understand the role of `/etc/nsswitch.conf`.
- Inspect `/etc/resolv.conf`.
- Identify configured DNS servers using available Linux tools.
- Resolve hostnames with `getent`.
- Distinguish IPv4 and IPv6 resolution results.
- Explain why successful DNS resolution does not prove application connectivity.
- Recognize common DNS misconceptions.

**Learning boundary:** This lab introduces DNS concepts and safe inspection. Detailed DNS failure investigation, record-specific querying, resolver configuration changes, and systematic DNS troubleshooting belong to JUN-050.

## 2. Understand What DNS Actually Does

Computers communicate over IP networks using addresses.

Humans generally find names easier to remember.

For example:

```text
example.com
```

is easier to recognize than repeatedly remembering an IP address.

DNS provides a distributed naming system that allows applications to obtain information associated with domain names, including IP addresses.

At a simplified level:

```text
HUMAN-READABLE NAME
        |
        v
       DNS
        |
        v
     IP ADDRESS
```

However, DNS is more than a simple name-to-address directory.

It also supports information such as:

- Mail-routing destinations.
- Name aliases.
- Authoritative name servers.
- Service-related records.
- Domain verification information.

### Domain name vs hostname

A **domain name** is a name within the DNS hierarchy.

Examples:

```text
example.com
```

```text
veriqta.com
```

A **hostname** identifies a host or service in a naming context.

For example:

```text
academy.example.com
```

A **fully qualified domain name (FQDN)** specifies a complete name within the DNS hierarchy.

A fully explicit DNS representation can end with a dot:

```text
academy.example.com.
```

The final dot represents the DNS root.

In everyday administration, the trailing dot is commonly omitted.

### DNS is not routing

Keep these concepts separate:

| Component | Primary responsibility |
|---|---|
| DNS | Resolves names and retrieves DNS information |
| IP addressing | Identifies network endpoints |
| Routing | Determines how packets are forwarded |
| Default gateway | Provides a next hop for applicable routes |
| Application | Uses the resolved destination to communicate |

A hostname can resolve successfully while the destination remains unreachable.

Similarly, a host may have working IP connectivity while name resolution fails.

## 3. Understand the DNS Resolution Process

When an application requests an address for:

```text
www.example.com
```

the operating system uses its configured name-resolution mechanisms.

A simplified DNS lookup can involve:

```text
APPLICATION
     |
     v
SYSTEM NAME-RESOLUTION API
     |
     v
LOCAL RESOLUTION CONFIGURATION
     |
     v
RECURSIVE DNS RESOLVER
     |
     +-------------------------+
     |                         |
     v                         v
CACHED ANSWER?           NO CACHED ANSWER
     |                         |
     v                         v
RETURN ANSWER          DNS HIERARCHY
                               |
                               v
                         ROOT SERVERS
                               |
                               v
                         TLD SERVERS
                               |
                               v
                    AUTHORITATIVE SERVER
                               |
                               v
                         DNS RESPONSE
                               |
                               v
                       RECURSIVE RESOLVER
                               |
                               v
                          APPLICATION
```

This diagram represents a conceptual recursive lookup, not a guarantee that every request contacts every server.

Caching, local files, resolver configuration, and other mechanisms can shorten or change the process.

### Recursive resolver

A recursive resolver performs resolution work on behalf of a client.

It may answer using cached information or obtain information from other DNS servers.

### Root servers

Root servers provide information used to locate the appropriate top-level domain infrastructure.

### TLD servers

TLD means **Top-Level Domain**.

Examples include:

```text
.com
.org
.net
```

A TLD server can direct the resolver toward authoritative information for the requested domain.

### Authoritative DNS server

An authoritative server provides DNS information for the zones it serves.

For example, the authoritative DNS infrastructure for a domain may contain records describing its web, mail, and other services.

### Engineer Note

Do not assume that an authoritative DNS server and a recursive resolver are the same thing.

They perform different roles, even though DNS software can support different configurations.

## 4. Recognize Common DNS Record Types

DNS stores different types of records.

Each record type has a defined purpose.

The following are important for a junior Linux engineer.

| Record | Purpose | Example |
|---|---|---|
| `A` | Maps a name to an IPv4 address | `192.0.2.10` |
| `AAAA` | Maps a name to an IPv6 address | `2001:db8::10` |
| `CNAME` | Defines a canonical-name alias | `www.example.com` → `web.example.com` |
| `MX` | Identifies mail exchangers for a domain | `mail.example.com` |
| `NS` | Identifies authoritative name servers | `ns1.example.com` |
| `TXT` | Holds text information used for various purposes | Domain-verification or email-policy data |
| `PTR` | Supports reverse DNS mapping | Address → domain name |
| `SOA` | Contains zone-authority and administrative information | Zone metadata |

The values above are illustrative, not live DNS query results.

### A records

An A record associates a DNS name with an IPv4 address.

Conceptually:

```text
app.example.com
       |
       v
   A RECORD
       |
       v
 192.0.2.10
```

### AAAA records

An AAAA record associates a name with an IPv6 address.

```text
app.example.com
       |
       v
  AAAA RECORD
       |
       v
 2001:db8::10
```

### CNAME records

A CNAME record establishes an alias to another DNS name.

It does not directly contain an IP address.

Conceptually:

```text
www.example.com
       |
       v
web.example.com
       |
       v
ADDRESS RESOLUTION
```

### MX records

MX records identify mail exchangers associated with a domain.

They are not ordinary web-server address records.

### PTR records

PTR records are commonly associated with reverse DNS.

Forward and reverse resolution are different operations.

Do not assume that a working forward DNS record guarantees a corresponding reverse DNS record.

### Checkpoint

Before proceeding, make sure you can explain the difference between:

```text
A
AAAA
CNAME
MX
```

You do not need to memorize every DNS record type yet.

## 5. Understand DNS Caching and TTL

DNS answers are not necessarily retrieved from authoritative servers every time an application requests a name.

Resolvers may cache answers.

Caching reduces repeated lookup work and can improve resolution performance.

### What is TTL?

TTL means **Time to Live**.

A DNS record's TTL specifies how long its information may be cached under normal DNS caching behavior.

For example, consider a hypothetical A record:

```text
app.example.com
A
192.0.2.10
TTL: 300
```

A TTL of 300 represents 300 seconds.

That is five minutes.

### Why TTL matters

Suppose a domain's address changes:

```text
OLD:
192.0.2.10

NEW:
192.0.2.20
```

A resolver with a valid cached answer may continue returning the previous address until the relevant cache lifetime expires.

Different resolvers and applications may also implement caching behavior differently.

### Important distinction

TTL does not guarantee that every user worldwide will observe a change at exactly the same second.

DNS updates involve several components, including authoritative data, recursive resolvers, caches, and client behavior.

For now, remember:

**A DNS answer can be correct according to a resolver's current cache while differing from a recently updated authoritative record.**

You will investigate this distinction further in JUN-050.

## 6. Inspect Linux Name-Resolution Configuration

Linux name resolution is not controlled by one universal file in every environment.

Ubuntu Server 24.04 LTS commonly uses `systemd-resolved`, but actual configuration depends on the installation and network-management setup.

Start with the files and tools available on your machine.

### Inspect `/etc/hosts`

Run:

```bash
cat /etc/hosts
```

You may encounter entries resembling:

```text
127.0.0.1 localhost
127.0.1.1 server01
```

Your file may differ.

`/etc/hosts` provides local name-to-address mappings.

It can allow a name to resolve without querying external DNS infrastructure.

For example, an administrator could define a local mapping for an internal test name.

You will not edit this file in this lab.

### Inspect `/etc/nsswitch.conf`

Run:

```bash
cat /etc/nsswitch.conf
```

Locate the line beginning with:

```text
hosts:
```

It may contain entries such as:

```text
files
dns
resolve
```

along with other mechanisms or action rules.

The Name Service Switch configuration helps determine which sources Linux consults for different name-service databases.

The exact `hosts:` line varies by installation.

**Important:** Do not assume `/etc/hosts` always has the same precedence on every Linux system. Inspect the actual configuration.

### Inspect `/etc/resolv.conf`

Run:

```bash
cat /etc/resolv.conf
```

You may see an entry such as:

```text
nameserver 127.0.0.53
```

On a typical systemd-resolved stub configuration, this is a local resolver address.

It does not mean that `127.0.0.53` is necessarily the upstream DNS server on the external network.

### Inspect the file relationship

Run:

```bash
ls -l /etc/resolv.conf
```

On some Ubuntu installations, `/etc/resolv.conf` is a symbolic link to a file managed by `systemd-resolved`.

This matters because editing a generated or managed resolver file directly may not be the correct persistent configuration method.

Do not edit it during this lab.

### Checkpoint

Record:

| Configuration item | Your findings |
|---|---|
| `/etc/hosts` exists? | |
| `hosts:` lookup configuration | |
| `/etc/resolv.conf` nameserver entries | |
| Is `/etc/resolv.conf` a symbolic link? | |
| Local resolver/stub address observed? | |

## 7. Inspect DNS Configuration with `resolvectl`

On systems using `systemd-resolved`, the `resolvectl` command provides information about resolver configuration.

First, check whether it is available:

```bash
command -v resolvectl
```

If available, run:

```bash
resolvectl status
```

Inspect the output.

Depending on your environment, you may see information about:

- DNS servers.
- DNS domains.
- Per-interface resolver configuration.
- Current DNS server selection.
- Resolver protocols.
- DNS-related settings.

### Focus on the DNS server information

Look for fields such as:

```text
DNS Servers:
```

and:

```text
Current DNS Server:
```

The exact output depends on the host.

A system can have different DNS configuration associated with different interfaces.

For example, a VPN or enterprise network may introduce additional DNS settings.

Do not assume every interface must use the same DNS server.

### What if `resolvectl` is unavailable?

Do not install or reconfigure anything just to make the lab output resemble an example.

Use the information available from:

```bash
cat /etc/resolv.conf
```

and document that `resolvectl` was unavailable or that the host does not appear to use the expected resolver setup.

### Engineer Note

A DNS server address shown in resolver configuration identifies a server the system may use for name resolution.

It is not automatically:

- the default gateway;
- the final application destination;
- the authoritative DNS server for every requested domain.

## 8. Resolve Hostnames with `getent`

Now perform a practical name-resolution lookup.

The `getent` command queries databases through the system's configured Name Service Switch mechanisms.

This makes it useful for observing how ordinary Linux name resolution behaves.

### Resolve a local name

Run:

```bash
getent hosts localhost
```

Inspect the returned address and name.

Depending on configuration, you may see an IPv4 or IPv6 result.

### Resolve an external domain

Run:

```bash
getent hosts example.com
```

The command attempts to resolve the name using the configured system mechanisms.

The exact returned address can vary.

If the lookup fails, record the failure. Do not change DNS configuration yet.

### Inspect IPv4 results

Run:

```bash
getent ahostsv4 example.com
```

This requests IPv4 address information through the system address-resolution interface.

### Inspect IPv6 results

Run:

```bash
getent ahostsv6 example.com
```

An IPv6 lookup may return no result depending on the name, resolver configuration, and local environment.

That does not automatically establish that all DNS is broken.

### Understand the distinction

Compare:

```bash
getent hosts example.com
```

with:

```bash
getent ahostsv4 example.com
```

and:

```bash
getent ahostsv6 example.com
```

These commands help you observe address-resolution behavior, but they are not complete tools for inspecting every DNS record type or querying a particular authoritative DNS server.

Record your findings:

| Lookup | Result |
|---|---|
| `localhost` | |
| `example.com` | |
| IPv4 resolution | |
| IPv6 resolution | |

## 9. Distinguish DNS Resolution from Network Connectivity

Consider the following situation.

An engineer runs:

```bash
getent ahostsv4 example.com
```

The command returns an IPv4 address.

The engineer concludes:

> The application must be reachable.

That conclusion is not supported.

Successful name resolution establishes that the system obtained an address for the requested name.

It does not establish that an application can communicate successfully with that address.

### Compare the layers

```text
HOSTNAME
   |
   v
NAME RESOLUTION
   |
   v
IP ADDRESS OBTAINED
   |
   v
ROUTING DECISION
   |
   v
NETWORK DELIVERY
   |
   v
TRANSPORT CONNECTION
   |
   v
APPLICATION RESPONSE
```

Each stage can fail independently.

### Connect DNS to JUN-048

Suppose a lookup returns an IPv4 address.

You can investigate how Linux would route traffic toward that address using:

```bash
ip route get DESTINATION_IP
```

Replace `DESTINATION_IP` with the actual address returned by your lookup.

This allows you to compare two separate questions:

**Question 1:** Can the system resolve the hostname?

**Question 2:** Can Linux identify a route toward the resolved address?

Neither command alone proves the remote application works.

### Common interpretation mistakes

| Observation | What it establishes | What it does not establish |
|---|---|---|
| Hostname resolves | Address information was obtained | Application availability |
| Route lookup succeeds | Linux found a route | Successful packet delivery |
| `/etc/resolv.conf` contains a nameserver | Resolver information is configured | DNS server is reachable |
| `localhost` resolves | Local name resolution works | External DNS works |
| IPv4 lookup succeeds | IPv4 address resolution succeeded | IPv6 resolution works |

This separation is fundamental to reliable networking investigations.

### Knowledge Check

12. What is the purpose of `/etc/resolv.conf`?
13. Why might `127.0.0.53` appear as a nameserver?
14. Does successful DNS resolution prove application connectivity?
15. Why is `getent` useful when investigating Linux name resolution?

### Answer guidance

The important principles are:

- DNS is a distributed naming system.
- Recursive resolvers perform resolution on behalf of clients.
- Authoritative servers provide DNS information for the zones they serve.
- A records contain IPv4 addresses; AAAA records contain IPv6 addresses.
- CNAME records represent canonical-name aliases.
- MX records identify mail exchangers.
- TTL influences how long DNS information may be cached.
- `/etc/hosts` provides local name mappings.
- NSS configuration influences the sources used for name resolution.
- `/etc/resolv.conf` exposes resolver-related configuration.
- `127.0.0.53` is commonly used as a local `systemd-resolved` stub address.
- `getent` exercises configured system name-resolution mechanisms.
- Successful name resolution does not prove routing, transport, or application health.

### Interview Practice

**1. What is DNS, and why is it important?**

DNS is the Domain Name System. It allows applications and users to retrieve information associated with domain names, including IP addresses, so services can be identified using human-readable names.

**2. What is the difference between an A and an AAAA record?**

An A record contains an IPv4 address. An AAAA record contains an IPv6 address.

**3. What is the difference between a recursive resolver and an authoritative DNS server?**

A recursive resolver performs resolution on behalf of a client, potentially using cached answers or consulting other DNS servers. An authoritative server provides DNS information for the zones it serves.

**4. What is DNS TTL?**

TTL means Time to Live. It specifies how long DNS information may be cached under normal DNS caching behavior.

**5. What is the purpose of `/etc/hosts`?**

It provides local name-to-address mappings that can participate in the operating system's name-resolution process.

**6. Why might `/etc/resolv.conf` show `127.0.0.53` instead of an external DNS server?**

On a system using the standard `systemd-resolved` stub configuration, applications may send DNS queries to the local stub resolver, which then uses the configured resolution infrastructure.

**7. How would you check whether Linux can resolve a hostname using its configured name-resolution mechanisms?**

I could use:

```bash
getent hosts example.com
```

For IPv4-specific address results:

```bash
getent ahostsv4 example.com
```

**8. A hostname resolves, but the application still fails. Is DNS necessarily the problem?**

No. Successful resolution establishes that address information was obtained. Routing, network delivery, firewall behavior, transport connectivity, and application health still need to be considered.
