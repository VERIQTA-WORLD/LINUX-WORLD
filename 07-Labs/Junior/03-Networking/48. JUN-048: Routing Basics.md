## 1. Mission: Understand How Linux Decides Where Packets Go

In JUN-047, you learned how an IPv4 address and prefix define a subnet.

You also learned that traffic for a destination outside the local subnet normally needs routing.

Now you will examine the mechanism Linux uses to make that decision.

Suppose a Linux host has:

```text
Address:
10.20.30.15/24

Default gateway:
10.20.30.1
```

The host needs to communicate with:

```text
10.20.30.50
```

and:

```text
203.0.113.50
```

Those destinations are not handled identically.

The first destination belongs to the directly connected network:

```text
10.20.30.0/24
```

The second does not.

Linux therefore needs a routing decision.

The simplified decision looks like this:

```text
PACKET DESTINATION
       |
       v
CHECK ROUTING TABLE
       |
       v
FIND MATCHING ROUTES
       |
       v
SELECT MOST SPECIFIC MATCH
       |
       v
DETERMINE:
- interface
- next hop, if required
- source address
       |
       v
SEND PACKET
```

Your mission is to inspect the routing table of a real Linux system and explain why Linux would select one route instead of another.

You will not modify routes.

### Learning objectives

By the end of this lab, you should be able to:

- explain what a routing table is;
- explain what a route represents;
- inspect IPv4 routes with `ip route`;
- recognize directly connected routes;
- recognize a default route;
- identify a next-hop gateway;
- identify the interface associated with a route;
- understand destination prefixes;
- explain longest-prefix matching;
- understand why a more-specific route beats a less-specific route;
- explain when the default route is used;
- distinguish a connected route from a route through a gateway;
- use `ip route get` to ask Linux how it would route a destination;
- interpret common route fields such as `via`, `dev`, `src`, and `proto`;
- understand that a host may have multiple routes and multiple gateways;
- avoid assuming that every remote destination uses the default gateway;
- gather routing evidence before troubleshooting higher network layers.

### Safety boundary

This lab is intentionally read-only.

Do not run:

```text
ip route add ...
ip route del ...
ip route replace ...
ip route flush ...
```

Do not change:

- default routes;
- static routes;
- interface addresses;
- prefix lengths;
- gateways;
- Netplan;
- NetworkManager configuration;
- interface state.

On a remotely administered server, an incorrect routing change can immediately make the server unreachable.

Use this workflow:

```text
OBSERVE
   |
   v
INTERPRET
   |
   v
QUERY
   |
   v
COMPARE
   |
   v
EXPLAIN
```

Do not change routing configuration in this lab.

## 2. Start With the Routing Table

Run:

```bash
ip route
```

You may see output conceptually similar to:

```text
default via 10.20.30.1 dev ens3

10.20.30.0/24 dev ens3 proto kernel scope link src 10.20.30.15
```

Your actual routes will differ.

A routing table answers a fundamental question:

```text
If Linux needs to send a packet
to destination X,
where should it send it?
```

A route can describe:

- a destination network;
- a destination host;
- a next-hop gateway;
- an outgoing interface;
- a preferred source address;
- routing metadata.

Think of the routing table as a set of forwarding instructions.

```text
DESTINATION
     |
     v
ROUTING TABLE
     |
     +---- matching route A
     |
     +---- matching route B
     |
     +---- default route
     |
     v
BEST ROUTE
```

### Inspect IPv4 routes explicitly

Run:

```bash
ip -4 route
```

This restricts the output to IPv4.

The shorter command:

```bash
ip route
```

normally displays the IPv4 routing table by default.

### Checkpoint

Record the routes exactly as your host reports them.

```text
ROUTING INVENTORY

Connected route(s):

Default route:

Other route(s):
```

Do not assume your system has only two routes.

A production host can have many.

## 3. Read a Connected Route

Consider:

```text
10.20.30.0/24 dev ens3 proto kernel scope link src 10.20.30.15
```

Break it apart.

### Destination prefix

```text
10.20.30.0/24
```

This identifies the destination network covered by the route.

You learned this subnet concept in JUN-047.

The route applies to destinations inside:

```text
10.20.30.0/24
```

### `dev`

```text
dev ens3
```

means the route uses interface:

```text
ens3
```

Your interface may have a different name.

### `proto kernel`

```text
proto kernel
```

indicates that this route was installed by the kernel.

A common reason is that an address and prefix were configured on an interface.

For example:

```text
ens3
10.20.30.15/24
```

can cause Linux to have a connected route for:

```text
10.20.30.0/24
```

### `scope link`

```text
scope link
```

indicates that the route's destination is reachable on the local link.

### `src`

```text
src 10.20.30.15
```

provides a preferred source-address hint for traffic using this route.

### Put the route together

```text
10.20.30.0/24
       |
       v
DIRECTLY CONNECTED NETWORK
       |
       v
ens3
       |
       v
preferred source:
10.20.30.15
```

Notice what is absent:

```text
via
```

A directly connected route commonly does not need a next-hop router for destinations on that connected network.

## 4. Read the Default Route

Now consider:

```text
default via 10.20.30.1 dev ens3
```

Break it apart.

### `default`

```text
default
```

represents the default destination route.

For IPv4, it corresponds conceptually to:

```text
0.0.0.0/0
```

A `/0` route has no fixed leading destination bits.

That allows it to match any IPv4 destination.

But matching every destination does **not** mean it wins against every other route.

You will see why shortly.

### `via`

```text
via 10.20.30.1
```

identifies a next-hop gateway.

Linux sends the packet toward that router rather than treating the final remote destination as directly attached to the local link.

### `dev`

```text
dev ens3
```

identifies the interface Linux uses to reach that next hop.

The conceptual path is:

```text
LINUX HOST
10.20.30.15
     |
     v
ens3
     |
     v
10.20.30.1
DEFAULT GATEWAY
     |
     v
OTHER NETWORKS
```

### Important distinction

The default gateway is not necessarily the final destination.

If the application needs:

```text
203.0.113.50
```

Linux may send the packet first to:

```text
10.20.30.1
```

The packet's destination is still the remote destination.

The gateway is the next hop.

Keep this distinction:

```text
FINAL DESTINATION
203.0.113.50

NEXT HOP
10.20.30.1
```

They serve different roles.

## 5. Understand Route Matching

Suppose the routing table contains:

```text
default via 10.20.30.1 dev ens3

10.20.30.0/24 dev ens3
```

Linux needs to send traffic to:

```text
10.20.30.50
```

Which routes match?

The connected route:

```text
10.20.30.0/24
```

matches.

The default route:

```text
0.0.0.0/0
```

also matches because `/0` can match any IPv4 destination.

Linux does not simply choose the first matching route.

It prefers the most specific matching prefix.

This principle is called:

```text
LONGEST-PREFIX MATCH
```

Compare:

```text
10.20.30.0/24
```

with:

```text
0.0.0.0/0
```

The `/24` is more specific than `/0`.

Therefore:

```text
10.20.30.50
       |
       v
10.20.30.0/24
```

wins over the default route.

### Why "longest" means more specific

A larger prefix length fixes more leading destination bits.

Compare:

```text
/0
/8
/16
/24
/32
```

As the prefix length increases, the route generally describes a narrower destination range.

For example:

```text
10.0.0.0/8
```

covers a large range.

```text
10.20.0.0/16
```

is narrower.

```text
10.20.30.0/24
```

is narrower still.

```text
10.20.30.50/32
```

identifies one IPv4 address.

If all four matched the destination:

```text
10.20.30.50
```

the `/32` would be the most specific prefix.

Conceptually:

```text
0.0.0.0/0
     |
     v
10.0.0.0/8
     |
     v
10.20.0.0/16
     |
     v
10.20.30.0/24
     |
     v
10.20.30.50/32

increasing specificity
```

## 6. Ask Linux Which Route It Would Use

Reading the entire routing table is useful.

Linux can also answer a more focused question:

```text
How would you route this destination?
```

Use:

```bash
ip route get DESTINATION
```

For example:

```bash
ip route get 127.0.0.1
```

Because `127.0.0.1` is local to the host, Linux should report a local routing decision.

Now choose an IPv4 address from your connected subnet, if you know one that is appropriate for inspection.

You can also safely query a documentation address without sending traffic:

```bash
ip route get 203.0.113.10
```

`ip route get` performs a route lookup.

It does not perform a connectivity test to that destination.

This distinction is important.

```text
ip route get
=
ROUTING DECISION QUERY
```

It is not:

```text
ping
```

and it is not:

```text
curl
```

### Typical route-query fields

Depending on the destination and host, output may contain:

```text
via
dev
src
```

For example, conceptually:

```text
203.0.113.10 via 10.20.30.1 dev ens3 src 10.20.30.15
```

Interpret it as:

```text
DESTINATION:
203.0.113.10

NEXT HOP:
10.20.30.1

OUTGOING INTERFACE:
ens3

SELECTED SOURCE:
10.20.30.15
```

### Important

The output proves a routing decision.

It does **not** prove:

- the gateway responds;
- the destination exists;
- the Internet works;
- DNS works;
- a remote port is open;
- an application is healthy.

Route selection and connectivity are different questions.

## 7. Compare Local and Remote Route Decisions

First inspect your addresses:

```bash
ip -4 addr
```

Then inspect routes:

```bash
ip route
```

Identify:

- one non-loopback interface;
- its IPv4 address;
- its connected network;
- its default gateway, if one exists.

Suppose your host resembles:

```text
Interface:
ens3

Address:
10.20.30.15/24

Connected network:
10.20.30.0/24

Gateway:
10.20.30.1
```

A destination such as:

```text
10.20.30.50
```

belongs to the connected network.

Linux can select:

```text
10.20.30.0/24 dev ens3
```

A destination such as:

```text
203.0.113.50
```

does not belong to that network.

If no more-specific route exists, Linux may select:

```text
default via 10.20.30.1 dev ens3
```

The difference is:

```text
LOCAL NETWORK DESTINATION
       |
       v
CONNECTED ROUTE
```

versus:

```text
REMOTE DESTINATION
       |
       v
NO MORE-SPECIFIC ROUTE
       |
       v
DEFAULT ROUTE
       |
       v
NEXT-HOP GATEWAY
```

### Checkpoint

Using your own system, record:

```text
Selected interface:

Interface IPv4 address:

Connected network:

Default gateway:

Default-route interface:
```

Then query a remote documentation address:

```bash
ip route get 203.0.113.10
```

Record:

```text
Destination:

Selected interface:

Next hop, if shown:

Selected source address:
```

Use only what Linux actually reports.

## 8. Understand More-Specific Routes

The default route is important, but it is only a fallback.

Suppose a routing table conceptually contains:

```text
default via 10.20.30.1 dev ens3

10.20.30.0/24 dev ens3

172.16.0.0/16 via 10.20.30.254 dev ens3
```

Now Linux needs to send traffic to:

```text
172.16.50.20
```

The default route matches.

But so does:

```text
172.16.0.0/16
```

Compare:

```text
/16
```

with:

```text
/0
```

The `/16` is more specific.

Linux therefore prefers:

```text
172.16.0.0/16 via 10.20.30.254
```

not the default route.

Conceptually:

```text
172.16.50.20
      |
      +--------------------+
      |                    |
      v                    v
172.16.0.0/16          0.0.0.0/0
MATCH                  MATCH
      |                    |
      +---------+----------+
                |
                v
       LONGEST PREFIX?
                |
                v
              /16
                |
                v
        USE SPECIFIC ROUTE
```

### Critical lesson

Do not say:

> Remote traffic always uses the default gateway.

That is incorrect.

A better statement is:

> Linux selects the best matching route. The default route is used when no more-specific route wins.

## 9. Understand Route Types at This Level

You do not need to master every Linux route type yet.

For JUN-048, focus on three practical categories.

### Connected route

Example:

```text
10.20.30.0/24 dev ens3 proto kernel scope link
```

Meaning:

```text
This network is directly reachable
through this interface.
```

### Route through a gateway

Example:

```text
172.16.0.0/16 via 10.20.30.254 dev ens3
```

Meaning:

```text
For this destination network,
send traffic to this next hop.
```

### Default route

Example:

```text
default via 10.20.30.1 dev ens3
```

Meaning:

```text
Use this route when it is the
best available match after
more-specific routes are considered.
```

This gives you the essential junior model:

```text
ROUTE
 |
 +-- directly connected
 |
 +-- via next hop
 |
 `-- default fallback
```

## 10. Source Addresses and Multiple Interfaces

Routing is not only about choosing where traffic goes.

Linux may also need to choose which local address to use as the packet's source.

Consider a host with:

```text
ens3
10.20.30.15/24

ens4
10.50.60.15/24
```

The routing table may contain connected routes for both networks:

```text
10.20.30.0/24 dev ens3
10.50.60.0/24 dev ens4
```

Traffic toward:

```text
10.20.30.50
```

may use:

```text
ens3
```

while traffic toward:

```text
10.50.60.50
```

may use:

```text
ens4
```

The host therefore does not have one universal outgoing interface.

Route selection depends on the destination.

### `src`

You may see:

```text
src 10.20.30.15
```

inside a route.

Or `ip route get` may show:

```text
src 10.20.30.15
```

This tells you the source address Linux selected or prefers for that route lookup.

### Do not assume

```text
first interface listed
=
outbound interface
```

Do not assume:

```text
first IP address
=
source address for every connection
```

And do not assume:

```text
default-route interface
=
interface used for every destination
```

The routing decision determines the path.

## 11. Investigate Routing Problems Without Changing Routes

Routing failures are easy to misdiagnose because many symptoms look similar.

An application may report:

```text
connection failed
```

That does not immediately tell you whether the problem is:

- addressing;
- subnetting;
- routing;
- DNS;
- firewall behavior;
- transport;
- remote service availability.

Start with evidence.

### Symptom 1: Host has an IP address but no default route

Inspect:

```bash
ip -4 addr
```

Then:

```bash
ip route
```

You may find a connected route but no:

```text
default
```

This does not mean local networking is impossible.

The host may still communicate with destinations covered by connected or other specific routes.

But destinations without a matching route will not magically become reachable.

### Symptom 2: A specific network uses a different gateway

Suppose:

```text
default via 10.20.30.1 dev ens3

172.16.0.0/16 via 10.20.30.254 dev ens3
```

Someone sees:

```text
172.16.50.10
```

and assumes it uses:

```text
10.20.30.1
```

That assumption is wrong.

The `/16` route is more specific.

Query:

```bash
ip route get 172.16.50.10
```

Linux can show the actual decision.

### Symptom 3: Interface is UP but remote traffic fails

An interface being:

```text
UP
```

does not prove the routing table contains a suitable route.

Inspect:

```bash
ip link
```

then:

```bash
ip -4 addr
```

then:

```bash
ip route
```

Different layers answer different questions.

### Symptom 4: DNS is blamed for an IP-routing failure

If communication to a literal IP destination fails, name resolution may not be involved in that specific test.

Do not change DNS merely because networking is failing.

### Symptom 5: The default gateway is blamed for local traffic

If the destination is covered by a connected route, the default route may not be selected at all.

Ask Linux:

```bash
ip route get DESTINATION
```

### Safe troubleshooting sequence

Use:

```text
SYMPTOM
   |
   v
INTERFACE EXISTS?
   |
   v
EXPECTED ADDRESS/PREFIX?
   |
   v
EXPECTED CONNECTED ROUTE?
   |
   v
ROUTE FOR DESTINATION?
   |
   v
WHICH ROUTE WINS?
   |
   v
EXPECTED INTERFACE?
   |
   v
EXPECTED NEXT HOP?
   |
   v
EXPECTED SOURCE ADDRESS?
   |
   v
CONTINUE TO CONNECTIVITY TESTING
IN LATER LABS
```

### Controlled failure analysis

You will not break the routing table in this lab.

Instead, diagnose these hypothetical failures.

#### Case A

```text
Host:
10.20.30.15/24

Routes:
10.20.30.0/24 dev ens3

Destination:
10.20.30.50
```

A matching connected route exists.

The absence of a default route does not prevent this route from matching the local destination.

#### Case B

```text
Host:
10.20.30.15/24

Routes:
10.20.30.0/24 dev ens3

Destination:
203.0.113.50
```

There is no default route and no route for the remote destination.

The routing table lacks an obvious route for that destination.

#### Case C

```text
Routes:

default via 10.20.30.1 dev ens3

172.16.0.0/16 via 10.20.30.254 dev ens3
```

Destination:

```text
172.16.40.10
```

The `/16` route wins because it is more specific than `/0`.

#### Case D

```text
Routes:

default via 10.20.30.1 dev ens3

10.50.0.0/16 dev ens4
```

Destination:

```text
10.50.20.30
```

The `/16` connected route through:

```text
ens4
```

wins.

Do not assume the default-route interface handles the packet.

## 13. Knowledge Check, Interview Practice, and Completion

### Knowledge Check

1. **What is a routing table?**  
   A set of routing information Linux uses to determine how packets should be sent toward destination networks or hosts.

2. **What does a route's destination prefix represent?**  
   The destination address range to which the route can apply.

3. **What does `dev ens3` mean in a route?**  
   It identifies `ens3` as the interface associated with that route.

4. **What does `via 10.20.30.1` mean?**  
   It identifies `10.20.30.1` as the next-hop gateway.

5. **What does the IPv4 default route represent conceptually?**  
   `0.0.0.0/0`.

6. **Does the default route automatically beat every other route?**  
   No. More-specific matching prefixes normally take precedence.

7. **What is longest-prefix matching?**  
   Selecting the matching route with the most specific destination prefix.

8. **Which is more specific, `/24` or `/16`?**  
   `/24`.

9. **Which is more specific, `/16` or `/0`?**  
   `/16`.

10. **What is a connected route?**  
    A route representing a network directly reachable through a local interface.

11. **Does a directly connected destination normally require the default gateway as its next hop?**  
    No, not when the connected route is selected.

12. **What does `ip route get` do?**  
    It asks Linux to perform a route lookup for a destination and report the resulting routing decision.

13. **Does `ip route get` prove that a remote server is reachable?**  
    No.

14. **What can `src` indicate in routing output?**  
    A source address selected or preferred for traffic using that route or lookup.

15. **Can two remote destinations leave through different interfaces?**  
    Yes. Different routes can select different interfaces and next hops.

### Interview Practice

#### How do you inspect the IPv4 routing table on Linux?

I use:

```bash
ip route
```

or explicitly:

```bash
ip -4 route
```

I inspect destination prefixes, gateways, interfaces, and other route attributes rather than looking only for the default route.

#### What is a default route?

A default route is the fallback route used when it is the best available match after more-specific routes are considered. For IPv4, it corresponds to `0.0.0.0/0`.

#### What does longest-prefix match mean?

When multiple routes match a destination, Linux normally prefers the route with the most specific destination prefix. For example, a matching `/24` is more specific than a matching `/16`, and both are more specific than `/0`.

#### What is the difference between a destination and a next hop?

The destination is where the packet ultimately needs to go. A next hop is an intermediate router to which the local host sends the packet so it can continue toward that destination.

#### Does all remote traffic use the default gateway?

No. A remote destination may match a more-specific route through another gateway or interface. The default route is a fallback, not a universal path.

#### How would you determine which route Linux would use for a specific destination?

I would run:

```bash
ip route get DESTINATION
```

and inspect the selected interface, next hop, source address, and other reported routing information.

#### A server has the correct IP address and its interface is UP, but remote connectivity fails. What routing checks would you perform?

I would inspect `ip route`, confirm the connected route, check whether an appropriate route exists for the destination, inspect the default route when relevant, and use `ip route get DESTINATION` to see the actual routing decision before changing configuration.

#### Does a successful `ip route get` mean the destination is online?

No. It only establishes that Linux can make a routing decision for that destination. It does not test packet delivery or application availability.
