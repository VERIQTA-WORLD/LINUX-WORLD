## 1. Your Engineering Mission

A Linux server has an IP address, an active network interface, and a configured default gateway.

Does that mean Linux will send every outgoing packet through the default gateway?

No.

Before sending an IP packet, Linux must determine how to reach its destination. It consults routing information and selects an appropriate route.

For example, consider a server with this configuration:

```text
Interface: ens3
Address:   192.168.10.20/24
Gateway:   192.168.10.1
```

The server needs to communicate with three destinations:

```text
192.168.10.50
10.20.30.40
8.8.8.8
```

Those destinations do not necessarily follow the same route.

Your mission is to investigate how Linux makes routing decisions, identify directly connected and gateway-based routes, and prove which route Linux selects for a destination.

You will use the existing routing configuration of your lab machine. You will not modify its network settings.

### What you will learn

By completing this lab, you will be able to:

- Explain what a Linux routing table contains.
- Identify connected, specific, and default routes.
- Read the destination, gateway, interface, source, and metric fields.
- Explain the difference between a destination and a next hop.
- Understand longest-prefix matching.
- Use `ip route get` to investigate a routing decision.
- Recognize when a destination is directly reachable.
- Identify which interface Linux intends to use.
- Explain why the default route is not always selected.
- Recognize common routing mistakes.
- Produce an evidence-based routing report.

**Learning boundary:** This lab covers basic IPv4 routing inspection and route selection. You will not configure static routes, manipulate routing tables, troubleshoot advanced policy routing, or change network services.

## 2. Understand the Linux Routing Model

In JUN-047, you learned that an IP address and prefix establish a network boundary.

For example:

```text
192.168.10.20/24
```

belongs to:

```text
192.168.10.0/24
```

That information helps Linux understand which network is directly connected.

Routing extends that concept.

A route tells Linux how to reach a destination network or address.

Consider this simplified network:

```text
                    LINUX SERVER
                  192.168.10.20/24
                         |
                         |
                 Local network
                 192.168.10.0/24
                         |
             +-----------+-----------+
             |                       |
      192.168.10.50           192.168.10.1
       Local host             Default gateway
                                     |
                                     |
                              Other networks
                                     |
                           +---------+---------+
                           |                   |
                       10.20.30.40          8.8.8.8
```

The server can use its directly connected route to reach `192.168.10.50`.

To reach destinations outside its directly connected networks, it needs another suitable route.

That route might identify a specific next-hop router or use the default gateway.

### Five routing terms to understand

| Term | Meaning |
|---|---|
| Destination | The address or network Linux needs to reach |
| Prefix | Defines the address range matched by a route |
| Next hop | The router to which a packet is forwarded |
| Interface | The Linux network interface selected for transmission |
| Metric | A route preference value relevant when comparing otherwise suitable routes |

A next hop is not necessarily the packet's final destination.

For example:

```text
Destination: 8.8.8.8
Next hop:    192.168.10.1
```

The server sends the packet toward `192.168.10.1`, which can forward it onward.

The packet's IP destination remains `8.8.8.8` under ordinary forwarding.

## 3. Inspect Your Existing Routing Table

Start by discovering your IPv4 configuration:

```bash
ip -4 addr
```

Identify your non-loopback interface and its IPv4 address.

Next, run:

```bash
ip -4 route show
```

The shorter equivalent is:

```bash
ip route
```

On a simple Ubuntu VM, you might encounter output resembling the following.

**Representative output — not your expected exact result:**

```text
default via 192.168.10.1 dev ens3 proto dhcp metric 100

192.168.10.0/24 dev ens3 proto kernel scope link
src 192.168.10.20 metric 100
```

Your machine may have additional routes, different addresses, multiple interfaces, or no default route.

Do not change the configuration to match this example.

### Interpret the connected route

Consider:

```text
192.168.10.0/24 dev ens3 proto kernel scope link
src 192.168.10.20 metric 100
```

Read it as follows:

| Field | Interpretation |
|---|---|
| `192.168.10.0/24` | Destination network |
| `dev ens3` | Interface associated with the route |
| `proto kernel` | Route origin is identified as kernel |
| `scope link` | Destination is directly reachable at link scope |
| `src 192.168.10.20` | Preferred source address associated with this route |
| `metric 100` | Route metric |

The preferred source address does not mean every possible packet must use that source under every circumstance.

### Inspect the default route

Consider:

```text
default via 192.168.10.1 dev ens3
```

This identifies:

```text
Destination: default
Next hop:    192.168.10.1
Interface:   ens3
```

For IPv4, `default` represents:

```text
0.0.0.0/0
```

A `/0` route matches the entire IPv4 address space, making it a fallback when no more specific applicable route is selected.

**Checkpoint:** Find the connected route and default route on your own machine, if present. Record their actual values.

## 4. Directly Connected Routes vs Gateway Routes

There are two important patterns to recognize.

### Directly connected route

Example:

```text
192.168.10.0/24 dev ens3 scope link
```

This tells Linux that the destination network is reachable through `ens3` without specifying a separate IP next-hop router.

For a conventional Ethernet network, Linux can use link-layer address resolution to deliver traffic to an appropriate destination on that link.

Detailed ARP troubleshooting is outside this lab.

### Gateway-based route

Example:

```text
10.20.0.0/16 via 192.168.10.1 dev ens3
```

This tells Linux that traffic matching:

```text
10.20.0.0/16
```

should be forwarded toward:

```text
192.168.10.1
```

through:

```text
ens3
```

Compare the two:

| Route | Forwarding interpretation |
|---|---|
| `192.168.10.0/24 dev ens3` | Directly connected network |
| `10.20.0.0/16 via 192.168.10.1 dev ens3` | Use the specified next-hop router |
| `default via 192.168.10.1 dev ens3` | Fallback route through the gateway |

A route without `via` is not automatically an error.

Similarly, the presence of `via` does not mean the route is the default route. Specific routes can also use gateways.

## 5. Understand Longest-Prefix Matching

This is the central concept of the lab.

Linux does not simply choose the first route displayed by `ip route`.

For ordinary destination-based routing, the most specific matching destination prefix takes precedence.

Consider this illustrative routing table:

```text
192.168.10.0/24 dev ens3

10.20.0.0/16 via 192.168.10.1 dev ens3

10.20.30.0/24 via 192.168.10.2 dev ens3

default via 192.168.10.1 dev ens3
```

Now suppose the destination is:

```text
10.20.30.50
```

Several routes match:

```text
10.20.0.0/16
10.20.30.0/24
0.0.0.0/0
```

But the `/24` is the most specific match.

Therefore, Linux selects:

```text
10.20.30.0/24 via 192.168.10.2 dev ens3
```

for this simplified routing scenario.

### Visualize the decision

```text
Destination: 10.20.30.50
              |
              v
       MATCHING ROUTES
              |
      +-------+--------+
      |       |        |
     /0      /16      /24
      |       |        |
      +-------+--------+
              |
              v
      LONGEST PREFIX
              |
              v
             /24
              |
              v
      Next hop 192.168.10.2
```

### Test your understanding

Using the illustrative table above:

| Destination | Selected destination prefix |
|---|---|
| `192.168.10.50` | `192.168.10.0/24` |
| `10.20.40.10` | `10.20.0.0/16` |
| `10.20.30.50` | `10.20.30.0/24` |
| `8.8.8.8` | `0.0.0.0/0` |

**Engineer Note:** Route metrics and other routing rules also matter. Longest-prefix matching identifies the most specific applicable destination prefix; metrics can help distinguish competing routes within the relevant selection context. Do not assume that a low-metric default route overrides a more specific destination route.

## 6. Investigate Route Selection with `ip route get`

Reading the routing table is useful, but Linux also provides a command for asking how it would route a particular destination.

The command is:

```bash
ip route get DESTINATION
```

This is a read-only lookup.

It does not require sending an ICMP packet, opening an HTTP connection, or contacting the destination.

### Test the loopback destination

Run:

```bash
ip route get 127.0.0.1
```

Inspect the returned interface and source address.

You should expect loopback-related routing.

### Test your gateway

If your host has a conventional IPv4 default gateway, run:

```bash
ip route get GATEWAY_IP
```

Replace `GATEWAY_IP` with the actual address from your routing table.

For example:

```bash
ip route get 192.168.10.1
```

Use this example only if that is genuinely your gateway.

### Test an external destination

Run:

```bash
ip route get 8.8.8.8
```

A representative result might resemble:

```text
8.8.8.8 via 192.168.10.1 dev ens3
src 192.168.10.20 uid 1000
```

The result may also contain a `cache` line or other details.

Focus on:

```text
Destination
Next hop, if present
Interface
Selected source address
```

Do not assume the result proves the remote host is reachable.

It establishes the routing decision for the lookup, not successful packet delivery.

### Why `ip route get` matters

Compare:

```bash
ip route
```

with:

```bash
ip route get 8.8.8.8
```

The first displays routing information.

The second asks Linux to resolve a route for a specific destination.

Both are useful, but they answer different questions.

**Checkpoint:** Identify the interface, next hop (if present), and selected source address for your external-destination lookup.

## 7. Understand the Source Address in a Routing Decision

A Linux host can have several addresses.

For example:

```text
ens3:
192.168.10.20/24
192.168.10.21/24
```

When an application initiates communication without explicitly selecting a source address, Linux may need to choose an appropriate source.

Run:

```bash
ip route get 8.8.8.8
```

Look for:

```text
src
```

For example:

```text
src 192.168.10.20
```

This indicates the selected source address for that lookup.

Do not confuse:

```text
src 192.168.10.20
```

with:

```text
via 192.168.10.1
```

They represent different roles.

| Field | Meaning |
|---|---|
| `src` | Selected or preferred source address |
| `via` | Next-hop gateway |
| `dev` | Outgoing interface |
| Destination | Address Linux is trying to reach |

### Common misconception

A route that selects `ens3` does not mean every packet must use the first address displayed under `ens3`.

Source-address selection can depend on route information, address configuration, and application behavior.

Advanced source selection belongs in later networking material.

## 8. Investigate Common Routing Misinterpretations

You will now work through controlled interpretation failures.

No actual route will be deleted or modified.

### Case A — The interface is UP, so routing must work

A server reports:

```text
ens3: UP, LOWER_UP
```

An engineer concludes:

> The network configuration is correct.

That conclusion is unsupported.

An interface can be operationally enabled while the host lacks an appropriate route.

Investigate with:

```bash
ip -4 addr
ip route
```

Then test a destination lookup:

```bash
ip route get 8.8.8.8
```

If no usable route exists, the lookup can fail with an error such as:

```text
RTNETLINK answers: Network is unreachable
```

The exact error depends on the configuration.

**Root-cause principle:** Interface state and routing state are different.

### Case B — The default gateway handles every destination

Consider:

```text
192.168.10.0/24 dev ens3

default via 192.168.10.1 dev ens3
```

The destination is:

```text
192.168.10.50
```

Which route is more specific?

The connected `/24`.

The default route is not needed for this destination.

### Case C — A specific route exists, but the default route has a lower metric

Consider:

```text
10.20.30.0/24 via 192.168.10.2 dev ens3 metric 200

default via 192.168.10.1 dev ens3 metric 100
```

For:

```text
10.20.30.50
```

the `/24` destination route is more specific than `/0`.

Do not compare metrics while ignoring prefix specificity.

### Case D — `ip route get` succeeded, so the application must work

Suppose:

```bash
ip route get 8.8.8.8
```

returns a valid route.

That proves Linux can resolve a route for the lookup.

It does not prove:

- the gateway responds;
- the upstream network is functioning;
- the destination is reachable;
- a firewall permits the traffic;
- the remote service is running;
- DNS works;
- the application is healthy.

This is an important troubleshooting boundary.

## 9. Build a Safe Routing Investigation Workflow

When a Linux server cannot reach an expected remote destination, begin with evidence.

Use this sequence:

```text
START
  |
  v
Identify destination IP
  |
  v
Inspect interface addresses
  |
  v
ip -4 addr
  |
  v
Inspect routing information
  |
  v
ip route
  |
  v
Check destination-specific lookup
  |
  v
ip route get DESTINATION
  |
  +--------------------------+
  |                          |
  v                          v
Route returned             Lookup fails
  |                          |
  v                          v
Record interface,          Investigate missing,
next hop and source        unsuitable or prohibited
  |                        routing information
  v
Continue connectivity
investigation in later labs
```

### Useful diagnostic commands

| Question | Command |
|---|---|
| What IPv4 addresses exist? | `ip -4 addr` |
| What routes are displayed? | `ip route` |
| Is a default route present? | `ip route show default` |
| How would Linux route a destination? | `ip route get DESTINATION` |
| Which source address is selected? | Inspect `src` in `ip route get` |
| Which interface is selected? | Inspect `dev` in `ip route get` |
| Is a gateway involved? | Inspect `via`, if present |

### Engineer Notes

1. A route lookup is not a connectivity test.
2. The default route is a fallback, not an instruction to send every packet through one router.
3. The next hop and final destination are different concepts.
4. A connected route normally does not need an explicit IP gateway.
5. Do not assume route display order is route-selection priority.
6. A system may legitimately have multiple routing tables, interfaces, or default routes. This lab focuses on ordinary IPv4 routing behavior; advanced policy routing is outside its scope.
7. Never delete or replace a production route merely because it looks unfamiliar.

## 11. Knowledge Check and Interview Preparation

### Knowledge Check

Answer these before reviewing the explanations.

1. What is the purpose of a routing table?
2. What does `default` represent in an IPv4 routing table?
3. What does `via` identify?
4. What does `dev` identify?
5. What does `src` represent in route information?
6. What is a directly connected route?
7. What is the difference between a destination and a next hop?
8. What does longest-prefix matching mean?
9. Which is more specific: `/16` or `/24`?
10. Can a specific route override a default route with a lower metric?
11. Does every destination require the default gateway?
12. What does `ip route get` investigate?
13. Does `ip route get` send an application request to the destination?
14. Does a successful route lookup prove end-to-end connectivity?
15. What should you inspect before changing a route on a remotely accessed server?

### Answer guidance

The important principles are:

- Routing information determines how Linux forwards traffic toward destinations.
- The IPv4 default route is `0.0.0.0/0`.
- `via` identifies a next-hop gateway.
- `dev` identifies the outgoing interface.
- `src` identifies a source-address preference or selection, depending on the output.
- Directly connected routes describe networks reachable through an interface without specifying a separate IP next-hop router.
- Longest-prefix matching favors the most specific applicable destination prefix.
- A `/24` is more specific than a `/16`.
- A default route is not automatically selected when a more specific route matches.
- `ip route get` performs a route lookup; it is not proof of packet delivery.

### Interview Practice

**1. How do you display the IPv4 routing table on Linux?**

```bash
ip route
```

**2. What is the difference between a connected route and a default route?**

A connected route describes a network directly reachable through an interface. A default route is a fallback for destinations without a more specific applicable route.

**3. What is longest-prefix matching?**

It is the selection principle that favors the most specific matching destination prefix in ordinary destination-based routing.

**4. What does `via` mean in a Linux route?**

It identifies the next-hop router used to forward traffic toward the matching destination.

**5. How would you determine which interface Linux intends to use for a destination?**

I would run:

```bash
ip route get DESTINATION
```

and inspect the `dev` field.

**6. What is the difference between `src` and `via`?**

`src` identifies source-address information for the route or lookup. `via` identifies the next-hop gateway.

**7. Can a server have a valid IP address but no usable route to an external destination?**

Yes. Address configuration and routing are separate. I would inspect `ip route` and perform a destination-specific lookup.

**8. A route lookup succeeds, but an application cannot connect. What does that tell you?**

Linux found a route for the lookup, but communication may still fail elsewhere. Further investigation could involve the link, gateway, upstream network, firewall, transport connection, DNS, or application.
