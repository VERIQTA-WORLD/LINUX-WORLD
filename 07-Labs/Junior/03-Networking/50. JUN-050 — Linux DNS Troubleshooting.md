## 1. Your Engineering Mission

A deployment has completed successfully. The application starts, but its logs report that it cannot resolve the hostname of an external dependency.

The reported error resembles:

```text
Temporary failure in name resolution
```

The operations team suspects DNS.

One engineer suggests replacing `/etc/resolv.conf` with a public DNS server. Another suggests restarting networking. A third thinks the default gateway is incorrect.

None of these actions should be your starting point.

Your job is to establish where the resolution process fails before deciding whether a configuration change is justified.

A Linux DNS failure can originate from several places:

```text
APPLICATION REQUEST
        |
        v
NAME-SERVICE CONFIGURATION
        |
        v
LOCAL HOSTS FILE / RESOLVER
        |
        v
DNS SERVER SELECTION
        |
        v
NETWORK PATH TO DNS SERVER
        |
        v
DNS RESPONSE
        |
        v
APPLICATION RECEIVES RESULT
```

The important engineering question is not simply:

**Is DNS working?**

It is:

**Which part of name resolution is working, which part is failing, and what evidence supports that conclusion?**

### Learning objectives

By completing this lab, you will be able to:

- Recognize common Linux DNS failure symptoms.
- Distinguish name-resolution failures from IP-routing failures.
- Inspect Linux name-service configuration.
- Understand the role of `/etc/hosts`, `/etc/nsswitch.conf`, and `/etc/resolv.conf`.
- Recognize the local `systemd-resolved` stub resolver.
- Inspect resolver status and upstream DNS configuration.
- Compare local, external, IPv4, and IPv6 resolution.
- Perform a resolver-specific query when supported.
- Investigate whether Linux has a route toward an upstream DNS server.
- Interpret common DNS errors without overclaiming their cause.
- Build and test a DNS failure hypothesis.
- Document findings and recommend an evidence-based corrective action.

### Safety rules

This is a read-only investigation.

You must not:

- Replace `/etc/resolv.conf`.
- Change configured DNS servers.
- Edit `/etc/hosts`.
- Restart networking.
- Restart `systemd-resolved`.
- Flush DNS caches.
- Disable IPv6.
- Modify routes.
- Change firewall rules.
- Install or expose an additional DNS service.

The controlled failure in this lab uses a deliberately invalid DNS name. You will investigate the resulting failure without damaging a functioning system.

## 2. Understand the DNS Failure Before Investigating It

In JUN-049, you learned that DNS provides information associated with domain names, including IP addresses.

For example:

```text
Application requests:
example.com
       |
       v
Name resolution
       |
       v
IP address returned
```

However, obtaining an address is only one stage in successful communication.

Consider:

```text
HOSTNAME
   |
   v
DNS RESOLUTION
   |
   v
DESTINATION IP
   |
   v
ROUTING
   |
   v
NETWORK DELIVERY
   |
   v
APPLICATION CONNECTION
```

A failure at any stage can produce an application-level error.

### Four important failure categories

| Category | Example symptom | Investigation direction |
|---|---|---|
| Name resolution | Hostname cannot be resolved | Resolver and DNS evidence |
| Routing | No suitable route exists | Routing table |
| Transport connectivity | Connection cannot be established | Ports and network path |
| Application | Service returns an error | Application and service evidence |

This lab focuses on the first category while using earlier networking knowledge to recognize when the underlying problem may belong elsewhere.

### Common DNS errors

You may encounter messages such as:

```text
Temporary failure in name resolution
```

```text
Name or service not known
```

```text
No appropriate name servers or networks for name found
```

These messages are useful evidence, but their wording alone does not always establish the root cause.

For example, a temporary resolution failure may involve resolver availability, configuration, or network reachability.

A name-not-found result may indicate that the requested name does not exist in the resolver's available DNS view.

Do not treat every unsuccessful lookup as the same failure.

**Checkpoint:** Before continuing, explain why replacing the DNS server immediately could be the wrong response to an application connection failure.

## 3. Establish the Host's Starting State

Before investigating DNS, collect the host's current networking evidence.

### Step 1 — Inspect IPv4 addressing

Run:

```bash
ip -4 addr
```

Identify the relevant non-loopback interface and its configured IPv4 address.

Record:

```text
Interface:
IPv4 address:
Prefix:
```

### Step 2 — Inspect routing

Run:

```bash
ip route
```

Identify the default route, if present.

You may encounter a route resembling:

```text
default via 192.168.10.1 dev ens3
```

This is illustrative output. Your system will have different values.

Record:

```text
Default gateway:
Default-route interface:
```

A valid IP address does not automatically guarantee that the host has a route toward its DNS server.

### Step 3 — Inspect the resolver file

Run:

```bash
cat /etc/resolv.conf
```

Look for entries beginning with:

```text
nameserver
```

On a typical Ubuntu installation using the `systemd-resolved` stub resolver, you may encounter:

```text
nameserver 127.0.0.53
```

This is a local stub address.

It does not necessarily identify the upstream DNS server.

### Step 4 — Identify how the file is managed

Run:

```bash
ls -l /etc/resolv.conf
```

Determine whether the file is a regular file or symbolic link.

A symbolic link may point to a file maintained by `systemd-resolved`.

This distinction matters because editing generated resolver information directly may not produce the intended persistent configuration.

### Step 5 — Inspect name-service configuration

Run:

```bash
grep '^hosts:' /etc/nsswitch.conf
```

The result identifies the configured name-service mechanisms and associated lookup behavior.

You may encounter mechanisms such as:

```text
files
resolve
dns
```

Your actual configuration may differ.

Do not assume every Ubuntu installation has an identical lookup order.

### Baseline checkpoint

Complete this record:

| Item | Your evidence |
|---|---|
| Interface | |
| IPv4 address/prefix | |
| Default gateway | |
| `/etc/resolv.conf` type | |
| Nameserver entries | |
| NSS `hosts:` configuration | |

You now have a starting state against which later observations can be compared.

## 4. Investigate Local Name Resolution

Start with a name that is normally resolved locally.

Run:

```bash
getent hosts localhost
```

On a normally configured Linux host, `localhost` should resolve to a loopback address.

The result may contain an IPv4 or IPv6 address depending on the system's configuration and lookup behavior.

Next, inspect:

```bash
cat /etc/hosts
```

Look for local mappings associated with `localhost`.

### Why start here?

A successful `localhost` lookup establishes that at least part of the configured system name-resolution mechanism is functioning.

It does not prove external DNS works.

Consider these two observations:

```text
localhost
    |
    v
RESOLVES
```

```text
example.com
    |
    v
DOES NOT RESOLVE
```

The evidence suggests that the failure is not a universal inability to resolve every name.

It does not yet establish the root cause.

### Engineering interpretation

Do not write:

> DNS is working because localhost resolved.

Write:

> Local name resolution succeeded. External DNS resolution has not yet been established.

That distinction is important in production incident reports.

## 5. Test External Name Resolution

Now investigate a known external domain.

Run:

```bash
getent hosts example.com
```

If resolution succeeds, record the returned address information.

If it fails, record the failure rather than immediately changing configuration.

Next, inspect the address families separately.

### IPv4 lookup

```bash
getent ahostsv4 example.com
```

### IPv6 lookup

```bash
getent ahostsv6 example.com
```

These commands use the host's configured name-resolution mechanisms.

The exact output depends on the environment.

### Compare the results

| Observation | What it suggests |
|---|---|
| IPv4 and IPv6 return results | Both tested address-family lookups succeeded |
| IPv4 succeeds, IPv6 does not | Investigate the IPv6-specific result |
| IPv6 succeeds, IPv4 does not | Investigate the IPv4-specific result |
| Neither succeeds | Continue investigating resolver configuration and availability |

Do not automatically classify an unsuccessful IPv6 lookup as a complete DNS outage.

A hostname may not have the address records you expected, and local resolver behavior can differ between address families.

### Record the evidence

```text
Domain tested:
example.com

General lookup:
Success / Failure

IPv4 lookup:
Success / Failure

IPv6 lookup:
Success / Failure

Returned addresses:
```

**Checkpoint:** Can you distinguish a complete failure of the tested name from a result that differs only by address family?

## 6. Inspect `systemd-resolved`

Ubuntu Server 24.04 LTS commonly uses `systemd-resolved`, although its exact resolver setup depends on installation and network configuration.

First, check whether the command is available:

```bash
command -v resolvectl
```

If available, run:

```bash
resolvectl status
```

Inspect the output for information such as:

```text
Current DNS Server
DNS Servers
DNS Domain
```

You may see configuration associated with individual network interfaces.

### Understand the local stub

If `/etc/resolv.conf` contains:

```text
nameserver 127.0.0.53
```

do not conclude that the host has no external DNS configuration.

On the standard `systemd-resolved` stub setup:

```text
APPLICATION
     |
     v
127.0.0.53
LOCAL STUB RESOLVER
     |
     v
UPSTREAM DNS INFRASTRUCTURE
```

Use `resolvectl status` to inspect the resolver information available through `systemd-resolved`.

### Inspect service state

If the host uses `systemd-resolved`, run:

```bash
systemctl status systemd-resolved --no-pager
```

Look for the service's reported state.

A representative healthy state may include:

```text
Active: active (running)
```

Do not expect every Linux environment to use the same resolver service.

If `systemd-resolved` is absent or intentionally inactive, document that fact and inspect the configured resolver mechanism rather than treating the difference as automatic evidence of a fault.

### Perform a resolver-specific query

When `resolvectl` is available and operational, run:

```bash
resolvectl query example.com
```

This asks `systemd-resolved` to resolve the requested name.

Compare the result with:

```bash
getent hosts example.com
```

The two commands investigate related but not identical paths.

`getent` follows the system's configured name-service mechanisms.

`resolvectl query` directly uses `systemd-resolved`.

If their results differ, investigate that difference before making changes.

## 7. Verify the Route Toward the Upstream DNS Server

Suppose your resolver configuration identifies this upstream DNS server:

```text
10.20.30.53
```

This is an example address.

Do not assume it is your actual resolver.

Use the upstream address reported by your environment.

Run:

```bash
ip route get DNS_SERVER_IP
```

Replace `DNS_SERVER_IP` with the actual IPv4 resolver address.

For example:

```bash
ip route get 10.20.30.53
```

A representative result might resemble:

```text
10.20.30.53 via 192.168.10.1 dev ens3 src 192.168.10.20
```

This tells you Linux has resolved a route toward the destination.

It does not prove that the DNS server responds to queries.

### Interpret the result

| Field | Meaning |
|---|---|
| Destination address | The DNS server being investigated |
| `via` | Next-hop gateway, if applicable |
| `dev` | Selected interface |
| `src` | Selected source address for the lookup |

If the route lookup fails, investigate the routing evidence before blaming the DNS records.

### Important limitation

If the only resolver address visible is:

```text
127.0.0.53
```

you are looking at a local stub address in the standard `systemd-resolved` configuration.

A route lookup toward that address does not establish upstream DNS reachability.

Use the actual upstream resolver address when available.

If you cannot establish it, record that limitation.

## 8. Controlled Failure: Investigate a Name That Should Not Resolve

You will now reproduce a DNS failure safely.

Do not break a working resolver or disconnect the machine.

Instead, query a deliberately invalid name under the reserved `.invalid` top-level domain.

Run:

```bash
getent hosts veriqta-lab-050.invalid
```

This name is deliberately unsuitable for normal public DNS resolution.

On a functioning conventional public DNS path, you should not receive an ordinary public address record for it.

The command may produce no standard output.

### Record the command status

Immediately after the lookup, run:

```bash
echo $?
```

A nonzero status indicates that `getent` did not successfully return the requested result.

The exact status should be recorded from your own system.

### Investigate using `resolvectl`

If available, run:

```bash
resolvectl query veriqta-lab-050.invalid
```

Observe the result or error.

Do not assume every resolver produces identical wording.

### Compare with the known domain

Run:

```bash
getent hosts example.com
```

Now compare:

```text
example.com
       |
       v
Resolution result
```

with:

```text
veriqta-lab-050.invalid
       |
       v
Expected name-resolution failure
```

### Investigate the failure

Use the troubleshooting model.

**Symptom:** The deliberately invalid name cannot be resolved.

**Impact:** An application requesting that name would not obtain a usable destination address through the tested lookup.

**Evidence:** The lookup failed, while the known-domain result was recorded separately.

**Hypothesis:** The requested name is invalid rather than the entire resolver being unavailable.

**Test:** Compare the invalid-name lookup with a known-domain lookup using the same resolution mechanism.

**Root-cause conclusion:** If the known name resolves while the deliberately invalid name does not, the evidence is consistent with the expected invalid-name failure.

**Fix:** Correct the requested hostname in the application or configuration. Do not replace a functioning DNS server.

**Recovery verification:** Repeat the lookup using the correct, intended hostname and confirm that it resolves.

### What this teaches

Not every DNS failure requires a DNS infrastructure change.

Sometimes the resolver is functioning correctly by refusing to return an address for an invalid or nonexistent name.

**Checkpoint:** Explain why replacing `/etc/resolv.conf` would be an inappropriate fix for this controlled failure.

## 9. Recognize Common DNS Troubleshooting Patterns

The following patterns will help you interpret real incidents.

### Pattern A — Local names resolve, external names fail

Example evidence:

```text
localhost:
Success

example.com:
Failure
```

Possible investigation areas include resolver configuration, upstream resolver availability, or the network path toward the resolver.

Do not conclude that `/etc/hosts` is broken.

### Pattern B — One hostname fails, others resolve

Example:

```text
example.com:
Success

api.internal.example:
Failure
```

The entire DNS system is not necessarily unavailable.

Investigate the requested name, its intended DNS zone, and whether internal or split DNS is involved.

### Pattern C — DNS resolves, but the application still fails

Example:

```text
getent hosts example.com
```

returns an address.

The investigation should now consider subsequent communication layers.

Do not continue changing DNS merely because the application remains unavailable.

### Pattern D — The resolver service is running, but queries fail

A running service does not prove successful upstream resolution.

Investigate:

- active resolver configuration;
- the requested name;
- the query result;
- the route toward the upstream resolver;
- whether failures affect multiple names.

### Pattern E — IPv4 resolution succeeds, IPv6 resolution differs

Treat the address families separately.

Do not disable IPv6 as an automatic response.

### Pattern F — `/etc/resolv.conf` points to `127.0.0.53`

On a standard `systemd-resolved` setup, this can be correct.

Inspect the resolver's upstream configuration before declaring it faulty.

### Pattern G — The route to the resolver exists, but queries fail

A valid route is necessary for ordinary network communication, but it does not establish that the DNS service is responding.

Continue investigating the resolver rather than claiming that routing success proves DNS availability.

5. What does the NSS `hosts:` configuration influence?
6. Why might `127.0.0.53` appear in `/etc/resolv.conf`?
7. What does `resolvectl status` help you inspect?
8. Why should IPv4 and IPv6 resolution be tested separately?
9. What does `ip route get` establish when used with a DNS server address?
10. Does a valid route prove that the DNS server responds?
11. Why might one hostname fail while another resolves successfully?

14. Does successful DNS resolution prove application connectivity?
15. What should you repeat after correcting a confirmed DNS issue?

### Interview Practice

**1. A Linux application reports a temporary name-resolution failure. What would you investigate first?**

I would confirm the exact failing hostname, inspect the system's resolver configuration, and compare local and known external lookups before changing DNS settings.

**2. How do you test hostname resolution through Linux's configured name-service mechanisms?**

```bash
getent hosts HOSTNAME
```

For address-family-specific investigation:

```bash
getent ahostsv4 HOSTNAME
```

```bash
getent ahostsv6 HOSTNAME
```

**3. Why does Ubuntu sometimes use `127.0.0.53` as a nameserver?**

On systems using the standard `systemd-resolved` stub configuration, applications can send queries to the local stub resolver, which uses the configured resolution infrastructure.

**4. How would you inspect `systemd-resolved`?**

```bash
resolvectl status
```

For service-state evidence:

```bash
systemctl status systemd-resolved --no-pager
```

**5. Why would you inspect the route toward an upstream DNS server?**

A resolver address can be correctly configured while the host lacks a suitable network path toward it. A route lookup helps identify that possibility, although it does not prove the resolver responds.

**6. One domain fails but several others resolve. What does that suggest?**

It suggests that a complete name-resolution outage has not been established. I would investigate the failing name and its intended DNS environment rather than immediately replacing the resolver.

**7. Why is restarting networking an inappropriate first response to a DNS incident?**

It changes system state before the cause is established, may interrupt unrelated workloads, and can remove useful diagnostic evidence.

**8. How would you verify recovery after correcting a DNS issue?**

I would repeat the exact lookup that originally failed, confirm the expected resolution result, and then verify the affected application separately.
