# 1. Mission: The Server Has Network Connectivity, but the Application Cannot Resolve Its Database Name

You have reached an important transition in your Linux networking journey.

In the previous labs, you investigated:

- Linux network interfaces.
- IPv4 and IPv6 addressing.
- Subnets and default gateways.
- Linux routing tables.
- Route selection.
- Directly connected and remote destinations.

You now understand how Linux determines where an IP packet should go.

But applications do not always begin with an IP address.

Consider a production application configured to connect to:

```text
database.internal.example
```

The application needs to determine the destination IP address before establishing its network connection.

That introduces another critical part of networking: the Domain Name System, commonly called DNS.

## 1.1 The production scenario

An application server has the following approved configuration:

```text
Hostname: app-server-01

IPv4 address: 10.20.10.25/24

Default gateway: 10.20.10.1

Approved DNS resolver: 10.20.10.53

Database hostname: database.internal.example

Expected database address: 10.20.20.30
```

The application team reports:

> The application cannot connect to the database using its configured hostname.

The network engineer investigates the server.

The interface is operational.

The expected IPv4 address is present.

The routing table contains the appropriate route to the database subnet.

However, a hostname lookup fails.

The engineer discovers that the application server is using a resolver that does not have access to the organization's private DNS records.

The problem is not necessarily the application, the network interface, or the default gateway.

The failure occurs earlier in the communication process: name resolution.

Your mission is to understand DNS well enough to identify this distinction.

By the end of this lab, you should be able to explain what DNS does, inspect how Ubuntu resolves names, recognize important DNS record types, perform safe name-resolution tests, and investigate a controlled DNS incident without modifying production networking.

# 4. Understand What DNS Actually Does

DNS stands for **Domain Name System**.

It is a distributed naming system that allows clients to retrieve information associated with domain names.

One of its most familiar functions is mapping a hostname to an IP address.

For example:

```text
Application hostname:
www.example.com

              |
              v

       Name resolution

              |
              v

An IPv4 or IPv6 address
```

DNS is not limited to address lookup.

It also stores information about mail delivery, authoritative name servers, aliases, service-related data, and other resource records.

## 4.1 Why DNS exists

Imagine managing 200 application servers.

If every application were configured using hardcoded IP addresses, infrastructure changes could become difficult.

Consider:

```text
Application A ---> 10.20.20.30
Application B ---> 10.20.20.30
Application C ---> 10.20.20.30
```

If the database endpoint changes, every affected configuration may need attention.

DNS provides a naming layer.

```text
Application A ---+
                 |
Application B ---+---> database.internal.example
                 |                |
Application C ---+                v
                           DNS resolution
                                  |
                                  v
                              IP address
```

DNS does not eliminate the need for infrastructure planning, configuration management, or application recovery logic.

It provides a standardized mechanism for resolving names into relevant records.

## 4.2 DNS versus routing

These two processes answer different questions.

| DNS | Routing |
|---|---|
| What address or record is associated with this name? | Which path should be selected for this IP destination? |
| Uses DNS records and name-resolution mechanisms | Uses routing rules and routing tables |
| Can return IPv4 and IPv6 addresses | Selects paths for IPv4 or IPv6 traffic |
| May involve recursive resolvers | May involve connected routes and gateways |
| Does not establish application connectivity | Does not automatically resolve hostnames |

A simplified application communication sequence is:

```text
Application
    |
    v
Needs database.internal.example
    |
    v
Name resolution
    |
    v
Receives 10.20.20.30
    |
    v
Linux routing decision
    |
    v
Selected interface / next hop
    |
    v
Network communication
    |
    v
Database service
```

This sequence is simplified. Applications may cache addresses, use alternative resolution mechanisms, or already possess the destination address.

The important lesson is that DNS resolution and routing are separate troubleshooting areas.

# 5. Understand Hostnames, Domains, and Fully Qualified Domain Names

Before investigating DNS servers, understand the names they process.

Consider:

```text
app01.production.example.com
```

This name contains several labels separated by dots.

```text
app01 . production . example . com
```

Read from right to left, the labels form a hierarchy.

A simplified interpretation is:

| Component | Example |
|---|---|
| Top-level domain | `com` |
| Registered domain | `example.com` |
| Subdomain | `production.example.com` |
| Hostname within that naming structure | `app01.production.example.com` |

## 5.1 Hostname

A hostname identifies a host within a naming context.

On Linux, the configured system hostname can be inspected with:

```bash
hostname
```

Representative output:

```text
ubuntu-lab
```

A local hostname does not automatically mean that a corresponding public DNS record exists.

## 5.2 Domain name

A domain name identifies a node within the DNS naming hierarchy.

For example:

```text
example.com
```

Subdomains can be created beneath it:

```text
production.example.com

development.example.com

training.example.com
```

## 5.3 Fully Qualified Domain Name (FQDN)

A fully qualified domain name identifies a name in the complete DNS hierarchy.

For example:

```text
app01.production.example.com.
```

The final dot explicitly represents the DNS root.

In everyday usage, the trailing dot is commonly omitted:

```text
app01.production.example.com
```

However, the distinction can matter when resolver search domains are involved.

## 5.4 Short names versus complete names

Consider:

```text
database
```

This is a short name.

An environment may use a search domain to expand it into something such as:

```text
database.production.example.com
```

The exact behavior depends on resolver configuration and the application performing the lookup.

Do not assume that every Linux host automatically expands short names in the same way.

```bash

```

Then:

```bash
hostname -f
```

**Explanation:**

- `hostname` displays the configured hostname.
- `hostname -f` attempts to obtain the fully qualified hostname through the system's configured name-resolution mechanisms.

# 6. Understand the DNS Hierarchy

DNS is hierarchical.

It is not one central server containing every domain record in the world.

Consider:

```text
www.example.com
```

A simplified DNS hierarchy looks like this:

```text
                         DNS ROOT
                            .
                            |
                            v
                    TOP-LEVEL DOMAIN
                           com
                            |
                            v
                    REGISTERED DOMAIN
                       example.com
                            |
                            v
                         HOSTNAME
                      www.example.com
```

Different authoritative DNS infrastructure is responsible for different portions of this hierarchy.

## 6.1 Root DNS servers

The root DNS system provides information used to locate authoritative servers for top-level domains.

It does not ordinarily supply the final address record for every hostname.

## 6.2 Top-level domains

Examples include:

```text
.com

.org

.net

.ng

.mx

.uk
```

Top-level-domain infrastructure helps direct resolution toward the appropriate authoritative servers for delegated domains.

## 6.3 Authoritative DNS servers

An authoritative DNS server provides authoritative answers for DNS data within the zones it serves.

For example, an authoritative server for a relevant zone may hold records associated with:

```text
www.example.com

mail.example.com

api.example.com
```

## 6.4 Recursive resolvers

A recursive resolver receives a client's resolution request and works to obtain an answer.

It may:

- Return a suitable cached answer.
- Query other DNS servers.
- Follow DNS referrals.
- Return an error when resolution cannot be completed.

The client normally does not need to perform every step of the DNS hierarchy itself.

### Conceptual resolution flow

```text
                 LINUX APPLICATION
                         |
                         v
                  DNS QUERY REQUEST
                         |
                         v
                  RECURSIVE RESOLVER
                         |
                Is answer cached?
                    /        \
                  YES         NO
                   |           |
                   |           v
                   |        DNS ROOT
                   |           |
                   |           v
                   |       TLD SERVER
                   |           |
                   |           v
                   |    AUTHORITATIVE SERVER
                   |           |
                   +-----+-----+
                         |
                         v
                    DNS ANSWER
                         |
                         v
                    APPLICATION
```

This diagram describes a simplified cache-miss resolution process.

Actual resolver behavior depends on caching, delegation, record type, configuration, and other DNS mechanisms.

### Checkpoint 2

Explain the difference between:

- A recursive resolver.
- An authoritative DNS server.

A recursive resolver works to obtain answers for clients. An authoritative server provides authoritative data for the zones it serves.

These roles can exist within the same broader infrastructure, but they are conceptually different.

# 7. Understand Important DNS Record Types

DNS information is represented using resource records.

You do not need to memorize every DNS record type in JUN-049.

However, you should recognize the records most commonly encountered during Linux administration and application troubleshooting.

## 7.1 A record

An `A` record associates a name with an IPv4 address.

Illustrative record:

```text
app.example.com.    A    192.0.2.20
```

Interpretation:

The name is associated with the IPv4 address `192.0.2.20`.

## 7.2 AAAA record

An `AAAA` record associates a name with an IPv6 address.

Example:

```text
app.example.com.    AAAA    2001:db8::20
```

## 7.3 CNAME record

A `CNAME` record establishes an alias from one DNS name to another canonical name.

Example:

```text
portal.example.com.    CNAME    app.example.com.
```

The alias does not itself mean that the final application is reachable.

Further resolution may be necessary.

## 7.4 MX record

An `MX` record identifies mail exchangers for a domain.

Example:

```text
example.com.    MX    10 mail.example.com.
```

The number represents the MX preference value. Lower values are preferred under ordinary MX selection rules.

## 7.5 NS record

An `NS` record identifies name servers associated with a DNS zone or delegation.

Example:

```text
example.com.    NS    ns1.example.net.
```

## 7.6 SOA record

An `SOA` record contains important administrative information about a DNS zone.

It includes fields such as:

- Primary name-server information.
- Responsible-party mailbox representation.
- Zone serial number.
- Refresh interval.
- Retry interval.
- Expire interval.
- Negative caching-related value.

You are not expected to administer DNS zones in this lab.

## 7.7 PTR record

A `PTR` record is commonly used for reverse DNS resolution.

It associates a reverse DNS name with another domain name.

## 7.8 TXT record

A `TXT` record stores textual information.

TXT records are frequently encountered in domain-verification and email-authentication configurations.

However, TXT records are not exclusively used for those purposes.

### Record summary

| Record | Primary purpose |
|---|---|
| A | Name to IPv4 address |
| AAAA | Name to IPv6 address |
| CNAME | Alias to another DNS name |
| MX | Mail exchanger information |
| NS | Name-server information |
| SOA | DNS zone administrative information |
| PTR | Reverse DNS naming |
| TXT | Textual DNS information |

### Practical Exercise 2 — Identify the record

Match each requirement to a record type.

| Requirement | Answer |
|---|---|
| Associate `api.example.com` with an IPv4 address | A |
| Associate a hostname with an IPv6 address | AAAA |
| Create a DNS alias | CNAME |
| Identify a mail exchanger | MX |
| Identify authoritative name-server information | NS |
| Support reverse DNS naming | PTR |
| Publish textual verification information | TXT |

# 8. Understand Forward and Reverse DNS Resolution

DNS resolution can operate in different directions.

## 8.1 Forward resolution

Forward resolution retrieves records associated with a name.

For example:

```text
app.example.com
        |
        v
      A lookup
        |
        v
   192.0.2.20
```

An AAAA lookup can retrieve IPv6 addressing information.

## 8.2 Reverse resolution

Reverse DNS commonly uses PTR records to retrieve a name associated with an IP address.

For IPv4, reverse DNS uses the `in-addr.arpa` namespace.

For example, the reverse DNS name corresponding to:

```text
192.0.2.20
```

is:

```text
20.2.0.192.in-addr.arpa
```

For IPv6, reverse DNS uses `ip6.arpa`.

### Important distinction

Forward and reverse DNS are not automatically symmetrical.

A name may resolve to an address without that address having a corresponding PTR record.

A PTR record may also identify a name whose forward records do not match the original address.

Do not assume that reverse DNS proves the identity or trustworthiness of a remote system.

2. Which record type normally supplies an IPv6 address?

4. Does every valid A record require a matching PTR record?

# 9. Understand DNS Caching and TTL

DNS queries do not always require contacting an authoritative DNS server.

Resolvers can cache suitable DNS information.

Caching reduces repeated lookup work and can improve resolution performance.

## 9.1 What is TTL?

TTL stands for **Time to Live**.

DNS records include TTL values that influence how long caching resolvers may retain the information under normal DNS caching rules.

Consider an illustrative DNS answer:

```text
app.example.com.    300    IN    A    192.0.2.20
```

The TTL value is:

```text
300 seconds
```

This represents five minutes.

### What TTL does not guarantee

TTL does not mean every application will immediately observe a DNS change after exactly 300 seconds.

Other factors can affect observed behavior, including:

- When a resolver originally cached the record.
- Intermediate caches.
- Application-level caching.
- Negative caching.
- Resolver-specific behavior.
- Existing network connections.

## 9.2 Positive caching

Positive caching stores successful DNS answers.

Example:

```text
Query:
app.example.com A

Answer:
192.0.2.20
```

The resolver may retain the answer according to applicable caching behavior.

## 9.3 Negative caching

DNS systems can also cache certain negative responses.

For example, a resolver may cache an authoritative response indicating that a requested name does not exist.

This matters when engineers create a previously missing DNS record and expect every resolver to recognize it immediately.

## 9.4 Production example

An application endpoint changes from:

```text
192.0.2.20
```

to:

```text
192.0.2.30
```

The DNS record is updated.

However, some clients may temporarily continue using previously cached information.

A production engineer should consider DNS caching when planning migrations and investigating inconsistent resolution results.

Do not flush caches indiscriminately during an incident. Cached data may be useful evidence.

# 10. Understand How Linux Resolves Names

This section is particularly important.

On Linux, an application's hostname lookup is not necessarily a direct DNS query.

Many applications use system name-resolution interfaces, such as the GNU C Library resolver functions.

The system's name-service configuration can influence where hostname information comes from.

Potential sources include:

- Local files.
- DNS.
- `systemd-resolved`.
- Other configured Name Service Switch modules.

A simplified model is:

```text
                   APPLICATION
                        |
                        v
              SYSTEM NAME LOOKUP
                        |
                        v
              NAME SERVICE SWITCH
                        |
             +----------+----------+
             |                     |
             v                     v
         LOCAL FILES        OTHER CONFIGURED
          /etc/hosts        RESOLUTION SOURCES
                                   |
                                   v
                               DNS RESOLVER
                                   |
                                   v
                               DNS ANSWER
```

The exact path depends on the host configuration and the application.

## 10.1 What is NSS?

NSS stands for **Name Service Switch**.

It provides a configurable mechanism for determining how different categories of system information are resolved.

The relevant configuration file is:

```text
/etc/nsswitch.conf
```

## 10.2 The `hosts` database

Within this file, the `hosts` entry controls the configured sources and ordering for hostname resolution through NSS-aware interfaces.

An Ubuntu host may contain an entry resembling:

```text
hosts: files resolve [!UNAVAIL=return] dns
```

Another environment may use a different arrangement.

Do not replace your actual configuration with this example.

The important concepts are:

| Component | Meaning |
|---|---|
| `files` | Local hostname information, commonly `/etc/hosts` |
| `resolve` | Integration with `systemd-resolved` through the appropriate NSS module |
| `dns` | DNS lookup through the NSS DNS module |
| Bracketed actions | Conditions influencing whether NSS continues to another source |

### Why this matters

Two tools may behave differently because they do not necessarily use the same name-resolution path.

For example:

- `getent hosts` uses the configured NSS mechanism.
- `resolvectl query` interacts with `systemd-resolved`.
- `dig` performs DNS queries using its DNS client behavior and does not perform the complete NSS lookup sequence.

This distinction becomes essential during troubleshooting.

# 12. Hands-On Task 2 — Inspect `/etc/hosts`

The `/etc/hosts` file provides local static hostname-to-address mappings.

Run:

```bash
cat /etc/hosts
```

A representative Ubuntu configuration may contain:

```text
127.0.0.1       localhost

127.0.1.1       ubuntu-lab

::1             localhost ip6-localhost ip6-loopback
```

The exact entries vary.

## 12.1 Understand the structure

Consider:

```text
127.0.0.1 localhost
```

The first field is the IP address.

The remaining field identifies the hostname associated with that address.

A line can also contain additional names.

## 12.2 Why `/etc/hosts` matters

Local mappings can support:

- Loopback hostname resolution.
- Host-specific naming requirements.
- Controlled testing.
- Certain bootstrap configurations.

However, `/etc/hosts` is not a replacement for a managed DNS infrastructure in a large environment.

Static entries can become stale.

### Practical Task

Run:

```bash
getent hosts localhost
```

Representative output:

```text
::1 localhost ip6-localhost ip6-loopback
```

Depending on NSS configuration and address-family behavior, the output may differ.

To inspect IPv4-specific resolution through the system's address-resolution interface, run:

```bash
getent ahostsv4 localhost
```

Representative output may include:

```text
127.0.0.1 STREAM localhost

127.0.0.1 DGRAM

127.0.0.1 RAW
```

### What do these entries mean?

`getent ahostsv4` retrieves IPv4 address information through the relevant system name-resolution interface.

The `STREAM`, `DGRAM`, and `RAW` labels describe socket-type information associated with the returned address entries.

They are not three separate DNS records.

### Verification

You should be able to explain why `localhost` can resolve successfully even when external DNS is unavailable.

**Answer:** It can be supplied through local name-resolution configuration rather than requiring an external DNS query.

# 13. Hands-On Task 3 — Inspect `/etc/resolv.conf`

The file:

```text
/etc/resolv.conf
```

is an important part of traditional Linux DNS resolver configuration.

Run:

```bash
cat /etc/resolv.conf
```

On an Ubuntu system using `systemd-resolved`, you may see something resembling:

```text
nameserver 127.0.0.53

options edns0 trust-ad

search .
```

Your actual configuration may differ.

## 13.1 Understand `nameserver`

The `nameserver` directive identifies a DNS server address used by traditional resolver clients reading this configuration.

Example:

```text
nameserver 127.0.0.53
```

The address `127.0.0.53` is commonly associated with the local `systemd-resolved` DNS stub listener.

It is a loopback address.

It does not mean that the organization's upstream DNS server is necessarily `127.0.0.53`.

## 13.2 Understand `search`

A search directive can influence how certain relative names are expanded during resolution.

For example:

```text
search production.example.com
```

A lookup for:

```text
database
```

may be attempted using the configured search-domain behavior.

Do not assume all applications process search domains identically.

## 13.3 Understand `options`

The `options` directive supplies resolver-related configuration options.

For example:

```text
options edns0 trust-ad
```

These options relate to DNS resolver behavior.

You are not expected to administer them in this lab.

## 13.4 Is `/etc/resolv.conf` always a normal file?

No.

On systems using `systemd-resolved`, it may be a symbolic link to a managed resolver configuration file.

Inspect it with:

```bash
ls -l /etc/resolv.conf
```

Representative output:

```text
/etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf
```

This is illustrative.

The actual link target may differ, and some systems use a regular file.

### Engineering principle

Do not overwrite `/etc/resolv.conf` merely because it contains a loopback nameserver.

First determine which component manages DNS configuration on the host.

# 14. Understand `systemd-resolved` on Ubuntu

Ubuntu Server commonly uses `systemd-resolved` as part of its name-resolution architecture.

It can provide services such as:

- DNS query handling.
- DNS caching.
- Per-link DNS configuration.
- Search-domain handling.
- A local DNS stub listener.
- Integration with supported system name-resolution interfaces.

Its exact behavior depends on system configuration.

## 14.1 Conceptual architecture

```text
                  APPLICATION
                       |
                       v
               NAME-RESOLUTION API
                       |
                       v
              SYSTEM RESOLVER PATH
                       |
                       v
                systemd-resolved
                       |
             +---------+---------+
             |                   |
             v                   v
          CACHE             DNS SETTINGS
                                 |
                                 v
                         UPSTREAM RESOLVER
                                 |
                                 v
                             DNS ANSWER
```

This is a conceptual model.

The actual path differs depending on whether an application uses NSS, the local DNS stub, another DNS client library, or its own resolver.

## 14.2 Why `127.0.0.53` appears

On a common Ubuntu configuration:

```text
nameserver 127.0.0.53
```

means that traditional DNS clients using the stub configuration send DNS requests to a local resolver listener.

That local resolver then handles the request according to its configured DNS environment.

### Important distinction

```text
Local stub address
        ≠
Upstream DNS server address
```

You must inspect the resolver's actual configuration before concluding which upstream DNS servers are in use.

# 18. Understand Common DNS Response Outcomes

A DNS query does not always return the requested address.

Different outcomes can indicate different conditions.

## 18.1 Successful response

A successful response may contain the requested resource records.

Example:

```text
Name: app.example.com

Type: A

Answer: 192.0.2.20
```

## 18.2 NXDOMAIN

`NXDOMAIN` indicates that the queried DNS name does not exist according to the applicable DNS response.

It does not mean that every DNS server in the world is unreachable.

## 18.3 NOERROR with no requested answer

A query can succeed at the DNS protocol level while returning no record of the requested type.

For example, a name may exist but have no A record.

This is different from concluding that the name itself does not exist.

## 18.4 SERVFAIL

`SERVFAIL` indicates that the DNS server was unable to complete the request successfully.

Potential underlying causes require further investigation.

Do not automatically assume that the queried hostname is invalid.

## 18.5 REFUSED

`REFUSED` indicates that the DNS server refused to perform the requested operation.

This may reflect server policy or configuration.

## 18.6 Timeout

A timeout means that the client did not receive an acceptable response within the relevant time window.

Possible causes can include:

- Network connectivity problems.
- Resolver unavailability.
- Filtering.
- Packet loss.
- Incorrect resolver configuration.
- Other infrastructure failures.

A timeout is not equivalent to NXDOMAIN.

### Response comparison

| Outcome | Basic interpretation |
|---|---|
| Successful answer | Requested information was returned |
| NXDOMAIN | Queried DNS name does not exist according to the response |
| NOERROR without requested record | The query completed without the requested answer |
| SERVFAIL | Server could not successfully complete the query |
| REFUSED | Server refused the operation |
| Timeout | No acceptable response was received in time |

These distinctions become central in JUN-050.

# 19. Understand DNS Transport at a Foundational Level

DNS commonly uses:

```text
UDP port 53

TCP port 53
```

Modern DNS environments can also support encrypted transport mechanisms, such as DNS over TLS and DNS over HTTPS, depending on client and server configuration.

You do not need to configure these mechanisms in JUN-049.

## 19.1 Why both UDP and TCP?

Traditional DNS commonly uses UDP for many queries.

TCP is also an established DNS transport and is important for situations such as:

- Responses requiring TCP.
- Certain larger exchanges.
- Zone transfers between appropriately configured DNS servers.
- Other supported DNS operations.

Do not assume DNS always uses UDP.

## 19.2 DNS query versus application connection

Consider:

```text
Application needs api.example.com
             |
             v
        DNS resolution
             |
             v
       Receives IP address
             |
             v
      Application connection
```

The application may subsequently use an entirely different destination port and transport protocol.

For example, an HTTPS application commonly uses TCP port 443, with other supported transport arrangements possible.

DNS port 53 is not the destination port for every application that relies on DNS.

# 20. Ten Common DNS Misconceptions

Before moving into the incident exercise, review these mistakes.

### Misconception 1 — DNS and routing are the same thing

Incorrect.

DNS resolves naming information. Routing determines network paths.

### Misconception 2 — A valid default gateway guarantees DNS resolution

Incorrect.

The resolver may be unavailable, incorrectly configured, or unable to resolve the requested name.

### Misconception 3 — `/etc/resolv.conf` always contains the actual upstream DNS server

Incorrect.

It may contain a local stub resolver address.

### Misconception 4 — `127.0.0.53` is automatically a configuration error

Incorrect.

It is commonly associated with the local `systemd-resolved` stub listener.

### Misconception 5 — `getent` and `dig` always use identical lookup paths

Incorrect.

They use different resolution interfaces and may produce different results.

### Misconception 6 — Every hostname must exist in public DNS

Incorrect.

Organizations commonly use private DNS namespaces and local naming arrangements.

### Misconception 7 — A successful DNS lookup proves the application is available

Incorrect.

DNS resolution does not independently verify routing, firewall permissions, transport connectivity, or application health.

### Misconception 8 — NXDOMAIN and timeout mean the same thing

Incorrect.

They represent different failure conditions.

### Misconception 9 — DNS changes become visible everywhere immediately

Incorrect.

Caching and TTL behavior can delay when different clients observe updated information.

### Misconception 10 — Restarting the resolver is always the correct first troubleshooting action

Incorrect.

Inspect the configuration and preserve useful evidence before considering an authorized change.

# 21. Controlled Failure Lab — The Wrong DNS Resolver

You will now investigate a simulated production DNS incident.

This is a controlled evidence-analysis exercise.

Do not change your actual resolver configuration.

## 21.1 Approved architecture

The organization operates a private DNS namespace:

```text
internal.example
```

The application server uses:

```text
10.20.10.25/24
```

Its approved resolver is:

```text
10.20.10.53
```

The private database name is:

```text
database.internal.example
```

The expected database address is:

```text
10.20.20.30
```

Conceptual architecture:

```text
                  APPLICATION SERVER
                     10.20.10.25
                           |
                           |
                    NAME RESOLUTION
                           |
                           v
                    INTERNAL RESOLVER
                     10.20.10.53
                           |
                           v
                database.internal.example
                           |
                           v
                       10.20.20.30
                           |
                           v
                    ROUTING DECISION
                           |
                           v
                     DATABASE SERVER
```

## 21.2 Symptom

The application reports:

```text
Unable to resolve database.internal.example
```

The application team initially suspects a network outage.

## 21.3 Impact

Database-dependent application functionality is unavailable because the application cannot obtain the expected database address through its configured name-resolution path.

## 21.4 Evidence A — Interface configuration

The interface reports:

```text
ens3: UP
```

The IPv4 address is:

```text
10.20.10.25/24
```

This matches the approved addressing baseline.

## 21.5 Evidence B — Routing configuration

The routing table contains the expected routes for the environment.

The engineer performs a lookup for the known database IP:

```bash
ip -4 route get 10.20.20.30
```

The supplied incident evidence shows that Linux selects the approved network path.

This does not independently prove database connectivity, but it reduces support for the hypothesis that a missing route is the immediate cause of the hostname-resolution failure.

## 21.6 Evidence C — Name-resolution failure

The engineer runs:

```bash
getent ahostsv4 database.internal.example
```

The command returns no address information and exits unsuccessfully.

## 21.7 Evidence D — Resolver configuration

The engineer inspects:

```bash
resolvectl dns
```

The supplied output is:

```text
Link 2 (ens3): 192.0.2.53
```

However, the approved internal resolver is:

```text
10.20.10.53
```

The observed resolver differs from the approved baseline.

For this simulated case, `192.0.2.53` represents an incorrectly supplied resolver that does not serve the organization's private DNS data.

## 21.8 Form the hypothesis

The application server is using an incorrect DNS resolver.

Because the configured resolver does not provide the private organization's DNS records, the application cannot resolve the internal database hostname.

## 21.9 Test the hypothesis

The engineer compares:

```text
Expected resolver:
10.20.10.53
```

with:

```text
Observed resolver:
192.0.2.53
```

The configuration deployment record confirms that the incorrect resolver address was introduced during a network-configuration update.

An authorized investigation also verifies that the approved internal resolver can return the expected record for the database name.

The evidence supports the resolver-configuration hypothesis.

## 21.10 Root cause

The confirmed root cause is an incorrect DNS resolver address introduced during configuration deployment.

The application server was no longer using the approved internal name-resolution infrastructure.

## 21.11 Corrective action

The authorized infrastructure engineer restores the approved resolver through the environment's persistent network-management configuration.

The correction is reviewed before application.

Do not manually overwrite `/etc/resolv.conf` as an assumed permanent fix.

On a managed Ubuntu system, DNS settings may originate from Netplan, DHCP, cloud-init, network-management services, or other infrastructure automation.

The actual configuration owner must be identified.

## 21.12 Recovery verification

After the approved correction, the engineer checks:

```bash
resolvectl dns
```

The expected resolver appears:

```text
10.20.10.53
```

The engineer repeats:

```bash
getent ahostsv4 database.internal.example
```

In the simulated recovery, the expected address is returned:

```text
10.20.20.30
```

The engineer also verifies that the application can complete its original database operation.

This final step matters.

A successful DNS lookup alone does not prove that the application has fully recovered.

## 21.13 Prevention

Recommended controls include:

- Version-controlled network configuration.
- Approved resolver baselines.
- Configuration review before deployment.
- Validation of internal DNS records after network changes.
- Monitoring for unexpected resolver changes.
- Documented ownership of DNS configuration.
- Application-level recovery verification.


# 25. Interview Preparation — 10 Questions with Worked Answers

## Interview Question 1 — Explain DNS to a junior engineer.

DNS is a distributed naming system that allows clients to retrieve records associated with domain names.

One common use is resolving a hostname into an IPv4 or IPv6 address.

Applications can then use that address when establishing network communication.

DNS does not replace routing or guarantee that the destination application is available.

## Interview Question 2 — What happens when an application resolves a hostname?

The application uses an appropriate name-resolution interface.

Depending on the environment, the lookup may involve local files, NSS modules, a local resolver, cached information, and recursive DNS infrastructure.

The resulting address information can then be used by the application.

The exact sequence depends on the application's resolver implementation and system configuration.

## Interview Question 3 — What is the difference between a recursive resolver and an authoritative server?

A recursive resolver obtains DNS answers for clients.

An authoritative server provides authoritative DNS data for the zones it serves.

A recursive resolver may contact multiple DNS servers to complete a request when a suitable cached answer is unavailable.

## Interview Question 4 — What is the difference between A and AAAA records?

An A record contains an IPv4 address.

An AAAA record contains an IPv6 address.

## Interview Question 5 — What is `/etc/hosts` used for?

It provides local static hostname-to-address mappings.

Depending on the configured name-resolution policy, these mappings can participate in hostname resolution without requiring an external DNS query.

## Interview Question 6 — Why does Ubuntu sometimes show `127.0.0.53` in `/etc/resolv.conf`?

Ubuntu commonly uses `systemd-resolved`.

The address `127.0.0.53` can represent its local DNS stub listener.

It does not necessarily identify the actual upstream DNS server.

I would inspect the resolver configuration using:

```bash
resolvectl status
```

and:

```bash
resolvectl dns
```

## Interview Question 7 — What is the difference between `getent` and `dig`?

`getent` uses the configured system name-service mechanisms for the requested database.

`dig` is a DNS query utility.

Therefore, `getent` may return information from sources such as `/etc/hosts`, while `dig` performs DNS queries rather than reproducing the complete NSS lookup process.

## Interview Question 8 — What does DNS TTL control?

TTL influences how long DNS information may be retained by caching resolvers under applicable caching rules.

It is important when planning DNS changes and investigating stale responses.

## Interview Question 9 — An application cannot resolve an internal hostname. What would you inspect first?

I would identify the exact failing name, inspect NSS policy, check local hostname mappings, inspect the resolver configuration, identify the active DNS servers, and perform a controlled lookup.

I would compare the observed configuration with the approved internal DNS design before making changes.

## Interview Question 10 — Can a server have correct routing and still experience DNS failure?

Yes.

Routing and DNS are separate components.

A server may have valid interfaces, addresses, and routes while using an unavailable or incorrect DNS resolver.
