# 2. What a Filesystem Actually Does

A storage device provides somewhere to store data.

A filesystem provides a structured way to organize and locate that data.

Conceptually, imagine raw storage as:

```text
+--------------------------------------------------+
|                                                  |
|                 STORAGE SPACE                    |
|                                                  |
+--------------------------------------------------+
```

A filesystem adds structures that allow Linux to represent things such as:

```text
/
├── etc/
│   ├── hosts
│   └── passwd
├── home/
│   └── user/
├── var/
│   └── log/
└── tmp/
```

The filesystem must track information such as:

```text
Where is this file's data?

What is its name?

Which directory contains it?

Who owns it?

What permissions apply?

How large is it?

When was it modified?

Which storage blocks belong to it?

Which metadata object represents it?
```

You have already interacted with these filesystem features throughout Linux World.

When you ran:

```bash
ls -l
```

you inspected filesystem metadata.

When you changed:

```text
permissions
ownership
```

you changed filesystem metadata.

When you created:

```text
hard links
```

you interacted with filesystem naming and inode relationships.

When you used:

```bash
du
```

you measured allocated usage associated with filesystem objects.

When you used:

```bash
df
```

you inspected filesystem capacity.

So filesystems are not a new topic in the sense that you have never used one.

This lab makes the underlying model explicit.

# 3. Keep the Storage Layers Separate

Suppose a machine has:

```text
/dev/nvme0n1
```

with:

```text
/dev/nvme0n1p2
```

containing:

```text
ext4
```

mounted at:

```text
/
```

These are four different things.

## Block device

```text
/dev/nvme0n1
```

represents the disk-like block device.

---

## Partition

```text
/dev/nvme0n1p2
```

represents a defined region of that device.

---

## Filesystem

```text
ext4
```

describes the filesystem format/implementation used to organize data on the relevant storage object.

---

## Mount point

```text
/
```

is the location in the Linux directory hierarchy where that filesystem is accessible.

The relationship might be:

```text
/dev/nvme0n1
       │
       ▼
/dev/nvme0n1p2
       │
       ▼
      ext4
       │
       ▼
       /
```

But this is not the only possible design.

A filesystem can also exist on:

```text
whole block device
logical volume
encrypted mapping
RAID device
loop device
other block-storage abstraction
```

Therefore, do not define a filesystem as:

> something that always lives inside a partition.

A better model is:

> A filesystem organizes data on an appropriate storage object.

### Lock these distinctions in

```text
DISK
≠
PARTITION
```

```text
PARTITION
≠
FILESYSTEM
```

```text
FILESYSTEM
≠
MOUNT POINT
```

```text
FILESYSTEM
≠
DIRECTORY
```

```text
FILESYSTEM TYPE
≠
DEVICE NAME
```

# 5. Inspect Filesystems with `lsblk -f`

Run:

```bash
lsblk -f
```

This provides filesystem-oriented information for block-device topology.

Depending on your system, you may see columns including:

```text
NAME
FSTYPE
FSVER
LABEL
UUID
FSAVAIL
FSUSE%
MOUNTPOINTS
```

Your environment may show fewer or additional fields.

## `NAME`

This identifies the block-device object.

Examples:

```text
sda1
nvme0n1p2
vda1
```

---

## `FSTYPE`

This identifies detected filesystem or storage-content type.

Examples might include:

```text
ext4
xfs
vfat
swap
```

You may also encounter types associated with other storage layers.

A blank `FSTYPE` does not automatically mean the device is broken or unused.

It could be:

- a parent disk;
- unformatted storage;
- part of another storage layer;
- a device whose content is not exposed as a normal filesystem at that level.

---

## `FSVER`

Where available, this reports filesystem version information.

Do not expect every filesystem type to expose a meaningful value here.

---

## `LABEL`

A filesystem can have a human-readable label.

Examples might conceptually be:

```text
ROOT
DATA
BACKUP
```

A label can make administration easier, but labels should not automatically be assumed unique.

---

## `UUID`

A filesystem UUID identifies the filesystem.

It may resemble:

```text
xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
```

The exact format varies by filesystem.

Do not memorize UUIDs.

Understand their purpose.

---

## `FSAVAIL`

Where reported, this indicates available filesystem capacity.

---

## `FSUSE%`

Where reported, this represents filesystem capacity usage.

---

## `MOUNTPOINTS`

This shows locations where the filesystem is currently mounted.

You will study mounting itself in JUN-040.

For now, use this field only to understand the relationship.

# 6. Recognize Common Filesystem Types

Linux can work with many filesystem types.

You do not need to master all of them in one junior lab.

You do need to recognize several names and understand that filesystem choice can depend on operating system, workload, boot requirements, interoperability, and platform design.

## ext4

You may encounter:

```text
ext4
```

ext4 is a widely used general-purpose Linux filesystem.

It supports standard Linux filesystem capabilities such as:

- directories;
- regular files;
- permissions;
- ownership;
- links;
- timestamps;
- journaling;
- large files and filesystems.

For this lab, the important point is:

```text
ext4
→ common Linux filesystem
```

You do not need to study ext4 internals yet.

---

## XFS

You may encounter:

```text
xfs
```

XFS is another mature, widely deployed Linux filesystem, particularly common in enterprise and large-storage environments.

At junior level:

```text
XFS
→ Linux filesystem
```

Do not treat:

```text
ext4
```

and:

```text
xfs
```

as merely different names for the same implementation.

They have different designs, tools, features, and operational characteristics.

---

## VFAT/FAT

You may encounter:

```text
vfat
```

particularly around an EFI System Partition.

For example, a UEFI system may expose:

```text
/boot/efi
```

on a FAT-family filesystem.

Do not conclude:

> Linux only uses ext4.

Linux systems often use multiple filesystem types simultaneously.

---

## tmpfs

Run:

```bash
df -hT
```

You may see:

```text
tmpfs
```

`tmpfs` is important because it demonstrates that not every mounted filesystem maps directly to a disk partition.

It is memory-backed storage managed by the kernel and can use memory and swap according to system behavior.

Conceptually:

```text
tmpfs
   │
   ▼
memory-backed filesystem
```

rather than:

```text
disk
 ↓
partition
 ↓
filesystem
```

This is why the storage model must remain flexible.

---

## Other filesystems

Depending on the environment, you may encounter names such as:

```text
btrfs
overlay
squashfs
iso9660
NFS
```

or others.

You are not expected to administer them in JUN-039.

The correct response to an unfamiliar filesystem type is:

```text
identify it
determine its role
understand the environment
avoid unsupported assumptions
```

# 7. Disk-Backed vs Virtual and Memory-Backed Filesystems

Run:

```bash
df -hT
```

You may notice entries that do not look like:

```text
/dev/sda1
```

or:

```text
/dev/nvme0n1p2
```

Examples can include:

```text
tmpfs
```

or other virtual filesystem sources.

This is important.

Not every filesystem shown by Linux represents a normal disk partition.

Conceptually:

```text
FILESYSTEMS
    │
    ├── block-storage backed
    │      │
    │      ├── ext4
    │      ├── xfs
    │      └── others
    │
    └── virtual / memory-backed / network-backed
           │
           ├── tmpfs
           └── other types
```

### Why this matters during troubleshooting

Suppose someone says:

> `/run` is almost full.

You should not immediately search for:

```text
/dev/sdX
```

First determine what filesystem actually backs `/run`.

Use:

```bash
df -hT /run
```

and:

```bash
findmnt -T /run
```

The correct investigation begins with evidence, not an assumption that every path maps to a physical partition.

# 9. Understand Filesystem UUIDs and Labels

Run:

```bash
lsblk -f
```

Locate any visible:

```text
UUID
```

and:

```text
LABEL
```

fields.

## UUID

A filesystem UUID provides an identifier associated with the filesystem.

This can be useful because device names such as:

```text
/dev/sdb1
```

describe the current device node.

A filesystem UUID identifies the filesystem independently of relying solely on that device name.

Conceptually:

```text
DEVICE NODE
/dev/sdb1
```

versus:

```text
FILESYSTEM IDENTITY
UUID=...
```

You will use this distinction more heavily when studying persistent mount configuration in JUN-041.

---

## Label

A label is a human-readable identifier assigned to a filesystem.

For example:

```text
LABEL=BACKUP
```

is easier for a human to interpret than a long UUID.

However:

```text
human-readable
```

does not automatically mean:

```text
globally unique
```

Do not assume labels are unique unless that is controlled by your environment.


```text

```

### Distinguish the layers

If you see:


```text

```

A useful model is:

```text
PARTITION
   │
   └── PARTUUID
```

and:



```text

```

```text

```

No single command should replace your understanding of the storage layers.

# 11. Connect Filesystems to Capacity

You already learned `df` in JUN-035.

Now connect it explicitly to filesystem structure.

Run:

```bash
df -hT ~/linux-world-labs/JUN-039
```

Suppose the result conceptually contains:

```text
Filesystem   Type   Size   Used   Avail   Use%   Mounted on
SOURCE       ext4   ...    ...    ...     ...    /
```

The important idea is:

```text
df
→ filesystem-level capacity
```

It is not reporting:

```text
raw disk free space
```

and it is not reporting:

```text
partition-table free space
```

These are different concepts.

### Example storage chain

```text
DISK
100 GiB
   │
   ▼
PARTITION
99 GiB
   │
   ▼
FILESYSTEM
reports its own capacity
   │
   ▼
MOUNT POINT
/
```

Do not expect every number to be identical.

### Why filesystem capacity can differ

A filesystem requires internal structures and metadata.

Depending on filesystem type and configuration, storage can be used for things such as:

```text
metadata
allocation structures
journaling structures
reserved space
filesystem bookkeeping
```

Therefore:

```text
PARTITION SIZE
≠
FILESYSTEM USABLE CAPACITY
```

# 12. Connect Filesystems to Inodes

You first encountered inode capacity in JUN-035 and inode identity in earlier file/link labs.

Now connect the concept directly to the filesystem.

Run:

```bash
df -i ~/linux-world-labs/JUN-039
```

You may see:

```text
Inodes
IUsed
IFree
IUse%
```

For filesystems that expose inode counts this way, these values represent filesystem metadata capacity for file objects.

Conceptually:

```text
FILESYSTEM CAPACITY
      │
      ├── storage blocks
      │      ↓
      │   df -h
      │
      └── inode capacity
             ↓
          df -i
```

A filesystem can therefore encounter different capacity pressures.

### Block exhaustion

Conceptually:

```text
Use%
≈ 100%
```

The filesystem has little block capacity available.

### Inode exhaustion

Conceptually:

```text
IUse%
≈ 100%
```

The filesystem has little inode capacity available, where that filesystem exposes a finite inode pool in this manner.

This can happen even if block capacity remains.

### Why small files matter

A workload creating enormous numbers of tiny files can consume inode capacity faster than block capacity.

Therefore:

```text
FILESYSTEM FULL
```

should trigger at least two questions:

```text
Are blocks exhausted?

Are inodes exhausted?
```

Check:

```bash
df -h PATH
```

and:

```bash
df -i PATH
```

# 14. Understand Filesystem Signatures

When a filesystem is created on a storage object, recognizable metadata structures are written to that storage.

Tools can use these structures to identify the content.

Conceptually:

```text
BLOCK DEVICE
      │
      ▼
filesystem metadata/signature
      │
      ▼
identification tools
```

This is why commands such as:

```text
lsblk -f
```

and:

```text
blkid
```

can often report:

```text
TYPE=ext4
UUID=...
```

### Important safety implication

A block device that already contains a recognizable filesystem signature may contain valuable data.

Never respond to:

```text
existing filesystem detected
```

by thinking:

> I can just create a new filesystem over it.

Creating a new filesystem can overwrite critical filesystem structures and make existing data inaccessible.

That is why:

```text
mkfs
```

commands are excluded from this lab.

### Another important rule

A missing filesystem signature does not automatically mean:

```text
safe to format
```

The device may belong to:

- LVM;
- encryption;
- RAID;
- another storage format;
- an application using raw block storage;
- an unrecognized storage system.

Absence of one kind of metadata is not permission to overwrite storage.

# 15. Filesystem Type Does Not Define the Entire Storage Architecture

Suppose:

```bash
df -T /srv/app
```

reports:

```text
xfs
```

You now know the filesystem type.

You still do not automatically know:

- whether it sits on a partition;
- whether LVM is underneath it;
- whether encryption is involved;
- which physical disk ultimately backs it;
- whether multiple storage devices participate;
- how the filesystem is persistently configured.

For topology, continue with:

```bash
lsblk -f
```

and:

```bash
findmnt -T /srv/app
```

This produces a better reasoning model:

```text
PATH
 │
 ▼
FILESYSTEM
 │
 ▼
FILESYSTEM SOURCE
 │
 ▼
BLOCK-DEVICE TOPOLOGY
```

rather than:

```text
I saw ext4, therefore I know the whole storage architecture.
```

You do not.

# 16. Controlled Troubleshooting: Avoid Filesystem Misdiagnosis

## Mistake 1 — Calling ext4 a partition

Incorrect:

```text
ext4 is my partition.
```

Better:

```text
ext4 is the filesystem type.
```

The partition might be:

```text
/dev/sda2
```

if a partition is involved.

---

## Mistake 2 — Calling `/` a filesystem type

Incorrect:

```text
My filesystem is /.
```

Better:

```text
/ is the mount point.
```

The filesystem type might be:

```text
ext4
xfs
```

or something else.

---

## Mistake 3 — Assuming every filesystem is ext4

Linux supports many filesystem types.

Always inspect:

```bash
df -T PATH
```

or:

```bash
findmnt -T PATH
```

instead of assuming.

---

## Mistake 4 — Assuming every filesystem is disk-backed

A path may live on:

```text
tmpfs
```

or another nontraditional filesystem.

Start from the path and inspect it.

---

## Mistake 5 — Confusing device capacity with filesystem capacity

This:

```bash
lsblk
```

shows block-device sizes.

This:

```bash
df -h
```

shows filesystem capacity.

They are related but not interchangeable.

---

## Mistake 6 — Looking only at block capacity

A filesystem can encounter inode pressure even when storage blocks remain.

Check:

```bash
df -h PATH
```

and:

```bash
df -i PATH
```

when investigating filesystem capacity.

---

## Mistake 7 — Assuming a blank `FSTYPE` means unused

A blank filesystem-type field does not prove the device is unused.

Investigate the storage topology before making changes.

---

## Mistake 8 — Assuming an existing filesystem is safe to reformat

Formatting is destructive to the existing filesystem structures.

Never run:

```text
mkfs.*
```

against a device merely because you think its current contents are unnecessary.

Positive device identification and explicit authorization are required.

# 17. Build a Filesystem Investigation Workflow

Suppose an application reports:

> No space left on device.

Do not immediately delete files or modify disks.

Use evidence.

### Step 1 — Start from the failing path

Example:

```text
/srv/application/data
```

### Step 2 — Identify its filesystem

```bash
df -hT /srv/application/data
```

Record:

```text
SOURCE:
FSTYPE:
SIZE:
AVAILABLE:
USE%:
MOUNT POINT:
```

### Step 3 — Check inode capacity

```bash
df -i /srv/application/data
```

Ask:

```text
block pressure?

inode pressure?

both?

neither?
```

### Step 4 — Confirm the mount relationship

```bash
findmnt -T /srv/application/data
```

Record:

```text
SOURCE:
TARGET:
FSTYPE:
```

### Step 5 — Inspect underlying topology where relevant

```bash
lsblk -f
```

Determine whether the filesystem source is:

```text
partition
logical/mapped device
whole device
other storage
```

### Step 6 — If block capacity is the problem, investigate usage

From JUN-036:

```bash
du -xh --max-depth=1 /relevant/scope | sort -hr
```

Do not run broad scans blindly.

### Step 7 — State the evidence

A good junior-level incident note might read:

```text
The failing path is on an ext4 filesystem mounted at /srv.
The filesystem is 94% used by block capacity.
Inode utilization is 18%.
The issue therefore appears related to block capacity rather
than inode exhaustion. Further directory-level investigation
is required before remediation.
```

That is better than:

```text
The disk is full.
```

The second statement collapses several storage layers and may be wrong.

# 19. Knowledge Check and Interview Practice

## Knowledge Check

1. **What is a filesystem?**  
   A structure and set of rules used to organize, identify, store, retrieve, and track files, directories, and associated metadata on storage.

2. **Is a filesystem the same thing as a disk?**  
   No. A disk is a block-storage device. A filesystem is a data-organization layer that can exist on an appropriate storage object.

3. **Is a filesystem the same thing as a partition?**  
   No. A partition defines a region of a block device; a filesystem can organize data within a partition or another suitable storage object.

4. **Is a filesystem the same thing as a mount point?**  
   No. A mount point is the location in the directory hierarchy where a mounted filesystem becomes accessible.

5. **What does `df -T` show?**  
   Filesystem capacity information together with the filesystem type.

6. **What does `lsblk -f` provide?**  
   Block-device topology with filesystem-oriented information such as type, label, UUID, and mount information where available.

7. **What is a filesystem UUID?**  
   An identifier associated with a filesystem that can be used to identify it without relying solely on the current device-node name.

8. **What is a filesystem label?**  
   A human-readable name that can be assigned to a filesystem.

9. **What is the difference between UUID and PARTUUID?**  
   UUID commonly identifies the filesystem; PARTUUID identifies a partition entry.

10. **Why can filesystem capacity differ from partition size?**  
    Filesystems use space for internal metadata and structures, and the tools report different storage layers.

11. **What does `df -i` inspect?**  
    Filesystem inode capacity and usage where the filesystem exposes inode counts in that model.

12. **Can a filesystem run out of inodes while block space remains?**  
    Yes, on filesystems with a finite inode pool. A workload containing very large numbers of small files can cause this.

13. **Does every filesystem come from a normal disk partition?**  
    No. Filesystems can be backed by logical devices, memory, network storage, loop devices, and other storage mechanisms.

14. **What is `tmpfs`?**  
    A memory-backed filesystem managed by the kernel rather than a normal disk-backed filesystem.

15. **Does a missing `FSTYPE` prove a device is safe to format?**  
    No. The device may belong to another storage layer or contain data not represented as a directly detected filesystem.

## Interview Practice

### What is the difference between a partition and a filesystem?

A partition defines a region of a block device. A filesystem provides the structures used to organize files, directories, metadata, allocation, and related information on storage.

---

### How would you determine the filesystem type used by `/var`?

I would use:

```bash
df -T /var
```

or:

```bash
findmnt -T /var
```

rather than assuming it is the same filesystem as `/`.

---

### How would you identify filesystem UUIDs on Linux?

I would normally begin with:

```bash
lsblk -f
```

and, where appropriate and accessible:

```bash
blkid
```

---

### What is the difference between `lsblk -f` and `df -hT`?

`lsblk -f` shows filesystem information in the context of block-device topology. `df -hT` shows capacity and usage information for mounted filesystems and includes their filesystem types.

---

### Why might `df -h` show free capacity while an application still receives `No space left on device`?

One possibility is inode exhaustion rather than block exhaustion. I would inspect:

```bash
df -i /affected/path
```

I would also avoid assuming that inode exhaustion is the only possible cause without additional evidence.

---

### Is ext4 the only Linux filesystem?

No. Linux supports many filesystems, including XFS, Btrfs, FAT-family filesystems, tmpfs, network filesystems, and others.

---

### Why is formatting an existing filesystem dangerous?

Creating a new filesystem writes filesystem structures to the target storage and can overwrite metadata required to access the existing data. The exact target and its purpose must be verified before formatting.

---

### How would you investigate the storage behind an application path?

I would begin with the path itself:

```bash
df -hT /path
```

then:

```bash
df -i /path
```

and:

```bash
findmnt -T /path
```

If I need the underlying block-storage relationship, I would then inspect:

```bash
lsblk -f
```

This keeps the investigation evidence-driven from the application path down through the storage layers.
