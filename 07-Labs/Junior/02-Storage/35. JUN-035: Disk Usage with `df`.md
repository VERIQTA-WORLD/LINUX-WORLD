## 1. Mission: Determine Whether a Filesystem Is Running Out of Capacity

A Linux system can fail even when the application itself is healthy.

One common reason is filesystem capacity.

Applications may need disk space to:

- write logs;
- create temporary files;
- store uploaded data;
- write database files;
- unpack deployments;
- create package caches;
- generate reports;
- store backups;
- rotate logs;
- write runtime state.

When a filesystem becomes full, you may see symptoms such as:

```text
No space left on device
```

or applications that:

- cannot create files;
- cannot append to logs;
- cannot complete deployments;
- cannot write temporary data;
- fail during package operations;
- stop accepting new data.

The first question is often:

> Which filesystem is full?

One of the primary Linux tools for answering that question is:

```bash
df
```

The name is traditionally understood as:

```text
disk free
```

But `df` gives you more than a single "free space" number.

It reports filesystem-level capacity information.

A useful model is:

```text
STORAGE DEVICE / VOLUME
        │
        ▼
    FILESYSTEM
        │
        ▼
    MOUNT POINT
        │
        ▼
DIRECTORIES AND FILES
```

`df` operates mainly at the **filesystem capacity** level.

It helps answer questions such as:

- Which filesystems are mounted?
- How much capacity does each filesystem report?
- How much is used?
- How much is available?
- What percentage is used?
- Where is each filesystem mounted?
- What filesystem type is involved?
- Is block capacity exhausted?
- Is inode capacity exhausted?
- Which filesystem contains a particular path?

### The central boundary

Keep this distinction clear throughout the lab:

```text
df
→ filesystem-level capacity
```

JUN-036 will introduce:

```text
du
→ space attributed to files/directories
```

Do not use `du` in this lab.

Your job today is to understand `df` deeply enough that when someone says:

> The disk is full.

you know that statement is incomplete.

You should ask:

> Which filesystem, which capacity resource, and what evidence proves it?

### Learning objectives

By the end of this lab, you should be able to:

- explain what `df` reports;
- run a basic filesystem-capacity check;
- interpret `Size`, `Used`, `Avail`, `Use%`, and mount-point information;
- use `df -h`;
- understand why `df -H` differs from `df -h`;
- inspect filesystem types with `df -T`;
- combine useful options;
- query the filesystem containing a specific path;
- distinguish a device/filesystem identifier from a mount point;
- understand that multiple paths can belong to the same filesystem;
- inspect inode capacity with `df -i`;
- distinguish block exhaustion from inode exhaustion;
- interpret pseudo-filesystems and memory-backed filesystems cautiously;
- understand why `100%` or near-`100%` requires context;
- recognize that `df` does not identify which directory consumed the space;
- build a safe first-response workflow for filesystem-capacity incidents.

### Lab boundary

This lab does **not** teach:

- `du`;
- partition creation;
- filesystem creation;
- mounting filesystems;
- `/etc/fstab`;
- LVM;
- RAID;
- filesystem expansion;
- filesystem repair;
- deleting production data;
- log rotation;
- inode repair.

Those topics appear later.

Today you investigate capacity.

You do not redesign storage.

## 3. Read Basic `df` Output Correctly

Run:

```bash
df
```

Your output depends on your environment.

A typical structure resembles:

```text
Filesystem     1K-blocks      Used Available Use% Mounted on
...
```

Do not memorize example numbers.

Interpret the columns.

### `Filesystem`

This identifies the filesystem's backing resource as reported by the system.

Depending on the environment, you may see entries resembling:

```text
/dev/sda2
/dev/nvme0n1p2
/dev/mapper/...
tmpfs
overlay
```

Containers, cloud systems, virtual machines, WSL, and traditional servers can look different.

Do not assume every Linux machine uses:

```text
/dev/sda1
```

### `1K-blocks`

In default output, GNU `df` commonly reports capacity in block-oriented units, often displayed under a heading such as:

```text
1K-blocks
```

The raw values are useful to software and precise inspection, but they are not always the easiest format for a human to scan quickly.

You will solve that shortly with:

```text
-h
```

### `Used`

This reports used filesystem block capacity according to the filesystem information available to `df`.

Do not interpret it as:

> the size of the directory I am currently standing in.

It describes the filesystem, not the current directory alone.

### `Available`

This reports capacity available for allocation under the filesystem's rules.

You may notice that simplistic arithmetic such as:

```text
Size - Used = Available
```

does not always match exactly.

Filesystem accounting can include reserved blocks, metadata, rounding, and filesystem-specific behavior.

Do not "correct" `df` using simplistic subtraction.

### `Use%`

This is the reported percentage of filesystem capacity in use.

For example:

```text
Use%
73%
```

means the filesystem is reporting substantial use of the measured block capacity.

It does **not** automatically mean:

- the server is unhealthy;
- an outage is imminent;
- files should be deleted;
- 27% is available to every user in every circumstance.

Interpret the number with the rest of the evidence.

### `Mounted on`

This tells you where the filesystem is attached to the directory hierarchy.

Examples might include:

```text
/
```

```text
/boot
```

```text
/home
```

A mount point is where a filesystem becomes accessible in the Linux directory tree.

You will study mounting in depth later.

For now, recognize:

```text
filesystem
      │
      ▼
mount point
      │
      ▼
paths beneath that point
```

## 4. Make the Output Human-Readable

Run:

```bash
df -h
```

The:

```text
-h
```

option produces human-readable sizes using powers of 1024.

Instead of a large block count, you may see units such as:

```text
K
M
G
T
```

A typical shape might resemble:

```text
Filesystem      Size  Used Avail Use% Mounted on
...
```

Again, your actual values and filesystems will differ.

### Why `df -h` is useful

During an incident, compare:

```text
104857600
```

with:

```text
100G
```

The second is usually easier for a human to interpret quickly.

For interactive investigation:

```bash
df -h
```

is therefore a common first command.

### But human-readable does not mean more accurate

`-h` changes presentation.

It does not create a different filesystem state.

Think:

```text
same filesystem data
        │
        ├── df
        │     ↓
        │ raw/block-oriented display
        │
        └── df -h
              ↓
          human-readable display
```

## 5. Understand `-h` vs `-H`

Run:

```bash
df -h
```

Then:

```bash
df -H
```

The numbers may differ slightly.

Why?

They use different unit systems.

### `-h`

Uses powers of 1024.

Conceptually:

```text
1 KiB = 1024 bytes
1 MiB = 1024 KiB
1 GiB = 1024 MiB
```

### `-H`

Uses powers of 1000.

Conceptually:

```text
1 kB = 1000 bytes
1 MB = 1000 kB
1 GB = 1000 MB
```

The difference is presentation and unit convention.

Do not interpret:

```text
df -h
```

and:

```text
df -H
```

as contradictory storage measurements merely because their displayed numbers differ.

### Engineer Note

When comparing storage numbers from:

- Linux tools;
- cloud consoles;
- hardware vendors;
- storage vendors;
- monitoring platforms;

check the unit convention.

A number labelled "GB" in one place may not use the same base as a Linux command showing GiB-style human-readable units.

## 6. Query the Filesystem Containing a Specific Path

You do not always need every mounted filesystem.

Suppose the question is:

> Which filesystem contains this lab?

Run:

```bash
df -h .
```

Because:

```text
.
```

means the current directory, `df` reports the filesystem containing that path.

Now run:

```bash
df -h ~/linux-world-labs/JUN-035
```

Then:

```bash
df -h ~/linux-world-labs/JUN-035/data/report.txt
```

If those paths belong to the same filesystem, the filesystem-level capacity values should refer to that same containing filesystem.

This is extremely useful.

Instead of asking:

> Which row in a long `df -h` output matters for my application?

you can ask:

```bash
df -h /path/to/application
```

Conceptually:

```text
APPLICATION PATH
       │
       ▼
Which filesystem contains this path?
       │
       ▼
df /path
       │
       ▼
relevant filesystem capacity
```

### Important distinction

This:

```bash
df -h ~/linux-world-labs/JUN-035/data
```

does **not** mean:

> show me how much space the `data` directory consumes.

It means:

> show me capacity information for the filesystem containing `data`.

This distinction is essential.

## 7. Understand Mount Points Through Path-Based Checks

Run:

```bash
df -h /
```

Now:

```bash
df -h /tmp
```

Then:

```bash
df -h ~
```

Depending on your system, these paths may:

- all belong to the same filesystem;
- belong to different filesystems;
- involve memory-backed or container-specific storage.

Do not assume.

Observe.

Record:

| Path | Filesystem | Size | Used | Avail | Use% | Mounted on |
|---|---|---:|---:|---:|---:|---|
| `/` | | | | | | |
| `/tmp` | | | | | | |
| `~` | | | | | | |
| Lab path | | | | | | |

### Why this matters

Suppose an application writes:

```text
/var/lib/application/data
```

while its logs are stored under:

```text
/var/log/application
```

Those paths might be on the same filesystem.

Or they might not.

If only one filesystem is full, the operational impact depends on which paths use it.

Never assume:

```text
same server
=
same filesystem
```

A Linux system can have many mounted filesystems.

## 8. Inspect Filesystem Types with `df -T`

Run:

```bash
df -T
```

The:

```text
-T
```

option adds filesystem type information.

For a more readable view:

```bash
df -hT
```

You may see filesystem types such as:

```text
ext4
xfs
tmpfs
overlay
vfat
```

Your system may show others.

### Why filesystem type matters

Different filesystems can have different:

- allocation behavior;
- metadata structures;
- limits;
- administrative tools;
- recovery procedures;
- performance characteristics;
- capacity behavior.

At junior level, you do not need to administer all of them.

You do need to avoid assuming:

> Every row represents the same kind of storage.

### Example reasoning

If you see:

```text
tmpfs
```

recognize that this is not simply another conventional disk partition.

`tmpfs` is memory-backed and can use memory/swap according to system behavior and configuration.

If you see:

```text
overlay
```

you may be operating in a containerized environment where the storage view differs from a traditional standalone server.

Do not force every environment into a physical-disk mental model.

### Query the lab filesystem type

Run:

```bash
df -hT ~/linux-world-labs/JUN-035
```

Record:

```text
LAB PATH:

FILESYSTEM:

TYPE:

SIZE:

USED:

AVAILABLE:

USE%:

MOUNT POINT:
```

That is a useful evidence record.

## 9. Understand Block Capacity vs Inode Capacity

A filesystem can become unable to create new files even when the familiar block-capacity display does not look full.

One reason is inode exhaustion.

Run:

```bash
df -i
```

You should see columns resembling:

```text
Filesystem      Inodes  IUsed   IFree IUse% Mounted on
```

For the lab filesystem:

```bash
df -i ~/linux-world-labs/JUN-035
```

### What is being measured?

You learned about inodes in JUN-034.

Now connect that knowledge to filesystem capacity.

A simplified model is:

```text
FILESYSTEM CAPACITY
      │
      ├── data/block capacity
      │
      └── inode capacity
```

Regular `df` output focuses on filesystem block capacity.

`df -i` reports inode usage.

### Interpret the columns

```text
Inodes
→ total inode count reported
```

```text
IUsed
→ inodes in use
```

```text
IFree
→ available inodes
```

```text
IUse%
→ percentage of inode capacity in use
```

### Why inode exhaustion matters

Imagine a filesystem with free data capacity but no available inodes.

Creating another file requires filesystem metadata for that new object.

The result can be failure even though a block-capacity view appears to show available space.

This gives you two different "full filesystem" conditions:

```text
BLOCK EXHAUSTION
```

and:

```text
INODE EXHAUSTION
```

### First-response habit

When someone reports:

```text
No space left on device
```

do not inspect only:

```bash
df -h
```

Also consider:

```bash
df -i
```

You are asking two different capacity questions.

## 10. Compare Block and Inode Views for the Same Path

Run:

```bash
df -h ~/linux-world-labs/JUN-035
```

Then:

```bash
df -i ~/linux-world-labs/JUN-035
```

Record:

```text
FILESYSTEM:

MOUNT POINT:

BLOCK USE%:

INODE USE%:
```

Now reason about these possible states.

### State A

```text
Block Use% = 96%
Inode IUse% = 14%
```

Interpretation:

> Block capacity is under much greater pressure than inode capacity.

Do not claim inode exhaustion.

### State B

```text
Block Use% = 42%
Inode IUse% = 100%
```

Interpretation:

> Block capacity remains, but inode capacity is exhausted or effectively exhausted.

Creating new filesystem objects may fail.

### State C

```text
Block Use% = 98%
Inode IUse% = 97%
```

Interpretation:

> Both resources are under severe pressure and require investigation.

### State D

```text
Block Use% = 40%
Inode IUse% = 20%
```

Interpretation:

> Neither displayed resource appears close to exhaustion.

That does not prove every storage-related application problem is impossible.

It only tells you these particular filesystem-capacity indicators are not showing exhaustion.

This is an important engineering discipline:

```text
EVIDENCE
→ supports specific conclusions
```

not:

```text
ONE HEALTHY METRIC
→ proves entire storage stack is healthy
```

## 11. Filter and Focus `df` Output Safely

Full `df` output may include filesystems that are irrelevant to the immediate question.

The best first filter is often not a text-processing command.

It is the path itself.

Instead of:

```bash
df -h
```

followed by manually searching many rows, use:

```bash
df -h /path/to/application
```

when you know the affected path.

For example:

```bash
df -h ~/linux-world-labs/JUN-035/data
```

Then:

```bash
df -i ~/linux-world-labs/JUN-035/data
```

This immediately focuses both checks on the containing filesystem.

### Inspect by filesystem type

GNU `df` can also limit reporting to a filesystem type using:

```text
-t
```

For example, if your machine actually has an `ext4` filesystem:

```text
df -h -t ext4
```

Do not assume your machine uses `ext4`.

First inspect:

```bash
df -hT
```

Then choose a type that actually exists if you want to test the filter.

You can also exclude a type with:

```text
-x
```

For example:

```text
df -h -x tmpfs
```

This can reduce noise from filesystem types you do not need for a particular investigation.

### Caution

Filtering output is useful only when you understand what you are excluding.

Do not hide a filesystem simply because its type looks unfamiliar.

Investigate first.

## 12. Understand Why `df` Does Not Tell You Which Directory Is Large

Suppose:

```bash
df -h ~/linux-world-labs/JUN-035
```

reports that the containing filesystem is heavily used.

What has `df` proven?

It has shown filesystem-level capacity pressure.

What has it **not** proven?

It has not identified:

- which directory consumed the capacity;
- which application wrote the data;
- which file is largest;
- whether logs are responsible;
- whether backups are responsible;
- whether deleted-but-open files are involved;
- whether a particular user caused the growth.

This distinction prevents a common troubleshooting mistake.

Bad reasoning:

```text
df says / is 95% used
        ↓
/var/log must be the problem
```

Nothing in that `df` result proves that.

Correct reasoning:

```text
df says filesystem X is 95% used
        ↓
filesystem capacity pressure confirmed
        ↓
next investigation must identify what accounts for usage
```

That next step belongs primarily to **JUN-036 — Disk Usage with `du`**.

For now, stop at the correct boundary.

## 13. Understand Reserved Space and `Avail`

You may notice that filesystem numbers do not always satisfy a simplistic equation such as:

```text
Size - Used = Avail
```

exactly as expected from the displayed values.

Several factors can contribute:

- filesystem metadata;
- reserved blocks;
- rounding;
- unit conversion;
- filesystem implementation details.

Some Linux filesystems can reserve a portion of capacity for privileged/system use.

This can help preserve system operation when ordinary-user capacity is exhausted.

The important junior-level lesson is:

> Trust the filesystem-aware reporting rather than inventing your own availability calculation from rounded display values.

If:

```bash
df -h
```

reports:

```text
Size
Used
Avail
Use%
```

interpret those fields as the filesystem reports them.

Do not assume:

```text
100% Use%
```

has exactly the same operational meaning on every filesystem under every identity and configuration.

It is still a serious signal that requires investigation.

## 14. Pseudo-Filesystems and Memory-Backed Filesystems

Run:

```bash
df -hT
```

You may see entries that do not resemble ordinary disk partitions.

Examples can include:

```text
tmpfs
devtmpfs
overlay
```

depending on the environment.

### `tmpfs`

`tmpfs` is memory-backed storage.

Its capacity behavior is different from a conventional disk filesystem.

Do not see:

```text
tmpfs
```

and automatically conclude:

> That is another physical disk.

### Container environments

Inside containers, `df` may show:

```text
overlay
```

or other storage abstractions.

The filesystem view available inside a container may not map one-to-one to what a host administrator sees.

### Operational lesson

Always record:

```text
filesystem identifier
filesystem type
mount point
```

along with capacity.

Do not report only:

> Disk is 82% full.

A stronger statement is:

> The filesystem containing `/path/to/application`, mounted at `<mount-point>`, reports `<Use%>` block utilization.

That is precise evidence.

## 15. Controlled Failures and Troubleshooting

### Failure 1 — Looking at the wrong filesystem

Someone reports:

> The application cannot write to `/var/lib/app`.

You run:

```bash
df -h ~
```

and see plenty of space.

That does not prove `/var/lib/app` has capacity.

Check the affected path:

```bash
df -h /var/lib/app
```

when that path exists and you are authorized to inspect it.

**Root cause:** you checked the filesystem containing your home directory rather than the filesystem containing the affected application path.

---

### Failure 2 — Treating a directory argument as directory size

You run:

```bash
df -h ~/linux-world-labs/JUN-035/data
```

and see a large filesystem size.

You conclude:

> My `data` directory is that large.

Incorrect.

`df` reports the filesystem containing that directory.

It does not report the directory's own accumulated file consumption.

---

### Failure 3 — Checking only block capacity

Suppose an application cannot create new files.

You run:

```bash
df -h /application/path
```

and see available block capacity.

Do not stop there.

Check:

```bash
df -i /application/path
```

The filesystem could be under inode pressure.

---

### Failure 4 — Treating every row as physical disk storage

You see:

```text
tmpfs
```

and assume it is another disk partition.

Check:

```bash
df -hT
```

and interpret the filesystem type.

Different rows can represent different storage mechanisms.

---

### Failure 5 — Assuming high usage identifies the cause

You see:

```text
Use% = 94%
```

and immediately delete logs.

That is not evidence-based troubleshooting.

`df` has identified capacity pressure.

It has not identified the consumer.

Do not delete data until you know:

- what is consuming space;
- whether it is safe to remove;
- what depends on it;
- whether retention requirements apply;
- whether removal actually addresses the cause.

---

### Failure 6 — Comparing `-h` and `-H` as though one must be wrong

Different displayed values can result from:

```text
powers of 1024
```

versus:

```text
powers of 1000
```

Check the unit convention.

---

### Failure 7 — Assuming `df` is a disk-health test

`df` reports filesystem capacity information.

It does not by itself prove:

- the physical drive is healthy;
- storage latency is normal;
- the filesystem has no corruption;
- the storage controller is healthy;
- the application can write;
- I/O errors are absent.

Do not stretch the conclusion beyond the evidence.

## 16. The Junior Filesystem-Capacity Investigation Workflow

When an application reports a possible space problem, use a disciplined sequence.

### Step 1 — Identify the affected path

For example:

```text
/path/to/application/data
```

Do not begin with the entire server if the affected path is known.

### Step 2 — Check the containing filesystem

```bash
df -h /path/to/application/data
```

Record:

```text
Filesystem:
Size:
Used:
Avail:
Use%:
Mounted on:
```

### Step 3 — Identify the filesystem type

```bash
df -hT /path/to/application/data
```

Record:

```text
Type:
```

### Step 4 — Check inode capacity

```bash
df -i /path/to/application/data
```

Record:

```text
Inodes:
IUsed:
IFree:
IUse%:
```

### Step 5 — Interpret only what the evidence proves

Possible conclusion:

```text
The filesystem containing the affected path is under block-capacity pressure.
```

or:

```text
The filesystem has available block capacity but is under inode pressure.
```

or:

```text
Neither displayed block nor inode capacity appears exhausted.
```

### Step 6 — Do not guess the consumer

At this point, if block capacity is high, the next question becomes:

> What is consuming the space?

That is a different investigation.

Do not invent the answer from `df`.

## 17. Challenge Mode — Investigate a Filesystem Capacity Alert

You receive this alert:

> Storage warning: the application may be running out of space.

The affected path is:

```text
~/linux-world-labs/JUN-035/data
```

Your job is to investigate without deleting or modifying data.

### Task 1 — Identify the containing filesystem

Use a path-specific `df` query.

Record:

```text
FILESYSTEM:

MOUNT POINT:
```

### Task 2 — Record human-readable block capacity

Record:

```text
SIZE:

USED:

AVAILABLE:

USE%:
```

### Task 3 — Determine filesystem type

Record:

```text
FILESYSTEM TYPE:
```

### Task 4 — Inspect inode capacity

Record:

```text
TOTAL INODES:

USED INODES:

FREE INODES:

INODE USE%:
```

### Task 5 — Compare paths

Check:

```text
/
```

```text
~
```

```text
/tmp
```

and:

```text
~/linux-world-labs/JUN-035/data
```

Determine which paths share the same reported filesystem and mount point in your environment.

Do not assume they do.

### Task 6 — Interpret the evidence

Answer:

```text
Is the lab path under block-capacity pressure?

Is it under inode-capacity pressure?

What filesystem type contains it?

What mount point contains it?

Does df identify which directory is responsible for used capacity?

Can you conclude that logs are responsible?

Can you conclude that the physical storage device is healthy?

What is the next investigation if filesystem block usage is unexpectedly high?
```

### Evidence record

Document:

```text
INCIDENT:
Possible filesystem capacity issue

AFFECTED PATH:

FILESYSTEM:

FILESYSTEM TYPE:

MOUNT POINT:

SIZE:

USED:

AVAILABLE:

BLOCK USE%:

TOTAL INODES:

USED INODES:

FREE INODES:

INODE USE%:

BLOCK CAPACITY STATUS:

INODE CAPACITY STATUS:

WHAT df PROVES:

WHAT df DOES NOT PROVE:

NEXT INVESTIGATION:
```

### Challenge rule

Do not:

- delete files;
- use `sudo`;
- create large files to force the filesystem toward exhaustion;
- modify mounts;
- modify partitions;
- use `du`;
- claim a root cause that `df` does not prove.

The goal is accurate diagnosis, not manufacturing a dangerous full-disk condition.

## 18. Knowledge Check and Interview Practice

### Knowledge Check

1. **What does `df` primarily report?**  
   Capacity and usage information for filesystems.

2. **What does `df -h` do?**  
   Displays filesystem capacity using human-readable powers-of-1024 units.

3. **What is the difference between `df -h` and `df -H`?**  
   `-h` uses powers of 1024, while `-H` uses powers of 1000.

4. **What does `Used` represent?**  
   Used block capacity reported for the filesystem.

5. **What does `Avail` represent?**  
   Filesystem capacity reported as available for allocation under the filesystem's accounting and reservation rules.

6. **What does `Use%` represent?**  
   The reported percentage of filesystem block capacity in use.

7. **What does `Mounted on` tell you?**  
   The mount point where the filesystem is attached to the Linux directory hierarchy.

8. **What does `df -T` add?**  
   Filesystem type information.

9. **What does `df -h /some/path` report?**  
   Capacity information for the filesystem containing that path, not the size of the path itself.

10. **What does `df -i` report?**  
    Filesystem inode capacity and usage.

11. **Can a filesystem fail to create new files while block capacity remains available?**  
    Yes. One possible cause is inode exhaustion.

12. **Does high `df` usage prove which directory consumed the space?**  
    No.

13. **Does `df` prove that a physical disk is healthy?**  
    No. It is a filesystem-capacity reporting tool, not a complete storage-health diagnostic.

14. **Why might `Size - Used` not exactly equal displayed `Avail`?**  
    Filesystem accounting, reserved capacity, metadata, rounding, and unit presentation can affect the displayed values.

15. **Why is a path-specific `df` query useful during an incident?**  
    It identifies the filesystem that actually contains the affected application path and avoids drawing conclusions from an unrelated filesystem.

### Interview Practice

**What is the difference between `df` and `du`?**

`df` reports filesystem-level capacity and usage. `du` attributes space consumption to files and directories. If I am investigating whether a filesystem is full, I begin with `df`; identifying which directories account for usage is a separate step.

**How would you check the filesystem containing `/var/lib/myapp`?**

```bash
df -h /var/lib/myapp
```

assuming the path exists and I have access to inspect it.

**How would you identify the filesystem type as well?**

```bash
df -hT /var/lib/myapp
```

**How would you check inode capacity?**

```bash
df -i /var/lib/myapp
```

**What would you investigate if `df -h` shows available space but the application reports "No space left on device"?**

I would also inspect inode capacity with `df -i` and continue investigating other relevant storage conditions rather than assuming block exhaustion.

**Does 95% filesystem usage automatically mean files should be deleted?**

No. It indicates significant capacity usage, but I still need to understand the affected filesystem, operational thresholds, growth pattern, what is consuming capacity, and whether any data is safe to remove.

**Why can `df -h` and `df -H` display different numbers?**

They use different unit bases: powers of 1024 versus powers of 1000.

**What information would you record in a filesystem-capacity incident?**

At minimum, the affected path, filesystem identifier, filesystem type, mount point, size, used capacity, available capacity, block-use percentage, and inode-use percentage, along with the time of observation and the symptom being investigated.
